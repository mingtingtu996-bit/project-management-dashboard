# 验收时间轴模板 Seed 设计

## 背景

前期证照模板 seed 已经形成可复用模式：项目静态画像识别地区，地区 profile 提供省市规则，领域 seed 提供事项模板，后端合成 preview 和应用结果，前端只展示商业化模板明细与已生成的业务内容。

验收时间轴要复用这套能力，但不能照搬前期证照的办证流程展示，也不能把标准工序、专项工程中的过程验收全部搬进验收时间轴。验收时间轴主页面仍保持现有流程板、台账、详情抽屉逻辑；新增 seed 只负责自动预制竣工交付相关验收事项。

## 产品口径

验收时间轴 seed 生成的是“竣工交付验收事项包”，不是资料清单，也不是办理流程图。

一个项目的验收模板由三部分合成：

- 地区规则：复用前期证照的省市识别、官方来源、政策更新和城市 profile。
- 业态包：按项目业态触发住宅、商业办公、工业厂房、医疗学校公建等事项。
- 通用竣工交付包：所有房建项目常见的竣工验收、备案、档案、规划、消防等事项。

合成结果通常生成 10-30 个验收事项。每个事项是验收时间轴上的一个节点，节点内部挂接前置条件、资料清单、结果文件、牵头部门、地区办理方式和来源规则。

## 主页面边界

验收时间轴主页面不改成“倒推树”或“政务办理流程”。主页面保持现有产品形态：

- 流程板：展示验收事项、计划/实际时间、状态、依赖、卡点。
- 台账：维护事项、责任单位、日期、状态和批量编辑。
- 详情抽屉：处理单个事项的前置条件、资料、记录、联动任务、问题和风险。

模板应用后，主页面只看到生成后的验收事项和它们的状态，不暴露 seed 治理字段。

## 模板明细展示

模板明细弹窗采用“交付目标倒推”的展示逻辑，用于解释系统为什么生成这些事项，但不改变主页面信息架构。

展示内容包括：

- 交付目标：综合验收、竣工联合验收、交付使用备案或地区等效口径。
- 生成事项：本次会生成哪些验收节点。
- 结果文件：每个事项最终需要取得的合格意见、备案表、核实文件、准许使用文件等。
- 前置来源：来自任务列表、标准工序、专项工程、前期证照、图纸档案或人工补充。
- 资料门槛：每个事项需要准备的资料清单和可由系统自动挂接的资料来源。
- 地区/业态依据：显示业务化来源说明，不展示内部规则治理细节。

## 节点命名规则

节点名称必须是去重后的业务事项名。不能把同一个事项拆成多个名称相近的节点。

规则：

- 一个业务事项只生成一个主节点。
- 备案、核实、登记、开通、准许使用等差异作为节点属性，不另起节点。
- 地区叫法作为 `regionalDisplayName` 或办理方式，不改变 `canonicalType`。
- 办理方式、结果文件、资料清单可按地区和项目条件覆盖。

示例：

- 消防验收：内部可覆盖为消防验收、消防验收备案、抽查、告知承诺等办理方式。
- 人防验收：内部可覆盖为人防竣工验收、人防备案、易地建设证明等结果口径。
- 燃气验收：内部挂接燃气验收、开通确认或准许使用文件，不拆成燃气开通节点。
- 电梯验收：内部挂接监督检验和使用登记，不拆成两个时间轴节点。

第一版以“通用房建 + 商品住宅 + 商业办公 + 工业厂房 + 医疗学校公建”为覆盖范围。特殊业态后续扩展。

- 综合验收

- 消防验收
- 人防验收
- 档案验收
- 质量监督报告
- 节能验收
- 防雷验收
- 电梯验收
- 供水验收
- 供电验收
- 燃气验收
- 排水验收

- 环保验收
- 物业承接查验

## 城市核查口径

联网核查 10 个以上城市后，第一版不把所有城市差异固化为默认事项，而是将差异沉到城市 profile 和条件专项候选池。主干事项在各地基本一致，差异主要集中在市政公用、节水/海绵/水保、交通接驳、公众聚集场所消防安全检查、环卫设施、国家安全事项等。

已覆盖城市 profile：

- 北京市：联合验收主干 + 供热/通信/市政接入；公众聚集场所消防安全检查、环卫设施按商业运营或项目画像触发。
- 成都市：联合验收一件事 + 国家安全事项、水保、海绵等条件专项按项目画像触发。
- 济南市：供水、排水、节水/中水、电力、燃气、供热等市政公用设施完工条件进入城市规则。
- 青岛市：联合竣工验收 + 市政公用、水土保持、卫生、国家安全等条件专项。
- 重庆市：竣工联合验收主干 + 市政接入、交通/海绵/水保、公众聚集场所消防安全检查按项目触发。
- 福州市：联合验收主干 + 市政、海绵、交通、环卫设施按项目触发。
- 齐齐哈尔市：套用黑龙江省联合验收口径，北方供热作为城市默认配套，燃气/通信/水保按项目触发。
- 承德市：套用河北省联合验收口径，供热作为北方交付默认配套，燃气/通信/水保/交通按项目触发。
- 盘锦市：套用辽宁省联合验收口径，供热、燃气、市政配套作为城市默认项，水保/环卫按项目触发。
- 中山市：联合验收主干 + 市政公用配套，环卫/海绵/交通按项目触发。
- 达州市：套用四川省联办口径，水保、通信、交通、海绵按项目触发。
- 周口市：套用河南省联办口径，市政接入为默认，水保、交通、海绵按项目触发。
- 洛阳市：城市联办材料覆盖竣工阶段联合验收；商业公众聚集场所按项目画像触发营业前消防安全检查。

已新增省级共享 profile：

- 覆盖前期证照 seed 同口径的 31 个省级行政区：广东、江苏、浙江、上海、安徽、福建、江西、山东、北京、天津、河北、山西、内蒙古、辽宁、吉林、黑龙江、河南、湖北、湖南、广西、海南、重庆、四川、贵州、云南、西藏、陕西、甘肃、青海、宁夏、新疆。
- 城市精细 profile 仍优先命中；未单独覆盖城市或项目画像只提供省份时，回退到省级共享规则。
- 省级共享规则全部进入官方来源自动发布候选，来源域名通过 `gov.cn` / `*.gov.cn` 可信门禁后，低风险政策变化可形成可消费 overlay，避免未覆盖城市长期停留在全国通用口径。
- 省级共享规则只承担地区兜底，不替代后续城市精细化规则；重点承接市政公用、北方供热、燃气/排水/供电、海绵/水保/交通接驳等地区差异。

关键调整：

- 城市解析先匹配城市，再做省级兜底，避免“山东省”把青岛项目误命中为济南。
- `optionalIndustryCodes` 只表示适用业态，不再单独触发事项；必须命中项目关键词或地区 profile。
- 公众聚集场所消防安全检查是消防验收之后的运营准入事项，不拆成第二个消防验收。
- 环卫设施验收是交付/运营条件事项，只在生活垃圾、环卫配套、垃圾分类等画像命中时生成。

## 数据模型映射

模板应用写入现有验收五层模型：

- `acceptance_catalog`：事项类型目录，保存 canonical type 和地区显示名。
- `acceptance_plans`：验收事项节点，是主生成内容。
- `acceptance_dependencies`：事项之间的依赖和并联关系。
- `acceptance_requirements`：资料、证照、专项成果、任务事实等前置条件。
- `acceptance_records`：执行过程记录，不由模板默认预生成。

模板 seed 本身需要保存：

- canonical 事项定义
- 业态触发规则
- 地区覆盖规则
- 资料包定义
- 结果文件定义
- 部门/责任主体映射
- 来源挂接规则
- 自动更新来源元数据

## 与现有系统关系

标准工序 seed 和专项工程 seed 负责产生底层任务、过程验收、专项执行事实。验收时间轴 seed 不重复生成这些任务。

任务列表中的过程验收、隐蔽验收、检验批、分项分部验收、地基基础验收、主体结构验收等留在任务列表和 WBS 模板内。只有能支撑竣工交付的结果，才作为验收事项的前置条件或来源挂接进入验收时间轴。

前期证照 seed 的输出作为验收事项 requirement 使用，例如施工许可证、规划许可、用地相关证照、图纸审查结果等。地区 profile、官方来源更新链路与前期证照共享。

## 自动更新规则

自动更新沿用前期证照的安全口径：

- 可信官方来源通过后形成结构化政策快照。
- 政策正文先解析为验收事项、条件事项、结果文件、牵头部门、办理方式等结构化 facts。
- 结构化解析必须覆盖真实中文政策正文和常见 `gov.cn` HTML 正文提取，不以历史乱码样本作为唯一有效回归。
- 结构化 facts 与当前城市 profile / 事项池比对形成规则差异。
- 低风险新增验收事项、结果文件名称、部门别名、办理方式可自动发布为可消费 overlay 版本。
- 条件事项只进入 `applicabilityConditions` 或城市 optional 规则，不因为业态或政策文本中出现就默认生成。
- 涉及事项替换/删除、依赖顺序、交付条件、法定前置、结果文件替换、办理流程重大变化的高风险变化进入 blocked 候选版本，不静默覆盖已发布 seed。
- 业务 preview 只消费已发布 overlay 和 `profileVersion`，不向前端暴露 sourceSnapshots、structuredPolicyFacts、policyRuleDiffs、publishedRuleOverlay 等治理字段。
- 真实项目回放只用于校准候选建议，不直接静默修改发布版本。

当前实现链路：

- `acceptanceTemplatePolicyUpdateService`：负责官方源校验、正文提取、结构化解析、规则差异生成、自动发布计划和运行记录映射。
- `acceptanceTemplatePolicyAutoPublishJob`：每日调度可信源检查，可手动执行；通过 `gov.cn` / `*.gov.cn` 来源门禁后才允许自动发布。
- `acceptancePolicyReplayCalibrationService`：从已通过/已归档验收事项、结果文件 requirement 和项目静态地区画像中采集回放样本，对比模板 preview 的预期事项、结果文件和主管部门。
- `acceptanceTemplateService`：模板 preview 合入最新已发布 overlay，返回可消费 `profileVersion`，同时隔离治理详情。
- 成熟度守护测试覆盖事项池、条件 taxonomy、省级共享 profile、城市 profile、官方来源覆盖率、解析命中率、低风险自动发布和高风险阻断。
- 自动发布质量门禁额外覆盖真实中文官方政策段落和 `gov.cn` HTML 正文，确保事项、条件、结果文件、部门、办理方式能进入可消费规则差异。
- 当前空库阶段额外保留黄金回放基线，用于冷启动自动化回归；它不伪装成真实项目回放，真实项目校准仍由已通过/已归档验收记录持续补样。

## 验收适用条件确认

“验收适用条件确认”不在 seed 未成熟前做前端硬编码。第一阶段只由后端 preview 返回动态 `applicabilityConditions`：

- 条件项包括条件名称、影响事项、触发关键词、适用业态、默认建议、来源、确认问题和政策提示。
- 项目画像或城市 profile 明确命中的条件可默认选中；其余只作为候选确认项。
- 用户确认结果写回项目 metadata 的 `acceptanceTemplateApplicability.confirmedConditionCodes`，再由后端重新合成事项。
- 前端后续弹窗只渲染后端返回的条件项和状态，不维护独立选项字典。
- 该确认交互放在验收时间轴页面，不放进新建项目向导；向导不承担验收专项画像采集。
- 当前模板明细弹窗只展示地区、业态、模板版本、生成事项、结果文件和资料来源；在条件池未完成更多真实项目回放校准前，不新增完整“适用条件确认”勾选表，避免把 seed 缺口转嫁给用户确认。

## 验收标准

第一版完成后应满足：

- 后端能按项目地区和业态合成 10-30 个去重后的竣工交付验收事项。
- 每个事项包含结果文件、前置条件、资料清单、主管/牵头部门、地区办理方式和来源挂接。
- 前端主页面保持现有验收时间轴工作台逻辑。
- 模板明细弹窗能解释生成事项和资料来源，但不展示 seed 治理内部字段。
- 不把同一事项拆成多个节点，不把资料清单单独生成时间轴主节点。
- 与标准工序、专项工程、前期证照保持弱耦合挂接，不重复生成底层施工任务。
