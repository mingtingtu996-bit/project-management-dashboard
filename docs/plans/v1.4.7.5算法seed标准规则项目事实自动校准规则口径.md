## 0. 2026-06-01 final range-tree boundary (authoritative)

This v1.4-series plan follows the final range-tree model. There is no production history or existing user data that needs a compatibility layer.

Authoritative engineering object types are exactly: `phase / section / building / basement / floor / physical_zone / functional_area`.

The following compatibility surfaces are deleted and must not be reintroduced in runtime code, migrations, or frontend contracts:

- `zone / professional / subproject / custom` as engineering object types.
- `zone_object_id / professional_object_id` task fields.
- `project_materials.professional_object_id` and `engineering_categories.professional_object_id`.
- `legacy_object_type`, deprecated object-type arrays, legacy bridge/backfill helpers, and old scope adapter functions.
- `/api/scope-dimensions`, `scope_dimensions`, and `project_scope_dimensions` as active application surfaces.

Professional/system/domain/method semantics remain business facts through `specialty_type`, `engineering_category_id`, `standard_work_code`, template metadata, and project profile facts. They are not range-tree objects.

Any older section in this document that mentions deleted object types, deleted fields, old scope tables, or compatibility adapters is superseded by this boundary.
# v1.4.7.5 算法 seed 标准规则、项目事实与自动校准规则口径

## 1. Summary

v1.4.7.5 的目标不是继续扩充算法辅助 seed 的关键词数量，而是正式确立一套更适合真实施工现场和商业化产品的算法规则体系：

```text
标准规则层
项目事实层
自动校准层
```

本文件是 v1.4.7.4 的后续规则口径文件。v1.4.7.4 已完成算法辅助 seed、seed 版本治理、自动校核、自动发布、异常隔离和地区气候画像底座；v1.4.7.5 负责明确这些 seed 后续不得继续走“关键词字典无限膨胀”的路线，而必须升级为“标准工序编码驱动 + 项目事实优先 + 自动校准闭环”。

本文件不新增普通用户维护入口，不恢复人工审核发布，不要求用户手动维护算法规则。所有规则升级仍然由后端自动校核、自动发布、异常隔离和审计追溯完成。

后续口径优先级：`v1.4.22.3` 已将算法 seed、规则资产、模板、校准结果统一纳入公司隔离、自学习、冲突检测、回放评估和发布锚点治理。本文件中的“不恢复人工审核发布 / 自动发布”只表示不新增普通业务用户可见的算法审核发布前端，也不允许用户手工维护 seed；后续执行时，不得绕过 `v1.4.22.3` 定义的 `publish_anchor / automation_maturity`、公司作用域、回放、冲突和回滚门禁。明确要求人工治理锚点的资产，应进入后台治理或自动治理评审包，而不是由单个候选直接自动发布。

## 3. 核心判断

当前有效算法辅助 seed 已经可以作为算法辅助底座，但不能作为真实现场商业化产品的最终判断来源；本文件后续新增的气候画像、月度产能、工序季节敏感和候选治理口径，属于对早期 seed 的商业化收口。

历史遗留问题与当前收口状态：

```text
workflow_dictionary 仍大量依赖 predecessorKeywords / successorKeywords。
building_pattern 仍大量依赖 applicableKeywords。
process_constraint 仍大量依赖 keywords。
process_seasonal_sensitivity 已补 standardWorkCodes + 气候画像门控，keywords 只允许低置信兜底。
resource_class 仍大量依赖 keywords。
seasonal_productivity 已对齐 GB50176 热工气候区，north/east/south/west 只能作为地址缺失 fallback。
regional_climate_rules 已补全国省级兜底和重点城市画像，但市级精细化仍需通过候选治理持续扩展。
```

后续不允许通过简单补充更多关键词来解决这些问题。关键词越多，误判越多，且无法稳定解释为什么某个任务被某条规则命中。

v1.4.7.5 明确：关键词只能作为低置信兜底，不能作为算法主链路。

## 4. 三层规则体系

### 4.1 第一层：标准规则层

标准规则层是系统默认权威规则，来自：

```text
v1.4.7.2 分部分项标准库
标准工序编码 standard_work_code
WBS 模板节点 template_node_id
工程对象 engineering_object_id / phase_object_id / section_object_id / building_object_id / basement_object_id / floor_object_id / physical_zone_object_id / functional_area_object_id
任务类型 task_type
专业 specialty_type / engineering_category_id / standard_work_code
任务主对象 engineering_object_id
国家标准、行业标准、企业工法和系统公共 seed
```

标准规则层用于回答：

```text
这个任务属于什么标准工序？
这个工序在 WBS 中处于什么层级？
这个工序前后通常接什么工序？
这个工序是否存在工艺间歇？
这个工序是否受季节、天气、验收、资源影响？
这个工序应该按哪个工程对象粒度流水？
```

标准规则层必须可解释、可追溯、可版本化。

### 4.2 第二层：项目事实层

项目事实层优先于系统经验 seed。项目事实包括：

```text
任务列表显式依赖 task_dependencies
任务计划日期、实际日期、实际完成日期
任务实际进度快照 task_progress_snapshots
任务阻碍 task_obstacles
任务开工条件 task_conditions
材料到货事实 project_materials
验收计划、验收记录、验收流程状态
图纸、证照、审批、专项流程状态
项目气候画像 project_climate_profiles
城市天气预报 project_weather_forecasts
责任单位、项目成员、班组或专业分包事实
用户保存、确认、发布、修订形成的变更留痕
```

项目事实层用于回答：

```text
这个项目实际怎么干？
这个责任单位实际效率如何？
这个城市/月份/天气是否真实影响过工期？
这个验收类型在该项目实际等待多久？
用户是否反复把某类任务改成更长或更短？
任务显式依赖是否已经覆盖了系统建议？
```

项目事实层不得被系统 seed 覆盖。若系统 seed 与项目事实冲突，系统必须尊重项目事实，并输出冲突提示或降低规则置信度。

### 4.3 第三层：自动校准层

自动校准层负责把项目事实和公司历史变成可治理的候选规则。

自动校准的输入：

```text
已完成任务的计划工期、实际工期、偏差原因
同类任务的重复样本
用户反复调整的计划日期、依赖 lag、验收时间轴事实 / 历史观测、资源安排
项目关闭、月末关账、基线重编建议形成的稳定事实
公司级多个项目的同类任务统计
国家标准或官方日历更新
城市天气、停工、预警与实际进度影响的关联事实
```

自动校准的输出：

```text
algorithm_seed_upgrade_candidates
algorithm_seed_overrides
duration_suggestion_overrides
项目级 project override
公司级 company override
异常候选 quarantine
只读审计记录
```

自动校准不直接改写 `server/src/seeds/v1474*Seed.ts` 文件。TS seed 文件永远只是系统公共基础规则和离线兜底。

standard_work_duration 的自动校准必须按“三层事实”落地：

```text
第一层：真实项目样本。
只采集已完成、process 级、duration_bearing、有真实 actual_duration 的 duration_experience_samples；summary、activity_step、资料、复核、验收门禁、移交、等待类样本不得晋升为主工期候选。

第二层：项目画像上下文。
候选生成时必须携带 project_type_code、structure_type_code、method_variant_codes、element_variant_codes、typical_responsibility_role 等画像维度；没有画像时允许回退到标准工序 P50，但不能把无画像样本泛化成所有项目通用规则。
standard_work_duration seed 的冷启动记录必须同步具备可消费画像字段：`projectTypeDurationFactors`、`structureTypeDurationFactors`、`defaultDaysByMethod`、`elementVariantDurationFactors`。其中结构体系系数来自工序族 / 专项域规则，只对结构差异明确的承载工序写入；部位 / 系统变体系数只对地下、屋面、外墙、钢构、机电系统、设备机房、电梯井、洁净医疗、数据中心、专项防水等现场差异明确的工序写入，不得为了覆盖率强行给无明确差异的工序填泛化 factor。

第三层：公司级经验沉淀。
公司级 override 候选必须来自同一公司多个项目的稳定共性，默认至少跨 3 个项目且满足样本数、CV、confidence 门槛；通过 algorithmSeedCandidateDiscoveryService -> algorithmSeedAutoGovernanceService 自动发布为 algorithm_seed_overrides 后，才允许被 algorithmSeedResolver 消费。
```

标准工期自动校准的运行链路固定为：

```text
duration_experience_samples
-> algorithmSeedCandidateDiscoveryJob / algorithmSeedCandidateDiscoveryService
-> algorithm_seed_upgrade_candidates
-> algorithmSeedAutoGovernanceService
-> algorithm_seed_overrides(project/company)
-> algorithmSeedResolver
-> durationSuggestionService(new_task_reference)
```

未通过自动校核前，候选只能作为 candidate_only / quarantined / rejected / 诊断记录存在，不得影响新建任务参考工期、项目基线、月度计划或执行任务。

2026-06-13 工期体系收口后，`standard_work_duration` seed 和 override 只负责提供 `durationSuggestionService` 可解释的标准参考输入，不直接生成计划工期、施工生产日、偏差、延期、剩余工期、CPM 或父级 rollup 真值。所有被 seed 影响的运行期工期结果，必须先落到 v1.4.22 定义的三层体系：事实型 `inclusiveDurationDays / constructionCalendar`、推断型五引擎、派生型六输出。seed 候选、公司 override、项目 override 不得绕过该体系写入第二套 duration 字段。

模板 seed 回流候选必须同样遵守该边界：

```text
1. 主标准工序模板 seed 与专项 / 分区模板 seed 只提供任务事实、stableCode 和语义标记。
2. 真实项目对模板的修正、删除、补行、语义纠偏、场景确认和生成结果断言漂移,只能进入 wbs_template_* candidate 或 algorithm_seed_candidates 观察事实。
3. 场景特征确认回流必须携带 projectType、featureAssumptions、templateIds、generatedRowCount、retainedRowCount、featureSource。
4. 生成结果断言漂移必须携带 caseCode、assertionCode、missingStableCodes、unexpectedRuntimeEffects、governanceVersion。
5. 上述候选不得直接改 TS seed、不得直接写 task_dependencies、不得直接覆盖 standard_work_duration_seed,也不得在普通前端生成待办或审批流。
```

## 5. seed 覆盖优先级与 override 候选来源

v1.4.7.5 必须严格区分两个概念：

```text
seed 覆盖优先级规则：解决“算法最终读取哪一份规则”。
override 候选来源规则：解决“新的项目级 / 公司级覆盖规则凭什么产生”。
```

这两个概念不得混用。`project_override / company_override` 说明 seed 不是死数据，但它只回答覆盖优先级；它不等于任何项目事实都可以直接覆盖 seed。能否成为 override，必须经过候选生成、自动校核、自动发布或异常隔离。

### 5.1 seed 覆盖优先级

seed 覆盖优先级固定为：

```text
项目级 active override
公司级 active override
当前 active 系统 seed
TS 内置 seed fallback
```

含义：

```text
project_override 优先于 company_override。
company_override 优先于 active 系统 seed。
active 系统 seed 优先于 TS 内置 seed。
TS 内置 seed 只做离线兜底和系统基础版本。
```

项目级 override 只影响对应项目。

公司级 override 只影响对应公司及其项目。

系统级 active seed 是公共基础规则。

TS 内置 seed 文件不得在运行时被自动改写。

### 5.2 override 候选来源规则

override 候选必须来自真实、可追溯、可审计的数据来源，不允许大模型自由生成。

项目级 override 候选只能来自该项目的真实事实：

```text
已完成任务实际工期
用户反复调整后的稳定工期
真实验收时间轴等待观测
真实材料到货影响
真实阻碍影响
真实开工条件影响
真实天气 / 停工 / 预警影响
真实依赖 lag 调整
月末关账和基线重编建议中的稳定偏差解释
```

公司级 override 候选只能来自公司多个项目的稳定共性：

```text
同类任务跨项目实际工期
同类验收时间轴等待观测
后续人材机主数据落地后的同类资源约束表现
同类季节 / 地区影响
同类依赖调整规律
同类责任单位或专业分包稳定表现
```

系统级 active seed 候选只能来自：

```text
内置 TS seed 导入
gov.cn 官方节假日更新
国家标准 / 行业标准 / 企业工法更新
后端可信来源导入
已通过校验的系统公共规则版本
```

### 5.3 自动发布边界

2026-05-22 候选发布边界修正：

```text
standard_work_duration 是当前唯一允许在自动校核通过后写入 project/company override 的真实工期经验类 seed。
process_constraint、standard_internal_flow、cross_item_workflow、process_seasonal_sensitivity、seasonal_productivity、site_capacity_pressure、title_weak_recognition 默认保持 candidate_only / 后台治理事实。
这些规则的真实项目样本可以提升后台命中率、降低/提高预测置信度、形成企业标准库候选或隔离建议，但不得直接发布为运行期 override，不得直接写 task_dependencies，不得静默改 TS seed。
只有后续企业标准库管理后台或明确的 curated seed 发布流程确认后，才能把 candidate 转成正式规则。
```

不是所有候选都能覆盖 seed。

候选必须通过自动校核：

```text
样本数达到对应层级阈值
方差达到对应层级阈值
置信度达到对应层级阈值
有证据来源
不与标准规则冲突
不与显式项目事实冲突
stableCode 完整
candidatePayload 完整
```

通过后才能成为 active override。

不通过则进入：

```text
candidate_only
quarantined
rejected
```

禁止：

```text
低样本直接覆盖系统 seed
无证据来源直接发布 override
方差过高仍发布 override
低置信候选进入正式推荐
模型自由生成 override
人工审核发布前端入口
普通用户维护算法规则入口
```

默认自动发布阈值：

```text
项目级 override：
min_samples >= 5
CV <= 0.35
confidence >= 0.75
仅影响当前项目，且必须来自该项目已确认、已关账或已完成事实。

公司级 override：
min_samples >= 20
cross_projects >= 3
CV <= 0.30
confidence >= 0.80
必须来自同一公司多个项目的稳定共性。

系统 active seed：
cross_companies >= 3
cross_projects >= 10
min_samples >= 100
CV <= 0.25
confidence >= 0.85
经验类来源时效 <= 24 个月；国家标准、官方日历和现行规范按有效状态判断，不按 24 个月强制作废。

低置信门槛：
confidence < 0.60 -> candidate_only
0.60 <= confidence < 对应层级发布阈值 -> candidate_only，不进入正式推荐

异常隔离：
CV > 0.60 -> quarantined
与标准规则冲突且无可解释证据 -> quarantined
与显式项目事实冲突且无解释 -> quarantined
来源等级为 community / unknown 且缺少其他佐证 -> rejected
```

上述阈值是 v1.4.7.5 的保守默认值。后续如需调整，只能由 v1.4.16 数据质量与口径治理体系统一发布版本，不允许各 seed 模块自行改阈值。

### 5.4 override 时效与衰减

override 不得永久无条件 active。

```text
项目级 override：
随项目关闭归档，不再影响新项目。
如果绑定 phase / building / zone / subproject，则对应范围完成后进入 archived_candidate，只用于复盘和公司级候选。

公司级 override：
默认 review_cycle_days = 180。
连续 180 天无新样本刷新时 confidence 衰减 0.10。
连续 360 天无新样本刷新时降级为 candidate_only，除非来源是仍有效的企业工法或正式制度。

系统 active seed：
官方标准 / 官方日历 / 现行规范按有效期管理。
经验类系统 seed 默认 review_cycle_days = 365。
超过 review 周期未刷新时不得提升 confidence，只能保持或衰减。

learned_days：
按最近 24 个月滑动窗口计算。
最近 6 个月样本权重最高，超过 24 个月只用于历史复盘。
```

### 5.5 confidence 统一口径

`confidence` 取值范围固定为 0 到 1，保留两位小数。字段定义、审计留痕和质量等级归 v1.4.16 统一治理，本文件只规定算法 seed 的计算骨架。

默认计算骨架：

```text
confidence =
sample_score * 0.25 +
variance_score * 0.20 +
source_authority_score * 0.20 +
recency_score * 0.15 +
standard_consistency_score * 0.15 +
project_fact_consistency_score * 0.05
```

评分要求：

```text
sample_score：由 min_samples、cross_projects、cross_companies 决定。
variance_score：CV 越低分越高。
source_authority_score：按 source authority tier 取值。
recency_score：来源越新分越高，官方长期有效标准按有效状态计算。
standard_consistency_score：与 standard_work_code / template_node_id / 标准规则一致性越高分越高。
project_fact_consistency_score：与显式项目事实、验收流程轴、任务实际日期一致性越高分越高。
```

多源命中时：

```text
同一结论多源一致：按权重合成，可提升 confidence，但不得超过最高来源等级允许上限。
同一结论多源冲突：取较低 confidence，并生成冲突记录。
高权威来源与低权威来源冲突：高权威来源优先，低权威来源进入 candidate_only。
官方标准与项目事实冲突：项目事实不覆盖标准规则，只生成偏差解释或修订建议。
```

## 6. 规则匹配优先级

v1.4.7.5 之后，所有算法 seed 匹配必须遵守统一优先级：

```text
1. 显式项目事实
2. 项目级 active override
3. 公司级 active override
4. 标准工序编码 / WBS节点 / 工程对象 / 专业 / 任务类型
5. 当前 active 系统 seed
6. TS 内置 seed fallback
7. 任务标题 keywords 低置信兜底
```

解释：

```text
任务列表中用户显式设置的依赖永远优先于 workflow_dictionary。
项目验收流程轴中的真实验收状态、计划日期和实际日期优先于任务标题中的验收语义命中。
项目气候画像和天气预报优先于 seasonal_productivity 的粗区域经验。
若后续启用 resource_class，项目资源事实优先于 resource_class 的默认限制。
标准工序编码优先于 keywords。
keywords 命中只能作为 low confidence，不得静默 auto_apply。
```

### 6.1 同级仲裁规则

纵向优先级相同但多条规则同时命中时，必须按统一 tie-breaker 仲裁。

通用仲裁顺序：

```text
1. standard_work_code 精确匹配优先于 template_node_id。
2. template_node_id 精确匹配优先于工程对象 / 专业 / 任务类型泛匹配。
3. 工程对象范围更窄的规则优先于范围更宽的规则。
4. confidence 更高的规则优先。
5. source_authority_score 更高的规则优先。
6. active_version 发布时间更新的规则优先。
7. 仍无法仲裁时，不自动选边，进入 candidate_only 并写冲突记录。
```

scope_rule 仲裁：

```text
默认按更窄工作面优先：
same_floor / same_zone > same_unit > same_building > same_system > same_phase > same_project

若 same_system 与 same_building 同时命中，且任务专业为机电 / 消防 / 智能化 / 暖通 / 给排水 / 电气，则 same_system 可优先。
否则按工程对象层级更窄者优先。
```

workflow_dictionary 多命中：

```text
from_standard_work_code + to_standard_work_code 精确命中优先。
其次 template_node_id 对命中。
其次工程对象 / 专业 / 任务类型组合命中。
多条依赖均成立且不冲突时可以合并。
依赖方向冲突时，显式任务依赖优先；无显式依赖时进入 quarantined，不生成默认依赖。
```

process_constraint 多命中：

```text
hard_blocker 永远作为开工条件，不转成天数。
technical_interval / quality_evidence_wait / handover_wait 可以共同进入工期候选计算。
同一前置事项的多个等待天数取 max。
不同前置事项同时存在时分别保留，计划引擎按最晚可开工时间计算。
experience_buffer 只能在无更高等级约束时参与估算，且不得突破 minimum_days 下界。
```

显式依赖冲突处置：

```text
显式依赖与 workflow seed 冲突：显式依赖优先，记录冲突。
显式依赖与项目事实冲突，例如实际开工早于显式前置完成：项目事实优先，降低显式依赖置信度，并写入数据质量 / 计划健康记录。
```

## 7. 有效 seed 的新定位

### 7.0 通用 seed 字段扩展

v1.4.7.5 之后，seed 不再只是关键词和默认天数字典，而必须升级为可计算的行业规则对象。

所有参与工期计算的 seed 项，除已有字段外，统一补充以下通用字段：

```text
seed_rule_id: string
rule_version: integer
is_active: boolean
standard_work_codes: string[]

typical_responsibility_role:
  general_contractor
  labor_subcontractor
  specialty_subcontractor
  supplier_install
  third_party
  owner_direct

applicable_method_codes: string[]
default_days_by_method: Record<methodCode, number>

applicable_granularity:
  process
  operation
  both

default_days_p20: number | null
default_days_p50: number | null
default_days_p80: number | null

evidence_quality:
  source_type
  source_doc
  source_url
  evidence_source_keys
  last_review_date
  applicable_region_scope
```

字段含义：

```text
seed_rule_id：单条 seed 规则的稳定 ID，override、quarantine、审计和偏差解释必须指向具体规则，不得只指向整个 seed 文件。
rule_version：单条规则版本号。一条规则更新不得影响同 seed 文件内其他规则的 active 状态。
is_active：单条规则是否可被算法消费。resource_class 本轮必须显式 is_active = false 或等价跳过标记。
standard_work_codes：该规则关联的标准工序编码集合，是跨 seed 互联的第一主键。
standard_catalog_code_prefixes：该规则对照 v1.4.7.2 标准库的模板节点编码前缀集合，用于把 02-01-02-Pxx 这类可执行工序映射到工期 seed 或算法 seed；不得用它要求 seed 记录数量与标准库一一对应。
duration_coverage_mode：仅 standard_work_duration seed 必填，取值 direct / family_fallback / variant_split / external_support；用于说明该工期规则是单工序直接覆盖、工序族兜底、工法/构件变体拆分，还是非标准库支撑项。
coverage_rationale：仅 standard_work_duration seed 必填，说明为什么一条工期规则覆盖这些标准工序，或为什么该规则属于 external_support。
typical_responsibility_role：表示该工序通常由谁承担，用于 learned_days 按责任主体角色分桶，避免总包自营、劳务分包、专业分包和第三方检测互相污染工期样本。
applicable_method_codes：表示规则适用的工法集合，例如 aluminum_form_early_strip、large_form、wood_form、prefab。
default_days_by_method：仅当该规则确实受工法显著影响时必填，不允许为了填字段而编造工法差异。
applicable_granularity：表示规则适用于工序级、作业级或两者。粒度过粗的任务不得强行命中 seed，应进入拆分建议或低置信候选。
default_days_p20 / p50 / p80：仅地下相关 standard_work_code 强制填写三点估计；其他工序可继续使用 default_days / default_days_by_method。
evidence_quality：规则证据质量元数据，用于解释、审计、置信度计算和自动发布治理。
```

责任主体角色枚举：

```text
general_contractor：总包自营，常见于土建主体、总包直接组织施工。
labor_subcontractor：劳务分包，常见于钢筋、模板、砌筑、抹灰等劳务作业。
specialty_subcontractor：专业分包，常见于机电、幕墙、消防、智能化、精装修等。
supplier_install：供货带安装，常见于电梯、设备、部分防水材料、幕墙单元等。
third_party：第三方服务，常见于检测、监督检验、监测、专项测评等。
owner_direct：甲方直发包或甲供甲装事项。
```

通用执行规则：

```text
1. standard_work_code / template_node_id 命中后，必须先检查 applicable_granularity。
2. applicable_granularity 不匹配时，不得套用 default_days，只能输出建议拆分或低置信候选。
3. applicable_method_codes 为空表示不区分工法；不为空时必须与任务、模板或项目工法事实匹配。
4. default_days_by_method 优先于 default_days，但不得突破 minimum_days 下界。
5. 地下工序存在 p20 / p50 / p80 时，默认使用 p50；地质复杂、降水、支护、验槽异常等项目事实命中时可提升到 p80；条件顺利且有项目事实支撑时可使用 p20。
6. typical_responsibility_role 参与样本分桶和经验校准，不等于 resource_class，也不直接触发已确认资源冲突计算。
```

`resource_class` 本轮搁置不影响其他 seed 使用 `typical_responsibility_role`。前者是未来资源约束引擎，后者是当前工期估算所需的最低责任主体画像。

跨 seed 互联规范：

```text
1. 每条参与工期计算的 seed 规则必须挂 standard_work_codes 数组。
2. workflow_dictionary、process_constraint、process_seasonal_sensitivity 必须优先通过 standard_work_codes 互联。
3. 同一 standard_work_code 下的依赖、工艺约束、季节影响和验收时间轴事实必须能被统一聚合成一个工期计算上下文。
4. keywords 只能在缺少 standard_work_codes 时作为 legacy fallback，不得成为跨 seed 互联主键。
5. standard_work_codes 缺失的规则不得 auto_apply，只能进入 candidate_only 或低置信兜底。
```

standard_work_duration seed 与标准工序 seed 的关系：

```text
1. standard_work_duration seed 是标准工序 seed 的工期参数扩展层，不是标准工序 seed 的复制层。
2. 两者不做物理一一对应，不以记录数量相等作为验收条件。
3. 可执行 process / task 级标准工序必须能通过 standard_work_code、template_node_stable_code 或 standard_catalog_code_prefixes 找到 direct seed 或 family_fallback。
4. summary / division / sub_division 节点不强制配置独立工期 seed。
5. 同一标准工序多规则命中时，按 exact standard_work_code > longest standard_catalog_code_prefix > template_node_id > keywords 低置信兜底仲裁。
6. keywords 只能用于缺少标准工序编码时的低置信检索，不得绕过标准工序 seed 直接生成 baseDays。
7. 当前落地允许一套工序族基础规则生成多个 process_duration:<standardWorkCode> direct records；这不是要求所有 seed 与标准库物理一一对应，而是为了保证每个可执行 process 在 L0 冷启动阶段都有可解释 direct baseDays。
8. process_duration:<standardWorkCode> 的生成依据必须来自多源证据：全国 / 地方工期定额、国家 / 行业 / 地方标准、企业已验证经验和 v1.4.7.2 标准库结构；sourceVersion 必须标记为 multi_source_cold_start_2026 或后续同级版本。
9. 工序族 family_fallback 只能作为缺口兜底或生成 process direct records 的依据，不得在已有 direct seed 时覆盖具体 process。
10. activity_step 不是 standard_work_duration 的主 baseDays 粒度。generationDepth=activity_step 时，activity_step 必须由父 process 推荐工期拆分；子步骤 planned days 合计与 reference_duration 合计必须等于父 process。
10a. 父子计划汇总不属于 standard_work_duration seed 职责。division / sub_division / item_work / process 的父子日期包络、reference_duration 汇总、activity_step 拆分校验统一归 `wbsPlanRollupService`，不得散落在模板生成、任务编辑、计划提交、数据质量校验等模块各写一份。
10b. 父级计划跨度按子级最早开始到最晚完成的日期包络计算，不按子级工期简单相加；子级工期合计只作为 childReferenceDurationTotal / 工作量参考。只有 process -> activity_step 显式展开场景要求子步骤 planned days 与 reference_duration 合计等于父 process。
11. 如果 direct process seed 缺失、family_fallback 也无法解释，不得使用 keywords 或固定 7 / 14 天生成伪精确 baseDays，只能返回 data_pending / unavailable，并进入 seed 覆盖缺口治理。
12. process_duration direct seed 的冷启动精修必须以“工序族基准 + 标准工序顺序 + 工序名称动作信号”生成，而不是为每条工序手工泛化拍数；动作信号至少覆盖测量放线、材料复验、参数确认、主工作面施工、复杂长周期、养护/等待、检测/调试、验收/移交、资料归档、清理收口，并写入 benchmarkBasis / 审计解释。2026-05-18 后的商业级精修版还必须细分钢筋翻样/绑扎、模板深化/支架、混凝土浇筑/灌注、基层处理/找平、预留预埋、管道/风管/桥架/电缆安装、面层施工、土方回填压实、成孔/成槽清理、冲洗/消毒/通球、电缆端头、板缝/热桥/节点处理等现场动作族。
13. 商业级冷启动验收必须断言所有 process_duration:<standardWorkCode> 记录均带 processSignals，且不得以 catalog_default 作为最终命中解释；catalog_default 只能作为开发期缺口诊断信号，一旦进入可发布 seed 必须为 0。验收还必须校验 P20 <= P50 <= P80、fixedDays + variableDays = P50。
13a. 商业级冷启动验收必须断言 baseDaysEligible=true 且 defaultDaysP50<=1 的记录为 0；短周期现场动作如果是真实承载工序，应提升为可解释的 2 天及以上 P50，若只是复核、资料、移交、试验等待或质量门禁，则必须降级为 embedded_check / quality_gate / record_only / external_wait / handover_marker，不得保留 1 天主工期占位。
14. 高频工序必须允许 code-level 专家覆盖层精修基准工期，但覆盖层只能修正 `process_duration:<standardWorkCode>` 的 P20/P50/P80、fixedDays / variableDays、工程量基准和工法分桶，不得绕过 standard_work_code 生成新的关键词规则。
15. 领域专家画像必须覆盖所有 `process_duration:<standardWorkCode>`：地基基础、主体结构、钢结构、木结构、装饰装修、屋面、给排水、暖通、电气、智能化、节能、电梯等均必须有 `domainExpert`、`domainReason`、产能单位和工法系数，不得只靠工序族均值。
16. 工法变体必须由 `defaultDaysByMethod` 承载，并由 `algorithmSeedResolver` 在 `methodVariantCodes` 命中时消费；未命中工法时仍返回该工序的 P50 基准工期，不得返回 7 / 14 默认兜底。领域专家画像生成的工法桶可以覆盖所有 process，但具体工序专家覆盖层优先级高于领域画像。
17. 工程量 / 产能基准必须使用 `defaultQuantity`、`defaultQuantityUnit`、`quantityUnitHint`、`baselineProductivity` 表达；这些字段是 baseDays 的解释和后续规模缩放依据，不要求前端新增工程量入口，也不得在缺少工程量时阻断冷启动工期建议。所有 process direct seed 均必须有产能或默认工程量基准；不适合面积/体积/吨位的系统类工序可使用 system、point、shaft、pile、workface、building 等单位。
18. fixedDays / variableDays 必须按动作族校准：养护、检测、验收、资料、深化、材料复验等固定窗口占比更高；钢筋、模板、砌筑、抹灰、管线安装、面层等工作面施工可变占比更高。拆分后的 fixedDays + variableDays 必须等于 P50，并作为规模缩放边界，禁止把养护 / 真实验收时间轴等待观测整体按规模放大。
19. 典型模板链路必须反推校验：标准层主体、砌体、抹灰、屋面、给排水、暖通风管等代表链路的工序 P50 合计必须落在商业冷启动合理区间；activity_step 展开时只能由父 process 拆分，子步骤 planned days 与 reference_duration 合计必须等于父 process。
```

证据质量规范：

```text
source_type:
  national_standard
  industry_standard
  local_standard
  government_notice
  enterprise_practice
  project_history
  company_history
  system_default

source_doc：标准、规范、工法、项目复盘或系统规则名称。
source_url：可追溯外部来源 URL；内部企业工法或项目历史可为空，但必须有 evidence_source_keys。
evidence_source_keys：指向证据来源、导入任务、审计记录或项目事实的稳定键。
last_review_date：规则最近复核日期。
applicable_region_scope：nationwide、regional_list、city_list、project_only、company_only。
```

单条规则版本治理：

```text
1. seed 版本治理必须细化到 seed_rule_id + rule_version。
2. 一条规则更新只影响该 seed_rule_id 的 active 状态，不得导致整个 seed 文件重新发布。
3. project override / company override / quarantined / rejected 必须指向 seed_rule_id。
4. 自动校准候选必须记录 source_seed_rule_id；无来源规则的新候选必须生成新的 seed_rule_id。
5. 异常隔离只隔离单条规则，不得波及同 seed 文件内其他规则。
6. 偏差分析和项目总结引用 seed 时，必须能追溯到 seed_rule_id、rule_version 和 evidence_quality。
```

### 7.1 workflow_dictionary

旧定位：前后工序关键词词典。

新定位：标准工序 / 工序包关系的识别信号 + 兜底解释 seed。

职责边界固定为：

```text
1. 同一分项 / 同一标准工序包内部派生出的 process 顺序,由 v1.4.7.2 标准工序结构和生成器 internal_flow / sibling_sequence 承接。
2. 同一 process 下 activity_step 作业步骤顺序,由 v1.4.7.2 的 activity_step 层和生成器本地顺序承接。
3. workflow_dictionary 只保留识别信号、候选解释和缺少结构化编码时的兜底说明；不得直接作为模板生成写入 task_dependencies 的强规则层。
4. standard_work_duration seed 只承接工期参数,不得承接依赖关系。
5. 当前普通前端展示不因本边界调整新增页面、Tab、按钮或 seed 名称；原先有标准工序、依赖结果、业务原因就继续展示原结果。
6. 后端 metadata / 审计 / 调试日志可以保留 seed 命中信息,但普通业务 DTO 不暴露 workflow_dictionary、internal_flow、standard_work_duration_seed 等技术名。
7. algorithmSeedResolver 命中顺序固定为 standardWorkCode / templateNodeStableCode / standard_task_metadata 优先；只有缺少结构化标准工序上下文时,才允许使用 predecessorKeywords / successorKeywords 作为关键词兜底。
8. workflow_dictionary 内的历史关键词规则必须持续治理：同父级顺序迁入 standard_internal_flow；稳定跨分项 / 跨施工包主线迁入 cross_item_workflow；跨业务域约束引用迁入 dependencyIntentTemplates；自己不再保存运行期 lag 权威,defaultLagDays 统一为 0。
```

五规则统一体系口径：

```text
workflow_dictionary、standard_internal_flow、cross_item_workflow、dependencyIntentTemplates、process_constraint 统一归入“工程任务工序依赖与约束规则体系”。
这个体系负责把“识别工序关系、生成同父级本地顺序、生成跨分项 / 跨施工包主线依赖、生成跨业务域约束依赖意图、叠加工艺硬约束”串成同一条后端链路。

workflow_dictionary 是后台治理和迁移证据层；它可以提示“历史弱结构文本里这里可能存在工序衔接关系”,但只进入治理报告 / 候选迁移 / 审计,不进入运行期 workflow_sequence、基线生成原因、task_dependencies 或工期置信度。
standard_internal_flow 是同父级内部流层。
cross_item_workflow 是同分部 / 同工程对象下跨分项、跨施工包主线依赖层。
dependencyIntentTemplates 是跨业务域约束依赖意图层。
process_constraint 是工艺约束层。

### 7.2 building_pattern

旧定位：靠 applicableKeywords 判断建筑组织节奏。

新定位：基于工程对象树和 WBS 结构判断流水组织模式。

后续判定来源必须优先使用：

```text
楼栋数量
地下室 / 裙房 / 塔楼对象
连续楼层对象
单元对象
区域对象
系统对象
标准层重复工序
多楼栋同类工序并行关系
专项系统调试关系
```

文本关键词只能作为低置信兜底。

当前代码复核结论：

```text
1. 当前已有 v1474BuildingPatternSeed、algorithmSeedRegistry 字段规范化和 resolveV1474BuildingPattern。
2. resolveV1474BuildingPattern 目前仍以任务文本 / 标题 / 关键词匹配 applicableKeywords 为主。
3. baselineGenerationService 只消费 building_pattern 与任务事实 / cross_item_workflow 产生的运行期节奏信号；workflow_dictionary 不再进入 directSeedSignalCount、businessReasons 或 recommendation metrics。
4. 当前代码尚未基于工程对象树、WBS、standard_work_code 生成 building_pattern 主判断结果。
5. 当前代码尚未把 typical_section_count_range、typical_cycle_days_by_method、typical_parallel_crews、rhythm_expansion_eligible 用于新建 / 生成任务参考工期算法的实际节拍修正。
6. durationContextService 中的 resource_conflict 只能识别同楼栋、同责任单位、同类资源的时间重叠，属于候选风险 / 置信度影响，不等同于工作面 / 流水段排程算法。
7. 在没有班组能力、机械能力、材料到货、工作面容量和责任单位产能等精确数据前，不得把当前 resource_class 或 building_pattern 解释为精确工期计算能力。
```

可执行补充：

```text
1. 新增 buildingPatternResolver，输入工程对象树、WBS节点、任务集合，不以项目名称或任务标题作为主输入。
2. 识别组织模式时先读取 engineering_objects，再读取 template_node_id / standard_work_code，再读取任务重复结构。
3. 输出 patternCode、confidence、matchedEvidence、objectSequence。
4. 模式识别结果优先参与新建 / 生成任务参考工期的节奏因子、业务原因和置信度；模板生成顺序、默认依赖网络、基线和月计划只能复用其高置信稳定输出，不在本节另行展开。
5. 文本命中仅允许在缺少工程对象树和标准工序时作为 low confidence fallback。
```

building_pattern seed 专属字段：

```text
typical_section_count_range
typical_cycle_days_by_method
typical_parallel_crews
applicable_standard_work_codes
rhythm_expansion_eligible
```

字段规则：

```text
typical_section_count_range：典型流水段数或楼层段范围，例如 4-8 段、10-30 层。
typical_cycle_days_by_method：按工法分桶的单段 / 单层节拍，例如 aluminum_form_early_strip = 4-5、large_form = 5-6、wood_form = 6-8、prefab = 3-4。
typical_parallel_crews：典型并行班组数，默认 1；仅用于节拍展开，不等同于 resource_class。
applicable_standard_work_codes：该组织模式适用的标准工序编码集合。
rhythm_expansion_eligible：是否允许按节拍展开。改造工程、超高层复杂穿插、大型公建系统联调等不稳定模式可标 false。
```

节拍展开规则：

```text
rhythm_expansion_eligible = true 时，计划生成可以按 patternCode、typical_section_count_range、typical_cycle_days_by_method 和工程对象层级展开工期。
rhythm_expansion_eligible = false 时，不得机械套用标准层节拍，只能使用模板、经验工期或项目事实。
```

本阶段执行口径：

```text
1. v1.4.7.5 不要求实现精确工作面 / 流水段工期计算。
2. 当前阶段只要求服务新建 / 生成任务参考工期算法，识别“组织节奏是否可信”：单楼栋、多楼栋、地下室塔楼、标准层、机电系统、精装流水等。
3. 当工程对象和标准工序不足时，只允许输出低置信提示、数据质量问题或算法降级原因，不得强行改变推荐工期、基线、月度计划、任务日期或依赖。
4. building_pattern 可以影响新建任务参考工期的置信度、保守工期和业务原因；只有在节拍字段、工程对象层级和样本依据同时满足时，才允许进入 recommendedDurationDays 修正。
5. 标准层流水节拍展开只允许在显式楼层数组、rhythmExpansionEligible=true 且模板 metadata 已配置 floorDurationCurve / floorDurationCurveByMethod 时启用；不得泛化到所有楼层模板包。
6. 基线和月计划只复用 durationSuggestionService 的稳定输出，不在 v1.4.7.5 里另做排程或纳入算法。
7. resource_class 本轮继续按 §7.7 处理，不得通过 candidate_only 因子实际改变推荐工期、基线或月计划。
```

工作面 / 流水段缺口补齐任务：

```text
1. 新增 buildingPatternResolver 服务：
   输入 project_id、engineering_objects、template_node_id、standard_work_code、任务集合；
   输出 patternCode、confidence、matchedEvidence、objectSequence、fallbackReason。
2. 补齐 v1474BuildingPatternSeed 字段：
   typical_section_count_range、typical_cycle_days_by_method、typical_parallel_crews、applicable_standard_work_codes、rhythm_expansion_eligible。
3. 建立 building_pattern 与 workflow_dictionary 的关联：
   通过 applicable_standard_work_codes 连接标准工序顺序，不再只靠 applicableKeywords。
4. 新任务参考工期接入：
   durationSuggestionService 仅在 high confidence 且节拍字段完整时使用 building_pattern 调整参考工期；
   medium / low confidence 只能进入 businessReason、factorSummary 或 dataQualityReasons。
5. 基线 / 月计划复用边界：
   baselineGenerationService 和 monthlyPlanGenerationService 只能复用 durationSuggestionService 的稳定工期建议、置信度和业务原因；
   不得在本文件范围内另行消费低置信 building_pattern 去改写 planned_start_date / planned_end_date、纳入范围或任务依赖。
6. resource_conflict 纠偏：
   在 resource_class 未解冻前，resource_conflict 统一解释为“现场承载压力”，冷启动只做 observation / confidence_only；当存在计划窗口、责任单位、工程对象或同类任务事实时，允许作为 bounded candidate multiplier 影响新建 / 生成任务参考工期；
   当同一任务或重叠任务存在人员 / 设备 / 材料开工条件未满足、资源类阻碍未解除、关联材料到货逾期且持续超过阈值时，可增加 bounded extraDays 并降低置信度；
   不得表达为已确认资源冲突，也不得要求用户录入精确人材机数量；输出必须使用“现场承载压力 / 资源条件长期未满足 / 关联材料到货逾期”等业务化语言。
7. 测试补齐：
   覆盖工程对象树优先、关键词低置信兜底、节拍字段缺失降级、resource_class 不改工期、durationSuggestionService 不输出计划日期、不修改基线 / 月计划 / 任务依赖。
```

### 7.3 process_constraint

旧定位：强工艺约束关键词表。

新定位：工艺约束分层规则。

必须拆分为：

```text
hard_blocker：不满足不能开始
technical_interval：技术间歇
quality_evidence_wait：质量证据等待
handover_wait：移交等待
experience_buffer：经验缓冲
```

每条规则必须至少区分：

```text
minimum_days
default_days
learned_days
action_policy
confidence
source_standard
blocking_level
progress_impact
partial_overlap_ratio
applicable_scope_rule
time_nature
```

强约束不得只靠关键词触发，必须优先绑定标准工序编码或模板节点。

可执行补充：

```text
1. process_constraint seed 必须拆成 minimum_days、default_days、learned_days。
2. 计划生成时不得机械使用 1 天作为默认填充。
3. minimum_days 只代表规范、工艺或流程最低动作窗口。
4. default_days 代表系统冷启动建议，必须来自标准、企业工法或可追溯经验。
5. learned_days 代表项目/公司历史校准结果，优先级高于 default_days。
6. 如果只有 minimum_days 且缺少 default_days，生成时只能输出候选影响或待确认项，不得直接写死任务日期。
7. hard_blocker 不直接生成工期天数，必须转为开工条件或阻断项。
8. technical_interval / quality_evidence_wait / handover_wait 才允许进入工期候选计算。
9. 执行计划生成时不得临时全网搜索后直接填入 default_days。
10. 外部检索只能由规则更新任务生成候选，候选经自动校核发布后才能被计划生成消费。
```

阻塞与影响字段必须与运行时体系对齐：

```text
blocking_level:
  hard
  soft
  info

progress_impact:
  blocked
  partial
  warning
  none

partial_overlap_ratio:
  0.0-1.0，仅 progress_impact = partial 时必填，默认 0.5。

applicable_scope_rule:
  same_floor
  same_zone
  same_section
  same_building
  same_system
  same_project

time_nature:
  physical_constant
  process_waiting
  mixed
```

字段含义：

```text
blocking_level 回答“这条 seed 命中后能不能开工”，对齐 task_conditions。
progress_impact 回答“等待期间后续链能不能并行推进”，对齐 task_obstacles。
time_nature 表示等待时间性质，物理常数、流程等待或混合。
```

运行时映射：

```text
blocking_level = hard / soft / info 必须可直接映射为 task_conditions 的阻塞强度。
progress_impact = blocked / partial / warning / none 必须可直接映射为 task_obstacles 的进度影响。
seed 命中后如需生成条件或阻碍记录，只能生成 v1.4.8 已定义的 task_conditions / task_obstacles，不得新增 seed 专属提醒表。
```

典型标注：

```text
物理常数 + 全停：
blocking_level = hard
progress_impact = blocked
time_nature = physical_constant
例如混凝土养护、防水固化、保温干燥、结构胶固化。

物理 / 流程混合 + 局部并行：
blocking_level = hard
progress_impact = partial
time_nature = mixed
例如基础验收按楼层移交、防水闭水区域内 hard 区域外 soft、主体结构分段验收。

流程等待 + 几乎不阻塞：
blocking_level = soft
progress_impact = warning
time_nature = process_waiting
例如检验批资料、隐蔽资料整理、报告归档。

信息性资料提醒：
blocking_level = info
progress_impact = none
time_nature = process_waiting
例如混凝土试块送检资料提醒。
```

天数字段优先级：

```text
external_calendar_days > learned_days > default_days
minimum_days 不直接作为候选计算值，只作为下界 clamp。

如果 external_calendar_days 存在，例如官方日历、主管部门明确日期、验收流程轴明确排期，则优先使用 external_calendar_days。
如果 learned_days 存在且满足 confidence 阈值，则优先于 default_days。
如果只有 default_days，则作为冷启动工期计算值。
如果计算结果小于 minimum_days，则必须提升到 minimum_days。
如果只有 minimum_days，缺少 default_days / learned_days / external_calendar_days，则不得直接写死计划日期，只能生成待确认影响。
```

必须补充的约束类型：

```text
桩基检测等待。
地基验槽 / 基础验收时间轴节点。
基坑支护验收、监测稳定条件。
降水停止 / 回填前条件。
大体积混凝土测温、养护。
后浇带封闭条件。
防水基层含水率、闭水 / 淋水试验。
保温、涂料、腻子、地坪的温湿度和干燥条件。
幕墙结构胶 / 耐候胶固化。
门窗 / 幕墙淋水试验。
管道压力、灌水、通球、冲洗。
电气绝缘、接地、电缆试验。
消防联动、智能化联调。
电梯监督检验。
室外管网闭水 / 压力试验。
节能检测、室内环境检测。

### 7.5 work_calendar

本 seed 的业务口径是施工产能日历，不是管理人员考勤 / OA 工作日历。周末默认可施工，调休补班只作为官方公告来源信息保留，不改变现场有效施工天数；普通法定节假日默认只进入产能衰减和置信度解释，春节窗口才作为施工停工窗口影响有效施工日展开。

旧定位：年度节假日 seed。

新定位：官方日历事实。

work_calendar 是有效 seed 中自动调节机制最成熟的一个，应作为其他 seed 自动治理的参照范本：

```text
数据来源：gov.cn 官方节假日公告。
触发时机：每年 11-12 月官方发布次年节假日安排时。
路径：official_calendar_import 候选发现 -> 自动校核 -> 自动发布为 active seed。
治理：历史年度保留用于复盘，不删除。
```

规则：

```text
不得长期固定 2026 年。
必须按 gov.cn 官方公告自动导入。
必须按 date / year / month 命中。
不得跨年复用。
历史年度必须保留用于复盘。
seed 文件仅保留当前已通过自动校核的最近 1-2 年作为最小冷启动版本。
其余年份由 official_calendar_import 自动候选发现和自动发布机制维护。
seed 文件不接受手工添加未来年份。
```

每条日历记录必须补充结构字段：

```text
is_compensatory_workday: boolean
adjustment_origin:
  gov_announcement_url
  manual
  learned
calendar_kind:
  statutory_holiday
  compensatory_workday
  forecast_calendar_window
```

字段规则：

```text
is_compensatory_workday 仅用于标记官方调休补班来源信息。补班日不得改变有效施工日计算，也不得把周末默认改成停工日。
adjustment_origin 默认必须是 gov_announcement_url。manual 只能用于内部应急补录候选，不得直接发布；learned 只能用于复盘，不得覆盖官方公告。
calendar_kind 用于区分法定节假日、调休补班日和未发布年份预测日历。
调休补班日不参与管理工作日式排程，只保留为审计和来源追溯字段。
forecast_calendar_window 必须标记 webVerified = false、reviewNeeded = true、confidence = low，不得作为正式官方日历。
```

跨年与未发布年份规则：

```text
跨年项目必须按自然年拼接 work_calendar，不得把上一年节假日平移到下一年。
已发布年份使用官方日历实际数据。
未发布年份只能使用系统预测日历参与草案估算，必须标记 low confidence。
未发布年份预测日历不得用于 confirmed baseline / confirmed monthly plan 的最终确认。
次年官方日历发布后，系统生成基线重编建议或月计划修订建议，不静默回改已确认计划。
forecast_calendar_window 发布时不得触发已确认计划 pending_realign；只有 gov.cn official work_calendar 发布后才触发重整建议。
```

### 7.7 resource_class

旧定位：资源类型关键词分类。

### 7.8 验收时间归属

验收不再保留独立的未绑定候选 seed。系统不得凭任务标题、关键词或固定等待天数生成“验收等 3 天 / 7 天 / 15 天”一类假工期。

验收相关“时间”只保留三条正式来源：

```text
1. 工序本身需要做多久：
   由 standard_work_duration 管。验收、检测、复核、资料、移交类非承载动作必须通过 durationContributionMode 降级为 quality_gate / record_only / handover_marker / external_wait，不得给普通 baseDays。

2. 工艺上必须等待多久：
   由 process_constraint 管。例如养护、技术间歇、法定间隔、检测等待、明确工艺等待。它可以被工期算法作为 contextImpactDays / lag / confidenceDelta 消费。

3. 重大验收什么时间办、是否通过：
   由 v1.4.11 acceptance_plans / acceptance_records 管。这是验收时间轴事实源。执行中剩余工期算法只消费 planned_date / actual_date / status 作为 finish gate 或闭合事实。
```

开工条件、阻碍、资料缺失导致不能推进时，由 task_conditions / task_obstacles / external_readiness 管。工期算法可以消费这些执行事实形成 buffer、delayRiskIndex 或业务原因，但不得把它们转写成静态验收 seed。

同一重大验收在任务列表和验收时间轴同时可见时，后端以 `acceptance_plans` 为计划日期、实际日期、状态的单一事实源；任务侧保存计划完成日或完成状态时只同步同一条验收事实，不生成第二套口径。前端保持现有任务列表和验收时间轴展示方式，不额外暴露“投影、事实源、联动口径”等技术词。

模板生成只允许 `linked_projection`、`isAcceptanceMilestone` 或显式 `acceptanceLinkRule` 的重大验收节点自动落入 `acceptance_plans`；普通检验批、分项 / 分部验收、工序自检和资料复核只保留在任务、条件或标准工序语义中，不自动污染验收时间轴。

判定原则：只有重叠但推进正常时必须保持 low；重叠 + 同责任单位推进偏慢才进入 medium/high；多任务推进偏慢叠加条件/阻碍/材料长期未解决时可较强影响剩余工期和生成计划。
边界：candidate_only，不生成风险/问题/阻碍，不要求用户维护精确人材机数量，不称为已确认资源冲突。
自我升级：duration_experience_samples 与 task_duration_forecasts 中的 resource_conflict 观测可生成 site_capacity_pressure 候选，候选进入 algorithm_seed_candidates，不直接覆盖正式 seed。候选样本必须携带 resourceOperationType 与 durationImpactMode：纯 `resource_window_impact_only` 只能形成观察 / 降权 / 偏差解释候选；只有出现 `conditional_duration_candidate`、真实延误、预测额外天数或 multiplier 明显大于 1 的样本，才允许候选声明可影响新建任务参考工期。
```

## 8. 地区气候规则的新定位

`v1474RegionalClimateRuleSeed.ts` 不属于当前算法 seed registry，但它是 `seasonal_productivity` 的上游气候底座。

### 8.0 区域气候 / 季节效率 / 工序季节敏感三层关系

本节先固化三类规则的职责关系，后续再分别修规则内容和算法消费方式。三者不是并列规则，而是自上而下的分层关系：

```text
regional_climate_rules
  -> project_climate_profiles
  -> seasonal_productivity
  -> process_seasonal_sensitivity
```

业务问题对应关系：

```text
regional_climate_rules：这个项目在哪，属于什么长期气候环境。
project_climate_profiles：这个项目最终解析出的项目级气候画像是什么。
seasonal_productivity：这个项目在这个月份，现场整体施工效率是否下降。
process_seasonal_sensitivity：这个工序对当前气候 / 季节信号是否额外敏感。
```

职责边界：

```text
regional_climate_rules 只维护气候事实：
  climate_region
  thermal_zone
  rainy_season_months
  high_temp_months
  cold_weather_months
  typhoon_risk_level
  flood_season_months
  winter_shutdown_risk_level
  climate_tags
  confidence

regional_climate_rules 不维护：
  月度产能系数
  工序敏感系数
  工期天数

seasonal_productivity 只维护月度产能上下文：
  month_productivity_factor
  calendar_productivity_context
  monthly_climate_signal
  confidence_delta

seasonal_productivity 不维护：
  省市气候事实
  热工气候区定义
  工序级敏感原因

process_seasonal_sensitivity 只维护工序级放大反应：
  process_climate_sensitivity
  sensitive_months
  sensitivity_reason
  process_productivity_multiplier

process_seasonal_sensitivity 不维护：
  项目位置推断
  省市气候事实
  基础月度产能系数
```

落地约束：

```text
1. regional_climate_rules 是气候事实源，不得直接输出工期系数。
2. project_climate_profiles 是算法消费的项目气候画像，不要求普通用户手填气候参数。

## 10. 自动发布与隔离规则

延续 v1.4.7.4 的自动治理原则：

```text
不建设算法 seed 人工审核发布前端入口。
不允许普通业务用户人工通过 / 驳回 / 发布算法候选。
后端自动校核。
高置信自动发布。
异常候选自动隔离。
所有结果写审计追溯。
```

口径修正：这里的“高置信自动发布”必须服从后续 `v1.4.22.3` 的发布锚点和自动化成熟度。只有已声明可自动发布、作用域明确、证据 / 回放 / 冲突 / 回滚门禁齐备的候选，才能进入受控自动发布；命中人工治理锚点、样本不足、证据不稳或缺少作用域的候选，仍保持 `candidate_only`、隔离或后台治理评审包。

最低治理口径：

```text
项目级候选样本数不足时不得发布。
公司级候选样本数不足时不得发布。
缺少证据来源不得发布。
方差过高不得发布。
低置信不得发布。
与标准规则冲突且无解释不得发布。
与显式项目事实冲突时不得静默覆盖。
```

### 10.1 quarantine 恢复路径

候选状态必须可解释、可恢复、可归档。

```text
candidate_only：
由 algorithmSeedCandidateDiscoveryJob 在每次新样本进入、月末关账、项目关闭、官方来源更新时重新评估。
满足阈值后可升级为 active override / active seed。

quarantined：
默认每 30 天重新评估一次。
当新增证据、标准规则版本更新、项目事实修正、样本方差下降时可重新评估。
连续 3 次重新评估仍不达标，降级为 rejected。

rejected：
默认不再自动发布。
同一 stableCode 连续 rejected >= 3 次，进入 denylist_candidate。
denylist_candidate 只在官方标准更新或 stableCode 规则变更时重新打开。
```

quarantine / rejected 不需要人工审核入口，但必须保留只读审计记录，便于偏差分析和后续算法复盘。

### 10.2 冲突记录去向

seed 冲突不是独立前端提醒模块，必须进入统一治理记录。

```text
规则与标准冲突 -> 写入 v1.4.16 数据质量记录，类型 algorithm_rule_conflict。
规则与显式任务依赖冲突 -> 写入计划健康记录和数据质量记录。
显式依赖与项目事实冲突 -> 写入数据质量记录，降低显式依赖置信度。
规则被隔离 / 拒绝 -> 写入审计追溯记录。
```

前端展示边界：

```text
不弹单条 seed 提醒。
不生成待办。
只在偏差分析、项目总结、计划健康说明、月末兑现解释、基线重编建议、月计划修订说明中作为解释依据展示。
```

### 10.3 阻塞字段缺失兜底

`process_constraint` seed 项必须标注 `blocking_level` 与 `progress_impact`。

```text
未标 blocking_level 的 seed 项 -> 默认 blocking_level = hard。
未标 progress_impact 的 seed 项 -> 默认 progress_impact = blocked。

## 12. 与计划治理的关系

算法规则不得直接改变已确认基线或已确认月计划。

规则输出只能用于：

```text
生成草案
生成候选建议
解释偏差
降低或提升置信度
提示冲突
建议基线重编
建议月计划修订
辅助执行任务排程
```

规则不得用于：

```text
直接回改 confirmed baseline
直接回改 confirmed monthly plan
静默删除任务依赖
静默覆盖用户显式设置
静默改变任务范围归属
```

## 15. 季节规则商业化收口口径

本节为 2026-05-19 对 `regional_climate_rules`、`seasonal_productivity`、`process_seasonal_sensitivity` 的补充口径，优先级高于前文“7 类工序敏感场景”的早期描述。

### 15.1 分类关系

`regional_climate_rules.thermal_zone` 必须与 `seasonal_productivity.region_code` 优先对齐：

```text
severe_cold -> severe_cold
cold -> cold
hot_summer_cold_winter -> hot_summer_cold_winter
hot_summer_warm_winter -> hot_summer_warm_winter
mild -> mild
```

`plateau` 和 `desert` 允许保留，但只能标记为“施工运营扩展分类”，不得包装成 GB50176 原生热工气候区。`north/east/south/west` 只能作为项目地址无法解析时的粗 fallback，不得作为商业主链路。

当前商业化首版执行数字：

```text
regional_climate_rules：31 个省级兜底 + 100 个主要城市规则。
seasonal_productivity：8 个基础热工 / 施工运营分类 + 12 个施工气候子区，合计 20 个 regionCode。
seasonal_productivity records：20 × 12 = 240 条。
process_seasonal_sensitivity：19 条房建标准工序族规则。
```

`seasonal_productivity.region_code` 的实际消费不止 8 个基础分类。算法必须通过 `deriveV1474SeasonalProductivityRegion` 结合 `project_climate_profiles.thermal_zone`、`climate_tags` 和项目 location 兜底，推导到东北严寒、西北严寒、北方平原寒冷、沿海寒冷、长三角夏热冬冷、长江中游夏热冬冷、西南盆地、华南沿海、海南热带、西南温和高地、青藏高原、西北干旱等施工气候画像。

### 15.2 月度整体施工效率

`seasonal_productivity` 只表示月度宏观施工产能背景，不表示某个工序一定停工。

执行口径：

```text
法定节假日 / 春节停工 -> work_calendar
普通高温导致作业时长压缩 -> seasonal_productivity 轻度宏观折减
40℃级别或连续极端高温导致露天作业调整 -> 天气事实 / 项目事实
雨天导致外墙、防水等无法施工 -> process_seasonal_sensitivity
```

华南夏季不得再使用过重的静态月度折减。首版企业底座只保留 `0.93-0.95` 的宏观背景，强影响交给工序敏感、真实天气和项目事实。

### 15.3 工序季节敏感

```text

  屋面卷材/涂膜防水
  地下室外墙防水
  外墙抹灰、外墙涂料、外立面湿作业

雨季中影响 / 需要组织降效：
  土方开挖、回填
  基坑支护、降排水
  幕墙密封、外立面安装窗口
  室外道路与硬化

雨季轻影响 / 部分工序仍可施工：
  室外给水管网
  室外排水管网
  室外供热/综合管网
  桩基成孔、泥浆、弃土外运等配套环节

冬季低温影响：
  混凝土浇筑、养护、强度控制
  砌体、抹灰、找平等湿作业
  防水材料低温施工窗口

高温：
  不再作为静态工序敏感规则。
  高温只进入月度宏观产能或天气事实，不给单个工序静态 productivityMultiplier。

### 15.4 触发门控

### 15.5 自我升级

三类规则都必须可自我升级，但不能静默覆盖企业标准库：

```text
regional_climate_rules：
  输入：project_location_observations、project_weather_forecasts
  输出：project_climate_profiles 自动更新；城市 / 区县没有精确规则时，自动生成 regional_climate_rules 治理候选
  当前状态：候选写入 algorithm_seed_upgrade_candidates，seed_type = regional_climate_rules，status = candidate_only，frontendVisible = false
  发布边界：不自动发布、不前端展示、不静默覆盖 regional_climate_rules；后续企业标准库管理后台上线后再接审核和发布

seasonal_productivity：
  输入：duration_experience_samples 中的 thermal_zone / month / actual_start_climate_signal / planned_duration / actual_duration
  分组：thermal_zone + month
  输出：seasonal_productivity 候选，candidate_only_until_review

process_seasonal_sensitivity：
  输入：duration_experience_samples 中的 standard_work_code / climate_signal / month / planned_duration / actual_duration
  分组：standard_work_code + climate_signal
  输出：process_seasonal_sensitivity 候选，candidate_only_until_review
```

候选必须记录 `sample_count`、`p20/p50/p80 productivity`、`coefficient_of_variation`、`confidence_level`、`sample_ids`、`task_ids`。任何低置信候选不得进入正式推荐。

### 15.6 天气预报 / 预警接入链路

`project_weather_forecasts` 是近期天气事实，不属于长期气候规则，也不替代项目经理确认。

联网天气查询接入（2026-05-19 调整）：

```text
默认走中国大陆公开天气站点，不再默认依赖海外公开源：
  WEATHER_LOOKUP_PROVIDER=cma_public_weather
  WEATHER_LOOKUP_PROVIDER_FALLBACKS=cma_public_weather,smartweatherapi,generic,on_demand_web
  CMA_PUBLIC_WEATHER_BASE_URL=https://weather.cma.cn/api/weather/view
  OFFICIAL_WEATHER_STATION_ID_MAP_JSON 可补充企业项目城市 stationid；重点城市代码内置兜底
  ON_DEMAND_WEATHER_FORECAST_DAYS=10
  PROJECT_WEATHER_SYNC_INTERVAL_HOURS=3

中国天气网 SmartWeatherAPI 仅保留为企业后续可选授权通道：
  OFFICIAL_WEATHER_PROVIDER=smartweatherapi
  SMARTWEATHER_API_APP_ID / SMARTWEATHER_API_PRIVATE_KEY 由企业申请后配置
  OFFICIAL_WEATHER_AREA_ID_MAP_JSON 负责把项目 adminCode / 城市名映射到中国天气 areaid

generic 只保留为企业自定义天气接口兼容备份；Open-Meteo / on_demand_web 只保留为显式配置后的末级备选通道，不作为中国大陆商业默认源。

缺项目 city / province 或联网城市查询无结果时：
  syncProjectWeatherForecast 返回 degraded
  不生成 project_weather_forecasts
  不用默认天气伪造计划影响，算法回退到 seasonal_productivity + process_seasonal_sensitivity + project_history + execution_facts
  返回 algorithmFallback / providerConfidence 供算法降权消费，前端不需要额外展示数据源可信度
```

安全边界：

```text
cma_public_weather 只保存城市级天气查询结果，不保存用户经纬度或浏览器定位坐标。
on_demand_web 显式启用时同样只保存城市级天气查询结果。
SmartWeatherAPI 如果后续启用，签名 key 只用于请求，不写入 source_url / raw_payload。
project_weather_forecasts.source_url 只保留可审计的脱敏请求口径。
天气 provider 必须限定在 weather.com.cn / weather.cma.cn / data.cma.cn / cma.gov.cn / open-meteo.com 可信域名。
```

落库口径：

```text
cma_public_weather daily forecast -> forecast_date / min_temp_c / max_temp_c / wind_level / warning_tags。
on_demand_web forecast -> forecast_date / min_temp_c / max_temp_c / precipitation_mm / wind_level / warning_tags。
SmartWeatherAPI forecast_f -> forecast_date / min_temp_c / max_temp_c / wind_level / warning_tags。
天气现象代码统一转成业务 warning_tags，例如 大雨 / 暴雨 / weather_code:10。
降雨量字段存在时直接写 precipitation_mm；缺失时不硬推 precipitation_mm，只让 weatherForecastImpactService 根据 warning_tags 做候选影响。
```

执行链路：

```text
projectWeatherForecastJob 定时同步（默认每 3 小时）
-> 写入 project_weather_forecasts
-> weatherForecastImpactService 识别强降雨 / 极端高温 / 低温 / 大风预警
-> durationContextService 消费天气影响信号
-> 结合 process_seasonal_sensitivity 判断当前任务是否属于天气敏感工序
-> 输出 weather_forecast_impact 候选影响
-> 基线 / 月计划 / 任务排期算法可消费该候选影响
-> 进入计划修订候选或风险提醒
-> 用户确认后才允许改变已确认基线 / 已确认月计划
```

边界：

```text
强降雨：优先影响防水、外墙湿作业、土方、基坑、室外管网、室外道路等。
极端高温：只作为宏观作业时长压缩或天气事实，不写入静态工序季节敏感 seed。
低温：只影响混凝土、湿作业、防水材料等明确冬施工序。
大风：当前只降低置信度和进入观察信号，不建立全国统一工期系数。
天气影响默认 candidate_only，不静默回改 confirmed baseline / confirmed monthly plan。
```

### 15.7 v1.4.22.9 与模板 seed P1 补厚的边界（2026-05-22）

v1.4.7.2 在 `WBS_TEMPLATE_PROJECT_SCENARIO_COMBINATIONS`、`WBS_TEMPLATE_METHOD_VARIANT_EXTENSION_RULES`、`WBS_TEMPLATE_NODE_EVIDENCE_REF_OVERRIDES`、`WBS_TEMPLATE_GOLDEN_CASE_STRONG_ASSERTIONS` 中补厚的内容，不是新的工期 seed，也不是新的依赖 seed。

算法侧消费边界如下：

```text
项目类型场景组合：
  只作为模板推荐和一键生成组合建议。
  不产生工期系数，不产生依赖边，不覆盖 projectType 事实。

工法变体扩展规则：
  只在 confirmationFields / 工程对象事实明确时作为推荐或触发控制包。
  不允许 title-only 自动扩展。
  不写入 standard_work_duration，不写入 task_dependencies。

精确 evidenceRefs：
  只加强证据链、验收解释和治理报告。
  可供预览、筛选、资料/验收跳转解释使用。
  不作为工期锚点，不作为依赖锚点。

Golden Case 强断言：
  只作为回归保护，防止 planItemKind / durationContributionMode / executionNature / evidenceRefs 被误改。
  不参与运行时生成计算。
```

因此 v1.4.7.5 后续如果要吸收这些内容，只能通过已有算法 seed 类型做二次治理：

```text
standard_work_duration      负责工期经验与 duration family
workflow_dictionary         负责后台治理中的历史弱结构关系识别与迁移证据
process_constraint          负责已有边的约束增强
dependency_intent_template  负责跨业务域约束依赖意图
project_history 回流        只形成候选，不直接改模板 seed
```

模板 seed 仍然是基石事实层：提供任务、来源分区、计划行语义、执行性质、横切控制属性、证据引用和可推荐组合；算法 seed 才负责调节计算。

## 16. 执行边界

v1.4.7.5 不要求一次性重写全部算法。

允许分阶段执行：

```text
先把匹配优先级改正确。
再把 seed 结构字段补齐。
再逐个模块替换 keywords 主链路。
最后做自动候选发现和项目历史校准。
```

禁止分阶段执行时出现：

```text
继续扩大关键词作为主方案。
低置信候选直接进入正式推荐。
项目事实被系统 seed 覆盖。
任务列表显式依赖被 seed 静默改写。
验收、天气、资源事实被忽略。
```

## 17. 最终口径

v1.4.7.5 的最终判断：

```text
算法 seed 是系统基础知识，不是现场事实。
项目事实优先于系统经验。
标准工序编码优先于任务标题。
自动校准优先于人工维护。
异常隔离优先于错误发布。
显式用户计划优先于算法建议。
```

这套规则体系执行后，系统才能从“看任务标题猜规则”升级为“理解标准工序、读取项目事实、自动校准经验”的计划算法底座。

### 13.8 工期承载类型与非承载动作口径（2026-05-19 补充）

为避免“测量放线、材料复验、标高复核、验收复核、资料归档、移交确认”等现场动作被机械写成 1 天工期，v1.4.7.5 固化 `duration_contribution_mode` 作为模板 seed 与 `standard_work_duration` seed 的统一字段。

字段取值固定为：
