## 0. 定位

`v1.4.24` 不是新的业务体系，也不替代 `v1.4.23.1体系收口台账与验收门禁矩阵.md` 或 `v1.4.23.1-A体系收口台账与验收门禁矩阵.md`。

本文件必须按“可执行测试方案”使用，不得按普通清单阅读。大模型 / Codex 的执行顺序固定为：

1. 先读 `0`、`1`、`2.5`、`2.6`、`2.7`，建立事实边界、缺口矩阵、生产基线状态矩阵和依赖顺序。

3. 执行中参考 `4` 至 `12` 的 G0-G8 细则，参考 `15` 判断历史证据能否复用。
4. 最后由 `19.10` / `20` 输出 `v1424-release-decision.json` 和最终回答。

若执行方只阅读文件、不生成状态文件、不运行命令、不归档证据，只能给出“未执行 / 不可判定”，不能给出 `release-pass`、`production-ready` 或等价表述。

## 1. 上线放行结论规则

本轮发布只允许四类结论：

| 结论 | 含义 | 是否可上线 |
|------|------|------------|
| `release-pass` | G0-G8 全部通过，live / DB 证据已归档，关闭评估 `mayCloseAll=true` | 可以上线 |
| `release-pass-with-explicit-gates` | 本地、浏览器、迁移、核心 live smoke 通过；仅剩已明确降级的非主链能力，且 v1.5 / 对外入口不消费 | 可受控上线 |
| `release-blocked` | 任一 P0 / 安全 / 写链 / 迁移 / RLS / 认证 / Advisor / 回滚硬门禁未过 | 不可上线 |
| `display-only` | 仅允许展示或只读观察，不允许作为主指标、主结论、自动处置或后台写入依据 | 不可作为正式能力上线 |

禁止以下放行口径：

- 用 dry-run、截图、MCP 探查、影刀 / Yingdao RPA 手工回放替代自动化 pass。
- 用本地 mock、单元测试、一次 API 200 替代 live 写入回读、RLS、迁移治理或 Advisor 复扫。
- 用 `rowCount=0`、没有历史数据、控制台看起来为空作为物理删除依据。
- 用 Supabase 控制台 Healthy 替代 `migrate:check`、`migrate:diagnose`、`migrate:drift`、production governance evidence。
- 把 `allowValidate=true` 自动解释为可打开 warmup / scheduler / runtime publication。

### 2.7 企业交付门禁、业务连续性和依赖顺序

v1.4.24 必须区分“受控上线”和“企业客户正式生产交付”：

| 门禁 | 受控上线口径 | 企业正式交付口径 | 输出字段 |
|------|--------------|------------------|----------|
| SSO / MFA | 可 explicit gate，但必须声明不具备企业 IAM 完整能力 | 企业客户签约 / 安全审查前硬门槛 | `enterpriseReadinessGates.iam` |
| 密钥轮换 / 访问复核 | 可登记 hardening backlog | 企业安全审计前硬门槛 | `enterpriseReadinessGates.accessReview` |
| Tracing / SLO / SLI | 可 explicit gate，不能宣称完整可观测性 | 企业 SLA 承诺前硬门槛 | `enterpriseReadinessGates.observability` |
| 告警响应 / on-call / 升级路径 / 复盘 | 可 explicit gate，但必须有临时负责人和响应方式 | 正式生产运维前硬门槛 | `businessContinuityStatus.incidentResponse` |
| 备份恢复演练 | 若只受控上线，可列 `restore-drill-missing` gate | 生产数据承诺前硬门槛；只备份不演练不得视为通过 | `businessContinuityStatus.restoreDrill` |
| SLA / RTO / RPO / 灾备 | 可不对外承诺，但必须写明无 SLA 声明 | 对外合同 / 企业交付前硬门槛 | `businessContinuityStatus.sla` |

依赖顺序：

1. `PB-11 测试体系` 是元基线，先建立执行状态、证据目录和 source manifest。
2. 先闭合 `PB-01 身份与权限`、`PB-02 数据与存储`、`PB-03 配置与密钥`、`PB-06 安全`，这些是地基。
3. 再闭合 `PB-07 稳定性`、`PB-05 可观测性`、`PB-10 运维与支持`，确认系统扛得住、看得见、有人处理。
4. 再闭合 `PB-04 发布与回滚`，确认可以安全上下线和回退。
5. 最后闭合 `PB-08 容量与性能`、`PB-09 业务闭环`、`PB-12 合规治理` 及 PB-T01 至 PB-T04 类型基线。
6. 若前置地基为 `not-ready / blocked`，后续性能、业务闭环或商业化能力不得被单独判为完整 `production-ready`。

5. 真实环境矩阵执行前的状态应保持 `matrix_ready_execution_blocked_until_real_environment_handoff`；只有完成真实环境证据、验证器通过并归档后，具体场景才能从 blocked 改为 pass。

#### 2.8.1 身份、权限和多租户角色矩阵

`PB01-RLS-MATRIX-01` 是 PB-01、PB-06、PB-T01 的最低安全用例。必须在 staging 或可写 disposable live 数据上执行；本地 mock 或 service-role 直连只能辅助定位，不能关闭该用例。

| 角色 | 同租户读 `GET /api/projects/:id` / `GET /api/dashboard/company-summary` | 同租户写 `POST /api/projects` / `POST|PATCH /api/projects/:id/tasks` | 跨租户读 | 跨租户写 | 未登录 |
|------|--------------------------------------|----------------------------------------|------------|------------|--------|
| owner | 200，返回同 company/project 数据 | 200/201，写入后可回读并可清理 | 403/404，不能泄露对象存在细节 | 403/404，不产生行 | 不适用 |
| company_admin | 200，只返回本 company | 200/201，仅本 company | 403/404 | 403/404 | 不适用 |
| project_admin / editor | 200，仅授权 project | 200/201，仅授权 project；越过 project/company 必拒绝 | 403/404 | 403/404 | 不适用 |
| viewer | 200，仅授权 project / company 读 | 403，不产生写入 | 403/404 | 403/404 | 不适用 |
| anon | 不适用 | 不适用 | 不适用 | 不适用 | 401；无 token 时不得返回业务数据 |

输入：

- `sameCompanyIdRef`、`sameProjectIdRef`、`crossCompanyIdRef`、`crossProjectIdRef`。
- `ownerTokenRef`、`companyAdminTokenRef`、`editorTokenRef`、`viewerTokenRef`、`anon/noToken`。
- 至少覆盖项目、任务、公司摘要、团队/成员或邀请中 1 个读写面。

预期：

- 所有跨租户读写都必须拒绝，且无业务行写入。
- viewer 不能写；anon 不能读写。
- 拒绝响应必须是 401/403/404 之一，不能 500。
- 证据必须含请求矩阵、状态码、响应摘要、DB readback、cleanup 记录。

失败判定：

- 任一跨租户读到数据、任一越权写成功、任一拒绝路径 500、任一写入没有 cleanup/readback，均为 `FAIL`。
- 只跑 owner happy path 或只跑 local mock 时，状态为 `missing-live`。

#### 2.8.6 现有测试去伪规则

对现有 516+ 测试和 browser/diagnostic scripts，必须输出 `v1424-false-green-audit.json`。以下情况必须标为 `suspect-fake-green` 或 `supporting-only`：

| 去伪项 | 判定 |
|--------|------|
| `describe.skip`、`it.skip`、`test.skip`、`.only` | 不得关闭任何 release gate；`.only` 出现在待执行测试集中为 G1 fail |
| `describeIfConfigured` 或缺 env 自动 skip | 对应能力为 `missing-env / not-executed`，不能算 pass |
| `mock-api`、`mock-api-browser`、`mock-api-production-build`、`route.fulfill()` mock 后端 | 只能证明 UI 渲染或脚本稳定，不能证明 G3/G5/G6/G7 |
| `vi.mock('../middleware/auth')`、`DISABLE_PERMISSION_SYSTEM=true`、`VITE_DISABLE_PERMISSION_SYSTEM=true` | 只能证明局部逻辑；不能证明认证、RLS、多租户或生产权限 |
| `dryRun=true`、`commandsExecuted=0`、`manual-assisted-only`、`operator://current-thread` | 不能关闭 live closeout、runtime publication、rollback、压测或生产证据 |
| 只断言文件存在、schema 存在、rowCount=0 | 不能证明行为闭环；必须补 readback、依赖、消费者观察和 cleanup |
| 只测候选、shadow、report-only、candidate-only 路径 | 不能证明 production-ready 或主链消费 |

若 `v1424-false-green-audit.json.summary.status=review-required`，G8 不能只因 `v1424-release-decision.json` 成功生成而视为无条件通过；必须把命中数量、`suspect-fake-green` 数量、`supporting-only` 数量写入 `downgradedCapabilities` 或 `mustRerunBeforeProduction`，并同步到 PB-11 测试体系基线。只有完成复核并证明这些测试没有被用于关闭 production gate 后，才允许移除该显式门。

状态更新规则：

- 每开始一个 gate，先把该 gate 写为 `running`。
- 每条命令执行后，立即追加 command result。
- 任一命令失败，不得继续把该 gate 判定为 pass；若后续命令仍可提供诊断，可继续执行但最终 gate 为 `fail`。
- 执行中断后，下一模型必须从 `v1424-execution-state.json` 恢复，不得从头猜测。

## 17. Source Manifest 生成规范

### 17.1 必须生成的文件


`v1424-source-manifest.json` 是 G0 的硬证据。没有该文件，G0 必须为 `fail`。

### 17.2 扫描命令

执行方必须同时记录：

- `docs/plans/v1.4*` 和 `docs/plans/v1.5*` 的路径清单。

### 17.3 分类规则

每个路径必须分类为以下之一：

| 分类 | 定义 | 默认 gate |
|------|------|-----------|
| `release-source` | 会进入产品运行时或部署包的源码 / 配置 | G1-G8 |
| `test-source` | 测试、guard、验证脚本、测试夹具 | G1 / G4 / G5 / G6 |
| `migration` | 数据库 migration、schema、seed、migration 脚本 | G2 / G7 |
| `release-doc` | v1.4 / v1.5 / release / runbook 文档 | G0 / G8 |
| `evidence` | 报告、截图、诊断输出、测试结果 | G0 / G8 |
| `generated` | 构建产物、临时生成文件、导出资产 | G0，默认不进入发布源码 |
| `dependency-cache` | `.pnpm-store`、node_modules 类缓存 | G0，必须排除 |
| `local-temp` | `tmp/`、临时脚本、一次性截图、scratch 文件 | G0，必须排除或归档 |
| `secret-risk` | env、key、token、DB URL 相关文件 | G7，必须人工复核 |
| `unknown` | 无法自动判断 | G0 fail，必须人工分类 |

### 17.4 路径到 gate 的最低映射

| 路径模式 | 最低分类 | 必须 gate |
|----------|----------|-----------|
| `client/src/**` | `release-source` | G1、G4；涉及 auth / project / dashboard / company / planning 时加 G3 |
| `client/package.json` / lockfile | `release-source` | G1、G4、G6 |
| `server/src/routes/**` | `release-source` | G1、G3、G7 |
| `server/src/services/**` | `release-source` | G1；涉及 DB / BI / runtime / duration / write chain 时加 G2/G3/G5/G7 |
| `server/src/jobs/**` | `release-source` | G1、G5、G7、G8 |
| `server/src/scripts/**` | `test-source` 或 `release-source` | G1、G2、G5、G7，按脚本能力判定 |
| `server/migrations/**` | `migration` | G2、G7 |
| `server/src/__tests__/**` | `test-source` | G1 |
| `scripts/verify-*browser*.mjs` | `test-source` | G4 |
| `scripts/check-*performance*.mjs` | `test-source` | G6 |
| `project-testing/**` | `test-source` 或 `evidence` | G0、G5、G8 |
| `project-ui/**` | `evidence` 或 `release-doc` | G0、G4 |
| `project-search/**` | `evidence` | G0、G8 |
| `.github/workflows/**` | `release-source` | G1、G2、G7、G8 |
| `deploy/env/**` | `secret-risk` 或 `release-source` | G3、G7、G8 |
| `tmp/**` / `.pnpm-store/**` / `generated_assets/**` | `local-temp` / `dependency-cache` / `generated` | G0 exclude |

判定规则：

- 任一 G0 / G1 / G3 / G4 / G7 为 fail，最终必须 `release-blocked`。
- G2 缺 Advisor rescan/export，最终不能是无条件 `release-pass`。
- G5 / G6 deferred 时，只能在对应能力不被主链消费且有明确降级时给 `release-pass-with-explicit-gates`，并必须写入 `explicitGateSummary.deferredGates`。
- 存在 P0 blocker 时，最终必须 `release-blocked`。
- 任一 gate 为 `blocked / fail / deferred` 时，必须在 `openBlockers`、`downgradedCapabilities`、`mustRerunBeforeProduction`、`productionGapMatrix` 或 `productionBaselineMatrix` 中有对应解释；缺解释时按假绿处理，并自动补入 release blocker。
- 存在任一非 P0 blocker、deferred gate、`downgradedCapabilities` 或 `mustRerunBeforeProduction` 时，最终不得为无条件 `release-pass`；若不是 `release-blocked`，只能是 `release-pass-with-explicit-gates`，且 `explicitGateSummary.status` 必须为 `explicit-gates-present`。
- `explicitGateSummary.status=none` 只允许在所有 gate 为 `pass / not-applicable`、`openBlockers=[]`、`downgradedCapabilities=[]`、`mustRerunBeforeProduction=[]` 时出现。
- `productionBaselineMatrix` 缺任一 PB 行，最终必须 `release-blocked`。
- 任一 PB 行为 `not-ready` 且涉及主链消费，最终必须 `release-blocked`。
- 任一 PB 行为 `needs-gating / explicit-gate`，必须在 `openBlockers`、`downgradedCapabilities`、`mustRerunBeforeProduction` 或 `explicitGateSummary` 中有对应解释。
- `executionMode=enterprise-production-delivery` 时，`enterpriseReadinessGates` 或 `businessContinuityStatus` 任一硬门槛为 `missing / explicit-gate / restore-drill-missing / no-external-sla-claim`，最终必须 `release-blocked`。
- `executionMode=controlled-launch` 时，上述企业或业务连续性缺口可以进入 explicit gate，但最终不得声明“完整生产级企业交付能力”。

## 21. 大模型续跑规则
