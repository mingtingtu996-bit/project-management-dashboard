## 0. 2026-06-01 final range-tree boundary (authoritative)

This v1.4-series plan follows the final range-tree model. There is no production history or existing user data that needs a compatibility layer.

Authoritative engineering object types are exactly: `phase / section / building / basement / floor / physical_zone / functional_area`.

The following compatibility surfaces are deleted and must not be reintroduced in runtime code, migrations, or frontend contracts:

- `zone / professional / subproject / custom` as engineering object types.
- `zone_object_id / professional_object_id` task fields.
- `project_materials.professional_object_id` and `engineering_categories.professional_object_id`.
- `legacy_object_type`, deprecated object-type arrays, legacy bridge/backfill helpers, and old scope adapter functions.

Professional/system/domain/method semantics remain business facts through `specialty_type`, `engineering_category_id`, `standard_work_code`, template metadata, and project profile facts. They are not range-tree objects.

# v1.4.12 风险问题预警升级体系执行方案

## Summary

v1.4.12 的目标是把当前应用中已经存在但口径分散的 `预警 / 风险 / 问题 / 通知 / 阻碍升级 / 条件过期 / 验收逾期 / 证照风险` 收口成统一的异常治理链。

本章不重做 RiskManagement 页面，不把所有健康横幅、数据质量提示和系统异常都塞进风险问题工作台。它只治理业务异常链路：

```text
预警：系统发现的业务风险信号，提醒用户关注，不代表已经形成正式风险或问题
风险：可能影响项目目标的不确定事项，可人工登记，也可由预警升级生成
问题：已经发生、需要跟踪处理的确定事项，可人工登记，也可由风险、阻碍、条件、验收等上卷生成
升级：系统按稳定规则把长期未处理或事实恶化的信号上卷到更高治理层级
关闭：来源事实解除、任务完成或人工确认后，系统自动降级 / 待确认关闭 / 关闭
```

本章主线必须明确为“预警链”，风险和问题是预警链在不同严重程度下的上卷结果，不再把预警当作一次性通知或前端提示。

```text
业务事实变化 -> 预警生成 / 去重 / 生命周期记录 -> 已知悉 / 静音 / 自然解除 / 转风险 -> 风险跟踪 -> 问题闭环
```

本章继续沿用 v1.4.8 之后的统一原则：

```text
用户维护业务事实，系统判断治理语义
能由系统自动识别、匹配、归集和提示的，不新增弹窗或必填项打断现场录入
普通前端不展示 source、lineage、confidence、mapping_reason、chain_id 等治理字段
用户最多填写标题、类型、描述和必要状态，升级、去重、来源、统计、关闭建议由系统处理
```

## Business Definitions

### 1. 预警

预警回答：

```text
系统发现了一个可能影响项目执行的业务信号，是否需要用户知悉或后续上卷？
```

预警特点：

```text
主要由系统生成
来源可以是任务、条件、阻碍、验收、证照、图纸、关键路径、进度趋势
用户不需要填写预警
项目编辑者可以治理已知悉、治理静音、转为风险
来源事实解除后，系统自动关闭或降级
长期未处理且未被项目编辑者治理已知悉 / 治理静音时，可自动升级为风险
```

预警不等于问题。

```text
预警只是信号
风险是可能发生的影响
问题是已经发生或需要处理的确定事项
```

### 2. 风险

风险回答：

```text
这个事项是否可能影响项目目标，需要提前管理？
```

风险来源：

```text
manual：人工登记
warning_converted：用户从预警确认转入
warning_auto_escalated：预警长期未处理后自动升级
source_deleted：来源已删除的兼容兜底
```

风险状态：

```text
identified：已识别
mitigating：处理中
closed：已关闭
```

风险用户操作：

```text
新建风险：用户填写标题、描述、级别即可
转为问题：用户确认该风险已经变成需要处理的问题
关闭风险：用户确认风险不再需要跟踪
确认关闭：仅当系统发现来源事实已解除并标记建议关闭时出现
保持跟踪：仅当系统建议关闭但用户判断仍需继续跟踪时出现
重新打开：仅在已关闭风险详情或已关闭筛选结果中出现，用于恢复误关或重新发生的风险
```

### 3. 问题

问题回答：

```text
这个事项是否已经影响执行或已经形成确定待办，需要持续处理到关闭？
```

问题来源：

```text
manual：人工登记
risk_converted：风险人工转入
risk_auto_escalated：风险长期未处理后自动升级
obstacle_escalated：阻碍上卷
condition_expired：开工条件或验收逾期上卷
source_deleted：来源被删除后的兼容兜底
```

问题状态：

```text
open：待处理
investigating：处理中，保留为兼容状态，不作为用户必须点击的流程节点
resolved：已解决，保留为兼容状态；用户侧“标记已解决 / 确认关闭”合并为关闭
closed：已关闭
```

问题用户操作：

```text
新建问题：用户填写标题、描述、严重度即可
关闭问题：用户确认该问题无需继续跟踪
确认关闭：仅当系统发现来源事实已解除并标记建议关闭时出现
保持处理中：来源已解除但用户判断仍需继续处理
重新打开：仅在已关闭问题详情或已关闭筛选结果中出现，用于恢复误关或重新发生的问题
```

### 4. 预警链与旁路上卷

预警链回答：

```text
一个业务异常信号从发现、提醒、知悉、静音、解除、升级到风险、再到问题闭环的全过程如何被系统稳定追踪。
```

标准预警链：

```text
业务事实 source fact
-> 预警 warning / notification
-> 已知悉 acknowledge / 静音 mute / 自然解除 resolve / 转风险 convert
-> 风险 risk
-> 转问题 issue
-> 待确认关闭 / 关闭
```

旁路上卷：

```text
阻碍 obstacle -> 问题 issue
条件过期 condition_expired -> 问题 issue
验收逾期 acceptance_expired warning -> condition_expired issue，source_entity_type = acceptance_plan
```

预警链与旁路上卷的区别：

```text
预警链用于“不确定但需要关注”的业务信号，先提醒，再根据持续时间或用户判断升级
旁路上卷用于“事实已经发生”的确定事项，不强制先变成风险
旁路上卷不共享 warning -> risk -> issue 的预警升级链 chain_id，但必须写入 source_type / source_entity_id / pending_manual_close / 删除保护规则
```

旁路上卷不一定先变成风险：

```text
阻碍已经影响现场执行，直接上卷为问题
开工条件或验收已经过期，直接上卷为问题
预警仍是不确定信号，先升级为风险
风险长期未处理或人工确认后，再升级为问题
```

### 5. 与其他体系的边界

```text
v1.4.5 状态字典：定义状态口径，本章消费状态口径
v1.4.6 来源与映射：记录数据从哪里来，本章记录异常链怎么升级
v1.4.7 计划治理：基线 / 月计划只在生成新一轮时消费风险问题，不被实时风险自动改写
v1.4.8 条件阻碍：条件和阻碍是上游事实，本章只接收其预警和上卷结果
v1.4.10 责任主体：风险 / 问题责任人可文本，责任单位若后续要统计必须 participant_unit_id
v1.4.11 图纸证照验收联动：专项事实可触发预警或问题，但不把专项页变成风险问题主入口
```

系统异常和数据质量提示不直接进入业务风险问题链。

```text
系统异常：接口失败、任务调度失败、迁移异常、后台健康检查异常，走系统健康或提醒中心系统异常分类
数据质量：缺 ID、低置信度、映射不完整，走数据质量和计划健康提示
业务预警：现场任务、图纸、证照、验收、条件、阻碍等业务事实可能影响项目执行，才进入本章链路
```

## Core Design

### 1. 单一预警生命周期权威

从 v1.4.12 开始，业务预警生命周期权威固定为：

```text
notifications 中 source_entity_type = 'warning' 的记录，且以 warning_lifecycle_status 作为业务生命周期真值
```

原因：

```text
notifications 已承载 first_seen_at / acknowledged_at / muted_until / escalated_to_risk_id / escalated_at / is_escalated / resolved_at / resolved_source
v1.4.12 新增 warning_lifecycle_status，把业务预警生命周期从 notifications.status 的通知阅读状态中拆出来
/api/warnings 当前已经通过 warningService.syncActiveWarnings 输出 notifications 投影
RiskManagement 已经消费 /api/warnings 的生命周期结果
```

`warnings` 表保留，但降级为兼容表 / 旧数据来源：

```text
不删除 warnings 表
不再让新业务只写 warnings 表
riskStatisticsService、Dashboard、Reports、RiskTrendChart 必须改为读取统一治理 service / repository 的 notifications warning 投影，不得依赖 /api/warnings HTTP 路由
旧 warnings 数据一次性迁移或投影到 notifications
无法迁移的旧 warnings 只作为历史展示，不参与升级链
```

### 2. 预警链主线

预警链以 `notifications(source_entity_type = 'warning').warning_lifecycle_status` 为生命周期真值，覆盖以下状态流：

```text
created：业务事实触发，系统生成预警并写入 first_seen_at
active：来源事实仍存在，预警参与展示、统计和升级窗口
acknowledged：项目编辑者执行治理已知悉，暂停自动升级，不代表来源消除
muted：项目编辑者执行治理静音，到期后若来源仍存在则重新进入 active
resolved：来源事实解除，预警自然关闭并记录 resolved_source
escalated：预警已转风险，写 escalated_to_risk_id / escalated_at / is_escalated
```

预警链不是通知中心的一条消息，而是业务异常治理链的起点：

```text
通知中心负责分发和提醒
RiskManagement 负责治理和闭环
Dashboard / Reports 只消费统一投影后的统计结果
专项页只展示关联预警、风险、问题摘要和跳转，不建立私有链路
```

### 2.1 已确认补强口径

以下口径用于消除当前代码和目标方案之间的执行分叉。

旧 `warnings` -> `notifications` 迁移映射：

```text
旧 warnings.id：写入 notifications.source_entity_id 或 metadata.legacy_warning_id
旧 warnings.project_id / task_id / warning_type / severity / title / message：按同名或现有通知字段投影
旧 warnings.created_at / updated_at：保留为 created_at / updated_at，缺失 first_seen_at 时用 created_at 回填
旧 acknowledged / acknowledged_at：warning_lifecycle_status = acknowledged，保留 acknowledged_at；仅在旧数据有明确 actor/user_id 时写 warning_acknowledgments，无 actor 时只写 metadata.legacyAcknowledgedWithoutActor = true，不伪造用户
旧 muted_until：warning_lifecycle_status = muted，保留静音到期时间，不因迁移重新触发升级
旧 resolved / closed：warning_lifecycle_status = resolved，仅历史展示，不重新进入升级窗口
旧 escalated / escalated_to_risk_id：warning_lifecycle_status = escalated，保留 escalated_to_risk_id、escalated_at、is_escalated，禁止再次转风险
重复数据：按 warning_signature 合并；保留最早 first_seen_at、最高 severity、最新 warning_lifecycle_status、已知悉 / 静音 / 升级结果，不双算统计
无法确定 project_id 或来源的旧记录：标记 warning_legacy，只做历史展示，不参与自动升级
```

`warning_signature` 自然键固定为：

```text
project_id + warning_type + source_entity_type + source_entity_id/task_id + business_date
```

说明：

```text
business_date 固定按 Asia/Shanghai 自然日取值；后续如项目表增加 timezone 字段，再统一切换为项目时区
source_entity_id 优先于 task_id；没有明确来源时使用稳定 source_hash
不得使用每次扫描临时生成的随机 ID 作为签名
当前 warningChainService 中的身份构造逻辑必须收口到 buildWarningSignature，避免服务之间各算各的
同一 warning_signature 在同一 business_date 内只允许一条生命周期记录；resolved 后同日再次出现时重开同一记录，warning_lifecycle_status 改回 active，并把上次 resolved_at / resolved_source 追加到 metadata.lifecycleHistory
跨 business_date 再次出现时生成新 warning_signature，不复用上一自然日记录
```

`GET /api/warnings` 写副作用处理：

```text
外部 HTTP GET /api/warnings 必须显式传 projectId 或 project_id；缺少项目参数直接返回 400，不允许通过外部请求触发全项目扫描
当前代码 GET /api/warnings 会触发条件、验收、预警、风险升级同步，这是历史兼容实现
v1.4.12 执行期允许短期保留读时同步，但同步逻辑必须迁入统一治理服务并保证幂等、限流和超时预算
目标口径是读取接口只读取统一投影；定时任务、后台同步或显式治理服务负责写入和升级
后台全项目扫描只允许通过 job / service 方法执行，不走 HTTP GET /api/warnings
无论是否短期保留读时同步，GET 多次调用不得重复生成 warning / risk / issue
```

验收逾期 source_type 口径：

```text
acceptance_expired 作为 warning_type 使用，用于表示验收临期、逾期或整改待处理预警
上卷到 issues 时，沿用当前 issues.source_type 兼容口径 condition_expired，source_entity_type = acceptance_plan
前端和报表按 source_entity_type = acceptance_plan 展示为“验收逾期 / 验收整改超期”，不展示 condition_expired 技术名
后续如要新增 issues.source_type = acceptance_expired，必须在数据库约束、RLS、统计、旧数据迁移中统一升级，本章不提前制造第二套写入口
```

`delay_exceeded` 口径：

```text
delay_exceeded 是计划偏差事实产生的业务预警，不恢复 delay_requests / task_delay_history 延期审批链
它只参与预警、风险、问题治理链，不要求用户补填延期申请或审批原因
任务完成、进度恢复或新计划发布后，可关闭或降级相关预警 / 风险，但不回写历史计划快照
```

通知状态与预警生命周期映射：

```text
notifications.status：只保留通知分发 / 阅读兼容状态，例如 unread / read / acknowledged / muted / resolved，不作为预警生命周期真值
notifications.warning_lifecycle_status：固定承载业务预警生命周期，取值 created / active / acknowledged / muted / resolved / escalated
个人已读 / 个人已知悉：只改变 notifications.status、is_read 或接收人个人状态，不改变 warning_lifecycle_status，不暂停自动升级
治理已知悉：项目编辑者在 RiskManagement 执行，warning_lifecycle_status = acknowledged，并记录 acknowledged_at / warning_acknowledgments；不代表来源解除
治理静音：项目编辑者在 RiskManagement 执行，warning_lifecycle_status = muted，保留 muted_until；静音期内不提醒、不自动升级，到期后来源仍存在则恢复 active
resolved：warning_lifecycle_status = resolved，来源事实解除，预警自然关闭；通知可不再作为未读待办
escalated：warning_lifecycle_status = escalated，保留 escalated_to_risk_id；不得再次生成风险
统计、升级、Dashboard、Reports、RiskManagement active 判定只读取 warning_lifecycle_status 和生命周期字段，不以 notifications.status 或 read / unread 判断是否 active
```

### 5. 升级与关闭原则

本节规则基于当前代码中的 `warningService / upgradeChainService / scheduler / RiskManagement` 已有链路，不要求用户手工维护升级关系。

升级原则：

```text
预警超过 3 个自然日仍未被项目编辑者治理已知悉 / 治理静音 / 来源解除，可自动升级为风险
风险超过 7 个自然日仍停留 identified 且未转问题，可自动升级为问题
阻碍超过规则阈值并达到严重影响时，可直接上卷为问题
条件或验收已经过期且仍未满足 / 未完成，可直接上卷为问题
```

关闭原则：

```text
普通预警：来源事实解除后，系统自动关闭，用户不需要手动关闭
待确认关闭：来源已解除但风险 / 问题仍可能需要人工判断时，系统标记 pending_manual_close；用户只需二选一，风险为确认关闭 / 保持跟踪，问题为确认关闭 / 保持处理中
手工风险 / 手工问题：由用户自行判断后关闭
升级链对象：不能物理删除，只能关闭或保留链路
任务完成后：任务相关延期来源风险和预警可由系统自动关闭或进入待确认关闭
```

低置信度原则：

```text
低置信度推断不生成 critical 严重阻断
低置信度推断不自动升级为风险或问题
低置信度只进入数据质量、计划健康提示或待观察信号
```

### 6. 三层计划关系

必须补强 notifications warning 生命周期字段一致性：

```sql
alter table notifications
  add column if not exists warning_signature text null,
  add column if not exists source_hash text null,
  add column if not exists warning_lifecycle_status text null;

update notifications
   set warning_lifecycle_status = case
     when coalesce(is_escalated, false) = true or escalated_to_risk_id is not null then 'escalated'
     when resolved_at is not null or resolved_source is not null or status = 'resolved' then 'resolved'
     when muted_until is not null and muted_until > now() then 'muted'
     when acknowledged_at is not null or status = 'acknowledged' then 'acknowledged'
     when first_seen_at is not null then 'active'
     else 'created'
   end
 where source_entity_type = 'warning'
   and warning_lifecycle_status is null;

do $$
begin
  if not exists (
    select 1 from pg_constraint
    where conname = 'notifications_warning_lifecycle_status_check'
  ) then
    alter table notifications
      add constraint notifications_warning_lifecycle_status_check
      check (
        (
          source_entity_type is distinct from 'warning'
          and warning_lifecycle_status is null
        )
        or (
          source_entity_type = 'warning'
          and warning_lifecycle_status in ('created','active','acknowledged','muted','resolved','escalated')
        )
      );
  end if;
end $$;

create index if not exists idx_notifications_warning_lifecycle
  on notifications(project_id, source_entity_type, warning_lifecycle_status, severity, created_at desc)
  where source_entity_type = 'warning';

create unique index if not exists idx_notifications_warning_signature_unique
  on notifications(project_id, warning_signature)
  where source_entity_type = 'warning' and warning_signature is not null;
```

原子升级 / RPC 同步要求：

```text

治理已知悉写 warning_lifecycle_status = acknowledged，但个人已知悉不写该字段
治理静音写 warning_lifecycle_status = muted、muted_until，但个人静音不写该字段
```


### 3. 预警规则

预警类型统一归类：

```text
condition_due：开工条件临期
obstacle_timeout：阻碍持续过久
acceptance_expired：验收临期 / 逾期 / 整改待处理
delay_exceeded：延期次数过多
critical_path_stagnation：关键路径停滞
critical_path_delay：关键路径延期
progress_trend_delay：进度趋势异常
permit_expiry：证照临期 / 过期
drawing_blocked：图纸未通过影响施工或验收
```

条件类预警边界：

```text
开工条件 target_date 未到但临近，生成 condition_due 业务预警
开工条件 target_date 已过且仍未满足，不再继续生成同类 condition_due 预警
条件已过期后，上卷为 condition_expired 问题，并关闭或降级已有 condition_due 预警
条件进入问题链后，前端只展示问题、必要状态提示和待确认关闭，不重复刷同类预警
```

预警等级：

```text
info：提醒关注，不进入严重阻断
warning：需要跟进，超过升级窗口可转风险
critical：高优先级关注，可广播给项目 owner / 责任人
```

去重规则：

```text
同一 project_id + task_id/source_entity_id + warning_type + 自然日 只保留一条活跃预警
同一任务同日同时出现 critical_path_stagnation 与 delay_exceeded 时，合并为更高严重度的预警描述
来源事实变好时，不新增反向预警，关闭原预警并记录 resolved_source
```

用户已知悉 / 静音：

```text
通知中心个人已读 / 个人已知悉 / 个人静音：只影响个人提醒，不暂停自动升级
RiskManagement 治理已知悉：项目编辑者执行，暂停自动升级，不影响来源继续扫描
RiskManagement 治理静音：项目编辑者执行，在 muted_until 之前暂停升级和提醒
治理静音到期后，如果来源仍存在，继续参与升级窗口
```

### 4. 风险规则

人工风险：

```text
用户填写标题、描述、级别
source_type = manual
status = identified
probability / impact 按级别给默认值，用户后续可调整
```

预警转风险：

```text
用户点击“转为风险”或系统 3 天自动升级
写入 source_type = warning_converted / warning_auto_escalated
写入 source_entity_type = warning
写入 source_id / source_entity_id / chain_id
预警标记 is_escalated = true、escalated_to_risk_id、escalated_at
```

风险转问题：

```text
用户点击“转为问题”或系统 7 天自动升级
写入 issue.source_type = risk_converted / risk_auto_escalated
写入 issue.source_entity_type = risk
写入 risk.linked_issue_id
风险进入 mitigating 或 closed 的链路保护状态
```

风险关闭：

```text
manual 风险可直接关闭
warning_auto_escalated 风险来源解除后进入 pending_manual_close
用户点确认关闭后 status = closed
用户点保持跟踪后 pending_manual_close = false，status 保持 identified / mitigating
已转问题风险不允许物理删除
```

### 5. 问题规则

人工问题：

```text
用户填写标题、描述、严重度
source_type = manual
priority 由系统计算
status = open
```

阻碍上卷问题：

```text
阻碍达到上卷条件后，系统创建或更新 issue
source_type = obstacle_escalated
source_entity_type = task_obstacle
severity 继承阻碍影响等级
阻碍解除后，问题不立即关闭，进入 pending_manual_close 或待观察
```

条件 / 验收过期问题：

```text
开工条件过期仍未满足 -> condition_expired issue
验收逾期 / 整改超期 -> condition_expired issue，source_entity_type = acceptance_plan
来源达成后，系统标记 pending_manual_close
同一来源已生成 active issue 后，不再重复生成同类过期预警
已存在的临期预警应写 resolved_source = converted_to_issue 或 source_resolved
```

问题关闭：

```text
用户不需要填写关闭说明
系统后台记录操作人、时间、来源和版本
source 已解除但问题仍可能需要人工跟踪时，用户可选择保持处理中
已参与升级链的问题禁止物理删除
```

### 6. 专项页接入

图纸：

```text
图纸未通过、图纸包影响施工或验收时，可生成 warning
只有明确影响任务 / 条件 / 验收要求时，才进入业务预警
图纸低置信度匹配不自动生成 critical，不自动上卷风险问题
```

证照：

```text
证照临期、过期、补正、阻塞可生成 warning

证照问题或风险来源写 source_entity_type = pre_milestone / certificate_work_item
```

验收：

```text
验收临期 / 逾期 / 整改生成 warning
验收逾期超过规则阈值生成 issue
验收通过 / 归档后关闭或降级相关预警
验收任务与普通施工任务关系按 v1.4.11 的 covers_task，不用风险问题链改普通任务进度
```

任务：

```text
任务完成可关闭任务相关延期来源风险和预警
任务进度恢复可降级阻碍影响状态，但不自动删除问题
任务删除或归档时，链路对象不物理删除，来源标记 source_deleted
```

## Assumptions

当前没有历史生产数据，所以旧对象迁移只做确定性投影，不做复杂人工清洗。

普通用户不需要理解预警签名、来源 ID、链路 ID、置信度和映射原因。

`notifications` 是业务预警生命周期权威，`warnings` 表保留兼容但不再作为新业务真值。

RiskManagement 页面继续保留，不新增单独的“升级规则配置”入口。

系统异常和数据质量问题不自动进入业务风险问题链，后续由数据质量与系统健康章节单独治理。

预警升级链必须明确通知渠道边界，避免“只写治理记录”或“默认多渠道推送”的执行分叉。

```text
同一 warning_signature 在同一业务日内只产生一条站内提醒，升级、静音、已知悉、关闭只更新生命周期和通知状态，不重复轰炸用户。
```

## 2026-05-26 算法收口补充

本轮按现有代码与新增 seed / 规则资产情况，对风险 / 问题 / 预警生命周期治理做收口，固定以下执行口径：

```text
1. 预警运行时真值源统一为 notifications 中 source_entity_type = 'warning' 的 warning 投影。
2. warning_lifecycle_status 是 warning active / acknowledged / muted / resolved / escalated 的生命周期判断字段。
3. 旧 warnings 表不再作为基线生成、月计划生成、风险统计趋势或新治理链的业务真值；历史兼容只允许通过投影或迁移兜底读取。
4. 基线生成和月计划生成通过 projectWarningProjectionService 读取 warning 投影，再用 isActiveWarning 判定活跃预警。
5. 风险页、统计、通知中心继续消费 notifications / warning_lifecycle_status，不新建平行 warning 事实层。
```

生命周期与扫描阈值统一进入 `riskIssueWarningRuleRegistry`：

```text
warning_to_risk：活跃 warning 首次出现超过 3 天，进入自动升级风险候选。
risk_to_issue：identified risk 超过 7 天且未关联 issue，进入自动升级问题候选。
critical_path_delay：延期 >= 20 天 critical，>= 10 天 warning，> 0 天 info。
delay_exceeded：延期次数 >= 5 critical，>= 3 warning。
obstacle_timeout：阻碍持续 >= 7 天 critical，>= 3 天 warning。
critical_path_stagnation：关键路径连续 7 天无进度变化 critical。
```

算法 seed / 规则资产与治理链的关系固定为：

```text
candidate_only / confidence_only / canCreateRiskIssue = false 的 seed 只能形成治理候选信号或解释证据。
site_capacity_pressure 等 seed 即使能影响工期预测、偏差解释、基线和月计划上下文，也不得直接创建 risk / issue。
只有带真实运行时证据且 actionPolicy = create_warning 的运行时信号，才可创建 warning；warning 后续是否升级 risk / issue 仍走生命周期治理链。
seed 不能绕开 warning_lifecycle_status、不能绕开 confirm_warning_as_risk_atomic / create_issue_from_risk_atomic，也不能直接改风险问题主表。
```

当前主要消费方：

```text
warningService：扫描条件、阻碍、验收、关键路径、延期次数、数据质量趋势等 warning，并持久化到 notifications warning 投影。
upgradeChainService / riskIssueWarningGovernanceService：处理 warning -> risk -> issue 自动升级、人工确认、静音、已知悉和来源解除。
riskStatisticsService / RiskManagement / Reports / Dashboard：消费风险、问题和 warning 摘要，不重新定义 warning 生命周期。
baselineGenerationService / monthlyPlanGenerationService：只把 active warning 当作计划生成上下文和风险信号，不直接创建风险或问题。
notification center：只负责触达、阅读、个人已知悉 / 静音，不改变业务生命周期真值。
```

验收要求：

```text
基线 / 月计划生成不得调用 warnings 表。
规则阈值不得散落在扫描或升级函数内，新增阈值先进入 riskIssueWarningRuleRegistry。
seed 候选信号必须证明不能直接创建风险 / 问题。
warning 链路回归测试必须覆盖通知去重、生命周期、自动升级和读取兼容。
```

## 2026-05-26 治理信号增强补充

本轮增强仅针对风险 / 问题 / 预警生命周期治理算法，不改变关键路径、项目健康、数据质量、计划治理、工期预测等算法的主逻辑；这些算法的输出只作为治理输入信号参与归一、候选、去重和归因。

统一治理信号目录固定为 `riskIssueWarningGovernanceSignalService`：

```text
normalizeGovernanceSignalDirectory：把 duration_context、execution_impact、planning_governance、data_quality、project_schedule_state、algorithm_seed 等算法输出归一为治理信号。
evaluateSeedWarningPromotion：统一判断 seed / 规则资产是否允许从候选信号提升为 warning。
dedupeGovernanceSignals：按 projectId + signalType + task/source subject 合并同一业务事实，并保留跨算法归因。
```

promotion gate 口径固定为：

```text
seed-only / candidate_only / confidence_only 信号只能进入 candidate_warning 或 explain_only，不能创建 warning、risk、issue。
只有 actionPolicy = create_warning、存在真实运行时证据、存在 projectId，并且存在 taskId / sourceEntityId / sourceId 之一时，才允许 canCreateWarning = true。
即使允许创建 warning，也只能进入 warning 生命周期；canCreateRisk 和 canCreateIssue 永远为 false，后续升级继续走 warning_lifecycle_status 和风险问题确认链。
缺 project 或缺业务主体的运行时证据一律退回 warning_candidate。
```

跨算法去重与归因口径固定为：

```text
同一 projectId + signalType + task/source subject 的信号合并为一条治理信号。
归因保留 primarySourceAlgorithm、sourceAlgorithms、sourceIds、evidenceCount。
确定性运行时证据优先于 seed-only 解释，create_warning 优先于 candidate_warning，critical 优先于 warning / info。
合并后仍不得直接创建 risk / issue；治理链只把它作为 warning 创建或解释依据。
```

## 2026-05-26 生命周期治理硬化补充

本轮继续只针对风险 / 问题 / 预警生命周期治理算法做工程硬化，固定以下执行口径：

```text
1. warning 写入边界统一补充治理信号归因：riskIssueWarningGovernanceService.upsertWarningLifecycle 会在缺少 metadata.governanceSignal 时，根据 sourceEntityType 映射 sourceAlgorithm，生成 create_warning 运行时信号，并把 dedupeKey、promotionStatus、sourceAlgorithm、sourceId、attribution、boundaryReason、evidence 写入 metadata.governanceSignal。
2. 批量治理信号入口 upsertWarningsFromGovernanceSignals 先执行 normalizeGovernanceSignalDirectory + dedupeGovernanceSignals，只把 canCreateWarning = true 且 project/subject 完整的信号写入 warning 生命周期。
3. riskIssueWarningGovernanceService 的 warning -> risk 与 risk -> issue 入口委托 upgradeChainService 的 confirm_warning_as_risk_atomic / create_issue_from_risk_atomic 原子链，不再维护第二套本地升级写法。
4. 来源解除 / 删除时，warning 生命周期关闭同时匹配 source_entity_id 和 source_hash，避免旧 warning_signature / 业务源 ID 混用导致 warning 残留；risk / issue 仍只标记 pending_manual_close 或 source_deleted，不自动物理删除。
```

这次硬化不扩大算法判定范围，不改变其他算法主输出，只把现有运行时事实进入 warning 生命周期前的归一、归因、升级和来源关闭边界收紧。
