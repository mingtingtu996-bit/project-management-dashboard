## 0. 2026-06-01 final range-tree boundary (authoritative)

This v1.4-series plan follows the final range-tree model. There is no production history or existing user data that needs a compatibility layer.

Authoritative engineering object types are exactly: `phase / section / building / basement / floor / physical_zone / functional_area`.

The following compatibility surfaces are deleted and must not be reintroduced in runtime code, migrations, or frontend contracts:

- `zone / professional / subproject / custom` as engineering object types.
- `zone_object_id / professional_object_id` task fields.
- `project_materials.professional_object_id` and `engineering_categories.professional_object_id`.
- `legacy_object_type`, deprecated object-type arrays, legacy bridge/backfill helpers, and old scope adapter functions.
- `/api/scope-dimensions`, `scope_dimensions`, and `project_scope_dimensions` as active application surfaces.

Professional/system/domain/method semantics remain business facts through `specialty_type`, `engineering_category_id`, `standard_work_code`, template metadata, and project profile facts. They are not range-tree objects.

Any older section in this document that mentions deleted object types, deleted fields, old scope tables, or compatibility adapters is superseded by this boundary.
# v1.4.9 里程碑与关键节点体系执行方案

## Summary

v1.4.9 的目标是把当前应用里已经存在的 `任务里程碑 / 项目基线里程碑 / 月度计划关键节点 / 关键路径关注 / 里程碑页展示 / Dashboard 汇总 / 预警` 统一成一套稳定口径。

本章不新建一套孤立的“里程碑主数据表”，也不新增“关键节点管理中心”。当前应用已经把施工里程碑主要落在 `tasks.is_milestone` 上，所以 v1.4.9 的重点是：

```text
里程碑：用户明确标记的计划控制节点
关键节点：系统根据里程碑、关键路径、基线、月度计划、人工关注和任务约束状态派生出的重点控制视角
```

本章继续遵循 v1.4.8 的原则：

```text
用户维护业务事实，系统判断治理语义
能由工程对象、WBS、任务、计划、依赖、条件、阻碍和来源映射自动判断的，不要求用户手工选择
普通前端不展示 source、lineage、key_node_type、inference_confidence、generation_metadata 等治理字段
```

## Business Definitions

### 1. 里程碑

里程碑是用户明确标记的计划控制节点，回答：

```text
这个任务是否代表一个阶段性、交付性或控制性节点？
这个节点的重要程度是一、二、三级中的哪一级？
这个节点是否需要进入里程碑页、Dashboard、报表、月计划和基线偏差分析？
```

当前系统里程碑继续使用现有字段：

```text
tasks.is_milestone
tasks.milestone_level
tasks.milestone_order
tasks.milestone_id
task_baseline_items.is_milestone
monthly_plan_items.is_milestone
```

里程碑等级口径：

```text
一级里程碑：项目总控节点，影响整体工期和核心交付
二级里程碑：阶段 / 专业 / 标段控制节点，影响局部关键路径
三级里程碑：过程监控节点，用于日常计划跟踪
```

### 2. 关键节点

关键节点不是用户维护的新业务对象，而是系统派生出的计划控制视角，回答：

```text
哪些任务或计划项需要被系统重点关注？
哪些节点会影响月度计划生成、基线重编、关键路径预警、驾驶舱健康度和 AI 分析？
哪些节点虽然不是显式里程碑，但仍然是当前计划里的高关注控制点？
```

关键节点来源：

```text
tasks.is_milestone = true
tasks.is_critical = true
当前关键路径算法输出的任务
task_critical_overrides 中的人工关注 / 人工插链任务
当前项目基线中 is_milestone = true 的条目
当前月度计划中 is_milestone = true 的条目
本月控制节点、临近交付节点和高风险节点
```

里程碑和关键节点关系：

```text
里程碑一定是关键节点的一种
关键节点不一定都是里程碑
关键路径节点不会自动变成里程碑，只提高关注等级和算法权重
取消里程碑只取消显式标记，不删除关键路径、月度计划、基线或人工关注产生的关键节点判断
```

## Core Design

### 1. 不新增里程碑主表

v1.4.9 不新增 `milestone_master` / `key_nodes` 这类主数据表。

权威关系固定为：

```text
当前执行层权威：tasks.is_milestone / milestone_level / milestone_order / milestone_id
项目基线快照：task_baseline_items.is_milestone / source_milestone_id
月度承诺快照：monthly_plan_items.is_milestone
展示汇总层：project-summary.milestoneOverview
旧兼容层：milestones / task_milestones
证照前置层：pre_milestones，不并入本章
```

### 2. 不新增关键节点管理入口

普通用户不维护关键节点类型、来源、风险等级或算法标签。

用户只做现有业务动作：

```text
在任务 / 甘特表标记里程碑
选择一级 / 二级 / 三级里程碑
取消里程碑标记
维护任务计划日期
维护任务进度和完成
维护前置任务、开工条件和阻碍
```

系统自动判断：

```text
是否关键路径节点
是否人工关注节点
是否月度控制节点
是否基线控制节点
是否临近关键节点
是否偏移关键节点
是否高风险关键节点
是否数据待校准节点
```

### 3. 新增后端关键节点摘要

v1.4.9 需要新增后端派生摘要 `keyNodeSummary`，供 Dashboard、月度计划、报表、预警、AI 和 BI 指标消费。

标准 DTO：

## Database Changes

### 1. 不建主数据表

v1.4.9 不新建 `milestones_v2`、`key_nodes`、`milestone_master` 主表。

### 2. 迁移文件与权威外键修正

基于当前代码库最高迁移 `127_plan_truth_snapshot_boundaries.sql`，v1.4.9 新增迁移固定为：

```text
server/migrations/128_reconcile_milestone_key_node_system.sql
```

当前已有 `server/migrations/088_reconcile_tasks_milestone_link.sql` 会把 `tasks.milestone_id` 外键指向旧 `milestones(id)`。v1.4.9 后，`tasks.milestone_id` 的权威含义改为“挂靠到同项目的里程碑任务”，即必须指向 `tasks.id`，且目标任务必须 `is_milestone = true`。

因此迁移必须先修正旧约束，不能在旧 `fk_tasks_milestone_id -> milestones(id)` 还存在时直接写入任务 ID：

```sql
do $$
declare
  constraint_to_drop text;
begin
  select tc.constraint_name
    into constraint_to_drop
  from information_schema.table_constraints tc
  join information_schema.key_column_usage kcu
    on tc.constraint_name = kcu.constraint_name
   and tc.table_schema = kcu.table_schema
  join information_schema.constraint_column_usage ccu
    on tc.constraint_name = ccu.constraint_name
   and tc.table_schema = ccu.table_schema
  where tc.table_schema = 'public'
    and tc.table_name = 'tasks'
    and tc.constraint_type = 'FOREIGN KEY'
    and kcu.column_name = 'milestone_id'
    and ccu.table_name = 'milestones'
  limit 1;

  if constraint_to_drop is not null then
    execute format('alter table public.tasks drop constraint if exists %I', constraint_to_drop);
  end if;
end $$;
```

新校验口径：

```text
tasks.milestone_id 只能指向同项目 tasks.id
tasks.milestone_id 不能指向自身
tasks.milestone_id 指向的目标任务必须 is_milestone = true
取消目标任务里程碑身份前，必须先处理所有挂靠到该任务的普通任务
```

PostgreSQL 普通 `CHECK` 不能跨表校验，v1.4.9 固定采用“数据库触发器 + 后端服务校验”双保险，不允许只做其中一层，也不允许保留“服务层兜底即可”的实现分支。

```text
数据库迁移必须新增触发器校验 tasks.milestone_id 指向同项目里程碑任务
后端 taskWriteChain / milestoneGovernanceService 必须在写入前执行同样校验，并返回业务错误
测试必须同时覆盖数据库触发器拦截和后端服务拦截
```

不得再创建 `tasks.milestone_id -> milestones(id)` 外键。

触发器校验规则固定为：

```text
milestone_id 为空：允许
milestone_id = 当前任务 id：拒绝
milestone_id 指向不存在任务：拒绝
milestone_id 指向跨项目任务：拒绝
milestone_id 指向 is_milestone != true 的任务：拒绝
milestone_id 指向 status = cancelled 的任务：拒绝
```

### 3. 字段补齐规则

如目标分支字段缺失，迁移必须幂等补齐：

```sql
alter table tasks
  add column if not exists is_milestone boolean not null default false,
  add column if not exists milestone_level integer null,
  add column if not exists milestone_order integer null,
  add column if not exists milestone_id uuid null,
  add column if not exists is_critical boolean not null default false;

create index if not exists idx_tasks_project_milestones
  on tasks(project_id, is_milestone, milestone_level, milestone_order)
  where is_milestone = true;

create index if not exists idx_tasks_milestone_id
  on tasks(milestone_id)
  where milestone_id is not null;
```

`milestone_level` 受控值：

```text
1：一级里程碑
2：二级里程碑
3：三级里程碑
null：非里程碑或待系统补齐默认等级
```

默认补齐规则：

```text
is_milestone = true 且 milestone_level 为空：默认补为 3
is_milestone = false：milestone_level 可为空
```

### 4. 派生快照可选

第一阶段采用实时计算，不新增 `project_key_node_snapshots`，也不把关键节点摘要写入新的用户可见表。

如 Dashboard、报表或 AI 需要历史趋势，优先复用现有项目日快照或计划治理快照的汇总字段；不得让前端自行缓存、扫描任务或生成临时关键节点结果。

如果性能或回放需要，可新增派生快照表，但它不是用户维护主数据：

```sql
create table if not exists project_key_node_snapshots (
  id uuid primary key default gen_random_uuid(),
  project_id uuid not null references projects(id),
  snapshot_date date not null,
  summary jsonb not null default '{}',
  signals jsonb not null default '[]',
  source_type text not null default 'system',
  created_at timestamptz not null default now(),
  unique(project_id, snapshot_date)
);
```

```text
关键路径、baseline_is_critical、criticality_weight、临近里程碑窗口、验收/图纸/证照等显式绑定前置条件只作为升级上下文；只有绑定到计划任务或承诺锚点时才进入硬治理

planningIntegrityService、planningHealthService、planningGovernanceService、progressDeviationService 继续消费同一份 MilestoneIntegrityReport；前端展示不新增入口
```

收口后的挡墙口径：

```text
aligned：不形成治理挡墙
needs_attention + manual / unanchored：confirm，进入计划治理确认，不阻断保存
missing_data：默认 confirm；如影响正式承诺锚点或关键路径上下文，可升级 block_save
blocked：block_save，目标面默认为 baseline
健康分和偏差归因只解释影响，不单独把里程碑问题升级为硬阻断
```

维护态口径：

```text
该算法当前收口，后续不再扩算法主流程。
后续只维护 milestoneIntegrityRuleSeed、公司 / 项目类型规则配置、M1-M9 场景文案、suggestedAction、severity、gateLevel、targetSurface 和承诺锚点策略。
新增图纸、证照、验收、开工条件等业务域信号时，只有形成明确任务依赖、验收前置、开工条件或承诺锚点，才允许通过规则资产配置进入 milestone_integrity 硬治理。
不得在 milestoneIntegrityService、planningGovernanceService、通知服务或前端展示层重新硬编码一套 M1-M9 场景表。
```

## Business Rules

### 1. 里程碑标记规则

```text
用户可以把任务标记为一级 / 二级 / 三级里程碑
用户可以取消里程碑标记
结构行是否允许标记里程碑，按 v1.4.2 WBS 语义判断；默认允许控制节点类结构行标记，禁止无意义空结构行标记
任务被标记为里程碑后，进入里程碑页、Dashboard、报表、月计划和基线控制口径
任务取消里程碑后，从新的里程碑统计中退出，但历史快照不删除
```

### 2. 里程碑兑现规则

里程碑不新增“确认兑现”按钮。

```text
任务完成且 actual_end_date 存在：里程碑自动兑现
actual_end_date <= 当前计划完成日期：按期兑现
actual_end_date > 当前计划完成日期：延后兑现
未完成且当前计划完成日期已过：已逾期
未来 7 天内到期：即将到期
未来 30 天内到期：进入 dueSoonCount
```

实际完成日期继续遵循 v1.4.7：

```text
普通用户不手填 actual_end_date
任务完成由后端统一生成 actual_end_date
验收通过、旧里程碑兼容、导入回填必须走后端执行事实服务或 correction/backfill 通道
```

### 3. 关键节点派生规则

后端以任务 ID 去重生成关键节点信号：

```text
显式里程碑：tasks.is_milestone = true
任务关键标记：tasks.is_critical = true
关键路径节点：当前 critical path 输出包含该任务
人工关注节点：task_critical_overrides 包含该任务
基线控制节点：当前生效 task_baseline_items.is_milestone = true 且能映射到任务
月度控制节点：当前 confirmed 或 draft 月度计划中 monthly_plan_items.is_milestone = true 且能映射到任务
```

去重规则：

```text
优先使用 task_id
其次使用 source_task_id
再其次使用 baseline_item_id / monthly_plan_item_id 映射
最后使用旧 source_milestone_id 兼容映射
不得只按任务名称合并关键节点
```

### 4. keyNodeSummary 指标规则

```text
total：去重后的关键节点总数
milestoneCount：tasks.is_milestone = true 的节点数
criticalPathCount：关键路径输出中的节点数
monthlyControlCount：本月月度计划控制节点数
baselineControlCount：当前生效基线控制节点数
dueSoonCount：未来 30 天内到期且未完成的关键节点数
shiftedCount：基线日期、当前计划日期或实际完成日期发生偏移的关键节点数
blockedCount：关键节点关联 hard 条件未满足或存在 blocked 阻碍的节点数
highRiskCount：逾期、blocked、关键路径影响、连续停滞等叠加后达到高风险阈值的节点数
```

计数边界：

```text
total 按 task_id 去重，同一任务无论命中多少来源只计 1 个关键节点
分类计数按来源 / 状态独立统计，同一任务可以同时计入 milestoneCount、criticalPathCount、monthlyControlCount、baselineControlCount
dueSoonCount、shiftedCount、blockedCount、highRiskCount 也是状态类独立计数，同一任务可同时命中多个状态类指标
criticalPathCount 只统计关键路径服务已经确认的节点；依赖网络不足或关键路径无法形成时不得臆造关键路径，只记录数据质量或治理提示
monthlyControlCount 只统计当前 draft / confirmed 月度计划中可映射到任务的控制节点
baselineControlCount 只统计当前生效基线中可映射到任务的控制节点
```

低置信度规则：

```text
低置信度不直接计入 blockedCount
低置信度可进入数据质量、治理提示和 AI 解释
低置信度不得让驾驶舱显示为严重阻断
```

### 5. 三个计划层级的里程碑 / 关键节点区分

v1.4.7 已经明确项目基线、月度计划、任务列表 / 甘特共用一套表格体验，但三者的数据语义不同。v1.4.9 必须避免把“里程碑 / 关键节点”按页面硬编码理解，而应按计划层级理解。

里程碑不是因为出现在某个页面才成立，而是用户在某个计划层级里显式标记“这个节点重要”的业务事实。页面只是编辑或查看入口。

```text
基线层级：task_baseline_items.is_milestone，表示基线快照里的总控里程碑 / 控制节点
月计划层级：monthly_plan_items.is_milestone，表示月度计划快照里的本月重点节点 / 控制节点
执行层级：tasks.is_milestone / milestone_level，表示当前执行任务中的里程碑
里程碑页：只读分析页，只展示显式里程碑任务和偏差结果，不承接健康问题 chip，也不新增关键节点维护入口
Dashboard / Reports / CompanyCockpit：只消费 milestoneOverview、keyNodeSummary 或 metricRegistry 指标，不在前端自行判断关键节点
```

关键节点的统一口径：

```text
关键节点是后端派生视角，不是三个页面里的新增可编辑对象
同一任务同时命中基线里程碑、月计划控制节点、执行里程碑、关键路径或人工关注时，keyNodeSummary 只按 task_id 计一次 total，但 sources 保留多个来源
不同计划层级出现标记差异时，不视为数据冲突：基线和月计划代表历史承诺快照，任务列表代表当前执行事实
不同任务分别在基线、月计划、执行层级被标记为重要节点时，全部进入关键节点池，由 keyNodeSummary 去重、分组和汇总
执行任务取消里程碑不会静默改写已发布基线和已确认月计划；只影响后续生成、后续修订和新的 keyNodeSummary
基线或月计划修订发布后，通过 v1.4.6 data_lineage 记录与执行任务里程碑之间的映射变化
```

前端文案建议：

```text
项目基线页：使用“基线里程碑 / 总控节点”
月度计划页：使用“本月控制节点 / 月计划里程碑”
任务列表 / 甘特页：使用“里程碑”
跨页面汇总、Dashboard、AI、BI：使用“关键节点”
```

### 6. 关联任务规则

里程碑关联任务继续兼容两种关系：

```text
parent_id = milestoneTaskId：任务树父子关系
milestone_id = milestoneTaskId：任务挂靠里程碑关系
```

v1.4.9 推荐：

```text
parent_id 表达 WBS / 任务树结构
milestone_id 表达所属里程碑挂靠
后端查询关联任务时继续合并两者并去重
前端任务弹窗保留“所属里程碑（可选）”
```

### 7. 任务汇总里程碑分组规则

当前 `server/src/routes/task-summaries.ts` 仍存在按旧 `milestones` + `task_milestones` 分组的链路，v1.4.9 必须统一为：

```text
优先使用 tasks 表中 is_milestone = true 的任务作为里程碑分组
优先使用 tasks.milestone_id 判断普通任务所属里程碑
同时兼容 parent_id = milestoneTaskId 的旧树形归属
旧 task_milestones 只在 tasks.milestone_id 缺失时参与补齐，且必须先把旧 milestones.id 解析为任务里程碑 ID
旧 milestones 表只用于旧数据展示和 source_milestone_id 映射，不再作为新分组权威
无法映射的历史任务进入“未归属里程碑”，不阻断汇总查看
```

### 8. 删除和取消规则

按 v1.4.8 口径，用户不需要理解物理删除、软删除和历史归档。

```text
取消里程碑：只把当前任务 is_milestone 改为 false，并清理当前显示所需 milestone_level；不删除历史快照
取消里程碑前，后端必须查询 tasks.milestone_id = 当前任务 ID 的挂靠任务
如果存在挂靠任务，默认允许取消，但必须在同一事务内把这些任务的 milestone_id 置空，并写 change_logs / data_lineage，原因固定为 milestone_unmarked_relation_detached
取消里程碑不得改动这些挂靠任务的 parent_id / WBS 树结构
取消后，被置空挂靠的任务进入后续任务汇总的“未归属里程碑”分组，不阻断任务查看
已被计划、预警、时间轴、Dashboard 或报表消费的里程碑取消：必须由后端写入业务原因、操作者、来源、原值、新值和审计日志
取消原因由后端根据操作上下文和消费关系生成标准业务原因，不要求普通前端额外弹窗收集
删除任务：退出后续关键节点识别和月度计划生成，但不回改已发布基线和已确认月计划
已进入基线、月计划、预警、时间轴、Dashboard 快照的里程碑：保留历史记录
旧 milestones 表记录不因取消任务里程碑而物理删除
旧 dbService / storageService / supabaseAdapter 中的 deleteMilestone 兼容壳不能再删除任务；新施工里程碑删除动作必须映射为 unmarkTaskMilestone
真正删除任务只能走任务删除链路，并遵守任务删除保护、计划快照不回改和审计留痕规则
```
