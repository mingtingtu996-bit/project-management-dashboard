# Dashboard 数据口径一致性修正方案 v1.3.5.3

> 版本定位：承接 `v1.2 BI 化两步走实施方案`、`UI_UX 商业级全面优化方案 v1.3`、`全站视觉对齐执行方案 v1.3.5.2`。本文件处理 Dashboard 当前暴露的数据与展示一致性问题，并追加里程碑页、项目基线页的关联收口项；不改变系统全面分析报告。

## 1. Dashboard 最终收口项

> 最后修订：2026-05-09。
> 本章合并原 1-7 的 Dashboard 改动，只保留最终口径；旧的补丁式编号不再作为执行依据。

### 1.1 目标与边界

- Dashboard 同一业务含义只保留一个可信来源。
- 主指标来自后端摘要、周报、健康度、快照或对比接口；前端只做展示映射、排序、跳转、加载态、空态和错误态，不新增主指标聚合，不使用本地数据重算 Dashboard 主指标。
- 页面结构和视觉组件继续沿用已落地的 `MetricCard`、`CardHead`、`DashboardHealthCards`、`WeeklyDigestPanel`、`DashboardCompareCard`、`StatusBadge/statusTheme`、`.num-display/.num-mono` 体系。
- 多接口保留，但职责必须清晰：项目摘要管实时主指标，周报管周指标，对比接口管周期 delta，健康接口管健康分解，数据质量接口管可信度明细。

### 1.2 基础数据口径

| 模块 | 最终口径 | 数据来源 |
| --- | --- | --- |
| 项目状态 | 顶部状态 pill 使用统一 `StatusBadge/statusTheme`；`进行中` 走 `in_progress`，`已完成` 走 `completed`，不手写私有灰色 pill。 | `/api/dashboard/project-summary` |
| 计划工期 | 只展示 `summary.plannedStartDate/plannedEndDate`；缺失时显示 `--`，不回读 `currentProject`。 | `/api/dashboard/project-summary` |
| 进度标签 | 使用统一 `StatusBadge`，数字保留 `.num-mono`，视觉 token 走 `statusTheme.info`。 | `summary.overallProgress` |
| 周报面板 | 3 个 BI 指标只消费 weekly digest；风险等级兼容 `severity/level`，不与实时风险总数混算。 | `/api/projects/:id/weekly-digest/latest` |
| CompareCard | `total_progress_change` 表示项目整体加权进度变化，不再是任务进度变化求和；`delayed` 表示截至周期结束日仍延期的任务存量。 | `/api/task-summaries/projects/:id/task-summary/compare` |
| 数据可信度 | 健康度后端只复用 `dataQualityService.buildProjectSummary().confidence.score`；数据质量服务不可用时 `dataTrustScore` 标记不可评估并显示 `暂无`，不再由健康度服务本地估算。 | `/api/data-quality/project-summary` + `/api/health-score/:projectId` |
| 风险与异常待处理 | 合计固定为 `activeRiskCount + activeIssueCount + activeObstacleCount + pendingConditionTaskCount`；同一区块所有数字只来自 `ProjectSummary`。 | `/api/dashboard/project-summary` |
| 分析范围 | 全系统摘要口径固定按接入后统计，不提供历史范围切换，也不保留历史范围兼容分支。历史任务 `standard_task_metadata.is_historical=true` 只作为建模上下文保留，不进入项目摘要、公司摘要、快照与今日进展统计。 | `/api/dashboard/project-summary` + `projectExecutionSummaryService` |
| 今日进展 / 重点任务 | 今日进展只消费 `/today-progress`，展示今日发生进度变化的叶子任务；数据优先取 `task_progress_snapshots` 的昨日/今日快照，快照缺失时用今日 `change_logs(field_name='progress')` 兜底；每行只保留任务名、进度条和 `昨天进度 → 今日进度` 数字。一周重点关注任务只消费 `/focus-tasks`；接口失败显示错误态，不读取本地任务、风险或 localStorage。 | `/api/projects/:id/dashboard/today-progress` + `/api/projects/:id/dashboard/focus-tasks` |

### 1.3 主 KPI 四卡

| KPI | 当前值来源 | 上期值来源 | 展示文案 |
| --- | --- | --- | --- |
| 整体进度 | `/api/dashboard/project-summary` 的 `overallProgress` | `project_daily_snapshot.overall_progress` 最近一条上周快照 | `较上周` |
| 本月偏差 | `/api/dashboard/project-summary` 的 `scheduleVarianceDays / delayDays` | `project_daily_snapshot.delay_days` 最近一条上周快照 | `较上周` |
| 活跃风险 | `/api/dashboard/project-summary` 的 `activeRiskCount` | `project_daily_snapshot.active_risk_count` 最近一条上周快照 | `较上周` |
| 今日待办 | `/api/dashboard/project-summary` 的 `todayTodoCount` | `project_daily_snapshot.today_todo_count` 最近一条上周快照 | `较上周` |

- 后端在 `ProjectSummary` 中返回 `kpiComparisons.weekly`，每项包含 `current`、`previous`、`delta`、`periodLabel` 与 `status`。
- 前端 `DashboardMetricCards` 只消费 `kpiComparisons.weekly` 渲染趋势，不写死 `formatMetricTrend(0)`，也不用当前风险数、当前偏差数冒充趋势变化。
- 上周快照不存在时，趋势显示 `待积累 较上周`，不得展示假“持平”。
- `todayTodoCount` 写入 `project_daily_snapshot`，作为后续周对比事实字段。

### 1.4 执行健康与完成率

| 指标 | 展示位置 | 含义 | 数据来源 |
| --- | --- | --- | --- |
| 执行稳定度 | 进度健康指标分解行 | 健康评分子维度，按延期任务比例、受阻任务比例、负责人缺失比例扣分，不等于完成率。 | `/api/health-score/:projectId` 的 `details.taskExecutionScore` |
| 完成率 | 任务执行情况 Donut | 已完成叶子任务占全部叶子任务的比例，不等同于整体加权进度。 | `/api/dashboard/project-summary` 的 `completedTaskCount / leafTaskCount` |
| 任务状态分布 | 任务执行情况列表 | 已完成、进行中、未开始、已延期的展示分布。 | `/api/dashboard/project-summary` 的任务计数字段 |

- 健康度分解行原“任务执行”统一改为“执行稳定度”，避免与“任务执行情况 / 完成率”混淆。
- `completed`、`leafTaskCount`、`inProgress`、`delayed` 均只使用 `ProjectSummary`；字段缺失时按 `0/暂无` 展示，不回读前端本地叶子任务列表。
- 任务执行情况 Donut 完成率固定为 `completedTaskCount / leafTaskCount`，不得使用 `totalTasks` 作为分母。
- 进度健康指标分解行只消费 `/api/health-score/:projectId` 的 `details`；接口细项未返回时显示 `加载中` 或 `暂无`，不得用 `overallProgress`、`completedRate`、`milestoneRate`、`100 - totalSignals*10` 等前端临时算法兜底。

### 1.5 进度健康与任务执行卡视觉

| 位置 | 最终规格 |
| --- | --- |
| `ScoreRow` / `StatusRow` label | `text-xs text-slate-600`；去掉 `font-medium`；不使用 `text-[13px] font-medium text-slate-700`。 |
| `ScoreRow` / `StatusRow` value | `num-mono text-xs text-slate-600`；零值保持 `text-slate-400`；不使用 `text-[13px] font-semibold text-slate-900`。 |
| `ProgressBar` 高度 | `h-[3px]`。 |
| `ProgressBar` tone | 由数值语义阈值统一计算：`>=80 bg-emerald-500`、`>=60 bg-slate-500`、`>=40 bg-amber-500`、`<40 bg-rose-500`；`loading` 或不可用状态走 `neutral=true / bg-slate-300`；不得从 `ScoreRow` / `StatusRow` 传入业务分类色。 |
| 分类 dot | 保留各行原业务色作为唯一分类信号，尺寸为 `h-1.5 w-1.5`。 |
| Donut 尺寸 | 使用 `110×110`，`r=48`，`strokeW=6`；不使用 `120×120 / r=52 / strokeW=7`。 |
| Donut 中心数字 | 使用现有 `metric-value-lg`，颜色为 `text-slate-900`；不硬编码 `text-[28px]`，不使用 `tracking-[-0.03em]`，不使用 drop-shadow filter。 |
| Donut 副标签 | 使用 `.eyebrow` 类，即 `text-[10px] font-semibold tracking-[0.08em] text-slate-400`。 |
| Donut 底环 | 使用 CSS var 或 Tailwind stroke token 表达 `slate-200`，不得继续硬编码裸 `rgb(226, 232, 240)`。 |

### 1.6 风险与异常追踪卡

- 待处理合计仍固定为 `activeRiskCount + activeIssueCount + activeObstacleCount + pendingConditionTaskCount`。
- 4 个信号 tile label 统一为 2 字：`风险 / 问题 / 阻碍 / 条件`；不使用 `活跃风险`。
- tile grid 使用 `mt-4 grid grid-cols-4 gap-2`；第 4 项 `条件` 跳转 `/projects/${projectId}/gantt`，与 `阻碍` 一致。
- tile title 字体与 `ScoreRow` / `StatusRow` label 一致：`inline-flex min-w-0 items-center gap-2.5 text-xs text-slate-600`，dot 为 `h-1.5 w-1.5`，文字使用 `truncate`。
- tile value 字体与 `StatusRow` value 一致：`num-mono mt-1 text-xs`；非零 `text-slate-600`，零值 `text-slate-400`；不得使用 `metric-value-md`、`.num-display` 或 `font-semibold`。
- 信号分布标题使用 `text-xs text-slate-600`，不显示右侧 `{totalSignals} 项 / 暂无` 数字。
- stacked bar 放在 `CardHead` 和 tile grid 之间；容器 `mt-5 space-y-1`；bar 使用 `flex h-[3px] overflow-hidden rounded-full bg-slate-100`。
- totalSignals > 0 时按 `count / totalSignals` 分段，颜色固定为 `风险 rose-500 / 问题 amber-500 / 阻碍 slate-400 / 条件 blue-500`；totalSignals === 0 时不渲染分段，只保留底条。
- stacked bar 需有 `role="img"` 与 `aria-label="信号分布：风险 X、问题 Y、阻碍 Z、条件 W"`。
- 底部说明删除 `待满足条件 N 项。`；只保留 `riskSuggestion`，例如 `首要关注：...` 或 `暂无活跃风险`。

### 1.7 无数据不造分

- 缺少可评估输入时，不使用默认高分代替真实业务分。
- 后端负责可评估性判断，前端只按 `metricAvailability` 展示。
- “不可评估”不等同于真实 0 分；前端展示为 `暂无`，总健康分按 0 权重参与，避免虚高。

| 指标 | 可评估条件 | 不满足时 |
| --- | --- | --- |
| 进度兑现 | 存在叶子任务，且项目或任务可推导计划进度窗口。 | 分项值按 0 参与总分，前端显示 `暂无`。 |
| 执行稳定度 | 存在叶子任务。 | 分项值按 0 参与总分，前端显示 `暂无`。 |
| 里程碑交付 | 存在里程碑任务。 | 分项值按 0 参与总分，前端显示 `暂无`。 |
| 风险阻碍 | 存在任务或任一风险/问题/阻碍/条件/自动延期信号。 | 分项值按 0 参与总分，前端显示 `暂无`。 |
| 数据可信度 | 由数据质量服务评估；无可评估任务时返回低可信度。 | 不再返回空数据高可信度；数据质量服务不可用时标记 `暂无`。 |

- `projectHealthService` 增加 `metricAvailability` 和 `metricUnavailableReasons`，向前端暴露分项是否可评估。
- `progressDeliveryScore`、`taskExecutionScore`、`milestoneDeliveryScore`、`riskControlScore` 不再在缺输入时使用默认高分。
- `dataQualityService.computeConfidence` 在无可评估任务时返回低可信度，并生成 0 分维度分解；健康度服务不得在数据质量服务不可用时自行估算 `dataTrustScore`。
- `DashboardHealthCards` 按 `metricAvailability` 将不可评估分项显示为 `暂无`，进度条不展示最小可见进度；健康分项接口未返回前显示 `加载中`，失败后显示 `暂无`。

### 1.8 验收标准

- 顶部状态、健康度、数据可靠性、进度 pill 使用统一标签体系，无单独私有颜色。
- 计划工期只来自后端摘要，缺失时显示 `--`。
- CompareCard 的 `total_progress_change` 表示项目整体进度变化，不再是任务进度变化求和。
- Dashboard 四张主 KPI 卡的趋势文案来自后端 `kpiComparisons.weekly`；无历史快照时显示 `待积累 较上周`。
- `project_daily_snapshot` 表具备 `today_todo_count` 字段，快照服务写入该字段。
- 健康度中的 `数据可信度` 与数据可靠性服务同源；健康度封顶规则包含 `<70` 与 `<50` 两档。
- 同屏不再出现容易混淆的“任务执行 90% / 完成率 0%”双口径文案；健康分项接口不可用时不展示前端估算分。
- 空项目不会显示 `进度兑现 100%`、`里程碑交付 95%`、`风险阻碍 100%` 这类虚高分项；无任务的数据质量可信度不再高于 70。
- `DashboardHealthCards.tsx` 中不得残留 `text-[10px] font-medium tracking-wide`、`num-display text-[28px]`、Donut drop-shadow、硬编码 Donut 底环 rgb、风险卡 `活跃风险` tile label、`grid-cols-3` tile 布局、`h-2` stacked bar、右侧 `{totalSignals} 项`、`metric-value-md num-display` tile 数字或 `待满足条件` 底部文案。
- 验证覆盖：Dashboard 相关前端测试、`DashboardHealthCards` 测试、前端 typecheck、后端快照/项目摘要/健康度/数据质量测试。

## 2. 里程碑页最终收口项

> 最后修订：2026-05-09。
> 本节只保留里程碑页最终口径，旧的 M14/M15、右侧详情面板、WBS 缩进、`节点状态` 详情列、日期后追加偏差文案等历史方案均不再作为执行依据。

### 2.1 页面定位与数据边界

- 里程碑页定位为 `进度管控 / 里程碑`，用于快速识别关键节点是否偏移、是否兑现、是否存在健康问题。
- 主数据入口统一为 `DashboardApiService.getProjectSummary`，消费 `/api/dashboard/project-summary?projectId=` 返回的 `milestoneOverview`；前端不新增主指标、不重新定义主口径。
- 前端只负责展示映射、搜索、筛选、跳转、轻量格式化和旧数据兼容兜底；正式口径以后端 `milestoneOverview` 字段为准。
- 视觉以 Dashboard 当前设计语言为主参照，落到 `Breadcrumb`、裸表头、`MetricCard`、`surface-card`、`.num-display/.num-mono`、`badge-micro` 与 Tailwind token 体系。

### 2.2 首屏结构

| 区域 | 最终口径 |
| --- | --- |
| 标题区 | 使用局部 `MilestonesPageTitle`：Breadcrumb、中文业务域 `进度管控`、中文主标题 `里程碑`、右侧轻量操作区；不使用卡片式 `PageHeader`，不显示英文模块名，不把业务域做成 pill/badge/border。 |
| 操作按钮 | 只保留 `刷新`、`导出节点表`、`任务管理`；返回能力交给面包屑；outline 按钮使用轻量小按钮规格，`任务管理` 为主按钮。 |
| KPI 四卡 | 复用共享 `MetricCard`，消费 `milestoneOverview.summaryStats` 与 `milestoneOverview.kpiComparisons.monthly`；eyebrow 固定为 `SHIFTED / ONTIME / DUE / RISK`；无历史时显示 `待积累 较上月` 与稳定水平线。 |
| 月度对比 | `较上月` 只能来自 `kpiComparisons.monthly` 的 `ready/insufficient_history` 状态；只有后端明确返回 `delta = 0` 才显示持平，前端不得把缺字段伪装成持平。 |
| 健康横幅 | 当前页闭环，不跳转。容器按健康强度使用轻量淡色块：`normal = bg-emerald-50/60 border-emerald-100`、`needs_attention = bg-amber-50/60 border-amber-100`、`abnormal = bg-red-50/60 border-red-100`；不额外显示状态 pill。 |

### 2.3 健康问题口径

- 健康横幅只展示 3 个业务问题 chip：`计划未对齐`、`责任未确认`、`数据待完善`。
- `任务已结束` 不再作为问题；`偏差需关注` 属于关注/风险信号，不进入健康问题 chip。
- `计划未对齐` 是前端唯一计划类大标签；缺基线、缺当前计划、映射待确认、未关联基线、基线版本已移除等具体根因由后端保留，不作为前端独立标签展示。
- `数据待完善` 只表示完成事实数据缺口，典型条件是任务已完成但缺少系统生成的 `actual_end_date`；缺基线/缺当前计划不借 `数据待完善` 表达。
- 前端展示不做问题优先级排他；同一节点如存在多个独立根因，可以同时展示多个问题标签。
- 点击健康摘要 chip 后，筛选节点偏差表、自动展开第一条命中节点并滚动过去，展开区同步高亮对应问题字段。
- 节点行内问题标签只作用于当前节点：点击后保持当前节点展开，并高亮对应字段；再次点击同一问题标签取消高亮，不改变全局健康筛选状态。

### 2.4 节点偏差表

- 表头裸露在页面背景上，不显示 `MILESTONE` 英文 eyebrow；中文标题 `节点偏差表` 使用 `text-[15px] font-semibold text-slate-900`。
- 搜索框与标题同行右对齐，规格为 `h-8 text-xs placeholder:text-slate-400 border-slate-200 ring-1 ring-inset ring-slate-200/60`，搜索图标 `h-3.5 w-3.5 strokeWidth=1.5`。
- Tabs 使用透明下划线样式：`text-xs gap-4`，活跃态 `text-blue-600` 与 `h-[2px]` 下划线；Tabs 只显示标签文本，不带数量。
- 列表按 `milestone_level` 拉平分组：`一级里程碑 / 二级里程碑 / 三级里程碑`；不展示 WBS 缩进、`├` 前缀或 `L2/L3` 层级标识。
- 分组标题使用 `.section-group-label`：`text-[13px] font-semibold tracking-tight text-slate-800`；计数使用 `· N` 且为 `text-xs text-slate-400`；组间使用 `border-t border-slate-100/80 pt-5 first:pt-2`。
- 组内按状态紧急度排序：已逾期 → 7天内 → 待完成 → 已完成；同状态再按计划日期和名称排序。
- 行容器使用全宽原生 `button`：`border-b border-l-2 border-b-slate-100 border-l-transparent hover:bg-slate-50/70`；选中态使用 `border-l-blue-500 bg-blue-50/40`。
- 行内第 1 行展示状态图标、节点名、状态 badge、问题 badge、右侧进度百分比和 chevron；进度数字按状态着色：overdue `text-red-600`、soon `text-amber-600`、completed `text-emerald-600`、其它 `text-slate-700`，`%` 与数字同色。
- 行内第 2 行为进度/时间叙事，使用 `text-xs text-slate-500`；选中态隐藏行内叙事，避免与展开区重复。

### 2.5 行内叙事

- 叙事句始终围绕“进度/时间”，不因为 `mapping_pending` / `owner_unconfirmed` 切换成数据质量话题。
- 已完成节点显示实际完成事实：按期为 `实际 {actual} · 按期完成`；延后为 `实际 {actual} · 延后 {N} 天`，其中 `延后 N 天` 使用 `text-amber-600` 普通权重；提前为 `实际 {actual} · 提前 {N} 天`。
- 已完成但缺 `actual_end_date` 显示 `完成时间缺失`，并归入 `dataIncomplete`。
- 已逾期节点显示 `已逾期 {N} 天 · 尚未开始` 或 `已逾期 {N} 天 · 进度 {X}%`。
- 7 天内节点显示 `今日到期 · 进度 {X}%` 或 `还剩 {N} 天 · 进度 {X}%`。
- 无 baseline + 有 current：`按当前计划推进 · 当前 {current}`。
- 无 baseline + 无 current：`待完成 · 日期待补齐`。
- 有 baseline + 无 current：`按基线推进 · 基线 {baseline}`。
- 有 baseline + current 时，根据当前计划相对基线输出 `按基线推进 / 较基线延后 / 较基线提前` 与当前日期或进度。

### 2.6 行内展开区

- 点击节点行后在当前行底部展开详情区，再次点击同一行收起，点击另一行自动切换；不默认展开首个节点，不使用 Dialog，不使用右侧固定详情栏。
- 展开区位于当前节点行底部，保留 `data-testid="milestone-detail-panel"`；容器使用 `border-t border-slate-100 pt-4 pb-1 mb-5`。
- 三列容器使用 `grid grid-cols-3 gap-0 divide-x divide-slate-200/70`，用两条 1px hairline 把 `时间线 / 偏差分析 / 关联执行` 锁成三联结构。
- 三列横向内边距为 `pr-6 / px-6 / pl-6`；section header 使用 `text-xs font-medium text-slate-700 mb-2`。
- Col 1 `时间线` 固定 3 行槽位：`基线`、`当前计划`、`实际`。有日期时只显示 `{标签} {日期}`；不在日期后追加 `计划无偏差 / 计划延后 / 实际延后` 等偏差字段。无日期时只保留 label，label 使用 `text-slate-300`，值为空；删除 `待补齐`、`—`、`N/A` 等占位文案。
- Col 2 `偏差分析` 固定 3 行：第一行对应基线并留空；第二行展示 `计划 vs 基线` 的偏差结论；第三行展示 `实际 vs 当前计划` 的偏差结论。不能计算偏差时保留空白行；实际未完成时显示 `实际尚未完成`。
- Col 3 `关联执行` 固定 3 行：第一行展示父级路径（有父级才显示），格式为 `A › B`，不加 `属于：`；第二行展示 `关联任务 N 个 · 已完成 M 个`；第三行为 inline `进入任务管理 →`。
- 删除 `对应关系`、`最近更新`、节点备注和低价值空态字段；问题解释只由健康横幅、节点问题标签和字段高亮承担。

### 2.7 偏差与高亮

- 展开区偏差拆成两段：`planVariance = baseline -> currentPlan`（计划偏差）与 `actualVariance = currentPlan -> actual`（实际偏差）；不再展示 `baseline -> actual` 的混合总偏差。
- 两段偏差相加即总偏差，界面不单独展示总偏差。
- 字段高亮粒度下沉到字段行；样式仅使用 `border-l-2 pl-2.5` 和问题色边线，不使用 `-ml-3`、背景色或 ring。

- `dataIncomplete`：高亮 Col 1 `实际`。
- `ownerUnconfirmed`：高亮 Col 3 `关联任务` 统计行。

## 3. 计划编制三页共享计划树与业务动作收口

> 追加日期：2026-05-10。
> 范围定位：承接 v1.2 BI 化、v1.3 全面优化、v1.3.5.2 全站视觉对齐，并对照 `业务流程优化清单.md` 中 `计划编制` 板块。第 3 章不再按零散页面问题堆叠，而统一收口为：共享计划树底座、三页字段预设、常规编辑动作、三页业务动作和验收记录。旧文中关于 `确认冻结`、`进入草稿态页面`、`观察池/修订池前台流程`、`9:3 常驻版本检查器`、`项目基线页内切月度计划 Tab` 的描述均以本章为准废止。

### 3.1 总原则：比 Excel 更省事，而不是比 Excel 更复杂

项目基线、月度计划、任务列表都是应用的计划数据入口。三页不是三套独立表格，也不是三套版本治理流程，而是共享一套 `PlanningTreeTable` 计划树底座：用户像编辑一张工程计划表一样录入、复制、调整、删除、缩进、排序、暂存和保存；系统负责自动生成、自动纠偏、自动留痕、自动写快照和把数据喂给后续算法。

三条边界固定：

- 底座负责编辑原子能力：WBS 树、层级缩进、单元格编辑、行选择、添加同级/子级、删除、升降级、上移下移、撤销重做、批量处理、只读/可编辑切换、键盘操作、视觉密度和轻量在线协作提示。
- 页面负责字段预设和业务语义：项目基线看总进度计划，月度计划看当月承诺，任务列表看现场当前执行。
- 业务动作负责流程闭环：项目基线发布版本，月度计划确认月份，任务列表更新现场事实；便捷/兜底动作只辅助生成和纠偏，不抢常规编辑主线。

### 3.2 共享计划树底座

共享底座统一命名为 `PlanningTreeTable`。项目基线、月度计划、任务列表都必须复用同一套表格壳和交互语言，只允许通过 `variant` 和列配置改变默认字段。

底座能力清单：

| 能力 | 统一口径 |
| --- | --- |
| WBS 树 | depth 缩进、WBS 编号、连接线和父子层级必须统一；参考里程碑偏差表的 `1.75rem × depth` 缩进、`wbsLabel` 和 `├` 前缀，但三页需使用更完整的计划表密度。 |
| 层级视觉 | 父级、二级、施工任务用字重和缩进区分；父级更重，施工任务正常字重；所有状态标签统一使用同一字体规格，不再每类标签一套字体。 |
| 编辑能力 | 单元格直接编辑，行号/WBS 区承载选择、添加、删除、升降级、上移下移、里程碑标记；不把高频操作藏在常驻三点菜单里。 |
| 批量能力 | 选中后出现轻量批量条，承接批量删除、复制、粘贴、填充、日期平移、责任人/责任单位等页面允许的批量字段。复制/粘贴使用 TSV 口径，允许从 Excel 复制行进入计划树；单行粘贴到多选行时按“填充”处理；从当前单元格粘贴多行多列时按表格覆盖写入，而不是新增行。 |
| 键盘录入 | 表格支持单元格焦点、方向键移动、Tab 横向连续录入、Enter 纵向连续录入；复制当前单元格、粘贴到当前单元格、Shift 连续选择都属于共享底座能力，三页不得各自实现一套。 |
| 表格效率 | WBS 与任务名称列冻结，避免宽表横向浏览时丢失层级上下文；大数据量按渐进渲染加载，保证首屏响应优先，不再一次性渲染全部计划行。 |
| 只读/可编辑 | 不切换独立页面。点击页面业务按钮后，当前表格原地从锁定切到可编辑；暂存、保存、取消、撤销、重做都在当前页面完成。 |
| 校核定位 | 阻断项、建议项、信息项点击后要高亮并滚动定位到表格行，交互与里程碑健康问题一致。 |
| 后端协作 | 多人编辑、锁、暂存、版本草案、冲突合并属于底座和后端内部能力；前台不要求用户理解“强制解锁草稿”等系统概念。项目 owner 是异常处理责任人，协作规则按在线表格常见体验自动处理。当前落地口径为：保存发生版本冲突时，非重叠字段组自动合并；同一字段组冲突才进入人工确认。完整多人光标、实时协同和 CRDT/OT 级合并不作为计划编制当前阶段必做项。 |

协作强化口径：

- 保留现有 `version` 乐观锁、WebSocket 通知和保存时版本校验，不引入 CRDT/OT。
- 字段组自动合并作为共享底座能力，不写在单个页面里；名称、日期、进度、责任、结构、里程碑等字段组之间互不冲突时自动保存。
- 普通用户不看到 `409 / VERSION_MISMATCH / 强制解锁` 等技术概念；前台只提示“已合并协作更新”或“该字段刚被更新，请确认后继续”。
- 单元格级操作日志本轮不做。计划编制的版本记录、任务快照、变更留痕仍按业务动作写入，不把每一次光标级编辑都升级为审计事件。
- 批量操作日志本轮也不做。复制、粘贴、填充、批量删除、批量平移等按表格编辑能力处理，只在保存/发布/月度确认/任务快照等业务动作层写留痕。
- 轻量在线提示只表达“有人正在查看/编辑”，不阻断常规编辑；owner 只处理异常协作状态，不作为日常入口。

视觉要求：

- 表格是页面主视觉，不再被右侧版本栏、异常面板或多层工具栏挤压。
- 主表默认不出现横向拖拽条；列数必须符合页面业务，不用“更多列”塞回一堆低频字段。
- 普通行白底，hover 轻微变色，选中用左侧蓝线；异常/建议仅用小标记或左线，不做整行大面积染色。
- 层级标题、表头、单元格、标签和按钮规格对齐 v1.3.5.2 已确认的 Dashboard / 里程碑设计语言。

### 3.3 三页默认字段预设

| 页面 | 页面角色 | 默认字段 |
| --- | --- | --- |
| 项目基线 | 项目总进度计划的当前生效版本和自动重编入口 | `WBS / 任务名称 / 计划开始 / 计划完成 / 工期` |
| 月度计划 | 系统自动生成的当月执行承诺，用户复核后确认 | `WBS / 任务名称 / 计划开始 / 计划完成 / 目标进度` |
| 任务列表 | 现场当前执行表，承接实时排期和进度维护 | `WBS / 任务名称 / 计划开始 / 计划完成 / 进度 / 状态 / 责任人 / 责任单位` |

字段边界：

- 项目基线不默认展示责任单位/人、执行进度、状态/差异、执行关联、目标进度、备注、来源、差异明细。它回答“总计划是什么”。
- 月度计划不展示历史基线选择器、主骨架差异、待重整、独立修正流程。它回答“本月准备怎么干”。
- 任务列表不展示基线版本、月度确认、延期申请、历史差异、修订候选。它回答“现场现在怎么干、干到哪了”。
- 不进默认列的字段不得在前台主表回流；若仍需后端保留，必须进入详情、算法日志、报表或管理后台，不作为三页主表字段。

### 3.4 常规编辑动作与底座关系

常规动作本质上都是底座能力，不应被包装成复杂业务流程。

| 动作 | 底座实现 | 页面差异 |
| --- | --- | --- |
| 新建/生成 | 初始化一张可编辑计划树 | 项目基线可空白、导入、当前任务列表生成；月度计划只由算法生成；任务列表可直接新增施工任务。 |
| 编辑 | 当前表格原地切为可编辑 | 项目基线保存会发布版本；月度计划确认前可编辑；任务列表长期可编辑。 |
| 暂存 | 保存未发布/未确认调整 | 用户只看到“暂存”，不看到草稿态页面。 |
| 保存/发布/确认 | 提交当前表格状态 | 项目基线是保存发布新版；月度计划是确认当月计划；任务列表是保存现场执行事实。 |
| 取消 | 放弃当前未保存调整 | 不使用“作废草稿 / 放弃修订”等重流程词。 |
| 撤销/重做 | 表格历史栈 | 三页一致。 |
| 添加/删除/升降级/排序 | 行号/WBS 区或快捷键 | 三页一致，字段和后续业务影响由页面决定。 |
| 标记里程碑 | 行号/WBS 区或里程碑小图标 | 三页都可用；兑现由任务完成事实自动回流里程碑页。 |

### 3.5 项目基线业务动作

项目基线定位：`项目总进度计划的当前生效版本 + 自动生成新版基线入口`。它不是日常填报页，核心价值是当现场任务列表长期变化后，系统可以基于当前执行事实自动重编一版总进度计划，用户只做复核和微调。

前台业务动作：

| 业务动作 | 触发位置 | 业务含义 |
| --- | --- | --- |
| 建立项目基线 | 无基线空态 / 页头入口 | 初始化第一版总进度计划，可空白、导入、从当前任务列表或 WBS 模板生成。 |
| 编辑总进度计划 | 当前计划状态带 / 表格区 | 当前表格原地可编辑，用户像改计划表一样调整名称、层级和计划日期。 |
| 生成新版基线 | 当前计划状态带的轻量按钮；偏差达到阈值时健康横幅提示 | 系统基于当前任务列表、实际进度、累计偏差和历史修正偏好自动生成待发布新版总进度计划。 |
| 暂存 | 编辑操作区 | 保存未发布调整，不改变当前生效版本。 |
| 保存发布新版 | 编辑操作区 | 弹出发布确认，允许系统建议版本号，用户可编辑版本名；发布后自动成为唯一当前生效项目基线。 |
| 取消 | 编辑操作区 | 放弃当前未保存调整，回到当前生效基线。 |
| 版本记录 | 当前计划状态带 | 合并历史版本、版本差异和保存发布留痕；历史版本只用于查看和差异核查，不切换现场执行版本。 |

不再作为前台动作：`进入草稿态页面`、`确认冻结`、`强制解锁草稿`、`发起修订`、`继续草稿`、`处理观察池 / 修订池`。后端可继续保留 draft、lock、revision log、suggestion pool，但前台统一表达为编辑、暂存、保存发布、系统建议。

项目基线自动生成算法：

`当前生效项目基线 + 当前任务列表排期 + 实际进度快照 + 累计偏差/变更信号 + 用户历史修正偏好 -> 待发布新版总进度计划表`

算法必须处理：新增任务自动纳入、删除任务退出后续计划集合、计划日期滚动、里程碑偏移、父子层级调整、WBS 稳定 ID 映射、人工覆盖保留、后续工期重排和异常项定位。阻断项只保留会影响自动生成稳定运行的问题：空任务名、父子层级断裂、计划开始晚于计划完成、关键映射断裂、关键里程碑缺失或无法定位。

阈值建议：

| 场景 | 提示策略 | 版本建议 |
| --- | --- | --- |
| 小范围计划修正 | 健康横幅轻量提示，不抢主线 | `v1.1 / v1.2` |
| 项目基线重编 | 总完工日期偏移 > 7 天、关键里程碑偏移 > 3 天、关键线路影响后续工期 > 7 天、受影响施工任务 > 15%、新增/删除主要分部或分项、任务累计新增/删除 > 10%、连续两个月月度计划大量纠偏 | `v2 / v3` |

### 3.6 月度计划业务动作与生成算法

月度计划定位：`系统自动生成的当月执行承诺，用户复核后确认`。它相比 Excel 的价值是自动算出本月该做什么，不要求用户理解来源差异、主骨架、待重整或独立修正流程。

前台业务动作：

| 业务动作 | 触发位置 | 业务含义 |
| --- | --- | --- |
| 选择月份 | 页头月份带 | 查看或处理指定月份计划。 |
| 确认上月执行结果 | 生成本月计划前；若上月已确认但未归档则轻量提示 | 归档上月实际执行结果，作为本月生成算法输入；不回改上月承诺。 |
| 生成本月计划 | 未生成月份主按钮 | 系统按算法生成本月计划表，用户不选择来源。 |
| 编辑本月计划 | 未确认计划表 | 用户复核算法结果，必要时修改范围、日期和目标进度。 |
| 暂存 | 编辑操作区 | 保存未确认调整。 |
| 确认当月月度计划 | 编辑操作区 | 锁定本月承诺快照，作为兑现率和月末关账边界；空月计划也可确认。 |
| 取消 | 编辑操作区 | 放弃未确认调整。 |

不再作为前台动作：`查看与主骨架差异`、`处理待重整`、`独立修正流程`、`确认冻结`、`强制解锁草稿`、`作废草稿`。确认后不再修正本月计划；后续错误和现场变化进入任务列表执行、上月执行结果归档和下月算法纠偏。

月度计划生成算法：

`当前生效项目基线 + 当前任务列表排期 + 上月执行结果归档 + 实际进度快照 + 用户历史修正偏好 -> 本月计划`

算法规则：

- 优先纳入上月滚入且未完成、本月计划完成、本月计划开工、正在施工且本月继续推进、本月控制节点/里程碑相关任务、当前排期已提前到本月的任务。
- 默认排除已完成且无需本月承接、远期任务且未具备开工条件、已取消或删除且不影响本月承诺的任务。
- 合并优先级为 `上月执行结果/已开工实际 > 当前任务列表排期 > 当前生效项目基线`。
- 目标进度尽量精确：本月内应完成默认为 100%；跨月任务按计划曲线、工期比例或工程量权重估算；已开工任务不得低于当前实际进度。
- 用户在未确认月度计划中的人工修改记录为 `manual_override`，同月保存和确认时优先保留，不反复覆盖用户判断。
- WBS 结构改动、拆分/合并、映射断裂等异常只在少数行标注 `需确认`，后台记录算法原因，不把复杂差异前台化。

已存在月度计划时，前台不提供“重新生成草稿/重新生成本月计划”作为常驻动作；用户直接在表格中调整并保存。算法重算只发生在未生成月份的首次生成、下月生成或后端纠偏任务中。

月末关账口径：月末关账仍保留，但它不再是复杂独立修正流程。它最好放在 `生成本月计划` 附近，作为生成新月计划前的必要归档动作：不完成上月归档时，不允许生成下月计划；首月、无上月计划或上月无数据时可跳过。

### 3.7 任务列表业务动作

任务列表定位：`现场当前执行表`。它是当前排期、执行进度、条件阻碍和实际快照的主入口。用户在表里改计划、填进度、补责任、维护条件和阻碍；系统自动写快照、自动判定状态、自动进入月度计划和项目基线重编算法输入。

前台业务动作：

| 业务动作 | 前台展现 | 业务含义 |
| --- | --- | --- |
| 更新现场进展 | `进度` 单元格直接编辑 | 记录现场实际推进情况；进度到 100% 时提示确认完成，不确认则回退到 99%。 |
| 调整当前计划 | `计划开始 / 计划完成` 单元格直接编辑 | 维护现场滚动排期，自动进入月度计划、月末关账和项目基线重编算法输入。 |
| 维护责任 | `责任人 / 责任单位` 单元格直接编辑 | 支撑责任主体分析、提醒送达和任务总结。 |
| 维护条件 | 条件单元格或浮层 | 维护开工前置条件、满足状态和补充说明。 |
| 维护阻碍 | 阻碍单元格或浮层 | 登记、更新、解除现场阻碍。 |
| 标记里程碑 | 行号/WBS 操作区或里程碑图标 | 标识执行层关键节点；兑现由完成事实自动回流。 |
| 删除施工任务 | 行号/WBS 操作区触发最小确认 | 删除误录任务或现场不再实施的任务；删除后退出后续计划集合。 |

不再作为前台动作：`发起延期 / 提交延期申请 / 审批延期申请`、`确认里程碑兑现`、`进入月末关账承接`、`关键路径人工插链`、`关闭 / 取消 / 删除` 三选一。前台统一只表达 `删除施工任务`；关闭、取消、归档等历史语义由后台留痕自动处理。

系统自动闭环：

- 每次更新进度、实际开始、实际完成或完成任务时，自动写入进度快照。
- 进度首次大于 0 自动记录实际开始；进度达到 100% 且确认后自动记录实际完成。
- 状态由进度、计划日期、实际完成、条件、阻碍自动计算。
- 超过计划完成且未完成自动判定延期；延期申请全链路删除，由自动延期状态、计划完成变更留痕和进度快照替代。
- 计划开始 / 计划完成变化自动进入月度计划生成、月末关账和项目基线重编算法。
- 条件阻碍自动进入提醒、风险问题、执行稳定度和报表分析输入。

## 4. 任务总结页视觉收口项

> 范围定位：承接 v1.2 BI 化、v1.3 全面优化、v1.3.5.2 全站视觉对齐，并对照 Dashboard 与里程碑页已经确认的首屏结构。本文收口 `任务管控 / 任务总结` 页的页头、KPI、结果摘要和总结列表叙事化；月度兑现归入报表分析的进度偏差视角，不作为任务总结页内容。

### 4.1 最终原则

- 任务总结页定位为 `任务管控 / 任务总结`，服务于已完成任务归档、按时/延期完成情况和完成结果回看。
- 前端不新增主指标口径；任务总结主数据继续消费 `/api/task-summaries/projects/:projectId/task-summary`。接口未明确返回项目全量任务数前，不用已完成任务集合伪装“总任务数”。
- 页头直接对齐里程碑页裸表头实现：Breadcrumb、中文业务域 `任务管控`、中文主标题 `任务总结`、右侧轻量操作区；不使用卡片式 `PageHeader`，不把业务域做成 pill/badge/border。
- KPI 卡片复用 Dashboard / 里程碑页已经使用的共享 `MetricCard` 格式：`eyebrow + 中文标题 + .num-display 大数字 + 月度趋势文案 + 右侧 sparkline + 右上角 icon + compact density`。
- 总结列表定位为“归属完成台账”，第一层采用归属对象卡片化表达，不再平铺每条完成任务；按 `分部工程 / 分项工程 / 专项工程 / 楼栋 / 区域 / 责任单位 / 责任人` 七类主数据展示归属对象，展开后再用共享 Table 承接所含任务明细。
- 七类分组必须来自明确主数据 ID 或结构节点 ID：分部/分项来自 WBS 结构树，专项/楼栋/区域只来自项目范围维度，责任单位来自参建单位台账，责任人来自项目团队成员；前端不得按展示文本扫描任务后自行造组。
- 归属对象按“大的任务对象”处理。点击归属对象卡片后，在卡片下方打开与单个任务展开区同样样式的归属完成复盘面板，面板下方再承接所含任务明细台账；归属完成复盘沿用选中浅蓝背景，覆盖到 `所含任务明细台账` 标题行前停止；单个任务过程复盘只在归属对象展开后的任务明细中进入，普通任务选中态覆盖任务自身行和任务自身详情。

| 任务结果行 | 归属展开区内的任务明细 | 任务明细台账固定列为 `序号 / 状态 / 任务名称 / 责任人 / 责任单位 / 完成日期`；状态列只在延期时显示 `延期` 文本 chip，按时/待确认只保留 sr-only 状态文本；任务名称旁不再重复显示延期 badge。点击任务行后在明细表内展开任务过程复盘，普通任务选中态覆盖任务自身行和任务自身详情。 |
| 展开区 | 结果复盘 + 变化摘要 + 完成过程 + 过程结论 | 展开区只承接任务总结自身职责：完成结果、开工条件、阻碍、进度/状态变化和总结结论；不另设“所属上下文”字段。 |
| 月度兑现 | 移出任务总结页 | 月度兑现属于月度计划承诺兑现，应归入 `报表分析 / 进度偏差` 或月度计划兑现分析，不在任务总结页展示。 |

### 4.3 数据口径说明

| 指标 | 数据来源 | 展示口径 |
| --- | --- | --- |
| 完成任务 | `stats.total_completed` | 已纳入任务总结的已完成任务数，不命名为“总任务数”；回答完成规模。 |
| 按时完成率 | `stats.on_time_count / stats.total_completed` | 已完成任务中的按时完成占比，分母使用 `stats.total_completed`；回答完成质量。 |
| 延期任务 | `stats.delayed_count` | 已完成任务中延期完成数量；回答延期压力。 |

| KPI 月度趋势 | `/api/task-summaries/projects/:projectId/task-summary/trend` | 四张卡第三行统一使用 `较上月 / 待积累 较上月 / 持平 较上月` 文案和 sparkline，视觉格式与 Dashboard、里程碑页 KPI 卡一致；趋势月份按实际完成月份归集，`延期任务` 的上升视为负向，其他三卡上升视为正向。 |
| 总结列表任务 | `groups[].tasks[]` 扁平化后排序 | 只作为归属对象聚合和展开后任务明细的数据源；第一层不直接平铺任务。任务明细仍按 `completed_at` 倒序排序。 |
| 归属维度 | `attribution_groups[].dimension` | 固定支持 `分部工程 / 分项工程 / 专项工程 / 楼栋 / 区域 / 责任单位 / 责任人` 七类归属维度；归属维度直接作为总结列表主 Tabs，默认进入 `分部工程`。前端只消费接口返回的 `attribution_groups`，不得再通过任务展示字段自行聚合。 |
| 归属对象 | `attribution_groups[]` | 归属对象必须带稳定 `sourceId` 与 `taskIds`：WBS 节点使用任务树节点 ID，范围维度使用 `project_scope_dimensions` 绑定 ID，责任单位使用 `participant_unit_id`，责任人使用 `assignee_user_id`。选中后形成一个归属对象上下文，其任务集合只按 `taskIds` 回取。 |
| 归属汇总指标 | `attribution_totals[dimension][optionId]` | 后端新增 `taskAttributionSummaryService` 统一计算 `{ total, completed, on_time, delayed, on_time_rate, completion_rate, max_delay_days, avg_delay_days, recent_completed_at, health_level }`。`total` 使用该归属下全量任务，`completed` 使用已完成任务；`avg_delay_days` 使用延期完成任务作为分母，前端只展示后端口径，不再从任务明细行重新计算均延；0 完成归属不进入第一层 `attribution_groups`，但可作为后续数据质量分析依据。 |
| 分组数据源 | WBS / 范围维度 / 参建单位 / 项目团队 | `分部工程、分项工程` 只来自 WBS 结构树；`专项工程、楼栋、区域` 只来自项目范围维度 `specialty/building/region`，不得从任务标题、WBS 标题或 `wbs_code` 文本匹配；`责任单位` 只来自参建单位管理 `participant_units`；`责任人` 只来自项目团队 `project_members` / 用户 ID。缺少正式绑定时进入 `未关联` 数据质量桶，不与正式主数据混合。 |

| 完成结果 | `task.completed_at`、`task.planned_end_date`、`task.delay_total_days`、`task.delay_records[]` | 表格行展示完成日期；状态列只在延期时展示延期 chip。展开区展示计划截止、实际完成、延期天数和延期原因摘要。 |
| 完成过程 | `timeline_events`，并可补充 `delay_records[]` | 过程复盘优先消费任务时间线事件；延期记录可作为过程补充进入完成过程，同时仍在完成结果区展示延期说明。 |

### 4.5 归属维度台账与归属复盘

“分组”在任务总结页内最终定义为归属对象复盘能力。归属对象像一个大的任务：它由同一 `分部工程 / 分项工程 / 专项工程 / 楼栋 / 区域 / 责任单位 / 责任人` 下的已完成任务聚合而成。主列表第一层展示归属对象，不展示单条任务；展开归属对象后，先给出归属层的完成复盘，再承接所含任务明细台账。

**归属维度交互**：

- 搜索框只做文本搜索，不再承载归属按钮；placeholder 使用 `搜索归属、任务、责任人...`。
- `分部工程 / 分项工程 / 专项工程 / 楼栋 / 区域 / 责任单位 / 责任人` 作为总结列表主 Tabs，默认进入 `分部工程`。
- 当前 Tab 下的卡片行是该维度的归属对象，例如 `主体结构`、`机电安装`、`1#楼`。
- 当前 Tab 下的归属对象来自后端 `attribution_groups`，前端仅按 `taskIds` 回取任务明细；不得用归属名称、责任人名称、责任单位名称等展示文本作为分组 key。
- 搜索关键词可命中归属对象名称，也可命中归属对象下所含任务的任务名、责任人、责任单位、完成日期等字段。
- 点击归属对象卡片后，在当前卡片下展开归属完成复盘面板；再次点击可收起。
- 原 `全部 / 按时 / 延期 / 本月完成` 状态筛选删除，不再作为任务总结页列表筛选。

**归属完成复盘面板**（复用任务展开区样式）：

| 区块 | 展示内容 | 口径 |
| --- | --- | --- |
| 归属完成结果 | `完成任务 N/M（完成率 X%）`、`按时任务 N 项（按时率 X%）`、`延期任务 N 项 · 最大延期 X 天`、最近完成时间、主要延期任务 | 从归属对象下的任务集合聚合，只表达完成事实；完成率并入完成任务行、按时率并入按时任务行，避免把同一分子分母拆成多行。 |
| 变化摘要 | 开工条件变化次数、阻碍记录次数 | 只回答该归属对象完成过程中开工条件如何形成、阻碍如何出现或处理；不展示“施工执行”和“完成批次”数量，避免与数据置信度、完成事实重复。 |
| 归属完成过程 | 按工程逻辑压缩后的过程段落 | 不逐条堆叠任务；按时间与施工语义合并为 `条件形成 / 阻碍演变 / 并行推进 / 完成收口` 等过程段。 |
| 过程结论 | 一句话总结归属对象完成过程 | 基于归属任务集合事实生成；没有明确因果时只写并列事实，不编造“导致 / 因此”。 |
| 所含任务明细台账 | 当前归属对象下的任务行 | 继续使用任务明细台账样式；不再受 `全部 / 按时 / 延期 / 本月完成` 状态 Tabs 影响，因为该组 Tabs 已删除。 |

**归属过程压缩规则**：

- 先按归属对象收集任务集合，再汇总每个任务的 `timeline_events`、`delay_records[]`、计划截止、实际完成和延期天数。
- 所有过程事件按日期排序，同日或同时间窗事件合并为同一过程组；并行发生的任务事件不强行写成因果链。
- 过程组再按工程语义归类：开工条件形成、阻碍出现与解除、过程推进、延期记录、完成收口。
- 连续同类过程组合并为一个阶段；每个阶段只保留最能说明过程的代表任务，例如最早完成、最近完成、延期最长、阻碍最多、关联关键节点的任务。
- 叙事使用工程管理语言，例如 `开工条件陆续满足`、`阻碍集中出现在安装收口阶段`、`多项任务并行推进`、`最终完成收口`；过程文案保持业务表达，不写成字段或状态枚举。
- 只有当延期记录或过程事件明确提供因果时，才允许使用 `导致 / 因此`；否则使用 `期间 / 同步 / 随后 / 最终` 等时间与并列表达。

### 4.6 任务行展开区过程复盘

任务总结的展开区不是任务详情跳转入口；它要复盘“任务是怎么完成的”。展开区不再另设“所属上下文”。展开区固定四块：

| 区块 | 展示内容 | 口径 |
| --- | --- | --- |
| 完成结果 | 计划截止、实际完成、按时 / 延期结论、延期原因摘要 | 来自任务行结果字段和 `delay_records[]`；只展示与完成结果直接相关的信息。 |
| 变化摘要 | 开工条件条数、阻碍记录条数 | 只帮助用户判断这项任务完成过程中开工条件和阻碍如何变化；不展示“施工执行”条数。 |
| 完成过程 | 开工条件、阻碍处理、关键节点、过程推进、延期记录、实际完成 | 优先来自 `timeline_events`；`delay_records[]` 可作为过程补充进入过程线，标签保持现有过程类型口径。 |
| 过程结论 | 一句话总结完成过程 | 基于完成结果与过程记录生成事实型结论；没有明确因果时只写并列事实，不编造“导致 / 因此”。 |

**过程线展示原则**：

- 不采用纵向单列时间线。纵向单列会导致展开区右侧留空、页面高度被单个任务过度拉长。
- 展开区过程线采用横向/分栏过程带方向：在同一展开区宽度内按时间组排列，每组内并列展示同日或同时间窗事件。
- 同一天发生多件事时，在同一时间组内并列展示，例如 `开工条件` 与 `阻碍处理` 同日发生时不强行排成因果链。
- 有持续区间的事件显示为时间段，例如 `04-04 - 04-08 阻碍处理中`；无区间的事件显示为单日节点。
- 默认展示关键事件，不把每条低价值更新全部摊开；超过阈值时提供 `展开全部过程`。
- 没有足够过程事件时显示轻量空态：`暂无过程事件，待开工条件、阻碍和完成动作进入时间线后展示。`

**过程类型映射**：

| 类型 | 示例 | 色彩 |
| --- | --- | --- |
| 开工条件 | 条件确认、条件记录、条件补齐 | blue |
| 阻碍处理 | 阻碍记录、延期记录、处理记录 | red |
| 关键节点 | 关联节点校核、计划节点 | amber |
| 过程推进 | 计划完成、实际完成、状态/进度记录 | slate |

### 4.7 验收标准

- 任务总结页首屏与里程碑页保持同一页头节奏：裸表头、无卡片式标题头、无业务域 pill。
- 页头按钮只显示 `刷新` 与 `导出总结`，且按钮尺寸、圆角、字号、图标尺寸与 Dashboard / 里程碑页一致。
- KPI 四卡全部使用共享 `MetricCard`，格式与 Dashboard / 里程碑 KPI 一致；固定为 `完成任务 / 按时完成率 / 延期任务 / 本月完成`，第三行展示月度趋势文案与 sparkline；不再出现“总任务数”和“完成里程碑”首屏 KPI。
- 页面不再出现 `结果摘要区`、`结果摘要`、`已收口` 这些非必要层级。
- 总结列表不显示英文 eyebrow，不显示 `返回任务管理` 按钮；标题、搜索框和 Tabs 样式与里程碑节点偏差表一致。
- 搜索框必须支持归属对象、任务、责任人搜索；不得再出现搜索框内嵌 `归属` 按钮或归属 Popover。
- 总结列表主 Tabs 固定为 `分部工程 / 分项工程 / 专项工程 / 楼栋 / 区域 / 责任单位 / 责任人`；不得再出现 `全部 / 按时 / 延期 / 本月完成` 状态 Tabs。
- 总结列表第一层使用归属对象卡片化台账，不显示表头和序号列；每张卡片展示归属名称、任务规模、按时率和叙事摘要。完成率只在展开复盘中作为结果字段出现，不在卡片头部使用彩色 chip。
- 点击归属对象卡片后打开归属完成复盘面板；面板样式与单个任务展开区一致，不新增独立报表样式。
- 归属完成复盘下方必须展示所含任务明细台账，任务明细表头固定为 `序号 / 状态 / 任务名称 / 责任人 / 责任单位 / 完成日期`。
- 任务明细行点击后在当前行底部展开任务过程复盘；普通任务选中态覆盖任务自身行和任务自身详情；展开区不另设“所属上下文”。
- 展开区过程线不采用纵向单列时间线；允许同时展示变化摘要与横向/分栏过程线。
- 任务总结页不再展示月度兑现；月度兑现后续进入进度偏差相关页面承载。

### 4.8 任务总结列表归属卡片台账视觉精修（2026-05-09 补充）

**背景**：任务总结列表在 100-200 条已完成任务规模下，主要问题不是滚动性能，而是第一层如果继续像任务明细表一样铺开，会把“归属复盘”压回普通任务台账。最终改为归属对象卡片台账：主 Tabs 选归属维度，第一层展示归属对象卡片，展开后展示归属完成复盘和所含任务明细。任务明细仍使用共享 `Table`，保证真正的数据台账合规。

本节覆盖 §4.2 的总结列表落地方式，并取代“双行 semantic row”“紧凑单行 div 台账”“第一层表格化归属台账”以及旧版状态重复提示的描述。

## 6. 任务列表页视觉收口项
