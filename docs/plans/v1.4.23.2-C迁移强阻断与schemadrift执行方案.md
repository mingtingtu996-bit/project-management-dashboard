> No production history or existing users need migration. `/api/scope-dimensions and scope_dimensions / project_scope_dimensions adapters` are removed compatibility surfaces and must not return as live write paths.

> 派生自 `v1.4.23.2后端商业化补强与AI可维护体系执行方案.md` 第 4.4（发布与迁移能力面）、7.3（商业化发布阻断门禁）、9.3（唯一"现在就做"项）。
> 触发类：`now_safety` —— 与付费、规模都无关，不做就有生产数据风险。这是 v1.4.23.2 全部底座里**唯一不依赖任何前置、必须立即落地**的一份。
> 一句话职责：**堵住"代码发了、数据库表没建"这个生产洞**，并让代码、迁移、真实库三者状态可比对。

## 0. 为什么这份是 now_safety、必须先做

A（清单化）、B（租户）解决"可维护""能收费"，但它们都不是**立即出事**的。这份不一样——它修的是一个**已经存在于 CI 里、与用户量无关、随时会触发**的生产数据风险洞。哪怕你只有 1 个用户，这个洞触发一次就是"线上 500 / 功能整块挂掉 / 数据写入失败"。

## 1. 真实缺口（本轮核查 deploy.yml，非估算）

`.github/workflows/deploy.yml` 的 `database-migration` job（行 231–277）：

```yaml
# deploy.yml:255-269  —— 缺 secret 时的真实行为
- name: Check migration connection secret
  run: |
    if [ -n "${DATABASE_URL}" ]; then
      echo "can_run=true"
    else
      echo "can_run=false"          # ← secret 缺失
      echo "### Database migration skipped"
      echo "- Deployment will continue without applying migrations in CI."   # ← 关键：继续部署
    fi
# deploy.yml:273-274
- name: Apply pending migrations
  if: steps.migration-config.outputs.can_run == 'true'   # ← can_run=false 时整步跳过
  run: npm run migrate:pending
```

**洞的机制**：`SUPABASE_MIGRATION_URL` secret 缺失（或 runner 网络到不了库）→ `can_run=false` → 迁移步骤被 `if` 跳过 → **但后续部署 job 照常进行**。结果：**新代码上线，它依赖的新表/新列没建**。后端一访问就炸，且炸在生产、炸在用户面前。

文件 [5.5](docs/plans/v1.4.23.2后端商业化补强与AI可维护体系执行方案.md) 已诚实记录此事："deploy workflow 在 migration secret 缺失时仍允许 database-migration skipped 后继续部署"。7.3 也已把"database migration 不能在生产发布中静默 skipped"列为发布阻断门禁——**本文件就是把这条门禁落地**。

> 注：当前 skip 逻辑不是疏忽，注释说明了原因——hosted runner 到 IPv6-only Supabase 直连库不通。所以**不能简单删掉 skip 分支**，要给一条"既能应对网络限制、又不放过真实 pending 迁移"的路径（见第 3 节）。

## 2. 目标

1. **迁移没成功 → 部署必须停**：缺 secret / 连不上库 / pending 迁移失败，生产部署一律阻断，不得继续发版。
2. **pending migration = 0 才放行**（7.3 门禁）。
3. **schema drift = 0**：代码期望的 schema 与真实库 schema 可比对，漂移即阻断。
4. **保留对 IPv6-only 网络限制的合法应对**：不是无脑删 skip，而是把"跳过"从"静默继续"改成"要么走通、要么显式阻断"。

### 2.1 强制口径：skip 不是正常发布路径

本文件里的 migration skip 只能是 break-glass 例外，不是生产发布的常规路径。

| 场景 | 是否允许 skip migration | 必要条件 | 部署结果 |
| --- | --- | --- | --- |
| push 到 `main / master` 的生产发布 | 不允许 | 无 | 缺 secret、连不上库、pending / drift 未确认时直接 fail |
| `workflow_dispatch` + `environment=production` | 原则不允许；仅 break-glass | `migration_skip_confirmation=EXTERNAL_PENDING_ZERO_AND_BLOCKING_SCHEMA_DRIFT_ZERO` + `migration_skip_reason` + `external_migration_evidence_ref`，且 summary 明确写出“外部已执行迁移 / pending=0 / blocking drift=0 的证据” | 缺任一证据仍 fail；有证据时才允许继续 |
| `workflow_dispatch` + `environment=staging` | 可允许 break-glass | 同 production，但必须标明 staging 证据，不得复用 production 证据 | 有证据才允许继续 |
| `environment=preview` | 不进入生产部署链 | 不适用 | 可跳过迁移，但不得影响 production readiness |

exact migration skip confirmation 不能自动等于“迁移安全”。如果缺少可追溯证据，job 必须失败。证据最小字段：

- `migration_skip_reason`：为什么无法由 CI 直接连库执行迁移。
- `external_migration_evidence_ref`：外部迁移 / DBA 执行 / 自托管 runner 执行 / Supabase 控制台执行的证据编号或 URL。
- `migration_skip_confirmation=EXTERNAL_PENDING_ZERO_AND_BLOCKING_SCHEMA_DRIFT_ZERO`：单一、精确且可审计地确认外部证据显示 pending migration 为 0、blocking schema drift 为 0。

因此，执行时不能只加一个布尔输入。必须同时加证据输入、summary 留痕和合同测试；否则等于把“静默 skip”换成“手动 skip”，洞仍在。

## 3. 执行步骤

**3.1 把"静默 skip 后继续"改成"阻断或显式放行"**
- 缺 `SUPABASE_MIGRATION_URL` 时，当前是 `can_run=false` + 继续。改为：**默认 fail 该 job**（从而 `needs: [database-migration]` 的下游部署 job 被阻断）。
- 网络限制的合法出口收敛为一条**显式、可审计**的路径：要么配通迁移连接（推荐：迁移走能连到库的环境/代理），要么精确填写 workflow_dispatch 的 `migration_skip_confirmation=EXTERNAL_PENDING_ZERO_AND_BLOCKING_SCHEMA_DRIFT_ZERO`，并同时填写 `migration_skip_reason / external_migration_evidence_ref`。这些确认必须写入 run summary。**默认路径是阻断，跳过必须是有人显式确认且有证据的例外，不是 secret 一缺就自动发生。**
- `deploy-server` 的条件必须反转：不再接受 `needs.database-migration.result == 'skipped'` 作为 production deploy 放行条件。允许 break-glass 时，`database-migration` job 也必须以“带证据的成功”结束，而不是 GitHub job-level skipped。

**3.2 pending migration 检查独立成门禁步骤**
- 新增脚本 `migrate:check`（区别于 `migrate:pending`）：只读地比对"迁移目录里的迁移"与"库里已应用的迁移记录"，输出 pending 数。
- pending > 0 且未成功应用 → fail。接入 `database-migration` job 或其前置。
- `migrate:check` 必须至少检查以下项，不能只打印 pending 数：
  1. 迁移目录 canonical migration 文件可解析、版本不重复、顺序稳定。
  2. `schema_migrations` ledger 存在且可读。
  3. 目录中存在但 ledger 未记录的 migration 数 = 0。
  4. ledger 中记录但目录不存在的 migration = 0，除非明确登记为 adopted baseline。
     - adopted baseline 的登记不能是口头说明或 runbook 备注，必须落在仓库内可审计清单：`server/migrations/adopted-baseline-ledger-rows.json`。
     - 该清单默认必须为空数组 `[]`；只有经迁移基线认领复核、确认该 ledger 行代表历史基线而非误删 SQL 文件时，才允许写入对应 migration filename。
     - 未写入该清单的 orphan ledger row 一律仍按 `orphan_ledger_rows_present` 阻断；写入清单的 adopted row 必须在 `migrate:check` 输出的 `adoptedBaselineLedgerRows` 中显式展示，不能静默吞掉。
  5. ledger checksum 与当前 migration 文件 checksum 一致；不一致即 fail，避免已应用迁移被本地改写。
     - checksum mismatch 不能通过“把 `schema_migrations.checksum` 覆盖成当前文件 hash”来修绿；那只会抹掉已应用 SQL 与仓库 SQL 的证据差异。
     - 已应用 migration 一旦进入 ledger，文件内容按不可变历史处理；如果确有后续 schema 变更，必须新增 forward migration，而不是改写旧 SQL。
     - 若历史 ledger checksum 对应的是旧文件内容、CRLF/BOM 归一化前内容或已归档基线内容，必须先形成可审计核查记录，再决定恢复旧文件、登记基线事实或补 forward migration。
  6. ledger 为空但业务基线表已存在时 fail，引导走 `migrate:adopt-baseline`，不得重放全量迁移。
  7. 无法连接真实库、无权限读取 ledger 或 introspection 时 fail；不得降级为 warning。
- `migrate:pending` 负责执行；`migrate:check` 负责只读验收。生产 deploy 必须在 `migrate:pending` 后再跑一次 `migrate:check`，确认应用后 pending=0。
- `migrate:pending` 自身也必须先复用同一套结构安全检查（允许的唯一未关闭原因只能是 `pending_migrations_present`，即等价于 `migrate:check --allow-pending`）。只在 CI workflow 前置跑 `migrate:check` 不够；脚本直接被人工、本地任务或外部 runner 调用时，也不得绕过 checksum mismatch、orphan ledger row、重复版本、unsafe baseline replay 等结构风险。
- `migrate:pending` 写入 `schema_migrations` 只能插入新 ledger row，不得通过 `ON CONFLICT DO UPDATE` 或类似 upsert 覆盖已存在 row 的 checksum / version；已应用 migration 一旦重名冲突，应让数据库唯一约束报错并阻断，而不是静默改 ledger。
- 新增只读诊断入口 `migrate:diagnose`：输出 `safeToApplyPending / safeToEvaluateDrift / nextAction / blockingReasonCodes`。当 checksum mismatch、orphan ledger row、重复版本或 unsafe baseline replay 任一未清零时，必须输出 `safeToApplyPending=false`，避免执行者只看到 pending 清单就误跑 `migrate:pending`。
- `migrate:check` 对同一个 `pg.Client` 的 ledger / baseline 查询必须顺序执行；不得在单连接上 `Promise.all([...client.query])` 造成运行时 query-overlap warning。发布门禁输出必须干净，warning 不能被当成“通过但可忽略”的噪声。

**3.3 schema drift 检查**
- 新增脚本 `migrate:drift`：比对代码期望 schema（迁移累积结果 / 或 `CLEAN_MIGRATION_V4.sql` 基线）与真实库 introspection。
- drift ≠ 0 → fail，并在 summary 列出漂移的表/列。
- 落地 v1.4.23.1 4.8 的"schema drift = 0"与 v1.4.23.2 4.4 的"代码、迁移、真实库状态必须可比对"。
- drift 基准必须唯一，不能在执行时自由选择。首版建议固定为：**canonical migration directory + `schema_migrations` ledger 是生产发布基准；`CLEAN_MIGRATION_V4.sql` 只作为空库初始化 / 全量覆盖一致性参考，不替代 ledger**。
- `migrate:drift` 首版最小覆盖范围：
  1. public schema 中业务表是否存在 / 是否多余。
  2. 列名、数据类型、nullable、default 是否一致。
  3. primary key、foreign key、unique constraint、check constraint 是否一致。
  4. 普通索引、唯一索引、部分索引的名称和定义是否一致。
  5. RLS enabled / forced 状态与 policy 名称、policy 命令、using / with check 谓词是否一致；在路线甲下也必须能标注“RLS 不作为隔离依赖”的显式状态，不能误报为数据库兜底。
  6. trigger、function、view、enum、extension、grant / privilege 若首版不能完整比对，必须列入 `drift_coverage_backlog`，并在 summary 标明“未覆盖对象不参与 drift=0 声明”。
- 输出必须分级：`blockingDrift`、`coverageBacklog`、`ignoredLegacyObjects`。只有 `blockingDrift.length === 0` 才可放行；不能用“未覆盖”冒充“无漂移”。
- schema introspection 对同一个 `pg.Client` 必须顺序读取 columns / RLS / policies / constraints / indexes；不得在单连接上并发 `client.query`。如果需要并发，只能使用连接池/独立 client，并补测试证明不会产生运行时 warning。

**3.4 把这些接成发布阻断门禁**
- 在 `deploy.yml` 把 migration 成功、pending=0、drift=0 设为部署 job 的硬 `needs` 前置。
- 对齐 v1.4.23.2 7.3 的发布阻断清单：`database migration 不能静默 skipped` / `pending migration = 0` / `schema drift = 0`。
- 同步更新 `deployWorkflowContract.test.ts`：旧断言必须反转为红灯。
  - 不得再包含 `Deployment will continue without applying migrations in CI`。
  - 不得再包含 `needs.database-migration.result == 'skipped'` 的 production 放行条件。
  - 必须包含 `migrate:check`、`migrate:drift`、`migration_skip_confirmation` 证据输入和 run summary 留痕。
  - 必须有测试证明：缺 `SUPABASE_MIGRATION_URL` 且未提供 break-glass 证据时 workflow contract fail。
- server package scripts 必须补齐 `migrate:check` 与 `migrate:drift`；CI 只能调用 scripts，不得在 workflow 内散写临时 SQL。

**3.5 单元归位**
本文件产出的 CI 步骤与 `migrate:check / migrate:drift` 脚本归 v1.4.23.1 §4.7.1「底座·平台运行观测」单元（A 的 registry 登记，`runtime_scope` 分组标签 = `platform_foundation`），与业务无耦合。

## 4. 验收标准

1. 缺 `SUPABASE_MIGRATION_URL` 时，部署默认**被阻断**，不再静默 skip 后继续。
2. 跳过迁移只能经**显式手动确认 + 外部 pending=0 / drift=0 证据**发生，且确认留痕在 run summary；push 生产发布不得使用 skip。
3. pending migration > 0 时部署 fail。
4. schema drift ≠ 0 时部署 fail，并列出漂移对象。
5. IPv6-only 等网络限制有一条记录在案的合法应对路径，不靠"secret 一缺就自动跳过"。
6. `migrate:check / migrate:drift` 归「底座·平台运行观测」（`runtime_scope` 分组标签=`platform_foundation`），进 A 的 registry。
7. `deployWorkflowContract.test.ts` 已反向保护新门禁：旧的 skipped 继续部署行为会让测试失败。
8. `migrate:check` 覆盖 pending、checksum、重复版本、ledger 缺失、baseline adoption 风险；`migrate:drift` 覆盖首版声明对象并显式列出未覆盖 backlog。
9. adopted baseline 例外必须可审计：默认 `server/migrations/adopted-baseline-ledger-rows.json = []`，未登记 orphan ledger row 仍 fail，已登记 adopted row 进入 `adoptedBaselineLedgerRows` 输出。
10. `migrate:check / migrate:drift` 不得在单个 `pg.Client` 上并发查询真实库；合同测试必须防止运行时 query-overlap warning 重新进入发布门禁。
11. `migrate:pending` 直接调用时也必须先执行结构安全门禁；checksum mismatch / orphan ledger / duplicate version / unsafe baseline replay 未清零时，即使存在 pending migration，也不得开始执行任何 SQL。
12. migration ledger 写入必须保持历史不可变；`schema_migrations` 冲突不得被 upsert 覆盖，checksum 修复不得通过改 ledger 达成。
13. `migrate:diagnose` 必须能在不执行 SQL 的前提下给出机器可读发布诊断：`blocked_before_apply` / `ready_to_apply_pending` / `ready_for_schema_drift_check`，并明确下一动作。

- `migrate:diagnose` 当前为 `status=ready_for_schema_drift_check`，`safeToEvaluateDrift=true`，`nextAction=run_schema_drift_check`。
- 仍有 14 条 `reconciledChecksumMismatches` 作为审计证据输出；它们不再是阻断项，但不能被解释成允许改写旧 migration 或覆盖 `schema_migrations.checksum`。

- 已新增并执行 forward migration：`server/migrations/225_v14232c_schema_drift_reconciliation.sql`。该迁移不改历史 migration、不改 `schema_migrations.checksum`，而是用受审的 forward reconciliation 对齐 declared coverage 内的真实 schema 决策。

- 本轮验证已覆盖：在 `server/` 下执行 `npm run migrate:check`、`npm run migrate:diagnose`、`npm run migrate:drift`，以及聚焦 Vitest（migration safety / schema drift parser / deploy workflow contract）与 `npx tsc -p server/tsconfig.json --noEmit --pretty false`。

这意味着文件执行者必须把两层口径分开：**发布阻断门禁在 declared coverage 下已通过**；**全对象 schema drift 覆盖仍有 backlog，后续扩展前不得作为全量 PostgreSQL schema 证明**。

### 4.2 历史迁移不可变与 forward migration 规则

已经进入 `schema_migrations` ledger 的 migration 文件按历史证据处理：

- 可以把被误改的已应用 SQL 恢复成 ledger 匹配内容。
- 不得把新的业务 schema 变更塞回旧 migration 文件。
- 不得通过更新 `schema_migrations.checksum` 让当前文件 hash 与 ledger 对齐。
- 若最终目标需要删除旧对象，必须新增 forward migration。例如 old scope 兼容表的最终边界由 `224_v14232_drop_legacy_scope_dimension_tables.sql` 承担，而不是改写 `067_create_scope_dimensions_tables.sql`。

schema drift 的 expected schema 必须按完整 migration 序列计算，包括后续 `DROP TABLE`。因此后续 parser / drift 工具不能只看 `CREATE TABLE` 和 `ALTER TABLE`，否则会把已经被 forward migration 删除的旧表错误地当成仍应存在。

### 4.3 后续执行路线

后续收口顺序调整为：

1. 保持 `migrate:check` 结构门禁绿色：pending=0、blocking checksum mismatch=0、orphan=0、duplicate=0、unsafe baseline replay=false。14 条 `reconciledChecksumMismatches` 只能作为审计事实继续输出，不能退化成静默豁免。
2. 保持 225 作为已应用 forward migration，不再修改该文件；后续若真实库还需要变化，必须新增下一号 forward migration。
3. 后续重点从“处理 209 条 blocking drift”转为“扩展 coverage backlog”：`trigger`、`function`、`view`、`enum`、`extension`、`grant`。每扩展一个对象类，都必须先补 parser/introspection/比较规则，再用真实库或 fixtures 证明不会产生误报。
4. 每轮扩展或新增 migration 后重跑 `migrate:check`、`migrate:diagnose`、`migrate:drift`。只要 declared coverage 内重新出现 `blockingDrift`，生产发布门禁必须重新阻断。
5. 只有 declared coverage 下 `blockingDrift.length=0`，且 coverage backlog 明确列出未覆盖对象时，才允许声明 schema drift gate 通过；只有 backlog 清空后，才允许声明“全 PostgreSQL 对象 drift=0”。

因此，当前 C gate 的放行语是“declared coverage release-ready”，不是“全对象 coverage complete”。

## 5. 边界与诚实声明

- 不改业务迁移内容、不改 `CLEAN_MIGRATION_V4.sql` 基线语义，只增加"是否已正确应用 + 是否漂移"的校验与阻断。

- blocking checksum mismatch 不是 adopted baseline 可豁免项；已登记的 `reconciledChecksumMismatches` 是审计事实，不是改写旧 migration / 改 ledger checksum 的通道。后续任何 schema 变化仍必须走 forward migration 或受审 reconciliation。
- `225_v14232c_schema_drift_reconciliation.sql` 已应用，后续不得为了微调文案或遗漏项回改该 migration；如需继续调整真实库，必须新增 forward migration。
