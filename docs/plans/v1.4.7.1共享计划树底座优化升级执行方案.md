## 0. 2026-06-01 final range-tree boundary (authoritative)

This v1.4-series plan follows the final range-tree model. There is no production history or existing user data that needs a compatibility layer.

Authoritative engineering object types are exactly: `phase / section / building / basement / floor / physical_zone / functional_area`.

The following compatibility surfaces are deleted and must not be reintroduced in runtime code, migrations, or frontend contracts:

- `zone / professional / subproject / custom` as engineering object types.
- `zone_object_id / professional_object_id` task fields.
- `project_materials.professional_object_id` and `engineering_categories.professional_object_id`.
- `legacy_object_type`, deprecated object-type arrays, legacy bridge/backfill helpers, and old scope adapter functions.
- `/api/scope-dimensions`, `scope_dimensions`, and `project_scope_dimensions` as active application surfaces.

Professional/system/domain/method semantics remain business facts through `specialty_type`, `engineering_category_id`, `standard_work_code`, template metadata, and project profile facts. They are not range-tree objects.

Any older section in this document that mentions deleted object types, deleted fields, old scope tables, or compatibility adapters is superseded by this boundary.
# v1.4.7.1 共享计划树底座优化升级执行方案

## 1. 目标

v1.4.7.1 的目标是基于 `v1.3.5.3` 已经形成的 `PlanningTreeTable / PlanTreeEditor` 共享计划树，进一步把 `项目基线 / 月度计划 / 任务列表` 三个页面的表格逻辑、编辑边界、业务动作边界、保存规则、删除规则、列能力和即时校验规则统一下来。

本章不是新建页面，也不是替代 v1.4.7。它是 v1.4.7 的补充章节，专门解决共享表格底座如何承接 v1.4 到 v1.4.13 已经确定的业务体系。

核心目标：

```text
项目基线、月度计划、任务列表继续共用同一个共享计划树底座
共享计划树采用行卡片混合体作为统一渲染形态，按使用场景在列表、卡片、详情三种视图之间自动切换
项目基线、月度计划默认阅读，点击编辑按钮后原地进入编辑态；任务列表默认作为快速浏览和详情查看页，点击编辑 / 进入编辑时打开计划表工作台并在工作台内编辑
表格编辑操作与业务操作必须分开定义
用户在表格里的大部分动作仍是普通编辑动作，系统后台负责理解业务影响
保存前只形成编辑缓冲，不立即形成业务事实
保存时进入编辑提交治理；发布、确认时进入阅读态业务动作治理
复杂业务对象不强塞进表格编辑态，开工条件、阻碍、验收影响等通过 chip 摘要、行号区快捷入口、行内弹层和右侧抽屉分层承接
```

v1.4.7.1 先确定共享计划树底座口径与渲染形态。后续再按本章口径修正 v1.4.14、v1.4.15、v1.4.16，避免变更留痕、删除保留、数据质量治理继续把"编辑操作"和"业务操作"混在一起。

## 3. 核心结论

共享计划树必须分成三层：

```text
阅读态：默认状态，用于查看、筛选、展开、定位、查看提示和进入业务动作
编辑态：项目基线 / 月度计划在当前页原地进入；任务列表在计划表工作台内进入，用于单元格编辑、复制粘贴、删除行、撤销重做、列配置和批量维护
业务动作层：发布基线、确认月计划、生成基线、生成任务、登记阻碍、勾选开工条件等改变业务状态或进入专项事实的动作
```

三层不能混用：

```text
阅读态不是只读页面，而是业务动作的入口
编辑态只处理表格编辑缓冲，不直接写业务事实
保存是编辑态动作，表示结束本轮表格编辑；发布、确认等业务动作必须在阅读态触发
存在未保存编辑时，业务动作必须先要求用户保存或取消
```

共享计划树统一采用行卡片混合体作为渲染形态：

```text
视觉是卡片，行为是表格
键盘焦点系统按虚拟表格坐标编址，Tab、方向键、Enter、F2、Esc 行为与 Excel 一致
复制粘贴、TSV 粘贴、填充、批量、撤销重做与纯表格完全等价
不同节点类型、不同字段类型通过卡片内的主带、数据带、事项带分层承载
三种视图（列表 / 卡片 / 详情）共享同一组件、同一数据、同一编辑缓冲、同一焦点系统
```

用户视角尽量简单：

```text
用户看到的是编辑、保存、取消、撤销、重做、删除、发布、确认、登记阻碍、勾选条件等自然动作
用户不需要理解物理删除、软删除、lineage、source_mode、pending_realign、revision lock、mapping confidence 等技术概念
系统后台根据 v1.4 系列规则判断这些动作的业务含义
```

## 4. 阅读态与编辑态

阅读态和编辑态在用户视角必须是轻区别，而不是两个业务入口、两套流程。任务列表允许用计划表工作台承载编辑沉浸感；该工作台属于当前页面的编辑层，不是新页面、不是第二个任务列表入口。

用户可以这样理解：

```text
阅读态 = 看表、查表、点进去处理业务
编辑态 = 像 Excel 一样改这张表
```

前端表现原则：

```text
默认看表
项目基线 / 月度计划点击编辑后原地变成可编辑表格
任务列表点击编辑后打开计划表工作台，并在工作台内进入可编辑表格
表格自动切换到对应视图，从阅读卡片视图切到编辑列表视图；任务列表大图编辑默认使用列表表格形态
项目基线 / 月度计划在当前表格顶部或底部出现保存、取消、撤销、重做
任务列表在计划表工作台顶部出现保存、取消、撤销、重做、复制、粘贴、字段配置、批量操作等重编辑动作
共享表格顶部状态条显示编辑态提示；任务列表该状态条位于计划表工作台内
保存或取消后回到阅读态并切回阅读视图；任务列表保存或取消后关闭计划表工作台并回到普通任务列表页
发布基线、确认月计划等业务动作可以在页面工具栏常驻显示
进入编辑态或存在未保存内容时，业务动作保持可见但置灰，不隐藏、不跳转
```

共享表格顶部状态条只在编辑态出现，统一承载以下轻提示：

```text
有未保存更改
有协作更新，保存时将自动合并
已合并他人的 N 处无关修改
该字段刚被更新，请确认后继续
```

状态条不弹窗、不打断编辑；只有同字段冲突、必填缺失、非法日期、循环依赖等阻断保存问题才阻止保存。

不得把阅读态 / 编辑态做成：

```text
两个独立页面
两个主菜单入口
草稿工作台
修订中心
需要用户理解锁、版本冲突、来源映射的复杂流程
```

阅读态和编辑态的区别对用户要轻，对系统要清楚：系统依靠这个边界判断哪些只是保存前编辑意图，哪些已经成为保存后的业务事实。

### 4.1 阅读态

阅读态是项目基线、月度计划、任务列表的默认状态。

阅读态允许：

```text
展开 / 折叠层级树
筛选 / 搜索 / 排序
查看表格字段
查看校核条、行级提示、数据问题定位；任务列表可查看健康横幅
查看版本记录、历史快照、差异摘要
查看里程碑、关键节点、影响验收、责任归属等只读信息
通过事项 chip 进入行内弹层或抽屉处理阻碍、开工条件、影响验收
通过事项带末端常驻链接登记阻碍、新增开工条件
通过行号区菜单进入任务详情、查看关键路径、智能展开
触发业务动作，例如生成基线、确认月计划、生成任务
```

阅读态不允许：

```text
直接改单元格
直接删除行
直接批量填充字段
直接复制粘贴写入表格
通过失焦自动保存进度或日期
```

### 4.2 编辑态

编辑态通过当前页面的 `编辑` 按钮原地进入，不新建页面，不跳转草稿页。

进入编辑态后，系统创建表格编辑缓冲区：

```text
当前表格数据副本
pending operations
dirty rows
dirty cells
local history stack
column visibility state
basic validation state
```

编辑态允许：

```text
改单元格
新增行
新增任务草稿行
删除行
TSV 粘贴
多选浮条批量改字段
调整层级
调整排序
切换 category_type (转为分部 / 子分部 / 分项 / 工序 / 作业步骤)
标记 / 取消里程碑
选择前置任务
选择工程对象
选择责任单位
输入责任人
撤销 / 重做
取消编辑
保存
```

编辑态不允许：

```text
直接添加阻碍
直接关闭阻碍
直接添加开工条件
直接删除开工条件
直接处理风险 / 问题
直接验收通过 / 作废
直接作废图纸或证照
直接修改后台生成的任务编码
直接修改实际开始 / 实际完成日期
```

这些不允许项不是不能操作，而是不属于表格编辑态。它们通过事项 chip、事项带末端常驻链接、主带末端常驻链接、行号区菜单、行内弹层、右侧抽屉或专项页面分层承接，具体规则见 §10。

### 4.3 状态切换

状态切换规则：

```text
点击编辑：阅读态 -> 编辑态，自动切换到编辑视图
点击取消：丢弃未保存编辑缓冲，回到阅读态并切回阅读视图
点击保存：提交编辑缓冲，后端治理通过后回到阅读态
保存失败：保留编辑态和用户编辑内容，提示阻断原因
发布基线：阅读态业务动作，必须基于已保存的基线草稿或当前计划执行
确认月计划：阅读态业务动作，必须基于已保存的月计划执行
任务列表保存：编辑态保存当前任务事实，成功后回到阅读态
存在未保存编辑时：发布、确认等业务动作必须禁用或提示先保存 / 取消
业务动作按钮：页面常驻显示；处于编辑态或存在未保存内容时置灰，提示请先保存或取消当前编辑
视图切换：阅读态与编辑态切换时自动应用视图自动切换规则，用户手工覆盖偏好后按个人偏好沿用
```

### 4.4 轻刷新与协作更新

共享计划树不要求用户通过浏览器刷新页面来获取最新数据。

```text
页面提供刷新按钮，语义是轻刷新当前表格数据，不重载整页
阅读态点击刷新：重新拉取当前表格数据，保留筛选、展开、滚动位置、列配置和视图选择
编辑态且无本地修改：可直接刷新为最新服务端数据
编辑态且有本地修改：不覆盖本地编辑，只把服务端最新数据作为保存时的 merge base
任务保存、批量保存、删除、恢复、进度更新成功后，后端广播 project.tasks.changed / task.changed
任务列表阅读态收到变更事件后，自动轻刷新当前表格数据
任务列表编辑态且无本地修改时，收到变更事件后自动轻刷新当前表格数据
任务列表编辑态且有本地修改时，收到变更事件后不覆盖本地编辑，只更新 merge base
收到协作更新时：只在编辑态顶部状态条显示有协作更新，保存时将自动合并
保存时非冲突字段组自动合并；同字段冲突才阻断保存
```

任务列表应补齐类似 Dashboard 的轻刷新按钮，用于拉取最新任务事实、进度快照和派生摘要；不得使用整页重载作为主刷新方式。

不得出现这些前台流程：

```text
进入草稿态页面
强制解锁草稿
作废草稿
进入修订池
处理观察池
来源链路弹窗
技术冲突页面
```

这些可作为后端内部状态或治理记录存在，不作为普通用户主流程。

### 4.5 协作与保存信号的克制层级

共享计划树必须把协作提示、自动合并提示、冲突提示和保存阻断提示放进同一套信号层级，避免行级提示、状态条、toast、弹窗和校核条同时堆叠。

信号分级：

| 等级 | 信号 | 表现 | 是否阻断 |
|---|---|---|---|
| L1 | 行级协作 presence | 行内弱提示，例如"张三正在查看 / 编辑" | 不阻断 |
| L2 | 自动合并结果 | 表格上方状态条或 toast 一次，例如"已合并 N 项协作更新" | 不阻断 |
| L3 | 同字段组冲突 | 保存时轻确认 / 冲突处理对话框，展示本地值和服务端值 | 阻断本次保存，处理后继续 |
| L4 | 业务规则阻断 | 保存或业务动作阻断对话框，定位到具体行、字段或事项 | 必须处理后继续 |

显示规则：

```text
任意时刻最多同时显示 2 级协作 / 保存信号
高等级信号出现时，自动收起或隐藏低等级信号
L3 / L4 出现时隐藏 L1 / L2
L2 只出现一次，不持续占用页面
L1 只在 hover、选中行、编辑态或协作用户正在同一区域时显示
业务规则阻断优先级高于协作冲突
协作冲突优先级高于自动合并提示
自动合并提示优先级高于行级 presence
```

L3 冲突处理规则：

```text
只在保存时出现
只展示同字段组冲突，不展示全部协作更新
必须展示本地值、服务端值、字段中文名和所在行
用户处理后继续保存，不进入独立冲突页面
```

L4 阻断规则：

```text
只处理无法保存或无法执行业务动作的问题
必须提供定位能力，点击后跳到具体行、字段、chip 或抽屉分段
不能用 toast 承载 L4
不能把 L4 混入普通协作提示
```

## 5. 编辑操作统一认定规则

编辑操作是用户在共享表格编辑态中完成的表格维护行为。编辑操作只改变编辑缓冲区，不直接改变业务事实。

标准编辑操作：

```text
改单元格
新增行
新增任务草稿行
删除行
TSV 粘贴
多选浮条批量改字段
调整层级
调整排序
切换 category_type
选择显示字段
增加可显示字段
撤销
重做
取消编辑
```

编辑操作的统一规则：

```text
保存前不写 change_logs
保存前不写 operation_logs 业务摘要
保存前不触发物理删除
保存前不触发风险问题升级
保存前不触发通知中心持久提醒
保存前不反写基线、月计划、任务事实
保存前只做轻量即时校验和本地编辑历史维护
```

编辑操作进入保存时，才由后端解释为：

```text
新增业务对象
更新业务字段
删除业务对象或移出当前表格
结构调整
里程碑标记变化
责任归属变化
计划日期变化
进度事实变化
范围对象变化
```

任务列表中的新增任务固定按同一口径处理：

```text
新增任务草稿行 = 编辑操作
保存后生成 tasks 记录 = 业务事实写入
```

任务列表不保留独立"新建任务"按钮。新增任务统一由共享表格编辑态承担；任务列表的新增行、粘贴行、批量导入和批量维护进入计划表工作台完成。需要补充详细字段时，在该草稿行上通过列配置、行内字段、行侧详情或行详情弹层继续补充，但不得另起一套任务创建入口。

不得出现：

```text
表格新增任务和按钮新建任务两套入口并存
表格新增的任务和弹窗新增的任务规则不同
表格新增绕过工程对象、责任单位、状态、任务编码、来源映射或数据质量校验
弹窗新增比表格新增更正式
```

## 6. 业务操作统一认定规则

业务操作是会改变业务状态、业务链路或历史承诺的动作。业务操作不一定进入表格编辑态。

标准业务操作：

```text
发布项目基线
生成新版项目基线
生成任务 (v1.4.7.2)
确认月度计划
月度关账
登记阻碍
关闭阻碍
新增开工条件
删除 / 标记不适用开工条件
标记开工条件已满足
风险转问题
关闭风险
关闭问题
验收通过
验收作废
图纸版本作废
证照作废
材料封样 / 到场确认
责任单位归档
工程对象停用
通知已知悉 / 静音 / 隐藏
```

业务操作的统一规则：

```text
必须通过后端业务服务提交
必须校验权限、状态、引用关系和生命周期
必须按需要写 change_logs、lineage、快照或 operation_logs
能自动判定的，不要求用户填写原因
需要轻确认的，只做最小确认，不做复杂审批
不属于当前页面的业务操作，不强塞进共享表格编辑态
发布、确认等业务动作在页面上常驻显示；进入编辑态后保持可见但置灰
登记阻碍、勾选条件等高频业务操作允许就地完成（事项带末端常驻链接 / chip 弹层），但仍走业务服务提交，不进编辑缓冲
```

保存不是业务动作层按钮，而是编辑态操作。任务列表点击保存后，后端确实会写入任务事实、进度快照、实际开始 / 实际完成、来源映射和留痕摘要，但用户理解上仍然只是"我改完这张表并保存"。

业务操作与编辑操作的边界示例：

| 用户动作 | 所属层级 | 说明 |
|---|---|---|
| 表格中删除一行 | 编辑操作 | 用户只理解为删除；保存前可撤销，保存时由后端判断真实处置方式 |
| 删除已被引用工程对象 | 业务操作 | 从工程对象管理入口触发，后端判断停用或拒绝 |
| 表格中把进度从 40 改为 60 | 编辑操作 | 进入缓冲区，点击保存后才形成进度事实 |
| 点击保存（任务列表） | 编辑态操作 | 保存本轮表格变更；其中包含进度变化时，后端自动写进度快照、实际开始 / 实际完成 |
| 表格中标记里程碑 | 编辑操作 | 保存后变成里程碑业务事实 |
| 事项带末端 [+ 登记阻碍] 链接 | 业务操作 | 立即写阻碍事实，不进编辑缓冲 |
| 事项 chip 勾选开工条件已满足 | 业务操作 | 立即写条件满足事实，不进编辑缓冲 |
| 发布基线 | 业务操作 | 阅读态执行，基于已保存草稿生成历史快照 |
| 确认月计划 | 业务操作 | 阅读态执行，基于已保存月计划生成当月承诺快照 |
| 关闭风险 | 业务操作 | 不属于表格编辑，风险页面或提醒导流处理 |


视图自动切换规则：

```text

覆盖偏好按 user_id + project_id + surface 持久化，下次进入沿用
```

```text
阅读卡片 → 编辑列表：200ms 过渡，行高从 56px 至 36px，数据带横向重排为单元格，事项 chip 收起到只读列
切换过程中保留：滚动位置、选中行集合、字段焦点、搜索 / 筛选状态
三种视图共享同一组件、同一数据、同一编辑缓冲、同一键盘焦点系统
切换视图不丢失未保存编辑
```

### 7.2.1 工具栏渐进披露

```text

业务动作区独立于表格编辑工具栏
进入编辑态或存在未保存内容时，业务动作可见但置灰
空间不足或窄屏时，优先保留当前状态主动作，其余进入更多
所有按钮必须有 tooltip，tooltip 显示中文动作名和快捷键
```

### 7.5 事项 chip 自适应规则

事项 chip 承载阻碍、条件、影响验收、模板来源、协作状态、数据质量提示等只读或入口型摘要。前置任务不归入事项带，单独由 §7.8 主带末端规则承载。

chip 数量按视图自适应：

```text
列表视图：事项摘要列只显示最高优先级 1 个 chip + 数量徽标（如 + 2），hover 显示完整列表
卡片视图：事项带最多直接显示 3 个 chip，其余收为 + N
详情视图：事项带可显示 5 个 chip，hover 行任意位置展开二级折叠区列出全部
```

chip 类型与视觉（与 v1.4.8-v1.4.12 对齐）：

```text
阻碍 N            红 / 琥珀 / 灰，按严重度(高/中/低)自适应；只显示数量摘要，不在 chip 上表达"影响执行"等语义
条件 硬 M/N 软 K/L  硬条件未满足显示琥珀；硬条件全满足且软条件部分未满足显示蓝灰；全部满足显示绿
影响 N 项验收     蓝灰，只读
模板              浅蓝（v1.4.7.2 生成行）
模板·已调整       浅蓝带边（v1.4.7.2，用户调整非任务名字段后）
责任单位缺失      琥珀，数据质量
工程对象缺失      琥珀，数据质量
协作冲突          琥珀，顶层显示
```

主带前置标志（不属于事项带，但是行级状态指示器）：

```text
开工受阻        硬条件未满足时主带前显示红色"⊘ 开工受阻"标识，优先级高于其他 chip（对齐 v1.4.8 §2.2）
关键路径        在关键路径上的任务行主带前显示红色细线 ━ （对齐现有 CriticalPathGraph 服务）
```

不出现的 chip 类型：

```text
关联风险 N        风险问题不在任务行 chip 上展示，按 v1.4.12 §2 仅在任务列表健康横幅和抽屉基本信息分段显示数量摘要
关联问题 N        同上
阻碍影响执行      不在 chip 上表达，由任务列表健康横幅按 §9.3 承担
进度停滞          同上
```

chip 优先级（在 §9.4 异常项优先级基础上具体化）：

```text
阻断保存       红色边框，必显
协作冲突       琥珀，顶层显示
强业务提醒     琥珀，保存时集中确认
执行健康问题   红 / 琥珀
只读派生信息   蓝灰，按视图容量决定是否常驻
```

chip 空间不足裁剪规则（卡片视图 3 槽位、列表视图 1 槽位时的保留优先级）：

```text
优先级 1（必显）：阻断保存类 → 协作冲突
优先级 2（强业务）：开工受阻标识 → 阻碍 chip → 硬条件未满足 chip
优先级 3（执行健康）：责任单位缺失 → 工程对象缺失
优先级 4（信息型）：影响验收 → 模板 → 软条件

裁剪算法：
  1. 按优先级排序所有待显示 chip
  2. 从高到低填入可用槽位
  3. 剩余 chip 合并为 "+ N" 徽标，hover 展开完整列表
  4. 同优先级内按时间倒序（最新在前）
  5. 列表视图 1 槽位只显示优先级最高的 1 个 chip，其余全部进 "+ N"
```

chip 行为：

```text
阅读态：chip 只读，点击进入对应承载（行内弹层 / 抽屉 / 跳转专项）
编辑态列表：chip 仍保持只读，由对应单元格或行号区菜单进入业务动作
编辑态卡片 / 详情：chip 仍只读，业务动作通过事项带末端常驻链接（§7.6）或行号区菜单触发
前置任务不通过事项 chip 编辑，统一走 §7.8
不允许通过 chip 单元格直接修改业务事实，业务事实仍由对应业务服务提交
```

### 7.6 事项带末端常驻链接

事项带末端用于提供高频业务动作的发现入口。该机制让用户在自然操作中发现功能，不需要任何主动引导。

```text
阅读态：
  对应业务为空时，事项带末端不显示链接（保持阅读视觉清爽）
  对应业务有内容时，显示 chip
编辑态：
  对应业务为空时，事项带末端显示浅灰链接：[+ 登记阻碍] [+ 新增条件]
  对应业务有内容时，显示 chip；同时事项带末端仍保留浅灰链接供继续追加
  链接视觉密度统一为浅灰小字，hover 变深，点击触发对应行内弹层
```

入口分布：

```text
[+ 登记阻碍]   → 行内弹层"快速登记阻碍"(3 字段，对齐 v1.4.8 §2.3)
[+ 新增条件]   → 行内弹层"新增开工条件"(类型 + 名称)
前置任务       → 不在事项带末端，由 §7.8 主带末端常驻承载
```

发现机制：

```text
阻碍、条件、前置任务三类业务通过统一的末端常驻链接模式被自然发现
用户在任意工序行进入编辑态，自然看到事项带末端的入口
事项带末端不堆积超过 2 个链接，避免视觉噪音
低频业务(如责任单位归档、风险问题处理)不放事项带末端，由专项页面承担
```

### 7.7 工程对象作用域条

工程对象不应每行选一次。建筑工程的典型场景是大量同质任务挂在同一工程对象上(例如 1#楼 3F 的全部工序都属于"1#楼 3F")。共享计划树提供"作用域条 + 父级继承 + 主带后缀"三重机制赋予工程对象。

作用域条位于共享表格顶部，默认折叠：

```text
当前作用域:  1#楼 ▾   3F ▾   [全部区域] ▾   切换 / 清空
```

作用域条规则：

```text
作用域条不是筛选器，不隐藏不在作用域的行，只为新增提供默认值
设定作用域后:
  新增的任务自动继承当前作用域工程对象
  从作用域之外的任务正常显示，主带工程对象后缀仍展示真实归属
  作用域条按 user_id + project_id + surface 持久化最近一次选择
工程对象赋予的四种路径:
  路径一: 模板生成时一次性指定(v1.4.7.2 §6 笛卡尔积)
  路径二: 作用域上下文继承(本节)
  路径三: 父级继承(分部/子分部/分项继承到工序)
  路径四: 多选行批量改(浮条"改工程对象")
父级和作用域都未设置时，工程对象字段标记"待补充"，由校核条统一引导补齐
```

工程对象在表格中的呈现：

```text
主带末端固定显示工程对象后缀:
  单对象: "· 1#楼 3F"
  多对象: "· 1#楼 3F, 4F (+1)"
  hover 显示完整列表
  编辑态点击进入工程对象选择器
列表视图:作为字段列存在，默认显示
工程对象选择器分维度展示(楼栋/楼层/区域/分期/专业)，可多选
选择器提供"从当前作用域继承"快捷按钮
```

工程对象在三页的差异：

```text
项目基线 / 月度计划: 工程对象快照只读
任务列表: 工程对象可编辑，作用域条仅在任务列表生效
```

作用域条状态变化表：

| 状态 | 视觉 | 行为 |
|------|------|------|

### 7.8 前置任务展示与发现机制

前置任务在任务列表是高频可编辑业务动作，是关键路径成立的核心操作之一。但由于 v1.4.7.2 模板生成已经按 previousSibling / parallel / custom 自动展开默认依赖，绝大部分前置关系不需要人工调整。前端展示必须在"日常视觉清爽"和"功能可被发现"之间取得平衡。

展示规则按页面与状态差异化：

```text
项目基线 / 月度计划:
  不展示前置任务(基线只回答"总进度计划是什么"，月度计划只回答"本月承诺")
  字段配置中没有前置任务字段
  编辑态也不出现前置任务入口

任务列表:
  阅读态卡片视图:
    非关键路径 + 无前置: 不显示
    非关键路径 + 有前置: hover 该行时主带末端浮现 [↩ N]，仅显示数量
    关键路径 + 有前置:   主带末端常驻显示 [↩ N] 红色
    关键路径 + 无前置:   主带末端常驻显示 [↩ 待补充] 红色提示
  阅读态详情视图:
    所有工序行常驻显示 [↩ N]，关键路径红色，非关键蓝灰
  阅读态列表视图:
    前置任务作为字段列默认显示
  编辑态卡片 / 详情视图:
    所有工序行主带末端常驻显示:
      有前置: [↩ N] 关键路径红色 / 非关键蓝灰
      无前置: [↩ 添加] 浅灰
    点击进入搜索选择器
  编辑态列表视图:
    前置任务作为字段列默认显示，Tab 可聚焦
```

前置任务发现机制(不依赖新手引导)：

```text
路径一: 编辑态卡片末端常驻链接
  用户任意时刻点击"编辑"进入编辑态，每个工序行主带末端都看到 [↩ N] 或 [↩ 添加]
  自然知道这个功能，与 §7.6 事项带末端链接的视觉语言一致

路径二: 编辑态列表视图字段列默认显示
  Excel 风格用户在列表视图看到"前置任务"列名，自然知道

路径三: 抽屉"前置任务"固定分段
  打开任务详情抽屉时被动看到分段
```

前置任务搜索选择器：

```text
出现位置: 主带末端 [↩ N] / [↩ 添加] 原位展开
搜索方式: 按序号、任务名搜索；支持粘贴序号或任务名匹配
建议项:  同分项内可能的前置(例如同分项已有的工序、模板节点的 defaultDependencyTargetIds 解析结果)
当前前置: 列表显示 + 单条移除
循环依赖: 选择阶段实时提示"该任务已是当前任务前置，不能形成循环"(对齐 v1.4.8 §2.1)
依赖类型: 默认 FS(完成-开始)，由系统按 v1.4.8 推断
          搜索选择器提供"高级"小按钮，默认折叠
          展开后才显示依赖类型(FS / SS / FF / SF)和延后天数，99% 用户不需要展开
不暴露:  循环依赖技术词、依赖类型枚举默认值之外的实现细节
```

前置任务的真正业务价值是关键路径，关键路径联动规则见 §10.10。

### 7.9 右侧抽屉与分段

右侧抽屉承担深度查看 + 中频复杂业务动作的统一归宿。

抽屉规格：

```text
宽度 480-560px，从行右侧滑入
打开方式：
  点击任务名称单元格
  键盘 F4
  行号区菜单 - 打开任务详情
  事项 chip 跳转到对应分段（条件 / 阻碍 / 验收等）
顶部固定：任务名 + 序号 + 状态徽章 + 关闭按钮
侧边导航：固定八个分段
主区域：当前分段内容
底部固定：上一行 / 下一行（切换任务时抽屉跟随）
```

固定八个分段：

```text
基本信息    只读基础摘要 + 关键日期 + 进度
工程对象    范围归属详情，可编辑（等价于编辑态字段）
责任        责任人 / 责任单位，可编辑
开工条件    完整列表 / 新增 / 删除 / 标记不适用 / 标记满足
阻碍        完整列表 / 新增 / 关闭 / 严重度调整 / 解除计划
前置任务    只读列表 + 跳转表格编辑
影响验收    只读列表 + 跳转验收专项页
来源        模板来源 / 创建时间 / 最近保存，只读
```

抽屉与行内弹层互斥：

```text
抽屉打开时，事项 chip 点击不再弹行内弹层，直接在抽屉切分段
行内弹层打开时，点击其他位置自动关闭
任意时刻只允许同时存在一个抽屉或一个行内弹层
```

抽屉不承载：

```text
风险问题处理
验收状态切换
图纸证照管理
材料台账
月度关账
任务汇总
AI 工期建议按钮 / 独立动作
专项方案查看
```

### 7.10 行内弹层

行内弹层承担中等复杂度业务动作的就地承接。

行内弹层规格：

```text
出现位置：行下方就地展开，不弹窗、不跳页
宽度：随行宽自适应
高度：受视口约束，内部独立滚动
关闭方式：点击其他位置自动关闭、Esc 关闭、提交后关闭
```

行内弹层承载场景：

```text
登记新阻碍（事项带末端 [+ 登记阻碍] 链接触发，3 字段最快路径，对齐 v1.4.8 §2.3）
开工条件清单（事项 chip / 事项带末端 [+ 新增条件] 触发，勾选满足 / 新增条件，对齐 v1.4.8 §2.2）
前置任务搜索选择器（编辑态主带末端 [↩ N] / [↩ 添加] 触发，对齐 §7.8）
智能展开（v1.4.7.2，行号区 + 菜单触发）
```

行内弹层不承载：

```text
完整阻碍管理（升级到抽屉）
初始批量配置开工条件（升级到抽屉）
任务详情完整字段（升级到抽屉）
任何会跳页或全屏的复杂表单
```

行内弹层与抽屉的升级路径：

```text
chip 点击 → 行内弹层（扫读 + 简单操作）
弹层底部 [打开任务详情查看更多] → 升级到抽屉对应分段
不强制每次都开抽屉
```

### 7.11 v1.4.2 工程分类视觉表达

v1.4.2 §4 定义五类工程分类节点（分部 / 子分部 / 分项 / 工序 / 作业步骤），行卡片混合体通过四重视觉差异表达：

语义类型解析优先级：

```text
1. wbs_node_type：任务行当前缓存/兼容语义，优先用于渲染
2. engineering_category_id -> engineering_categories.category_type：当 wbs_node_type 缺失时使用，API 可展开为 engineering_category_type / category_type
3. depth / 是否有子级 / is_executable：仅作为旧数据展示 fallback

行卡片混合体的字号、字重、语义标签、汇总/执行行视觉权重，都必须优先使用解析出的 WBS 语义类型。
不得只依赖前端 buildWBSTree 计算出的 depth 来判断“分部 / 子分部 / 分项 / 工序 / 作业步骤”。
```

```text
字号字重：
  division 分部工程      字号 14px / 字重 600
  sub_division 子分部    字号 13px / 字重 600
  item_work 分项工程     字号 13px / 字重 500
  process 工序           字号 13px / 字重 400
  activity_step 作业步骤 字号 12px / 字重 400

缩进：
  1.5rem × depth

背景密度：
  division 浅灰背景
  sub_division 极浅灰
  item_work / process / activity_step 白底

节点类型图标（主带前置）：
  ▾ / ▸  可折叠节点
  ◆      执行节点 (process)
  ·      作业步骤 (activity_step)
  ★      里程碑 (覆盖默认图标，金色)
  ⬥      关键节点（系统派生，蓝色）

语义标签（主带名称右侧轻量小字，蓝灰色）：
  分部工程 / 子分部工程 / 分项工程 / 工序 / 作业步骤
  列表视图下收起，hover 任务名时显示
  卡片 / 详情视图常驻
  编辑态点击标签快速切换 category_type（等价于行号区菜单的"转为..."）
```

汇总节点（division / sub_division / item_work）与执行节点（process / activity_step）的数据带差异化：

```text
执行节点数据带：完整字段，计划日期 + 工期 + 进度条 + 责任人 + 责任单位
执行节点事项带：完整 chip
汇总节点数据带：汇总字段，计划日期范围（子级最早—最晚）+ 总工期 + 汇总进度
汇总节点事项带：子级汇总摘要（如 "2 个子级有阻碍" "5 个工序待满足条件"）
汇总节点编辑态可编辑字段：名称 / 分类 / 层级 / 排序 / 里程碑标记 / 计划约束
汇总节点编辑态不可编辑字段：进度 / 责任人 / 责任单位（由子级汇总）
```

按 v1.4.2 §6 切换 category_type 后，节点视觉立即变化：

```text
process 下首次新增作业步骤后，process 自动转为汇总节点
数据带切到汇总数据带
弹出轻提示："已转为汇总节点，进度由作业步骤汇总"
```

### 7.12 父子层级折叠与排序

```text
折叠图标位于主带最前，▾ 展开 / ▸ 折叠
```

所有动画使用 CSS transition / Framer Motion，不使用 setTimeout 模拟。

时序 token：

| 拖拽放置 | 200ms | spring(300,20) | 行归位 |

关键交互时序图：

```text
用户点击 [编辑]
  ├─ 0ms    工具栏切换为编辑态按钮组
  ├─ 0ms    视图开始从卡片→列表过渡 (200ms)
  ├─ 200ms  过渡完成，焦点落在第一个可编辑单元格
  └─ 200ms  事项带收起，列表列头出现

用户点击 [保存]
  ├─ 0ms    保存按钮进入 loading 状态
  ├─ 0ms    前端即时校验
  ├─ 校验失败 → 校核条展开 (200ms)，定位到第一个错误行
  ├─ 校验通过 → 提交后端
  ├─ 后端返回 → 编辑态→阅读态过渡 (150ms)
  └─ 过渡完成 → toast "已保存" (200ms 出现)

用户 hover 行号区 [...]
  ├─ 0ms    ... 图标出现 (100ms fade-in)
  ├─ 点击   菜单弹出 (150ms)
  ├─ 选择菜单项 → 菜单关闭 (100ms) → 执行对应动作
  └─ 点击外部 → 菜单关闭 (100ms)
```

禁止的动画模式：
- 禁止 `scale` 导致布局抖动（行 hover 不用 scale）
- 禁止超过 300ms 的非必要动画
- 禁止 `prefers-reduced-motion: reduce` 下播放非必要动画（保留 opacity 过渡，移除位移和缩放）
- 禁止动画阻塞用户输入（所有动画 `pointer-events: auto`）

## 8. 共享表格底座能力

三页定位是填写数据，不做具体分析；分部分项标准库(v1.4.7.2)已经把"批量录入"压到最小，因此 Excel 化能力按数据填写所必需的最小集裁剪。

### 8.1 必须具备的基础能力

共享计划树必须统一提供：

```text
阅读 / 编辑状态切换
三种视图渲染（列表 / 卡片 / 详情）与自动切换
编辑缓冲区
dirty 标记
保存 / 取消
撤销 / 重做（Ctrl+Z / Ctrl+Y）
单元格直接编辑
键盘焦点导航（Tab / Shift+Tab / 方向键 / Enter / F2 / Esc）
行新增
删除行
多选行（Shift / Ctrl）+ 多选浮条批量动作
缩进 / 反缩进（Tab / Shift+Tab）
拖拽排序（行最左侧隐性拖拽区）
列冻结（列表视图，序号 + 任务名）
TSV 粘贴（仅支持以当前焦点单元格为起点的应急粘贴）
渐进渲染 / 虚拟滚动
行级提示定位
字段级轻校验
事项 chip 渲染
事项带末端常驻链接（§7.6）
主带末端常驻链接（§7.8）
行号区菜单
右侧抽屉与八个分段
行内弹层
更多菜单导出 Excel / CSV
```

不再支持的 Excel 化能力（按"三页只填写数据，不做分析"裁剪）：

```text
覆盖多行多列粘贴   去掉  容易绕过校验，与责任单位 / 工程对象的强 lookup 冲突
批量填充手柄       去掉  数据带字段类型多样，机械填充意义不大；改用多选浮条"批量改字段"
替换 Ctrl+H       去掉  容易绕过编辑缓冲和后端校验；只保留查找定位
连续单元格选区     去掉  卡片视图下选区视觉别扭；行选择 + 多选浮条已能覆盖批量场景
列宽手工拖拽       去掉  系统提供三档预设宽度，列宽偏好不持久化
快速浏览模式       去掉  阅读态卡片视图本身就承担了快速浏览
```

精简的核心动机：用户日常 80% 的录入由模板生成承担，剩余的 15% 由作用域条 + 多选浮条批量改承担，5% 由单元格直接编辑承担；TSV 粘贴只作为从历史 Excel 应急导入的兜底路径。

### 8.3 撤销与重做

撤销 / 重做只对保存前编辑缓冲生效。

规则：

```text
改单元格可撤销
TSV 粘贴可撤销
多选浮条批量改字段可撤销
新增行可撤销
删除行可撤销
层级调整可撤销
切换 category_type 可撤销
模板生成可撤销（作为原子操作整批回滚，不允许撤销其中部分行，见 v1.4.7.2 §8.1）
保存后不可用本地撤销回滚数据库
保存后的反向处理是新的业务操作，必须重新校验权限、状态、引用关系和留痕
```

落地要求：

```text
月度计划当前已有局部 history stack，应抽象为共享底座能力
项目基线当前不能继续 canUndo=false / canRedo=false
任务列表必须补齐编辑态下的 undo / redo
快捷键 Ctrl+Z / Ctrl+Y 或 Cmd+Z / Cmd+Shift+Z 必须三页一致
```

### 8.4 删除行

表格中的删除行对用户就是正常删除。

规则：

```text
未保存新行：可直接从编辑缓冲移除
已保存行：保存时提交删除操作
后端根据 v1.4.15 判断物理删除、软删除、取消、不再执行、停用、归档或拒绝删除
删除操作在保存前可撤销
删除操作不立即触发通知、风险问题、历史保留或物理删除
```

前端口径：

```text
用户只看到删除
保存前可以撤销
保存成功后只提示已保存
不展示物理删除、软删除、source_deleted、delete intent 等技术词
```

### 8.5 复制粘贴

复制粘贴属于编辑操作，仅作为从历史 Excel 应急导入数据的兜底路径。

规则：

```text
支持以当前焦点单元格为起点的 TSV 粘贴
不支持覆盖多行多列的整块粘贴
不支持选区填充手柄
单行值填充到多选行通过多选浮条"批量改字段"动作完成，不通过填充手柄
粘贴和填充不得绕过字段校验
粘贴责任单位时必须匹配 participant_units
粘贴工程对象时必须匹配 engineering_objects
匹配不唯一或不存在时标记为校验错误，阻止保存或进入待选择状态
```

行卡片混合体下的 TSV 粘贴目标列规则：

```text
列表视图：起始单元格即焦点位置，粘贴向右、向下展开
卡片视图 / 详情视图：起始单元格仍为焦点位置，但虚拟表格坐标按主带 + 数据带可编辑字段顺序展开
粘贴 5 行 3 列时，按 (任务行 +0..4) × (起始字段及其后两个字段) 展开
```

批量改字段(取代 Excel 填充手柄):

```text
多选 N 行 → 表格底部出现多选浮条
浮条按钮: [批量改责任单位] [批量改工程对象] [批量改责任人] [批量平移日期] [批量改目标进度] [批量删除]
按钮文字明确表达，不使用通用"填充"
浮条按钮按当前页面允许编辑字段动态显示
```

### 8.6 列配置与字段注册表

共享表格需要支持"选择显示列 / 增加列"，但不是让用户自由创建数据库字段。

行卡片混合体下的列配置：

```text

卡片视图 / 详情视图：控制数据带和事项带中字段的显示与排序
用户视角统一称为"字段配置"，不区分列与字段
```

字段来源必须来自系统字段注册表：

```text
基础计划字段
工程对象字段
工程分类字段
责任主体字段
里程碑字段
关键节点摘要字段
前置任务字段
影响验收字段
计划来源字段
数据质量提示字段
```

字段配置规则：

```text
用户可以选择显示已有治理字段
用户不能自由创建无治理口径的业务字段
不同页面有不同默认字段集
不同页面允许显示的字段集合不同
项目基线页只允许显示基线自身计划字段，不提供关键节点摘要、偏差摘要等分析判断字段
```

字段注册表示例：

| 字段组 | 示例字段 | 可编辑规则 |
|---|---|---|
| 基础计划 | 任务名称、计划开始、计划完成、工期 | 三页按状态可编辑 |

```ts
  lookupSource?: PlanningLookupSource;
  editableIn: PlanningSurface[];
  editableWhen?: PlanningFieldEditableWhen;
  defaultVisibleIn: PlanningSurface[];
  formatter?: PlanningFieldFormatter;
  validators?: PlanningFieldValidator[];
  readonlyReasonCode?: string;
  surfaceLabel?: Partial<Record<PlanningSurface, string>>;
}
```

字段注册表维护规则：

```text
新增字段必须先进入后端字段注册表，再由前端字段配置选择显示
字段 label 必须是用户能理解的中文，不使用数据库字段名作为展示名
lookup 字段必须声明 lookupSource，前端不得自行拼装来源
enum 字段必须绑定 dictionary 或后端返回的枚举项，不得前端硬编码
editableIn 和 editableWhen 共同决定字段能否编辑
defaultVisibleIn 只控制默认可见，不代表字段是否能参与治理
validators 只定义轻量保存校验，复杂治理仍归 v1.4.16
readonlyReasonCode 用于解释字段为什么当前不可编辑，前端不自行猜测
surfaceLabel 只处理同一字段在三页中的轻微叫法差异，不改变字段语义
```

字段注册表返回结果必须支持版本标识：

```ts
interface PlanningFieldRegistryResponse {
  registryVersion: string;
  generatedAt: string;
  fields: PlanningFieldDefinition[];
}
```

前端缓存规则：

```text
按 project_id + surface + registryVersion 缓存
registryVersion 变化时刷新字段配置和轻校验规则
字段配置中已隐藏或已废弃字段不立即删除，进入不可选或只读兼容状态
保存时后端仍以当前字段注册表校验为准，前端缓存不能绕过后端判断
```

### 8.8 字段组双口径对齐

共享计划树必须区分"展示粒度"和"合并粒度"。

展示粒度用于用户看表、字段配置、列排序和视觉分组；合并粒度用于协作保存、冲突判断、变更摘要、数据质量归因。两者不能各自散落定义，必须由同一份字段注册表派生。

统一规则：

```text
每个字段必须有唯一 displayGroup
每个字段必须有唯一 mergeGroup
每个 mergeGroup 必须归属到一个唯一 displayGroup
displayGroup 可以比 mergeGroup 更细，也可以承载只读派生字段
mergeGroup 不得直接作为用户字段分组展示
planningConflictMerge.ts 不再维护独立 PLANNING_CONFLICT_FIELD_GROUPS 常量
v1.4.14 变更留痕、v1.4.16 数据质量、协作合并都引用字段注册表中的 mergeGroup
```

展示组与合并组对照：

| 展示组 displayGroup | 合并组 mergeGroup | 示例字段 | 说明 |
|---|---|---|---|
| 基础计划 basic_plan | identity | title、name | 名称变化单独合并 |
| 基础计划 basic_plan | schedule | planned_start_date、planned_end_date、duration | 日期和工期作为同组冲突 |
| 进度事实 progress_fact | progress_status | progress、status、actual_start_date、actual_end_date | 进度、状态、实际日期同组治理 |
| 工程对象 engineering_object | engineering_object | engineering_object_id、phase_object_id、section_object_id、building_object_id、basement_object_id、floor_object_id、physical_zone_object_id、functional_area_object_id | 范围对象同组治理 |
| 工程分类 engineering_category | engineering_category | engineering_category_id、category_type | WBS / 工程分类语义同组治理 |
| 责任主体 responsibility | assignee | assignee、assignee_user_id、assignee_name | 责任人可自由编辑 |
| 责任主体 responsibility | responsible_unit | participant_unit_id、responsible_unit、assignee_unit | 责任单位必须主数据选择 |
| 节点控制 node_control | node_control | is_milestone、milestone_level、is_critical | 里程碑可编辑，关键节点派生 |

| 验收影响 acceptance_impact | readonly_derived | acceptance_impact_summary | 只读派生，不参与前端编辑冲突 |

当前代码中的 `PLANNING_CONFLICT_FIELD_GROUPS` 应迁移为字段注册表生成结果：

```text
旧 8 组合并粒度继续作为兼容基础
新增工程分类、依赖、只读派生等 mergeGroup
展示字段组可以保留 10 组，但必须映射到 mergeGroup
测试断言从 getPlanningConflictFieldGroup(field) 改为读取 registry.mergeGroup
```

## 9. 即时校验与数据治理边界

共享表格底座只做轻量即时校验。复杂治理交给后端数据质量与计划治理服务。

### 9.1 表格即时校验

即时校验只判断保存能否形成基本合法事实。

阻断保存的轻量规则：

```text
任务名称不能为空
计划开始、计划完成必须是合法日期
计划开始不能晚于计划完成
可执行任务必须有计划开始和计划完成；纯汇总行可由子级汇总
进度必须在 0-100
active 任务至少有一项有效工程范围归属
责任单位必须来自 active participant_units
工程对象必须来自 active engineering_objects
工程对象字段类型必须匹配，例如楼栋字段不能选择专业对象
父子层级不能断裂
不能把任务挂到自己的子级下
状态值必须来自 v1.4.5 状态字典
前置任务不能选择自身
前置任务必须来自同项目有效任务
前置关系不能形成循环依赖
已发布基线、已确认月计划、已关账月计划不能直接编辑
空白新增行可自动忽略，不阻断保存
```

校验错误文案对照表：

| 规则 | 行级错误文案 | 校核条摘要 |
|------|-------------|-----------|
| 任务名称为空 | "请输入任务名称" | "N 行缺少任务名称" |
| 日期非法 | "请输入有效日期" | "N 行日期格式错误" |
| 开始晚于完成 | "开始日期不能晚于完成日期" | "N 行日期倒挂" |
| 可执行任务缺日期 | "工序/作业步骤必须填写计划日期" | "N 行缺少计划日期" |
| 进度越界 | "进度范围 0-100" | "N 行进度超出范围" |
| 工程对象缺失 | "请选择工程对象" | "N 行缺少工程对象" |
| 责任单位无效 | "该单位已停用或不存在" | "N 行责任单位无效" |
| 工程对象类型不匹配 | "该字段不接受此类型对象" | "N 行工程对象类型错误" |
| 层级断裂 | "不能跳过中间层级" | "N 行层级结构异常" |
| 循环挂载 | "不能将任务挂到自己的子级下" | "N 行层级循环" |

| 前置循环依赖 | "存在循环依赖，请检查前置链" | "N 行前置循环" |
| 状态值非法 | "请选择有效状态" | "N 行状态值无效" |
| 只读数据被修改 | "该数据已锁定，不可编辑" | — (���应出现) |

错误展示规则：
- 行级：单元格 `border-red-500` + 下方 12px 红色文案 + `role="alert"`
- 校核条：表格顶部黄色横幅，列出所有错误摘要，每条可点击定位到对应行+字段
- 校核条最多显示 5 条，超出显示"还有 N 条问题"折叠链接

可轻确认的规则：

```text
首次进度从 0 -> >0，且存在人员、设备、现场准备、一般协调类软条件未满足
批量把大量任务进度改为 100
计划日期大幅移动
删除多条已保存行
```

轻确认不要求用户填写原因。

### 9.2 高层数据治理

以下不属于表格即时校验，不阻断普通编辑保存，交给后端治理、质量提示、任务列表健康横幅、算法参考或提醒触达：

```text
来源映射是否完全准确
WBS 分类语义置信度是否低
当前任务事实与旧基线 / 旧月计划差异
关键路径是否需要重算
是否触发新版基线建议
是否影响下月计划生成
是否影响验收链路
是否触发风险、问题或预警
是否影响 BI 指标可信度
是否适合沉淀为模板
```

核心原则：

```text
能后台判断的，不让用户手动选择
能弱提示的，不做强阻断
数据质量问题不直接变成风险问题
计划差异不直接变成用户必须处理的待办
```

### 9.3 校核条、健康横幅与定位能力

共享计划树需要区分"基础录入校核"和"执行健康问题"。

页面边界：

```text
项目基线页：不保留独立健康横幅，基础录入问题由共享表格校核条承接
月度计划页：不保留独立健康横幅，基础录入问题由共享表格校核条承接
任务列表页：保留健康横幅，但只承载实时执行事实问题，不重复承载普通录入校核
```

项目基线和月度计划原健康横幅中的以下问题，全部下沉为共享表格校核条或发布 / 确认前校核：

```text
任务名称缺失
计划开始 / 计划完成缺失
日期倒挂
父子层级异常
关键节点缺失
月计划范围缺失
月计划目标进度缺失
重复行
责任单位缺失
工程对象缺失
```

任务列表健康横幅只处理实时执行事实：

```text
进度停滞
开工条件未满足但已开工
阻碍影响执行
实际进度与当前排期偏差
关键路径任务异常
验收影响提示
协作更新导致的执行事实需刷新
```

校核条和健康横幅都必须有定位能力：

```text
点击"关键节点缺失 10 项"，从上到下定位到第一个问题行和具体字段
再次点击或点击"下一个"，继续跳到下一项
支持"上一个 / 下一个"在问题项之间切换
定位时自动展开父级、滚动到行、聚焦到输入框或只读提示
三种视图必须使用同一套定位结果
定位时如果当前视图是卡片视图但阻断字段在数据带中，自动闪烁高亮该字段；如果在事项带，则跳转到对应行内弹层或抽屉分段
```

定位规则：

```text
可编辑问题定位到具体输入框
只读派生问题定位到对应行和提示 chip
跨页问题不在当前表格强行展示，只提供跳转到对应页面或过滤条件
问题修复后从定位队列中移除
```

### 9.4 异常项优先级

同一行同时命中多种提示时，系统必须统一视觉优先级，避免同一行堆满颜色和 chip。

优先级从高到低：

```text
1. 阻断保存：必填缺失、非法日期、循环依赖、责任单位非法、工程对象非法
2. 协作冲突：同字段被他人更新，需要用户确认
3. 强业务提醒：首次开工软条件未满足、批量完成、删除多条已保存行
4. 执行健康问题：阻碍影响、进度停滞、关键路径异常、验收影响
5. 只读派生信息：系统派生关键节点、影响验收名称、数据质量弱提示
```

视觉权重：

```text
阻断保存：字段红色边框 + 校核条统计，必须定位到字段
协作冲突：字段提示 + 顶部状态条，不覆盖用户输入
强业务提醒：保存时集中轻确认，不逐行弹窗
执行健康问题：任务列表健康横幅 + 行内 chip
只读派生信息：灰色或蓝灰色 chip，不抢占主表
```

按视图容量展示：

```text
列表视图：最高优先级 1 个 chip + 数量徽标
卡片视图：最多 3 个 chip + 数量徽标
详情视图：最多 5 个 chip，hover 展开全部
```

### 10.3 阻碍

阻碍按 v1.4.8 §2.3 治理口径，必填三字段：描述、严重度、预计解除。严重度按 v1.4.8 §2.3 分高 / 中 / 低。

按三层升级承载：

```text
快速登记(高频)：
  事项带末端常驻浅灰链接 [+ 登记阻碍] (无阻碍时显示)
  点击 → 行下方就地展开"快速登记阻碍"弹层：
    描述
    严重度: 高 / 中 / 低

    [取消] [登记]
  Enter 提交，Esc 取消
  登记后立即写入业务事实(业务动作，不进编辑缓冲)
  事项带立即出现 [阻碍 1] chip

扫读 + 简单操作(中频)：
  事项 chip [阻碍 N] 点击 → 行下方"阻碍列表"弹层
    每条阻碍一行: 描述前 30 字 / 严重度 / 状态 / 登记时间
    每条右侧: [关闭] [查看详情]

深度管理(低频)：

  阻碍专项页跨任务分析(原有，行为不变)
```

业务原则(对齐 v1.4.8 / v1.4.12)：

```text

chip 弹层 / 抽屉的操作都通过业务服务提交
阻碍存在不阻断进度填报，只在任务列表健康横幅提示(对齐 v1.4.8 §2.3)
chip 上不出现"阻碍影响执行"等语义文本，仅显示数量摘要
阻碍登记后由 v1.4.12 自动判断是否升级风险/问题，前端不暴露升级路径
关闭阻碍由 v1.4.13 自动决定是否通知相关人
```

### 10.4 开工条件

## 11. 保存与业务动作流程

### 11.1 编辑态保存流程

三页共享统一保存流程只处理表格编辑缓冲，不同时发布基线或确认月计划：

```text
用户进入编辑态
用户进行表格编辑
前端记录 pending operations
前端进行轻量即时校验
用户点击保存
前端提交 editIntent
后端执行字段规范化
后端执行基础业务校验
后端执行对象、责任单位、状态字典、工程分类校验
后端执行删除规则判断
后端执行计划治理规则
后端写入业务事实 / 快照 / 来源映射 / 摘要留痕
前端回到阅读态并提示已保存
```

保存结果按页面解释：

```text
项目基线页：保存基线草稿或当前基线编辑结果，不等于发布基线
月度计划页：保存未确认月计划编辑结果，不等于确认月计划
任务列表页：保存当前任务事实，本轮进度变化由后端自动写进度事实
```

### 11.2 保存频率规则

系统不限制用户保存频率。用户可以改几条保存一次，也可以完成一批后统一保存。

```text
每次保存只提交本轮 changed operations，不整表覆盖
每次保存只更新当前草稿的 revision_no / updated_at / content_hash，不等于发布业务版本
多次保存不创建多个正式版本，也不为每次保存永久保留一条完整草稿快照
任务列表保存后写当前任务事实、进度快照和本轮摘要
项目基线保存后只更新基线草稿或待发布版本，不等于发布基线
月度计划保存后只更新未确认月计划，不等于确认月计划
发布基线、确认月计划才形成正式业务快照
频繁保存产生的通知、预警和留痕需要后端合并去噪，不逐次打扰用户
如需保留保存过程，只保留短期内部记录或最近 N 次轻量摘要；发布 / 确认后压缩为一条业务摘要
```

保存成功前端只提示"已保存"。不要要求用户理解保存产生了多少内部 revision，也不要展示技术版本号作为主流程信息。

### 11.3 阅读态业务动作流程

发布基线、确认月计划、生成基线、生成任务等业务动作必须在阅读态执行：

```text
用户在阅读态点击业务动作
前端检查是否存在未保存编辑
如存在未保存编辑，要求用户先保存或取消
前端调用对应业务服务
后端校验权限、状态、引用关系和生命周期
后端写入快照、生命周期、来源映射和业务摘要
前端提示动作成功
```

发布 / 确认前允许出现轻确认弹窗，但只展示用户能理解的业务摘要：

```text
确认发布这版基线？

新增 8 项
日期调整 21 项
删除 2 项
最后保存：今天 14:32

取消 / 确认发布
```

月度计划对应为：

```text
确认这个月计划？

新增 8 项
日期调整 21 项
删除 2 项
最后保存：今天 14:32

取消 / 确认月计划
```

确认弹窗不展示 draftRevisionId、planVersionId、source_version_id、content_hash 等技术字段。后端仍必须用这些字段校验用户确认的是否是当前已保存版本；如已被协作更新，提示"计划已被协作更新，请同步后再发布 / 确认"。

业务动作不得与编辑态保存合并为一个按钮：

```text
不做"保存并发布"
不做"保存并确认"
不做"编辑态发布"
不做"编辑态确认"
```

### 11.5 业务事实来源统一表达

共享计划树三页必须统一表达业务事实来源，让用户能分清“我维护的”“系统已经生成并生效的”“系统给出的候选方案”。但这套语言要尽量轻，不能把页面变成系统说明书。

统一来源类型：

```text
手动维护：用户通过编辑态保存、行侧业务动作、右侧抽屉或专项页面操作形成的事实
系统生成：系统按既定规则自动生成、推断、派生或写入的数据；多数情况下已经生效
系统建议：只用于生成新版基线、生成月度计划时的算法候选；未被用户采纳前不进入业务事实
```

来源边界：

```text
手动维护和系统生成都可以成为已生效事实
系统建议不是事实，只是候选方案
系统建议被用户采纳后，才通过生成、保存、发布或确认转为系统生成或手动维护后的业务事实
健康横幅、表格校核、数据质量提示、风险问题预警、通知提醒都不叫系统建议
```

系统建议只允许出现在两个场景：

```text
项目基线页：生成新版基线时，展示算法候选
月度计划页：生成月度计划时，展示算法候选
```

系统建议不得出现在：

```text
任务列表健康横幅
表格校核条
数据质量提示
风险问题预警
通知中心
任务详情
驾驶舱指标
```

系统生成默认静默生效，只有当它影响用户判断、追溯或确认动作时才弱展示来源。

系统生成来源示例：

```text
实际开始：进度首次 > 0 后系统自动写入
实际完成：进度 = 100 或状态完成后系统自动写入
状态：由进度、实际日期和状态字典规则推断
关键节点：由里程碑、关键路径、计划节点规则派生
依赖类型：用户只选前置任务，系统推断依赖类型
任务编码：后端自动生成，前端默认不展示
工程对象编码：对象创建时自动生成
工程分类语义：按层级、分类规则和节点类型识别或派生
影响验收摘要：由验收事项与任务关联关系派生
进度快照、来源映射、快照摘要：保存、发布、确认时后端生成
基线草稿 / 月计划草稿：点击生成动作后由系统生成；发布 / 确认前仍是草稿
```

前端显示规则：

```text
手动维护：默认不打标签，用户通过编辑保存天然知道是自己维护
系统生成：默认不打标签；仅在任务详情、确认弹窗、草稿来源、悬浮说明中弱展示
系统建议：必须明确展示为候选，不得表现成已经生效的数据
```

弱展示示例：

```text
实际开始：2026/05/12（由进度自动生成）
关键节点：蓝色菱形图标，悬浮显示“系统派生关键节点”
基线草稿来源：由当前任务列表生成
月计划草稿来源：由当前任务列表生成
新版基线候选：系统建议纳入 8 项变化
月计划候选：系统建议滚入 12 项任务
```

不展示示例：

```text
任务编码生成过程
依赖类型推断过程
状态推断公式
进度快照生成过程
来源映射、lineage、content_hash、draftRevisionId
```

核心原则：

```text
用户不需要时时知道系统做了什么，只需要在会影响决策、追溯或确认时知道
系统建议必须少而明确，只服务于新版基线和月度计划生成
健康横幅和校核条只表达问题，不表达建议
```

业务动作文案统一规则(对齐 v1.4.7 §7.2)：

```text
所有月份相关业务动作动词带具体月份，不用"上月""本月""下月"等相对词
按钮显示: [生成 5 月计划] [确认 5 月计划] [4 月关账]
```

月度计划生成结果带来源标识(对齐 v1.4.7 §7.2 source_mode)：

```text
生成结果中每行带轻量来源 chip：
  [滚入]    上月未完成项滚入本月
  [基线]    当前生效基线本月应执行项
  [现场]    当前任务列表当月排期
  [新增]    用户在编辑态手动新增
来源 chip 颜色为浅蓝灰，与模板 chip(浅蓝)区分
hover chip 显示原因摘要，例如 "4 月计划完成但实际未完成，滚入 5 月"
用户不需要理解 source_mode 技术词
```

source_mode 到来源 chip 的映射表：

```text
baseline -> [基线]：当前生效基线在目标月份应执行的计划项。
schedule -> [现场]：来自当前任务列表 / 现场滚动排期的计划项。
mixed -> [基线] / [现场] / [滚入]：按行级 source_chip 或 source_reason 决定；没有行级信息时显示 [基线+现场]。
manual -> [新增]：用户在月度计划编辑态手动新增或手动调整形成的计划项。
imported -> [新增]：外部导入形成的月计划项，hover 说明导入来源；不在普通行上展示 import_batch_id。
carryover / rolling_in 行级来源 -> [滚入]：上月未完成项滚入本月；这是行级来源，不作为 monthly_plans.source_mode 值域。
```

约束：

```text
monthly_plans.source_mode 只描述整版月计划生成口径。
monthly_plan_items.source_chip / source_reason 描述行级来源。
前端展示 chip 文案，不展示 baseline / schedule / mixed / manual / imported 等技术值。
v1.4.6 负责 API 返回 source_mode；v1.4.7.1 负责把它转成用户可理解的来源 chip。
```

```text
关账作为生成下月计划前的必要归档动作
首月、无上月计划或上月无数据时可跳过
关账不回改本月承诺
```

```text

确认前校核条必须支持定位到具体行和字段
```

### 12.3 任务列表页

任务列表页回答"现场当前怎么排、干到哪、谁负责"。

默认状态：

```text
阅读态，默认卡片视图
可筛选、查看、定位问题、进入任务详情、条件、阻碍、验收影响等业务入口
完整事项 chip：阻碍、条件、前置、影响验收、模板、责任单位缺失、工程对象缺失
任务列表保留健康横幅，承载实时执行事实问题
```

编辑态：

```text
点击编辑后进入编辑态，自动切换到列表视图（大数据量时强制）
允许新增任务
允许编辑任务名称、计划开始、计划完成、进度、状态、责任人、责任单位、工程对象、工程分类、里程碑标记、前置任务、category_type
进度修改必须显式保存，不能失焦即写入
进度 0-100 统一一个保存逻辑，不单独把 100 做一套流程
progress_method = percent 时允许直接编辑 progress
progress_method = quantity / milestone / manual_weighted 时，进度单元格、任务详情进度控件、粘贴、填充、批量编辑、状态改完成自动补 100 全部不得写 progress
非 percent 进度展示只读提示：“该任务进度由{method}自动计算”
实际开始 / 实际完成不作为普通可编辑字段
删除行保存前可撤销
```

新增任务入口规则：

```text
任务列表不再保留独立"新建任务"按钮
新增任务统一通过表格新增行、粘贴行或批量导入完成
导入支持常见计划编制文件格式（xlsx / xls / csv / tsv），导入结果先进入编辑缓冲，保存后才形成任务事实
空项目第一次创建任务时，空态主入口提供两个并列按钮：
  [+] 进入编辑并新增首行
  [⤵] 生成任务（v1.4.7.2）
两个按钮共用同一个编辑缓冲、同一个保存提交模型
所有新增任务最终走同一个任务创建服务、同一套后端校验和同一套保存治理
```

新项目首入口规则：

```text
任务列表是新项目计划编制第一步
任务列表保存形成任务事实后，阅读态提供计划治理入口
没有可用基线：按钮显示“计划治理”，高亮，指向基于当前任务列表生成第一版项目基线
已有可用基线：按钮显示“更新基线”，普通样式，指向生成新版基线草案
是否存在未保存编辑不改变按钮文案和样式；保存、撤销、合并仍由共享计划树编辑缓冲负责
项目基线页和月度计划页无基线时不再引导用户从空白 / 旧 WBS 模板直接新建，统一提示先回任务列表维护当前任务事实
```

任务列表保存规则：

```text
保存是编辑态操作，不是独立业务动作按钮
保存后形成当前执行事实
用户不单独点击"保存任务进度"，只点击任务列表统一保存
本轮表格变更中包含进度字段变化时，后端自动识别为进度事实写入
本轮表格变更中如果目标任务 progress_method != percent，前端必须在提交前剔除 progress 变更，只保留其他字段变更
进度首次 > 0 且 actual_start_date 为空时，后端自动写实际开始
进度为 100 时，后端自动写实际完成
状态改为完成时，percent 任务由后端统一补齐 progress = 100 和 actual_end_date；非 percent 任务只更新状态/实际完成事实，不由普通前端补写 progress
保存后写进度快照、来源映射、业务摘要
保存后不反写已发布基线和已确认月计划
```

阅读态业务动作：

```text

导入计划文件
```

```ts
  fields: PlanningFieldDefinition[];
  groups: PlanningFieldGroupDefinition[];
  updatedAt: string;
}

interface PlanningFieldDefinition {
  key: string;
  group: PlanningFieldGroup;
  mergeGroup: PlanningFieldMergeGroup;
  label: string;
  dataType: 'text' | 'number' | 'date' | 'percent' | 'enum' | 'lookup' | 'boolean';
  lookupSource?: 'participant_units' | 'engineering_objects' | 'tasks' | 'dictionary';
```

字段注册表后端规则：

```text
字段注册表以后端为权威，前端不得硬编码第二套字段定义
lookup 字段必须绑定后端主数据或字典，不能保存自由文本责任单位和自由文本工程对象
validators 只表达轻量保存校验，复杂治理归 v1.4.16
mergeGroup 用于协作冲突判断、变更摘要、数据质量归因，不能继续由前端 PLANNING_CONFLICT_FIELD_GROUPS 独立维护
registryVersion 必须进入保存请求，后端发现版本过期时返回 FIELD_REGISTRY_STALE
```

```ts
type PlanningSurface = 'baseline' | 'monthly_plan' | 'task_list';

interface PlanningTableCommitRequest {

  resourceId?: string | null;        // baselineId / monthlyPlanId / null for task_list
  baseRevision?: string | number | null;

  | { op: 'update_row'; rowId: string; values: Record<string, unknown> }
  | { op: 'delete_row'; rowId: string }
  | { op: 'move_row'; rowId: string; parentId?: string | null; afterId?: string | null; sortOrder?: number }
  | { op: 'indent_row'; rowId: string; direction: 'in' | 'out' }
  | { op: 'mark_milestone'; rowId: string; isMilestone: boolean; milestoneLevel?: 1 | 2 | 3 | null }
```

```text
3. 读取服务端当前 rows 作为 server base
4. 按 mergeGroup 做协作冲突判断
5. 执行轻量阻断校验：必填、日期、lookup、循环依赖、只读状态
6. 标准化字段：日期、进度、责任、工程对象、WBS 层级、里程碑
7. 对 delete_row 调用 v1.4.15 删除判断
8. 对 task_list 调用 v1.4.2 / v1.4.3 / v1.4.4 / v1.4.5 / v1.4.10 已有治理服务
9. 对 task_list 进度变化执行实际开始/实际完成自动生成
10. 对 set_predecessors 写 task_dependencies，依赖类型由后端推断
11. 对 task_list 保存后重算关键路径
12. 写业务事实 / 草稿 / 快照 / 来源映射
13. 写一次业务摘要 change_logs，operation_logs 只做技术审计
14. 发送必要实时事件
15. 返回 rows、摘要、阻断项、关键路径变化和删除处置结果
```

其中第 8 步必须复用这些既有底座，不允许在 `planningTableCommitService` 内重复实现一套业务规则：

