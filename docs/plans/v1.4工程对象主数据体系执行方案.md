# v1.4 工程对象主数据体系执行方案

## 0. 2026-06-01 final range-tree boundary (authoritative)

No production history or existing users need migration. The engineering-object range tree has no compatibility layer.

Final object types are exactly:

```text
phase / section / building / basement / floor / physical_zone / functional_area
```

Deleted and forbidden as range-tree/runtime write concepts:

```text
zone / professional / subproject / custom engineering object types
zone_object_id / professional_object_id task fields
project_materials.professional_object_id
legacy_object_type / DEPRECATED_OBJECT_TYPE_VALUES
/api/scope-dimensions and scope_dimensions / project_scope_dimensions adapters
```

Specialty, system, domain package, and method semantics remain business facts only. They must come from specialty_type, engineering_category_id, standard_work_code, template metadata, or the project profile, not from engineering_objects. Any older section in this document that describes legacy compatibility, old fields, or old object types is superseded by this boundary.
## 1. 目标

v1.4 的目标是把当前分散在 `范围维度 / WBS / 任务 / 材料 / 验收 / 报表` 里的工程对象信息统一收口到一套“工程对象主数据体系”，让系统后续的任务编码、WBS 拆解、进度驾驶舱、AI 分析都基于稳定对象 ID，而不是前端文本、枚举或临时字段。

本次按“当前没有历史生产数据”的前提一步到位建设：新增工程对象主表作为权威底座，保留现有表和入口做兼容适配，不删除已有功能，避免影响当前任务、甘特图、报表、材料、验收等页面。

## 2. 数据库改造

新增迁移文件：

```text
server/migrations/120_create_engineering_objects.sql
```

> 执行说明：当前仓库已存在 `068_normalize_acceptance_flow_model.sql`，因此本方案不得再使用 `068` 作为迁移编号。若执行时迁移序列已继续增长，以当时最新编号后一位为准，并保持文件名语义为 `create_engineering_objects`。

新增主表 `engineering_objects`：

```sql
id uuid primary key
project_id uuid not null references projects(id)
object_type text not null
object_code text not null
object_name text not null
parent_id uuid null references engineering_objects(id)
path text not null
level integer not null default 1
sort_order integer not null default 0
status text not null default 'active'
source_type text not null default 'manual'
source_ref_id uuid null
metadata jsonb not null default '{}'
created_at timestamptz not null default now()
updated_at timestamptz not null default now()
```

`object_type` 固定为以下值，不允许自由扩展：

```ts
'phase' | 'section' | 'building' | 'basement' | 'floor' | 'physical_zone' | 'functional_area'
```

`metadata` 必须允许承载工程特征画像，作为 v1.4.7.2 模板生成、v1.4.18 工期建议、v1.4.22 算法治理的稳定输入。非主流结构 seed 扩展时，不得只靠任务标题关键词匹配，必须优先读取工程对象或模板节点的结构化特征。

工程特征画像字段建议统一放在 `metadata.projectGenerationFacts`：

```ts
{
  projectTypeCode?: string;        // residential / commercial / industrial / municipal / hospital / school / complex 等
  structureTypeCode?: string;      // cast_in_place_frame / shear_wall / brick_masonry / precast_pc / steel_structure / super_highrise_core_tube / deep_basement / large_span 等
  methodVariantCodes?: string[];   // climbing_form / aluminum_form / pc_hoisting / steel_hoisting / top_down / deep_excavation_support 等
  elementVariantCodes?: string[];  // basement / standard_floor / roof / curtain_wall / core_tube / corridor / equipment_room 等
  confidence?: 'high' | 'medium' | 'low';
  inferredBy?: 'project_setup' | 'template_seed' | 'import' | 'object_bootstrap' | 'manual_correction';
}
```

写入边界：

```text
projectTypeCode 通常挂在项目级 root 对象或项目 metadata 上
structureTypeCode 优先挂在 building / basement / physical_zone 对象上
methodVariantCodes 和 elementVariantCodes 可挂在 building / basement / floor / physical_zone / functional_area 对象或模板节点上
专业、系统、工法、专项语义只作为业务事实进入 specialty_type、engineering_category_id、standard_work_code、模板 metadata 或项目画像，不再建 professional 工程对象
无法推断时允许为空，算法降低置信度；不得为了补齐算法输入而制造虚假的楼栋、楼层、区域或结构对象
普通前端不新增技术枚举入口；对象管理里可以用“项目类型 / 结构形式 / 主要工法”等业务语言轻量展示
```

唯一约束与唯一索引：

```sql
unique(project_id, object_type, object_code)

create unique index uq_engineering_objects_root_active_name
  on engineering_objects(project_id, object_name)
  where parent_id is null and status = 'active';

create unique index uq_engineering_objects_child_active_name
  on engineering_objects(project_id, parent_id, object_name)
  where parent_id is not null and status = 'active';
```

说明：不得使用 `unique(project_id, parent_id, object_name)` 作为唯一 sibling 名称约束，因为 PostgreSQL 中 `parent_id is null` 的根节点不会被该约束阻止重复。对象编码 `object_code` 在同项目同类型下永久唯一；对象名称只限制 active 状态下同父级不可重复，允许停用后重新创建同名对象。

索引：

```sql
(project_id, object_type, status)
(project_id, parent_id, sort_order)
(project_id, path)
```

材料与验收表引用边界：

```sql
-- project_materials 不再新增 professional_object_id。
-- 材料专业归属使用 specialty_type / engineering_category_id / standard_work_code 等业务事实。

alter table acceptance_plans
  add column if not exists building_object_id uuid null references engineering_objects(id) on delete set null;

create index if not exists idx_acceptance_plans_building_object_id
  on acceptance_plans(building_object_id);
```

字段语义：

```text
engineering_object_id：任务主归属对象，表示该任务最主要落在哪个工程对象上，可为任意 active 工程对象。
phase_object_id：分期维度归属，只能引用 phase 类型。
section_object_id：标段维度归属，只能引用 section 类型。
building_object_id：楼栋维度归属，只能引用 building 类型。
basement_object_id：地下室维度归属，只能引用 basement 类型。
floor_object_id：楼层维度归属，只能引用 floor 类型。
physical_zone_object_id：实体工程区域归属，只能引用 physical_zone 类型，如屋面、外立面、室外总平、地下局部。
functional_area_object_id：功能触发区归属，只能引用 functional_area 类型，如手术部、ICU、数据机房、消防控制室。
project_materials：不再通过工程对象表达专业，材料专业仍由 specialty_type 等业务字段表达。
acceptance_plans.building_object_id：验收计划所属楼栋，只能引用 building 类型。
```

写入时若传入的对象类型与字段语义不一致，后端必须返回 400，不允许静默保存。

`engineering_objects.path` 规则：

```text
path 使用对象 ID 路径，格式为 /rootId/childId/grandchildId
根节点 path = /id
level = path 中 ID 段数量
创建对象时由后端生成 path 和 level
更新 parent_id 时，必须同步刷新自身和所有后代的 path / level
禁止前端提交 path / level
```

RLS 与发布迁移口径：

```text
engineering_objects 必须 ENABLE ROW LEVEL SECURITY
SELECT 策略：company_admin 或项目成员可读
INSERT / UPDATE / DELETE 策略：仅 service_role 可写，业务写入统一走后端 API
新增 numbered migration 后，必须同步更新仓库仍作为全新环境基线使用的全量迁移快照：
CLEAN_MIGRATION.sql
CLEAN_MIGRATION_V2.sql
CLEAN_MIGRATION_V3.sql
CLEAN_MIGRATION_V4.sql
FULL_MIGRATION_ALL_IN_ONE.sql
FULL_MIGRATION_ALL_IN_ONE_FIXED.sql
```

保留现有字段，不删除：

```text
tasks.specialty_type
tasks.phase_id
tasks.building_id
tasks.region_id
tasks.participant_unit_id
```

这些字段在 v1.4 后只作为兼容字段读取和回填，不再作为新业务规则的权威来源。

## 3. 对象初始化规则

后端新增初始化服务：

```text
engineeringObjectBootstrapService
```

项目创建或首次进入对象管理时，为项目初始化工程对象能力。默认只生成项目级必要范围骨架，不生成专业对象，也不强制生成具体楼栋、楼层、实体工程区域等业务对象。

初始化时还必须尝试生成工程特征画像：

```text
从项目类型、模板选择、导入字段、WBS 标准库和项目画像中推断 projectTypeCode / structureTypeCode / methodVariantCodes
只在已有可靠来源时写入 metadata.projectGenerationFacts
没有可靠来源时只初始化必要范围骨架，不制造楼栋、楼层、实体区域、功能区、结构体系或工法对象
后续模板生成、工期建议和算法 seed 匹配只能把缺失特征视为低置信，不得强制用户补录
```

对象类型：

```text
分期 phase
标段 section
楼栋 building
地下室 basement
楼层 floor
实体工程区域 physical_zone
功能触发区 functional_area
```

对象父子层级规则：

```text
phase 可包含 section / building / basement / physical_zone
section 可包含 building / basement / physical_zone
building 可包含 floor / physical_zone / functional_area
basement 可包含 floor / physical_zone / functional_area
floor 可包含 functional_area
physical_zone 可包含 floor / functional_area
functional_area 为叶子节点
```

服务端创建和更新对象时必须校验父子关系。前端树形管理只展示合法的新增子级入口，不能只靠前端隐藏按钮来保证规则。

专业、系统、专项不是工程对象初始化内容。土建、机电、装饰装修、幕墙、消防、智能化、景观、市政等语义保留在 `specialty_type`、工程分类、标准工项、模板 metadata 和项目画像中。

对象编码规则：

```text
phase: PH-001
section: SG-001
building: BD-001
basement: BS-001
floor: FL-001
physical_zone: PZ-001
functional_area: FA-001
```

编码由后端按项目和对象类型自动递增生成，前端不允许手写 `object_code`。


## 5. 终态对象处理策略

v1.4 不再设计旧范围维度兼容层。当前没有历史生产数据和存量用户迁移负担，因此工程对象主数据一步到位采用 7 类范围树：

```text
phase / section / building / basement / floor / physical_zone / functional_area
```

废止内容：

```text
旧范围维度表和工程对象之间的 adapter
旧范围维度接口
zone / professional / subproject / custom 工程对象类型
任务和材料上的旧专业/区域对象字段
legacy 对象类型元数据
```

范围树语义：

```text
phase：项目分期或实施阶段
section：标段、施工段、合同段
building：地上单体
basement：地下室、地库、人防地下空间
floor：楼层
physical_zone：现场真实物理区域，例如屋面、外立面、室外总平、地库分区、设备平台
functional_area：功能触发区域，例如手术部、ICU、数据机房、厨房、消防控制室、客房区
```

WBS、材料、验收、报表处理规则：

```text
WBS 任务范围只读取最终 7 类工程对象字段
材料专业使用 specialty_type 等业务属性表达，不创建专业工程对象
验收、报表、驾驶舱统计按最终对象 ID 和对象路径聚合
无法归入范围树的专业、工法、专项、系统语义进入模板 metadata、标准工项、工程分类或业务标签
```

跨模块字段映射：

```text
tasks.phase_object_id             -> phase
tasks.section_object_id           -> section
tasks.building_object_id          -> building
tasks.basement_object_id          -> basement
tasks.floor_object_id             -> floor
tasks.physical_zone_object_id     -> physical_zone
tasks.functional_area_object_id   -> functional_area
project_materials.specialty_type  -> 材料业务专业属性，不进入工程对象树
reports 归属分组                 -> 优先使用 engineering_objects.id / path / object_type
```

材料和验收不再通过旧专业对象或旧区域对象补范围字段；确需表达施工空间时，直接选择 `building / basement / floor / physical_zone / functional_area`。

前端入口处理规则：

```text
保留当前甘特图顶部“范围维度”按钮
按钮打开的弹窗内部升级为“工程对象管理”
不新增孤立的“工程对象管理”主菜单
前端状态直接消费 engineeringObjects，不再维护旧 scopeDimensions 适配数据
```

`participant_units`：

```text
继续作为责任主体主数据独立存在
不合并进 engineering_objects
任务责任单位仍引用 participant_units
任务工程对象归属引用 engineering_objects
```

## 6. 任务与汇总逻辑

任务创建、编辑接口支持新增对象字段：

```ts
engineeringObjectId?: string
buildingObjectId?: string
basementObjectId?: string
sectionObjectId?: string
floorObjectId?: string
physicalZoneObjectId?: string
functionalAreaObjectId?: string
phaseObjectId?: string
```

字段在 DTO 中保留可选写法，是为了支持不同任务类型的最小范围归属；但 active 任务新建和编辑保存时，后端必须校验至少存在一个有效范围对象 ID。`participant_unit_id`、责任人、任务标题、专业文本字段不能替代工程范围归属。

写入规则：

```text
只写最终 7 类对象字段
专业、系统、专项、工法进入业务属性或模板语义，不写工程对象字段
```

读取规则：

```text
读取 object_id 关联对象、对象路径和对象类型
不存在对象 ID 时按“范围缺失”治理，不用旧文本兜底制造范围
```

任务链路必须同步改造这些层，不允许只改前端或只改路由：

```text
server/src/middleware/validation.ts
新增 engineeringObjectId / phaseObjectId / sectionObjectId / buildingObjectId / basementObjectId / floorObjectId / physicalZoneObjectId / functionalAreaObjectId 的 camelCase 入参校验，同时支持对应 snake_case 入参。

server/src/types/db.ts
Task 类型包含 engineering_object_id / phase_object_id / section_object_id / building_object_id / basement_object_id / floor_object_id / physical_zone_object_id / functional_area_object_id 以及响应端 camelCase 可选字段。

server/src/services/dbService.ts
createTask / updateTask 必须写入最终 snake_case 范围列，并返回对象摘要。

server/src/services/taskWriteChainService.ts
createTaskInMainChain / updateTaskInMainChain 在写入前调用工程对象校验与范围一致性 helper。

server/src/routes/tasks.ts
请求进入后统一把 camelCase 对象字段规范化为 snake_case，响应时返回 snake_case 和 camelCase，供当前前端直接消费。
```

范围对象展示规则：

```text
phase_object_id -> phase_name / phase_object_code
section_object_id -> section_name / section_object_code
building_object_id -> building_name / building_object_code
basement_object_id -> basement_name / basement_object_code
floor_object_id -> floor_name / floor_object_code
physical_zone_object_id -> physical_zone_name / physical_zone_object_code
functional_area_object_id -> functional_area_name / functional_area_object_code
```

`taskAttributionSummaryService` 和 `task-summaries` 改为基于 `engineering_objects` 汇总，输出仍兼容当前前端字段：

```ts
dimension: 'phase' | 'section' | 'building' | 'basement' | 'floor' | 'physical_zone' | 'functional_area' | 'participant_unit' | 'assignee' | 'unassigned'
source: 'engineering_object' | 'participant_unit' | 'project_member' | 'unassigned'
```

## 7. 前端改造

保留当前甘特图顶部“范围维度”按钮，但弹窗内部升级为“工程对象”管理。

`ScopeDimensionsDialog` 改造成工程对象树形管理：

```text
左侧：对象类型筛选，分期 / 标段 / 楼栋 / 楼层 / 区域 / 专业 / 子项目 / 其他
中间：对象树
右侧或弹窗：新增 / 编辑对象
```

任务表单改造：

```text

楼栋：从 building 类型选择
标段：从 section 类型选择
```

材料和验收页面：

全局状态新增：

```ts
engineeringObjects: EngineeringObject[]

```

保留：

```ts
participantUnits
```

`participantUnits` 继续作为责任主体主数据；范围树状态只保留 `engineeringObjects`。

## 8. 类型与前端 API

新增共享类型：

```ts
export type EngineeringObjectType =
  | 'phase'
  | 'section'
  | 'building'
  | 'basement'
  | 'floor'
  | 'physical_zone'
  | 'functional_area';

export interface EngineeringObject {
  id: string;
  projectId: string;
  objectType: EngineeringObjectType;
  objectCode: string;
```

# 2026-06-01 终态口径修订：无历史数据，不保留兼容层

本文件的工程对象模型以 v1.4.22.1 收口结果为准。当前产品没有存量数据和用户迁移负担，因此不再保留旧范围维度兼容层，也不再保留旧工程对象类型。

- 工程对象类型唯一支持 7 类：`phase / section / building / basement / floor / physical_zone / functional_area`。
- 已删除工程对象类型：`zone / professional / subproject / custom`。其中“专业/专项”仍可作为材料 `specialty_type`、标准工项、模板类型、WBS 业务语义存在，但不再是工程对象。
- 任务范围字段唯一支持：`engineering_object_id / phase_object_id / section_object_id / building_object_id / basement_object_id / floor_object_id / physical_zone_object_id / functional_area_object_id`。
- 删除旧任务字段：`zone_object_id / professional_object_id`；材料也不再写 `professional_object_id`，只保留业务专业属性 `specialty_type`。
- 删除 `/api/scope-dimensions` 兼容接口和 `scope_dimensions / project_scope_dimensions` 适配层；前端直接消费 `/api/engineering-objects`。
- 不再设计 `legacy_object_type`、`DEPRECATED_OBJECT_TYPE_VALUES`、旧 unit/custom 映射、旧 scope 表迁移脚本或 adapter。
- v1.4.22.1 快速建模 Step 3 的结构化范围录入表属于当前验收目标，不是后续增强项。商业化主路径固定为：组织划分 -> 物理空间 -> 共享范围 -> 空间细分 -> 范围树确认。项目整体规模改由 Step 1 填写；Step 3 只负责现场空间建模。
- 自由文本解析和直接树编辑不得作为范围树默认入口或验收依据；按业态推荐只能输出“推荐物理空间草稿”，并追加回填到录入表，由用户采用、编辑、确认后再生成工程对象，不得覆盖已录入的分期、标段或其他组织划分。
- 物理空间顶层只表达真实空间：单体建筑、地下空间、室外总平、独立工程区。室外道路、园建绿化、管网、围墙大门、海绵设施等不是顶层空间类型，必须作为室外总平下的水平细分；独立工程区默认作为末级物理范围。
- 地下室、室外总平等项目级共享范围必须保留“项目整体”挂载入口；存在分期、标段时也不得强制挂到某个标段。共享范围若跨标段，必须记录明确的 `sharedSectionObjectIds / sharedSectionNames`，支持只选择部分标段共享，不再使用不可解释的粗粒度跨标段开关。
- 空间细分同时服务竖向层级和水平分区：单体建筑按楼层或塔楼+裙房组合生成；地下空间先根据物理空间步骤录入的 `basementLevelCount` 自动生成 B1/B2 等地下层，不重复输入起止层，必要时再在具体地下层下做水平分区；室外总平只做道路区、园建绿化区、管网区、围墙/大门区、海绵设施区等水平细分。
- 楼层性质属于楼层节点属性，默认全部为标准层；用户只在范围树确认或高级树编辑中点选具体楼层后修改为架空层、避难层、设备层、转换层、屋面层、夹层、裙房屋面等单一性质，并且范围树必须显示非标准楼层标签，供模板生成、工期和专项触发读取。
- 节点属性面板不得在每个步骤都重复出现。常规流程只在“范围树确认”展示节点属性；“高级树编辑”作为异常复杂场景的补救能力，可以提前打开，但不是主路径。
- 塔楼+裙房组合在单栋楼内生成塔楼区、裙房区两个 `physical_zone`，用于保证同一楼层不重复划分；跨多栋塔楼共享的裙房不应挂在某一栋楼下，应作为独立/共享物理空间建模后再通过共享范围选择具体标段。
- 结构化录入产出的 `childrenComplete` 与 `decompositionMode` 是实体空间 MECE 闭合主依据；面积覆盖率只作为 info 级辅助参考，不作为闭合判定主依据。
- v1.4.22.1 向导业务语义图标统一由 `wizardScopeIcons.tsx` 的 Lucide 注册表提供，覆盖入口、步骤、业态、项目空间、特征、草稿、保存、生成、预警等状态；工程对象主数据不再依赖各组件自定义图标口径。
