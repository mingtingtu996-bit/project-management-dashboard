## 0. 为什么单独起 D（不并入 A/B）

上线前 8 项里，租户隔离是唯一没有独立 owner 的：A 管依赖归位、B 管 quota，RLS 跨租户隔离**不天然属于任何一份主线**，结果"谁都提了、谁都没真正落地"。而它是 8 项里后果最严重的一项。故单独成文，给它确定的 owner 与验收。

## 1. 真实基线（本轮核查代码，非台账记账——且比台账更糟）

| 核查项 | 真实结果 | 含义 |
|---|---|---|
| 后端 DB 连接身份 | `dbService.ts:42` 优先用 `SUPABASE_SERVICE_KEY`（service_role） | **决定性事实：service_role 在 PostgreSQL 中天然 bypass RLS。** 后端所有查询都绕过 RLS |
| 现有 RLS 策略 | migrations `007_enable_rls_policies.sql`（tasks/milestones 等 7 表）、`011`（phases 等）已 `ENABLE` + `CREATE POLICY` | 策略**存在**，但因上一行 = **形同虚设的死代码**：后端以 service_role 连库，策略永不触发 |
| RLS 策略的租户判据 | 全部基于 `auth.uid()`（`007:62` 等） | `auth.uid()` 是 Supabase 会话函数；后端用**自有 JWT + `companyContext.ts`** 解析租户，根本不走 Supabase 会话 → 即使不 bypass，判据也对不上 |
| 当前真正在隔离的是什么 | 应用层 `companyContext`（`auth/companyContext.ts`）+ 各 route/service 手写 `company_id` 过滤 | **隔离真值在应用层，不在数据库层。** 任何一处 route 忘了带 company 过滤 = 该处裸奔（台账 C-17.39：duration-accuracy 无公司过滤即实例） |
| JWT fast-path | C-17.40：5 个治理路由用 JWT `globalRole` 走 fast-path，绕过 `company_members` 实表校验 | 角色冻结在 7 天 JWT 内、不复核实表，跨公司越权风险 |
| 跨租户契约测试 | `workspaceIsolationContract.test.ts` / `workspaceIsolationMatrix.test.ts` 存在 | 但 C-17.47 记账："grep 白名单式，新路由默认裸奔，RLS 脚本没进 CI" |

> **核查结论（必须先让你知道，不迎合）**：台账说"RLS 需核查"，实际比台账更糟——**RLS 策略不是"没启用"，是"启用了但因 service_role 连接而完全失效"**。这比没有 RLS 更危险：它制造了"我们有 RLS"的安全错觉。当前真实隔离 100% 靠应用层逐查询过滤，**一处遗漏即一处数据泄漏**，且没有数据库兜底。

## 2. 隔离策略抉择（D 的核心决策，必须先定）

有两条路，**不能既要又要、半套最危险**（现状就是半套）：

**路线甲：应用层为唯一隔离真值（推荐，贴合现状与上百用户规模）**
- 承认隔离在应用层，把它做成**单一、可强制、可回归**的：所有租户数据访问必须经过统一的 company-scoped 查询封装，禁止 route/service 手写裸查询。
- 把失效的 RLS 死代码**明确标注为非隔离依赖**（保留或移除，但不得让人误以为它在隔离）。
- 配套：CI 静态扫描——任何访问租户表的查询未经过 scoped 封装即阻断（堵 C-17.39 类遗漏）。

**路线乙：启用真正的数据库层 RLS（更强，但成本高、与现架构冲突）**
- 要求后端改用**最小权限连接角色**（非 service_role）+ 每请求 `set_config` 注入租户上下文，policy 判据从 `auth.uid()` 改为读注入的 company/user。
- 工作量大、要重构连接层、风险高；对上百用户规模属过度工程。

**决策（已拍板）：上线前走路线甲**（应用层单一真值 + 强制封装 + CI 扫描 + 修 C-17.40 fast-path），**路线乙的数据库兜底移交 v1.6**（接入有不可赔数据的重要客户前）。理由：现架构整体是 service_role + 应用层过滤，临上线重构连接层风险 > 收益；但"半套 + 错觉"必须立刻终结。

> C-18.L01–L05 在这里仅作为“RLS 已失效、应用层为准”的核查证据，不代表数据库层兜底已经上线。

> 已确认按**甲**执行；下面执行步骤按甲展开。

## 3. 执行步骤（按路线甲）

> **上线前不可拆包（承重）**：步骤 2/3/4 是**一个整体，必须同时完成、不得只做一半**。原因——单修 bug（2/3）= 把应用层这道唯一的墙补严，但 migrations 007/011 的失效 RLS 死代码还在，"以为数据库在兜底"的**安全错觉照旧**；单处置死代码（4）= 点破错觉但漏洞没补。**只有"修 23.1 隔离 bug + 处置死代码"两半都做，错觉才真正消除、且唯一的墙是严的。** 任何"先修 bug、回头再点破错觉"的拆法都不接受——回头往往不回头，留下"洞补了但仍以为有两道墙"的危险中间态。

**【上线前不可拆包：修隔离 bug + 消除错觉】= 步骤 2+3+4 捆绑**

1. **统一 company-scoped 数据访问封装**：所有租户表的读写经过单一封装（强制带 company/project 边界），route/service 不得手写裸 `company_id` 过滤或无过滤查询。（这是承载下面修复的地基）
2. **〔包·补洞〕全 route 隔离审计 + 修 23.1 隔离 bug**：以 A 的 registry（route 清单）为输入，逐个 route 核"是否经过 scoped 封装"；清零 v1.4.23.1 隔离债务——**C-17.39**（duration-accuracy 等缺公司过滤）、**C-17.40**（5 个治理路由 JWT `globalRole` fast-path 绕过 `company_members`）、**C-17.41**（认证不复核用户存活/吊销）。fast-path 改为查 `company_members` 实表 + 复核存活。
3. **〔包·消错觉〕失效 RLS 死代码处置**：明确处置 migrations 007/011 的 RLS 策略——它们当前**不构成隔离依赖**（service_role bypass + auth.uid 判据失配）。要么移除，要么保留并加显著注释"此 RLS 当前失效、不兜底隔离、隔离在应用层、v1.6 路线乙再激活"。**不得让台账、注释、AI 或任何人误以为它在隔离。** 这一步是消除"安全错觉"的唯一动作，与步骤 2 同批交付，缺它则错觉留存。
4. **CI 隔离门禁**：① 静态扫描——访问租户表未经 scoped 封装即阻断（堵新路由裸奔，对应 C-17.47）；② 跨租户契约测试从"grep 白名单"升级为真实跨公司读/写/聚合三类用例，进 CI（C-18.L01-05 的应用层等价校验）。
5. 隔离封装与扫描脚本归 v1.4.23.1 §4.7.1「底座·组织权限」单元，登记进 A 的 registry。

## 4. 验收标准

1. 所有租户表访问经过统一 scoped 封装；CI 静态扫描可阻断未封装的新查询。
2. **不可拆包整体通过（步骤 2+3+4 同批）**：补洞与消错觉必须一起验收——下面 3/4/5 全绿才算包通过，不接受"bug 修了但死代码还在制造错觉"或反之的中间态。
3. 全 route 隔离审计通过：无 route 缺 company 过滤（C-17.39 清零）；C-17.40 治理路由不靠 JWT fast-path、查 `company_members` 实表；C-17.41 认证复核用户存活/吊销。
4. 失效 RLS 死代码已处置：移除或加显著"失效·不兜底·应用层为准"注释，台账/注释/AI 不再被误导有 RLS 兜底——"安全错觉"消除。
5. 跨租户契约测试覆盖跨公司读/写/聚合三类，进 CI 且可阻断回归（非 grep 白名单）。
6. A 公司用户对 B 公司项目的读/写/聚合，端到端验证全部拒绝。

## 5. 边界与诚实声明

- **核查决定性事实**：后端以 service_role 连库（`dbService.ts:42`），现有 RLS 策略全部失效；当前隔离 100% 在应用层。D 的前提是承认这一点，不假装 RLS 在工作。
- **路线甲 ≠ 数据库兜底**：甲是"把应用层隔离做成唯一可强制真值"，没有数据库层兜底。真正的 RLS 兜底（路线乙）移交 v1.6，触发=接入有不可赔数据的重要客户前。这是诚实的取舍，不是遗漏。
- C-18.L01–L05 原文要求**连 prod/staging 查 `pg_class`/`pg_policies`/`pg_roles`** 核 RLS——在路线甲下，这些核查结论应是"RLS 不作隔离依赖、应用层封装为准"，而非"补齐 RLS policy"。若选路线乙才需逐表补 policy。
- 隔离封装的具体形态需结合现有 `companyContext` 与 `dbService` 落地，本文件定**策略与门禁**，不定具体函数签名。
- 行号/连接方式为本轮核查事实，随代码演进以实际为准。
