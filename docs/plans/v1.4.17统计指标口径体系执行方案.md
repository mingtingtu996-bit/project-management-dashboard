## 0. 2026-06-01 final range-tree boundary (authoritative)

This v1.4-series plan follows the final range-tree model. There is no production history or existing user data that needs a compatibility layer.

Authoritative engineering object types are exactly: `phase / section / building / basement / floor / physical_zone / functional_area`.

The following compatibility surfaces are deleted and must not be reintroduced in runtime code, migrations, or frontend contracts:

- `zone / professional / subproject / custom` as engineering object types.
- `zone_object_id / professional_object_id` task fields.
- `project_materials.professional_object_id` and `engineering_categories.professional_object_id`.
- `legacy_object_type`, deprecated object-type arrays, legacy bridge/backfill helpers, and old scope adapter functions.
- `/api/scope-dimensions`, `scope_dimensions`, and `project_scope_dimensions` as active application surfaces.

Professional/system/domain/method semantics remain business facts through `specialty_type`, `engineering_category_id`, `standard_work_code`, template metadata, and project profile facts. They are not range-tree objects.

Any older section in this document that mentions deleted object types, deleted fields, old scope tables, or compatibility adapters is superseded by this boundary.
# v1.4.17 统计指标口径体系执行方案

## 1. 目标

v1.4.17 的目标是把当前应用中分散在 `Dashboard / Reports / CompanyCockpit / TaskSummary / ResponsibilityView / 项目健康度 / 进度偏差 / 风险问题 / 里程碑 / 月度计划 / 数据质量 / AI 分析` 里的统计指标统一成一套稳定的指标口径体系。

本章解决的是系统能否稳定回答这些问题：

```text
同一个指标在不同页面是不是同一个算法
指标到底来自任务实时事实、历史快照、月度计划、项目基线、风险问题链，还是数据质量快照
前端能不能自己按列表临时算指标
当指标缺少输入时，是显示 0、空、暂无，还是数据待完善
历史快照按旧口径生成后，是否会被新口径反写
Dashboard、Reports、AI、周报、健康度是否消费同一套指标 key
后续新增页面或新数据对象如何接入指标体系
```

本章继续沿用 v1.4.8 之后形成的统一原则：

```text
用户维护业务事实，系统判断治理语义
前端展示业务结果，不暴露指标公式、SQL、分母分子、rule_code、metric_source 等治理字段
指标口径由后端统一注册和计算，前端只消费结果、格式化展示和跳转定位
不能计算的指标显示“暂无”或“数据待完善”，不得用 0、100%、空数组伪造成有效指标
历史快照只用于历史对比，不被当前任务列表反写
```

本章所说“新增指标”主要指后端新增或补全指标注册项、统一计算口径、统一快照口径，不等于前端新增大量指标卡或新页面。

```text
已有页面继续展示当前业务需要的指标
后端可能新增 metric_key、计算服务、快照字段和兼容映射
前端指标数量原则上不增加，除非对应页面原本就需要该业务信息
前端展示变化主要是同一指标在 Dashboard、Reports、周报、AI 中口径一致，不再各算各的
```

## 4. 核心口径

### 4.1 指标事实源分层

指标必须明确来自哪一层事实源：

```text
实时执行事实：tasks、task_progress_snapshots、task_conditions、task_obstacles、risks、issues、warnings、project_entity_links
历史承诺快照：task_baselines、task_baseline_items、monthly_plans、monthly_plan_items、closeout snapshots
项目日快照：project_daily_snapshot，用于 Dashboard、趋势、公司汇总、周报和 AI 历史对比
专项事实：acceptance_plans、acceptance_records、construction_drawings、pre_milestones、project_materials
质量与可信度事实：data_quality_findings、data_confidence_snapshots
来源映射事实：data_lineage_links、data_lineage_events、project_entity_links
技术观测事实：client_errors、performance_reports，仅用于系统运维，不进入施工业务指标
```

原则：

```text
实时指标从任务列表和专项事实计算
趋势指标从快照计算
历史承诺指标从基线和月计划快照计算
责任归因指标从任务完成事实和责任主体主数据计算
数据可靠性只影响指标可信度、封顶、可用性说明，不直接改业务指标值
```

### 4.1.1 稳定数据与权重边界

指标只能充分利用现有应用和 v1.4 系列落地后可稳定产生的数据，不得为了指标完整性假设不存在或尚未稳定维护的字段。

第一阶段稳定输入优先级：

```text
任务实时事实：计划日期、实际开始、实际完成、进度、状态、WBS 结构、任务来源
计划快照事实：已发布基线、已确认月计划、项目日快照、指标快照
治理事实：工程对象、WBS 工程分类、责任主体、状态字典、来源映射
执行影响事实：依赖、开工条件、阻碍、风险、问题、预警
专项事实：材料、图纸、证照、验收、关键节点、里程碑
预测事实：经验工期、剩余工期预测、预计完成偏差
```

权重边界：

```text
进度、偏差、健康、公司级汇总指标不得按任务条数简单平均
第一阶段优先使用计划工期、WBS 层级、关键路径、关键节点、工程对象范围和业务影响作为权重
工程量、产值、合同额、建筑面积只有在字段稳定维护、单位口径清晰、可按任务或 WBS 节点可靠归集后，才作为增强权重
工程量未稳定时，不得用 progress 字段、任务数量或文本描述伪装工程量完成率
```

### 4.1.2 工期类指标计算边界

工期类指标不重新计算现场工期算法。凡涉及参考工期、剩余工期、预计完成、预测延期、工期偏差和工期可靠性的指标，必须优先消费 v1.4.18 的统一输出：

```text
recommendedDurationDays
conservativeDurationDays
remainingDurationDays
forecastFinishDate
forecastDelayDays
confidence
businessReason
factorSummary
```

metricCalculationService 不得重新实现 v1.4.7.4 的季节产能、工作日历、验收时间轴事实 / 补链候选、流水段节奏、现场承载压力、工序硬约束、进度趋势学习或填报异常识别。

```text
v1.4.7.4 负责提供现场领域知识和算法上下文
v1.4.18 负责把这些上下文转化为新建任务参考工期和执行中任务剩余工期预测
v1.4.17 只消费 v1.4.18 输出，形成指标口径、指标快照和跨页面统一展示
```

工期类指标快照可记录 `calculation_context`：

```ts
interface DurationMetricCalculationContext {
  duration_source: 'standard' | 'benchmark' | 'forecast' | 'legacy';
  adjusted_by: Array<
    | 'seasonal_productivity'
    | 'workflow_sequence'
    | 'resource_conflict'
    | 'process_constraint'
    | 'external_readiness'
    | 'progress_velocity'
    | 'progress_quality'
  >;
  confidence_level: 'high' | 'medium' | 'low';
  factor_summary_available: boolean;
}
```

口径约束：

```text
adjusted_by 仅用于后端解释、v1.4.19 偏差归因和口径追踪，不在前端展示技术字段
若 v1.4.18 输出不存在，指标 availability = data_pending / source_unavailable / low_confidence
不得回退到前端自算、旧 ai_duration 或页面临时公式作为权威工期指标
reference_duration / ai_duration 只能作为 legacy 兜底，并必须标记 duration_source = legacy
```

### 4.2 指标可用性

每个指标必须返回可用性：

```ts
type MetricAvailabilityStatus =
  | 'ready'
  | 'insufficient_data'
  | 'not_applicable'
  | 'data_pending'
  | 'source_unavailable'
  | 'low_confidence';
```

展示规则：

```text
ready：正常展示数值
insufficient_data：显示“数据不足”
not_applicable：显示“不适用”
data_pending：显示“数据待完善”
source_unavailable：显示“暂无”
low_confidence：显示数值，但附带轻提示或在 Dashboard 数据可靠性中解释
```

禁止：

```text
用 0 代表没有数据
用 100% 代表没有异常
用空数组伪造无风险、无延期、无问题
前端在接口失败时自行兜底成健康状态
```

### 4.3 指标过滤口径

所有指标必须统一 active predicate：

```text
active 任务：未删除、未归档、未取消、未关闭，且属于当前实时任务列表
completed 任务：状态字典归一为 completed，或 progress = 100 且后端自动写入 actual_end_date
cancelled 任务：不进入完成率分子，不进入执行任务分母，但可进入取消率、偏差解释和计划重编建议
结构行：不进入任务执行完成率分母；只作为 WBS 汇总容器
工序行：默认进入执行进度和完成率分母
验收任务：进入验收域指标，不默认进入普通施工任务执行完成率，除非作为普通任务关联验收事项展示
停用主数据：不进入新建选择器和当前分组，但历史快照继续显示当时名称
source_deleted：不删除历史指标，只标记来源已失效
```

执行分母优先级：

```text
优先使用 v1.4.3 标准任务字段判断：is_executable = true 且 is_wbs_summary = false 的任务才能进入普通施工执行类指标分母。
is_wbs_summary = true 的结构汇总节点只能作为聚合容器，不直接进入完成率、延期率、任务执行进度分母。
acceptance_required / acceptance_task / acceptance linkage 指向的验收事项进入验收域指标；除非该行同时满足普通施工可执行任务口径，否则不进入普通施工任务完成率分母。
状态必须通过 v1.4.5 状态字典归一后再进入 active / completed / cancelled / closed / archived 判断，不能直接按原始 status 字符串计算。
progress_method = quantity 的任务由 v1.4.3 工程量规则换算进度；前端不得用 progress 字段单独覆盖工程量进度口径。
只有当任务具备稳定计量单位、计划工程量、完成工程量和完成规则时，才启用工程量口径；否则相关指标 availability = data_pending / low_confidence / not_applicable，不得伪造工程量指标。
```

### 4.4 前端消费边界

```text
Dashboard：消费后端项目实时摘要、项目日快照、关键节点摘要、数据可靠性；不前端扫描任务重算核心指标
Reports：消费后端趋势、偏差、S-Curve、专项分析；不前端硬编码指标列表和分母分子
TaskSummary：消费 taskAttributionSummaryService；前端不自行判定责任归因健康档
CompanyCockpit：消费公司级项目快照和趋势聚合；不跨项目拉任务列表自算
RiskManagement：只展示业务风险、问题、预警指标；不展示数据可靠性卡片
Milestones：消费 milestoneOverview / keyNodeSummary；不自行扫描任务推导关键节点
专项管理页面：展示本领域业务指标，不变成指标治理页面
AI 分析：只消费后端 metric context，不直接读取前端缓存或局部列表
```

```ts
  domain: MetricDomain;
  valueType: MetricValueType;
  unit?: string;
  source: MetricSource;
  defaultGranularity: MetricGranularity;
  supportedGroupBy: MetricGroupBy[];
  authoritativeService: string;
  numerator?: string;
  denominator?: string;
  emptyValuePolicy: 'null' | 'zero_when_true_zero' | 'not_applicable';
  availabilityInputs: string[];
  qualityDimensions: string[];
  snapshotPolicy: 'realtime_only' | 'daily_snapshot' | 'monthly_snapshot' | 'commitment_snapshot';
  consumers: MetricConsumer[];
  legacyAliases?: string[];
  deprecated?: boolean;
}
```

说明：

```text
authoritativeService 是指标唯一权威计算服务
numerator / denominator 用业务语言描述分子分母，不暴露 SQL
emptyValuePolicy 决定指标不可用时如何展示
availabilityInputs 决定哪些前置数据缺失时返回 unavailable
qualityDimensions 与 v1.4.16 数据质量维度对应
consumers 是指标允许进入的消费方列表；同一指标可以同时服务 Dashboard、Reports、AI、周报和通知，不得用单一 frontendVisibility 限制多端消费
legacyAliases 用于旧字段和旧前端命名兼容
```

类型扩展要求：

```text
MetricSource 必须从当前 projectExecutionSummaryService / project_daily_snapshot / taskAttributionSummaryService 扩展到 progressDeviationService、projectHealthService、riskStatisticsService、materialReportsService、acceptanceSummaryService、preMilestoneBoardService、dataQualityService、metric_value_snapshots 等来源。
MetricGroupBy 必须新增 professional、zone、engineering_object、wbs_category、scope_dimension 等 v1.4 之后的标准维度。
旧 building / specialty / region / phase 继续作为 legacy groupBy 兼容输入，但服务层必须映射到 engineering_object / professional / zone / scope_dimension；新指标不得继续把 specialty / region 当主口径。
旧 groupBy 映射固定为：specialty -> professional，region -> zone，building -> engineering_object(object_type = building)，phase -> engineering_object(object_type = phase)。scope_dimension 只作为旧范围维度兼容适配层，不作为新指标主分组口径。
unsupported groupBy 必须由后端返回错误或 availability = not_applicable，不允许前端静默兜底。
```

## 6. 核心指标清单

### 6.1 项目执行指标

```text
overall_progress：项目整体加权进度
权威来源：projectExecutionSummaryService + progressCalculation
分母：active 工序/执行任务的工期权重
分子：任务 progress * 工期权重
快照：project_daily_snapshot.overall_progress
不可用：无可评估任务时 data_pending

planned_progress：截至当前日期理论应达进度
权威来源：projectHealthService / 后续 metricCalculationService
口径：先按任务计划窗口计算单任务截至今日的应达进度，再按任务权重汇总
单任务应达进度：今日在该任务计划周期中的时间位置，未到计划开始为 0，超过计划完成为 100
项目应达进度：Σ(单任务应达进度 × 任务权重) / Σ任务权重
权重：第一阶段使用 active 工序/执行任务的工期权重；后续有工程量、产值或合同额后可升级为工程量/产值权重
禁止：不得按任务条数简单平均；不得在工程量字段未稳定时用任务数量或 progress 字段冒充工程量权重
不可用：缺少计划开始/完成日期时 data_pending

progress_deviation：进度偏差
权威来源：progressDeviationService
公式：actual_progress - planned_progress
展示：Reports / Dashboard 摘要 / AI
不可用：缺计划窗口或缺执行进度时 data_pending

active_delayed_tasks：当前延期任务数
权威来源：projectExecutionSummaryService
口径：active 且未完成任务超过计划完成日期
快照：project_daily_snapshot.active_delayed_tasks

completed_late_tasks：已完成但实际完成晚于计划完成日期的任务数
权威来源：projectExecutionSummaryService / taskSummaryService
口径：已完成任务 actual_end_date 晚于 planned_end_date
用途：用于历史履约分析，不混入 active_delayed_tasks

open_delay_days：当前开放延期天数
权威来源：projectExecutionSummaryService / project_daily_snapshot
口径：当前未完成延期任务从计划完成日到今日的延期天数求和

completed_delay_days：历史完成延期天数
权威来源：taskSummaryService / task_completion_reports
口径：已完成延期任务 actual_end_date - planned_end_date 的天数求和

critical_delay_days：关键路径延期影响天数
权威来源：criticalPathService / progressDeviationService
口径：关键路径任务产生的延期影响天数

delay_days：兼容旧字段
口径：仅保留为旧接口兼容字段，新指标计算优先使用 open_delay_days、completed_delay_days、critical_delay_days
注意：不能与 delay_count 混用，也不能把历史已完成延期和当前未完成延期混成一个业务结论

delay_count：兼容旧字段
口径：仅保留为旧接口兼容字段，读取时优先解释为 active_delayed_tasks 的旧别名
注意：新指标不得继续使用 delay_count 表达延期次数；如果确需统计次数，必须明确是 open_delay_task_count、completed_late_task_count 还是 milestone_delay_count

s_curve_planned_cumulative：S-Curve 计划累计进度
权威来源：metricCalculationService / progressDeviationService
口径：按项目计划窗口或基线/月计划快照生成计划累计曲线
不可用：缺少计划窗口、基线或月计划时 data_pending

s_curve_actual_cumulative：S-Curve 实际累计进度
权威来源：metricSnapshotService + project_daily_snapshot / metric_value_snapshots
口径：优先读取项目日快照 actual overall_progress；当日可叠加实时 projectExecutionSummaryService
不可用：无快照且无实时执行进度时 data_pending

s_curve_metric_context：S-Curve 专用指标上下文
说明：Reports 不能继续在路由或前端临时拼 planned curve；第一阶段旧 /reports/s-curve 可保留 URL，但内部必须收口到 metricCalculationService / metricSnapshotService
```

```text
/api/progress-deviation
```

目标服务：


API 权限与返回规则：

```text
GET /api/metrics/registry：已登录用户可读取前端可见指标的业务化注册信息；返回 key、label、description、domain、valueType、unit、supportedGroupBy、consumers、availability 文案，不返回 SQL、内部公式、registry_hash 或治理字段。如后续按项目裁剪指标，再通过 projectId 校验项目成员权限。

GET /api/company/metrics/trend：必须校验公司级权限或 company_admin 权限，不允许普通项目成员跨项目读取。
旧 /api/analytics/company-trend 可短期保留“仅聚合当前用户可见项目”的兼容模式，但不得作为新 CompanyCockpit、周报、AI 或公司经营分析的权威接口。
```

## 11. 后续新增数据如何融入指标体系

后续任何新增业务数据、页面、导入字段或系统生成记录，先按两层判断：

```text
单页面局部辅助 UI：只在当前页面、当前弹窗或当前表格中帮助用户操作，例如筛选后多少条、当前选中几行、某个 Tab 的局部 badge、保存前字段缺失数量。这类不作为项目管理判断依据、不进入趋势/考核/AI/提醒，可由领域页面后端接口返回，不必进入全局指标体系。
业务统计 / 跨页面指标：只要该数据会成为 Dashboard、Reports、健康度、AI、周报、提醒、计划生成算法、公司驾驶舱、项目排名、趋势分析或跨页面管理判断依据，就必须进入 v1.4.17 指标体系。
```

底线：

```text
前端不得把局部辅助统计升级成业务指标口径。
材料准时到场率、验收通过率、风险关闭率、责任单位完成率等业务统计，即使第一阶段只在单个专项页面展示，也应由后端领域接口计算；一旦进入跨页面消费或管理判断，必须注册 metric_key。
```

后续任何新增业务指标，只要要进入 Dashboard、Reports、健康度、AI、周报、提醒或计划生成算法，都必须先经过以下流程：

```text
1. 判断是否属于施工业务指标；技术性能、前端错误、接口耗时默认不进入业务指标池
2. 明确业务事实源：数据来自任务、计划、快照、专项表、来源映射还是质量发现
3. 明确指标归属域：project_execution / planning / acceptance / material / risk_issue_warning 等
4. 在 metricRegistry 注册 metric_key
5. 指定 authoritativeService
6. 定义分母、分子、过滤条件、状态过滤、空值策略、可用性原因
7. 定义是否写入 project_daily_snapshot 或 metric_value_snapshots
8. 定义前端消费页面、展示文案、跳转定位和不可用文案
9. 定义是否进入 Dashboard、Reports、AI、周报、通知、计划生成算法
10. 定义数据质量依赖和低可信度处理
11. 定义旧字段、旧接口、旧快照兼容方式
12. 补测试，禁止前端绕过后端自算
```

没有完成注册的指标：

```text
不能进入 Dashboard 指标卡
不能进入 Reports 趋势选择
不能进入 AI 上下文
不能作为项目健康度输入
不能作为提醒触发条件
```
