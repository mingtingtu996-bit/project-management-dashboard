### 0.1 本文件解决什么

1. 建立工期预测的误差闭环：每次预测必须留下预测事件，完工后必须能对上实际结果，并产生可回放、可灰度、可回滚的修正信号。
2. 让 base 工期、剩余工期预测、项目剩余工期预测、上下文因子、冷启动基线在同一套精度指标下验收。
3. 把“会自动变准”的说法限定为已经接入 live 消费且通过灰度门禁的资产；未接入 runtime 的候选、回放、shadow 只能说“有学习证据”，不能说“已改善预测”。
4. 将 A 类工期精度闭环和 B 类计划网络精度层作为确定实施范围写入；B 类包括关键路径、依赖规则、WBS 参考天数、WBS 结构生成和父子汇总。
5. C 类执行进度、baseline、月度计划、计划状态只接事实层和验收口径，不把 baseline / monthly plan 业务承诺做成自学习主线。
6. D 类风险 / 预警 / 健康与 E 类外部条件资产先登记为下游消费者或事实信号来源；除天气、工作日历、材料反馈等直接工期事实信号外，不进入本轮实施。

### 0.2 本文件不做什么

1. 不绕过 v1.4.22.3 的 `publish_anchor / automation_maturity / learning_maturity / learning_target`。
2. 不把回放结果直接写回 `standard_work_duration` seed。
3. 不把其他公司私有样本混入当前公司桶。
4. 不自动改写任务事实、实际完成日期、baseline、monthly plan、依赖关系、关键路径和业务状态。
5. 不把“有 MAE / 有 bandit / 有 replay / 有 candidate”解释为“live 数字已变准”。
6. 不新增普通用户算法配置页、工期精度工作台或普通业务页中的技术治理入口。普通前端仍只在任务列表、任务详情、月度计划、项目健康度、Dashboard / Reports 等既有业务页看到业务化结果、可信度和原因；`prediction event / outcome / MAE / Bias / overcompensation / seed key / source key / publication key` 等技术字段只进入后台治理、审计、测试和管理端证据链。

### 0.3 与 v1.4.22.3 的关系

v1.4.22.3 是治理控制面，v1.4.22.4 是精度执行面。两者必须串联，不能互相替代。

| 维度 | v1.4.22.3 | v1.4.22.4 |
| --- | --- | --- |
| 核心问题 | 哪些规则 / seed / 参数 / overlay 可以被发现、登记、隔离、回放、发布、回滚 | 哪些运行期预测真的因为样本、误差和灰度消费而变准 |
| 资产范围 | 所有影响工期、计划网络、关键路径、依赖顺序、模板结构、风险预警、健康解释的资产都要登记 | 从已登记资产中选 A 类工期、B 类计划网络、C 类事实验收层先建立精度闭环 |
| 主要产物 | `learning_target`、`learning_maturity`、`publish_anchor`、`automation_maturity`、candidate、replay、release-exit、rollback target | prediction event、actual outcome、MAE / Bias / overcompensation、runtime overlay 消费、network outcome 对账 |
| 允许动作 | 生成治理证据、候选、回放、发布请求、回滚包 | 在通过 v1.4.22.3 门禁后，让 canary / published 参数或 overlay 被 runtime 消费 |
| 禁止偷换 | 治理通过不等于精度提升 | 精度改善不能绕过治理发布 |

硬关系：

1. v1.4.22.4 的任何参数、seed、依赖规则、WBS 参考天数、critical path 修正要进入 runtime，都必须先满足 v1.4.22.3 的登记、作用域、回放、冲突清理、发布锚点和回滚目标。
2. v1.4.22.3 已登记为 `frozen_constant / shadow_report_only / governed_candidate / manual_governance_required` 的资产，v1.4.22.4 只能生成精度证据和解锁条件，不能直接把它们当 live 学习资产消费。
3. v1.4.22.3 证明“安全、诚实、可审计”；v1.4.22.4 证明“误差下降、偏差收敛、过度补偿受控”。对外表述必须同时满足这两层。

代码锚点：`durationPrecisionGovernanceBoundaryService.ts` 是本文件与 v1.4.22.3 的边界契约。它把 `register_asset / evaluate_release_gate / publish_runtime_parameter / rollback_runtime_parameter / block_fact_rewrite` 固定归属 v1.4.22.3 governance control，把 `record_prediction_event / record_actual_outcome / calculate_accuracy_metrics / produce_precision_candidate / consume_published_runtime_overlay / claim_accuracy_improved` 固定归属 v1.4.22.4 precision learning，并把 `auto_rewrite_fact` 固定归入 business fact lock。对应测试必须证明：v1.4.22.4 不能绕过 v1.4.22.3 release-exit 直接发布 runtime；v1.4.22.3 不能在没有 v1.4.22.4 MAE / Bias / overcompensation 证据时宣称“更准”；两边都不能自动改写 actual、baseline、monthly plan、已确认依赖、关键路径事实和进度快照。

### 0.3a “越用越准”的合格定义

本文件允许对外表达“越用越准”的前提不是“项目数量变多”，而是：同类、同口径、可采信样本足够后，按分层作用域受控校准，并且校准结果已经进入 runtime 消费。

| 校准层级 | 解决什么问题 | 可自动调整的对象 | 禁止越界 |
| --- | --- | --- | --- |
| 全局 / 行业基线 | 新公司、新账号、长尾工序冷启动 | 匿名 `industry_baseline / segment_baseline` 参考值、冷启动覆盖状态、冷启动置信度 | 不用单家公司私有样本污染全局；样本池不足时不能声称行业基线有效 |
| 公司级 calibration | 同一公司、同类项目、同类工序的稳定偏差 | base P50/P75 blend、公司级 benchmark 权重、公司级 residual overlay、上下文因子乘数 | 不把一个公司的校准外推到其他公司；不写回系统 seed |
| 项目级 overlay | 当前项目运行节奏偏快 / 偏慢 | 剩余工期、预测完成日、项目级 residual overlay、关键路径剩余窗口 | 不反向改写标准工序 seed、专项模板 seed、baseline、monthly plan 或已确认依赖 |
| 手工确认 / 事实锁定层 | 业务承诺、实际状态和可采信样本 | manual override 作为 prediction event 与误差样本来源 | 不允许学习系统自动改写 actual、baseline、monthly plan、进度快照和用户确认事实 |

因此，“可以自动越用越准”的最小标准是：

1. 有 prediction event、actual outcome、MAE / Bias / overcompensation / Coverage 证据。
2. 样本达到当前层级的门槛，且 `accepted` 样本占比足以支撑发布；`weak` 只能做候选证据。
3. 候选通过 replay、冲突检查、最大漂移限制、canary 监控和 rollback target。
4. 发布结果进入 `algorithm_learnable_parameter_runtime_publications`、`duration_forecast_residual_overlays` 或等价 runtime 表，并被业务预测服务实际消费。
5. runtime 输出必须标注 `seed_only / cold_start_baseline / company_calibration / project_overlay / manual_override` 等来源，不能把候选或报告说成 live 改善。

### 0.3b 非纯工期资产参与工期精度的分层边界

除 base 工期外，专项工序 seed、WBS、依赖、关键路径、模板选择、范围推断、进度快照、baseline、monthly plan 都会影响工期，但它们不能用同一种“自动调整”口径：

| 资产类型 | 是否可自动调准 | 正确口径 |
| --- | --- | --- |
| base 工期、blend 权重、P50/P75 融合、剩余工期 residual overlay | 可以，在满足样本、门禁、作用域和回滚后 | “受控 runtime 校准已能改预测数字” |
| 天气、季节、现场承载、资源压力、生产率上下文因子 | 条件可以，必须证明同场景误差下降 | “作为上下文校准参数进入 canary / published 后才生效” |
| 标准工序识别、专项工序 seed、WBS 模板、依赖规则、关键路径规则、模板选择、范围生成 | 可以学习候选，但默认不能静默改事实或结构 | “进入 network prediction event、actual network outcome 和候选发布链” |
| actual start/end、完成状态、进度快照、baseline、monthly plan、计划提交、用户确认依赖 | 不可自动改写 | “事实层 / 承诺层，只能作为样本、验收、误差分解和回滚依据” |

本轮结论：v1.4.22.4 的目标不是让所有资产无条件自改，而是建立 `system seed -> global / industry baseline -> company calibration -> project overlay -> manual override / fact lock` 的分层精度模型。只有已经进入 runtime 消费的层级，才能纳入“越用越准”的对外说法；其余只能说“有候选、可回放、可验收”。

### 0.3c 推荐包准确率矩阵与商业可用边界

`wbsTemplateRecommendationAccuracyMatrixService.ts` 是本文件的 WBS 推荐包精度账本。它消费 `wbsTemplateGoldenBenchmarkGateService` 的 13 个真实项目 replay / runtime benchmark 结果，并按推荐包、业务类型、`building_pattern`、规模带和工法变体输出商业可用状态。

矩阵输出分两层：

| 层级 | 状态 | 作用 |
| --- | --- | --- |
| 总体矩阵 | `commercial_ready / needs_calibration_evidence / blocked` | 判断推荐包体系是否具备商业可用声明条件 |
| 单个推荐包 | `commercial_ready / candidate_only / blocked` | 判断住宅、装配式、医院、IDC、工业洁净、大跨度钢结构、改造、文保、校园、TOD、MiC、酒店、深基坑等推荐包是否可进入商业推荐 |

校准队列固定包括：

- `missingRuntimeEvidenceRecommendationPacks`：缺 runtime / replay 证据的推荐包，只能保持 `candidate_only`。
- `failedRecommendationPacks`：已 replay 但未过阈值的推荐包，必须进入校准 backlog。

阈值沿用 golden benchmark gate：`expectedScenarioCount=13`、`maximumDurationDeviationRatio=0.15`、`minimumDependencyPassRate=0.95`，并叠加模板覆盖、深度覆盖和 runtime 证据可读性。矩阵只证明推荐包准确率与校准优先级，不直接调参、不写 seed、不改计划日期、不改依赖，也不发布 runtime。任何由矩阵发现的参数或模板调整，都必须回到 v1.4.22.3 的登记、release-exit、专项 writer、消费者验证、影响面监控和 rollback target 后才能生效。

## 1. 当前工期精度问题的事实判断

### 1.1 窄义正确：base 工期有有限收敛

当前 `durationSuggestionService.ts` 中的 `benchmarkBlendWeight(sampleCount)` 已经让 base P50/P75 随公司内同工序完工样本有限收敛：

| 样本数 | 观测中位数权重 |
| --- | ---: |
| `< 5` | `0` |
| `>= 5` | `0.3` |
| `>= 10` | `0.5` |
| `>= 20` | `0.7` |

这条是 live 路径，机制方向正确。但它只覆盖 base duration，不等于整个预测模型自学习。

### 1.2 需要补的四个洞

| 问题 | 当前状态 | v1.4.22.4 改正方向 |
| --- | --- | --- |
| 结构参数冻结 | `taskDurationForecastService.ts` 里 L0/L1/L2 候选权重、进度曲线乘数、置信度扣分等仍主要是模型 profile 或默认常量 | 参数必须进入预测事件和误差回放；只有通过参数注册、replay、canary 和 rollback 后才能被 runtime 消费 |
| MAE 不回流 live | `projectProductivityCalibrationService.ts` 计算 `maeBefore / maeAfter`，但更多用于策略、候选、门禁或报告 | 复用并扩展既有预测事件账本和 residual overlay 消费链，把误差修正接入 `taskDurationForecastService` 与 `projectRemainingDurationForecastService` 的受控 runtime 层 |
| 公司隔离导致长尾冻结 | 公司 x 工序桶样本不足时仍长期依赖 seed；匿名行业基线已有服务但未作为 duration suggestion 冷启动 live 参考层 | 把 `algorithmAssetColdStartBaselineService` 接入 duration suggestion 冷启动路径，作为只读参考层，不写公司 override |
| 样本缺事实就消失或降级 | `actual_duration`、开始/完成时间不完整时样本难以进入强样本 | 用 sample health 明确 accepted / weak / rejected；弱样本只进候选证据，不污染 benchmark；业务完成动作必须尽量补齐实际结束、实际开始和实际工期 |

## 2. 工期与计划网络精度闭环目标

### 2.1 必须统一度量的对象

| 对象 | 代表服务 | 精度目标 |
| --- | --- | --- |
| 新任务参考工期 | `durationSuggestionService.ts` | 预测 P50/P75 与后续实际工期误差下降 |
| 单任务剩余工期 | `taskDurationForecastService.ts` | 当前进度下的剩余天数 MAE、bias、过度补偿率下降 |
| 项目整体剩余工期 | `projectRemainingDurationForecastService.ts` | 项目预测完工日、剩余工期、关键任务集合解释更稳定 |
| 上下文因子 | `durationContextService.ts` 及 policy learning 服务 | 天气、季节、现场承载、生产率因子只在有实证改善时生效 |
| 人工修正 | `manualDurationCorrectionService.ts` | 人工纠偏沉淀为误差样本，而不是一次性覆盖数字 |
| 计划网络结构 | `projectCriticalPathService.ts`、`constructionDependencyRuleSystemService.ts`、`wbsTemplateGenerationService.ts` | WBS、依赖、关键路径和父子汇总能用实际执行结果回放验证 |

### 2.1a 五引擎工程合理性护栏

2026-06-19 补充收口：五引擎精度治理除 MAE / Bias 外，必须有一层共享工程合理性护栏，防止脏 seed、错误计划窗口、倒置概率带或无依赖冷启动网络把预测结果推到离谱区间。

| 引擎 | 护栏口径 | 当前代码锚点 |
| --- | --- | --- |
| E1 参考工期 | `durationSuggestionService.ts` 在最终输出前调用共享护栏；养护 7 天属于正常参考下限，只做 warning，不硬改早强混凝土、项目批准方案或 seed 已确认的 sub-7 天输入；标准层节拍 4-7 天/层也只做 warning，不生成第二套工期真值 | `durationEngineeringPlausibilityGuardrailService.evaluateDurationPlausibility(...)` |
| E2 单任务剩余 | `taskDurationForecastService.ts` 对 P20/P50/P80 排序并输出 `durationPlausibilityWarnings`；主剩余、乐观、保守三条路径同时受“不得明显超过计划/参考基准 10 倍”的相对 cap 保护；`forecastPaths.optimistic` 在输出前必须满足 optimistic <= recommended，避免 S-curve 中段出现 P20 / optimistic 大于 P50 / recommended | `orderDurationBand(...)`、`capDurationRelativeToBaseline(...)`、`duration.forecast_paths.optimistic_order` |
| E3 关键路径 CPM | `projectCriticalPathService.ts` 对单任务 duration 做上限保护；未连依赖冷启动网络输出 `networkMaturity=low`，提示“最长单任务不是权威 CPM”；负 float / 负 lag 不再静默吞掉，只写诊断 | `networkMaturity`、`durationPlausibilityWarnings` |
| E4 项目剩余 | `projectRemainingDurationForecastService.ts` 对项目级 P20/P50/P80 finish band 排序，对项目剩余天数设 730 天稳定性 cap，并把修正原因写进 `calculationContext.durationPlausibilityWarnings` | `orderCriticalBandFinishDates(...)`、共享 cap |
| E5 赶工压缩 | `scheduleAccelerationService.ts` 继续使用 E5 原有压缩上限、养护/验收排除、crash floor 等强护栏；目标赶工 proposal 不再用硬编码 50/50 覆盖 seed / runtime 预算拆分，且 `criticalCandidateDays` 已进入 fast-track 预算约束，非关键长尾任务不得放大关键路径可恢复天数 | `fastTrackBudgetDays` / `fastTrackBudgetRatio` / `criticalCandidateDays` |

边界：该护栏只负责“挡离谱值、显式告警、稳定输出”。它不是新的 seed 来源，不自动改写 `standard_work_duration`、任务事实、baseline、monthly plan、依赖或关键路径事实；真正参数收敛仍要走 prediction event、actual outcome、样本健康、release-exit、impact monitoring 和 rollback。E3 的 P80 / 标准差不覆盖 `projectDurationDays` 这个 CPM 点值真值，只进入高方差近关键链、置信解释和下游风险判断，避免在同一关键路径语义下制造第二个主工期。

### 2.2 必须上线的精度指标

| 指标 | 用途 |
| --- | --- |
| `MAE` | 平均绝对误差，主验收指标 |
| `MdAE` | 中位绝对误差，避免少数极端项目掩盖体验 |
| `Bias` | 系统性高估或低估，决定 residual overlay 方向 |
| `MAPE` | 只在实际工期足够大时使用，避免短任务除数过小 |
| `OvercompensationRate` | 修正后比修正前更差的比例 |
| `Coverage` | 有预测事件且能对上实际结果的样本覆盖率 |
| `AcceptedSampleRate` | accepted 样本占比，避免弱事实被误当精度提升 |
| `ColdStartHitRate` | 样本不足时是否命中行业 / 分层基线 |

## 3. 工期精度系统设计

### 3.1 预测事件账本

复用或扩展既有 `duration_prediction_events` 类事实层，所有会输出工期数字的 runtime 服务必须写入预测事件：

| 字段族 | 必填内容 |
| --- | --- |
| 作用域 | `company_id`、`project_id`、`task_id`、`standard_work_code`、`template_node_id`、`business_type` |
| 预测来源 | `source_service`、`model_profile_id`、`model_profile_version`、`learning_target` |
| 输入快照 | base P50/P75、工程量、项目画像、进度、日历、上下文因子、冷启动层级、standard work seed 版本、standardWorkCode 命中依据、WBS / dependency / critical path 版本 |
| 输出快照 | predicted duration、predicted remaining、predicted finish、confidence、basis |
| 发布状态 | `seed_only / company_blend / cold_start_baseline / residual_overlay_canary / residual_overlay_published / manual_override` |
| 追踪键 | prediction id、input hash、model hash、rollback target |

要求：

1. `durationSuggestionService.ts` 生成新任务参考工期时写 prediction event。
2. `taskDurationForecastService.ts` 生成任务剩余工期时写 prediction event。
3. `projectRemainingDurationForecastService.ts` 汇总项目剩余工期时写 prediction event，并保留参与汇总的任务预测事件 id。
4. 所有 prediction event 必须记录 seed lineage 和 network lineage：使用了哪个 `standard_work_duration` seed 版本、哪个 standardWorkCode 命中链路、哪个 WBS 模板版本、哪个依赖规则版本、哪个 critical path 输入 hash。
5. 预测事件不得依赖前端展示触发；后台任务、API、计划生成、赶工评估都必须可追踪。

### 3.2 实际结果归因与样本健康

完工后由 `durationExperienceService.ts` 与 `algorithmAssetSampleHealthService.ts` 生成样本健康报告，并与 prediction event 对账。

| 样本等级 | 可用于什么 | 禁止什么 |
| --- | --- | --- |
| `accepted` | benchmark、MAE、residual overlay、参数 replay、canary 验收 | 无 |
| `weak` | 候选证据、样本缺口提示、冷启动参考观察 | 不得直接进入 base benchmark 或 live 参数发布 |
| `rejected` | 数据质量报告、录入补全任务 | 不得参与精度改善计算 |

弱样本抢救规则：

1. 有完成操作时间但没有 `actual_finish_at` 时，可作为 weak end。
2. 有 first progress 但没有实际开始时间时，可作为 weak start。
3. 有 planned duration 与完成状态但缺 actual duration 时，只能生成补录提示，不能伪造 accepted。
4. 从 weak 晋升 accepted 必须保留修订痕迹和原始弱样本原因。

### 3.3 base 工期 live blend 调参

当前 `benchmarkBlendWeight` 是硬编码阶梯。v1.4.22.4 要把它变成参数化、可回放、可灰度的公司级 live tuning。

| 参数 | 当前问题 | 改正 |
| --- | --- | --- |
| 样本阈值 | 5 / 10 / 20 固定 | 进入 `algorithm_learnable_parameter_registry` 的实例值，按公司 / 工序族回放 |
| blend 权重 | 0.3 / 0.5 / 0.7 固定 | 只能在最大变化幅度内灰度，且必须证明 MAE 和 Bias 改善 |
| P50/P75 融合 | 口径存在但不等于全面自学习 | 对不同工序族可生成候选比例，但未通过门禁前不影响 live |
| 长尾桶 | 样本不足仍 seed-only | 接入冷启动基线作为只读参考，不写公司 override |

验收：

1. 每个参数候选必须有 before / after replay。
2. `accepted` 样本数不足时只能生成 candidate，不得进入 live。
3. 任何参数发布必须有 rollback target。
4. 回滚后 prediction event 能解释“本次预测使用了旧参数”。

### 3.4 residual overlay 接入 runtime

v1.4.22.3 已有 `duration_forecast_residual_overlays` 和 `algorithmAssetForecastResidualOverlayService.ts`，但默认更多是候选或 shadow。v1.4.22.4 要补上 runtime 消费链。

接入位置：

| 服务 | 消费方式 |
| --- | --- |
| `taskDurationForecastService.ts` | 在 base candidate 汇总后读取 published / canary residual overlay，修正剩余天数和置信度 |
| `projectRemainingDurationForecastService.ts` | 汇总任务预测时保留 overlay 前后两个结果，用项目级 MAE 与过度补偿率验收 |
| `durationAlgorithmAccuracyService.ts` | 输出 overlay 前后对比，不只输出治理报告 |
| `durationOutputGovernanceService.ts` | 在业务输出上标注 seed / company blend / residual overlay / manual correction 来源 |

门禁：

1. `shadow_report_only` overlay 不得被 runtime 消费。
2. canary overlay 只对允许的项目 / 公司 / 工序族生效。
3. 任一窗口 `OvercompensationRate` 超阈值立即停止。
4. 如果 Bias 改善但 MAE 变差，不允许发布。
5. overlay 不能写回 `standard_work_duration` seed。

### 3.5 冷启动共享基线接入

当前已有 `algorithmAssetColdStartBaselineService.ts`，但 duration suggestion live 路径没有稳定消费它。v1.4.22.4 要把它放在 seed 与 company override 之间：

```text
system seed -> anonymous industry / segment baseline -> company benchmark blend -> project / manual overlay
```

规则：

1. 行业 / 分层基线只读，不生成公司私有 override。
2. 基线必须满足最小公司数、最小项目数、单公司占比上限、去标识化策略。
3. 未满足共享池门槛时，明确返回 `cold_start_baseline_unavailable`，继续使用 system seed。
4. 新公司冷启动时，业务解释只能说“行业参考”，不能说“本公司经验”。
5. 当公司 accepted 样本足够后，公司基准优先于行业基线。

### 3.6 上下文因子精度闭环

天气、季节、现场承载、资源压力、生产率等因子不能继续停留在“专家乘数像真的一样”。

| 因子族 | 代表资产 | 改正 |
| --- | --- | --- |
| 天气 / 季节 | `weatherForecastImpactService.ts`、`v1474SeasonalProductivitySeed.ts`、`v1474ProcessSeasonalSensitivitySeed.ts` | 只在同地区 / 同工序族 replay 证明改善时进入 canary |
| 日历 | `workCalendarForecastBuilder.ts`、`officialHolidayCalendarService.ts`、`v1474WorkCalendarSeed.ts` | 节假日和工作日是事实层，不能被学习改写；只能学习对工期影响的 overlay |
| 现场承载 | `durationContextService.ts`、`v1474SiteCapacityPressureSeed.ts` | cold start observation-only，样本不足时只能降置信度或提示风险 |
| 生产率 | `projectProductivityCalibrationService.ts`、`projectProductivityCompensationService.ts` | MAE 改善必须回到 prediction event / residual overlay，不能只停在策略报告 |
| 进度速度 | `progressVelocityLearningService.ts` | 只能影响剩余工期预测，不得改写实际进度事实 |

### 3.7 完成动作的数据捕获

为了让精度闭环有样本，完成任务时必须把最小事实采集做实：

1. 状态改为完成时，如果没有完成日期，默认带出当前操作时间并标记为 weak end，需要用户确认或后续补正。
2. 如果没有实际开始时间但存在首次进度记录，作为 weak start。
3. 如果用户填写实际工期，与开始 / 完成日期不一致，进入冲突提示而不是静默采用任一值。
4. Gantt、月度计划、任务详情、移动端完成动作必须走同一后端完成事实入口。
5. 数据缺口必须进入样本健康 dashboard，而不是静默丢弃。

### 3.8 计划网络精度层

B 类资产正式纳入 v1.4.22.4 第二阶段。原因是：单任务工期 P50 再准，如果 WBS 拆错、依赖错、关键路径错、父子汇总错，项目剩余工期仍然会错。

计划网络精度层不直接改写已确认业务事实，只对“生成 / 推荐 / 预测 / 解释”链路建立误差闭环：

| 精度对象 | 代表资产 | 必须补的闭环 |
| --- | --- | --- |
| WBS 结构生成 | `wbsTemplateGenerationService.ts`、`wbsTaskStructureGovernancePipelineService.ts` | 生成结构与实际保留 / 删除 / 补录 / 拆分结果对账 |
| WBS 参考天数 | `wbsReferenceDaysInference.ts`、`wbsTemplateFeedback.ts` | 参考天数与实际任务跨度对账，区分 report-only feedback 与 live reference days |
| 父子工期汇总 | `wbsPlanRollupService.ts` | 子任务合计、父级计划窗口和 project remaining forecast 口径一致 |
| 依赖规则 | `constructionDependencyRuleSystemService.ts`、`v1475DependencyIntentTemplates.ts`、`standardInternalFlowSeed.ts` | 推荐依赖与用户保留 / 删除 / 调整、实际前后置兑现情况对账 |
| 依赖 replay | `constructionDependencyReplayCalibrationService.ts`、`constructionDependencyReplayCalibrationJob.ts` | replay 只能生成候选和证据；通过发布门禁前不写 live 依赖规则 |
| 关键路径 | `projectCriticalPathService.ts`、`criticalPathHelpers.ts` | 关键路径预测集与实际延期贡献、完工阻塞、剩余工期误差对账 |

计划网络层的硬边界：

1. 不因学习结果自动改写已确认的 `task_dependencies`、baseline、monthly plan 或用户锁定的关键路径。
2. replay 可以生成 dependency / WBS / critical path 候选，但不得绕过 v1.4.22.3 release-exit。
3. WBS 参考天数和任务工期预测必须共享 prediction event / actual outcome，不允许两套准确率口径。
4. 关键路径精度不能只看“算法能算出 critical path”，必须看它是否更早、更准地解释实际延期贡献。

### 5.2 “全部工期资产 live 自学习”口径升级边界

本文件收口后，如果后续要把对外表述升级为“越用越准”的强版本，只能使用以下受限口径：

> 所有可学习的工期预测与计划网络资产，都已进入 live 自学习 / 自升级闭环；事实与承诺层保持锁定，只作为样本、验收和回放依据。

本句只是生产证据全部齐备后允许释放的窄口径，不是本文件收口后的默认当前状态。执行时必须继续由 `v1.4.22.6` 和 `buildDurationLiveLearningProductionClaimAuditFromDb(...)` 证明 canonical source rows、runtime consumer observation、runtime-call、真实业务路径、publication、impact monitoring、rollback、accuracy、scope provenance 与 fact-lock 全部满足；若涉及外部 / 内部资料校准结果，还必须先经过 `v1.4.22.5` 的候选资产、校准回放和自动发布 readiness。未重新验证时只能写 `historical_evidence_needs_refresh / not_ready`。

禁止使用的口径仍然是：

> 所有工期相关资产都已经 live 自学习、自我升级。

原因：baseline、monthly plan、actual start/end、完成状态、进度快照、已确认依赖、用户确认关键路径等属于事实或承诺层，不能被学习系统自动改写。它们最多作为 actual outcome、sample health、basis lineage、fulfillment evidence 和 replay acceptance 输入。

代码锚点：`durationLiveLearningClosureService.ts` 是该升级口径的代码级判定口。它强制登记每个工期相关资产的 `assetClass / canLearn / factLocked / selfLearningPublishAllowed / runtimeWriterRequired / publishGateRequired / requiredLearningScopes`，并用五项闭环条件判定是否允许 live 自学习声明：

1. 资产分级已登记；
2. prediction event 与 actual outcome event 均存在；
3. 已登记 global / industry / company / project 分层学习策略；
4. runtime consumer 确实消费 published / canary artifact；
5. release-exit、impact monitoring、rollback target 和 accuracy metrics 齐备。

验收口径：

| 判定对象 | 允许声明 | 禁止声明 |
| --- | --- | --- |
| 单个可学习资产五项齐备 | `learnable_duration_asset_only` 范围内已 live 自学习 | 不得外推到事实层 |
| 所有可学习资产齐备且事实资产保持锁定 | `all_learnable_duration_prediction_and_network_assets_are_live_self_learning;facts_and_commitments_remain_locked` | `all_duration_assets_are_live_self_learning` |
| 任一可学习资产缺 prediction/outcome、分层学习、runtime consumer、release/monitor/rollback/accuracy | 只能说 not ready 或 evidence/candidate | 不得说 live 自学习 |
| 事实/承诺资产 | fact locked closed | 不得作为 self-learning runtime writer |

该升级口径的实施专项进入 `v1.4.22.6可学习工期资产live自升级闭环专项方案.md`。v1.4.22.4 的职责到“精度闭环边界与验收矩阵收口”为止；v1.4.22.5 负责外部 / 内部进度知识源候选资产与自动发布 readiness，v1.4.22.6 才负责逐项证明可学习资产是否真的达到 live 自学习。

## 7. 范围决议

| 资产族 | 决议 | 原因 |
| --- | --- | --- |
| A 类工期资产 | 纳入 v1.4.22.4 第一阶段 | 这是“越用越准”的直接目标；标准工序工期 seed、seed replay、standardWorkCode 命中链路、专项工序影响 reference days 的 lineage 都在此层 |
| B 类关键路径 / 依赖 / WBS | 纳入 v1.4.22.4 第二阶段 | 它们决定计划网络和项目剩余工期，是工期精度的另一半；专项工序 / 领域模板 seed、依赖关系规则、依赖 replay、依赖模板 seed 都在此层 |
| C 类 baseline / 月度计划 / 计划状态 | 只纳入事实层和验收口径 | 这些是业务承诺或事实参照，不能被学习系统自动改写 |
| D 类风险 / 预警 / 健康 | 登记为下游消费者，暂不实施 | 先避免把精度方案膨胀成风险健康重构 |
| E 类外部条件资产 | 天气 / 日历 / 材料反馈作为事实信号接入，其余登记或另开专项 | 外部条件会影响工期，但证照 / 图纸 / 验收更适合独立周期精度专项 |

最终范围：v1.4.22.4 = A 类工期精度闭环 + B 类计划网络精度层 + C 类事实验收层。D 类和大部分 E 类只登记，不进入本轮实施。

其中，标准工序 seed 和专项工序 seed 都不是“只归 v1.4.22.3 管”的治理资产。标准工序 seed 在 v1.4.22.4 中必须进入 A 类工期精度闭环；专项工序 seed 在 v1.4.22.4 中必须进入 B 类计划网络精度层，并在影响 reference days / standardWorkCode 命中时写入 A 类 lineage。依赖关系也不是外围资产，它在 v1.4.22.4 中必须进入计划网络精度层。区别只是：v1.4.22.3 决定它们能不能安全发布，v1.4.22.4 证明它们发布后是否真的让预测更准。

同时，工序身份 / 任务编码链、任务写入链、进度快照、数据质量、数据 lineage、计划快照 seed 版本、工程对象和 WBS 候选事件都必须纳入候选池。它们不一定都是“可学习参数”，但会决定预测事件是否指向正确 seed、actual outcome 是否可信、回放是否能复现当时的计划网络。漏掉这些资产，会让 v1.4.22.4 只修数字出口、不修精度证据链。

## 10. 2026-06-17 基线、月计划与统一回放校准补充

本轮补充把项目基线生成、月度计划生成与历史回放校准收口到同一套精度边界内。目标不是让事实层自学习改写，而是先保证生成口径、候选校准和生产证据链一致。

### 10.1 项目基线生成算法结构补丁

1. 依赖图重算顺序固定为：先完成 B2 锚定，再消费 E3 fresh CPM snapshot 按 FS / SS / FF / lag 进行网络顺重排；生成器不内置前向 / 后向 CPM 计算。运行期优先使用 E3 `networkSchedule` 的 CPM offset 在 B2 锚点上换算日期；只有 offset 缺失时才回退到网络顺串排。
2. 全量工作日历化修回归：生成层和项目层日期换算必须走既有施工日历解析链，复用 `resolveConstructionCalendarContext`，不再让运行期 calendar 恒为 null 后退到自然日。
3. 确认前基线专属校验闸门拦截里程碑倒序、资源峰值超限、总工期压缩超上限、互斥工序冲突；资源峰值复用 E3 RCPSP 空间日限，并按 `resource_class + global/building/unit/floor/zone/system + 日期` 展开部分重叠窗口，避免跨日窗口只因起止日期不完全相同而漏拦；互斥工序复用 `v1474ProcessConstraintSeed`，不另写冲突规则。
4. baseline item metadata 在 B2 `dateSource` 基础上补齐 `applied_factors / source_priority / confidence / override_level`，用于解释来源优先级和人工覆盖层级。

### 10.2 月度计划生成算法结构补丁

1. `capacityBudgetDays` 改为工作日预算：先用 `resolveConstructionCalendarContext` 扣除施工日历中的春节 / 项目停工 / 明确 shutdown 窗口，再按工作日 × 国标默认班组/专业产能 × 天气 / 节假日 / 停工日历因子形成预算；输出显式标注这是“默认产能上限”，不宣称真实班组产能，并写入 `monthly_capacity_calendar_basis / source / shutdown_deducted_days`。
2. 容量竞争按 `resourceClass + specialty / building / floor / zone / workface` 多池计算，复用已接入 RCPSP 的空间 scope key，不新增维度体系。基线生成侧在 `resource_class + scope_keys` 上生产 `rcpsp_capacity_pool_key / rcpsp_capacity_pool_key_source / rcpsp_capacity_pool_key_policy`，并同步挂入 item `algorithm_context`；月计划运行期优先消费该 E3 / RCPSP canonical key，并在月计划 item metadata 写入 `monthly_capacity_pool_key_source / monthly_capacity_pool_key_policy`；仅当 canonical key 缺失时，才从既有 `generation_metadata.scope_keys` / `scope_snapshot.dimensions` fallback 重建池 key。
3. 月窗任务的纳入门改为“planned overlap + 已开工未完工孤儿救回 + E2 预测完工落月补纳入”三路并行：planned_start/planned_end 与目标月重叠的任务照常纳入；已开工未完工且 progress < 100 的跨月任务继续由 orphan 分支救回；未开工但 `forecastFinishDate` 已落在目标月的任务必须在候选形成阶段补纳入，不能等到 target/capacity 消费环节才看 E2，否则会出现“大偏差但计划未更新”的整批漏项。
4. `target_progress` 固定为 `min(计划线性目标, E2可完成目标, 容量可分配目标)`，三者均写入 metadata，堵住“轻载月仍线性”的旧口径。
5. 连续结转、上月完成率、责任方响应和阻碍解除状态进入结转老化惩罚；长期结转且原因未解除的项降为管理关注 / 条件承诺。

### 10.3 统一回放校准闭环

复用并补强已存在的 `planningReplayCalibrationService.ts` 与 `planningReplayCalibrationJob.ts`，作为基线和月计划共享的回放校准编排层与生产 sweep 入口：

1. 同一台回放机器同时接收 `baseline_generation` 与 `monthly_plan_generation` 样本，比较“当时算法会生成什么”与“实际发生什么”。

## 11. 2026-06-17 工期策略自动发布门禁补充

本补充解决一个明确不一致：验收 / 证照策略已经采用“门禁通过零人工复核、门禁不通过才人工”的自动发布模式，工期策略学习不能继续停留在每个 canary 都必须人工 approve 的状态。但工期策略不能照搬模板发布的宽松口径，因为工期参数会影响计划基线、预测和全项目排程信任，必须加更严的精度门禁。

### 11.1 自动与人工的分界

`durationContextPolicyLearningJob.ts` 已在每日 06:20 自动运行学习 sweep，并在 `generateDurationContextPolicyCanaryCandidates(...)` 后调用 `autoPublishDurationContextPolicyCandidates(...)`。该自动门禁的 `humanReviewPolicy` 固定为 `zero_human_review_when_gate_passes`：

1. 门禁通过：自动写入 `duration_context_policy_canary_candidates`，并在 `duration_context_policy_versions` 登记 `activation_mode='auto_publish_gate_canary'` 的 canary version。
2. 门禁未通过但不是硬风险：保留 `hold_as_candidate_for_manual_review`，进入人工审批口。
3. MAE 回退、过度补偿、非低风险状态或硬 guardrail 命中：`block_and_retain_previous`。

这不是“自动改生产数字”。job 的运行期边界是 `none_runtime_or_fact_mutation_canary_registry_only`：允许自动写候选 / canary version registry，不允许改 seed、task、actual、baseline、monthly plan、依赖、关键路径事实或任何业务承诺层。

### 11.2 工期专属硬门禁

自动 canary 必须同时满足以下条件：

| 门禁 | 最低要求 | 失败动作 |
| --- | --- | --- |
| 四层 scope 覆盖 | `global / industry / company / project` 全部出现，`system` 归一到 `global`，`industry_baseline / segment_baseline` 归一到 `industry` | 缺失或未知 scope 进入 manual review |
| scope 样本量 | global >= 50、industry >= 30、company >= 10、project >= 5 | 样本不足进入 manual review，不得用项目样本上推公司或全局 |
| 总样本量 | sampleCount >= 50 | manual review |
| replay 厚度 | replayCaseCount >= 20 | manual review |
| 精度非回退 | `maeAfter <= maeBefore` | block and retain previous |
| 过度补偿 | overcompensationRate <= 0.08 | block and retain previous |
| 风险状态 | 仅低风险 state bucket | block and retain previous |
| guardrail | 无 hard / high-risk / manual runtime promotion guardrail | block and retain previous |

replay 到 canary 的证据桥由 `durationContextLearnedPolicyReplayService.ts` 与 `durationContextPolicyCanaryGateService.ts` 负责：前者把 `project_productivity_compensation_calibrations` 的 MAE、overcompensation、scope sample 和 evidence refs 带入 replay case；后者按 calibration ref 去重后汇总到 canary candidate，避免同一份 calibration 被多个 decision 重复计样本。

### 11.3 批量审批、风险分级与观察窗回滚

人工闸不再解释为“逐条盯、逐条点”。治理工作台必须支持每周 / 每批把同一门禁周期内满足人工审批条件的 canary candidate 打包成一次审批动作。后台入口为 `durationContextPolicyCanaryApprovalService.ts` 的 `approveDurationContextPolicyCanaryCandidateBatch(...)` 与 `duration-context-governance` 路由的 `/canary-candidates/batch-approve`；每批必须记录 `batchId / approvedBy / reason / item decisions / failures / humanReviewMode='weekly_batch_single_click'`。批量审批仍逐条复用单条审批的低风险、guardrail、候选状态和唯一 active version 保护，失败项只进入 failures，不得让整批静默通过。

发布策略按“影响半径”分层，而不是追求所有资产全自动：

| 资产 / 参数类型 | 风险层级 | 生效策略 | 观察与回滚 |
| --- | --- | --- | --- |
| `forecast_residual_overlay`、`forecast_confidence_weight` 等只在 company / project scope 内生效、可回滚、不改 seed / 事实 / 承诺层的预测残差或置信度类资产 | low | 门禁通过后允许 `auto_canary_with_observation_window`，不需要逐条人工点头 | 默认 7 天观察窗；MAE、Bias、overcompensation、coverage 任一退化触发自动 rollback 或回退到上一版本 |
| company/project 范围内的中等影响参数、冷启动 shrinkage、局部 blend 权重 | medium | 默认进入批量人工审批；只有后续被证明影响半径小、回滚稳定、生产监控齐备，才允许提升为低风险自动 canary | 默认 14 天观察窗；自动监控，人工确认或自动建议 rollback |
| `base_duration_benchmark`、`standard_work_duration_seed`、`special_work_duration_seed`、`wbs_reference_days`、`dependency_rule_candidate`、`critical_path_rule_candidate`、影响计划网络 / 关键路径 / baseline 信任的结构性规则 | high | 保持批量人工审批，不允许零人工自动进入 runtime writer | 默认 14 天以上观察窗；必须有 release-exit、rollback target、impact monitoring、accuracy evidence 和可追溯审批记录 |

`durationContextPolicyAutoPublishGateService.ts` 的 `classifyDurationLearningAssetReleasePolicy(...)` 是该分层的代码口径：低风险预测类资产返回 `auto_canary_with_observation_window`，高影响计划网络 / seed / benchmark / 关键路径类资产返回 `batch_manual_approval_required`。自动 canary 写入 `duration_context_policy_versions.canary_scope` 时必须带上 `assetRiskTier / releaseGovernanceMode / observationWindowDays / rollbackPolicy`，让后续 `algorithmAssetLearnableParameterImpactMonitoringJob.ts`、`algorithmAssetForecastResidualOverlayService.ts` 或同类监控任务能按观察窗执行精度退化检查和自动回滚。

因此，本节的目标不是“无人车式全自动发布”，而是把人工成本压缩到低频、批量、可审计：低风险小半径资产自动 canary 并带安全网；高风险、强约束、影响计划网络 / 关键路径 / 工期承诺的资产保留人工闸，但通过批量审批和证据包把人工动作从持续盯盘降到周期性确认。

### 11.4 与 v1.4.22.3 的边界

本补充只补齐精度学习侧的自动门禁，不替代 v1.4.22.3 的治理发布边界。v1.4.22.3 仍负责 release-exit、rollback、冲突清理、事实锁定和 publish anchor；v1.4.22.4 只证明“这批低风险策略候选有足够样本、回放和 MAE 非回退证据，可以自动进入 canary registry”。若候选来自外部 / 内部进度知识源，先由 v1.4.22.5 生成校准结果与自动发布 readiness；最终是否能对外宣称某类工期资产已经 live 自学习，仍由 v1.4.22.6 的生产证据门禁判定。

## 2026-06-20 向导深算浅出与工期精度边界补充

`generation_depth_policy` 接入后，向导计划表的可见行与工期计算层可能不同：首屏行按 `materializeDepth` 生成，工期按 `durationComputeDepth` 继续向下计算，再通过隐藏子孙工序 rollup 回写到可见 frontier 行。这一机制属于计划生成结构修复，不是新的工期引擎。

2026-06-20 可信门槛补充：向导 / 模板生成结果新增 `scheduleTrustGate`，用于判断“深算浅出”的证据是否足以支撑生产排程。它不计算新工期，只校验生成深度规则是否显式命中、低置信 fallback 是否存在、需要下钻深算的可见行是否已有 `contextual_descendant_rollup`、以及 duration-bearing 行是否有可写入的参考工期。`status=trusted` 才可直接进入排程；`review_required / blocked` 只能作为待复核生成结果。

精度口径：

1. 可见 frontier 行的 `smart_reference_days` 仍是数字型计划事实，来源必须可追溯到 E1 / 模板 seed / 下层 process rollup。

3. 下层工序未物化不等于不参与计算；只要 `durationComputeDepth` 深于 `materializeDepth`，工期精度验证必须把隐藏子孙 rollup 纳入证据。
4. 生成排序按施工时间线输出，不按模板目录顺序证明工期可信。
5. 该机制不写实际进度、不改预测闭环、不调整 MAE / bias，不可作为 E1/E2/E3/E4/E5 精度提升的独立证据；它只修复“同一计划表内可见行工期与隐藏工序真值脱节”的结构问题。

## 2026-06-21 施工组织三场景与 E5 精度边界补充

施工组织服务层与向导事实的闭合口径现在按三种 use-case 输出，而不是把同一套事实压成一个模糊通用方案。`constructionOrganizationScenarioSelector.ts` 在消费向导 / `projectGenerationFacts` 已有事实后，必须同时产出 `scenarioRecommendations.newProjectPlanning`、`scenarioRecommendations.startingLineOnboarding`、`scenarioRecommendations.accelerationRecovery`，并把三者与 `recommendedPlanOption / planOptions / generatedRowProjection` 一起暴露给 E5 和治理候选事件。

精度闭环边界如下：

1. `newProjectPlanning` 只服务新建项目和向导主计划解释，表示当前静态事实下系统建议采用的施工组织组合方案；它不反写 E1 seed、计划日期、真实依赖或 E3 关键路径。
2. `startingLineOnboarding` 只服务起跑线接入解释。若 `onboardingSubstage` 已进入主体、机电、装饰、移交等后续阶段，基础 / 地下室方案必须降级为 `not_actionable_after_current_phase`，只做证据留痕，不允许倒改现场已经发生的组织事实。
3. `accelerationRecovery` 是 E5 的消费视图。`scheduleAccelerationService.ts` 可以优先读取该视图的 `recoveryFactorHint`，但只能作为赶工恢复预算的有界温和修正和解释，不得绕过 E5 的压缩上限、hold-point 保护、E3 关键路径预算和候选治理边界。
4. 三个视图共用同一套事实源、同一组 `planOptions`、同一个虚拟网络评估和生成行投影；不得新增普通前端输入，也不得把塔吊、施工电梯等资源数量升级为主排程驱动。

因此，本补充不构成第六个工期引擎，也不构成完整 A/B/C 真实计划网络优选。它的验收点是：同一套向导事实进入施工组织服务后，在新建、起跑线、赶工三个入口下都有清晰的推荐 / 解释 / 消费边界；E5 只消费 `accelerationRecovery` 的候选证据和有界 factor；治理事件能追溯三场景推荐、事实依据、生成行投影和不写事实的 mutation boundary。
