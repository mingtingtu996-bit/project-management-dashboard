## 0. 2026-06-01 final range-tree boundary (authoritative)

This v1.4-series plan follows the final range-tree model. There is no production history or existing user data that needs a compatibility layer.

Authoritative engineering object types are exactly: `phase / section / building / basement / floor / physical_zone / functional_area`.

The following compatibility surfaces are deleted and must not be reintroduced in runtime code, migrations, or frontend contracts:

- `zone / professional / subproject / custom` as engineering object types.
- `zone_object_id / professional_object_id` task fields.
- `project_materials.professional_object_id` and `engineering_categories.professional_object_id`.
- `legacy_object_type`, deprecated object-type arrays, legacy bridge/backfill helpers, and old scope adapter functions.
- `/api/scope-dimensions`, `scope_dimensions`, and `project_scope_dimensions` as active application surfaces.

Professional/system/domain/method semantics remain business facts through `specialty_type`, `engineering_category_id`, `standard_work_code`, template metadata, and project profile facts. They are not range-tree objects.

Any older section in this document that mentions deleted object types, deleted fields, old scope tables, or compatibility adapters is superseded by this boundary.
# v1.4.13 提醒通知与待办触达体系执行方案

## Summary

v1.4.13 的目标是把当前应用中已经存在但口径分散的 `提醒 / 通知 / 今日待办 / Header 红点 / Dashboard 重点关注任务 / 页面健康横幅 / 浏览器弹窗` 收口成统一的触达体系。

在 v1.4 全系列已经建设完成后，本章不再预留“后续体系待定”口径，而是作为全系统触达总线，承接 `v1.4` 到 `v1.4.23` 已定义的所有业务事实、治理事实和权限边界。

本章不重做风险问题、计划治理、开工条件、图纸证照验收、材料、数据质量、指标健康度、权限协作等业务系统。它只回答一个问题：

```text
同一条业务事实变化，应该以什么方式、在什么位置、对谁、提醒到什么程度？
```

核心结论：

```text
业务模块维护事实
通知中心承接持久提醒
今日待办承接当天需要看一眼或处理的信号
Header 红点只做全局入口和数量提示
页面横幅只提示当前页面上下文问题
浏览器弹窗只做可关闭的轻提醒，不作为业务真值
```

本章继续沿用 v1.4.8 之后形成的统一原则：

```text
用户维护业务事实，系统判断治理语义
能由系统自动识别、匹配、归集和提示的，不新增弹窗或必填项打断现场录入
普通前端不展示 source、lineage、confidence、mapping_reason、chain_id 等治理字段
用户最多执行“前往处理 / 已知悉 / 暂时静音 / 关闭已处理提醒”
提醒中心不内嵌审批、验收、风险处理、任务编辑等业务操作，只负责导流
通知只触达用户需要知道或处理的事项，不把后端治理链、AI 兼容链、来源映射链暴露给普通用户
```

与前面章节的关系：

```text
v1.4.7 决定计划对象和执行事实怎么治理
v1.4.8 决定依赖、开工条件、阻碍如何形成准备度和执行影响
v1.4.9 决定里程碑和关键节点如何参与计划和提醒
v1.4.10 决定提醒送达责任人和责任单位的基础口径
v1.4.11 决定图纸、证照、验收事实如何影响任务
v1.4.12 决定预警、风险、问题如何升级和关闭
v1.4.14 决定确认、变更留痕和审批边界是否需要触达
v1.4.15 决定删除、关闭、归档、作废后的通知生命周期和历史保留
v1.4.16 决定哪些数据质量问题进入轻提示、健康横幅或系统异常通知
```

## Business Definitions

### 1. 提醒

提醒回答：

```text
这件事是否需要用户在某个时间窗口内注意？
```

提醒可以是轻量的，不一定要求处理。

```text
材料即将到场
月度计划即将关账
验收临近
图纸版本已更新
某条条件即将影响开工
```

### 2. 通知

通知回答：

```text
这条提醒是否需要被持久记录、可筛选、可知悉、可静音、可跳转？
```

通知中心是持久提醒的承接层，不是业务真值层。

```text
通知不等于风险
通知不等于问题
通知不等于任务
通知不等于审批
通知不负责修改业务状态
```

### 3. 今日待办

今日待办回答：

```text
今天用户打开项目时，最需要看一眼或推进的事项是什么？
```

今日待办是派生结果，不新建独立人工待办表。

```text
来源可以是风险、问题、条件、阻碍、逾期任务、流程催办、未读关键通知
不允许用户在今日待办里手工创建“待办”
用户点击待办后进入原业务页面处理
待办数量必须按 source identity 去重，避免同一事实在 Header、Dashboard、通知中心重复累计
今日待办不新增独立页面，也不保留独立“今日关注”卡片
Dashboard 中由现有“一周重点关注任务”组件承接，作为第一筛选项“今日”
```

### 4. 触达

触达回答：

```text
同一条业务事实应该在哪一层被用户看到？
```

触达层级固定为：

```text
L0 页面内提示：只提示当前页面上下文，不作为全局待办
L1 Dashboard 重点关注任务：以 今日 / 3天内 / 本周 / 紧急 四个筛选承接派生事项
L2 Header Bell：展示去重后的全局注意数量
L3 提醒中心：展示持久提醒、已知悉、静音、跳转、归组
L4 浏览器弹窗：只对临近、逾期、严重或用户启用的提醒弹出，不承载业务状态
```

## Standard Taxonomy

### 1. 通知类型

统一保留三类前端认知分类：

```text
business-warning：业务预警
flow-reminder：流程催办
system-exception：系统异常
```

分类规则：

```text
业务预警：来自 v1.4.12 预警、风险、问题链，关注业务异常是否上卷
流程催办：来自任务、计划、图纸、证照、验收、材料、协作流程，关注某个业务动作是否需要推进
系统异常：来自数据质量、映射孤立、状态进度矛盾、日期逆序、系统一致性检查，关注数据是否可信
```

不再新增第四类“普通消息”。普通消息如果没有明确来源和目标，不进入提醒中心。

### 1.1 与 v1.4 全系列体系的触达覆盖矩阵

v1.4.13 必须承接 v1.4 全系列体系产生的触达需求，但不能把所有底座治理问题都变成业务风险或用户待办。

统一规则：

```text
业务异常进入 business-warning
流程推进进入 flow-reminder
底座治理、数据质量、映射断链、状态非法进入 system-exception
页面当前动作受影响时，优先进入当前页面健康横幅
不影响当前动作的底座问题，不生成普通用户每日待办
底座治理问题不自动升级为风险 / 问题
```

覆盖矩阵：

| 章节 | 触达来源 | v1.4.13 触达口径 |
|---|---|---|
| v1.4 工程对象主数据 | 工程对象缺失、停用对象仍被引用、对象归属异常、对象 ID 与 legacy 字段不一致 | `system-exception` 或当前页面健康横幅；不进入风险问题；影响任务保存时在任务弹窗/任务列表提示 |
| v1.4.1 项目范围维度 | 范围对象缺失、范围维度未归属、范围变更影响任务/材料/验收 | 作为数据质量或页面健康横幅；只在生成计划、保存任务、报表统计时提示；不作为每日待办 |
| v1.4.2 WBS 拆解标准 | WBS 工程分类待校准、结构行/工序行语义异常、层级不完整 | 进入任务列表/计划表健康横幅或 `system-exception`；不弹强提醒；不进入风险问题 |
| v1.4.3 施工任务标准数据模型 | 任务标准字段缺失、执行行不完整、结构行错误写入进度、状态进度矛盾、日期逆序 | 状态进度矛盾和日期逆序进入 `system-exception`；字段缺失进入任务列表健康横幅；不进入业务预警 |
| v1.4.4 建筑工程任务编码规则 | 编码生成失败、编码兜底、编码规则异常、编码与对象/WBS 不一致 | 后端记录并进入 `system-exception`；普通前端不展示 task_code；不生成用户手工处理待办 |
| v1.4.5 状态与生命周期字典 | 旧状态待校准、未知状态、非法状态迁移、状态字典缺值 | 进入 `system-exception` 或状态字典后台治理；业务页面只展示可理解的状态兜底文案 |
| v1.4.6 数据来源与映射关系 | 来源断链、映射缺失、导入批次异常、拆分合并异常、孤立指针 | 进入 `system-exception`、计划页健康横幅或后台数据质量；不进入业务预警和风险问题链 |
| v1.4.7 计划治理 | 基线发布、月度确认、关账、重排、临时任务、历史快照差异 | 流程推进进入 `flow-reminder`；历史快照差异只在新一轮生成、偏差分析或 BI 中消费 |
| v1.4.7.1 共享计划树底座 | 表格校核条、保存前校核、发布/确认前校核、任务列表健康横幅、系统建议候选 | 校核条和健康横幅只在当前页面提示；保存前不生成持久通知；系统建议只出现在新版基线/月计划候选，不进入通知中心 |
| v1.4.7.2 分部分项标准库与模板生成 | 模板生成预览、标准节点归档通知、模板候选治理、参考工期带入 | 普通模板候选不通知、不进待办；节点归档影响已使用项目时可轻量通知；模板生成预览中的参考工期只做上下文提示 |
| v1.4.7.3 GanttView 共享计划树收口 | 甘特图入口、任务列表入口、基线/月计划入口共用表格事实和校核结果 | GanttView 不另建通知真值；只消费共享计划树的校核、保存、健康横幅和通知跳转结果 |
| v1.4.8 依赖/条件/阻碍 | 条件到期、条件过期、阻碍超时、阻碍恢复、建议关闭 | 条件/阻碍触达按事实进入 `flow-reminder` 或 `business-warning`；具体规则以 v1.4.8 和 v1.4.12 为准 |
| v1.4.9 里程碑/关键节点 | 临近、延期、完整性异常、关键节点变化 | 临近/延期进入 `flow-reminder` 或 `business-warning`；完整性异常进入 `system-exception` |
| v1.4.10 责任主体 | 责任人缺失、责任单位缺失、送达对象无法解析 | 影响送达时进入 `system-exception`；责任单位缺失也可进入当前业务页面健康横幅 |
| v1.4.11 图纸证照验收 | 图纸更新、证照风险、验收临近/逾期/整改、联动断链 | 业务进度影响进入 `flow-reminder` 或 `business-warning`；联动断链进入 `system-exception` |
| v1.4.12 风险问题预警 | 预警、风险、问题、升级、建议关闭 | 进入 `business-warning`；通知中心只导流，不处理风险/问题动作 |
| v1.4.14 变更留痕审批审计 | 需要确认的高影响动作、编辑者提交需管理员处理的动作、变更摘要生成失败 | 确认动作不进入通知中心；需要他人处理时进入 `flow-reminder`；审计记录不前端展示；变更摘要异常进入 `system-exception` |
| v1.4.15 删除关闭归档历史保留 | 删除被拒绝、作废完成、关闭完成、来源解除、历史保留策略变更 | 用户当前操作内即时反馈优先；需后续关注才进入 `flow-reminder`；历史保留后台决策不生成普通通知 |

触达边界：

```text
工程对象、范围、WBS、编码、状态、来源映射、指标口径、旧 AI 去 AI 化属于底座治理。
底座治理问题只有在影响当前保存、发布、确认、生成、统计或送达时，才提示用户。
底座治理问题默认不作为现场执行风险，不进入风险问题链，不打断普通进度填报。
工作台待处理、公司邀请、项目申请属于协作触达，优先由 `/workspace` 承接，不混入项目内今日待办。
材料系统到场建议、参考工期建议、剩余工期预测属于系统建议，默认不生成通知；只有建议背后的业务事实达到提醒或预警条件时才触达。
```

### 2. 通知状态

通知状态分为全局生命周期和用户处理态。

全局生命周期：

```text
active：来源事实仍然存在
resolved：来源事实已经解除
archived：超过保留期或已完成归档
source_deleted：来源对象被删除后的兼容兜底
```

用户处理态：

```text
unread：未读
read：已读
acknowledged：已知悉
muted：暂时静音
hidden：用户已从个人列表隐藏
```

规则：

```text
已知悉不等于已解决
静音不等于已解决
隐藏不等于删除业务事实
来源事实未解除时，系统可以不再高亮，但仍保留可追踪记录
来源事实解除后，系统自动转 resolved，并可进入已处理列表
```

### 3. 触达优先级

同一条事实的优先级由系统按来源、严重度、临近时间和是否逾期计算。

```text
critical：严重逾期、关键路径停滞、重大业务风险、必须今天关注
warning：即将到期、持续未处理、可能影响执行
info：普通流程提醒、状态变化、可稍后查看
success：来源解除、完成确认、自动满足类提示
```

前端不让用户选择触达优先级。

### 1. notifications 表补强

保留现有 `notifications` 表作为持久提醒主表，不新建第二套通知主表。

新增字段：

```sql
alter table notifications add column if not exists lifecycle_status text not null default 'active';
alter table notifications add column if not exists touchpoint_type text not null default 'persistent';
alter table notifications add column if not exists scope_type text not null default 'project';
alter table notifications add column if not exists company_id uuid null references companies(id);
alter table notifications add column if not exists dedupe_key text null;
alter table notifications add column if not exists target_route text null;
alter table notifications add column if not exists target_label text null;
alter table notifications add column if not exists expires_at timestamptz null;
```

约束口径：

```text
lifecycle_status: active / resolved / archived / source_deleted
touchpoint_type: persistent / dashboard_todo / popup / page_banner / system_record
scope_type: project / company / workspace / system
company_id: 多公司隔离字段；项目级通知必须可由 project_id 解析并回填 company_id
dedupe_key: 同一业务事实的稳定去重键
target_route / target_label: 后端可写入明确导流目标，前端文本猜测只作为兜底
expires_at: 临时提醒过期时间，不等于自动删除时间
```

执行要求：

```text
迁移必须提供 notifications company_id 自动回填触发器，避免旧服务直接写 notifications 时漏写公司归属
任何带 project_id 的通知插入或更新，都必须由数据库或统一服务自动补 company_id
当前仓库已存在 138_add_notifications_company_scope.sql，140 迁移不得重复发明 company_id 回填逻辑，应复用并幂等补强 138 已有字段、触发器和索引
```

索引：

```sql
create index if not exists idx_notifications_project_lifecycle
  on notifications(project_id, lifecycle_status, created_at desc);

create index if not exists idx_notifications_company_scope_lifecycle
  on notifications(company_id, scope_type, lifecycle_status, created_at desc);

create index if not exists idx_notifications_project_type_lifecycle
  on notifications(project_id, notification_type, lifecycle_status);

create index if not exists idx_notifications_source_identity
  on notifications(project_id, source_entity_type, source_entity_id, type);

create unique index if not exists uq_notifications_active_project_dedupe
  on notifications(company_id, project_id, dedupe_key)
  where lifecycle_status = 'active'
    and scope_type = 'project'
    and company_id is not null
    and project_id is not null
    and dedupe_key is not null;

create unique index if not exists uq_notifications_active_company_dedupe
  on notifications(company_id, dedupe_key)
  where lifecycle_status = 'active'
    and scope_type = 'company'
    and company_id is not null
    and project_id is null
    and dedupe_key is not null;

create unique index if not exists uq_notifications_active_workspace_dedupe
  on notifications(company_id, coalesce(user_id::text, ''), dedupe_key)
  where lifecycle_status = 'active'
    and scope_type = 'workspace'
    and company_id is not null
    and project_id is null

  on notifications(scope_type, dedupe_key)

    and project_id is null
    and dedupe_key is not null;
```

PostgreSQL 唯一约束注意事项：

```text
PostgreSQL unique index 对 NULL 不视为相等，不能只依赖 company_id + project_id + dedupe_key 覆盖所有范围。
项目级通知：使用 company_id + project_id + dedupe_key 唯一。
公司级通知：使用 company_id + dedupe_key 唯一，project_id is null。
工作台级通知：使用 company_id + user_id/recipient_identity + dedupe_key 唯一，project_id is null。
系统级通知：使用 scope_type + dedupe_key 唯一，company_id/project_id 可为空，但不得进入公司或项目强计数。
执行迁移时必须使用 partial unique index 或生成列 scope_identity，避免 company_id/project_id/user_id 为空时重复生成 active 通知。
```

服务层同步硬约束：

```text
server/src/types/db.ts 必须补齐 notifications 新字段类型
NotificationInput 必须支持 lifecycle_status / touchpoint_type / scope_type / dedupe_key / target_route / target_label / expires_at
notificationStore.normalizeNotificationInput 必须写入上述新字段，不允许新增列被服务层吞掉
notificationStore.listNotifications 必须支持 lifecycle_status / touchpoint_type / scope_type / dedupe_key / company_id / target_route 查询或过滤
notificationStore.insertNotification 必须继续复用 project_id -> company_id 回填逻辑，并补齐 scope_type 默认值
notificationStore.updateNotificationById 必须允许更新 lifecycle_status、target_route、target_label、expires_at，但业务侧不得用它绕过 notificationTouchpointService 随意改生命周期
```

### 2. 新增 notification_user_states

用于把“通知本身是否存在”和“某个用户是否已读 / 静音 / 隐藏”分开。

```sql
create table if not exists notification_user_states (
  id uuid primary key default gen_random_uuid(),
  notification_id uuid not null references notifications(id) on delete cascade,
  company_id uuid null references companies(id),
  project_id uuid null references projects(id),
  user_id uuid not null,
  user_state text not null default 'unread',
  acknowledged_at timestamptz null,
  muted_until timestamptz null,
  hidden_at timestamptz null,
  metadata jsonb not null default '{}',
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),
  unique(notification_id, user_id)
);
```

索引要求：

```sql
create index if not exists idx_notification_user_states_user_state
  on notification_user_states(user_id, user_state, updated_at desc);

create index if not exists idx_notification_user_states_company_user
  on notification_user_states(company_id, user_id, user_state, updated_at desc);

create index if not exists idx_notification_user_states_project_user
  on notification_user_states(project_id, user_id, user_state, updated_at desc);
```

用户态写入约束：

```text
user_id 必须来自 req.user.id 或已认证用户上下文，不能用空用户写用户态
旧接口没有用户上下文时，只允许读取 notifications.status / is_read / muted_until 兜底，不写 notification_user_states
同一通知同一用户只能有一条用户态记录
公司级和工作台级通知已由 v1.4.20 / v1.4.20.1 定义，project_id 可为空，但唯一性仍以 notification_id + user_id 为准
公司级、工作台级通知必须写 company_id；项目级通知必须通过 project_id 回填 company_id
```

状态：

```text
unread
read
acknowledged
muted
hidden
```

兼容规则：

```text
新链路优先读 notification_user_states
没有用户态记录时，兜底读取 notifications.is_read / notifications.status / notifications.muted_until
写已知悉、静音、隐藏时优先写 notification_user_states
旧接口仍可继续更新 notifications.status，避免已有页面断裂
```

用户态切换顺序：

```text
第一步：新增 notification_user_states 表和索引，不立刻删除 metadata.personal_states、status、is_read、acknowledged_at、muted_until 等旧字段。
第二步：读取顺序固定为 notification_user_states -> metadata.personal_states -> notifications 旧字段。
第三步：迁移脚本把 metadata.personal_states 中已有用户态复制到 notification_user_states；无法解析 user_id 的旧状态只保留为旧字段兜底，不制造匿名用户态。
第四步：已读、已知悉、静音、隐藏等用户动作先写 notification_user_states；短期同步更新旧 metadata/status/is_read，保证旧页面和旧测试不立即断裂。
第五步：Header、Sidebar、Notifications、Dashboard 全部切到新用户态后，停止写 metadata.personal_states；旧字段只读不写。
第六步：如切换失败，回滚读取可继续走 metadata.personal_states 和旧字段；不得删除旧用户态字段。
```

服务函数要求：

```text
新增 notificationUserStateService，至少提供：
getNotificationUserState(notificationId, userId)
listNotificationUserStates(notificationIds, userId)
upsertNotificationUserState(notificationId, userId, userState, patch)
markNotificationRead(notificationId, userId)
acknowledgeNotification(notificationId, userId)
muteNotification(notificationId, userId, mutedUntil)
hideNotificationForUser(notificationId, userId)

notifications route 不再直接拼 metadata.personal_states 作为新链路写入；metadata.personal_states 只作为兼容读取和短期同步字段。
```

### 5. RLS / 权限 / 幂等迁移要求

本章新增表属于触达治理数据，不允许普通前端绕过 API 直接写。

```text
notification_user_states：当前用户只能读写自己的用户态；公司管理员可按权限查看汇总，但不能伪造普通用户态；后台服务可迁移和修复。
reminder_preferences：项目 owner/editor 可维护项目级设置；公司管理员可维护公司级默认；普通成员只读生效结果。
reminder_dismissals：当前用户只能写自己的弹窗关闭记录；后台服务可清理过期 dismissals。
notifications：普通用户不能直接创建通知；创建、resolve、archive 由内部服务或治理任务完成；用户动作只能写个人用户态。
```

迁移脚本必须幂等：

```text
ADD COLUMN 使用 if not exists。
ADD CONSTRAINT 使用 DO $$ 检查或先 DROP CONSTRAINT IF EXISTS 后重建。
索引使用 create index if not exists。
触发器和函数允许重复执行，但必须先 drop trigger if exists。
回填脚本按批次执行，可重复跑，不重复制造 notification_user_states / reminder_preferences / reminder_dismissals。
全量初始化快照必须同步新增表、字段、索引、RLS 策略和回填函数，避免新环境只拿到增量口径。
```

## Backend Implementation

### 1. 新增 notificationTouchpointService

新增服务：

```text
server/src/services/notificationTouchpointService.ts
```

职责：

```text
统一生成 dedupe_key
统一判断 notification_type
统一写 target_route / target_label
统一处理 recipients
统一执行 upsert，而不是各服务散写 insertNotification
统一把来源事实解除后的通知转为 resolved
统一过滤 system_record，不进入普通提醒中心
```

与现有 notificationStore 的关系：

```text
notificationTouchpointService 是业务通知写入入口
notificationStore 是底层持久化工具
新业务服务不得直接调用 insertNotification / updateNotificationById 生成 active 通知
已有直接写入点迁移前可保留，但每迁移一个模块都必须删除该模块的散写 insertNotification / persistNotification / supabase.from('notifications').insert
deleteNotificationById 只允许 notificationLifecycleService 在 archived 且保留策略允许时调用
```

状态边界：

```text
notifications.lifecycle_status 表示通知投影生命周期：active / resolved / archived / source_deleted。
notification_user_states.user_state 表示当前用户处理态：unread / read / acknowledged / muted / hidden。
notifications.warning_lifecycle_status 只服务 v1.4.12 预警治理链：created / active / acknowledged / muted / resolved / escalated。
个人已知悉、个人静音、个人隐藏不得改变 warning_lifecycle_status，不得暂停或破坏预警升级链。
预警治理动作改变 warning_lifecycle_status 时，可以同步影响通知投影 lifecycle_status，但必须由 warning / risk / issue 业务服务发起，不由通知中心按钮直接发起。
```

```ts
  sourceEntityType: string;
  sourceEntityId: string;
  eventType: string;
  title: string;
  content: string;
  notificationType: 'business-warning' | 'flow-reminder' | 'system-exception';

  targetRoute?: string;
  targetLabel?: string;
  recipients?: string[];
  metadata?: Record<string, unknown>;
}
```

去重规则：

```text
同一 source_entity_type + source_entity_id + event_type 默认只保留一条 active 通知
跨公司永不去重；dedupe_key 必须带 company_id 或由 company_id + project_id 参与唯一约束
工作台邀请、加入申请、项目申请按 company_id + user_id + source identity 去重

同一批数据质量或系统异常可按 project_id + category + day 聚合
同一任务多条条件或阻碍不强行合并为一条业务事实，但在前端按目标页面归组展示
```

统一 source identity：

```text
所有通知、今日待办、Header/Sidebar attention-summary 必须使用同一套 source identity。
标准 identity = scope_type + company_id + project_id + source_entity_type + source_entity_id + event_type + time_window。
project_id、company_id、time_window 为空时必须转为空字符串或固定占位符后参与 dedupe_key 生成，不能依赖 NULL 参与唯一判断。
event_type 用于区分同一来源的不同触达事件，例如 due_soon、overdue、blocked_timeout、material_arrival、material_overdue、resolved。
time_window 只用于周期型提醒，例如 daily、weekly、yyyy-mm-dd；非周期型提醒为空。
todoTouchpointService 输出必须包含 dedupeKey 或 eventType，不能只输出 sourceEntityType/sourceEntityId。
attention-summary、Dashboard 今日待办、Notifications 列表归组、浏览器弹窗去重均按该 identity 判断同一事实。
```

调整规则：

```text

```
