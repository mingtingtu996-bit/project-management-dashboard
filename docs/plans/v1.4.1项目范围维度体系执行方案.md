# v1.4.1 项目范围维度体系执行方案

## 0. 2026-06-01 final range-tree boundary (authoritative)

No production history or existing users need migration. The engineering-object range tree has no compatibility layer.

Final object types are exactly:

```text
phase / section / building / basement / floor / physical_zone / functional_area
```

Deleted and forbidden as range-tree/runtime write concepts:

```text
zone / professional / subproject / custom engineering object types
zone_object_id / professional_object_id task fields
project_materials.professional_object_id
legacy_object_type / DEPRECATED_OBJECT_TYPE_VALUES
/api/scope-dimensions and scope_dimensions / project_scope_dimensions adapters
```

Specialty, system, domain package, and method semantics remain business facts only. They must come from specialty_type, engineering_category_id, standard_work_code, template metadata, or the project profile, not from engineering_objects. Any older section in this document that describes legacy compatibility, old fields, or old object types is superseded by this boundary.
## 1. 目标

v1.4.1 是对 v1.4“工程对象主数据体系”的补充与修订，专门解决“项目范围维度体系：分期、标段、楼栋、地下室、楼层、实体工程区域、功能触发区”如何落地。

本方案不另建一套与 `engineering_objects` 平行的范围维度体系。范围维度必须基于 v1.4 的工程对象主数据实现：

```text
engineering_objects 负责存对象
项目范围维度体系负责规定这些对象如何组成项目范围、如何被任务/材料/验收/报表引用
```

执行本方案时，以 v1.4.1 锁定最终范围维度口径：没有历史数据需要迁移，不保留兼容层；`zone / professional / subproject / custom / unit` 不作为工程对象核心类型，任务范围归属不允许为空。当前 v1.4 文档已同步为 7 类型终态；如遇旧版 v1.4 文档或旧实现残留，以本文件为准修正。

## 2. 核心结论

项目范围维度不是固定表格，也不是一组全部必填字段，而是一组可组合的项目归属坐标。

核心范围维度：

```text
分期 phase
标段 section
楼栋 building
地下室 basement
楼层 floor
实体工程区域 physical_zone
功能触发区 functional_area
```

不纳入核心范围维度：

```text
单元 unit
旧区域 zone
旧专业 professional
旧子项目 subproject
旧自定义 custom
```

说明：

```text
当前产品不需要单元维度
任务、材料、验收、报表不新增 unit_object_id / zone_object_id / professional_object_id
工程对象类型不初始化 unit / zone / professional / subproject / custom
专业、系统、工法、专项语义使用 specialty_type、engineering_category_id、standard_work_code、模板 metadata 或项目画像承接，不进入范围树
后续个别项目确实需要单元或其他维度时，必须作为新版本显式扩展，不通过 custom 兼容兜底
```

## 3. 数据模型修订

`engineering_objects.object_type` 在 v1.4.1 中固定为：

```ts
export type EngineeringObjectType =
  | 'phase'
  | 'section'
  | 'building'
  | 'basement'
  | 'floor'
  | 'physical_zone'
  | 'functional_area';
```

任务表范围维度字段：

```sql
alter table tasks add column engineering_object_id uuid null references engineering_objects(id);
alter table tasks add column phase_object_id uuid null references engineering_objects(id);
alter table tasks add column section_object_id uuid null references engineering_objects(id);
alter table tasks add column building_object_id uuid null references engineering_objects(id);
alter table tasks add column basement_object_id uuid null references engineering_objects(id);
alter table tasks add column floor_object_id uuid null references engineering_objects(id);
alter table tasks add column physical_zone_object_id uuid null references engineering_objects(id);
alter table tasks add column functional_area_object_id uuid null references engineering_objects(id);
```

不新增：

```sql
tasks.unit_object_id
tasks.zone_object_id
tasks.professional_object_id
project_materials.professional_object_id
```

材料、验收、报表涉及范围维度时，优先使用同一套 7 类型对象 ID 口径。材料专业归属不再通过 professional 工程对象表达，继续使用 specialty_type / engineering_category_id / standard_work_code 等业务事实。

## 4. 范围结构规则

推荐空间范围结构：

```text
项目 project
  分期 phase
    标段 section
      楼栋 building
        楼层 floor
          功能触发区 functional_area
      地下室 basement
        实体工程区域 physical_zone
          功能触发区 functional_area
  实体工程区域 physical_zone
    功能触发区 functional_area
```

专业、系统、工法、专项语义是横向业务事实，不强制挂在楼栋或实体区域下面，也不作为 engineering_objects.object_type：

```text
specialty_type / engineering_category_id / standard_work_code / template metadata / project profile
```

任务可以同时拥有工程范围和业务语义：

```text
工程范围：一期 / 一标段 / 1#楼 / 10层 / 手术部
业务语义：机电、消防、洁净、精装、专项施工等
```

对象父子关系校验：

```text
phase 可包含 section / building / basement / physical_zone
section 可包含 building / basement / physical_zone
building 可包含 floor / physical_zone / functional_area
basement 可包含 floor / physical_zone / functional_area
floor 可包含 functional_area
physical_zone 可包含 floor / functional_area
functional_area 为叶子节点
```

后端必须校验父子关系，不能只依赖前端隐藏按钮。

## 5. 范围选择规则

范围维度不要求全部必选。

任务创建和编辑时，必须校验为：

```text
至少存在一个归属维度：engineering_object_id / phase_object_id / section_object_id / building_object_id / basement_object_id / floor_object_id / physical_zone_object_id / functional_area_object_id 任一即可
专业、系统、工法、专项只作为业务语义，不作为范围归属
phase、section 未配置时，前端不显示或不要求选择
floor 必须在已选 building、basement 或 physical_zone 的情况下才显示
physical_zone 表达真实物理区域，可挂在 phase / section / building / basement 下
functional_area 表达功能触发区域，可挂在 building / basement / floor / physical_zone 下
engineering_object_id 是主要施工对象（内部字段仍叫 engineering_object_id），可由已选范围自动推荐，也允许手动指定
普通前端文案使用“主要施工对象”或“主要施工范围”，不得直接显示“任务主对象”
```

硬性业务口径：

```text
任务不允许无范围归属。
新建任务和编辑任务保存时，后端必须校验至少一个范围对象 ID 存在。
前端可以引导用户选择 building、basement、floor、physical_zone、functional_area 或主要施工对象 engineering_object_id，但不能提交完全没有范围对象的任务。
legacy 字段 specialty_type / phase_id / building_id / region_id 不能单独作为“已归属”的判断依据，只能作为业务展示字段。
当前没有历史数据，不提供旧任务兼容保存；如导入数据缺少范围对象 ID，进入编辑保存时必须补齐至少一个范围对象。
```

不同项目复杂度的允许示例：

```text
小项目：主要施工对象
普通项目：楼栋 / 地下室 + 主要施工对象
精细项目：分期 + 标段 + 楼栋/地下室 + 楼层 + 实体工程区域/功能触发区
专项任务：实体工程区域 / 功能触发区 / 主要施工对象
```

手动指定主要施工对象示例：

```text
系统推荐：用户已选择 1#楼 + 10层 + 手术部时，系统可默认推荐“手术部”或“10层”作为主要施工对象。
人工调整：如果任务实际是“机电综合调试”，用户可以手动把主要施工对象改为“地下车库”或“设备机房”等真实范围对象。
跨范围任务：如果任务是“地下车库整体移交”，即使已选多个楼层或区域，也可以手动指定“地下车库”作为主要施工对象。
专项协调任务：如果任务是“临水临电移交”，可以手动指定现场实体区域或项目主要施工对象，不通过 custom 对象兜底。
```

禁止实现为：

```text
强制所有任务都必须选择分期、标段、楼栋、楼层、区域、专业
把未配置的维度显示成空下拉并阻断保存
用前端文本拼接作为任务归属判断依据
```

## 6. 前端实现原则

范围维度选择必须做成可复用数据能力，不绑定某一个固定表格 UI。

后续维护入口可以变更，不影响数据模型：

```text
甘特图 -> 范围维度弹窗
项目设置 -> 工程对象管理
计划编制 -> 范围管理
WBS 模板 -> 对象维护
任务表单 -> 级联选择
Excel 式批量维护
图纸或 BIM 点选区域
```

只要所有入口都调用同一套 API，就不影响任务、材料、验收、报表口径：

```text
/api/engineering-objects
```

前端组件建议抽象为：

```text
EngineeringObjectSelector
EngineeringObjectTree
EngineeringObjectPicker
EngineeringObjectManagePanel
EngineeringObjectBreadcrumb
```

组件约束：

```text
组件只通过 project_id、object_type、parent_id、status 获取数据
组件返回对象 ID，不返回拼接文本作为业务主键
页面可以决定展示为树、表格、看板、抽屉、弹窗或级联选择器
任务、材料、验收提交时保存对象 ID，并回填兼容文本字段
```

## 7. 现有入口处理

当前甘特图顶部“范围维度”按钮保留。

v1.4.1 中它只是一个临时或当前版本的维护入口，不是业务契约：

```text
按钮可以继续叫“范围维度”
弹窗内部可以升级为工程对象/范围对象管理
后续如果迁移到项目设置或其他页面，不需要改后端数据模型
旧入口可保留为跳转、快捷入口或逐步下线
```

`ScopeDimensionsDialog` 改造方向：

```text
左侧：对象类型筛选，分期 / 标段 / 楼栋 / 楼层 / 区域 / 专业 / 其他
中间：对象树或列表
右侧或弹窗：新增 / 编辑 / 停用对象
```

不得在弹窗内部维护一套独立状态，必须读写 `engineering_objects`。

## 8. 旧对象处理策略

v1.4.1 不删除旧对象、旧表、旧字段和旧入口，而是把它们收进工程对象主数据的兼容层。

旧范围维度表：

```text
scope_dimensions / project_scope_dimensions 不再作为正式数据结构保留
新建范围对象只写 engineering_objects
当前没有历史数据，不提供旧表映射、兼容读取或历史兜底来源
```

旧表已有数据时的映射规则：

```text
不执行旧表映射
不把 specialty / professional / region / area / unit 转换为工程对象
导入外部数据时必须显式落到 7 类终态对象：phase / section / building / basement / floor / physical_zone / functional_area
无法识别的外部范围不得自动制造 custom 对象，必须进入导入校验问题清单
```

当前没有历史数据时的处理：

```text
不做历史清洗
不从旧表制造业务对象
只初始化必要范围骨架
分期、标段、楼栋、地下室、楼层、实体工程区域、功能触发区由用户或项目画像按需要创建
```

旧对象和新对象重名时的处理：

```text
同一 project_id、object_type、parent_id 下如果已存在同名 active engineering_object，以 engineering_objects 为准
不存在旧表同名对象合并逻辑
导入来源如需审计，可写入导入批次 metadata.sourceRef，不设计 legacyRefs 兼容字段
```

旧任务字段：

```text
tasks.specialty_type 继续作为业务专业字段，不回填 professional 对象
tasks.phase_id / building_id / region_id 如存在，只作为旧业务字段或外部导入字段，不作为范围树事实
新建和编辑任务时，只写入最终 7 类 *_object_id 字段
读取任务时，优先读取 *_object_id 关联对象
旧字段无法匹配对象时，只作为导入校验提示，不自动创建工程对象
```

前端旧状态：

```text
scopeDimensions store 字段继续保留
scopeDimensions 由 engineeringObjects 适配生成
新增页面和新组件不得直接依赖 scopeDimensions 作为主数据
旧组件如果暂时仍读 scopeDimensions，必须拿到由 engineering_objects 转换后的兼容数据
```

旧维护入口：

```text
现有“范围维度”按钮保留
按钮背后的数据读写改为 engineering_objects
后续迁移维护入口时，不迁移数据，只替换 UI 外壳和路由入口
```

责任主体对象：

```text
participant_units 继续作为责任主体主数据独立存在
不迁入 engineering_objects
任务责任单位继续引用 participant_units
工程范围归属继续引用 engineering_objects
```

## 9. API 与终态范围树

`/api/engineering-objects` 是范围维度对象的唯一读写入口。

正式接口：

```http
GET /api/engineering-objects?projectId=:projectId
```

说明：旧范围维度接口不再注册，也不作为验收口径。前端、报表、任务表单和项目画像统一从 `engineering_objects` 读取 7 类终态对象。

旧字段继续保留并回填：

```text
tasks.specialty_type
tasks.phase_id
tasks.building_id
tasks.region_id
```

读取优先级：

```text
优先读对象 ID 关联的 engineering_objects
对象 ID 缺失时读 legacy 字段
legacy 字段无法匹配对象时按文本展示，不自动制造对象
```

## 10. 汇总与报表口径

任务汇总、报表、驾驶舱、材料、验收统计必须优先按对象 ID 聚合。

标准统计维度：

```text
按分期 phase
按标段 section
按楼栋 building
按楼层 floor
按地下室 basement
按实体工程区域 physical_zone
按功能触发区 functional_area
按分期 + 标段 + 楼栋
```

兜底规则：

```text
对象 ID 存在时，禁止再用同名文本覆盖统计结果
对象 ID 缺失时，legacy 文本只作为兼容展示和临时统计来源
统计结果必须标识 source：engineering_object / legacy / invalid_unassigned
invalid_unassigned 只用于暴露历史或异常数据质量问题，不允许作为新建/编辑任务的合法保存结果
```

## 11. 执行前评审结论与补充要求

按当前代码状态看，v1.4.1 的工程对象底座已经部分落地，但还不能按“项目范围维度体系已完成”验收。当前应把第 11 节作为执行门禁：先确认已修正项，再处理剩余 P0/P1/P2 问题。

当前已基本对齐的内容：

```text
120_create_engineering_objects.sql 已锁定 7 类 object_type：phase / section / building / basement / floor / physical_zone / functional_area
120_create_engineering_objects.sql 已包含 engineering_object_id / phase_object_id / section_object_id / building_object_id / basement_object_id / floor_object_id / physical_zone_object_id / functional_area_object_id
EngineeringObjectType 已不包含 unit / zone / professional / subproject / custom
CLEAN_MIGRATION / CLEAN_MIGRATION_V2 / CLEAN_MIGRATION_V3 / CLEAN_MIGRATION_V4 / FULL_MIGRATION_ALL_IN_ONE / FULL_MIGRATION_ALL_IN_ONE_FIXED 中的工程对象片段已同步 section/floor 与非 unit 类型口径
/api/engineering-objects 已注册，且具备 list / create / update / deactivate / bootstrap 主接口
ScopeDimensionsDialog 已改为调用 /api/engineering-objects，并展示最终 7 类范围对象
store 中已增加 engineeringObjects，不再保留 scopeDimensions adapter 作为正式入口
任务后端写入链路已包含最终 7 类对象字段，并已有“至少一个范围对象 ID”校验
旧 scope-dimensions 兼容路由不得注册
任务不再通过 legacy bridge 匹配 professional / zone 对象
任务保存已调用 validateScopeObjectTypes，校验对象存在、同项目、active、字段类型匹配
任务保存已调用 validateTaskScopeConsistency，校验 engineering_object_id 与分维度对象的项目、类型、空间父链一致性
甘特任务前端已透传最终 7 类对象字段，任务表单已包含标段、地下室、楼层、实体工程区域和功能触发区对象选择
ScopeDimensionsDialog 已支持跨类型树展示，父级下拉已按合法父子关系过滤
材料后端不再支持 professional_object_id，专业归属回到 specialty_type 等业务事实
验收后端已支持 building_object_id，并回填 building_id
```

剩余 P0 问题，必须先处理：

```text
P0-1：planningIntegrityService 仍用 specialty_type + phase_id 判断 missing_scope_dimension_count，必须改为 engineering_object_id / phase_object_id / section_object_id / building_object_id / basement_object_id / floor_object_id / physical_zone_object_id / functional_area_object_id 任一存在即有范围。
P0-2：projectTrendAnalyticsService 仍读旧范围维度生成范围趋势，必须改为 engineering_objects。
P0-3：taskAttributionSummaryService 的 TaskSummaryAttributionSource 类型仍保留 scope_dimension，必须移除或确保不再输出；section / floor 缺对象 ID 时当前会落为 legacy，必须改为 invalid_unassigned。
P0-4：Reports 中如需显示专业，应读取 specialty_type 或工程分类；范围筛选必须读取 engineering_objects。
```

剩余 P1 问题，进入功能验收前处理：

```text
P1-1：材料前端保留 specialty_type 业务专业字段，不能再要求专业工程对象选择闭环。
P1-2：验收前端仍主要是 building_id 文本输入和筛选，虽然后端支持 building_object_id，但页面未形成楼栋对象选择闭环。
P1-3：旧范围维度 route 和 adapter 必须删除，避免再次出现 building / specialty / phase / region 与 7 类对象并存。
P1-4：验收口径只允许 `/api/engineering-objects`，不得补回旧范围维度 route。
P1-5：ProjectInfoCard 仍只识别 building / specialty / phase / region 四类旧范围摘要；若继续保留项目卡片范围维护，必须转为只读摘要或接入 engineering_objects。
P1-6：旧 scope_dimensions / project_scope_dimensions 到 engineering_objects 的一次性映射脚本不再执行；当前无历史数据，必须通过删除守护测试防止该兼容链路回归。
P1-7：旧 unit 对象转 custom 并写 metadata.legacyType 的方案废止；当前应验证不会生成 custom / metadata.legacyType 兼容对象。
P1-8：验收域中的 scope_level = unit、unit_completion、单位工程验收属于验收业务层级，不等于 engineering_objects.unit。文档和测试必须显式区分，避免误删验收“单位工程”语义。
```

剩余 P2 问题，建议在收口阶段处理：

```text
P2-1：engineering object code 生成按当前最大 object_code 推下一个编号，并发创建时依赖唯一约束兜底，建议补冲突重试。
P2-2：deleteEngineeringObject 当前是 status=inactive 软停用，前端文案应统一为“停用”，不要表现为物理删除。
P2-3：工程对象树的移动父级操作会级联更新 path/level，仍需覆盖多层级移动测试，防止 path 断链。
P2-4：Reports / Dashboard / TaskSummary 的筛选展示仍存在以文本 label 为主的路径，后续应逐步改为对象 ID + label 的双字段筛选。
P2-5：无历史数据时只初始化必要范围骨架；专业清单属于业务专业事实或系统字典，不进入 engineering_objects。
```

执行本方案前必须修正：

```text
如果 120_create_engineering_objects.sql 尚未在目标环境执行，直接使用当前修订后的 120 文件，并用 migration contract 测试锁住：
  object_type 不接受 unit
```

## 2026-06-01 范围树空间账本补充

范围树同时服务“现场空间账本”和“模板触发条件”，但两者不能混在一起：

- `building / basement / floor / physical_zone` 是实体空间账本对象，默认 `coverageRole='exclusive_scope'`、`areaAccountingMode='counted'`。
- `functional_area` 是功能触发对象，默认 `coverageRole='overlay_trigger'`、`areaAccountingMode='not_counted'`，用于触发医院、IDC、酒店、洁净、厨房、消防控制室等模板差异，不默认参与面积闭合。
- 如果功能空间确实需要表达实体分区，应先创建对应 `physical_zone` 或挂在具体 `floor` 下，再把 `functional_area` 作为下级触发点，不把 `functional_area` 直接当互斥空间分区。

项目画像确认页必须做范围闭合检查：总建筑面积与已计入实体范围面积的覆盖率、同级实体范围重名、拆分轴混用。面积覆盖和重名类检查作为治理提示，不直接改写模板推荐。

范围树不是展示树，而是 WBS 挂接事实源。正式提交生成 WBS 前必须执行范围模型就绪硬校验：楼栋必须能落到 `floor` 或 `physical_zone`，地下室必须具备地下层数或地下层对象，模板生成后的标准工序/专项工序不得出现找不到挂接空间的情况。若出现楼栋未配置、地下室层级缺失、模板要求的室外/独立工程区/特殊楼层不存在，系统必须阻断正式任务创建，并提示用户先补齐空间事实或取消对应专项触发。

因此，`childrenComplete / decompositionMode / floorUsage / physical_zone` 是模板生成和任务落位的业务输入，不只是前端显示字段。预览阶段可以返回治理提示；正式提交阶段必须保证生成出来的任务能够挂到项目物理空间模型上。

2026-06-14 WBS 挂接闭环补充：

- 工程物理空间模型已经按 7 类对象作为 WBS 挂接事实源：`phase / section / building / basement / floor / physical_zone / functional_area`。解析器和结构化录入只负责把用户描述或录入内容转成这套对象，不直接承诺任意自然语言都能完整生成施工范围。
- 楼栋只声明 `standardFloorCount` 且未展开全部楼层时，可视为快速建模阶段的有效体量事实；系统可以先据此完成模板试算和范围就绪判断，不强制用户在向导内手工生成每一层。
- 预览阶段必须做两类检查：先检查空间模型本身是否能承接 WBS，再调用模板生成做挂接试算。若模板返回 `SCOPE_ASSIGNMENT_TARGET_NOT_FOUND`，项目画像页必须指出缺少的空间对象、影响的任务挂接范围和下一步修复动作。
- 正式提交阶段必须硬阻断 `SCOPE_MODEL_NOT_READY_FOR_WBS`：空间基础事实缺失或模板挂接目标缺失时，不创建任务、不静默降级、不把任务挂到错误范围。
- 商业化承诺口径为“规则和 seed 覆盖内自动识别、自动触发模板、自动挂接空间；规则外或用户漏填时，在生成前暴露缺口并阻断错误生成”。不得对外表述为“任意工程空间都能完全识别并自动挂接”。

2026-06-01 补充修订：

- 允许 `building -> physical_zone -> floor`，用于表达 `1#楼 -> 塔楼区/裙房区 -> Lx`。
- `building / basement / physical_zone` 下只能使用一种直接拆分轴：按楼层，或按物理分区；不得同级混挂 `floor` 与 `physical_zone`。
- 父级 metadata 使用 `decompositionMode` 表示拆分轴，实体空间节点使用 `childrenComplete` 表示结构化录入已完整列出子空间。
- `functional_area.partitionMode` 默认为 `trigger_tag`；只有 `spatial_partition` 才参与互斥空间账本。功能区计面积不再单独按错误处理。
- 面积覆盖率只作为 info 级辅助参考，MECE 闭合主要由结构化录入、拆分轴和 `childrenComplete` 保证。

## 2026-06-01 特殊楼层商业化口径补充

架空层、避难层、设备层、转换层、屋面层、夹层、裙房屋面、雨棚/连廊层都不新增工程对象类型。它们仍是 `floor`，差异写入 `floor.metadata.floorUsage`：

```ts
type floorUsage =
  | 'standard'
  | 'ground_pilotis'
  | 'refuge'
  | 'mechanical'
  | 'transfer'
  | 'roof'
  | 'mezzanine'
  | 'podium_roof'
  | 'canopy'
```

业务边界：

- `floor` 负责竖向实体空间切片，继续参与 MECE 范围闭合；`floorUsage` 只描述该层现场用途/性质，不改变空间互斥关系。
- 用户在楼层节点属性里选择“楼层性质”；结构化录入或楼层命名可辅助推断，但最终以节点属性为准。
- 模板生成前，向导把所有楼层的 `floorUsage` 汇总为 `floorUsageCodes`，进入 `ProjectGenerationFacts`、`projectFeatures` 和 `template_generate.scope`。
- `floorUsageCodes` 可触发专项模板、危大控制、验收/移交里程碑、普通范围抑制和后续工期/依赖上下文；例如 `transfer` 触发转换层结构与高支模/大体积混凝土控制，`refuge` 触发消防、排烟、应急电源和避难层验收移交。
- 严禁把“避难层”“设备层”“转换层”等作为 `physical_zone` 或 `functional_area` 的替代类型来表达；只有该层内部再拆空间时，才在该 `floor` 下创建 `physical_zone` 或 `functional_area`。

## 2026-06-02 结构化范围录入口径补充

范围树不再以自由文本解析、按业态一键默认生成、自由拖拽树编辑作为主路径。商业化主路径改为“组织划分 + 物理空间 + 共享范围 + 空间细分 + 范围树确认”的步骤化结构化录入：步骤卡片在上方，范围树结果在下方实时更新，用户可前进/返回；高级树编辑仅作为极端场景兜底。

该口径已经纳入 v1.4.22.1 快速建模当前交付范围。范围模型、向导 Step 3 和后续模板生成消费方必须按结构化录入表产出的 7 类工程对象对齐；不得再把自由文本解析结果或业态默认样板当作范围树闭合事实。业态推荐仅允许作为“推荐物理空间草稿”，用户采用后仍需编辑确认。

Step 3 主路径固定为：

1. 组织划分：只录入分期和施工区域标段。标段通常挂在分期下面，结构为 `项目整体 -> 分期 -> 施工区域标段`；无分期项目允许标段直接挂在项目整体下。标段仅表达 `A标 / B标 / 一标 / 二标 / 东区标段 / 西区标段` 等现场施工区域，不得录入机电标、精装标、幕墙标、消防标等合同包或专业包。
2. 物理空间：录入真实互斥物理范围，主类型固定为单体建筑、地下空间、室外总平、独立工程区。物理空间创建时必须直接选择挂载位置：项目整体、某个分期或某个施工区域标段；不再通过后置“归属关系”步骤二次分配。道路、园建、管网、围墙、海绵设施不作为顶层空间类型，而是室外总平下的后续细分或任务包触发内容。
3. 共享范围：只处理地下室、室外总平等可能跨标段共用的范围。普通单体不进入共享范围设置；多个标段共用地下室时只建一个地下室节点，并通过 `sharedBySections` 标记跨标段共享，后续再按地下层和水平分区表达 A区/B区/公共区。
4. 空间细分：不同物理空间按现场逻辑使用不同细分方式。单体建筑走 `building -> floor`，综合体/塔楼裙房走 `building -> physical_zone(塔楼区/裙房区) -> floor`；地下室必须先走 `basement -> floor(B1/B2)`，再在具体地下层下走 `floor -> physical_zone(A区/B区/公共区)`；室外总平只走 `physical_zone(室外总平) -> physical_zone(道路区/园建区/管网区等)`；独立工程区默认是末级实体空间，不进入普通细分流程。
5. 范围树确认：展示结构化录入产出的 7 类工程对象，并执行“已配置 / 待配置”诊断。地下整体和室外总平如果作为末级实体空间录入，可直接闭合，不强制生成楼层子节点。特殊楼层不再是独立录入步骤，用户在范围树中点击具体 `floor` 节点后，在节点属性面板维护 `floorUsage`。

向导图标口径：v1.4.22.1 向导内入口、步骤、业态、项目空间、特征、草稿、保存、生成、预警等业务语义图标必须统一从 `wizardScopeIcons.tsx` 的 Lucide 注册表取值，不在单个步骤组件里散落维护业务语义图标。

模型边界：

- 结构化录入产出的已闭合实体空间节点写入 `childrenComplete=true`；父级写入 `decompositionMode`。楼栋在未分解前不得默认声明闭合，地下整体和室外工程区域作为末级实体空间时可直接闭合。
- 同一父级实体空间不得直接混挂 `floor` 与 `physical_zone`；塔楼/裙房必须表达为 `building -> physical_zone -> floor`，地下室水平分区必须表达为 `basement -> floor -> physical_zone`。
- `functional_area` 默认只作为功能触发标签，不参与空间互斥闭合；确需实体分区时应先建 `physical_zone`。
- 面积覆盖率只作为 info 级辅助判断，不作为 MECE 闭合的主依据；闭合主依据是结构化行、拆分轴和 `childrenComplete`。
- `object_type` 负责空间形态，`metadata/category` 负责施工逻辑；不得为 TOD、医院、工业厂区等场景无限增加 object_type。示例：地铁车站可表达为 `physical_zone + physicalCategory: metro_station`，露天装置区可表达为 `physical_zone + physicalCategory: process_unit_yard`，普通地下室可表达为 `basement + basementKind: common_basement`。
- 独立工程区可选项必须按 Step 2 业态过滤。医院项目展示液氧站、污水处理站、高压氧舱、医疗废物暂存点；工业项目展示罐区、露天装置区、管廊、堆场、公用工程站、污水站；数据中心、TOD/交通和普通民建分别展示各自合理选项，不允许向用户展示跨业态大杂烩。
- 标记为“可自动排程”的独立工程区必须同时具备两条后端链路：`projectFactsToTemplateService` 依据 `physicalZoneTypeCodes` 自动推荐对应模板/工序包，`scopeAssignmentRulesService` 再把这些工序包挂接到 `physical_zone`。例如 `railway_operation_zone` 不只需要挂接规则，还必须由空间事实触发 TOD 轨行保护和运营接口工序包；否则前端不得标记为可自动排程。
- 业态过滤只限制手工下拉录入，不限制描述解析。用户在项目范围描述中明确写出“轨行区、变电站、液氧站、冷站”等已知独立工程区时，解析器应跨业态识别为对应 `physical_zone`，并继续进入模板推荐和空间挂接链路；未明确命中的空间仍按当前业态选项和手工补充口径处理。
- Step 6 生成确认页必须展示任务挂接检查，不得只显示模板数量或行数。检查结果固定分三类：`可自动生成` 表示任务会自动落到对应楼栋、地下室、楼层或专项空间；`生成后补充` 表示空间保留为筛选范围但当前没有自动任务包；`缺少空间` 表示模板已经要求该空间，未补齐前必须阻断生成，避免任务挂错位置。
- `缺少空间` 只适用于已由项目范围事实、用户显式特征 / 工法 / 约束或正式触发项要求的空间。业态默认样板、模板目录或推荐组合顺带携带的可选独立工程区，只能作为 candidate / advisory 提示，不得升级为正式生成阻断；否则会把普通项目误判为必须配置开闭所、消防泵房、垃圾房、变配电所等空间。
- 向导预览接口 `/api/projects/wizard/preview` 必须返回 `scopeTemplateCoverage`，并以 `generationScope.scope_objects`、模板推荐结果和 `scopeAssignmentRules` 为依据计算，不能只依赖前端枚举或描述解析结果。可自动生成状态需要能追溯到命中的规则，例如轨行区应命中 `TOD-01-01-02|TOD-04-01-08|TOD-04-01-09`。

节点属性面板只描述会被后续排程、模板、范围挂载消费的局部事实：

- `building`：仅保留工法覆盖，作为项目默认工法的局部覆盖。
- `basement`：保留地下室面积和是否含人防。
- `floor`：保留楼层性质 `floorUsage`。
- `physical_zone`：保留区域类型和可选区域面积。
- `functional_area`：保留功能分类、特殊房间类型和内部触发标签语义。

以下字段不得再作为 Step 3 节点属性采集：`foundationDepthM / supportHeightM / maxSpanM / towerCraneCount / constructionHoistCount / standardFloorAreaM2 / civilDefenseAreaM2 / elevationM`，也不得向用户暴露 `coverageRole / areaAccountingMode` 手动编辑。`foundationDepthM` 来自 Step 4 的 `deep_pit` 数值，`maxSpanM` 来自 Step 4 的 `large_span` 数值，`supportHeightM` 来自 Step 4 的高支模项目级事实。
