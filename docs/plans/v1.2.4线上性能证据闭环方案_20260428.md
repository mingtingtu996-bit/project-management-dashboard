# v1.2.4 线上性能证据闭环方案

编制日期：2026-04-28

## 1. 背景

v1.2.1 已完成包体与部署产物收口，v1.2.2 已完成项目初始化与页面加载路径收口，v1.2.3 已完成 API GET 短缓存、并发请求去重与写后失效。当前剩余问题不应继续凭主观感受盲目优化，而要把“页面还是有点慢”转成可追踪证据。

v1.2.4 不新增业务功能，只建立线上性能证据闭环。

## 2. 收口目标

- 采集真实页面加载耗时，判断慢感是否来自首屏、路由切换、Web Vital、主线程长任务或 API。
- 记录慢/失败 API 的前端视角耗时，同时让服务端记录自身慢 API warning。
- 证据直接落入自有服务器日志，避免依赖 Vercel 或外部监控平台。
- 采集链路轻量、可关闭、不阻断业务操作。

## 3. 本轮实施范围

### 3.1 前端性能证据采集

新增 `performanceEvidenceReporter`：

- 页面加载：记录 Navigation Timing，包含 TTFB、DOMContentLoaded、loadEvent、资源体积字段。
- 路由切换：记录 SPA 路由稳定耗时。
- Web Vital：记录 LCP 与 CLS。
- 主线程：记录 Long Task。
- API：记录慢 API 与失败 API 的前端观测耗时。

默认开启，测试环境默认关闭。生产环境可通过：

```bash
VITE_PERFORMANCE_EVIDENCE_ENABLED=false
```

临时关闭前端上报。

### 3.2 后端证据入口

新增：

```text
POST /api/performance-reports
```

后端行为：

- 校验上报字段。
- 写入 `Client performance evidence reported` 日志。
- 超阈值时写入 `Client performance threshold exceeded` warning。
- 只保存截断后的 URL、route、userAgent 与 metadata，避免日志膨胀。

### 3.3 服务端慢 API 日志

在 `requestLogger` 内增加慢 API 判断：

- 默认阈值：`1200ms`。
- 超阈值写入 `Slow API request detected` warning。
- 可通过 `SLOW_API_REQUEST_THRESHOLD_MS` 调整。

## 4. 阈值口径

- API 慢请求：`>= 1200ms`
- 页面加载慢：`>= 2500ms`
- 路由稳定慢：`>= 250ms`
- LCP 慢：`>= 2500ms`
- CLS 异常：`>= 0.1`
- Long Task：出现即记录，单页面最多 8 条

## 5. 本轮不纳入

- 不新增数据库性能表。
- 不新增 BI 性能看板。
- 不接入 Sentry、Lighthouse CI 或第三方 RUM。
- 不做 Supabase Explain 和索引专项。
- 不做甘特/风险/材料虚拟列表专项。

这些应基于 v1.2.4 收集到的证据进入后续版本。


部署验收：

- GitHub Actions `Deploy Project Management System` 成功。
- 自有服务器部署成功。
- API 健康检查返回 `{"status":"ok"}`。
- 部署日志中 `project-management-api` 为 healthy。

## 7. 放行标准

- 前端性能证据上报不阻断页面交互。
- 慢/失败 API 有前端证据。
- 服务端慢 API 有后端 warning。
- 测试、构建、体积门禁通过。
- 自有服务器健康检查通过。
