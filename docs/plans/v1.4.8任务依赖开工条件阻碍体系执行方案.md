This v1.4-series plan follows the final range-tree model. There is no production history or existing user data that needs a compatibility layer.

# v1.4.8 任务依赖、开工条件、阻碍体系执行方案

## Summary

v1.4.8 的目标只做一件事：把当前应用里已经存在的 `任务依赖 / 开工条件 / 阻碍记录` 三类能力统一口径、统一规则、统一派生结果。

本章不扩展成证照、验收、图纸、材料、风险问题、预警、专项施工方案的完整治理章节。只有当这些模块已经直接读写或消费 `task_dependencies / task_conditions / task_obstacles` 时，才在本章定义映射边界。

当前应用已经具备：

```text

task_obstacles

```

v1.4.8 做的标准化口径是：

```text

开工条件：回答任务是否具备建议开工的准备条件
阻碍记录：回答任务执行是否存在预警、部分影响或严重阻断
```

2026-06-14 补充边界：本章维护的是依赖、前置关系、开工条件和阻碍的执行事实，不直接生成参建方问责结论。过去偏差问责由 v1.4.19 的 `progressDeviationService` 消费这些事实：`task_dependencies` / `tasks.preceding_task_id` 只证明 A 与 B 存在上游关系，`task_duration_forecasts` 的 dependencyPropagation 证明该关系在当前偏差中形成等待影响，二者组合后才允许进入 `attribution.cause_chain` 并指向上游任务 owner。`task_conditions` / `task_obstacles` 只有在未满足 / active 且自身带有责任单位或责任人字段时，才进入条件 / 阻碍致因责任链；字段缺失时只能作为原因说明，不能自动追责当前任务 owner。影响生产日、权重贡献和证据来源由偏差归因服务在 `responsibility_contribution` 中输出，本章事实表不维护独立问责排行。


## Business Definitions

### 1. 任务依赖

任务依赖是任务之间的计划逻辑关系，用于判断任务能否按计划顺序接续、是否影响排期和关键路径。

```text
FS：前置任务完成后，后续任务才能开始
SS：前置任务开始后，后续任务才能开始
FF：前置任务完成后，后续任务才能完成
SF：前置任务开始后，后续任务才能完成，少用但保留兼容
lag_days：依赖滞后天数，可为正数或 0
required_for_start：是否作为开工约束
```

依赖不是开工条件，也不是阻碍。依赖是一种结构性计划关系，主要来源于 WBS、任务表、模板、手工调整或算法生成。

普通用户不选择 `FS / SS / FF / SF`，只选择“前置任务”。依赖类型、滞后天数、是否作为开工约束由后端结合 v1.4 工程对象、WBS 工程分类、任务计划时间、实际进度和来源映射自动推断。无法稳定推断时，系统按 `FS` 保守处理，并在 `metadata` 或快照中记录 `inference_confidence = low` 与推断原因。

关键路径不是另一套任务依赖。关键路径算法必须优先读取 `task_dependencies` 作为网络图输入；`tasks.dependencies` 只作为兼容缓存；`task_critical_overrides` 只表达人工关注、人工插链和算法修正，不直接成为普通任务依赖的权威来源。

### 2. 开工条件

开工条件是任务开工前需要确认的准备事项。

固定类型：

```text
图纸
材料
人员
设备
手续
前置工序
其他
```

开工条件可以由人工创建，也可以由系统从任务依赖、图纸包通过、材料到货等当前已有联动自动满足。条件是否满足会影响 `ready_for_start` 和 `readiness_status`。

`condition_type` 保持粗粒度业务类型，不承载全部来源细节。比如专项施工方案、证照审批、政府手续都归入“手续”；图纸包审查归入“图纸”；材料到货归入“材料”。真实来源通过 `source_type/source_ref_id` 或已有 `drawing_package_id/drawing_package_code` 追溯。

### 3. 阻碍

阻碍是任务执行过程中已经发生、正在发生或提前识别到的影响因素。

固定类型：

```text
人员
材料
设备
环境
设计
手续
资金
其他
```

阻碍不是开工条件，也不等于任务完全停滞。开工条件是“开工前还缺什么”，阻碍是“执行中或即将执行时存在什么影响”。阻碍可能只是提前预警，可能造成部分效率损失，也可能导致任务严重受阻。

因此 v1.4.8 必须区分：

```text
warning：提前预警，尚未造成实际进度损失
partial：部分影响，任务仍能推进但效率、资源或完成概率下降
blocked：严重阻断，任务无法正常继续推进
```

系统不能把所有阻碍都折算成“未准备好”，而应单独形成执行影响状态。

普通用户只维护阻碍事实：阻碍类型、描述、必要时关闭记录。`progress_impact_level / blocking_scope / blocking_level` 默认由系统根据任务状态、计划时间、月计划目标、实际进度、进度维护频率、阻碍创建时间、阻碍是否关闭、阻碍类型和描述自动推断。前端不要求用户选择“预警 / 部分影响 / 严重阻断”。

## Core Design

### 1. 三类对象不合并

```text
task_dependencies：结构性计划依赖
task_conditions：任务开工准备清单
task_obstacles：任务执行影响记录
task_constraint_state：由三者派生出来的任务约束状态
```

v1.4.8 不把依赖、条件、阻碍合并成一张大表。三者业务含义不同，保留独立表更清楚。新增或补齐的是统一派生结果和统一服务。

### 2. 任务约束状态

任务约束状态由后端自动计算，不由前端人工填写。它拆成两类结果：

```text
开工准备度：由必需依赖、hard 开工条件决定，回答是否建议开工
执行影响状态：由阻碍决定，回答当前执行是正常、预警、部分受影响还是严重阻断
```

建议派生结果：

```ts
type TaskReadinessStatus =
  | 'ready'
  | 'not_ready'
  | 'partially_ready'
  | 'not_applicable';

interface TaskConstraintState {
  taskId: string;
  projectId: string;
  dependencyStatus: 'satisfied' | 'unsatisfied' | 'partial' | 'not_applicable';
  conditionStatus: 'satisfied' | 'unsatisfied' | 'partial' | 'not_applicable';
  obstacleStatus: 'clear' | 'warning' | 'partial_impact' | 'blocked' | 'not_applicable';
  readinessStatus: TaskReadinessStatus;
  progressImpactLevel: 'none' | 'warning' | 'partial' | 'blocked';
  readyForStart: boolean;
  blockedForProgress: boolean;
  constraintConfidence: 'high' | 'medium' | 'low';
  dependencyConfidence: 'high' | 'medium' | 'low';
  conditionConfidence: 'high' | 'medium' | 'low';
  obstacleConfidence: 'high' | 'medium' | 'low';
  reasonCodes: string[];
  blockingReasons: string[];
  evaluatedAt: string;
}
```

`readinessStatus` 只表达开工准备度，不替代阻碍影响判断。`blockedForProgress = true` 只表示严重阻断，不代表所有阻碍都阻断进度。

权威口径：

```text
task_dependencies / task_conditions / task_obstacles 是三类事实表
taskConstraintGovernanceService.evaluateTaskConstraint 是唯一判断入口
tasks 上的 readiness_status / dependency_status / condition_status / obstacle_status / progress_impact_level / ready_for_start / blocked_for_progress / readiness_summary 是当前状态缓存
task_constraint_snapshots 是历史回放和 BI/AI/计划算法快照，不作为当前状态写入口
普通业务服务读取当前判断时优先读 tasks 当前缓存；需要解释原因时读取 readiness_summary；需要历史趋势时读取 task_constraint_snapshots
任何服务不得再绕过 taskConstraintGovernanceService 自行用“未满足条件数量 / 未关闭阻碍数量”直接推导业务状态
```

事务与幂等：

```text
同一次依赖、条件、阻碍、任务进度或任务状态写入，必须在业务写入成功后立即调用 evaluateTaskConstraint
evaluateTaskConstraint 必须幂等：同一事实输入重复执行，不产生重复有效快照，不改变业务事实
当前状态缓存更新与快照写入必须使用同一个后端服务封装；如果数据库事务能力不足，必须用 source_event_type + source_event_id/source_event_key + calculation_version 保证快照去重
并发更新时以后发生的 evaluated_at / version 为准；旧计算结果不得覆盖新计算结果
批量重算只能修正派生缓存和快照，不得改写依赖、条件、阻碍三类事实表
```

`blocking_level` 固定值：

```text
hard：未满足时不建议开工，正式计划算法必须保守处理
soft：未满足时允许现场记录继续，但进入提醒和数据质量提示
info：仅提示，不影响开工准备度
```

`source_type` 固定使用受控来源值，不允许前端自由填写。v1.4.8 只保留与当前应用直接相关的来源：

```text
manual
dependency
drawing_package
material
special_construction_plan
business_rule
import
system
```

已有 `drawing_package_id / drawing_package_code` 字段继续兼容；新增 `source_type/source_ref_id` 是为了后续统一来源口径，不强制一次性替换旧字段。

状态和归档约束：

```text
task_conditions.status 继续由 v1.4.5 状态字典统一，至少归一到 pending / satisfied / not_applicable / deleted 四类业务语义
is_satisfied = true 时，status 必须归一为 satisfied / completed / 已满足 / 已确认 之一
not_applicable 表示条件不再参与 ready_for_start，必须写 archived_at，可写 archived_by
deleted 只允许误录、草稿、未被预警/时间轴/来源映射/计划治理消费的条件；已被消费条件点击删除时转为 not_applicable
condition_confidence 只表达系统判断把握，不影响条件事实是否满足
```

状态字典落地必须与当前 `124_create_status_dictionary_system.sql` 对齐。当前字典已有 `condition.lifecycle = open / met / confirmed / blocked / closed`，但本章业务语义统一采用 `pending / satisfied / not_applicable / deleted`。实施时不保留二选一方案，固定采用以下唯一方案：

```text
扩展 condition.lifecycle，新增 pending / satisfied / not_applicable / deleted
旧 open / met / confirmed / blocked / closed 不再作为接口主状态，只作为 legacy alias
status_aliases 必须写入：open -> pending，met -> satisfied，confirmed -> satisfied，closed -> satisfied，blocked -> pending
旧中文值必须写入 alias：未满足 -> pending，已满足 -> satisfied，已确认 -> satisfied，不适用 / 作废 / 已删除 -> not_applicable 或 deleted
接口层和 DTO 只返回 pending / satisfied / not_applicable / deleted 业务语义，不让普通前端同时看到 open/met/confirmed 与 pending/satisfied 两套口径
```

条件类型统一映射：

```text
标准 condition_type 仅保留：图纸 / 材料 / 人员 / 设备 / 手续 / 前置工序 / 其他
preceding -> 前置工序
material -> 材料
personnel -> 人员
equipment -> 设备
drawing / blueprint -> 图纸
procedure / permit / approval / special_construction_plan -> 手续
weather -> 其他
design / design-change：若有关联 drawing_package 或图纸来源则归为图纸，否则归为其他并写 metadata.legacyConditionType
无法识别的旧值 -> 其他，并写 metadata.legacyConditionType
```

“现场准备 / 一般协调”不新增为顶层 `condition_type`。这两类现场事实条件统一使用 `condition_type = '其他'`，并在 `metadata.factType` 或 `sub_type` 中写 `site_preparation / coordination`。首次进度 0% -> >0% 的轻确认只针对：人员、设备、以及 `其他 + factType/site_preparation/coordination`。

`required_for_start / blocking_level` 默认推断表必须固定，避免不同接口各自理解：

```text
前置工序：required_for_start = true，blocking_level = hard
图纸：required_for_start = true，blocking_level = hard
手续：required_for_start = true，blocking_level = hard
材料：当任务 material_required = true 时 required_for_start = true 且 blocking_level = hard；否则 required_for_start = true 且 blocking_level = soft
人员：required_for_start = true，blocking_level = soft；只有系统 / 导入 / 后台治理明确标记时才允许 hard
设备：required_for_start = true，blocking_level = soft；只有系统 / 导入 / 后台治理明确标记时才允许 hard
其他 + metadata.factType/sub_type = site_preparation：required_for_start = true，blocking_level = soft
其他 + metadata.factType/sub_type = coordination：required_for_start = true，blocking_level = soft
普通其他：required_for_start = false，blocking_level = info；不阻断 ready_for_start
```

如果实现时为了兼容已有命名继续使用 `task_readiness_snapshots`，也必须在代码注释中说明它实际保存的是任务约束状态，而不是单纯准备度。

快照权限和保留规则：

```text
task_constraint_snapshots 只允许后端服务写入，普通前端只读聚合 DTO，不直接读写快照表
RLS 按 project_id 继承项目成员可读、项目编辑者也不可直接写，写入由 service role 或后端内部服务完成

source_event_type 固定值：dependency_changed / condition_changed / obstacle_changed / task_progress_changed / task_status_changed / linkage_auto_update / migration_backfill / project_recalculate
source_event_key 必须由后端确定性生成，不允许为空。单条事实事件使用 `${source_event_type}:${source_event_id}`；批量重算使用 `${source_event_type}:${projectId}:${taskId}:${calculationVersion}:${batchId或migrationVersion}`。
project_recalculate / migration_backfill 即使没有单条 source_event_id，也必须写稳定 source_event_key，避免重复执行时产生重复快照。
```

## Backend Services

新增服务：

```text
server/src/services/taskConstraintGovernanceService.ts
```

职责：

```text
统一读取 task_dependencies / task_conditions / task_obstacles
统一计算 dependency_status / condition_status / obstacle_status / readiness_status / progress_impact_level
统一写 tasks 派生字段
统一写 task_constraint_snapshots
统一触发 warning / issue / monthly plan / critical path 相关后续消费
提供批量重算能力，用于迁移、导入、计划生成前校准
```

建议方法：

```ts
evaluateTaskConstraint(taskId: string, reason: string): Promise<TaskConstraintState>
evaluateProjectConstraints(projectId: string, reason: string): Promise<{ updated: number }>
syncTaskDependencyCache(taskId: string): Promise<void>
inferDependencySemantics(taskId: string, dependencyTaskId: string): Promise<{ dependencyType: 'FS' | 'SS' | 'FF' | 'SF'; lagDays: number; requiredForStart: boolean; confidence: 'high' | 'medium' | 'low'; reason: string }>
inferObstacleImpact(obstacleId: string): Promise<{ progressImpactLevel: 'none' | 'warning' | 'partial' | 'blocked'; blockingScope: 'start' | 'progress' | 'finish' | 'none'; confidence: 'high' | 'medium' | 'low'; reason: string }>
normalizeTaskConditionType(value: string): string
normalizeTaskObstacleType(value: string): string
```

服务硬规则：

```text
evaluateTaskConstraint 是唯一写 tasks 派生字段和 task_constraint_snapshots 的服务
taskStandardModelService.readiness_status 只能作为兼容 DTO 或临时摘要，不能继续自行散算条件/阻碍作为权威状态
businessStatusService / taskBusinessStatus 必须优先消费 tasks.progress_impact_level / tasks.ready_for_start / tasks.readiness_summary；旧条件/阻碍数量只允许作为无缓存时的兜底
dashboard / weeklyDigest / projectAttention 可消费统一摘要生成汇总指标，但不得展示条件/阻碍问题处理入口，不得把低置信度显示成严重阻断
月度计划生成可消费统一约束状态调整 inclusion_score / target_progress，但月度计划健康横幅不得展示前置任务、条件、阻碍或延期作为确认问题
```

现有服务改造：

```text
monthly plan / baselineGovernanceService：生成和确认月度计划时读取统一任务约束状态，不再散查条件和阻碍
businessStatusService / taskBusinessStatus：不再直接用“有未解决阻碍”判断为简单受阻，改为读取 progress_impact_level；warning / partial / blocked 显示不同业务含义

taskDurationForecastService：依赖数量优先来自 task_dependencies，阻碍影响系数来自 progress_impact_level，不再只按阻碍数量粗算
dashboard / weeklyDigest / projectAttention：顶部关注、侧边栏关注、周报和驾驶舱只消费统一摘要，不自行解释条件/阻碍
task timeline：task_conditions / task_obstacles 新增、更新、删除、满足、关闭仍写入时间轴事件；事件内容增加统一约束状态快照引用
validation / sqlColumns：同步新增字段和允许值，避免 route 能写、服务不能读，或迁移字段不在列白名单里
```

## Business Rules

### 1. 依赖满足规则

```text
普通前端只提交 dependencyTaskId，不提交 dependency_type / lag_days / required_for_start
后端创建或更新依赖时必须禁止跨项目依赖、自依赖和循环依赖；校验失败时不写入 task_dependencies，只返回业务错误
后端优先从任务时间关系、WBS上下游、模板来源和计划治理规则推断 dependency_type
无法稳定推断时按 FS 保守处理，标记 inference_confidence = low
FS：前置任务 status = completed 或 progress = 100，且满足 lag_days
SS：前置任务 actual_start_date 存在、status = in_progress/completed 或 progress > 0，且满足 lag_days
FF：前置任务完成后，当前任务才允许完成
SF：只保留导入和旧数据兼容，系统不主动推断为常规工程任务类型
required_for_start = true 的未满足依赖影响 ready_for_start
required_for_start = false 的未满足依赖只影响计划提示和算法置信度
多个前置依赖同时存在时，required_for_start = true 的依赖必须全部满足，任务才算依赖满足；非必需依赖不阻断 ready_for_start
用户移除前置任务时，只删除或失效当前有效依赖，不删除历史快照、来源映射和时间轴事件；删除后立即重算后续任务 ready_for_start / constraint_status
关键路径算法只消费依赖和任务约束状态，不把关键路径计算结果自动写回普通依赖
人工插链仍写入 task_critical_overrides，不替代 task_dependencies
```

依赖类型和 `lag_days` 推断优先级必须固定：

```text
1. 导入 / 模板 / 管理员治理接口传入合法 dependency_type、lag_days、required_for_start 时优先采用，并写 source_type、inference_confidence、inference_reason
2. 同开始日或明显并行开工：推断为 SS
3. 同完成日或共同收尾：推断为 FF
4. 前置任务计划完成后当前任务计划开始：推断为 FS，lag_days = 当前任务 planned_start_date - 前置任务 planned_end_date
5. SF 只允许导入或历史兼容数据保留，系统不主动推断为 SF
6. 无法判断：dependency_type = FS，lag_days = 0，required_for_start = true，inference_confidence = low，并写 inference_reason
```

### 2. 三个计划层级的依赖差异识别

项目基线、月度计划、任务列表 / 甘特都可能消费依赖关系，但三者不是同一个时间口径。系统不能要求用户在三个入口之间手工判断谁对谁错，而应把差异理解为“计划快照与当前执行事实的差异”。

```text
当前执行依赖：task_dependencies 是当前执行任务依赖的权威事实
项目基线依赖：已发布基线中的依赖关系或前后顺序是历史承诺快照，不被任务日常编辑静默改写
月度计划依赖：已确认月计划中的依赖关系或排产假设是当月承诺快照，不被任务日常编辑静默改写
任务列表 / 甘特页：承接当前依赖非法、循环依赖、缺失前置、跨项目依赖、自依赖和执行准备问题
关键路径图：只消费 task_dependencies 和任务约束状态；task_critical_overrides 不自动写回普通任务依赖
```

差异分两类处理：

```text
非法依赖：自依赖、循环依赖、跨项目、前置任务不存在、父子层级非法；进入对应健康横幅 / 数据校验，要求用户修正
正常差异：当前执行依赖不同于已发布基线、已确认月计划，或月计划不同于基线；不要求用户处理，不阻断查看、确认或执行
当前任务依赖变化后，不回写已发布基线和已确认月计划，只作为后续基线修订、月计划重算、偏差分析、关键路径、AI 分析和数据来源映射的输入
未发布基线 / 未确认月计划重新生成时，必须读取最新 task_dependencies
已发布基线和已确认月计划保留原快照，并通过 v1.4.6 data_lineage 记录当时的依赖假设
基线发布前发现依赖自循环、跨项目、缺失任务或父子层级非法时，作为基线发布阻断问题
月度计划确认前发现依赖未满足时，不作为月度健康横幅问题；系统应自动下调 target_progress、保守纳入或写入后端 generation_metadata
任务列表 / 甘特页发现依赖异常时，进入任务健康横幅和任务详情辅助提示
```

旧字段冲突处理：

```text
task_dependencies 优先级最高
tasks.dependencies 只作为兼容缓存，冲突时由 task_dependencies 覆盖并重建缓存
tasks.preceding_task_id 只作为旧单前置入口，回填到 task_dependencies 后不再单独参与 ready_for_start
task_preceding_relations 只表达条件级前置关系，用于自动满足对应条件，不额外叠加一次任务依赖阻断
task_critical_overrides 只表达关键路径人工关注 / 人工插链，除非用户明确转为任务依赖，否则不写入 task_dependencies
```

### 3. 开工条件满足规则

```text
required_for_start = true 且 is_satisfied = false 的 hard 条件，使 ready_for_start = false
soft 条件未满足时，ready_for_start 可为 true，但 readiness_status = partially_ready
info 条件不影响 ready_for_start
图纸包通过、材料到货、前置任务完成可自动满足明确关联的条件
用户手动确认不要求填写原因；系统后台自动记录操作者、时间、来源和 change_logs
```

开工条件不使用“关闭”作为主语义，统一按以下状态处理：

```text
已满足：条件事实已经达成，可由系统自动满足，也可由用户手动确认
不适用：条件因任务调整、范围调整或来源失效不再适用；用户可在条件行执行“不适用/归档”，系统后台自动记录操作人、时间和来源，不要求用户填写原因
已删除：仅限误录、草稿或未被任何流程消费的条件；已进入预警、时间轴、来源映射或计划治理后不做物理删除
待满足：默认状态，继续参与 ready_for_start / readiness_status 计算
```

对用户而言：

```text
已满足：用户可点击“确认已满足”；系统也可根据明确事实自动满足
不适用：用户可点击“标记不适用”，该条件从主列表折叠到归档/历史，不再影响 ready_for_start
已删除：仅对刚新增、误录、尚未被系统消费的条件显示“删除”；已被消费的条件点击删除时转为“不适用/归档”
待满足：正常展示在开工条件主列表
```

用户侧操作规则：

```text
确认已满足：用于现场确认条件已经达成；用户只点击确认，不填写原因
标记不适用：用于条件曾经需要、现在因任务/范围/计划/来源变化不再需要；点击后归档，不再参与开工准备度
删除误录：用于刚录错、还没有进入预警/时间轴/来源映射/计划治理的条件；点击后从普通界面消失
删除已被消费条件：前端不做物理删除，转为“不适用/归档”，避免历史预警、时间轴、计划治理断链
```

自动满足规则：

```text
前置任务完成：自动满足明确关联的前置工序类条件
图纸包通过：自动满足明确关联 drawing_package_id / drawing_package_code / source_ref_id 的图纸类条件
材料到货：自动满足明确关联材料来源的材料类条件
专项施工方案等手续来源完成：自动满足明确关联 source_ref_id 的手续类条件
现场事实类条件 + 首次进度 0% -> >0%：仅对人员、设备、现场准备、一般协调类条件弹出轻确认；用户确认后系统自动满足，不要求填写原因
现场事实类条件 + 首次进度 0% -> >0%：用户取消轻确认时，不提交本次进度修改，用于避免误操作
同次进度填报：图纸、材料、手续、前置任务等有明确外部来源的 hard 条件不因进度变化自动满足
```

如果系统无法判断条件是否已满足，不要求用户补录，也不强制关闭；保留为待满足，并把“未满足但已开工”写入数据质量提示或计划保守处理。

图纸、材料、专项施工方案不在本章做主流程治理，只作为已存在开工条件的来源或满足事件：

```text
drawing_package：只满足明确关联 drawing_package_id / drawing_package_code / source_ref_id 的图纸类条件
material：只满足明确关联 material source_ref_id 或既有材料到货联动的材料类条件
special_construction_plan：只作为手续类条件的来源标记，不新增专项方案页面或审批流
```

### 4. 阻碍影响规则

```text
普通前端只维护阻碍类型、描述和关闭动作，不要求用户判断影响程度
后端根据任务计划、实际进度、月计划目标、进度维护频率、阻碍持续时间和阻碍类型推断 progress_impact_level
status in pending / active / resolving / 待处理 / 处理中 的阻碍视为未关闭
progress_impact_level = warning 时，只进入预警、计划风险和 AI 提示，不等同于进度停滞
progress_impact_level = partial 时，影响计划算法的保守系数、目标进度和健康度，但不把任务视为完全停滞
progress_impact_level = blocked 时，blocked_for_progress = true
blocking_scope 用于说明影响阶段：start / progress / finish / none
长期未关闭阻碍继续进入 warning / issue 升级链
任务完成后可自动关闭普通阻碍，但不得自动关闭已升级为问题或风险的受保护阻碍
```

默认推断阈值：

```text
none：阻碍已关闭，或仅为历史留痕，或明确不影响 start/progress/finish
warning：阻碍未关闭，但任务未进入计划窗口、尚未开工、或当前进度未明显偏离计划；默认用于低影响材料/图纸/协调提醒
partial：阻碍未关闭，任务已进入计划窗口或本月承诺范围，且出现以下任一情况：预计解决日已过、阻碍持续超过 3 天、当前进度低于按计划线性推算值 20% 以上、关键路径任务存在未关闭阻碍
blocked：阻碍未关闭，且出现以下任一情况：任务处于进行中但连续 2 次进度填报无增长且阻碍持续超过 5 天、预计解决日逾期超过 3 天、阻碍类型为手续/设计/材料且明确导致现场无法继续、人工升级为问题或风险后仍标记影响当前任务推进
低置信度：上述事实缺少计划日期、月计划目标、进度记录或预计解决日时，不直接升为 blocked；写 impact_confidence = low，并进入数据质量或治理提示
```

阈值可配置，但必须从统一配置读取：

```text
warning_to_partial_days 默认 3
partial_to_blocked_days 默认 5
expected_resolution_overdue_blocked_days 默认 3
progress_deviation_partial_ratio 默认 20%
critical_path_weight_enabled 默认 true
```

阻碍关闭规则：

```text
用户手动关闭：现场确认影响已消除时，可在现有阻碍入口点击关闭；处理说明可选，不必填，系统后台自动记录关闭人、关闭时间和关闭方式
来源自动关闭：由前置任务完成、图纸包通过、材料到货、手续来源完成等明确来源触发的阻碍，可由系统自动关闭并写 lineage
任务完成自动关闭：任务完成后，普通未升级阻碍可自动关闭；已升级为问题、风险或进入预警 / 问题 / 风险链的阻碍不自动关闭，只解除任务侧影响
进度恢复不立即关闭：仅凭进度恢复，系统先降低 progress_impact_level 或清除 blocked_for_progress；连续恢复且达到月计划目标或任务完成后，才允许自动关闭
低置信度不关闭：无法判断影响是否消除时，保持未关闭；不得把低置信度本身记为 blocked，只在后台记录 constraint_confidence = low，并进入数据质量/治理提示
```

低置信度与执行影响分离：

```text
progress_impact_level 只表达对进度的实际影响：none / warning / partial / blocked
constraint_confidence 或 data_quality_confidence 表达系统判断把握：high / medium / low
低置信度不进入驾驶舱“严重阻断”统计，不驱动 blocked_for_progress
低置信度可进入数据质量、治理提示、AI解释，但不改变任务真实执行影响状态
```

材料、图纸、专项施工方案相关事项不自动等同于阻碍：

```text
材料未到默认先作为材料到货提醒或开工条件，只有影响具体任务推进时才生成阻碍
图纸版本变更默认先作为图纸变更通知或开工条件，只有影响具体任务执行时才生成阻碍
专项施工方案未批复默认作为手续类开工条件，只有造成执行影响时才生成阻碍
```

### 5. 任务状态与约束状态关系

```text
todo + ready_for_start = true：可建议开工
todo + ready_for_start = false：未具备建议开工条件
in_progress + progress_impact_level = warning：执行存在预警，但不代表停滞
in_progress + progress_impact_level = partial：执行部分受影响，计划算法应保守
in_progress + blocked_for_progress = true：执行严重受阻，通常对应 progress_impact_level = blocked
completed：任务约束状态只作为历史记录，不再反向阻断完成状态
cancelled / closed：退出约束状态主扫描，但保留快照
```

### 6. 不强行阻断现场录入

v1.4.8 不把所有未满足条件都做成硬拦截。现场实际很可能先发生、后补资料，所以规则是：

```text
普通进度录入允许继续，但写入数据质量提示和约束状态快照
hard 条件未满足时，计划算法保守处理，后端和 AI 可记录业务原因；Dashboard / 驾驶舱只展示汇总指标，不展示问题处理入口
阻碍按 progress_impact_level 分级处理，warning / partial 不得被误判为完全停工
只有状态机明确要求的动作，如正式确认、关账，才根据对应章节规则做硬校验
用户不负责选择依赖类型、影响程度、阻碍阶段等治理字段；这些由系统根据事实自动推断
仅当存在人员、设备、现场准备、一般协调类现场事实条件时，首次 0% -> >0% 的进度填报才触发轻确认；确认后自动满足这些条件
取消现场事实类条件轻确认时，不提交本次进度修改
数据质量状态与执行影响状态分离，不能因为系统判断低置信度就把任务显示为严重受阻
```

## 与已确认取舍的补充口径

以下口径用于消除 v1.4.8 与旧《业务流程优化清单》、关键路径专项、v1.4.7 计划治理、v1.4.9 关键节点、v1.4.11 图纸证照验收联动和 v1.4.12 风险问题预警升级之间的边界偏差。

### 1. 开工条件不硬阻断进度填报

v1.4.8 继承 v1.4.7 的计划治理口径：开工条件、前置任务和阻碍参与月度计划生成、目标进度保守估算、后续偏差分析和 AI 分析，但不作为月度计划健康横幅问题，也不阻断月度确认。

未满足开工条件时，普通进度填报仍允许提交。系统记录真实执行事实，并把“未具备建议开工条件但已有执行事实”写入任务列表 / 甘特页健康横幅、数据质量提示、任务约束快照或后端分析。前端可以提示，但不得把所有未满足条件做成进度填报硬拦截。

### 2. 不新增管理员强制解除开工条件

v1.4.8 不新增“管理员强制解除开工条件”动作，也不把强制解除包装成普通用户按钮。

普通前端只保留三个业务动作：

```text
确认已满足
标记不适用
删除误录
```

后台治理可以通过服务端修复数据、回填状态、归档误录或重算任务约束状态，但不得要求普通用户理解“强制解除”“治理字段”“审计字段”等技术概念。需要记录的操作人、原因、原值、新值和审计日志由后端自动写入。

### 3. target_date 是预警截止日，不是必填主键

`task_conditions.target_date` 只表示开工条件的预警截止日，不是开工条件的业务主键，也不是普通用户必须填写的字段。

执行规则：

```text
前端填写 target_date：按填写值保存
前端未填写 target_date：后端按任务计划开始日、计划完成日、条件类型或项目默认提醒规则推导
无法推导 target_date：仍允许保存条件，不生成 condition_due 到期提醒，写入数据质量提示
target_date 缺失不得阻止任务开工、进度填报或月度计划确认
```

### 4. 旧无法解决状态只做兼容，不作为新写入口

`unresolvable / 无法解决` 不再作为新写入状态暴露给普通前端。

旧数据必须兼容读取并映射为业务可理解状态：

```text
仍影响任务推进：映射为 active / resolving，并由 progress_impact_level 判断 warning / partial / blocked
已不影响任务推进：映射为 resolved / closed，并保留历史说明
无法判断影响程度：progress_impact_level = warning，impact_confidence = low，不进入严重阻断统计
```

`unresolvable / 无法解决` 只表示历史事项难以关闭或无法消除，不直接等同于 `blocked`。是否严重阻断必须由任务计划窗口、实际进度、预计解决日、持续时间、阻碍类型和关键路径状态综合推断。

### 5. 阻碍超时只输出标准影响信号

阻碍超时不是新增前端审批流程，也不由 v1.4.8 完整定义预警 / 风险 / 问题升级链。普通用户只维护阻碍事实：阻碍类型、标题、描述、预计解决日期和关闭动作；不选择影响阶段、影响程度、升级等级或算法字段。

v1.4.8 后端只负责把阻碍事实转成标准影响信号：

```text
阻碍未关闭且持续时间达到阈值：提高 progress_impact_level 或写入 task_constraint_snapshots
expected_resolution_date 已过且阻碍仍未关闭：作为 progress_impact_level、impact_confidence 和 readiness_summary 的输入
达到严重影响阈值：输出 blocked_for_progress、progress_impact_level = blocked 或标准化 obstacle impact signal
阻碍解除后：恢复任务侧 progress_impact_level / blocked_for_progress，并保留历史快照
低置信度：写 impact_confidence = low 和数据质量提示，不直接生成严重阻断
```

`obstacle_timeout` 预警、阻碍上卷 issue / risk、通知链、`pending_manual_close`、同一阻碍 active issue 幂等、问题关闭观察期等完整生命周期由 v1.4.12 统一治理。v1.4.8 不重复定义这些链路，只保证 v1.4.12 可以稳定消费标准化阻碍影响信号。

当前代码已经存在 `warningService.scanObstacleWarnings`、`warningChainService.escalateObstacleSeverity`、`severity_escalated_at`、`severity_manually_overridden` 和 `ensureObstacleEscalatedIssue` 等链路。v1.4.8 的任务是把这些链路的上游判断统一接入 `progress_impact_level / blocked_for_progress / readiness_summary / task_constraint_snapshots`；完整预警、风险、问题生命周期以 v1.4.12 为准。

### 6. 不恢复延期审批链

v1.4.8 不恢复 `delay_requests / task_delay_history` 审批流，不新增“延期申请 / 审批 / 驳回 / 超时审批”流程。

延期只作为以下事实被系统消费：

```text
计划偏差
任务执行事实
预警信号
健康横幅问题或数据质量问题
基线 / 月计划后续生成、修订、偏差分析和 BI 指标输入
```

若旧代码、旧测试或旧迁移仍引用延期审批链，必须按 v1.4.7 的删除口径清理或保留只读兼容，不得恢复为新功能。

### 7. 迁移顺序必须与 v1.4.9 协调

v1.4.8 与 v1.4.9 可以同步执行，但迁移编号和字段依赖必须统一排期，不能各自新增同号迁移。

推荐顺序：

```text
先落 v1.4.8：task_dependencies、task_conditions、task_obstacles 的标准字段、回填、派生状态、约束快照和重算服务
再落 v1.4.9：里程碑 / 关键节点消费 ready_for_start、progress_impact_level、blocked_for_progress 和 task_dependencies
同步开发时：v1.4.9 只能消费已落库或有兼容 DTO 的字段，不反向要求 v1.4.8 读取关键节点结果
```

### 8. 关键路径专项不由本章替代

v1.4.8 不实现完整关键路径算法，不负责浮时、关键线路重算、路径网络优化或关键路径专项看板的完整治理。

本章只提供关键路径专项需要消费的执行事实：

```text
task_dependencies
ready_for_start
readiness_status
progress_impact_level
blocked_for_progress
task_constraint_snapshots
阻碍预警 / 严重阻断状态
```

## Assumptions

当前没有历史生产数据，但仍按兼容方式处理旧字段，避免已有页面和测试断裂。

v1.4.8 只建设“任务依赖、开工条件、阻碍”的统一标准，不完整重写风险 / 问题 / 预警升级体系，也不完整重写图纸、材料、证照、验收、专项施工方案主流程。

业务流程优化清单不作为新增前端模块处理。本章只把其中已在 v1.3.5.3 和当前代码中体现的“任务表维护条件/阻碍、条件/阻碍进入预警、月度计划和报表”的口径沉淀到后端任务约束状态。

现场录入不做过度硬拦截。系统应记录真实执行事实，再用任务约束状态和数据质量提示告诉用户“为什么这项任务不健康”。

后续 v1.4 其它体系治理也遵循同一原则：前端让用户维护业务事实，系统基于主数据、计划、状态、来源映射和行为数据自动判断语义；普通用户不承担技术枚举、算法参数和治理标签选择。

## 11. 前置任务环检测的前端交互

后端 `task_dependencies` 写入前必须执行跨项目、自依赖和循环依赖校验；前端必须把循环依赖错误表达成用户能处理的业务提示，而不是暴露 `detectCycle`、依赖图算法或数据库错误。

保存任务或前置任务选择时：

```text
后端返回循环依赖错误时，不写入 task_dependencies，不关闭任务弹窗。
toast 标题：无法保存前置任务关系
toast 描述：当前选择会形成任务依赖环路，请移除其中一个前置任务后再保存。
如果后端返回 cycleTaskIds，前端在任务详情 / 甘特顶部健康提示中列出任务名称；如果只有 ID，优先转任务名称，无法解析时显示“相关任务”。

关键路径计算检测到已有环路时，甘特页显示“关键路径计算已暂停，请先消除依赖环路”，并提供查看关联任务入口。
```
## 多公司空间与数据隔离统一口径

本文件执行时必须承接 `v1.4.20 权限角色与协作体系执行方案` 的多公司空间要求。除非本文件明确声明为 `system_seed`、全局字典或演示样例数据，否则所有项目级数据都必须先归属于项目，再通过项目解析到所属公司。

```text
所有新增表：优先包含 project_id；确属公司级数据时包含 company_id；确属系统公共数据时标记 scope = system_seed / global_dictionary。
所有查询：先按 currentCompanyId / company_id 隔离，再按项目权限过滤，不允许前端二次过滤替代后端隔离。
所有汇总：公司级汇总只统计当前公司项目；项目级汇总只统计当前项目；演示项目不进入真实公司汇总和真实项目统计。
所有引用：禁止跨公司引用任务、工程对象、范围维度、责任单位、图纸、证照、验收、风险、问题、预警、计划、模板沉淀和经验数据。
所有模板 / 经验数据：系统公共种子可跨公司复用；公司沉淀模板、公司经验工期、公司历史数据只能在当前公司内使用。
所有旧数据：没有 company_id 的历史数据在迁移时归入默认公司，并保留兼容读取；不得因为补公司空间而删除旧对象。
```

本文件如出现“全部项目”“公司汇总”“项目列表”“可见项目”等表述，执行层一律理解为：先限定当前公司，再按 v1.4.20 的 `owner / editor / 当前公司 company_admin / regular` 权限模型过滤。

## 2026-05-21 与工期上下文因子的同步口径

v1.4.8 的开工条件和阻碍事实会被 v1.4.7.4 / v1.4.18 消费为 `external_readiness`，但用户操作仍保持最小化：用户只维护条件事实、阻碍类型、描述和必要的关闭动作，系统自动解释影响。

```text

日期规则：
- 条件 target_date、阻碍 expected_resolution_date 缺失时，不凭空增加等待天数，只降低置信度或进入数据质量轻提示。
```
