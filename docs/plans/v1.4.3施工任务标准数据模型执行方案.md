## 0. 2026-06-01 final range-tree boundary (authoritative)

This v1.4-series plan follows the final range-tree model. There is no production history or existing user data that needs a compatibility layer.

Authoritative engineering object types are exactly: `phase / section / building / basement / floor / physical_zone / functional_area`.

The following compatibility surfaces are deleted and must not be reintroduced in runtime code, migrations, or frontend contracts:

- `zone / professional / subproject / custom` as engineering object types.
- `zone_object_id / professional_object_id` task fields.
- `project_materials.professional_object_id` and `engineering_categories.professional_object_id`.
- `legacy_object_type`, deprecated object-type arrays, legacy bridge/backfill helpers, and old scope adapter functions.
- `/api/scope-dimensions`, `scope_dimensions`, and `project_scope_dimensions` as active application surfaces.

Professional/system/domain/method semantics remain business facts through `specialty_type`, `engineering_category_id`, `standard_work_code`, template metadata, and project profile facts. They are not range-tree objects.

Any older section in this document that mentions deleted object types, deleted fields, old scope tables, or compatibility adapters is superseded by this boundary.
# v1.4.3 施工任务标准数据模型执行方案

## 1. 目标

v1.4.3 的目标是把当前已经承载 `项目基线 / 月度计划 / 任务列表 / 甘特图 / 条件 / 阻碍 / 验收 / 材料 / 报表 / 驾驶舱 / AI 工期` 的 `tasks` 表，升级为一套可被系统稳定理解的“施工任务标准数据模型”。

本方案不新建 `construction_tasks` 替代 `tasks`。当前应用的真实施工任务实例仍然是 `tasks` 行。

v1.4.3 只解决：

```text
一条施工任务由哪些标准字段组成
哪些字段由用户录入
哪些字段由系统推断或汇总
哪些能力留在关联表
旧任务字段如何兼容
后续任务编码、审批流、经验工期库如何预留挂点
```

版本依赖顺序必须固定为：

```text
v1.4 工程对象主数据体系
-> v1.4.1 项目范围维度体系
-> v1.4.2 WBS 拆解标准体系
-> v1.4.3 施工任务标准数据模型
```

v1.4.3 依赖 v1.4.1 提供的范围对象 ID，依赖 v1.4.2 提供的 WBS 工程分类语义。若前两者未完成，施工任务模型无法稳定判断“在哪做”和“做什么”。

## 2. 核心结论

施工任务模型不是一张新的大表，而是一套围绕 `tasks` 的标准业务契约：

```text
tasks = 施工任务实例主表
engineering_objects = 范围对象，回答“在哪做”
engineering_categories = WBS/工程分类，回答“做什么”
participant_units / project_members = 责任主体，回答“谁做”
task_dependencies / dependencies = 任务依赖，回答“前后关系”
task_conditions = 开工条件，回答“能不能开工”
task_obstacles = 阻碍事项，回答“为什么受阻”
task_progress_snapshots / task_timeline_events = 执行过程事实
acceptance_plans / project_materials / drawing_packages = 外部业务联动
risks / issues / warnings / notifications = 风险问题预警链
change_logs / data_quality_findings / project_daily_snapshot = 治理、质量和 BI 口径
```

标准施工任务必须覆盖 12 组字段：

```text
1. 身份字段
2. WBS 语义字段
3. 范围归属字段
4. 计划排期字段
5. 执行进度字段
6. 工程量与进度计量字段
7. 责任主体字段
8. 依赖与前置关系字段
9. 里程碑与关键路径字段
10. 外部业务联动字段
11. 基线/月度计划治理锚点字段
12. 审计、版本、快照、数据质量与 BI 口径字段
```

不是所有字段都应塞进 `tasks`。原则是：

```text
任务主事实、常用筛选字段、稳定外键放在 tasks
多条记录、过程记录、审批记录、条件、阻碍、验收、材料、风险、问题、预警、总结、快照放在关联表
tasks 只保留必要引用、兼容字段和系统计算入口
验收可以与任务建立关联和完成回写关系，但不进入任务详情执行摘要
```

## 4. 12 组字段标准

### 4.1 身份字段

用途：定义任务自身是谁。

`tasks` 主字段：

```text
id
project_id
title
description
task_code
task_code_version
```

说明：

```text
title 是当前表格主展示名称
task_code 是后续建筑工程任务编码规则的预留字段，v1.4.3 不实现完整编码规则
task_code 可以为空；一旦生成，同项目内应唯一
task_code 在 v1.4.3 阶段默认只读，不允许前端手工编辑
WBS、范围对象、专业、楼栋、楼层等字段变化时，v1.4.3 不自动重算 task_code，只记录为待后续编码服务处理
后续任务编码服务上线前，task_code 不得作为任务创建、编辑、筛选和 BI 统计的必填依赖
description 只作为说明，不作为业务分类依据
```

### 4.2 WBS 语义字段

用途：定义任务在 WBS 中代表什么、是否可执行、是否汇总。

来自 v1.4.2 的字段：

```text
parent_id
wbs_code
wbs_level
wbs_path
sort_order
engineering_category_id
wbs_node_type
is_leaf
is_wbs_summary
is_executable
standard_work_code
standard_work_name
template_id
template_node_id
task_type
```

规则：

```text
division / sub_division / item_work 默认是结构汇总行
process 默认是施工任务执行行
activity_step 不设置项目级开关，不默认生成；仅在用户显式新增、模板明确给出或导入数据明确给出时作为更细执行行
结构行不直接维护现场进度、责任、工程量和完成事实
执行行可以维护计划、进度、责任、条件、阻碍、完成事实
后端必须拒绝执行行以外的现场完成事实写入，不能只依赖前端禁用
结构行的 progress、actual_start_date、actual_end_date、completed_quantity 只能由后端汇总或历史兼容逻辑写入
standard_work_code / standard_work_name 来自 v1.4.2 的 engineering_categories 或模板节点语义
template_node_id 指向模板节点来源，不等同于标准工艺库主键
standard_processes 是历史标准流程/工艺候选库，不作为 v1.4.3 权威 WBS 分类来源
```

### 4.3 范围归属字段

用途：定义任务“在哪做”。

来自 v1.4.1 的字段：

```text
engineering_object_id
phase_object_id
section_object_id
building_object_id
floor_object_id
physical_zone_object_id
functional_area_object_id
```

兼容字段：

```text
phase_id
building_id
region_id
specialty_type
```

规则：

```text
新建或编辑执行行时，必须至少存在一个范围对象 ID
责任人、责任单位不能替代范围对象
specialty_type 保留为业务专业属性；专业不进入工程对象范围树
旧业务字段只做展示或导入校验线索，不再作为主数据来源
```

### 4.4 计划排期字段

用途：定义任务“什么时候计划做”。

`tasks` 主字段：

```text
planned_start_date
planned_end_date
planned_duration
standard_duration
ai_adjusted_duration
reference_duration
ai_duration
start_date
end_date
```

规则：

```text
planned_start_date / planned_end_date 是新主口径
start_date / end_date 继续作为兼容字段
planned_duration 可由 planned_start_date / planned_end_date 计算，也可缓存
standard_duration 是标准工期挂点，不等于完整经验工期库
ai_adjusted_duration / ai_duration 作为 AI 工期建议挂点
结构行计划日期默认由子级汇总；确需人工约束时作为计划约束，不覆盖子级执行事实
```

### 4.5 执行进度字段

用途：定义任务“做到哪了”。

`tasks` 主字段：

```text
status
progress
progress_method
actual_start_date
actual_end_date
first_progress_at
delay_reason
completion_rule
```

标准枚举：

```text
status: todo | pending | in_progress | blocked | completed | cancelled
progress_method: percent | quantity | milestone | manual_weighted
completion_rule: progress_100 | quantity_completed | acceptance_passed | manual_confirmed
```

状态兼容映射：

```text
todo -> todo
pending -> pending
in_progress -> in_progress
blocked -> blocked
completed -> completed
cancelled -> cancelled
not_started -> todo
delayed -> blocked
on_hold -> blocked
done -> completed
unknown / 空值 -> pending
```

兼容规则：

```text
当前系统已有 todo / pending / in_progress / completed / blocked，v1.4.3 不强制一次性删除旧状态
API 写入时必须先 normalizeTaskStatus，再进入 taskStandardModelService
已知 legacy 状态按上表归一化；未知非法状态直接拒绝，返回 TASK_STATUS_INVALID
API 读取时统一返回标准状态；legacy 原始值如需保留，只能放入 standard_task_metadata.legacyStatus
前端展示只识别标准状态枚举，不再新增页面级状态翻译表
cancelled 表示任务取消，不等同于删除；取消任务不进入完成率分子，但仍可进入历史统计
progress 继续作为 0-100 展示与 BI 主进度字段
progress_method = percent 时，progress 由用户或系统直接维护
progress_method = quantity / milestone / manual_weighted 仅作为后端数据模型预留和导入兼容口径，v1.4.3 前端不得出现模式切换、工程量输入或工程量展示
普通前端写入和普通任务 API 写入必须固定为 progress_method = percent；非 percent 写入只能来自显式 systemWrite / importBackfill，并由 taskStandardModelService 校验
任务列表、任务详情、共享计划树单元格、粘贴、填充、批量编辑、状态改完成自动补进度等所有前端写入路径，遇到 progress_method != percent 时必须跳过 progress 写入
progress_method != percent 的进度展示为只读，并提示“该任务进度由{method}自动计算”
actual_start_date 默认在首次进度推进时自动写入
actual_end_date 默认在完成时自动写入
first_progress_at 默认在首次 progress > 0 时自动写入
completion_rule = acceptance_passed 只表示任务完成可由验收模块回写
验收通过回写任务完成时，只允许更新任务完成事实、进度、实际完成日期和时间线事件
任务详情 DTO 不因 acceptance_passed 返回验收摘要、验收状态卡或验收记录列表
```

### 4.6 工程量与进度计量字段

用途：为后续工程量计量、加权汇总和经验工期库预留稳定字段。v1.4.3 不在前端开放工程量模式，现场进度仍只按百分比填报。

新增 `tasks` 字段：

```text
planned_quantity numeric null
completed_quantity numeric null
quantity_unit text null
progress_weight numeric not null default 1
```

规则：

```text
v1.4.3 前端不得展示 progress_method 选择器、planned_quantity、completed_quantity、quantity_unit
普通前端写入和普通任务 API 写入必须固定为 progress_method = percent，planned_quantity / completed_quantity / quantity_unit 必须为空
progress_method = quantity 仅允许显式 systemWrite / importBackfill 使用
如果导入或系统回填形成 quantity / milestone / manual_weighted 任务，前端仍只展示 progress 主字段的当前值，不开放直接编辑；保存任务其他字段时不得顺手覆盖 progress
systemWrite / importBackfill 使用 quantity 时，planned_quantity 必须 > 0，quantity_unit 必填且不得为空字符串
systemWrite / importBackfill 使用 quantity 时，completed_quantity 为空按 0 处理，但写入后应规范化为 0
completed_quantity 不得小于 0，不得超过 planned_quantity，除非显式允许超量
允许超量时必须显式设置 standard_task_metadata.allowOverQuantity = true，并记录 standard_task_metadata.overQuantityReason
结构行不得直接维护 planned_quantity / completed_quantity；结构行工程量只能由子级执行行汇总或为空
quantity_unit 使用文本短期承接，后续可接单位字典
progress_weight 用于结构行和 BI 加权汇总，默认 1；结构行汇总进度优先按子级执行行 progress_weight 加权，缺失时才回退计划工期权重
```

### 4.7 责任主体字段

用途：定义任务“谁来做”。

`tasks` 主字段：

```text
participant_unit_id
assignee_user_id
assignee_name
assignee
assignee_unit
responsible_unit
assignee_type
```

规则：

```text
participant_unit_id 是责任单位主口径
assignee_user_id 是项目成员主口径
assignee_name / assignee / assignee_unit / responsible_unit 只做兼容展示和短期回填

```

### 4.8 依赖与前置关系字段

用途：定义任务之间的前后关系、开工条件和关键路径输入。

必须新增标准依赖表 `task_dependencies`：

```sql
id uuid primary key default gen_random_uuid()
project_id uuid not null references projects(id) on delete cascade
task_id uuid not null references tasks(id) on delete cascade
dependency_task_id uuid not null references tasks(id) on delete cascade
dependency_type text not null default 'FS'
lag_days integer not null default 0
required_for_start boolean not null default true
source_type text not null default 'manual'
source_ref_id uuid null
created_at timestamptz not null default now()
updated_at timestamptz not null default now()
```

约束与索引：

```sql
unique(project_id, task_id, dependency_task_id, dependency_type)
check(task_id <> dependency_task_id)
index(project_id, task_id)
index(project_id, dependency_task_id)
index(project_id, required_for_start)
index(project_id, source_type)
```

兼容字段与现有表：

```text
tasks.dependencies
tasks.preceding_task_id
task_preceding_relations
task_conditions.preceding_task_id
```

规则：

```text
task_dependencies 作为任务级依赖主口径
tasks.dependencies 继续保留为兼容字段和关键路径短期缓存
task_preceding_relations 继续服务条件级前置任务关系
关键路径计算优先读取 task_dependencies，缺失时回退 tasks.dependencies
写入任务依赖时同步回填 tasks.dependencies，避免旧功能断裂
新增或替换依赖时必须校验 task_id 与 dependency_task_id 属于同一 project_id
新增或替换依赖时必须做循环依赖校验，禁止形成 A -> B -> A 或更长环
循环依赖校验由 taskStandardModelService 负责；数据库至少保留自依赖约束和同项目触发器兜底
task_dependencies 必须启用 RLS，并沿用任务所属项目成员权限
task_dependencies.updated_at 必须由统一 updated_at trigger 维护
```

历史结构兼容：

```text
当前仓库已有迁移曾引用 task_dependencies(predecessor_id / successor_id) 索引口径
v1.4.3 标准口径使用 task_id / dependency_task_id
执行迁移前必须检测 public.task_dependencies 是否已存在
如果不存在，按 v1.4.3 新结构创建
如果已存在且是 predecessor_id / successor_id 旧结构，必须先做结构迁移或创建兼容视图，不能直接假设 task_id / dependency_task_id 存在
关键路径服务、数据质量服务和前端依赖编辑只面向 v1.4.3 标准口径
```

用途：定义任务是否关键、是否里程碑、是否进入关键节点统计。

`tasks` 主字段：

```text
is_milestone

milestone_id
is_critical

```

规则：


### 4.10 外部业务联动字段

用途：定义任务与图纸、材料、验收、风险、问题、预警、质量之间的关系。

其中验收只作为任务关联锚点和任务完成回写来源，不作为任务详情摘要来源。

`tasks` 必须新增轻量字段：

```text
drawing_required boolean not null default false
material_required boolean not null default false
acceptance_required boolean not null default false
quality_required boolean not null default false
```


### 5.2 新增任务依赖标准表

执行前必须先探测 `task_dependencies` 是否已存在：

```text
不存在：直接创建 v1.4.3 标准结构
存在且包含 task_id / dependency_task_id：按标准结构补字段、补索引、补约束

禁止在旧结构存在时直接执行 create table if not exists 后继续写 task_id / dependency_task_id
```

```sql
create table if not exists task_dependencies (
  id uuid primary key default gen_random_uuid(),
  project_id uuid not null references projects(id) on delete cascade,
  task_id uuid not null references tasks(id) on delete cascade,
  dependency_task_id uuid not null references tasks(id) on delete cascade,
  dependency_type text not null default 'FS',
  lag_days integer not null default 0,
  required_for_start boolean not null default true,
  source_type text not null default 'manual',
  source_ref_id uuid null,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),
  constraint task_dependencies_not_self check (task_id <> dependency_task_id),
  constraint task_dependencies_type_check check (dependency_type in ('FS', 'SS', 'FF', 'SF'))
);

create unique index if not exists uq_task_dependencies_unique
  on task_dependencies(project_id, task_id, dependency_task_id, dependency_type);

create index if not exists idx_task_dependencies_task
  on task_dependencies(project_id, task_id);

create index if not exists idx_task_dependencies_dependency
  on task_dependencies(project_id, dependency_task_id);

create index if not exists idx_task_dependencies_required_for_start
  on task_dependencies(project_id, required_for_start);

create index if not exists idx_task_dependencies_source_type
  on task_dependencies(project_id, source_type);
```

同项目约束、更新时间和 RLS：

```text
数据库必须提供 task_dependencies 同项目触发器，确保 task_id、dependency_task_id、project_id 三者一致
数据库必须提供 updated_at trigger
必须启用 RLS，并复用项目成员/项目编辑权限判断
RLS 口径：项目成员可 SELECT；项目编辑可 INSERT / UPDATE / DELETE
同项目触发器必须校验 task_id.project_id = dependency_task_id.project_id = task_dependencies.project_id
服务层必须提供循环依赖检测；数据库触发器可作为后续增强，不强制在 v1.4.3 首版实现递归检测
```


当前没有历史生产数据，但仓库和测试环境可能已有旧任务数据。处理策略：

```text
不删除现有 tasks
不新建 construction_tasks 搬迁旧任务
不批量硬改任务标题、WBS、范围和责任文本
```

默认回填：

```text
progress_method = percent
completion_rule = progress_100
progress_weight = 1
standard_task_metadata = {}
planned_quantity / completed_quantity / quantity_unit 保持 null
task_code 保持 null，等待后续编码规则生成
```

语义推断：

```text
旧行的 WBS 语义按 v1.4.2 推断
旧行的范围归属按 v1.4.1 兼容规则推断
旧 dependencies 数组回填到 task_dependencies
旧状态按 v1.4.3 状态兼容映射回填或读取时归一化
旧 assignee / assignee_unit 继续展示，保存时优先回填 participant_unit_id / assignee_user_id
specialty_type 作为业务专业属性继续展示；保存时不回填专业工程对象字段
```

编辑保存规则：

```text
旧任务只查看不阻断
旧任务再次编辑保存时，必须补齐当前模型要求的必填项
执行行保存时必须至少有一个范围对象 ID
执行行保存时 planned_start_date / planned_end_date 不得缺失
普通编辑保存不得切换或提交 quantity 模式；若旧缓存带入 planned_quantity / completed_quantity / quantity_unit，保存前必须剔除或由后端拒绝
结构行再次编辑时，不要求补齐执行行必填字段，但不得新增现场执行事实
旧任务再次编辑时，如仍无法推断 WBS 或范围对象，应返回明确错误并保留只读查看能力
```

### 8.1 范围对象处理边界

v1.4.3 不设计旧范围对象迁移。当前没有历史数据和存量用户，任务标准数据模型直接采用 v1.4.1 的 7 类范围树终态。

处理规则：

```text
scope_dimensions / project_scope_dimensions 不作为 v1.4.3 的新写入口或读取入口
phase_id / building_id / region_id / specialty_type 只作为业务展示或外部导入字段，不作为范围树事实
phase_object_id / section_object_id / building_object_id / basement_object_id / floor_object_id / physical_zone_object_id / functional_area_object_id 必须来自 engineering_objects

旧 unit/custom/professional/zone 兼容映射废止；不读取 metadata.legacyType
participant_units 继续作为责任主体，不迁入 engineering_objects，也不能作为范围对象兜底
```

外部导入对象映射失败时：


## 15. 与计划快照 / 当前执行事实的关系

施工任务标准数据模型必须遵循 v1.4.7 的计划真相模型。`tasks` 是当前执行事实核心表，基线和月计划是从任务事实生成或用于对比的计划快照。

执行项：

```text
tasks 保存当前任务名称、对象归属、WBS 分类、责任主体、计划日期、进度、实际时间、依赖、条件、阻碍和当前里程碑标记。
task_baseline_items / monthly_plan_items 生成时保存当时的任务字段快照，不被后续任务编辑静默覆盖。
任务对象、WBS、责任、计划日期、里程碑、依赖、条件、阻碍变化，只影响当前任务和后续生成。
实际开始 / 实际完成只属于任务执行事实，不作为基线或月计划生成字段。
```
