# v1.2.5 线上证据驱动精准治理方案

编制日期：2026-04-28

## 1. 背景

v1.2.1 已完成首包与部署产物收口，v1.2.2 已完成项目初始化链路收口，v1.2.3 已完成 API 运行时短缓存与并发去重，v1.2.4 已完成线上性能证据上报闭环。

从 v1.2.5 开始，性能优化不再继续按“感觉慢”扩大范围，而是按线上证据做 TOP 慢点治理。

## 2. 收口目标

- 将 v1.2.4 的原始性能上报聚合成可执行的慢点清单。
- 给出当前线上窗口的放行状态：`pass`、`watch`、`fail`、`insufficient_data`。
- 输出 TOP 慢 API、慢路由、Web Vital 异常、Long Task。
- 保持轻量实现，不新增数据库表，不引入第三方监控平台。
- 后续优化只允许围绕 TOP 1-3 个真实瓶颈展开。

## 3. 本轮实施范围

### 3.1 线上证据窗口

服务端在内存中保留最近性能证据：

```text
PERFORMANCE_REPORTS_MEMORY_LIMIT=1000
```

默认保留最近 1000 条。该窗口用于线上即时治理判断，不作为长期审计存储。

### 3.2 性能证据摘要接口

新增：

```text
GET /api/performance-reports/summary
```

返回内容：

- `window.retainedReports`：当前窗口证据数量。
- `window.thresholdExceeded`：超阈值证据数量。
- `topSlowApis`：慢 API / 失败 API TOP。
- `topSlowRoutes`：慢页面加载 / 慢路由 TOP。
- `topWebVitals`：LCP / CLS 异常 TOP。
- `topLongTasks`：主线程长任务 TOP。
- `releaseGate`：性能放行状态与原因。
- `recommendations`：下一步定点治理建议。

该接口返回 `Cache-Control: no-store`，避免性能证据摘要被普通读缓存污染。

### 3.3 放行状态口径

- `insufficient_data`：当前窗口没有线上性能证据，需要真实访问或核心路径巡检后再判定。
- `pass`：当前窗口无超阈值性能证据。
- `watch`：存在超阈值证据，但未达到阻断级别，需要按 TOP 慢点治理。
- `fail`：存在失败 API、严重慢 API，或严重 Web Vital 超阈值，需要阻断处理。

## 4. 本轮不纳入

- 不新增数据库性能历史表。
- 不新增 BI 看板。
- 不接入 Sentry、Lighthouse CI 或外部 RUM。
- 不做无证据的大范围组件重构。
- 不直接处理甘特、材料、风险等具体页面专项，除非 summary 证明它们是 TOP 慢点。

## 6. 上线要求

- GitHub Actions 质量门全部通过。
- 自有服务器部署成功，非 Vercel 路径。
- `project-management-api` 健康检查为 healthy。
- `/api/health` 返回 `{"status":"ok"}`。
- `/api/performance-reports/summary` 可用于查看线上性能证据摘要。

## 7. 后续治理原则

v1.2.5 之后的性能优化必须遵守：

- 先看 summary，再决定改哪里。
- 一次只治理 TOP 1-3 个瓶颈。
- 每个瓶颈都要有前后证据。
- 没有证据的优化不进入上线阻断范围。
