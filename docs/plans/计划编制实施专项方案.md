## 执行方法补充

- 正文任一步骤开始前，必须先对照《三份专项方案执行前检查清单.md》筛出本步适用的 `blocked` 条件；若命中任一阻断项，当前步骤不得直接进入实现。
- 下列步骤已在正文内明确拆成子步骤：`15.1 / 15.3 / 15.4 / 15.5 / 15.6 / 15.7 / 15.8 / 15.9 / 15.10`；执行时不再依赖模型自行判断是否拆分。
- 子步骤只允许内联本步必需的需求摘录，推荐控制在 `20-80` 行，并同时保留来源锚点 `业务流程优化清单.md:xxxx`；不得全文复制需求章节，避免形成第二份需求真值。
- 数据模型 / API / 状态机类步骤统一采用 `test -> impl -> review`；页面壳层 / 组件类步骤统一采用 `contract-test -> impl -> review`；纯视觉一致性统一采用 `story/e2e -> review`。
- 高风险页面步骤的子步骤命名统一采用 `15.xa-contract-test -> 15.xa-impl -> 15.xa-review` 这一组模式；同一父步骤下的下一块功能继续用 `15.xb-* / 15.xc-*` 顺延，父步骤总复核统一写成 `15.x-review`。
- `review` 步骤只做检查，不写新功能；若发现缺口，当前父步骤必须保持 `blocked`，不得直接记为 `completed`。
- `review` 发现的问题写回 `EXECUTION_PROGRESS.json` 时，必须使用统一 `gaps` 结构，至少包含 `id / source / rule / finding / fix_in` 五个字段，例如：

```json
{
  "step": "15.3-review",
  "status": "blocked",
  "gaps": [
    {
      "id": "GAP-15.3-01",
      "source": "业务流程优化清单.md:5660",
      "rule": "确认冻结吸底条：存在阻断级问题时主按钮禁用",
      "finding": "BaselineConfirmBar 未检查 blockingIssues > 0",
      "fix_in": "15.3-fix-01"
    }
  ]
}
```

- 跨文件前置依赖必须显式声明；`15.0 planning-types` 的前置步骤固定为 `10.1 completed`、`10.2b completed`。三份专项方案的实际交错顺序应理解为：`10.1 → 10.2a → 10.2b → 15.0 → 15.0a → 15.1 ...`，而不是做完全部 `10.x` 后再进入 `15.x`。
- 计划编制的 E2E / story 验收不能只覆盖主流程；至少必须覆盖：`并发锁冲突 / 来源版本过期 / 数据不足降级态 / 关账处理中被他人先处理 / 快速确认路径 vs 标准路径`。

- **具体动作**
  1. 先定义计划编制域共享类型：`BaselineVersion / BaselineItem / MonthlyPlanVersion / MonthlyPlanItem / CarryoverItem / RevisionPoolCandidate / PlanningStatus / PlanningEvent`
  2. 明确共享 API 契约：至少锁定 `基线确认冻结 / 月计划确认 / 月末关账 / 独立修正 / 观察池读取与提交 / 偏差分析读取` 的 request / response / error shape

  4. 为状态机补专门测试：验证合法转换可通过、非法转换被拒绝，覆盖 `draft / confirmed / closed / revising / pending_realign` 等核心状态与事件组合

     ```json
     {
       "types": ["BaselineVersion", "MonthlyPlanVersion"],
       "endpoints": [
         {
           "method": "POST",
           "path": "/api/task-baselines/:id/confirm",
           "requestShape": "{ version: number }",
           "responseShape": "{ id: string, status: 'confirmed' }",
           "errorCodes": ["VERSION_CONFLICT", "BLOCKING_ISSUES_EXIST"]
         }
       ],
       "stateMachine": {
         "states": ["draft", "confirmed", "closed"],
         "events": ["CONFIRM", "CLOSE_MONTH"],
         "transitions": ["draft + CONFIRM -> confirmed"]
       }
     }
     ```
- **不要做的事**
  - 不在本步编写页面 UI
  - 不在本步落数据库迁移和业务路由副作用链
  - 不重复定义 `10.1 / 10.2b` 已落地的共享类型

## 2026-06-17 计划编制算法口径补充

本补充不改变 `15.0 -> 15.11` 的执行顺序，只把后续维护基线生成、月度计划生成和历史回放校准时必须遵守的算法口径写回计划编制域。

### 项目基线生成

1. 基线草案生成顺序固定为：先完成 B2 锚定，再消费 E3 fresh CPM snapshot，按 FS / SS / FF / lag 对 E3 任务做网络顺重排。生成器不在自身内部重写前向 / 后向 CPM；它优先消费 E3 输出的 `networkSchedule` CPM offset，在 B2 锚点上按工作日换算 `earliestStart/earliestFinish`，写入 `e3_calendarized_*` metadata；只有 E3 未提供 offset 时才回退到网络顺串排。
2. 日期换算必须全量施工日历化：项目层和生成层统一复用 `resolveConstructionCalendarContext`，不得在运行期 calendar 为空时退回自然日 `addCalendarDays` 口径。
3. 确认前基线专属闸门必须拦截里程碑倒序、资源峰值超限、总工期压缩超上限、互斥工序冲突。资源峰值复用 E3 已接入的 RCPSP 空间日限，并按 `resource_class + global/building/unit/floor/zone/system + 日期` 展开部分重叠窗口，避免 5/1-5/3 与 5/2-5/4 这类重叠资源超限漏拦；互斥工序复用 `v1474ProcessConstraintSeed`，不得另建平行冲突规则。
4. 每个 baseline item 的 `generation_metadata` 必须在 B2 `dateSource` 基础上保留 `applied_factors / source_priority / confidence / override_level`，用于解释 actual / E2 / E1 / current schedule 的来源优先级与人工覆盖层级。

### 月度计划生成

1. `capacityBudgetDays` 只表示“施工日历化工作日 + 国标默认班组 / 专业产能 + 日历因子”的默认产能上限，不得写成真实班组产能；真实班组采集未完成前，输出 metadata 必须保留这个天花板说明。月计划容量预算必须复用 `resolveConstructionCalendarContext` 扣除春节 / 项目停工 / 明确 shutdown 窗口，并写入 `monthly_capacity_calendar_basis / source / shutdown_deducted_days`，不得只按周一到周五粗算。
2. 容量竞争按 `resourceClass + specialty / building / floor / zone / workface` 多池计算，复用 RCPSP 的空间 scope key，不新增维度体系。基线生成侧在已有 `resource_class + scope_keys` 上沉淀 `rcpsp_capacity_pool_key / rcpsp_capacity_pool_key_source / rcpsp_capacity_pool_key_policy`，并同步挂入 item `algorithm_context`，供月计划沿用同一资源 / 空间池口径。运行期必须优先消费 E3 / RCPSP 已沉淀的 `rcpsp_capacity_pool_key`，并在 monthly item metadata 写入 `monthly_capacity_pool_key_source / monthly_capacity_pool_key_policy`；只有该 canonical key 缺失时，才允许从既有 `generation_metadata.scope_keys` / `scope_snapshot.dimensions` fallback 重建池 key。土建、机电、楼栋和作业面不能再挤在单一月预算池里竞争。
3. 月窗任务纳入门不能只看 planned 日期窗口。除了 planned_start/planned_end 与目标月份重叠、以及已开工未完工的跨月孤儿项外，凡 `source_task_id` 对应 E2 预测 `forecastFinishDate` 落在目标月内的未开工任务，也必须纳入当月候选，并在 metadata 标记 `e2_forecast_month_overlap / e2_forecast_inclusion`，防止“计划还停在上月、实际已注定拖入本月”的任务整批漏出月计划。
4. `target_progress` 固定为 `min(计划线性目标, E2可完成目标, 容量可分配目标)`，并把三项输入全部写入 metadata，避免轻载月份继续只按线性目标承诺。
5. 连续结转次数、上月实际完成率、责任方响应和阻碍是否解除进入结转老化惩罚；长期结转且原因未解除的项应降为管理关注 / 条件承诺。实现口径要求：上一月已有 `last_month_actual_completion_rate / responsible_response_status / unresolved_blocker_count` 时优先继承；缺字段时必须从上一月 `current_progress / target_progress` 和 runtime 事实总线的未解除前置、条件、阻碍、材料 / 验收映射信号推导，不得只因旧 metadata 缺失而漏掉老化惩罚。
6. 月计划优先级消费 E4 fresh snapshot 的 `floatDays` 分档，只区分真关键、近关键和伪关键；存在 fresh `critical_float_tier` 时必须优先于陈旧 baseline `is_critical` 标记，只有缺少 fresh 分档时才允许回退旧关键标记。
7. “可直接确认 / 必须人工复核”的评分由 `monthlyPlanSummaryService` 产出，并注册到 `metricRegistryService`；路由层只编排服务调用，不自算 BI / 摘要口径。

### 统一回放校准

1. 基线和月计划共用 `planningReplayCalibrationService.ts`，用同一台回放机器比对历史已完工 / 已关账数据中的“算法当时会生成什么”与“实际发生什么”；生产 sweep 入口为 `planningReplayCalibrationJob.ts`，默认扫描 confirmed / closed / archived 的基线和月计划样本。
2. 第一阶段按粗工序分桶：`standardWorkCode -> standardWorkName -> engineeringCategoryId`。项目类型、楼型、气候、楼栋、楼层、分区、作业面暂缓细分，样本不足时不得拆细。
3. 默认每个粗工序桶至少 5 条 accepted 样本才输出校准建议。输出只允许是 E1 / E2 / seed / 容量 / 优先级 / E2 target 折减的候选调参建议，策略固定为 `candidate_overlay_only_no_fact_mutation`。
4. 回放校准不得写 `task_baselines / monthly_plans / monthly_plan_items / tasks / task_dependencies / critical_path_snapshots / actual_duration_outcomes / progress_snapshots / algorithm_seed_records / algorithm_seed_versions / algorithm_seed_overrides / duration_forecast_residual_overlays`。它只能通过既有 replay evidence 持久化链写治理证据包，不能直接改业务事实、承诺或 runtime 发布件。
5. `readPlanningReplayCalibrationReadback(...)` 是统一消费口：E1 `durationSuggestionService.ts` 消费 `e1DurationAdjustmentDays`，只作为有界候选 overlay 调整本次参考工期输出和解释 metadata；E2 `taskDurationForecastService.ts` 消费 `e2ResidualCorrectionDays`，只作为 residual overlay 之后的有界候选修正，重算剩余天数、预测完成日和延误天数。两者都保留 `writePolicy / evidenceRefs / acceptedSampleCount / MAE` 证据，不改 seed、不改任务事实、不改已确认基线或月计划。
6. E2 residual overlay 生产侧由独立的 `forecastResidualOverlayProductionJob.ts` 每日 06:05 扫描已完成预测结果；它不是 `planningReplayCalibrationJob.ts` 的写入副作用。生产样本必须存在明确 residual overlay / `forecastPaths.recommended` 来源，不能用原始 `forecast_finish_date` 兜底冒充 overlay；项目级默认至少 5 条 accepted 样本才可进入 overlay 发布评估。该生产者只服务 `duration_forecast_residual_overlays` 的专属治理 / runtime overlay 门禁，不改基线、月计划、实际进度或依赖事实。

## 2026-06-20 向导计划表生成颗粒度补充

项目向导生成的计划表必须按“可投产首屏骨架 + 隐藏子孙深算 + 后续可下钻”的计划编制口径执行。该口径用于解决大中型项目一次生成时同时满足行数上限、总工期可信、施工时间排序和后续维护深度的问题。

计划编制消费规则：

1. 向导预览和正式提交统一调用 `planning_skeleton / managed_frontier`，不得因用户选择 detailed 而在首屏直接铺开全部 `process / activity_step`。
2. 首屏行是管理颗粒度，不是目录颗粒度；每个节点通过 `generation_depth_policy` 决定停在 `sub_division / item_work / process`。
3. 可见行的工期来自 `durationComputeDepth` 下的隐藏子孙工序 rollup，不能用父级目录节点自身粗估或默认 1 天兜底。
4. 隐藏子孙 rollup 必须使用网络窗口而不是简单求和：下层工序仍消费 E1 参考工期、seed、规则资产和项目事实，父级只承接 `network_rollup` 后的可见计划窗口。
5. 可见汇总行必须通过阶段 / 专业 / 作业面释放网络排程，生成 `summaryNetworkSchedule` 证据；禁止回退到一个 catalog cursor 把所有子分部首尾相接。
6. 跨项依赖只在空间或系统事实充分时连边。缺楼层、分区、系统或功能区证据时，不得把 `same_floor / same_zone / same_system` 当成全项目兼容关系。
7. 专项模板和管理支撑模板必须通过 `packType / templateGroup / templateId` 命中显式停层规则，不得落回核心土建通用规则。
8. 生成结果按施工时间排序，供计划表审核和投产使用；模板编号只作为稳定次序 fallback。
9. `smart_reference_days` 保持数字型计划事实；深算依据、规则版本、停层说明和下钻来源写入 `duration_suggestion / standard_task_metadata`。
10. 生成结果必须返回 `scheduleTrustGate`；只有 `status=trusted` 的计划表可直接作为生产排程，`review_required / blocked` 需要先复核规则、下钻 rollup 或参考工期缺口。
11. 下钻只用于后续维护和明细展开，不表示首屏计划缺失；首屏 500 行约束仍是产品边界。
12. 对于 `review_required / blocked` 的生成结果，正式提交链路只通过既有候选治理链沉淀 `generation_depth_policy` 规则候选，不直接改写计划表事实、依赖、基线、月计划或工期 seed。

与既有工期体系关系：向导生成计划表不是新建一套算法，而是把已有工期体系接入计划表装配。生成期消费 E1 参考工期和项目事实，复用施工日历、依赖语义、阶段释放和规则资产形成计划日期；任务落表后，再由 E2/E3/E4/E5 分别负责执行中剩余预测、关键路径、项目整体剩余和工期压缩建议。计划编制侧只保存可解释的计划窗口和规则证据，不写第二套工期真值。

项目层施工组织定位：它是向导生成期的施工组织装配层，不是资源约束排程器，也不是第六个工期引擎。主输入是项目建设对象、楼栋/单体数量、共享地下/裙房/总平、业态策略、阶段释放、分区/系统/功能界面 gate 和目录候选实际化结果；`towerCraneCount / constructionHoistCount` 等资源字段即使由向导或项目事实带入，也只能作为 sidecar feasibility signal，用于生成后验算资源需求、解释现场承载压力或提示后续优化，不得反过来决定楼栋车道、主阶段网络或总工期主骨架。

2026-06-21 施工组织方案选择器补充：项目层施工组织不是新增第六个工期算法，而是在向导生成期和 E5 工期压缩之间新增一层可治理的候选选择器 `constructionOrganizationScenarioSelector.ts`。该选择器只消费既有向导 / 项目事实，不新增前端输入；当前支持从桩基础、基坑深度、支护方式、雨季 / 土方天气敏感、共享地下室、多楼栋、室外总平 / 市政 / 景观等事实生成 `pile_before_excavation`、`excavation_before_pile`、`tower_lane_early_release_after_core_basement`、`shared_basement_first_then_tower`、`outdoor_site_early_release_after_basement_backfill`、`outdoor_site_after_primary_structure` 等候选。每个候选现在都带结构化 `virtualNetwork`：抽象节点、候选依赖、相对总跨度、关键节点、写入边界和 E1 / E3 / E5 评估摘要；推荐 / 排除理由不再只是文字 hints。选择结果写入 `standard_task_metadata.projectOrganization.scenarioSelection`，供生成结果解释和后续治理消费；E5 `scheduleAccelerationService` 已把推荐施工组织方案作为 `constructionOrganizationScenario` 一等上下文写入 `calculationBasis`，并消费候选评估里的 `recoveryFactorHint / virtualNetworkTotalSpanDays / virtualNetworkCriticalNodeIds` 做温和恢复预算修正和解释。
