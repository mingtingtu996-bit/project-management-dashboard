## 0. 2026-06-01 final range-tree boundary (authoritative)

This v1.4-series plan follows the final range-tree model. There is no production history or existing user data that needs a compatibility layer.

Authoritative engineering object types are exactly: `phase / section / building / basement / floor / physical_zone / functional_area`.

The following compatibility surfaces are deleted and must not be reintroduced in runtime code, migrations, or frontend contracts:

- `zone / professional / subproject / custom` as engineering object types.
- `zone_object_id / professional_object_id` task fields.
- `project_materials.professional_object_id` and `engineering_categories.professional_object_id`.
- `legacy_object_type`, deprecated object-type arrays, legacy bridge/backfill helpers, and old scope adapter functions.
- `/api/scope-dimensions`, `scope_dimensions`, and `project_scope_dimensions` as active application surfaces.

Professional/system/domain/method semantics remain business facts through `specialty_type`, `engineering_category_id`, `standard_work_code`, template metadata, and project profile facts. They are not range-tree objects.

Any older section in this document that mentions deleted object types, deleted fields, old scope tables, or compatibility adapters is superseded by this boundary.
# v1.4.23 总集成与全链路验收体系执行方案

v1.4.23 是 v1.4 系列最后的总控章节，不再新增独立业务体系。

截至 2026-07-01，本文件只作为 v1.4 总集成边界、实施顺序、旧对象处置原则和验收框架的总收口文件，不再作为当前自动执行队列或生产可交付状态的唯一判定来源。当前状态升级、证据编号、红灯门禁和旧对象物理清理承接，以 `v1.4.23.1-A体系收口台账与验收门禁矩阵.md`、当前门禁复跑输出和 `project-testing/reports/` 下的收口报告为准。

本章目标是把 `v1.4` 到 `v1.4.22` 以及补充文件 `v1.4.7.1 / v1.4.7.2 / v1.4.7.3 / v1.4.20.1` 串成一条可实施、可验收、可回归的完整链路，解决：

```text
各章节执行顺序是什么
数据库迁移、后端服务、前端入口如何分批落地
旧对象、旧字段、旧接口如何兼容和收口
项目基线、月度计划、任务列表、专项管理之间如何避免口径冲突

哪些能力必须在后端统一计算，哪些只做前端展示
哪些场景必须验收通过，才算 v1.4 真正完成
```

本章不是重新设计产品，也不是新增 AI 助手、OA 审批、采购库存、成本合同、质量安全、竣工档案等新模块。

## 2. 总原则

### 2.1 任务列表是实时事实，基线和月计划是历史承诺快照

v1.4 系列必须统一遵循：

```text
任务列表：当前项目执行事实和动态治理核心
项目基线：某一时点确认后的历史承诺快照
月度计划：某一月度确认后的历史执行计划快照
专项管理：图纸、证照、验收、材料、风险、问题等业务事实来源
Dashboard / Reports / 周报 / 公司驾驶舱：消费统一后端摘要和快照
```

项目基线和月度计划确认后不被任务列表反写。

当任务列表中的依赖、关键节点、工程对象、责任主体、日期、阻碍、风险、材料、验收等事实发生变化时，不要求用户逐条同步旧基线或旧月计划；系统应在生成新一轮基线或月计划时提示差异，由用户决定是否纳入新一轮历史承诺。

### 2.2 能系统自动判断的，不增加用户操作

v1.4 系列所有体系都必须遵循：

```text
用户负责录入现场事实、确认关键业务动作、选择必要主数据
系统负责自动编码、自动归因、自动校核、自动联动、自动提示、自动沉淀
前端不展示技术字段、来源链、置信度公式、样本编号、快照编号、内部映射 ID
后台可记录完整事实，前端只展示用户需要理解和处理的业务结果
```

典型规则：

```text
实际开始：进度从 0 变为 >0 后由后端自动生成
实际完成：进度变为 100 后由后端自动生成
开工条件：明确事实可自动满足，软条件在首次进度变化时轻确认
阻碍：用户只填类型和描述，系统按进度恢复、任务完成、来源解除自动降级或建议关闭
风险问题：用户主要操作为转问题、关闭、重新打开，系统负责建议关闭、升级、预警链
删除：用户点击删除，系统判断物理删除、软删除、停用、作废、归档或拒绝
```

### 2.3 数据质量和业务问题分离

数据质量问题不得混同为业务风险问题。

```text
业务问题：影响现场推进、计划兑现、验收、材料、责任闭环
数据质量问题：影响系统能否正常计算，或影响分析结论可信度
```

阻断型数据质量问题只在录入和确认场景提示；分析可信度问题主要在 Dashboard / Reports / 健康度摘要中轻提示。

### 2.4 不建立独立 AI 体系

历史实现中曾存在 `ai-duration / ai-schedule / ai_duration` 等旧命名链路；这些不是大模型 AI，也没有 OpenAI / GPT / LLM 运行依赖。当前总集成口径下，这些旧命名链路属于退役对象，不再作为兼容入口保留。

v1.4 不建设独立的“AI 分析与智能辅助底座”，而是统一收口为规则化智能治理能力：

```text
AI 到货建议 -> 系统到场建议
AI 工期估算 -> 参考工期建议 / 工期建议
AI 排程 -> 执行风险分析 / 到场风险分析
AI 推荐 -> 系统建议
```

旧接口不再保留兼容入口，业务权威统一迁移到 v1.4.18 / v1.4.21 定义的规则服务和语义化工期出口。

### 2.5 多公司空间与数据隔离统一口径

v1.4.23 作为总集成章节，必须把 v1.4.20 的多公司空间口径作为全链路验收门禁：

```text
所有项目级数据必须先归属 project_id，再通过 projects.company_id 解析当前公司
所有公司级汇总必须先限定 currentCompanyId / company_id，再按用户可见项目集合聚合
普通 company regular 未加入项目时，只能看到 company_visible 项目的基础目录卡片，不得进入项目业务详情接口
当前公司 company_admin 可按 owner 等效管理当前公司项目，但不得跨公司访问、汇总或写入
工作台、公司驾驶舱、Dashboard、Reports、通知、成员、责任单位、材料、验收、风险问题、健康度、指标快照必须随当前公司切换刷新
演示项目和只读产品预览不得写入真实公司项目、指标快照、通知、经验工期或健康度统计
旧无 company_id 数据只能迁入默认公司或进入治理待校准，不得在多公司模式下作为全局共享业务数据
```

总集成验收时，任何一个页面或后端服务只按前端隐藏过滤、未按公司空间过滤 SQL / 服务查询，都视为 v1.4 未闭环。

2026-05-16 真实库隔离修复已纳入总集成验收：

```text
真实库必须已执行 137_company_workspace_isolation.sql、138_add_notifications_company_scope.sql、139_add_wbs_template_company_scope.sql。
真实库中 projects 必须具备 company_id，且现有项目必须归入公司空间。
真实库中 companies / company_members 必须存在，能够校验公司成员到项目成员的边界。
notifications / operation_logs 中引用不存在 project_id 的历史记录必须解除外键式业务引用，并把旧 ID 留存在 metadata / detail。
notifications 中引用不存在 task_id 的历史记录必须解除业务引用，并把旧 ID 留存在 metadata。
wbs_templates 必须同时具备 project_id / company_id / catalog_scope；项目模板按 projects.company_id 回填，公司模板按 company_id 隔离，系统公共模板保持只读复用。
真实库临时回归种子必须可创建、可验证、可清理，回归后公司 / 用户 / 项目 / 任务 / 通知 / operation_logs / wbs_templates 临时种子残留必须为 0。
代码门禁必须接入根目录 `verify:workspace-isolation:live`，CI 发布链路必须在数据库迁移后执行真实库隔离回归；有 `SUPABASE_MIGRATION_URL` 时失败即阻断部署。
```

## 4. 实施顺序

### 4.1 第一阶段：底层主数据和字典

优先实施：

```text
v1.4 工程对象主数据体系
v1.4.1 项目范围维度体系
v1.4.2 WBS 拆解标准体系
v1.4.3 施工任务标准数据模型
v1.4.4 建筑工程任务编码规则
v1.4.5 状态与生命周期字典体系
v1.4.10 责任主体体系
```

验收重点：

```text
工程对象能创建、停用、选择、兼容旧范围维度
范围维度不强制所有任务都选满，但任务必须至少有一个有效归属
WBS 行能被系统识别为分部 / 子分部 / 分项 / 工序 / 作业步骤，不硬编码层数
任务保存时能写入对象、分类、责任、状态、编码、计划事实
状态字典能覆盖任务、基线、月计划、图纸、证照、验收、风险、问题、预警、材料
责任单位必须来自 participant_units，责任人可自由文本或成员匹配
```

### 4.2 第二阶段：计划树和三层计划治理

实施：

```text
v1.4.7 项目基线 / 月度计划 / 执行任务计划治理体系
v1.4.7.1 共享计划树底座优化升级
v1.4.7.2 分部分项标准库与模板生成体系
v1.4.7.3 GanttView 共享计划树视图收口
v1.4.6 数据来源与映射关系体系
```

验收重点：

```text
项目基线、月度计划、任务列表共用共享计划树底座
任务列表是实时事实，基线和月计划是历史快照
无基线时可以从当前任务列表生成临时月度计划，但必须标记当前排期来源，不替代长期基线
保存前校核、发布前校核、确认前校核边界清晰
撤销 / 重做只作用于保存前编辑历史
保存后的撤销必须重新作为业务动作校验权限、状态、引用和留痕
复制粘贴、批量填充、批量改字段不能绕过后端校验
来源映射、拆分、合并、导入批次后台记录，不给普通用户增加链路操作
```

### 4.3 第三阶段：任务执行联动

实施：

```text
v1.4.8 任务依赖 / 开工条件 / 阻碍体系
v1.4.9 里程碑与关键节点体系
v1.4.11 图纸 / 证照 / 验收与任务联动体系
v1.4.21 材料管控与任务联动体系
```

验收重点：

```text
用户选择前置任务即可，依赖类型由系统按治理规则默认判断，非法依赖进健康横幅
阻碍不等于未准备好，必须形成独立执行影响状态
开工条件尽量自动满足，人员 / 设备 / 现场准备 / 一般协调类条件在首次进度变化时轻确认
图纸通过、证照完成、材料到场、验收要求能联动任务开工条件
验收页面创建的是验收事项，任务列表里的施工任务通过 task_id / source_ref_id 与验收事项互相引用
普通施工任务详情只弱展示影响验收名称，例如“影响消防专项验收等其他 2 个验收”
材料页不再展示 AI 到货建议，而展示系统到场建议
材料未到不自动等同阻碍，只有影响具体任务推进时才进入阻碍 / 风险 / 问题链
```

### 4.4 第四阶段：风险、通知、变更和历史保留

实施：

```text
v1.4.12 风险 / 问题 / 预警升级体系
v1.4.13 提醒通知与待办触达体系
v1.4.14 变更留痕 / 确认 / 审批边界 / 审计体系
v1.4.15 删除 / 关闭 / 归档 / 历史保留体系
```

验收重点：

```text
风险按钮收敛为“转为问题 / 关闭 / 重新打开”
问题按钮收敛为“关闭 / 重新打开”
建议关闭以数量角标、筛选项、详情弱提示呈现，不做弹窗轰炸
预警链必须承接业务流程优化清单中的预警升级精神
通知只触达需要用户知道或处理的事项，不把后端治理链暴露给用户
确认只用于会改变业务事实且容易误操作的动作
```

### 9.8 数据质量、指标、健康度

```text

```

计划治理与数据质量闭环按一条链路收口，不再新增平行算法：

```text
数据质量发现 -> 计划域转译 -> 计划完整性 -> 计划健康 -> 发布/确认挡墙 -> 偏差归因解释
```

总集成要求：

1. 数据质量发现只提供问题、严重度、建议和可信度；进入计划发布、确认、保存前必须先转译为计划域信号。
2. 计划治理快照使用 `governanceSignals` 统一承接既有算法输出，字段为 `sourceAlgorithm / gateLevel / targetSurface / evidence / recommendation`。
3. `block_save` 只给明确影响承诺锚点、父子计划汇总、M1-M9 完整性或发布确认合法性的硬问题；`confirm` 用于需要负责人确认的血缘、重整、被动重排、关键异常和约束绑定问题；`hint/explain` 用于健康下降、预测、节奏候选和偏差归因说明。
4. 共享计划树编辑态已有的行级校验和健康横幅继续保留，不把所有数据质量诊断重复塞进健康横幅；健康横幅只展示可定位、可处理、和当前编辑动作相关的问题。
5. 偏差归因只解释“为什么健康下降 / 为什么计划兑现变差”，不直接作为确认前硬阻断；只有其底层事实被计划域转译为硬问题时才影响挡墙。

2026-05-26 增量接入口径：

1. `governanceSignals` 已补齐剩余既有算法来源的统一转译入口：`wbs_plan_rollup / planning_revision_pool / progress_anomaly / task_constraint / task_condition_linkage / drawing_package / pre_milestone / acceptance_flow / progress_deviation / project_schedule_state / duration_context / task_duration_forecast / construction_rhythm`。
2. 计划治理快照只低成本读取已持久化事实：`pending_realign` 基线/月计划、`task_constraint_snapshots`、进度快照异常、`project_schedule_states`、当前 `task_duration_forecasts`；不在治理扫描中重跑图纸、证照、验收、偏差归因、节奏候选等重业务算法。
3. 挡墙分级保持收口：WBS 父子汇总错误可 `block_save`；基线重整、关键进度异常、绑定到任务的约束/图纸/证照/验收前置只进入 `confirm / hint`；偏差归因、排期状态、工期预测、节奏候选只进入 `explain / hint`，不直接阻断发布或确认。
4. 前端展示保持不动；共享计划树编辑态行级校验与现有健康横幅继续负责可定位问题，治理信号作为后端门禁、确认和解释层的统一上下文。

2026-05-26 算法本身口径加固：

1. 计划完整性检查的执行类分母只统计可执行任务，WBS 汇总行、非承载行、仅记录/仅里程碑节点不再放大缺责任主体、缺范围维度、缺进度快照等执行类问题。
2. 进度快照完整性和 stale 判断按每个可执行任务的最新快照口径计算，历史旧快照不会在已有新快照的任务上继续制造 stale 诊断。
3. 发布/确认前治理新增统一挡墙 helper：`block_save` 才阻断；`confirm` 进入负责人确认项；`hint/explain` 只作为上下文。当前前端展示和发布/确认交互保持不变。

2026-06-13 工期体系总集成收口：

1. 工期体系验收按三层检查：事实型 span helper（`inclusiveDurationDays` / `constructionCalendar`）、五个推断引擎（`durationSuggestionService` / `taskDurationForecastService` / `projectCriticalPathService` / `projectRemainingDurationForecastService` / `scheduleAccelerationService`）、六个派生输出（父节点 rollup / 偏差 / 延期 / 完成总结 / 学习样本 / 滞后与业务状态派生）。
2. 同一任务 + 同一语义必须输出唯一值。计划工期、施工生产日、参考工期、剩余工期、关键路径工期、项目剩余工期和赶工建议不能在不同入口下各自重算。
3. 计划表只有一套日期真值。父级节点通过 `wbsPlanRollupService` 消费子级日期包络或包窗口；子工序参考工期只能解释自身合理时长，不得与父级计划窗口形成第二套计划值。
4. 新建 / 新增任务统一展示“工期智能参考”：项目未开始显示标准参考工期；项目已开始但任务未开工显示项目节奏参考工期；已开工或有进度显示执行中剩余工期预测；月计划目标进度显示“本月目标需 X 天”。
5. 服务端和客户端必须保留 raw date math 防回退契约。新增业务天数字段前必须先声明语义并接入共享 helper；裸毫秒天数只允许用于缓存 TTL、调度周期、图表 padding 或技术 cooldown。
6. 本轮收口后，`reference_duration`、`ai_duration`、旧 `/api/ai-duration`、旧 `/api/ai-schedule`、旧 AI 工期兼容对象不得作为新业务 fallback；新经验工期、参考工期、剩余工期预测都必须消费语义化服务出口。

2026-06-17 准确性结构补丁：
