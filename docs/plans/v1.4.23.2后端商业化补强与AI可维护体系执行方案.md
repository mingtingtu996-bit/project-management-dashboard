## 0. 结论口径

允许达成的目标口径：

> v1.4 系列业务闭环完成后，后端已补齐商业化产品所需的租户、运营、观测、发布、恢复、安全、契约和 AI 可维护基础。

禁止达成或宣传的口径：

> 仅凭 v1.4 业务文件完成，就直接视为商业化 SaaS 后端已完整可卖、可扩张、可托管。

本文件不是新的业务章节，不新增独立工程单元或能力面，不把 AI 作为独立产品能力重新回流。

## 1. 定位

本文件是后端执行文件，不是台账说明。

它解决的是一个更硬的问题：

1. v1.4 系列把工程业务闭环做出来。
2. 但商业产品还需要能卖、能限、能管、能恢复、能追责、能持续上线。
3. 后续系统维护主要交给 AI 时，系统本身必须足够结构化、可读、可验、可回放。

因此，本文件的目标不是再拓一层业务，而是把后端补成：

```text
业务可运行
商业可交付
运维可观测
故障可恢复
变更可回滚
规则可追溯
AI 可维护
```

## 3. 总原则

### 3.1 商业化原则

商业化后端至少要回答以下问题：

```text
谁在用
用多少
能不能限
能不能停
出问题谁知道
出问题怎么恢复
改动怎么回滚
数据怎么导出或迁移
责任怎么追
```

### 3.2 AI 可维护原则

后续维护主要由 AI 完成时，系统必须满足：

```text
每个能力有唯一归属
每个 route/service/job 有显式登记
每个指标有统一来源
每个迁移有可回放顺序
每个废止对象有回归扫描
每个高风险规则有门禁
每个变更有测试和回滚
```

AI 维护不是“让模型记住更多东西”，而是“让系统自己把边界说清楚”。

### 3.3 与 v1.4 业务规则治理的边界

`v1.4.23.2` 只补商业化后端与 AI 可维护底座，不重新定义工程业务算法、规则、seed、工期参数、依赖规则、关键路径规则或 v1.5 消费状态。

```text
v1.4.22 管算法 / 规则 / seed / 学习 / 发布 / 回滚的业务治理真值
v1.4.23.1 管终态原则、架构口径和解释性正文
v1.4.23.1-A 管 production-ready / needs-gating / not-ready 的当前状态索引
v1.4.23.2 管商业化平台能力、运行观测、发布恢复、安全契约和 AI 可维护 registry
```

因此，`v1.4.23.2` 新增的 route / service / job / metric / migration / deprecation / health / retention / quota 只要会影响计划、工期、关键路径、风险、指标、发布、回滚或治理结论，就必须同时进入 `v1.4.22` 的自动发现与准入链；但这些平台底座不得反向覆盖 `v1.4.22` 的算法资产总账、公司 / 项目隔离规则和 release-exit 口径。

### 3.4 单元模型（对齐 v1.4.23.1 §4.7 权威架构，不另立口径）

> **口径修正（承重）**：本节早期草稿曾自造 `business_core / governance / platform_foundation / commercial_foundation` 四类 `runtime_scope` 分组标签，并把"主执行环 + 预测桥 + 横切履约 + 验收事实子通道"全折叠进 `business_core`。这与 **v1.4.23.1 §4.7.1 已确定的权威架构冲突**——§4.7.1 明确"废止旧口径"，长期架构是**7 个单元**，不是 4 个分组标签；折叠会抹掉 C-16.1 依赖门禁要守护的关键区分（预测桥不得写 actual、验收子通道是受治理的第二写入通道、横切履约只写条件/阻碍）。本节据此改为：**v1.4.23.1 §4.7 的 7 单元是唯一架构真值；`5.4 domain_registry` 的 `runtime_scope` 只是它们的粗粒度分组标签，不替代、不重定义。**

**3.4.1 权威架构单元（来源：v1.4.23.1 §4.7.1，本文件不重定义）**

唯一长期口径是 v1.4.23.1 §4.7.1 的 7 个架构单元：

```text
主执行环（建模 → 计划编制 → 执行事实 → 描述分析 → 行动闭环；日节奏·单向·事实锁定）
学习治理环（自动发现→准入→回放→标定→发布→回滚；慢节奏·闸门控）
预测桥（只读读模型，消费执行事实+已发布学习制品，不写 actual/baseline/monthly plan）
横切履约（材料/图纸/证照，只写任务条件/阻碍/关联投影，不抢写执行事实）
验收事实子通道（经 AcceptancePass 合法写 actual 的受治理第二事实入口）
底座·组织权限（auth/company/members/invitations/workspace；租户隔离边界）
底座·平台运行观测（health/jobs/status-dictionary/realtime/中间件/安全/缓存；可靠性与运维）
```

**3.4.2 `runtime_scope` 分组标签 = 7 单元的 registry 字段（不作架构真值）**

`5.4 domain_registry` 的 `runtime_scope` 字段需要粗粒度枚举，按下表把 7 单元归组。**归组只为 registry 字段服务；依赖方向、写权限等约束一律以 7 单元为准，不以分组为准。**

| `runtime_scope` 分组标签 | 覆盖的 v1.4.23.1 §4.7 单元 | 本文件（23.2）是否新增/改动 |
|---|---|---|
| `business_core` | 主执行环（5 段）+ 预测桥 + 横切履约 + 验收事实子通道 | 否，归 v1.4 业务各章；23.2 不碰 |
| `governance` | 学习治理环 | 否，归 v1.4.22 / 22.3；23.2 不碰 |
| `platform_foundation` | 底座·平台运行观测 | **是**：观测/迁移/job runtime/错误码/API 契约补强（4.2–4.7） |
| `commercial_foundation` | 底座·组织权限的商业化延伸（租户状态机/quota/计费准入） | **是**：v1.4.23.1 §4.7.3 已写明"商业化补强进入 v1.4.23.2" |

> **关键归属事实**：v1.4.23.2 真正新建的只有两块——`platform_foundation` 与 `commercial_foundation`，二者都落在 v1.4.23.1 §4.7 的**"底座"层**，不是新环、不嵌入双环。商业化是底座的延伸，单向被双环依赖（见 3.4.3）。

**3.4.3 依赖方向以 C-16.1 为权威门禁，本文件不另造矩阵**

依赖方向的唯一权威是 **v1.4.23.1 C-16.1**（双环架构依赖方向机器门禁，覆盖主执行环/学习治理环/预测桥/横切履约/验收事实子通道/组织权限底座/平台观测底座）。本文件新增的 commercial/platform 两块必须接入 C-16.1，不重写一套矩阵。对商业化补强最关键的三条方向（均为 C-16.1 已声明方向的实例化）：

- **底座 ↛ 业务主链**：`platform_foundation` 与 `commercial_foundation` 不得反向依赖主执行环/预测桥/横切/学习环的业务语义（C-16.1 "禁止底座反向依赖业务主链"）。
- **业务主链 ↛ commercial**：主执行环等不得读 `plan_tier`/quota 改变业务结论——商业 gating 只在写入口 guard 层拦截，否则同一结论随套餐漂移、违反单一真值。
- **commercial → 计量事实为只读**：`commercial_foundation` 可只读消费主执行环的计量事实（项目数/成员数）做 quota 判定，不写、不改其口径。

> **现实债务（必须先还）**：v1.4.23.1 **C-17.45** 已记账"依赖方向单向无任何门禁，且已被违反，service 反向 import 10+ routes"；C-16.1 自身标注"完成前，§4.7.2 的'禁止依赖/主链单向'不得作为已兑现约束"。因此 commercial/platform 的"单向被依赖"在 C-16.1 门禁落地、C-17.45 存量违规清零前**不是已兑现的保证**。`v1.4.23.2-A` 的依赖扫描器即 C-16.1 门禁的实现载体，须先关闭 C-17.45。

**3.4.4 每单元契约（单元对外保证什么 = CI 可验证的断言）**

契约挂在 7 单元上（不挂在分组标签上）。与商业化补强直接相关的：

```text
主执行环·描述分析（business_core 分组标签）契约：
  - 被 v1.5 当主结论/主指标/动作入口消费的能力，须在 v1.4.23.1-A 的 C-13 活表中有 production-ready 标注（否则 display-only）
  - 指标只从 metricRegistry 出，不在 route handler 散算（已有 guard:route-aggregation；C-05 要求扩面）
  - = 把 v1.4.23.1-A C-13 活表变成 domain_registry.production_readiness_source 机读字段
预测桥契约：只读建议，不得写 actual/baseline/monthly plan（C-16.1 方向 + §4.7.2 第3条）
验收事实子通道契约：仅经 AcceptancePass 合法写 actual，带权限/审计/幂等/回滚（对应 C-17.35~37、C-18.L08）
底座·商业化（commercial_foundation 分组标签）契约：
  - 所有项目级写入口必须经商业状态 + quota guard（7.3 发布阻断门禁）
  - 计价主轴 = active project；免费钩子白名单不得被 gate（4.1 / 6.2）
  - 商业状态变更必有审计证据（6.2 执行项 5）
底座·平台运行观测（platform_foundation 分组标签）契约：
  - /api/health 区分 live/ready/degraded/maintenance；ready 检查 DB/迁移/核心 job（6.3）
  - 每个 job 有 idempotency/lock/retry/失败终态/run log（6.3）
  - 生产迁移不得静默 skipped（7.3；落地见 v1.4.23.2-C）
学习治理环契约：边界沿用 v1.4.22 / 22.3，23.2 不重定义；新增对象回填自动发现准入链（3.3 / 7.4）
```

每条契约挂一个 CI 校验（覆盖检查/扫描/contract test），校验脚本归 `底座·平台运行观测`。

**3.4.5 registry 必须代码生成，禁止人工副本**

`5.4` 的 registry 是 AI 维护的地图。地图与代码漂移比没有地图更危险。硬规则：

- route_registry 从 `server/src/index.ts` 抽取；job_registry 从 `server/src/scheduler.ts` 与 `server/src/jobs` 抽取；metric_registry 从 `metricRegistryService` 抽取；migration_registry 从 `server/migrations` 抽取（输入源同 6.1）。
- registry 是**生成产物 + CI 校验**，不是人手维护的表；unknown-route/service/job 扫描：代码有 registry 无 → 阻断；registry 有代码无 → 标 deprecated。
- 单元归属（每个成员属 3.4.1 哪个单元）可人工在 registry 旁声明，但"成员存在与否"必须来自代码扫描。这与 v1.4.23.1 **C-16.2**（存量 route 归位扫描，以 `server/src/index.ts` 为输入比对 §4.7.1 归属清单）是同一件事，不另起一套。

> **执行序含义**：3.4.5 的"系统清单化 + 单元归属"是 6.1 第一阶段的具体化，且**先于**一切商业化补强——不先把现存 route/service 扫出来归位（C-16.2）、不先把反向依赖清零（C-16.1 / C-17.45），commercial 的 quota guard 选址和 platform 契约校验都无可靠对象。先有地图、先修单向，再设卡。

## 4. 商业化差距清单

### 4.1 租户商业运营能力面

| 缺口 | 说明 | 补法 | 优先级 |
|---|---|---|---|
| 租户权益 | 需要套餐、席位、配额、到期、停用、续费、升级边界 | 补表、补服务、补管理接口、补门禁 | P0 |
| 组织授权 | 需要公司 / 项目 / 成员 / 角色 / 权限的商业化隔离 | 统一授权模型与后台校验 | P0 |
| 用量控制 | 需要项目数、成员数、存储、导出、任务量、调用量上限 | 增加 quota 与超限拦截 | P0 |
| 商业状态 | 需要 trial / active / suspended / expired / archived | 统一状态机与审计链 | P1 |

> **计价主轴口径（承接 v1.5 定位结论，承重）**：上表 quota 维度平铺，未指明计价主轴。硬口径——**计价单位 = active project（与价值单位一致）；席位 / 存储 / 导出 / 调用量作为配额上限，不作计价轴。严禁 per-seat 计价**：按席位收费会诱导客户砍人省钱 → 现场录入的人变少 → 喂不饱"少录多得"的推导引擎，亲手装上反向激励。集团档可按"项目数 × N 或组合套餐"伸缩，仍以项目为主轴。

> **总开关 + 全程计量口径（承重，落地"先免费、后启用"）**：本产品上线初期免费，待用户量起来再启用收费。但"先免费"**不等于"先不做付费功能"**，正确形态是三件事同时成立——
> 1. **功能全建**：租户状态机、quota、付费档、收款闭环（4.9）全部建齐，不分期、不留半成品。
> 2. **拦截默认关**：一个全局开关 `billing_enabled`（公司级可覆盖），默认 `false`。关闭时**所有公司视同最高档、不撞任何 quota/付费墙、不被暂停**；启用只需改开关，无需再开发。
> 3. **计量从第一天全程记**：无论开关开关，每个公司的开通时间、active 项目数、用量必须从注册第一天就持续记录。**这是"先免费、后收费"不留历史债的前提**——将来启用收费时，能凭真实历史界定老用户、免费期起算点、各公司当前用量，不必事后追溯（追溯会很难看且不可靠）。
>
> 一句话：**功能全建、计量全程记、拦截开关默认关。** 满足"有相应功能但上线不立即收费"，同时不欠历史数据债。

#### 4.1.1 付费模式（已定型，替换早期"留白"）

> 计价主轴 = active project（4.1 已立）；向获益者（老板/操盘者）收，**不向录入者收，人数永远不计价**（按人头收会诱导砍现场录入员 → 饿死"少录多得"引擎）。下面四档与二维付费墙已与用户逐条确认。

**四档结构**

| 档 | 活跃项目数 | 价格 | 录入人数 | 目标客户 |
|---|---|---|---|---|
| 免费 | 1 | ¥0 | 不限 | 自助试用者、分包老板试水（获客钩子） |
| 入门 | 2（总数，非增量） | ¥49/月 | 不限 | 自费的单项目操盘者 / 分包老板 |
| 专业 | 5 | ¥149/月 | 不限 | 管 3–5 个工地的老板 |
| 集团 | 不限 / 按包 | 待定 | 不限 | 以后做，本版不碰 |

> 入门档维持 2 个项目（非 3）的理由：让"管 3 个工地"的主力客群自然被推向专业档；给 3 会削平升级阶梯、把该升专业的人焊死在 ¥49。

**二维付费墙（项目数 × 价值层；核心日常回路永不设墙）**

铁律：**建模→生成计划→录进展→看健康**这条获客钩子链路在所有档完整、永不设墙。墙只卡"决策深度"和"规模"。

|---|---|---|---|
| 核心回路 Gantt建模/Baseline生成/MonthlyPlan录入 | ✅完整 | ✅ | ✅ |
| 现状统计 Dashboard/健康分/Milestones | ✅完整 | ✅ | ✅ |

**卖点口径（与真实能力对齐，禁止虚标——本轮核查结论）**

- 偏差归因专业档卖点措辞 = **"量化影响分解 + 浮时公平问责 + 上游追溯"**，**禁止写"AI 因果归因"**——因果归因要等 v1.6 第3级回测撑腰。当前能讲的是"延期 N 天的影响分解 + 用浮时区分'有余地还拖'vs'被关键路径逼到墙角'"。
- 未来预测卖点措辞 = **"智能预测参考 + 置信度"**，**禁止写"准确率/精确到天"**——四引擎当前零回测（`no_accuracy_samples`）。
- 责任绩效措辞 = 升级后可讲"浮时公平判定"，仍**不写"自动问责定责"**直到第2级上游追溯落地。
- 对外导出/业主月报 = 已补后端真 PDF/Excel/月报导出；付费墙卖点可以写"可下载报表/业主月报"，但不写"自动生成盖章版正式公文"或"批量归档交付"。

**降级规则**：不续费从高档掉回低档/免费时，**超额的活跃项目转只读（可看、可导出已有数据，不可再录入/编辑），数据绝不删**，续费即恢复。与 D 文件"欠费只锁不删"同原则。

**活跃项目定义**：只算"进行中"项目；归档/完结项目**不占额度、数据保留**。避免老板因"干完一个被扣一个名额"而删数据腾坑。

**老用户宽限**：启用收费（`billing_enabled` 翻 true）时，已注册老用户给宽限——按 `onboarded_at` 识别，给一段宽限期或保留高于新用户的免费额度（奖励早期用户）。具体宽限长度待启用前定，但识别字段（`onboarded_at`）从上线第一天就记（见 4.1 计量口径）。

**数字校准**：免费 1 / 入门 ¥49×2 / 专业 ¥149×5 为已定锚点；集团档、各档具体上限随真实用户付费意愿数据再校准，但**计价主轴=项目、不计人头、核心回路免费**三条结构不变。

### 4.10 跨公司匿名工期学习飞轮（明确移交未来版本，不在本版范围）

> 本节是**登记，不是执行项**。记录原因：避免后续误以为"免费数据喂引擎"的飞轮已具备或只差接通。

**核查结论（本轮代码核实，纠正"只是接通"的误判）**：跨公司匿名学习的**读取端已建**（基线表/类型/runtime 读取钩子/`publishedOnlyRuntimeConsumption` 护栏），但**生产端为零**——把 N 个公司完工工期聚合成匿名行业 P50 的代码不存在：无跨公司聚合 SQL、无 k-匿名强制、无数据质量闸、无基线生成 job。系统自身 requirement 审计已把它标为**缺口**而非已完成能力。核查估算净新建 **~1600–2400 行**聚合/治理/隐私逻辑。

**为什么移交未来版本（两条硬理由，非排期偏好）**：
1. **是建造不是接通**：生产端净新建上千行，且涉及多公司数据聚合（隐私敏感，错即合规事故），放进本版会撑爆"上百用户够用"的上线范围。
2. **冷启动期物理上空转**：跨公司匿名聚合要求每工序段 ≥ 最小公司数（k-匿名）。上线初期用户少且分散，任何工序段都凑不齐门槛 → 此功能在最需要它的早期必然无原料、空转。它天生属于"规模起来之后"。

**前置条件（触发才立项，不设固定排期）**：累积公司/项目基数达到 k-匿名最小聚合门槛（每细分段 ≥ 最小公司数、单公司占比 ≤ 上限）。这与"先免费攒用户"策略串联——免费期攒的不是当下喂得进的飞轮燃料（现在喂不进），而是**将来够得着 k-匿名门槛的公司基数**。

**与当前商业设计的关系**：当前付费设计与免费档**不依赖**此飞轮。免费档当前理由 = 获客 + 口碑传播 + 制造老板转移成本（详见 v1.5 与 4.1）；"免费数据越用越准"在飞轮接通前**不作为卖点、不写入对外文案**。届时立项的专项范围 = 聚合管道 + k-匿名强制 + 数据质量闸 + publish 闸 + runtime 优先级（fallback 层级）。

## 6. 实施顺序

> **冷启动重排口径（承重，反"上线前先建完整托管平台"）**：第 4 节 8 个能力面的 P0 合起来是一个"可托管 SaaS 平台"的完整后端底座，数月工程量。但本产品 GTM 是线上冷启动、先攒少量用户验证付费意愿。**若把 8 个能力面的 P0 一次啃完再上线，等于在还没验证有人付费之前就建好托管平台——又一次大爆炸。** 因此按"先验证收入、再建托管底座"重排，而非按能力面平铺并行：
> - **第 0 步（A 首段 registry 骨架落地后，先于 B/C/D 主体执行）= 收入验证最小集**：只做 [4.1 租户商业运营能力面] 的 active project quota guard + 状态机 + 升级提示 + 免费钩子白名单（见 6.2 执行项 6、7），收款走人工。目标：能区分 free/paid、能 enforce 项目数上限、能验证转化率。**这是"能不能收费"的全部，不依赖其余 7 个能力面。**
> - **其余 P0（备份恢复演练、step-up、迁移强阻断、schema drift、registry SSOT、告警、错误码、幂等）= "有规模用户后才致命"的托管底座**：排在"已验证有人付费"之后，按真实用户规模和事故风险逐步补，不阻塞收入验证上线。
> - 例外：直接危及数据安全的少数项（如生产迁移静默 skipped、高危删除无审计）即使在收入验证期也应有最低保护，但同样不必首日做到豪华版。
> 下面 6.1–6.4 是底座**做全**时的工程化分层顺序，正确；但冷启动落地时按上面"收入验证最小集先行"切入，不必等系统清单化全量完成才动租户/quota。

### 6.1 第一阶段：系统清单化

目标：

```text
先把系统边界、单元、route、service、job、metric、migration、deprecation 全部显式登记
```

验收：

```text
AI 可以仅靠 registry 找到责任边界
新增能力不会落入“隐式存在”
废止能力不会在新写入链路中复活
```

执行项：

```text
1. 以 server/src/index.ts 为 route_registry 初始输入，覆盖所有 app.use / app.get 注册入口。
2. 以 server/src/scheduler.ts 与 server/src/jobs 为 job_registry 初始输入，覆盖定时、手动、API 触发任务。
3. 以 metricRegistryService / analytics/metricRegistry 为 metric_registry 初始输入。
4. 以 server/migrations 与 CLEAN_MIGRATION_V4.sql 为 migration_registry 初始输入。
5. 以 v1.4.23.1 C-16 / C-16.1 / C-16.2 / C-17 / C-18 为单元归属和禁止回流初始门禁。
6. unknown route / service / job 扫描必须进入 CI；新增入口没有单元归属时阻断。
```

### 6.2 第二阶段：商业化底座

目标：

```text
补租户、权益、quota、后台运维、错误码、幂等、迁移阻断
```

验收：

```text
可以卖、可以限、可以停、可以追、可以回滚
```

执行项：

```text
1. 新增商业租户状态机：trial / active / suspended / expired / archived。
2. 新增套餐 / 权益 / 席位 / 项目数 / 成员数 / 存储 / 导出 / API 调用量 quota。
3. 所有写接口在业务权限之后增加商业状态与 quota guard；只读降级策略必须显式。
4. 公司停用 / 到期 / 超限必须可审计、可恢复、可解释，不得只靠前端隐藏入口。
5. 商业状态变更必须写 operation_logs / change_logs 或专门 audit table，并具备管理员动作证据。
6. 免费钩子白名单（承重，自助漏斗顶端不得关死）：免费档必须放行"1 个 active 项目的完整建模 → 生成计划 → 录进展"闭环——这是"少录多得"护城河的体验钩子，quota guard 不得 gate 掉它。付费墙卡在"随认真使用而增长的东西"：第 2 个及以上 active 项目、历史留存超期、导出 / 业主月报、多项目看板（CompanyCockpit）。即"用得越深越付费"，与产品"深度随操盘规模显形"同一条线。
7. 收款自动化可延后（冷启动期口径）：本阶段先做"状态机 + quota guard + 升级提示 + 订单/支付事件/人工开通留痕"，收款先走人工开通（转账后手动改 tier）即可上线验证付费意愿；支付网关（微信支付 / 支付宝）官方签名 webhook 和自动对账是其后的事，不是上线收费验证的前置。先回答"有没有人愿意付费"，再回答"怎么自动收钱"。
```

### 6.3 第三阶段：生产运行闭环


验收：

```text
出问题可定位
出事故可恢复
出发布可追踪
```

- 后端新增 `projectReportExportService`：以 `projectExecutionSummaryService` 为项目摘要入口，按当前基线读取 `progressDeviationService.responsibility_contribution / cause_chain / top_deviation_causes`，生成报表概览、偏差与归责、偏差明细、原因链证据、关键节点、风险问题。
- 后端路由新增 `GET /api/projects/:projectId/reports/export?format=pdf|xlsx&view=progress|progress_deviation|risk`，返回当前报表视图 attachment；新增 `GET /api/projects/:projectId/reports/owner-monthly?format=pdf|xlsx&period=YYYY-MM`，返回业主月报 attachment。
- XLSX 由后端 `@e965/xlsx` 生成真实 workbook；PDF 由后端 Playwright Chromium 渲染 HTML 报告，响应设置 `Content-Type`、`Content-Disposition`、`Content-Length`，不再用 JSON 伪导出或前端 `window.print()` 代替。
- 前端 `Reports` 导出菜单已接后端下载链：`导出 Excel`、`导出 PDF`、`业主月报 Excel`、`业主月报 PDF`；失败走 toast，文件名优先使用后端 attachment header。
- 依赖与 CI：`server/package.json` 显式声明 `@e965/xlsx` 与 `playwright`；`server/package-lock.json` 和 root `package-lock.json` 对齐；deploy `server-quality` 在全量 server tests 前安装 Playwright Chromium，避免干净 runner 上 PDF 测试缺浏览器。
- 边界：当前落地的是单项目当前视图和单月业主月报下载；批量归档、盖章流转、正式公文套版、水印/付费墙拦截策略仍属于后续商业化策略或 v1.6 增强，不在本第 10 项内虚标。
- 验证：`projectReportExportService.test.ts` 覆盖真实 XLSX magic bytes/sheet 内容、真实 PDF `%PDF-` buffer、非法格式拒绝；`reportsRoutes.test.ts` 覆盖 attachment header、二进制 body、非法 `json` 拒绝；`Reports.test.tsx` 覆盖前端菜单调用后端接口且不再使用前端 print/XLSX。

### 9.3 移交 v1.6（规模起来再做，本版不做）

整体推迟到 v1.6，**上百用户阶段不影响正常使用**：

| 项 | 属哪个能力面 | 为什么可推迟 |
|---|---|---|
| 运行指标 / 告警 | 4.2 | 用户量小，肉眼+日志够用；告警是给"看不过来"准备的 |
| 分层健康探针（live/ready/degraded） | 4.2 | 现 `/api/health` 单态 + deploy 探活，上百用户够用 |
| job_run 全量持久化 + 幂等键 + 手动重放 | 4.3 / 4.7 | 现有失败重试 + job_failures 够用；幂等是"重试/补跑变多"才痛 |
| 灾备 / 恢复演练 / 租户导出 / 保留期 | 4.5 | 接重要付费客户、有不可赔数据前补；本版人工备份兜底 |
| 重输密码 step-up / 密钥轮换 / 上传扫描 / 依赖扫描 | 4.6 | 弹窗确认 + 基础隔离已覆盖上百用户；这些是 at_scale 加固 |
| contract_test / runbook registry | 4.8 | AI 维护闭环的加固层，registry 主体已在 A |
| 接口版本 / 分页硬上限 | 4.7 | 大查询/版本演进是规模问题 |

> **诚实声明**：移交 v1.6 不等于"不重要"，而是"上百用户阶段不做不会出事、且做了用户也感知不到"。其中灾备一项有个硬提醒——**本版用人工备份兜底，但一旦接入有不可赔数据的重要客户，灾备就从 v1.6 提前为必做**，这是唯一一条"可能因客户性质提前"的项，需运营者留意。其余按版本走，不设触发判断。
