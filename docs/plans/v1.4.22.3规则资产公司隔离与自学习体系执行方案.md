## 0. 2026-06-01 final range-tree boundary (authoritative)

This v1.4-series plan follows the final range-tree model. There is no production history or existing user data that needs a compatibility layer. This means no legacy runtime compatibility layer is required for production user data; it does not remove the need to archive, audit, re-scope, or re-admit historical candidates and old rule assets through the governance process below.

执行时不得把 “no production history” 理解为可以跳过旧候选、旧规则资产、旧字段、旧 adapter 的审计和隔离；它只表示不需要为生产用户数据保留旧范围对象运行期兼容链路。

Authoritative engineering object types are exactly: `phase / section / building / basement / floor / physical_zone / functional_area`.

The following compatibility surfaces are deleted and must not be reintroduced in runtime code, migrations, or frontend contracts:

- `zone / professional / subproject / custom` as engineering object types.
- `zone_object_id / professional_object_id` task fields.
- `project_materials.professional_object_id` and `engineering_categories.professional_object_id`.
- `legacy_object_type`, deprecated object-type arrays, legacy bridge/backfill helpers, and old scope adapter functions.
- `/api/scope-dimensions`, `scope_dimensions`, and `project_scope_dimensions` as active application surfaces.

Professional/system/domain/method semantics remain business facts through `specialty_type`, `engineering_category_id`, `standard_work_code`, template metadata, and project profile facts. They are not range-tree objects.

Any older section in this document that mentions deleted object types, deleted fields, old scope tables, or compatibility adapters is superseded by this boundary.

1. 这里的顺序是解释 / 校验顺序，不是实施顺序：先应用本文件 `0. 2026-06-01 final range-tree boundary` 排除旧范围对象运行期兼容，再对照 `v1.4.22` 主台账和当前代码 diagnostics；实施上仍以 `v1.4.22` 为父底座，本章不得反向覆盖 `v1.4.22` 的登记、准入、审计、回放和回滚底座。

## 0.2 机器执行硬判定表

当执行者是大模型、自动化脚本或代码生成器时，必须先用下表判定动作，不允许只根据自然语言愿景、服务名或本地状态名推断权限：

| 发现情况 | 唯一允许动作 | 禁止动作 |
|---|---|---|
| 缺 `learning_target / learning_maturity / publish_anchor / automation_maturity` 任一字段 | 生成登记草案、候选事件、reviewItems 或 blockers | 写 runtime、写 published、写 override |
| 本地状态包含 `candidate_only / confidence_only / recognition_only / planned_candidate` | 保留为候选、证据或影子对照 | 当成发布许可、可发布版本或 runtime 生效结果 |

| 既有 seed / 算法 / 专项服务自带“自学习 / 自更新 / 自发布”逻辑或状态名 | 先冻结为本地能力事实，按资产实例补齐四元字段、作用域、冲突、replay、writer、消费者、监控和 rollback target；缺证据时只产出候选事件、治理包或锚点升级申请 | 把服务内部 `auto_* / self_publish / published` 状态直接当成统一发布结果、发布权或 runtime 写入许可 |
| 命中 `manual_* / no_unattended_runtime_auto_publish / candidate_only_until_manual_*` | 生成自动化解锁证据、更多验证需求和锚点升级申请；现有锚点保持不变 | 单次 replay 后直接改成 `auto_publish` |
| 产品目标要求“尽量自动化”，但当前资产锚点仍是 `manual_* / manual_required` | 自动化搜证、自动回放、自动冲突归类、自动生成治理包、自动生成 `automation_unlock_criteria` 和版本化锚点升级候选 | 以产品目标覆盖当前硬锚点、跳过平台异常仲裁、直接把候选发布到 runtime |

| 系统级候选通过多项目 / 多公司 / 多场景验证，但缺系统级发布策略或影响面监控 | 生成系统级发布建议或平台异常仲裁请求 | 写 `system_published` 或改系统 seed |

## 1. 目标

本章承接 `v1.4.22` 的统一口径治理底座，继续向下解决三件事：

1. 规则、seed、算法、模板与校准结果如何按公司空间隔离
2. 不同公司的资产如何独立自学习、独立晋升、独立回滚
3. 资产治理如何形成统一台账、统一证据链、统一冲突处理和统一审计

本章不新增面向普通用户的“算法中心”页面，也不把技术字段暴露到业务页。普通用户仍然只看业务结果、业务原因和必要提示；资产治理仅面向后台或高权限治理入口。

## 2. 与前序章节关系

```text
v1.4.22  ：统一算法 / 规则 / seed / 模板口径治理底座
v1.4.22.1：项目快速建模与起跑线接入，消费治理口径
```

核心边界：

- `v1.4.22` 负责“登记什么、怎么命名、怎么解释”
- `v1.4.22.1` 负责“项目建模场景怎么消费”
- `v1.4.22.2` 负责“前期证照怎么从系统模板生成可确认、可裁剪、可幂等应用的办理骨架”
- `v1.4.22.3` 负责“不同公司怎么各自生长、各自隔离、各自回滚”
- `v1.4.22.4` 负责“发布后是否真的更准、误差是否下降、过度补偿是否受控”
- `v1.4.23` 负责“最终是否闭环可验收”

不重复原则：

- 本章不重新维护 `v1.4.22` 的算法、规则、Seed 总账，不覆盖 `v1.4.22` 的自动发现、资产登记、准入门禁、版本、输入输出、审计、回放和回滚底座。
- 本章只定义公司级 / 项目级资产的作用域隔离、自学习状态机、发布锚点、自动化成熟度、冲突仲裁、回放、灰度、回滚与验收门禁。
- 本章引用的资产数量、算法数量、Seed 类型数量和自动发现结果仅作为当前执行证据；长期真值仍以 `v1.4.22` 主台账、`algorithmRuleAssetInventoryService` diagnostics、`algorithmSeedRegistry` 和 `v14AssetAdmissionAutomationService` 自动发现报告为准。
- 本章不负责证明“工期数字已经更准”。release-exit、publish_anchor、automation_maturity、rollback target 和治理 dashboard 只能证明升级动作具备安全、隔离、审计和回滚条件；是否真的更准，必须由 v1.4.22.4 的 prediction event、actual outcome、MAE / Bias / overcompensation、coverage 和 runtime consumption 证据证明。
- 本章可以阻断事实层被学习改写，但不能把阻断事实改写本身包装成精度提升。actual、baseline、monthly plan、已确认依赖、关键路径事实和进度快照仍由各自业务写入链管理，只能作为学习证据输入。

代码边界契约：`durationPrecisionGovernanceBoundaryService.ts` 将 `register_asset / evaluate_release_gate / publish_runtime_parameter / rollback_runtime_parameter / block_fact_rewrite` 固定归属 v1.4.22.3 governance control，将 `record_prediction_event / record_actual_outcome / calculate_accuracy_metrics / produce_precision_candidate / consume_published_runtime_overlay / claim_accuracy_improved` 固定归属 v1.4.22.4 precision learning，并将 `auto_rewrite_fact` 固定归属 business fact lock。对应测试必须阻断 v1.4.22.4 绕过本章 release-exit 直接发布 runtime，也必须阻断本章在缺少 v1.4.22.4 精度指标时宣称“越用越准”。

## 4. 核心原则

### 4.1 三层作用域固定

| 层级 | 作用域 | 学习 / 治理方式 | 是否可直接影响运行 |
|---|---|---:|---:|
| `system_seed` | 系统默认 | 不接受公司 / 项目样本直接改写；只能接收平台级治理建议、回放证据和系统级自动治理包作为发布前置输入 | 只读消费；系统级写入必须另走系统级发布门禁 |
| `company_override` | 公司空间 | 可以接收公司级候选、证据和回放作为治理输入；写入必须经过统一发布出口、门禁测试、资产类型专属 writer、消费者验证和 rollback target | 仅完成发布执行链的版本可被本公司 runtime 消费 |
| `project_override` | 项目空间 | 可以接收项目级候选、证据和回放作为治理输入；写入必须经过统一发布出口、门禁测试、资产类型专属 writer、消费者验证和 rollback target | 仅完成发布执行链的版本可被本项目 runtime 消费 |

说明：

- 这里的“后端门禁”不是 OA 流程，也不是任意 service 内部布尔判断；必须能落到统一发布出口、作用域校验、冲突 / 回放门禁、发布记录和 rollback target。
- 普通编辑者不能直接发布资产。
- 公司管理员只能在本公司 / 本项目作用域内触发候选治理；后台治理任务只能按已绑定作用域触发，不能借自动任务扩大作用域。
- 候选治理结果必须留下自动治理摘要、证据和状态。
- 表格中的“可直接影响运行”只表示 runtime 可以读取已发布版本，不表示学习任务、候选事件或大模型可直接写入该层级。
- 本节的 `system_seed / company_override / project_override` 是作用域层级和读取优先级，不是所有资产类型的物理发布表名；参数、policy、模板、overlay、样本健康和冷启动基线必须走各自专属 writer 或保持候选 / 审计状态。

### 4.2 读写优先级固定

```text
project_override
> company_override
> system_seed
```

历史对象不属于运行期读写优先级。旧 seed、旧候选、旧 override 或旧工程范围对象只能进入 `legacy_audit / system_observation / re_admission` 等治理链路，作为审计、只读观察、重新定界和重新准入时的临时参考；不得恢复旧范围对象运行期兼容层，也不得把 unknown scope 历史候选当作公司 / 项目 override 消费。

读写优先级只适用于已完成对应资产类型发布链的 runtime 消费。若资产类型没有显式 runtime writer 或消费者，例如参数 publication 尚未接入具体消费者、policy 审计 run 尚未写模板实体 runtime 表、overlay 只作为误差证据，则该资产不得因为落在 `project_override / company_override / system_seed` 逻辑作用域而被运行期消费。

### 4.3 资产不能越级

- 公司学到的结果不能直接改写系统 seed
- 项目样本不能直接污染别的公司
- 候选资产默认不生效，只能进入评审、隔离或晋升流程
- 已发布资产必须版本化，不允许静默改口径

### 4.4 普通前端减负

- 不展示 `confidence`
- 不展示 `stable_code`
- 不展示 `source key`
- 不展示内部命中路径
- 不把资产治理动作混进业务页主流程

### 4.5 自动治理控制面、发布锚点与自动化成熟度

现有 seed、模板、工期、天气、WBS、证照等模块可以保留各自的候选发现、样本学习、反馈校准、质量评估和专项回放能力。统一控制面可以由现有 service、protocol、adapter、admission gate 和后台治理入口 / 汇总视图组合承载，不代表新增一个可直接发布所有资产的超级控制器，也不代表后台治理入口本身就是发布出口。它的职责不是简单把所有资产立即推向自动发布，也不是把 `manual_*` 锚点永久固化，而是分两层处理：

1. 单个候选不能绕过当前发布锚点。
2. 发布锚点本身只有在“已登记的锚点升级策略”满足证据阈值后，才能作为治理资产被版本化升级。

也就是说，人工治理锚点不是长期产品目标，也不应成为系统级晋升的默认路径；但在锚点升级策略未登记、证据阈值未满足或回滚目标不完整之前，它仍是运行期硬阻断。控制面应持续自动补齐样本、证据、冲突解释、回放、shadow、回滚目标建议和影响面监控证据需求；回滚目标建议不能被视为已经存在的可执行 rollback target。当证据显示某类资产可能达到自动化成熟度时，只能先生成锚点升级申请或成熟度升级候选。只有已登记的锚点升级策略通过门禁时，才允许版本化升级锚点；锚点升级只改变后续候选的判定规则，不追溯发布当前候选，也不能把未重新过门禁的历史候选补发到 runtime。系统级晋升的优先证据来源应是更多项目、更多公司、更多场景的自动验证；这些自动验证是发布前置证据，不是发布执行权。人工或平台异常仲裁只处理自动验证无法裁决、锚点升级策略缺失、边界扩大或合规安全等情况。

执行落点必须拆成两条链：候选治理链可以自动运行到发现、证据、回放、冲突、shadow、canary 建议和锚点升级申请；发布执行链只有在发布出口、锚点、成熟度、门禁测试、资产类型专属 writer、消费者验证、影响面监控和 rollback target 同时存在时才启动。缺少发布执行链时，任何候选治理链的 pass 结果都不得写成 `published / auto_published / system_published`，也不得写入 project override、company override、system seed 或同等级 runtime 表。

统一规则：

- 业务算法可以自产候选，但不能自己决定是否发布、发布到哪里、是否绕过治理锚点。
- 专项服务可以自产 replay / quality / calibration 证据，但必须交给统一治理协议 / 控制面做锚点校验和冲突仲裁。
- `manual_governance_required / manual_review_required_before_publish / manual_runtime_promotion_required / no_unattended_runtime_auto_publish / manual_review_only / candidate_only_until_manual_*` 是当前强锚点；单个候选不得绕过，控制面只能为它们生成自动化解锁证据、更多验证需求和迁移建议。迁移建议不是发布许可，也不是锚点升级结果；必须再经过锚点升级策略或平台异常仲裁，且升级后只影响后续判定，候选仍需按新锚点重新通过发布门禁。
- `candidate_only / confidence_only / recognition_only / planned_candidate` 等本地状态默认不进入运行期；只有资产声明允许自动发布、发布执行链完整且门禁通过，才可由统一发布出口写入 published 版本。
- runtime 只消费已经由统一发布出口和资产类型专属 writer 写入的 `project_override / company_override / system_seed`、参数 publication、模板 runtime projection 或同等级 published asset 版本；候选状态机中的 `published` 字样若没有发布出口、writer、消费者验证和回滚证据，只能视为命名遗留或待核查治理结果。
- 对证照 / 验收模板 policy，`stable run` 只表示对应 domain release record 已被审计记录且具备交给模板实体 runtime writer 的资格；业务预览只能消费 `policy_template_entity_runtime_publications.runtime_publication_status=runtime_stable_published` 的未回滚投影，不能 fallback 到审计 run、进程内 latest run 或本地 `auto_published` 状态。它不等于模板 seed、系统 seed、其他模板实体、可学习参数或业务事实都获得自动发布权。
- 对可学习参数，`published / canary` 只表示参数 publication 的消费状态；消费者必须逐项登记并只读接入，不能反向改 seed、改业务事实或扩大到未登记参数。
- 各模块自己的自动升级逻辑不能绕过公司隔离、冲突检测、回放门禁和版本回滚。

发布锚点类型：

| `publish_anchor` | 含义 | 可消费范围 | 控制面处理 |
|---|---|---|---|
| `candidate_only` | 只能产生候选、证据、解释或隔离建议 | 后台治理 | 禁止发布，保留证据 |
| `manual_governance_required` | 当前成熟度下不得无人值守发布，例如高风险算法、关键路径、强约束依赖、需异常仲裁的规则 | 后台治理队列 | 自动生成治理包和更多验证需求，不自动发布；满足已登记锚点升级策略后，也只能先形成锚点升级或迁移候选，后续发布仍需重新通过对应自动发布门禁 |
| `trusted_source_auto_publish` | 官方政策源、证照 / 验收模板可信来源刷新 | 登记作用域 | 来源健康、弱来源阻断、保留上一 published 版本；仅由统一发布出口和对应资产类型 writer 写 published 版本、发布记录与可验证回滚目标 |
| `guarded_runtime_auto_publish` | 已声明可自动运行发布的低风险因子、基线校准、受控公司 / 项目 override | 项目 / 公司 | shadow / replay 通过、过度补偿监控、可回滚；仅由统一发布出口和对应资产类型 writer 写入，runtime 只消费已通过消费者验证的 published 版本 |
| `system_curated_publish` | 系统 seed、集团级共识、跨公司通用规则 | 全局 | 平台级验证与发布门禁；公司自学习通道不得直接发布到系统级，多项目 / 多公司 / 多场景验证成熟后，只能形成系统级发布建议；只有系统级发布策略明确允许无人值守、成熟度门禁、影响面监控和回滚目标全部通过后，才允许平台级自动发布机制写入系统 published 版本；否则进入平台异常仲裁 |

自动化成熟度：

| `automation_maturity` | 含义 | 控制面动作 |
|---|---|---|
| `manual_required` | 当前不得自动发布 | 自动生成治理包、补证据、补 replay、补更多验证需求，不发布 |
| `auto_review_package` | 系统可自动给出推荐结论，但仍需确认 | 自动生成批准建议 / 驳回建议 / 回滚建议；不形成最终治理结论，不写 runtime |
| `auto_shadow` | 可自动影子运行并与当前规则对照 | 不影响 runtime，沉淀对照证据 |
| `auto_canary` | 可自动小范围灰度 | 仅在 `publish_anchor` 允许、统一发布出口存在、门禁测试通过、资产类型专属 writer 明确、canary-aware 消费者存在、流量 / 作用域边界明确、影响面监控存在且 rollback target 可执行时，在指定项目 / 公司生效，带停止条件 |
| `auto_publish` | 可自动发布 | 仅在 `publish_anchor` 允许、发布执行链完整、门禁测试通过、发布记录 / 影响面监控 / rollback target 均存在、资产类型专属 writer 明确且消费者验证通过时，写入受控 published 版本 |

因此，本章口径为：所有规则资产都必须纳入自动学习治理闭环，可以自动发现、自动评估和自动生成治理包；但“纳入自学习治理”不等于该资产参数本身可被学习改写，也不等于具备发布权或 runtime 写入权。是否能进入 live、是否能自动发布，必须同时看 `learning_maturity`、`publish_anchor` 和 `automation_maturity`，并复核 writer、消费者、监控和回滚闭环。当前不得自动发布的强锚点只能通过已登记的自动化成熟度证据和锚点升级策略逐步消解。未登记 `publish_anchor` 的资产一律按 `candidate_only` 处理，未登记 `automation_maturity` 的资产一律按 `manual_required` 起步。

机器执行判定顺序固定为：先判定资产是否在 `v1.4.22` / diagnostics / 自动发现报告中登记；再判定四元字段是否齐全；再判定作用域、冲突、replay、锚点、成熟度、writer、消费者、监控、发布记录和 rollback target；最后才允许解释自然语言中的“可自动 / 已接入 / stable / published”。任一前置证据缺失时，后续自然语言状态词全部降级为候选、证据、review 或 blocker。

落地说明：`publish_anchor` 与 `automation_maturity` 是本章用于统一多学习入口的新增协议字段，不代表当前所有表、service 或 payload 已经存在同名字段。执行时必须先把现有 `action_policy / status / auto_governance_result / runtimeActivationBoundary / updateMode / boundaryPolicy` 等口径映射到统一协议，再决定是否需要新增物理字段、view 或 candidate event adapter。

自动治理与自动发布必须拆开：

- 自动治理的目标覆盖面是所有资产的发现、登记草案、补证据、冲突检测、replay / shadow、隔离、治理包、回滚建议和自动化解锁条件；这些动作不等于修改发布锚点或写入 runtime。某类资产的 adapter、字段或回放证据未落地时，只能进入 `reviewItems / blockers / candidate_only`，不得假定已经完成全覆盖。
- 自动发布不是全资产默认能力：只有命中 `trusted_source_auto_publish` 或 `guarded_runtime_auto_publish`，且 `automation_maturity` 已达到 `auto_canary / auto_publish`，同时统一发布出口、资产类型专属 writer、门禁测试、消费者验证、影响面监控和 rollback target 均存在的资产，才能写入受控 published 版本。
- 高风险资产默认不能由单个候选直接进入 runtime，但不等于长期必须人工逐条治理；它们应先自动治理到 `auto_review_package / auto_shadow`，只有已登记锚点升级策略、canary-aware 消费者、流量 / 作用域边界、停止条件、影响面监控、资产类型专属 writer 和可执行回滚都明确后，才允许进入 `auto_canary` 候选路由；是否迁移到受控自动发布必须由锚点升级策略或平台异常仲裁另行版本化裁决，不得由大模型总结、单次 replay 或服务内部 `auto_*` 状态直接生成。
- 当前不得自动发布的资产如果未来要自动化，先自动化的是“证据生产和解锁判断”，不是直接改写发布结果；`automation_unlock_criteria` 通过后也只能生成锚点升级候选或成熟度升级候选，升级后的资产仍需按新锚点重新过发布门禁。

### 4.6 自学习成熟度与 live 边界

“具备自学习体系”不能等同于“所有参数都会实时自动变准”。本章必须把自学习拆成成熟度矩阵，执行和验收时逐项标注：

| `learning_maturity` | 含义 | runtime 影响 |
|---|---|---|
| `frozen_constant` | 专家手写常量或代码常量，当前不会从结果学习，例如固定候选权重、置信度扣分公式、乘数上限 | 只能作为待登记治理资产；不得宣称已自我升级 |
| `shadow_report_only` | 能回放、算 MAE、算 reward 或生成对照报告，但不改 runtime | 不影响业务结果，只沉淀证据和解锁条件 |
| `governed_candidate` | 能基于样本生成候选、overlay 或参数建议 | 默认不进入 runtime，必须走发布锚点和成熟度门禁 |
| `guarded_live_tuning` | 低风险、可回滚、作用域明确的项目 / 公司级参数可受控自动生效 | 只能影响新生成结果，必须有停止条件、版本和 rollback target |
| `system_curated_learning` | 多项目 / 多公司 / 多场景验证后可形成系统级默认建议或发布建议包；只有已有系统级自动发布策略的资产，才可形成平台自动发布候选包 | 不允许单公司样本直接改系统 Seed；候选包本身不写 runtime，仍需系统级发布锚点、自动化成熟度、影响面监控和回滚门禁 |

当前已确认的口径：

- `standard_work_duration` 的公司历史 benchmark 融合 P50 / P75 只能作为局部 `guarded_live_tuning` 样例：样本达到阈值后，仍需作用域隔离、门禁记录和 rollback target，才可在新任务参考工期中融合观测中位数。
- 预测误差 MAE、duration context policy learning、bandit recommendation、shadow replay 和 canary plan 当前多属于 `shadow_report_only / governed_candidate`，不得被表述为已经 live 自动改模型。
- L0 / L1 / L2 候选权重、置信度扣分、前重 / 后重乘数、现场压力阈值、冷启动样本阈值等，如未登记为可学习参数并通过门禁，默认属于 `frozen_constant` 或 `governed_candidate`。
- `learning_maturity` 只说明学习闭环能走到哪一步，不授予发布权；任何 live tuning 仍必须同时满足作用域隔离、发布锚点、自动化成熟度、冲突清零、回放通过和 rollback target。
- 自学习结论必须写明“影响 base 工期、影响预测残差 overlay、影响置信度、影响候选权重、还是只影响治理报告”，不得把不同闭环混写。

可学习参数注册表：

所有会影响算法输出的规则参数，都必须进入 `algorithm_learnable_parameter_registry` 或等价资产视图，至少登记以下字段。这里的“算法输出”不只指 `standard_work_duration` 的参考工期，还包括模板结构、模板选择、依赖顺序、计划网络、关键路径、最早开始、剩余工期、加速建议、风险预警、健康解释和候选权重等会改变工期判断的输出。执行时不得只把 base 工期纳入自学习闭环，而遗漏模板类 seed、依赖类规则和其他工期相关资产。

| 字段 | 要求 |
|---|---|
| `parameter_key` | 稳定参数键，例如 `duration.benchmark_blend_weight`、`forecast.L1.candidate_weight` |
| `owner_algorithm` | 归属算法或服务 |
| `current_value` / `default_value` | 当前值和系统默认值 |
| `learning_maturity` | frozen_constant / shadow_report_only / governed_candidate / guarded_live_tuning / system_curated_learning |
| `publish_anchor` / `automation_maturity` | 发布锚点和自动化成熟度 |
| `scope_policy` | project / company / segment_baseline / industry_baseline / system |
| `evidence_required` | 样本数、MAE 改善、方差、过度补偿率、冲突数、回放覆盖 |
| `max_delta_per_release` | 单次发布最大变化幅度 |
| `rollback_target` | 可回滚版本或默认值 |
| `risk_level` | low / medium / high |

数据自动升级边界：

- 本章执行后可自动补齐或更新的是学习与治理数据：样本摘要、候选事件、残差 overlay、参数建议、冷启动基线、样本健康、回放证据、shadow / canary 结果和 `automation_maturity` 解锁证据。`published` 版本记录只能在发布锚点与成熟度门禁通过后由发布出口写入，不能因为学习任务运行而自动生成。
- 普通业务事实不是静默升级对象：已确认任务、实际完成日期、基线、月计划、依赖关系、关键路径和业务状态不得因为学习任务在后台运行而被无提示改写；只能在生成新建议、新候选、新计划或受控 published 版本被 runtime 消费时产生影响。
- 能自动进入 runtime 的升级只限 `publish_anchor` 允许、`automation_maturity` 达到 `auto_canary / auto_publish`、作用域明确、回放通过、冲突清零且有 rollback target 的资产；否则只能停留在候选、shadow、治理包或 reviewItems。
- 模板类 seed、依赖类规则、关键路径规则和系统级默认参数即使能自动积累证据，也不得由单次学习结果直接升级为系统 published 版本；必须走多项目 / 多公司 / 多场景验证。

### 4.7 冷启动共享基线与公司隔离

公司隔离不能变成小账号长尾冻结。解决方式不是跨公司直接混训，而是新增匿名共享基线层。以下是冷启动只读参考层级，不是候选写入优先级，也不允许共享基线反写公司 / 项目 override：

```text
project_override
> company_override
> industry_baseline / segment_baseline
> system_seed
```

共享基线规则：

- `industry_baseline` 只消费匿名化、多公司、多项目、不可反推单公司的样本摘要，不消费公司私有 override。
- `segment_baseline` 可按地区、业态、结构类型、工法、规模、阶段等分层，但必须满足最小公司数、最小项目数、样本去标识化和单公司占比上限。
- 公司样本不足时，runtime 可以读取 system seed + 行业 / 分层基线作为冷启动参考；该读取只提供参考值或候选基线，不得把共享基线反写为公司 override。公司样本达到门槛后，逐步由 company override 接管。
- 行业 / 分层基线属于 `system_curated_learning` 或 `guarded_live_tuning`，不得被单家公司样本直接更新，也不得读取其他公司的 company override、项目样本明细、候选结果或 replay 明细。
- 所有共享基线必须能解释来源范围、样本覆盖、方差、适用场景、禁用场景和 rollback target。

### 4.8 预测误差闭环与样本健康

base 工期收敛和预测误差闭环必须拆开：

- `base_duration_learning`：用完工样本的 P50 / P75、样本数、方差和上下文分桶校准参考工期。
- `forecast_residual_overlay`：用预测完成日和实际完成日之间的误差，校准预测模型的候选权重、置信度和残差修正，不直接改系统 seed。
- `context_factor_learning`：季节、天气、现场压力、资源冲突等因子先生成候选、shadow 或 canary，不得静默叠加成未登记乘数。

样本健康必须显式化：

| 样本状态 | 含义 | 处理 |
|---|---|---|
| `accepted` | 开始、结束、工序码、实际工期、质量标记均满足学习要求 | 可进入对应作用域的样本健康证据池；是否进入 benchmark 或 seed 学习仍取决于 learning_target、benchmarkEligible、作用域和发布门禁 |
| `weak` | 使用计划开始、更新时间、低置信匹配或进度质量降级推导 | 只可进入候选证据或补全建议，不直接进入高权重 benchmark，也不得触发发布许可 |
| `rejected` | 缺开始 / 结束、实际工期不可算、工序码缺失、日期异常、质量不可用 | 记录拒绝原因，不参与学习 |

任务完成时应尽量自动补齐样本事实：

- 只有完成状态但缺 `actual_end_date` 时，可用完成操作时间作为弱结束事实，并提示补充。
- 缺 `actual_start_date` 时，可按 `first_progress_at`、计划开始或首次有效进度推导弱开始事实。
- 非工期业务完成样本可以进入 sample health 以避免治理证据静默丢失，但必须保留 domain / businessCode 元数据，并标记 `benchmarkEligible=false`；即使样本为 accepted，也不得进入工期 benchmark、工期 seed、验收 / 图纸 / 证照 runtime 表或发布许可判断。
- 系统必须统计每家公司、每项目、每工序的样本可用率、弱样本率、拒绝原因、长尾冻结率和冷启动覆盖率。
- 样本被拒绝或降级不得静默发生；后台治理摘要必须展示原因，普通业务页只展示可处理的数据补全提示。

### 4.9 高风险资产边界

高风险资产指：一旦自动发布，会直接改变任务结构、依赖关系、计划日期、关键路径、工期预测、风险预警、健康评分、发布门禁、删除保护或跨公司共享边界的规则、Seed、模板、算法参数和治理策略。

工期相关资产的纳管范围必须按结果影响判断，而不是按表名或服务名判断。凡会影响工期生成、计划网络、关键路径、依赖顺序、模板结构、计划日期、剩余工期、加速建议、风险预警或健康解释的资产，都视为工期相关资产，必须进入 `learning_target + learning_maturity + publish_anchor + automation_maturity` 四元登记，并统一走公司隔离、候选事件、回放、发布门禁和回滚治理。`standard_work_duration` 只是其中一个资产类，不能代表工期相关资产已经全覆盖。

以下资产默认按高风险处理，除非后续在成熟规则中明确降级：

| 分类 | 高风险资产 |
|---|---|
| 任务结构 / WBS 模板 | 主标准工序模板 Seed、专项 / 分区模板 Seed、`chinaGb50300TemplateCatalog`、`domainWbsTemplateCatalogs`、模板场景组合、工法变体扩展、模板反馈候选、模板生成结果漂移候选 |
| 模板选择 / 项目事实映射 | `projectFactsToTemplateService`、`projectTypeRecommendations`、`projectFeatureToItemPackMap`、`scopeAssignmentRulesService`、`wbsTemplateProjectRecommendations` 中会改变模板包选择或生成范围的规则 |
| 依赖 / 顺序 / 门禁 | `standard_internal_flow`、`cross_item_workflow`、`dependencyIntentTemplates`、`process_constraint`、`workflow_sequence`、`executionGateSeedService`、`taskConstraintGovernanceService` |
| 关键路径 / 计划网络 | `projectCriticalPathService`、关键路径判定规则、阶段网络规则、里程碑接口规则、父子计划 rollup 规则 |
| 工期 Seed / 工期预测 | `standard_work_duration` 的系统级或跨公司发布、`earliest_start_rule`、`durationContributionMode`、`durationSuggestionService`、`taskDurationForecastService`、`projectCriticalPathService`、`projectRemainingDurationForecastService`、`scheduleAccelerationService` 相关参数 |
| 工期上下文高风险因子 | `seasonal_productivity`、`process_seasonal_sensitivity`、`weather_forecast_impact`、`calendar_missing`、`project_schedule_state` |
| 资源 / 现场压力 | `site_capacity_pressure`、`resource_conflict`、资源冲突阈值、工作面压力阈值、产能挤压规则 |
| 风险 / 问题 / 预警 | `risk_issue_warning_rule`、风险问题升级规则、预警阈值、关键路径停滞预警、延误预警、warning impact signal 规则 |
| 健康度 / 偏差 / 责任归因 | `progress_deviation_cause`、`responsibility_health_rule`、`milestone_integrity_rule`、健康评分权重、偏差归因规则、责任主体健康规则 |
| 状态派生 | 任务 due / lag / business status 派生规则、状态字典中会影响任务业务状态或列表筛选的规则 |
| 数据质量硬门禁 | 会阻断保存、发布、确认、导入、基线 / 月计划提交的数据质量规则 |
| 指标 / 报表口径 | `metricRegistry` 中影响 Dashboard、Reports、CompanyCockpit、健康分、趋势、排名的指标规则 |
| 证照 / 验收模板 | 非官方来源的证照模板 Seed、验收模板 Seed、城市 / 项目 override、会改变办理骨架或验收流程轴的模板候选 |
| 删除 / 保留 / 审计 | 删除保护、保留策略、归档策略、审计留痕策略、回滚策略 |
| 发布门禁本身 | `publish_anchor`、`automation_maturity`、自动发布阈值、canary 停止条件、rollback target、`policyOpsAutoPublishGateService`、`algorithmSeedGovernancePolicyService`、`durationContextFactorAutomationPolicy` |
| 大模型候选 | 任何由 LLM 生成或改写的规则、Seed、模板、参数、解释链、候选 payload |

补充口径：

- `standard_work_duration` 的公司 / 项目 override 可以走受控自动发布，但它仍属于高影响资产；只有在作用域明确、replay 通过、冲突为 0、`automation_maturity` 达到 `auto_canary / auto_publish`、存在 rollback target、且 `publish_anchor=guarded_runtime_auto_publish` 时，才允许通过统一发布出口写入灰度或 published 版本。
- `standard_work_duration` 的系统级、跨公司或集团级发布仍按高风险处理，不得由公司自学习候选直接改写系统 Seed。
- `durationPipelineTopology` 只作为 `v1.4.22` 阶段 1-3 已登记的工期管线治理边界被本章引用：它描述 `ProjectGenerationFacts / RuntimeExecutionFacts -> 5 个工期引擎 -> durationOutputGovernance` 的拓扑契约，不属于 algorithm seed、公司 / 项目 override、候选事件或自学习晋升对象。
- `runtimeExecutionInferenceService` 只负责把已有执行状态反推为商业级 `RuntimeExecutionFacts` 证据对象：资源压力、并行密度 / 施工节奏、里程碑压力和执行证据标签必须保留 `factType=inferred`、`confidence`、`sourceWindowDays`、`contributions`、`evidenceObjects` 和 `runtimeInferenceSummary`。该服务不得要求或伪造真实班组人数、真实工作面数量、塔吊小时利用率、施工电梯占用率或楼栋每日真实节拍；这些推断事实可在置信度和下游策略允许时影响预测 / 赶工建议，但不得自动改写任务日期、依赖、基线、月计划、项目静态事实或系统 seed。事实层验收由 `durationFactLayerAcceptanceService` 的 `runtime_execution_inference` 契约约束：只允许作为 basis lineage、偏差解释和准确率报告上下文，不允许作为 actual outcome 或自学习发布目标。
- 上述高风险资产不是“永远人工治理”的清单，而是“不得由单个候选直接自动发布”的清单；是否迁移到自动发布，必须等成熟规则、证据阈值、回放集、canary 半径、停止条件和回滚链路明确后再判定。

building_pattern 专项补充：
- `building_pattern` 属于高影响工期相关资产，但它的发布权力只到 `schedule_rhythm_context`，不得发布为五层依赖规则，不得写 `task_dependencies`，不得直接写计划日期。
- `building_pattern` 的 runtime 升级必须同时满足：seed 结构字段完整、项目规模事实完整、场景 schedule profile 存在、`buildingPatternScheduleCalibrationService` 绑定 11 个产品业态 / 13 个真实项目推荐包 / golden benchmark 13 场景，且 `buildingPatternScheduleBenchmarkEvidenceService` 能读取并验证已通过 gate 的全量 runtime replay artifact。
- 未绑定校准门槛、缺推荐包覆盖、缺业务类型覆盖、缺全量 runtime artifact 或 golden benchmark 阈值不可用时，`building_pattern` 只能是 `candidate_only` / `confidence_only`；公司或项目学习样本只能形成 overlay / candidate，不得静默改系统 seed。
- 当前 golden benchmark 门槛为：expectedScenarioCount=13、maximumDurationDeviationRatio=0.15、minimumDependencyPassRate=0.95。该门槛是 release blocking gate，不是 `building_pattern` 自己的算法权力；单个分场景 replay 只能作为诊断证据，不能替代全量 13 场景 release 证据。

### 4.10 大模型执行边界

- 大模型可以生成候选、解释、差异摘要、治理包草稿和自动化解锁建议。
- 大模型不得直接决定 `publish_anchor`、`automation_maturity`、运行期发布结果、系统级 Seed 改写、公司级 / 项目级 override 生效或跨公司共识晋升。
- 大模型不得根据服务名、Seed 名、历史习惯或单次样本表现推断自动发布权限。
- 大模型生成的规则、Seed、模板、参数、解释链和 payload 默认进入候选或隔离评审；只有通过本章作用域、证据、冲突、回放、灰度、回滚和发布锚点门禁后，才能进入 runtime。
- 大模型不得把 `auto_published`、`auto_governance`、`self_learning`、`trusted_source` 等词当成充分条件；必须逐项核验四元登记、当前锚点、成熟度、消费者和 rollback target。
- 大模型在补 adapter、service 或测试时，如果无法确认资产作用域或发布权，必须生成 `review_required / blocker / candidate_only` 路径，不能生成默认发布逻辑。
- 大模型不得把本文中的长期目标句、产品愿景句或“默认不走逐条人工审批”解释成省略门禁；所有执行动作必须能回指到明确字段、状态机、测试或 diagnostics 证据。
- 大模型不得把“锚点升级候选”“自动化解锁建议”“系统级发布建议包”“reviewItems 已清零”写成 runtime 发布动作；除非代码中存在明确发布出口、门禁测试和 rollback target，否则只能输出候选、shadow、review 或 blocker。
- 大模型不得把“服务已存在”“迁移表已存在”“dashboard API 已存在”解释为专项 adapter、后台页面、发布出口、回滚链路全部完成；必须逐项核对写入路径、权限边界、测试证据和 runtime 消费点。

### 4.11 系统级晋升的验证证据来源

系统级晋升指把项目级或公司级学习得到的候选规则，升级为全平台默认规则、系统 Seed、系统模板或系统算法参数。它会影响其他公司和新项目，因此不得由单个项目、单个公司或单次候选直接发布。

系统级晋升优先依赖更多项目、更多公司、更多场景的自动验证证据，不以人工逐条审批作为主路径；但自动验证只提供证据和门禁结论，不天然授予发布执行权：

1. 项目候选只进入本项目 candidate / shadow，不改系统 Seed。
2. 公司候选必须先在同公司多项目稳定后，才允许形成公司级候选；是否写入公司级 override 仍必须重新通过统一发布出口、门禁测试和 rollback target。
3. 跨项目验证池必须覆盖不同项目类型、地区、结构类型、工法、规模和阶段。
4. 跨公司验证池必须覆盖多家公司，不允许单公司样本直接晋升系统级。
5. Shadow 对照必须证明新规则优于或不劣于当前系统规则，且不会扰动已确认事实、基线、月计划、关键路径和风险升级策略。
6. Canary 灰度必须限定项目、公司、场景、时间窗和新生成结果，带停止条件和 rollback target。
7. 达到成熟规则后，只有当系统级发布锚点、自动化成熟度和锚点升级策略都已登记且通过门禁，且该资产类明确允许平台级无人值守发布时，才可以由平台级自动发布机制写入系统级 published 版本，并保留版本、审计、影响面监控和回滚目标；否则只能形成系统级发布建议或平台异常仲裁请求。
8. 如果当前代码只具备验证报告、发布建议包或 `system_curated_learning` 候选，而没有平台发布出口和发布门禁测试，则系统级状态最高只能到 `system_proposed` 或 `system_canary`；不得写成 `system_published`。

人工不是系统级晋升的默认路径，但也不是可以被大模型或单个候选跳过的空环节。只有自动验证无法裁决、不同公司场景差异无法解释、涉及法规 / 强安全 / 强合规口径、缺少回滚目标、canary 退化、LLM 试图直接进入 runtime、发布边界被扩大或锚点升级策略缺失时，才进入人工或平台异常仲裁。

## 6. 公司隔离

### 6.1 隔离对象

以下内容必须按公司空间隔离：

- 规则候选
- seed 候选
- 公司级 override
- 项目级 override
- 回放样本
- 评估结果
- 审计记录
- 缓存和异步任务结果

系统 seed、系统 seed 版本和系统 seed 记录是全局公共资产，不按公司复制。这里的“全局公共资产”只表示归属层级和治理来源，不表示旧系统 seed、旧 `active / published` 名称或系统 target surface 可以被 runtime 默认消费；跨公司只读消费仍必须证明系统级 active / published 版本、统一发布记录、消费者验证、影响面监控和 rollback target。公司差异通过 `company_override` 和候选治理承载。

### 6.2 隔离要求

- 公司级 / 项目级资产查询必须带 `company_id` 或可由 `project_id` 推导出公司
- scoped 缓存必须按 `company_id` 或 `project_id` 分片
- 所有后台任务必须按公司空间执行
- 所有回放样本必须只使用本公司或本项目历史
- 默认不做跨公司自动训练

### 6.3 跨公司边界

不同公司的资产可以共用同一个系统 seed，但不能共用彼此的公司 override、项目 override、候选结果和回放样本。

如果后续需要集团级共识升级，必须走单独的系统级验证与发布门禁，不得混在公司自学习通道里。

## 7. 自学习链路

### 7.1 输入来源

自学习只消费真实业务事实，不消费业务页上的技术字段。这里的“消费”只能解释为只读证据输入和样本归因，不表示学习链可回写、纠正、覆盖或自动补全业务事实本身；任何反向写入任务、计划、依赖、验收、图纸、证照、风险或材料业务记录的动作，仍必须回到对应业务章节和用户操作 / 审批链路。

```text
任务实际开始 / 完成
任务进度快照
计划偏差结果
风险 / 问题 / 预警处理结果
材料到场与验收事实
用户手工修正结果
候选采纳 / 驳回 / 回滚记录
```

### 7.2 现有自学习入口统一纳管

当前代码中已经存在多条自学习或自升级链路，本章不要求删除这些链路，也不要求把所有资产硬塞进 algorithm seed 生命周期；要求是统一候选协议、统一作用域、统一发布门禁。

| 现有入口 | 典型能力 | 统一纳管方式 |
|---|---|---|
| `algorithmSeedLearningService` / `algorithmSeedCandidateDiscoveryService` | 生成 algorithm seed 升级候选 | 继续写入 `algorithm_seed_upgrade_candidates`，同时进入统一资产台账摘要 |

### 7.3 候选分类

| 类别 | 说明 | 默认去向 |
|---|---|---|
| `deterministic_rule` | 明确业务规则，偏硬约束 | 后台治理门禁 |
| `candidate_rule` | 真实样本发现，只能先提示 | 候选池 / 隔离池 |
| `learned_calibration` | 可影响系数或权重，但需门禁 | 公司级或项目级治理 |
| `learned_base_duration` | 用完成样本 P50 / P75 校准基础工期 | 最高只能在项目 / 公司作用域申请受控 live tuning；仍需四元字段、replay、冲突、writer、消费者、监控和 rollback target 全部通过 |
| `forecast_residual_overlay` | 用预测误差校准预测残差、置信度或候选权重 | 默认候选或 shadow；只有证据、replay、冲突、发布出口、消费者边界、监控和 rollback target 同时通过后才可受控 live |
| `cold_start_baseline` | 匿名行业 / 分层共享基线 | 只作冷启动参考，不改公司私有 override |
| `learnable_parameter` | 原代码常量、阈值、权重、乘数注册为治理参数 | 默认 frozen，满足门禁后迁移成熟度 |

### 7.4 晋升规则

- 样本数不足，不晋升
- 证据不稳定，不晋升
- 冲突未清，不晋升
- 回放误差过大，不晋升
- 只在本公司内表现稳定，才能进入本公司发布候选池或 release-exit 前置池；是否写入公司级 runtime 仍取决于发布锚点、自动化成熟度、发布出口、专属 writer、消费者验证、监控和 rollback target
- 只有满足平台级验证门禁，才允许进入系统级 Seed 发布候选；系统级发布候选仍不是 `system_published`，缺平台发布出口、系统 writer、消费者验证、影响面监控或 rollback target 时只能停在建议 / canary / 平台异常仲裁
- 资产未登记 `publish_anchor`，默认按 `candidate_only` 处理
- 已声明 `manual_governance_required`、`manual_review_required_before_publish`、`manual_review_only`、`candidate_only_until_manual_*`、`no_unattended_runtime_auto_publish` 或 `manual_runtime_promotion_required` 的资产，在当前 `manual_required` 或未满足解锁条件前不得自动发布
- 来源可信、弱来源阻断、上一 published 版本可保留的政策 / 模板类 seed，可以登记为 `trusted_source_auto_publish` 候选；是否发布仍取决于统一发布出口、门禁测试、发布记录和 rollback target
- 低风险且已声明可自动运行发布的因子或 override，可以登记为 `guarded_runtime_auto_publish` 候选，但仍需 `automation_maturity` 达到灰度或发布门槛，并由统一发布出口执行
- 当前不得自动发布的强锚点必须同步生成 `automation_unlock_criteria` 和更多验证需求，不能只停留在“人工处理”
- 当同类异常仲裁结论可由规则稳定复现时，控制面只能按已登记锚点升级策略把成熟度从 `manual_required` 推进到 `auto_review_package / auto_shadow`
- 只有 `learning_maturity=guarded_live_tuning`、`publish_anchor` 允许自动发布、`automation_maturity` 达标、发布执行链完整且可回滚的低风险参数，才能影响新生成结果；`shadow_report_only / governed_candidate` 不得被消费为 live 参数
- `forecast_residual_overlay` 不能直接改写 `standard_work_duration` seed；它只能作为预测模型残差层或候选权重层，并必须保留原始预测、误差、改后预测和回滚目标
- 小公司或低频工序样本不足时，允许读取匿名 `industry_baseline / segment_baseline` 冷启动参考；不得把其他公司的 company override 或项目样本直接混入当前公司学习池
- 样本被拒绝或降级时必须记录 sample health，不得用“没有样本”掩盖日期缺失、工序码缺失、质量降级或 actual duration 不可推导

统一晋升状态机：

```text
observed
> candidate
> replay_ready
> conflict_checked
> anchor_decided
> maturity_decided
  - manual_governance_required / manual_required -> review_required / auto_review_package / auto_shadow
  - guarded_runtime_auto_publish + auto_canary + release_exit + domain_writer + consumer_verified + impact_monitoring + rollback_target -> project_canary / company_canary
  - trusted_source_auto_publish + auto_publish + source_health + release_exit + domain_writer + consumer_verified + release_recorded + impact_monitoring + rollback_target -> project_published / company_published
  - guarded_runtime_auto_publish + auto_publish + replay_passed + release_exit + domain_writer + consumer_verified + release_recorded + impact_monitoring + rollback_target -> project_published / company_published
  - system_curated_publish + auto_publish + system_auto_publish_policy + anchor_upgrade_strategy + cross_company_replay_passed + platform_release_exit + system_writer + consumer_verified + release_recorded + impact_monitoring + rollback_target -> system_proposed / system_canary / system_published_after_platform_writer
> active_runtime_consumption
> superseded / rollback / quarantined / rejected
```

上述状态机是带分支的治理路由，不是所有候选线性直达 published。`release_exit / platform_release_exit` 只是前置门禁和 handoff，不是 writer；`project_published / company_published / system_published_after_platform_writer` 只在代码中存在明确发布出口、资产类型专属 writer、消费者验证、发布门禁测试、影响面监控、发布记录和 rollback target 时成立；否则对应候选必须停在 `review_required / project_canary / company_canary / system_proposed / system_canary / platform_exception_review`。命名中出现 `published` 的本地状态或历史字段也必须先映射到统一状态机，不能反向证明发布已经发生。各专项服务可以保留自己的本地状态，但必须映射到上述状态机。不能映射的状态视为后台观察态，不得进入运行期。

## 8. 冲突、隔离与回滚

### 8.1 冲突检测

需要检测的冲突至少包括：

- 同一 `stable_code` 在不同公司中语义差异明显，且试图晋升为系统级共识
- 同一公司内多个资产对同一业务事实给出相反结论
- 候选资产试图覆盖已发布资产
- 公司级和项目级 override 叠加后出现过强影响
- 学习样本和正式规则之间口径不一致

不同公司内部差异本身不是错误；只有当差异被错误地用于跨公司训练、集团级共识或系统级发布时，才算冲突。

### 8.2 与当前已有规则的冲突仲裁

自动治理控制面处理新候选与当前已有规则的冲突时，必须先保护已发布规则、系统 seed 和当前不得自动发布的强锚点。仲裁顺序如下：

1. **锚点优先**：已有规则或候选声明 `manual_governance_required / manual_review_required_before_publish / manual_review_only / candidate_only_until_manual_* / no_unattended_runtime_auto_publish / manual_runtime_promotion_required` 时，新候选不能直接自动覆盖；控制面必须生成评审包、更多验证需求和自动化解锁条件。
2. **作用域优先**：项目级候选只能挑战本项目规则；公司级候选只能挑战本公司规则；不得用项目样本直接覆盖公司规则或系统 seed。
3. **已发布优先**：当前 active / published 规则继续生效；候选只能在 shadow / replay 中比较，不能抢占 runtime。
4. **更窄半径优先**：当公司规则与项目 override 冲突，runtime 仍按 project override > company override > system seed 读取；冲突记录进入后台治理。
5. **证据强度优先**：只有当候选证据、回放、冲突清理、显式 domain adapter / runtime writer、消费者边界、影响面监控和回滚目标都齐备，且 `publish_anchor` 允许自动发布、`automation_maturity` 达到对应 `auto_canary / auto_publish` 门槛时，才可进入统一发布出口校验；发布出口校验通过后才可写入灰度或新的 published 版本。
6. **强锚点不可被单个候选绕过**：凡是当前代码或台账已有 `candidate_only_until_manual_*`、`manual_review_required_before_publish`、`manual_runtime_promotion_required`、`no_unattended_runtime_auto_publish`、`manual_review_only` 等声明的资产，控制面不能以“单次证据足够”为由直接发布；但可以在资产类层面沉淀验证规则，满足 `automation_unlock_criteria` 后提升自动化成熟度。

冲突结果分为：

| 结果 | 含义 | runtime 行为 |
|---|---|---|
| `no_conflict_publish_allowed` | 无冲突、锚点允许自动发布、成熟度达标，且证据 / replay / adapter / writer / 消费者边界 / 监控 / rollback target 均齐备 | 只能进入统一发布出口校验；校验通过后才写入对应作用域 canary 或 published 版本 |
| `shadow_compare_only` | 可学习但不能覆盖已有规则 | runtime 继续用已有 published 版本 |
| `manual_governance_required` | 命中当前不得自动发布锚点或冲突无法自动裁决 | 写评审包和更多验证需求，不发布 |
| `automation_unlock_candidate` | 冲突可解释，且具备自动化解锁潜力 | runtime 不变，进入 auto_review_package / auto_shadow |
| `quarantine_required` | 候选存在硬冲突、越级或旧对象污染 | 隔离，不参与运行 |
| `supersede_with_rollback_target` | 锚点和成熟度允许替换，上一版本可回滚，且候选已重新通过作用域、证据、冲突、回放、adapter / writer、消费者边界和监控门禁 | 只能由统一发布出口写新版本并记录 rollback target；不得由候选服务直接覆盖 |

### 8.3 隔离策略

- 冲突资产先进入 `quarantined`
- 隔离资产仍可保留证据，但不参与运行
- 隔离原因必须可解释、可追踪、可复盘

### 8.4 回滚策略

- 公司级发布支持回滚到上一稳定版本
- 项目级 override 支持按项目回滚
- 系统 seed 回滚必须走更高一级治理门禁
- 回滚动作必须写审计和摘要
- 回滚完成判定必须同时满足：资产类型专属 writer 已执行撤销 / 降级 / disable 写入，发布记录或 runtime projection 已标识为不可消费，相关消费者已经验证不再读取被回滚版本，且审计事件能回指 rollback target。只有 `rollback_target`、`rollback audit`、`rollback event`、监控失败记录或 release-exit handoff，不得声明真实 runtime 回滚完成。
- 对 forecast residual overlay，当前可以声明“受控 runtime publication 状态、overlay 专属 rollback writer、rolled-back 状态落库和 `taskDurationForecastService` 排除 rolled-back overlay 已接入”；该声明仅覆盖 `duration_forecast_residual_overlays` 这一资产类型，不得外推为其他 seed、参数、模板、WBS、依赖或样本健康资产已具备完整自动发布 / 回滚闭环。

- 不在普通页面展示公司级冲突详情
- 不把候选、隔离、回放做成业务操作入口
- 只在后台治理或公司管理员视图暴露资产台账；治理 dashboard API 和后台汇总入口只是 review / 观测入口，不是发布执行链，也不能替代发布出口、门禁测试、发布记录和 rollback target

## 11. 执行步骤

本节是剩余执行与验收清单，不是当前实现事实。执行者必须按“当前已补 / 待接入 / 待验收”分层处理：已写“补齐 / 增加 / 建立 / 支持”的条目，如果没有当前代码、迁移、测试或 diagnostics 证据，只能进入待办、reviewItems 或 blockers；不得因为本节动词是强制语气就直接生成发布、回滚、消费或锚点升级逻辑。

### 11.1 台账与作用域

1. 以 `algorithmRuleAssetInventoryService` 作为唯一后端资产台账入口
2. 待补齐系统 seed、候选、override、工期 override、非 registry 规则资产和支撑治理模块的统一资产视图；未补齐前不得把只读台账、局部 diagnostics 或单个专项 service 当成全资产统一视图
3. 统一读写优先级，并保留 `evaluateAlgorithmAssetAdmissionGate()` 作为新增资产准入前置门禁；读写优先级只适用于已完成对应资产类型发布链、消费者验证和 rollback target 的 runtime 版本，不适用于旧对象、候选事件、审计 run、只读 dashboard 摘要或无 projection / 无 writer 的本地状态

### 11.2 候选与学习

1. 从真实事实生成候选
2. 按公司空间聚合候选
3. 只在本公司范围内做自学习
4. 为 algorithm seed、WBS 模板、证照模板、验收模板、天气影响、工期校准等现有学习入口补统一候选事件 adapter；已接入的 WBS 模板提交 / 参考天数反馈 / 语义治理 finding / 结构治理 profile 和施工依赖 replay 校准队列仍只代表候选或 review 包接入，不代表 WBS seed、模板 runtime、reference_days 或 `task_dependencies` 已被自动发布；已接入的天气影响仍只代表候选事件接入，不代表自动发布链路闭合；证照 policy 更新与验收 policy 更新已进一步补齐 release adapter 记录构建、发布审计运行表写入、projection-backed 预览消费判定、stable 模板实体 runtime projection 写入、projection rollback disable 写入、release / rollback / monitoring 执行事件记录和 `policyTemplateReleaseImpactMonitoringJob` 发布后监控调度；业务预览不得读取无 projection 的 stable 审计 run，但仍不代表其他资产类型真实 runtime 回滚写入已完成或具备全域无人值守自动发布链路
5. 对所有会影响工期、计划网络和关键路径的资产做结果影响扫描；模板类 seed、模板选择规则、依赖 / 顺序 / 门禁规则、关键路径规则、工期上下文因子、预测权重、置信度、风险预警和健康解释规则必须与 `standard_work_duration` 同批纳管
6. 后续新增的相关资产不得依赖人工补清单；必须先被 `v14AssetAdmissionAutomationService` 或等价自动发现链路识别，再自动生成资产登记草案、作用域判断、消费者矩阵、风险级别、候选事件 adapter 需求和治理缺口。自动生成登记草案不等于登记完成，也不授予发布权；缺字段或不可分类时仍进入 `reviewItems / blockers`
7. 所有候选统一落到 observed / candidate / replay_ready / review_required / quarantined / rejected / superseded 状态机；`published` 不属于普通候选 adapter 可自行写入的候选状态，只能由统一发布出口在发布执行链完整通过后生成
8. 保留专项服务本地学习逻辑，但禁止本地学习结果绕过统一治理协议直接进入 runtime
9. 为每类 seed / 算法资产登记 `publish_anchor`，把“发布锚点允许进入自动发布门禁”“当前不得自动发布”“只做候选”的资产分开；不得仅凭 seed / 算法自带学习能力、历史 `auto_published` 名称或可信来源名称判定为可自动发布
10. 为当前不得自动发布的资产登记 `automation_maturity`、`automation_unlock_criteria` 和更多验证需求，把强锚点转成可逐步自动化的待解锁项
11. 为锚点升级建立独立策略资产：登记适用资产类、证据阈值、跨项目 / 跨公司 / 跨场景要求、最大灰度半径、停止条件、回滚目标和审计字段；没有该策略时，`manual_required` 只能生成解锁候选，不能自动升为 `auto_publish`
12. 为每个自学习入口登记 `learning_maturity`，明确其当前是 `frozen_constant`、`shadow_report_only`、`governed_candidate` 还是 `guarded_live_tuning`
13. 建立可学习参数注册表，把 `benchmarkBlendWeight`、P50/P75 融合比例、L0/L1/L2 权重、置信度扣分、工期上下文乘数、样本阈值、canary 停止条件等从隐式代码常量提升为治理资产；参数建议实例必须再经 `algorithmAssetLearnableParameterSuggestionService` 转成候选事件，合格低风险建议只能进入 release-exit handoff；ready handoff 才能交给 `algorithmAssetLearnableParameterReleaseExecutionService` 写入参数 runtime publication / release event / rollback audit；该写入仍只是参数 publication 链，不得被解释为 seed / override / 业务 runtime 写入；高风险、证据不足或缺 adapter 的建议只能进入 review / 治理包
14. 将 base 工期收敛、预测误差残差 overlay、工期上下文因子学习拆成三条候选链，分别登记 `learning_target`
15. 增加样本健康事件，记录样本 accepted / weak / rejected、拒绝原因、降级原因和可补全建议；非工期业务完成样本必须额外记录 domain metadata、`nonDurationBusinessCompletionSample=true` 和 `benchmarkEligible=false`，只作为治理证据

### 11.3 冲突与回放

1. 增加语义冲突检测
2. 增加隔离池
3. 增加离线回放评估
4. 回放样本按公司 / 项目空间隔离，禁止跨公司混训
5. 专项 replay 报告必须输出统一摘要，供发布门禁和资产台账消费
6. 冲突仲裁结果要区分 quarantine、manual governance、shadow compare 和 automation unlock candidate
7. 预测误差回放必须同时输出原始预测、实际完成、误差、overlay 后预测、MAE 改善、过度补偿率和是否影响 runtime
8. 对 `shadow_report_only` 资产，回放结果只能形成治理证据，不得写入 live 参数

### 11.4 发布与回滚

1. 公司级 / 项目级发布增加治理记录
2. 发布执行链必须支持按版本回滚；当前若只有 `rollback target / rollback audit / rollback event`，不得视为真实 runtime 回滚已完成。回滚生效必须由资产类型专属 writer 执行撤销、降级或 disable，并由对应消费者验证不再读取被回滚版本。
3. 系统级 Seed 仍保留更高的平台级验证与发布门禁，优先通过多项目 / 多公司 / 多场景自动验证补齐证据；这里的“自动验证”只替代重复人工搜证和人工逐条比对，不替代发布策略、锚点升级、影响面监控、资产类型专属 writer、消费者验证和回滚门禁。“不走逐条人工审批”不等于无人值守发布，也不适用于尚未完成锚点升级的 manual 强锚点；自动验证只提供证据和门禁结论。只有系统级锚点、成熟度、影响面监控、回滚门禁和资产类无人值守发布策略全部通过时，才允许平台级自动发布；否则只能生成系统级发布建议或平台异常仲裁请求
4. 发布路由固定先判定 project / company / system 三层作用域，但物理发布出口必须按资产类型拆分：seed / override 类只能由 seed 专属 writer 写版本或 override；可学习参数只能由参数 publication 链写 `algorithm_learnable_parameter_runtime_publications`，再由已登记消费者逐项只读接入，当前已登记消费者包括 `durationSuggestionService` 的 `duration.benchmark_blend_weight` stable 消费、`durationSuggestionService.company_benchmark_p50_p75_blend` 对 `duration.p50_p75_blend_ratio` 的显式 canary 公司 benchmark reference 消费，以及 `durationContextService.weather_forecast_impact` / `durationContextService.resource_conflict` 对 `duration.context.weather_multiplier` / `duration.context.site_pressure_multiplier` 的显式 canary 新结果消费；policy 类先写 policy 审计运行表，只有 stable-consumable run 才可由模板实体 runtime writer 写 `policy_template_entity_runtime_publications` 投影，业务预览只读该 active projection；candidate record 或无 projection 的 stable run 不能因为 target surface 命中 project / company / system 就直接成为运行期规则
5. `auto_published` 如来自既有本地服务状态，只能先解释为待核查治理结果；只有同时存在统一发布出口、资产类型专属 writer、发布记录、作用域证据、消费者验证、门禁测试和 rollback target 时，才可解释为已发布到受控作用域。它不等于允许改写系统 seed，也不能覆盖当前不得自动发布的强锚点
6. `trusted_source_auto_publish`、`guarded_runtime_auto_publish` 和 `manual_governance_required` 必须各自有独立门禁测试，禁止混用
7. 当前不得自动发布资产的成熟度提升必须有版本化记录、验证证据和回滚目标；不能由单个候选直接把 `manual_required` 改成 `auto_publish`
8. `guarded_live_tuning` 只能影响新生成结果，不能静默改写已确认基线、已确认月计划、历史快照或已经发布的系统 seed
9. 冷启动共享基线发布必须有匿名化证明、最小公司数、最小项目数、单公司占比上限、适用分层、runtime publication 状态、消费者排除 `runtime_rolled_back` 验证和 rollback target；真实回滚只能由 `algorithm_cold_start_baselines` 专属 writer 标记 `runtime_rolled_back`，不得写 company override、项目样本或 `standard_work_duration` seed
10. 可学习参数从 `frozen_constant` 晋升到 `guarded_live_tuning`，必须有参数级版本、最大变化幅度、停止条件和回滚目标
11. 缺少统一发布出口或 rollback target 的实现，只能完成候选治理、shadow、canary 建议或后台 review；不得把服务测试通过写成发布验收通过
12. 当前已补 `algorithmAssetReleaseExitService` 作为发布执行链前置门禁：它只能在锚点、成熟度、replay、冲突仲裁、rollback target、显式 domain adapter、系统级平台策略和影响面监控均满足时生成 handoff package；其中 `impactMonitoringReady` 是 project / company / system 三类 runtime handoff 的共同硬门禁，不只是 `system_seed` 平台发布策略字段；它本身不是 runtime writer，不能替代专项 adapter、发布执行记录、模板 runtime writer 或回滚执行。
13. 当前已补 `policyTemplateReleaseAdapterService` 作为证照 / 验收模板 policy 的专项 adapter：它只能消费 `release_package_ready` 的 release-exit 结果，并在 adapter、domain、targetSurface 与 rollback target 匹配时生成 domain release record；它不代表模板 runtime 已发布，不替代发布执行服务、回滚执行、影响面监控或平台级发布策略。
14. 当前已补 `policyTemplateReleaseExecutionService` 作为证照 / 验收模板 policy release record 的审计运行表、执行事件记录、模板实体 runtime projection writer 与 projection rollback writer：它只能消费 ready release record，向证照 / 验收 policy auto-publish run 表写入带 releaseExecution、rollbackExecution 和 impactMonitoring 元数据的审计记录，并向 `policy_template_release_execution_events` 记录 release / rollback / monitoring 事件；当 PolicyOps 判定 `stableConsumptionAllowed=true` 且 `runtimeConsumptionStatus=stable_consumable` 时，stable run 只具备写入模板实体 runtime projection 的资格，业务预览的 latest stable 来源必须是 `policy_template_entity_runtime_publications.runtime_publication_status=runtime_stable_published` 的未回滚投影；candidate run 和无 projection 的 stable 审计 run 仍只做后台审计，不写、不替代模板实体 runtime projection；rollback 执行时只把对应 projection 标记为 `runtime_rolled_back`，不写 seed、不写模板本体表；当前已补 `policyTemplateReleaseImpactMonitoringJob` 调度 stable 证照 / 验收 policy run 的发布后监控，记录 monitoring event，并在阈值失败时委托 `policyTemplateReleaseExecutionService` 执行 projection rollback；二者都不改系统 seed、不改模板 seed，也不授予本地 `auto_published` 状态额外发布权。
15. 当前已补 `algorithmAssetLearnableParameterReleaseExecutionService` 作为可学习参数 release-exit handoff 的首批执行服务：它只能消费 ready package，写 `algorithm_learnable_parameter_runtime_publications / algorithm_learnable_parameter_release_events`，rollback 只把参数 publication 标记为 `rolled_back` 并记录审计事件；它不写 `algorithm_seed_records / algorithm_seed_overrides / standard_work_duration`，也不代表参数消费者或完整后台运营闭环已经完成。
16. 当前已补 `algorithmAssetLearnableParameterImpactMonitoringJob` 作为可学习参数发布后的首批影响面监控调度：它只读取参数 publication，记录 monitoring event；缺外部专项 evaluator 时，只读冻结 `governance.canary_stop_conditions.default` 作为 overcompensation / regression 默认停止条件阈值，并在阈值失败时委托参数 release execution 服务写 rollback audit；它不写 seed、不写 `standard_work_duration`、不替代参数 runtime 消费接入，也不允许 `governance.canary_stop_conditions` 通过参数 publication 自我发布或自我放宽。
17. 当前已补 `algorithmAssetLearnableParameterRuntimeConsumptionService` 作为可学习参数 publication 的只读消费门禁：它只读取 `algorithm_learnable_parameter_runtime_publications`，复核注册表、作用域、证据、delta、rollback 和 publication 状态；stable 默认只读 `publication_status=published`，`publication_status=canary` 必须显式传入 canary runtime boundary（consumerKey、作用域边界、停止条件、监控窗口）才可被 canary-aware 消费者读取；当前已将 `duration.benchmark_blend_weight` 接入 `durationSuggestionService` 的公司 benchmark blend，并将 `duration.context.weather_multiplier` 与 `duration.context.site_pressure_multiplier` 分别接入 `durationContextService.weather_forecast_impact` 与 `durationContextService.resource_conflict` 的 canary-aware 新结果因子；这些 canary 接入仍保持候选影响和计划修订确认边界，不写 seed、不写已确认计划、不表示 stable 发布；其他参数消费者仍需继续接入。
17a. 当前还已将 `duration.p50_p75_blend_ratio` 接入 `durationSuggestionService.company_benchmark_p50_p75_blend` 的显式 canary 消费边界；该参数只能影响公司 benchmark runtime reference 的 P50/P75 参考天数融合，不能被解释为模型权重应用、stable 参数消费、seed 更新、`standard_work_duration` 更新或 confirmed plan / snapshot 改写。执行时若需要枚举“已登记消费者”，必须把它与 `duration.benchmark_blend_weight`、`duration.context.weather_multiplier`、`duration.context.site_pressure_multiplier` 分开列明，避免把 P50/P75 canary reference 误归为未接入参数或全域自动发布参数。
18. `taskDurationForecastService` 已使用参数 runtime 消费门禁记录 forecast 高风险参数阻断证据，但该记录只能作为“未被应用”的治理证据；不得把它解释为 `forecast.L0/L1/L2.candidate_weight`、`forecast.progress_curve_multiplier` 或 `forecast.confidence_penalty` 已具备 stable / canary runtime 消费，也不得据此调整预测模型权重；另已接入的 `forecast.confidence_weight_multiplier` 只能作为剩余工期预测 confidence weight 的受控乘数消费，不得扩大解释为候选权重、曲线策略、seed 或任务事实自动更新。

### 11.5 验收与门禁

本节未标注“当前已补”的条目均为待补 / 待验收项，不得作为当前实现事实、发布许可或 runtime 生效证据；已标注“当前已补”的条目也只覆盖句内明确列出的资产类型、service、writer、consumer 和测试范围，不能外推到其他资产类型或全链路闭环。

1. 待补资产隔离测试；必须覆盖专项 writer、runtime consumer、缓存、异步任务结果和回滚链路，而不是只覆盖后台只读摘要
2. 当前已补后台治理证据摘要层的公司 A / B 互不污染测试：`algorithmAssetGovernanceDashboardEvidenceService` 只按当前 `company_id` 汇总 candidate / replay / sample health，不读取 `company_id IS NULL` 的 system observation，也不读取其他公司行；后续专项 writer / runtime consumer 仍需按各资产类型继续补 A / B 隔离测试
3. 待补候选晋升与回滚测试；候选晋升必须证明 release-exit 之后仍由资产类型专属 writer 执行，回滚测试必须证明消费者不再读取被回滚版本
4. 待补 CI 门禁；门禁只能证明当前快照通过台账、准入、禁止路径和关键专项测试，不得作为后续新增资产或旧对象重扫的永久白名单
5. 待补多来源自学习入口纳管测试：algorithm seed、WBS、证照、验收、天气、工期候选、风险预警、健康解释和指标口径都必须默认不直接影响 runtime
6. 待补发布锚点与成熟度联动测试：未登记 `publish_anchor` 不得进入自动发布门禁、不得写 runtime；可信来源“可进入自动发布门禁”、低风险运行期“可进入自动发布门禁”和当前不得自动发布队列必须分别命中自己的锚点与 `automation_maturity` 门禁，并断言当前不得自动发布队列不会因自动治理通过而写入 runtime
7. 待补自动化成熟度测试：当前不得自动发布资产可生成自动化解锁条件、更多验证需求和 shadow/canary 建议，但不能在成熟度不足时直接发布
8. 当前已补锚点升级策略评估与协议门禁测试：`algorithmAssetAnchorUpgradeStrategyService` 会阻断单个候选 / 单次 replay / 大模型直接升级 manual 锚点，只在策略 key / version、证据阈值、跨项目 / 跨公司 / 跨场景影响面、rollback target 和 audit record 齐备时生成版本化锚点升级候选；`algorithmAssetGovernanceProtocolService` 不再接受裸 `anchorUpgradeStrategy` 字符串作为系统级发布证据。该候选仍不直接修改 `publish_anchor / automation_maturity`，也不追溯发布原候选；后续若要真正变更锚点，仍需平台异常仲裁或已登记策略的版本化落库与审计闭环
9. 待补自学习成熟度测试：`frozen_constant / shadow_report_only / governed_candidate / guarded_live_tuning / system_curated_learning` 必须在资产台账和候选事件中可区分
10. 待补可学习参数注册、参数建议、参数发布执行和参数影响面监控测试：未登记参数不得被 runtime 当作可学习参数消费；已登记参数必须有作用域、风险级别、证据阈值、最大变化幅度和 rollback target；参数建议实例必须先写候选事件，只有合格低风险建议能形成 release-exit handoff package；ready package 才能写 `algorithm_learnable_parameter_runtime_publications / algorithm_learnable_parameter_release_events`，参数影响监控只能写 monitoring event 和 rollback audit，并断言不会写 `algorithm_seed_records / algorithm_seed_overrides / standard_work_duration`；高风险、证据不足或缺 adapter 的建议不得发布
11. 待补冷启动共享基线测试：小公司样本不足时可以消费匿名行业 / 分层基线，但不得读取其他公司的 company override、项目样本明细或候选结果；`runtime_rolled_back` 基线必须被 `algorithmAssetColdStartBaselineService` 和 `durationSuggestionService` 排除，rollback writer 只能更新 `algorithm_cold_start_baselines`
12. 待补预测误差闭环测试：MAE / forecast error 只能写入 `forecast_residual_overlay` 或候选权重层，不得直接改写 `standard_work_duration` seed
13. 待补样本健康测试：完成任务样本 accepted / weak / rejected 的原因必须可追踪，日期缺失、工序码缺失、弱样本不得静默消失；非工期业务完成样本必须断言 `benchmarkEligible=false`、domain metadata 被保留，且不会写入工期 benchmark 或业务 runtime；当前已补后台治理 dashboard 的 sample health 计数摘要，确保 accepted / weak / rejected 可按公司观测
14. 待补禁止路径测试：缺四元字段、缺 company/project/system 作用域、命中 manual 锚点、缺 domain adapter、缺资产类型专属 writer、缺消费者验证、缺影响面监控、缺 rollback target、旧对象污染、冲突未解、只有 dashboard API 或只有 release-exit handoff 时，均不得写 `published`、不得写 runtime、不得声明回滚生效

## 12. 旧对象处理

### 12.1 系统 seed 旧对象

已有 `algorithm_seed_versions / algorithm_seed_records / algorithm_seed_import_logs` 仍按系统级资产处理，不补 `company_id`，不迁成公司私有表。

旧系统 seed 的“系统级资产”只表示归属层级，不等于当前系统默认可消费版本。缺少 active / published 版本证据、统一发布记录、消费者验证、冲突核验和 rollback target 时，只能作为 `system_observation / legacy_audit / review_required`；不得因历史表名、导入日志或默认名称直接作为跨公司 runtime 基线。

### 12.2 候选与 override 旧对象

已有候选和 override 按以下方式做历史审计、作用域重定界和重新准入，不得理解为恢复运行期兼容：

- `project_id` 不为空：按项目级资产处理，并通过项目推导公司
- `company_id` 不为空：按公司级资产处理
- `project_id / company_id` 都为空：仅作为 `system_observation / legacy_audit`，不得直接产生公司级运行影响，也不得作为系统只读基线或系统默认规则被 runtime 消费

### 12.3 WBS 模板与经验工期旧对象

旧 WBS 模板页面不作为普通前端入口恢复。模板、经验工期、工期 override 如要参与资产治理，只能通过后台资产台账汇总展示，不重新打开旧页面维护链路。

### 12.4 旧候选处理

历史候选如果缺少作用域、证据或回放结果，默认保持 `candidate_only` 或进入 `quarantined`，不得自动发布；只有重新补齐作用域、证据、回放和解锁记录后，才能按新候选进入治理。

### 12.5 旧工程范围对象处理

规则资产、WBS 模板、工期规则和候选治理不得重新引入已删除的旧范围对象。`zone / professional / subproject / custom`、`zone_object_id`、`professional_object_id`、`scope_dimensions`、`project_scope_dimensions` 和 `/api/scope-dimensions` 只能作为历史数据清理或审计线索，不得作为新规则资产的作用域字段、运行期消费字段或兼容适配入口。

口径澄清：部分算法 seed、工期因子或模板 metadata 中可能继续出现 `zone`、`sameZone`、`scopeGranularity: zone` 等业务维度词。这些只能表示施工空间、流水段、现场拥挤维度或 `physical_zone` 语义别名，不得解释为已删除的 `zone` 工程对象类型；新增 schema、候选 payload、override payload 和导入 payload 必须使用 `physical_zone` / `physical_zone_object_id` 或更明确的业务事实字段。

## 14. 验收标准

满足以下条件才算通过：

- 不同公司不会读到彼此的 override 和候选
- 公司学习不会改写系统 seed
- 候选资产不能直接影响运行结果
- 现有 seed / 算法 / 规则资产自带学习能力只能按登记的 `publish_anchor + automation_maturity` 生成候选、证据、回放摘要、受控发布请求或异常仲裁请求，不能绕过统一资产治理协议自由发布
- 可自动发布 seed / 算法 / 规则资产只能表示“该资产实例、资产类和作用域允许进入自动发布门禁”；最终发布必须证明其属于 `trusted_source_auto_publish` 或 `guarded_runtime_auto_publish`，且 `automation_maturity` 已达到对应 `auto_canary / auto_publish` 门槛，并留下来源、回放或 shadow、版本、回滚和作用域证据；实际写入只能由统一发布出口和资产类型专属 writer 执行，并经消费者验证，不能由 seed、算法、候选 adapter 或大模型直接写入
- “可自动发布 seed / 算法 / 规则资产”只适用于已明确声明允许自动发布的资产实例、资产类和作用域；本地 `published / auto_published / published profile` 名称、可信来源名称或样本通过，不能把当前不得自动发布的 seed / 算法 / 规则资产转换为可自动发布
- 明确要求当前不得自动发布的 seed / 算法必须进入 `manual_governance_required` 或同等级锚点，不得被单个候选直接触发自动发布；同时必须生成 `automation_unlock_criteria` 和更多验证需求，作为后续自动化成熟度提升依据
- 锚点升级本身必须作为治理资产验收：具备策略版本、适用资产类、证据阈值、影响面、回滚目标、审计记录和门禁测试；不得由大模型、业务算法、单个候选或单次 replay 直接修改 `publish_anchor / automation_maturity`
- 高风险资产必须先自动生成治理包、冲突检测、replay / shadow 证据、canary 建议、停止条件和 rollback target 建议；在成熟规则、资产类型专属 writer、消费者验证和可执行回滚未明确前，不得由单个候选直接自动发布到 runtime
- 自动治理通过不等于自动发布通过；验收时必须能区分 `candidate_only / auto_review_package / auto_shadow / auto_canary / auto_publish`
- 自学习通过不等于 live 自我升级；验收时必须能区分 `frozen_constant / shadow_report_only / governed_candidate / guarded_live_tuning / system_curated_learning`
- `auto_canary / guarded_live_tuning` 验收必须证明 canary-aware 消费者、作用域 / 流量边界、停止条件、监控指标和可执行回滚同时存在；否则只能算 shadow / canary 建议，不得进入 stable runtime 消费
- 回滚验收必须验证资产类型专属 writer 已完成撤销、降级或 disable，且对应消费者不再读取被回滚版本；只有 rollback target、rollback audit 或 rollback event 不能算真实 runtime 回滚闭环
- 业务事实本身不得被自学习链静默升级或改写；学习链只能从业务事实生成候选、证据、样本健康、参数建议、policy 更新或治理包，并继续通过本章发布门禁
- 所有影响工期、计划网络、关键路径、模板结构、依赖顺序、风险预警和健康解释的资产都必须完成四元登记：`learning_target + learning_maturity + publish_anchor + automation_maturity`；验收不得只以 `standard_work_duration` 已收敛作为工期相关资产已闭环的证明
- 后续新增的工期相关资产必须被自动发现链路捕获并进入登记 / reviewItems / blockers / 候选事件 adapter 之一；不得因没有手工写入本文件清单而绕过治理，也不得静默成为 runtime 规则
- 所有会影响算法输出的权重、阈值、乘数、blend 阶梯、置信度扣分和 canary 停止条件，都必须在可学习参数注册表或资产视图中登记；未登记参数按冻结常量处理；具体参数建议实例必须转成候选事件并通过 release-exit / domain adapter，不能由学习服务直接写 runtime
- base 工期收敛、预测误差残差 overlay、工期上下文因子学习必须分别验收；不得把 P50/P75 样本收敛扩大解释为模型结构、候选权重、乘数和置信度公式都已经自学习
- 小公司和低频工序的冷启动必须有匿名行业 / 分层共享基线作为只读参考；同时必须证明不会读取其他公司的 company override、项目样本明细、候选结果或回放样本
- 样本健康必须可观测：accepted / weak / rejected 数量、拒绝原因、降级原因、长尾冻结率、冷启动覆盖率和可补全建议必须进入后台治理摘要；非工期业务完成样本必须以 `benchmarkEligible=false` 和 domain metadata 区分，不能混入工期 benchmark
- 大模型生成或改写的规则、Seed、模板、参数、解释链和候选 payload 默认不得直接进入 runtime，必须先进入候选事件、隔离池或后台治理队列
- `publish_anchor / automation_maturity` 本身属于发布门禁资产，修改它们必须经过已登记锚点升级策略、同等级治理记录、回放证据、审计记录和回滚目标，不得由业务算法或大模型直接改写
- 冲突资产能被隔离并留下证据
- 新候选与当前已有规则冲突时，runtime 继续消费既有 active / published 规则，直到冲突仲裁明确允许替换
- 人工或平台异常仲裁形成的批准、驳回、回滚等治理结论必须反哺为自动治理证据、验证规则或反例，避免同类场景长期重复人工处理；反哺结果不得直接放宽 `publish_anchor / automation_maturity`，也不得追溯发布原候选
- 系统级晋升验收必须证明优先证据来源是多项目 / 多公司 / 多场景自动验证，而不是人工逐条审批；但自动验证只形成发布前置证据和门禁结论，不自动改写系统 seed。人工或平台异常仲裁只处理自动验证无法裁决的异常、边界扩大和合规安全事项
- 回放报告能说明为什么晋升或拒绝
- 普通业务页不暴露技术字段
- 所有新增治理指标都已注册到统一指标口径
- 自动发现阶段允许可分类未确认项进入 `reviewItems`；阶段 1-3 登记完成验收时，`algorithmRuleAssetInventoryService` diagnostics 与自动发现报告不得仍存在重复资产 key、未登记 algorithm seed 类型、缺治理能力的 algorithm seed、未登记的当前扫描项，或作用域 / 消费者 / 运行影响不可分类的 blockers
- `reviewItems=0 / blockers=0` 只作为当前代码快照的准入健康证据；后续新增代码、旧对象重扫、专项 adapter 接入、LLM 生成候选或迁移回放结果出现时，必须重新运行自动发现并重新判定，不能沿用旧快照放行
- 资产只读台账、准入门禁和相关路由测试通过；治理动作仍按公司管理员和公司空间校验执行
- 新增候选、override、导入和 replay payload 均不得重新引入 `zone_object_id / professional_object_id / scope_dimensions / project_scope_dimensions` 等旧对象字段

## 15. 不做的事

- 不做全新独立算法中心前端页
- 不做跨公司自动混训
- 不做系统 seed 的静默改写
- 不允许各 seed / 算法以“自学习”“自动升级”为名绕过统一候选、冲突、回放、发布门禁和回滚门禁；也不允许单个候选把当前不得自动发布的强锚点直接升级为自动发布
- 不把“自动治理已通过”偷换成“自动发布已允许”；高风险资产在成熟规则未明确前只能自动生成治理证据、shadow / canary 建议和回滚建议，不直接写 runtime published 版本
- 不把 `auto_canary / guarded_live_tuning` 偷换成稳定生产发布；没有 canary-aware 消费者、边界、停止条件、监控和回滚执行链时，不得进入 stable runtime
- 不把 `rollback audit / rollback event / rollback target` 偷换成真实 runtime 回滚；缺资产类型专属 writer 和消费者验证时，只能算回滚待执行或回滚审计
- 不把业务事实当成可被 seed / 算法自动改写的发布结果；业务事实只能作为学习证据输入，仍由各自业务章节和用户操作链路管理
- 不把“有 MAE / 有 reward / 有 bandit 推荐 / 有 replay 报告”偷换成“已经 live 自动改模型”
- 不把 base 工期 P50/P75 收敛偷换成所有模型结构、权重、乘数、置信度扣分和阈值都已自学习
- 不允许小公司样本不足时直接跨公司混训；只能消费匿名行业 / 分层共享基线
- 不允许完成样本因缺日期、缺工序码或质量降级而静默丢弃；必须进入样本健康统计
- 不把人工治理当成长期默认终态，也不把人工逐条审批当成系统级晋升的默认路径；但这不是当前放开自动发布的许可。人工或平台异常仲裁结果必须先沉淀为自动化解锁条件、验证规则或反例，再通过版本化锚点升级和发布门禁重新判定
- 不把资产治理动作强塞进普通业务页
- 不用“看起来更聪明”的方式绕过审计、回放和回滚

```text
4. 候选规则、公司 override、项目 override、回放结果和冲突记录不得因为“自动发现”而自动发布；仍需通过本章的作用域、证据、冲突、回放、回滚、发布锚点和自动化成熟度规则。
5. 发现阶段的手工登记缺失不再直接阻断普通业务发现流程，但仍阻断发布、runtime 生效和系统级晋升；高风险不可分类、跨公司作用域不明、消费者不明、回滚边界不明或候选 / 正式边界不明必须进入 blockers。最终验收阶段必须清理或裁决未确认的高风险项。
6. 自动发现报告中出现 reviewItems 时，表示后台治理待确认；不表示普通业务功能失败，也不要求前端隐藏已经可用的业务能力。但 reviewItems 不得被 runtime 消费，也不得作为发布前置条件已满足的证据。阶段 1-3 完成验收时，当前代码事实的 reviewItems 应归零；后续新增代码如再次出现 reviewItems，应在同一自动登记链路中补齐。
7. 后续新增服务、seed、模板、依赖规则、预测参数、风险阈值或指标口径，只要会影响工期、计划网络、关键路径或计划解释，就必须由自动发现链路纳入治理；自动发现无法判断作用域、消费者或运行影响时，进入 blockers，不得静默进入 runtime。
8. 自动发现必须输出是否属于工期相关资产、影响的 `learning_target`、默认 `learning_maturity`、默认 `publish_anchor` 和默认 `automation_maturity`；缺字段时按候选或冻结处理，不能推断为可 live 升级。
```

### 与公司隔离关系

```text
system_seed：只有已证明系统级 active / published 版本、发布记录、消费者验证和 rollback target 的系统资产，才可跨公司只读复用；否则只能作为 system observation / legacy audit。
company_candidate：必须带 company_id，只在当前公司内学习、评估和生成治理证据，不具备发布权。
company_override：必须带 company_id；seed / override 类资产只能由统一发布出口和 seed / override 专属 writer 写入，并在当前公司内按版本回滚。
project_candidate：必须带 project_id，并可通过项目推导 company_id，只在当前项目内学习、评估和生成治理证据，不具备发布权。
project_override：必须带 project_id，并可通过项目推导 company_id；seed / override 类资产只能由统一发布出口和 seed / override 专属 writer 写入，并在当前项目内按版本回滚。
unknown_scope：只能进入 system observation 或治理复核，不进入运行期。
```

上述关系只说明作用域隔离。执行时不得把 `company_override / project_override / system_seed` 泛化成所有资产的物理写入表；非 seed 资产必须先找到对应的参数 publication、policy audit run、模板 runtime writer、overlay 表或样本健康表等专属落点，缺落点时进入 reviewItems / blockers 或候选审计。

自动发现层如果只能识别服务或文件存在，但无法判断其公司 / 项目作用域，则该资产进入 blockers；如果可以判断作用域但缺少正式证据、版本、回放或消费者矩阵，则进入 reviewItems。

### 旧对象处理补充

旧 seed、旧候选、旧经验工期、旧 WBS 模板、旧数据质量规则和旧指标规则如缺少作用域，不因本次自动发现准入而删除；但不得自动升级为公司私有经验或项目运行期规则。历史对象只能按以下顺序处理：

```text
1. 可由 project_id 推导公司：迁移为项目级历史资产。
2. 已有 company_id：保留为公司级历史资产。
3. 无法推导作用域：保留为 system observation / legacy audit，不参与公司 runtime。
4. 与当前正式规则冲突：进入 quarantined 或 review_required，不直接覆盖 active / published 规则。
```
