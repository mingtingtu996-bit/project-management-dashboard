## 0. 2026-06-01 final range-tree boundary (authoritative)

This v1.4-series plan follows the final range-tree model. There is no production history or existing user data that needs a compatibility layer.

Authoritative engineering object types are exactly: `phase / section / building / basement / floor / physical_zone / functional_area`.

The following compatibility surfaces are deleted and must not be reintroduced in runtime code, migrations, or frontend contracts:

- `zone / professional / subproject / custom` as engineering object types.
- `zone_object_id / professional_object_id` task fields.
- `project_materials.professional_object_id` and `engineering_categories.professional_object_id`.
- `legacy_object_type`, deprecated object-type arrays, legacy bridge/backfill helpers, and old scope adapter functions.
- `/api/scope-dimensions`, `scope_dimensions`, and `project_scope_dimensions` as active application surfaces.

Professional/system/domain/method semantics remain business facts through `specialty_type`, `engineering_category_id`, `standard_work_code`, template metadata, and project profile facts. They are not range-tree objects.

Any older section in this document that mentions deleted object types, deleted fields, old scope tables, or compatibility adapters is superseded by this boundary.
# v1.4.19 项目健康度与偏差分析体系执行方案

## 1. 目标

v1.4.19 的目标是把当前分散在 `Dashboard / Reports / 项目健康度 / 进度偏差 / 公司驾驶舱 / 周报 / 计划健康横幅 / 风险问题 / 里程碑 / 数据质量` 里的健康判断和偏差分析统一成一套稳定的“项目健康度与偏差分析体系”。

本章解决的是系统能否稳定回答这些问题：

```text
项目现在到底健康不健康
健康分是业务执行问题，还是数据可靠性问题
项目偏差到底是相对基线、相对月计划，还是相对当前任务列表
同一个延期、阻碍、风险、关键路径异常，在 Dashboard、Reports、周报和 AI 中是否口径一致
基线和月计划作为历史承诺快照，是否只参与对比和考核，不被当前任务列表反写
任务列表作为实时事实，是否成为动态判断、下一轮计划生成和健康趋势的核心输入
数据质量低时，是业务健康差，还是分析结论可信度低
旧健康分、旧偏差接口、旧快照、旧前端局部计算如何兼容
```

本章继续沿用 v1.4.8 之后形成的统一原则：

```text
用户维护业务事实，系统判断治理语义
前端展示业务结果，不展示公式、权重、SQL、rule_code、confidence_formula 等技术字段
健康度是项目业务执行状态，不是数据质量评分
数据可靠性只影响可信度、封顶、可用性提示和分析解释，不直接混入业务风险问题
项目基线、月度计划是历史承诺快照；任务列表是实时执行事实
偏差分析只用于对比、解释、提示和下一轮计划算法输入，不要求用户日常逐条修复历史差异
```

### 3.2.1 工期体系消费边界（2026-06-13 收口）

v1.4.19 只消费工期体系的派生结果，不再重新定义计划工期、施工生产日、参考工期或剩余工期。

权威来源固定为：

```text
计划工期：inclusiveDurationDays，由任务计划开始 / 完成日期形成。
施工生产日偏差 / 延期：constructionCalendar + delayDayDelta，周末默认照算，只扣施工停工窗口。
执行中剩余工期：taskDurationForecastService。
项目整体剩余工期：projectRemainingDurationForecastService。
关键路径工期压力：projectCriticalPathService。
父节点计划工期：wbsPlanRollupService。
```

偏差分析三条主线只允许在参照系上不同：

```text
baseline：对生效 / 锁定基线版本。
monthly_plan：对当月承诺版本。
execution：对当前任务实时计划和执行事实。
```

三条主线不得因为私有天数公式而不同。所有 `deviation_days`、延期原因、健康分中的进度兑现、周报中的偏差摘要、CompanyCockpit 中的工期压力，必须消费同一套生产日 helper 或后端摘要字段。前端不得用 `Date.now() - getTime()`、`86400000` 或本地 `daysBetween` 重新生成偏差、延期、滞后或健康分解释。

健康度中的工期类信号只解释业务执行状态：

```text
参考工期偏离 = 计划合理性解释，不直接等于健康扣分。
剩余工期预测变差 = 执行趋势压力，可进入健康趋势和风险提示。
关键路径 float 变小或关键链延长 = 关键路径压力，可进入健康原因。
数据质量缺口 = 可信度 / 可用性提示，不直接混入业务健康分。
```

## 4. 核心口径

### 4.1 三层计划对象 + 一层实时事实

健康度与偏差分析必须以 v1.4.7 的计划治理模型为基础：

```text
项目基线：历史承诺快照，用于长期目标对比和版本考核
月度计划：历史承诺快照，用于当月兑现率和滚动计划对比
任务列表：实时执行事实，是当前项目健康、风险、阻碍、进度、下一轮生成算法的核心
实际执行事实：实际开始、实际完成、进度快照、阻碍、条件、风险、验收、材料等现场事实
```

规则：

```text
基线和月计划一旦发布 / 确认，即成为历史快照
历史快照不被任务列表实时变化反写
任务列表变化可以改变当前健康度、当前偏差、下一轮基线 / 月计划建议
当前任务依赖、关键节点、风险、阻碍与历史快照不同，不要求用户日常逐条处理
只有生成新一轮基线 / 月计划时，系统把差异作为算法候选提示给用户选择是否采纳
```

### 4.2 健康度不是数据质量分

健康度回答：

```text
项目业务执行状态是否健康
当前进度兑现是否稳定
关键节点是否受影响
风险、问题、阻碍是否对执行产生影响
月计划和基线是否偏离严重
```

数据可靠性回答：

```text
这些健康和偏差结论是否可信
数据缺口是否影响分析
是否需要补充字段、修正映射、校准对象
```

执行要求：

```text
projectHealthService 需要拆分 businessHealthScore 与 dataConfidenceScore
业务健康分不直接把数据质量当作一个业务扣分维度
dataConfidenceScore 只参与 healthConfidence、metricAvailability、scoreCap、analysisNote
Dashboard 可同时展示“健康度”和“数据可靠性”，但二者文案和含义必须分开
Reports 偏差分析只在必要时展示数据可靠性摘要，不做固定大卡片扩散
```

### 4.3 健康度五类业务维度

v1.4.19 后项目健康度固定为五类业务维度：

```text
进度兑现：当前进度相对计划进度、延期天数、S 曲线偏离
执行稳定：任务完成率、进行中任务稳定性、长期停滞、90%-99% 收尾停滞、关键路径任务影响
关键目标：里程碑、关键节点、关键验收、关键路径节点是否逾期或受影响
异常影响：业务风险、问题、阻碍、预警链是否影响执行
计划治理：基线、月计划、任务列表之间是否存在需要在下一轮计划处理中关注的重大偏差
```

数据可靠性不作为业务维度，但作为独立可信度：

```text
数据可靠性高：健康分正常展示
数据可靠性中：健康分展示，附带“部分数据待完善”
数据可靠性低：健康分展示但标记“结论可信度较低”，严重时封顶或显示“待完善”
无法评估：显示“暂无健康度”，不显示 0 分或 100 分
```

### 4.4 偏差分析三条主线

偏差分析固定三条主线：

```text
基线偏差：已发布基线 vs 当前执行事实，用于长期目标偏离分析
月度兑现偏差：已确认月计划 vs 当前执行事实，用于当月承诺兑现分析
执行偏差：当前任务计划 vs 当前执行事实，用于实时执行跟踪
```

规则：

```text
基线偏差不得要求用户把任务列表改回旧基线
月度兑现偏差不得要求用户把任务列表改回旧月计划
执行偏差服务当前项目管理和下一轮计划生成
偏差原因优先来自阻碍、开工条件、风险问题、材料、图纸证照验收、关键路径影响
无法归因时显示“待识别原因”，不强行归入风险或问题
```

### 4.4.1 偏差原因展示口径

偏差原因展示要真实反映建设工程现场实际情况，不把所有偏差简单归结为“延期”或“责任单位问题”。

系统判断偏差原因，用户只维护现场业务事实：

```text
用户维护：进度、实际开始 / 完成、阻碍、风险问题、材料、图纸、证照、验收、责任主体、关键节点等业务事实
系统判断：偏差属于计划偏离、现场受阻、外部条件未满足、关键目标受影响、责任归因还是数据可靠性不足
前端展示：展示业务语言，不展示 source_type / rule_code / SQL / confidence_formula
```

偏差原因按以下优先级归因：

```text
1. 关键目标影响：关键路径、关键节点、里程碑、关键验收受影响
2. 现场执行受阻：阻碍、风险、问题、连续停滞、收尾停滞
3. 外部条件影响：图纸、证照、材料、验收、前置节点、开工条件未满足
4. 计划承诺偏离：基线、月计划、当前任务计划与实际执行偏离
5. 责任与组织归因：责任单位、责任人、参建单位、专业、工程对象范围
6. 数据可靠性不足：缺少必要事实、来源映射不稳定、历史兼容字段无法确认
7. 待识别原因：以上依据均不足，不能硬归因
```

展示文案应贴近现场：

```text
关键路径任务已延期，影响主体结构节点
材料未到场，导致砌筑工序进度滞后
图纸未通过，相关机电安装任务无法按计划展开
验收未通过，影响后续装饰装修工序
本月计划兑现偏低，主要集中在消防专业
当前任务已恢复推进，历史月计划仍存在兑现偏差
原因待识别，需要继续观察现场进度和阻碍变化
数据来源不完整，本条偏差结论可信度较低
```

数据可靠性不足只能影响结论可信度和提示语，不得包装成业务风险、业务问题或现场阻碍。

现场领域知识类偏差原因必须承接 v1.4.7.4 / v1.4.18 的统一上下文，不新增用户维护入口：

```text
季节产能影响：来自 calendar_productivity_factor，用于解释春节、雨季、冬期等产能折扣导致的目标进度偏差
验收时间轴影响：主要来自 acceptance_plans / acceptance_records，用于解释前道工序完成后因验收计划未通过、未到计划验收日、验收资料未闭合或验收条件未满足导致的后道工序延后；不得凭任务标题或默认天数直接归因。若同一重大验收在任务列表和验收时间轴同时存在，偏差归因按 acceptance_plans 单一事实读取 planned_date / actual_date / status，不按任务标题重复生成一条验收时间影响。
流水段节奏偏差：来自 workflow_sequence_factor，用于解释同楼栋同楼层串行、不同楼栋并行节奏与当前计划不一致
现场承载压力影响：来自 resource_conflict_factor，用于解释同楼栋、同工作面、同责任单位、同类工序任务并行过密、近期推进偏慢、资源类开工条件未满足、资源类阻碍未解除或关联材料到货逾期造成的执行压力；偏差归因时必须以任务推进情况作为主证据，责任单位 / 工作面 / 同类工序重叠只作为背景证据，材料 / 条件 / 阻碍只作为原因解释和增强证据；推进偏慢判断必须承接剩余工期算法的工序曲线，验收、养护、检测、移交等待类任务不得因线性日期进度偏低被误判为资源压力
现场承载压力归因必须读取工序语义元数据：显式 standard_work_code / standard_task_metadata 优先，standard_work_duration_seed 的 durationContributionMode / executionNature 次之，标题弱识别仅作低置信兜底。resource_class_mapping 只承接标准工序到现场资源类别的映射，不重新解释任务标题；同名或近义场景必须由 standardWorkCodes / standardCatalogCodePrefixes 分流，不能按关键词数组顺序决定。resourceClass / resourceOperationType 只回答“是什么资源、发生什么资源行为”，pressureDimensionScores / dominantPressureDimensions 只用于把偏差解释成 labor / material / equipment / workface 四类压力来源；前端仍统一展示为“现场承载压力”，不新增资源维度组件。若任务被识别为 quality_gate、external_wait、record_only、handover_marker 或非 physical_work，不得作为“资源排不开”的主因，只能作为等待、门禁、资料或移交类次因说明。
执行态推断事实必须承接 `runtimeExecutionInferenceService`：资源压力、并行密度 / 施工节奏、里程碑压力和证据标签只能由已有任务状态、进度、实际日期、阻碍、关键路径 / 浮动、里程碑和 schedule-state 窗口反推；不得要求用户补填真实班组、真实工作面、塔吊小时、施工电梯占用或楼栋每日节拍。健康度和偏差归因消费 `evidenceObjects / runtimeInferenceSummary`，置信度不足时只能解释为 `advisory_only / confidence_only`，不能作为强风险、强延期或强资源不足结论。
工序硬约束未满足：来自 process_constraint_factor，用于解释养护、拆模、隐蔽验收、工艺前置等物理或工艺约束未满足
上游依赖等待：来自 `task_duration_forecasts.calculation_context / metadata.forecastSources.dependencyPropagation` 的 `blockingDependencies`，并用 `task_dependencies` 或 `tasks.preceding_task_id` 佐证任务关系；只在预测事实已经给出 `dependencyTaskId / waitDays / floorRemainingDays` 且上游任务仍未完成时进入 `attribution.cause_chain`。该链回答“谁造成了这次等待”，不是重新计算剩余工期，也不是把 workflow_sequence_factor 调得更准。
开工条件 / 阻碍责任：来自 `task_conditions.responsible_unit / participant_unit_id / responsible_person` 与 `task_obstacles.responsible_unit / responsible_person`；这些字段只在对应条件未满足或阻碍仍 active 时生成 `cause_chain`，用于回答“谁应解除这个条件或阻碍”。如果字段缺失，只能保留为条件 / 阻碍原因说明，不得把责任默认扣到当前任务 owner。
```

展示规则：

```text
这些原因作为偏差分析的主因或次因展示，不要求用户新增维护动作
高置信原因可作为主因，例如“验收时间轴未闭合影响后续装饰工序”
中低置信原因只能作为次因或可信度说明，例如“可能存在现场承载压力影响”
只有排期重叠或承载上限超限但任务推进正常时，不得将现场承载压力列为主因，只能作为“排期较密，需观察现场推进”的次因或置信度说明
同责任单位多个任务推进偏慢、连续多天推进不足、临近完成但进度低，且叠加条件 / 阻碍 / 材料长期未解决时，现场承载压力可以作为主要偏差原因
现场承载压力、季节产能、填报异常等不得被自动包装成风险、问题或阻碍
偏差原因展示位置仍在 Reports 偏差列表 / 详情原因链，不进入生成新一轮基线 / 月计划弹层
现场承载压力原因从 task_duration_forecasts.factor_summary.resource_conflict 聚合，展示为“现场承载压力”，不得展示为“资源冲突”或暗示系统已完成精确人材机排程
```

## 10. 健康分算法

### 10.1 业务健康分

初始默认权重：

```text
进度兑现 30%
执行稳定 25%
关键目标 20%
异常影响 15%
计划治理 10%
```

说明：

```text
权重只在后端配置，不前端展示
权重变化必须记录 health_caliber_version
权重变化不重算历史快照
健康分不得按任务条数简单平均
任务完成率只作为辅助指标
核心进度应优先按现有应用和 v1.4 系列落地后可稳定获得的数据综合计算，包括计划工期、WBS 层级、关键路径、关键节点、工程对象、任务状态、进度快照、实际开始 / 实际完成、阻碍、风险问题、材料、图纸证照验收和业务影响
工程量只有在 v1.4.3 / 后续计量字段已稳定维护、单位口径清晰、可按任务或 WBS 节点可靠归集时才参与权重
当前缺少稳定工程量数据时，不得为了算法完整性假造工程量权重，应以计划工期、WBS 层级、关键路径、关键节点和业务影响作为主权重
零星小任务完成不能掩盖关键工序、关键材料、关键验收、关键路径未兑现的问题
```

无基线 / 无月计划场景：

```text
项目尚未发布基线时，基线偏差主线标记为 not_applicable，不扣业务健康分
项目尚未确认月度计划时，月度兑现偏差主线标记为 not_applicable，不扣业务健康分
项目阶段已经要求发布基线或确认月计划但仍缺失时，进入计划治理维度和数据可靠性提示
新项目准备期不因缺少基线或月计划直接判定为危险
```

### 10.2 可信度与封顶

```text
数据可靠性 >= 85：不封顶
70 <= 数据可靠性 < 85：健康分正常展示，标记“部分数据待完善”
50 <= 数据可靠性 < 70：健康分最多展示到 80，并提示“结论可信度较低”
数据可靠性 < 50：健康分最多展示到 65，并提示“关键数据待完善”
无法评估：健康分显示暂无，不用 0 冒充真实健康差
```

### 10.3 强制封顶场景

```text
无可评估任务：最高 55 或显示暂无，按项目阶段判断
关键路径任务严重受影响：最高 65
关键里程碑逾期：最高 70
高等级业务风险 / 问题存在：最高 75
活跃阻碍较多且影响关键任务：最高 80
数据可靠性低：按 10.2 封顶
多个封顶规则同时命中时，最终展示分取所有封顶上限中的最低值
capReasons 必须保留全部命中的封顶原因，不只保留最低封顶原因
```

## 11. 偏差分析输出

偏差分析必须使用现有应用和 v1.4 系列落地后已有的稳定数据，不得假设不存在或尚未稳定维护的数据字段。

偏差严重程度按以下优先级判断：

```text
第一优先级：关键路径、关键节点、里程碑、关键验收是否受影响
第二优先级：基线 / 月计划 / 当前任务计划的应达进度与实际进度偏离
第三优先级：计划工期、剩余工期预测、延期天数、长期停滞、90%-99% 收尾停滞
第四优先级：WBS 层级、工程对象范围、专业、责任主体、专项事实归因
第五优先级：工程量；仅在工程量字段稳定、计量单位清晰、可归集到任务或 WBS 节点时参与计算
```

规则：

4. 编辑态共享计划树已有的行级校验和健康横幅继续负责可定位问题，不把所有数据质量诊断都塞进健康横幅；`governanceSignals` 只承接需要计划域转译的门禁、确认、提示和解释信号。
