## 0. 2026-06-01 final range-tree boundary (authoritative)

This v1.4-series plan follows the final range-tree model. There is no production history or existing user data that needs a compatibility layer.

Authoritative engineering object types are exactly: `phase / section / building / basement / floor / physical_zone / functional_area`.

The following compatibility surfaces are deleted and must not be reintroduced in runtime code, migrations, or frontend contracts:

- `zone / professional / subproject / custom` as engineering object types.
- `zone_object_id / professional_object_id` task fields.
- `project_materials.professional_object_id` and `engineering_categories.professional_object_id`.
- `legacy_object_type`, deprecated object-type arrays, legacy bridge/backfill helpers, and old scope adapter functions.
- `/api/scope-dimensions`, `scope_dimensions`, and `project_scope_dimensions` as active application surfaces.

Professional/system/domain/method semantics remain business facts through `specialty_type`, `engineering_category_id`, `standard_work_code`, template metadata, and project profile facts. They are not range-tree objects.

Any older section in this document that mentions deleted object types, deleted fields, old scope tables, or compatibility adapters is superseded by this boundary.
# v1.4.10 责任主体体系执行方案

## Summary

v1.4.10 的目标是把当前应用里分散在 `任务 / 材料 / 验收 / 开工条件 / 风险问题 / 责任主体分析 / 任务总结 / Dashboard / 报表 / 预警` 中的责任归属统一成稳定口径。

本章只治理责任主体，不扩展成完整权限体系、审批体系、合同主体体系或组织架构体系。

责任主体拆成两类：

```text
责任人：具体执行或推进的人，可以来自项目成员，也可以是临时录入的人名
责任单位：参建单位、分包单位、部门或组织主体，必须来自参建单位台账
```

本章最关键的口径：

```text
责任人可以自由编辑
责任单位不允许自由编辑，必须从 participant_units 选择
任务列表允许维护责任归属事实
项目成员入口维护正式责任人主数据
参建单位入口维护正式责任单位主数据
系统负责把任务上的责任事实收口为稳定 ID、统计口径、提醒对象和数据质量提示
```

本章继续遵循 v1.4.8 之后的统一原则：

```text
用户维护业务事实，系统判断治理语义
能由系统自动识别、匹配、归集和提示的，不新增弹窗或必填项打断现场录入
普通前端不展示 source、lineage、confidence、mapping_reason 等治理字段
```

## Business Definitions

### 1. 责任人

责任人回答：

```text
这项任务、验收、图纸、证照或条件由谁推进？
系统是否能把提醒、预警、复盘和责任分析关联到某个项目成员？
```

责任人允许两种形态：

```text
正式责任人：有 assignee_user_id / responsible_user_id，关联 project_members / users
临时责任人：只有 assignee_name / responsible_person 文本，尚未关联项目成员
```

责任人 ID 边界：

```text
assignee_user_id / responsible_user_id 写入 users.id，不写 project_members.id
project_members 只用于判断该 user 是否属于当前项目、是否可选、是否可接收项目内提醒
如果 users.id 存在但不在当前 project_members 中，后端拒绝作为正式责任人写入，并提示先加入项目成员
待关联责任人匹配成功后，写入 users.id，同时保留 assignee_name / responsible_person 作为当时显示名
历史数据中已存在 assignee_user_id / responsible_user_id 但该用户不属于当前 project_members 时，不自动清空 ID，不阻断查看；进入“非项目成员责任人”治理项，用户在团队管理中处理
新写入和编辑保存必须执行项目成员校验，不能继续写入非项目成员 user id
```

责任人允许自由编辑的原因：

```text
现场经常存在临时负责人、班组长、外部协作人、尚未加入项目的成员
自由输入能降低任务维护阻力
责任人文本污染对统计影响小于责任单位，且可通过待关联责任人逐步收口
```

责任人自由输入后的系统处理：

```text
任务可以保存
提醒精准送达不可用时退回项目 owner / 项目责任组
责任主体分析中进入“未关联责任人 / name:*”临时桶
成员新增后自动检测同名待关联责任人
用户可在团队管理的“待关联责任人”中批量关联
```

### 2. 责任单位

责任单位回答：

```text
这项任务、材料、验收、阻碍、风险或责任分析归属于哪家参建单位或责任组织？
系统是否能按单位稳定统计进度、材料、阻碍、验收和预警？
```

责任单位只允许一种权威形态：

```text
participant_unit_id
```

责任单位唯一性边界：

```text
participant_units 必须在同一 project_id 内具备可匹配唯一性
同项目内忽略首尾空格和大小写后，不允许存在两个 active 单位同名
project_id 为空的全局 participant_units 不作为 v1.4.10 责任单位来源
历史全局单位如需继续使用，必须复制或迁移为具体项目下的 participant_units
历史上已存在重复名称时，先进入台账清理或停用其中一个，不自动回填 participant_unit_id
导入、回填、复制粘贴遇到重复名称时，不能猜测选择哪一个单位，必须返回“责任单位名称重复，请先维护台账”
```

责任单位不允许自由输入的原因：

```text
责任单位是 BI、驾驶舱、材料、验收、阻碍、任务总结和责任主体分析的核心统计维度
自由输入会造成同一单位多种写法，污染统计口径
单位数量多、简称多、部门多，靠文本难以长期治理
```

责任单位的用户操作口径：

```text
任务列表、任务弹窗、材料、验收、开工条件、阻碍相关入口只能选择 participant_units 中的单位
如果目标单位不存在，用户先点击“维护台账”新增单位，再回来选择
不提供“手工输入责任单位”作为新数据入口
```

### 3. 责任归属事实

任务列表允许编辑责任主体，但编辑的是任务责任归属事实，不是直接维护主数据。

```text
任务责任人：写入 assignee_user_id + assignee_name，或仅写入 assignee_name
任务责任单位：写入 participant_unit_id，同时由后端回填 responsible_unit / assignee_unit 兼容展示
```

## Core Design

### 1. 主数据分层

```text
project_members：项目成员主数据，维护正式责任人
participant_units：参建单位主数据，维护正式责任单位
tasks：任务责任归属事实
acceptance_plans：验收责任归属事实
project_materials：材料责任单位归属事实
responsibility_watchlist / responsibility_alert_states：责任主体治理结果
```

责任主体不新增一张“大一统责任主体表”。人和单位业务含义不同，主数据来源也不同，强行合并会让权限、通知、统计和台账维护变复杂。

### 2. 字段权威关系

```text
责任人权威字段：
  assignee_user_id / responsible_user_id

责任人兼容字段：
  assignee_name / assignee / responsible_person

责任单位权威字段：
  participant_unit_id

责任单位兼容字段：
  responsible_unit / assignee_unit
```

从 v1.4.10 开始，新写入规则固定为：

```text
责任人可以写文本
责任单位必须写 participant_unit_id
responsible_unit / assignee_unit 只允许后端根据 participant_unit_id 回填
前端不再把 responsible_unit / assignee_unit 当作可编辑字段
```

### 3. 旧字段定位

```text
responsible_unit / assignee_unit 不删除
保留用于历史展示、导出兼容、旧接口兜底和迁移提示
不再作为新数据录入入口
不再作为责任单位分组、预警、BI 统计和驾驶舱指标的权威来源
```

旧字段读取优先级：

```text
优先 participant_unit_id -> participant_units.unit_name
没有 participant_unit_id 时，responsible_unit / assignee_unit 只显示为“未关联责任单位：xxx”
统计分组进入 unassigned_unit / unresolved_unit，不进入正式单位桶
```

### 4. 责任主体分析口径

责任主体分析只按稳定 ID 做正式分组。

```text
责任人正式分组：assignee_user_id
责任人临时分组：assignee_name，仅作为待关联责任人
责任单位正式分组：participant_unit_id
责任单位未绑定：unassigned_unit / unresolved_unit
```

责任单位不得再出现：

```text
unit-name:总包
unit-name:三局
unit-name:机电部
unit-name:某某项目部
```

这些都应进入“未关联责任单位”治理桶，由用户到参建单位台账关联或新增。

### 5. 任务、基线、月计划关系

按 v1.4.7 的口径：

```text
任务列表是实时执行事实
项目基线和月度计划是发布时点的历史快照
责任归属发生变化时，任务列表实时更新
已发布基线 / 已发布月计划不被自动改写
生成新一轮基线或月计划时，系统从当前任务列表读取最新责任归属，并提示与上一轮差异
```

基线和月计划快照中继续保存：

```text
assignee_user_id
assignee_name
participant_unit_id
```

但快照不允许用 `responsible_unit / assignee_unit` 文本重建正式单位关系。

## Implementation Changes

### 1. 数据库

新增迁移，迁移号使用当前最大迁移号 + 1，不占用已存在编号。

必须补充参建单位生命周期字段：

```sql
alter table participant_units
  add column if not exists status text not null default 'active',
  add column if not exists archived_at timestamptz null,
  add column if not exists archived_by uuid null references users(id) on delete set null,
  add column if not exists archive_reason text null;

do $$
begin
  if not exists (
    select 1
    from pg_constraint
    where conname = 'participant_units_status_check'
  ) then
    alter table participant_units
      add constraint participant_units_status_check
      check (status in ('active', 'archived', 'disabled'));
  end if;
end $$;

create index if not exists idx_participant_units_project_status
  on participant_units(project_id, status);
```

生命周期状态语义：

```text
active：当前可用，允许新任务、材料、验收、开工条件选择和写入
disabled：临时停用，可由管理员恢复；历史记录和报表可展示，新写入不可选择
archived：历史归档，原则上不恢复；历史记录和报表可展示，新写入不可选择
普通责任单位下拉只展示 active 单位
```

必须补充同项目 active 单位名称唯一约束。加约束前必须先扫描并处理重复名称；如果存在重复，不允许跳过后继续执行唯一约束迁移，但可以先生成健康横幅问题和后台治理报告。

```sql
create unique index if not exists idx_participant_units_project_name_active_unique
  on participant_units(project_id, lower(btrim(unit_name)))
  where status = 'active';
```

project_id 为空的 participant_units 不再作为责任单位权威来源：

```text
新建 / 更新 participant_units 时 project_id 必填
历史 project_id 为空的单位，不参与任务责任单位回填、导入匹配、责任主体统计和责任单位下拉
如确需沿用历史全局单位，先复制到具体项目台账，再由用户或回填脚本使用该项目内 ID
```

participant_units 接口契约必须固定：

```text
GET /api/participant-units?projectId= 默认只返回 status = active 的单位，供任务录入、验收录入、材料录入和开工条件选择器使用
GET /api/participant-units?projectId=&status=all 返回 active / disabled / archived，供 ParticipantUnitsDialog 台账维护使用
GET /api/participant-units?projectId=&status=disabled 或 archived 只返回对应状态，供台账筛选使用
POST /api/participant-units 必须写入 project_id，默认 status = active，不允许创建 project_id 为空的全局单位
PUT /api/participant-units/:id 可更新基础信息和 status；恢复 disabled 时允许改回 active，archived 不作为普通恢复路径
```

## Assumptions

当前没有历史生产数据，所以 v1.4.10 不做复杂人工清洗工具，只做自动精确匹配和未关联提示。

责任人自由输入是为了现场效率；责任单位禁止自由输入是为了 BI、驾驶舱和责任主体分析稳定。

`participant_units` 仍作为责任单位主数据，不并入 `engineering_objects`。

`project_members` 仍作为项目成员主数据，不并入 `participant_units`。

责任主体页面继续保留，不回退到 TaskSummary；TaskSummary 只消费责任主体稳定 ID 做归属分析。

## 责任主体异常与履约洞察收口补强

2026-05-26 已按当前算法、seed 和规则资产口径补强 `responsibilityInsightService`：

```text
1. 责任主体异常阈值集中到 RESPONSIBILITY_HEALTH_RULES，避免服务内散落硬编码。
2. 完成/延期判断抽到 taskPerformance 共享工具，TaskSummary 的 taskAttributionSummaryService 和责任主体洞察复用同一完成任务延期语义。
3. unassigned_unit / unresolved_unit 只作为数据质量治理桶，不作为正式责任单位异常主体触发履约异常。
4. 重点承诺缺口继续以关键路径 / 里程碑延期任务为高权重解释，不升级为发布硬挡墙。
5. 风险压力保持解释型压力，已叠加风险/阻碍等级、持续时长、关键路径和里程碑影响，但不能替代真实履约事实。
6. site_capacity_pressure / resource_conflict 只能作为责任主体压力解释和置信度背景，不得仅凭排期重叠判定责任主体异常。
7. weeklyDigestService 已改为按 responsibility_alert_states.current_level = abnormal 消费 subject_key / subject_label / dimension 新字段。
8. 正式责任主体覆盖统一由 `responsibilitySubject` 工具判定：单位只认 `participant_unit_id`，个人只认 `assignee_user_id / responsible_user_id / assignee_id`。
9. `participant_unit_name / responsible_unit / assignee_unit / assignee_name` 仅保留为旧数据展示、提示和诊断线索，不再计入责任覆盖率、项目健康缺负责人豁免或正式责任单位覆盖。
10. `dataQualityService / projectHealthService / projectExecutionSummaryService` 已统一复用同一责任主体覆盖口径，避免数据质量、健康分、摘要指标之间互相漂移。
11. 旧版 `buildAlertReasonsLegacy` 已移除，告警原因只走 `buildAlertReasons + RESPONSIBILITY_HEALTH_RULES`，阈值和广播升级条件集中在规则资产内。
12. `RESPONSIBILITY_HEALTH_RULES` 显式声明 explain-only 压力信号：`site_capacity_pressure / resource_conflict`；`risk_pressure` 策略为 `explain_only_requires_execution_fact`，只能解释健康下降或履约压力，不能单独触发责任主体异常。
13. 责任主体异常阈值已从服务内散落常量收口到 `responsibilityHealthRuleSeed`，服务导出的 `RESPONSIBILITY_HEALTH_RULES` 由 seed 派生；后续如需公司级 / 项目类型级阈值，只扩展规则解析，不再改异常算法主体。
14. `risk_pressure` 已从 `风险数 + 阻碍数` 升级为 explain-only 加权压力分：纳入风险/阻碍严重度、关键路径影响、里程碑影响和最长未关闭天数；该分值只影响排序、解释和置信度背景，不进入 `buildAlertReasons` 硬异常触发。
15. 责任主体分析必须区分两种身份：`execution_owner` 是当前任务承办履约主体，`accountable_subject` 是由上游依赖、条件、阻碍或专项事实证据链指向的致因责任主体。二者可以是同一参建方，也可以不同，不能在统计桶里合并后再对外问责。
16. 过去偏差归因中的上游依赖、开工条件和阻碍问责由 `progressDeviationService.attribution.cause_chain` 提供，事实源为 `task_duration_forecasts` 的 dependencyPropagation、`task_dependencies`、`tasks.preceding_task_id`、`task_conditions`、`task_obstacles` 和相关 owner 字段；`responsibilityInsightService` 仍负责责任主体异常和履约洞察，不单独读取 `preceding_task_id` 来推断因果责任。
17. `responsibility_basis` 不是责任方身份，只是原因类别或证据类型，例如 site_capacity / external_wait / upstream_dependency。对参建方问责时必须同时展示 owner 身份、受影响任务、致因任务、证据来源、影响天数和置信度，不能只展示 basis。
18. 当 B 任务因上游 A 未完成、C 条件未满足或 D 阻碍未解除而延期时，B 的 owner 只能作为受影响 / 承办主体出现在执行视角；若 `cause_chain` 证据成立，责任贡献必须把 A / C / D 的 owner 列为 `accountable_subject`，并用 `causal_task_ids` 或 evidence 指回具体致因对象，禁止继续把责任默认扣到 B owner。
19. `responsibilityInsightService` 必须通过 `RESPONSIBILITY_INSIGHT_SCOPE` 固定算法身份：`model = execution_performance_insight`，`taskOwnershipBasis = tasks.execution_owner_fields`，`causalAttributionPolicy = excluded_use_progress_deviation_service`。它的 `person_rows / unit_rows` 只能用于履约异常、趋势、关注名单和恢复确认；正式问责必须回到 `progressDeviationService.responsibility_contribution.owner_id / impact_days / weighted_count / evidence_sources`。
20. 前端 `ResponsibilityView` 必须以“履约洞察”定位呈现，并提供“进度偏差归因”入口跳转到 Reports 执行偏差视角；页面上的异常、关注、恢复确认只表示履约管理状态，不替代问责证据链。
```

## 多公司空间与数据隔离统一口径

本文件执行时必须承接 `v1.4.20 权限角色与协作体系执行方案` 的多公司空间要求。除非本文件明确声明为 `system_seed`、全局字典或演示样例数据，否则所有项目级数据都必须先归属于项目，再通过项目解析到所属公司。

```text
所有新增表：优先包含 project_id；确属公司级数据时包含 company_id；确属系统公共数据时标记 scope = system_seed / global_dictionary。
所有查询：先按 currentCompanyId / company_id 隔离，再按项目权限过滤，不允许前端二次过滤替代后端隔离。
所有汇总：公司级汇总只统计当前公司项目；项目级汇总只统计当前项目；演示项目不进入真实公司汇总和真实项目统计。
所有引用：禁止跨公司引用任务、工程对象、范围维度、责任单位、图纸、证照、验收、风险、问题、预警、计划、模板沉淀和经验数据。
所有模板 / 经验数据：系统公共种子可跨公司复用；公司沉淀模板、公司经验工期、公司历史数据只能在当前公司内使用。
所有旧数据：没有 company_id 的历史数据在迁移时归入默认公司，并保留兼容读取；不得因为补公司空间而删除旧对象。
```
