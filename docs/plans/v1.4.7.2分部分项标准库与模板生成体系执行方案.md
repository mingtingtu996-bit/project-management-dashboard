## 0. 2026-06-01 final range-tree boundary (authoritative)

This v1.4-series plan follows the final range-tree model. There is no production history or existing user data that needs a compatibility layer.

Authoritative engineering object types are exactly: `phase / section / building / basement / floor / physical_zone / functional_area`.

The following compatibility surfaces are deleted and must not be reintroduced in runtime code, migrations, or frontend contracts:

- `zone / professional / subproject / custom` as engineering object types.
- `zone_object_id / professional_object_id` task fields.
- `project_materials.professional_object_id` and `engineering_categories.professional_object_id`.
- `legacy_object_type`, deprecated object-type arrays, legacy bridge/backfill helpers, and old scope adapter functions.
- `/api/scope-dimensions`, `scope_dimensions`, and `project_scope_dimensions` as active application surfaces.

Professional/system/domain/method semantics remain business facts through `specialty_type`, `engineering_category_id`, `standard_work_code`, template metadata, and project profile facts. They are not range-tree objects.

Any older section in this document that mentions deleted object types, deleted fields, old scope tables, or compatibility adapters is superseded by this boundary.
# v1.4.7.2 分部分项标准库与模板生成体系执行方案

## 1. 目标

v1.4.7.2 的目标是基于 `v1.4.7.1` 已经确定的共享计划树底座，在共享表格之上提供一套标准的分部 / 子分部 / 分项 / 工序模板库，并把"用户选择分部或分项后系统自动生成到最细工序"作为共享计划树的标准编辑能力之一。

```text
用户的目标不是写一份 200-2000 行的计划表
用户的目标是确认这个项目应当包含哪些分部分项,然后微调日期、责任和工程对象
模板库负责承担工序级标准结构、默认依赖、默认责任角色、默认开工条件、默认验收链接
共享计划树只负责把模板展开结果作为一次原子编辑写入编辑缓冲
用户随后可以撤销、可以微调、可以与其他编辑一起一次性保存
```

v1.4.7.2 不替代 v1.4.7.1。v1.4.7.2 只在 v1.4.7.1 已经定义好的"阅读态 / 编辑态 / 业务动作"三层模型上，新增一种叫"模板生成"的编辑操作和一类叫"生成任务"的阅读态业务动作。

两者的底座分工固定为：

```text
v1.4.7.1 = 共享计划树操作底座
负责阅读态 / 编辑态 / 保存 / 撤销 / 重做 / 协作 / 校核 / 列配置 / 大图视图

v1.4.7.2 = 共享计划树标准模板输入底座
负责分部 / 子分部 / 分项 / 工序标准库,把标准模板展开成可编辑任务行
```

因此模板生成出来以后,必须回到 v1.4.7.1 的规则中处理：

```text
可撤销
可编辑
可保存
可协作合并
可表格校核
可发布基线 / 确认月计划 / 保存任务事实
```

核心目标：

```text
建筑工程标准分部分项体系下沉为可被多项目复用的模板库
共享计划树在编辑态新增"智能展开"批量插入操作,语义沿用 v1.4.7.1 编辑缓冲规则
项目基线页和任务列表页阅读态新增"生成任务"业务动作,语义沿用 v1.4.7.1 业务动作规则
生成结果带后端权威的 WBS 分类、任务编码、责任单位角色解析、依赖、验收链接
生成结果不直接写库,而是先进入编辑缓冲、可撤销、可微调、可与其他编辑合并保存
模板沉淀回流由后端安静记录为候选事实,未来在模板管理后台由管理员周期性治理
普通用户视角始终只看到"勾选 -> 展开 -> 复核 -> 保存",不暴露技术细节
```

## 3. 核心结论

模板生成必须分成四层：

```text
模板层：分部 / 子分部 / 分项 / 工序四级标准结构,以及节点上预绑的默认字段
选择层：用户在共享计划树编辑态或阅读态选择模板节点、楼栋 / 楼层 / 区域
展开层：系统按笛卡尔积展开为多行任务,后端解析责任单位角色、依赖、验收链接、编码、WBS
缓冲层：展开结果以一条 template_generate 原子操作进入共享计划树编辑缓冲
```

四层不能跨界：

```text
模板层不存储实例,不绑楼栋,不绑责任单位实例,不绑日期
选择层不直接修改任务事实,只产生一次展开请求
展开层不立即写库,只把展开结果加入编辑缓冲
缓冲层完全沿用 v1.4.7.1 编辑缓冲、保存、撤销、协作合并规则
```

用户视角尽量简单：

```text
用户看到的是分部分项选择、楼栋楼层选择、生成预览、撤销和保存
用户不需要理解 wbs_templates / wbs_template_nodes / generation_batch_id / lineage
系统后台根据 v1.4 系列规则把模板节点解释为业务事实
```

v1.4.7.2 的“主 seed”不是单一 GB55032 树，而是房建现场标准模板库的统一注册入口。它必须同时管理质量主干、现场管理扩展、危大工程、质量责任、项目里程碑、资料与商务配合、专业专项，但不得把这些内容混入 GB55032 的 10 个质量分部统计口径。

```text
core_quality：GB55032 / GB50300 房屋建筑质量分部分项主干
site_management：安全文明、临设、现场准备、临水临电、扬尘治理
danger_control：危险性较大的分部分项工程专项管理包
quality_responsibility：五方责任、见证取样、第三方检测、专项验收、分户验收
project_milestone：开工、样板、基础 / 主体验收、竣工、备案、移交、保修
document_commercial_support：非图纸类工程资料、签证变更、计量支付、结算配合、商务证据链
specialty：消防深化、智能化、幕墙、钢结构、装配式、精装、人防、洁净医疗等专业专项 seed
```

模板包的生成策略也必须分层：

```text
default_selected：项目计划骨架默认建议生成,例如现场准备、开工里程碑、基础/主体验收、竣工移交
triggered：命中工程特征、危险源条件或主干 WBS 后提示生成,例如危大工程、塔吊安拆、深基坑、高支模
explicit：用户显式选择才生成,例如洁净医疗、医用气体、防辐射、复杂智能化专项
```

### 3.1 深度增强四路径的当前落地口径

本章后续扩展不再把“主 seed 无限加粗”作为唯一方案。现场深度增强按以下四条路径分工执行：

```text
专项 seed：
  作为复杂专业深度的主承载路径。
  幕墙、钢结构、装配式、消防、智能化、洁净医疗、人防、电梯等复杂专业优先在 specialty catalog 内深化。
  专项节点必须通过 replacesCoreQualityCodes / referencedCoreQualityCodes 说明与 core_quality 的关系,不得物理改写或删除主干节点。

工法变体：
  作为专项 seed 和局部增强工序包的触发条件,不作为新的笛卡尔积维度。
  节点使用 applicableMethodVariantCodes / methodVariantExpansionPolicy 声明“命中某工法才补充或替换”。
  生成器只在工程特征 method_variant_codes 命中时展开对应工序；未命中时不生成该工法专属行。

项目类型档位：
  作为模板推荐、里程碑过滤、专项灰显和节点适用性过滤的条件。
  节点使用 applicableProjectTypes / applicableStructureTypes 绑定当前应用已有工程特征编码。
  项目类型不参与行级笛卡尔积,也不新增平行项目类型维护入口。

历史项目回流：
  只进入经验工期、依赖候选、工序包候选和后台治理队列。
  默认 historyFeedbackPolicy.mode = candidate_only。
  历史项目样本不得静默反写 v1.4.7.2 seed 文件；必须经模板治理或算法 seed 治理发布后才影响正式生成。
```

代码执行要求：

```text
wbsTemplateGenerationService 必须消费节点级 applicableProjectTypes / applicableStructureTypes / applicableMethodVariantCodes。
methodVariantCodes 只能改变“是否生成某个变体节点”和“工期建议上下文”,不得把同一工序按多个工法自动复制成多行。
durationExperienceService / algorithmSeedCandidateDiscoveryService 只能把历史样本沉淀为 candidate fact,不得直接修改 seed catalog。
```

## 4. 标准分部分项标准库设计

### 4.0 标准 seed 权威与旧模板处理

当前应用已经存在 `wbs_templates`、`wbs_template_nodes`、`standard_processes` 和 WBS 模板页面。v1.4.7.2 的普通业务生成源统一收口到版本化标准 seed，不再把旧 WBS 模板数据库记录作为新项目计划生成来源。

执行口径固定为：

```text
server/src/seeds/chinaGb50300TemplateCatalog.ts + domainWbsTemplateCatalogs.ts = 普通生成权威 seed
wbs_templates / wbs_template_nodes = 历史兼容、后台治理、管理员导入校验留痕表
engineering_categories = WBS / 工程分类语义主数据
standard_processes = 历史标准工序参考库,不作为 v1.4.7.2 权威分类来源
```

旧对象处理：

```text
已有 wbs_templates 继续保留,不删除,不迁出
已有 wbs_template_nodes 继续保留,仅作为历史兼容和后台治理数据
已有 wbs_templates.wbs_nodes / template_data JSON 不再进入普通 template_generate 主路径
已有 standard_processes 只作为工序建议参考,不能直接作为分部 / 子分部 / 分项权威来源
已有 WBS 模板页面退出普通用户主流程,只保留兼容 URL / 后台治理口径
普通用户在任务列表或项目基线页看到的“生成任务 / 智能展开”只消费 v1.4.7.2 seed catalog
```

需要补齐的模板节点字段：

```text
category_type: division | sub_division | item_work | process | activity_step
engineering_category_id: 引用 engineering_categories.id
standard_work_code: 中国标准分类稳定编码
standard_work_name: 中国标准分类名称快照
source_standard: GB55032-2022 / 企业工法 / 项目沉淀
default_duration_days
default_responsible_unit_role
default_dependency_mode
precondition_templates
acceptance_link_templates
default_milestone
default_status_initial
metadata
```

工期 seed 边界规则：

```text
chinaGb50300TemplateCatalog.ts 与 domainWbsTemplateCatalogs.ts 只提供标准任务事实、层级、来源分区和计划行语义,不维护权威 defaultDurationDays
division / sub_division / item_work 结构节点不承载工期规则,父级日期包络与参考工期汇总统一由计划汇总服务处理
当某个分项暂无深度企业工法样本时，也必须配置不少于 3 个带分项语义的可排期 process；不得再使用“准备 / 施工或安装 / 自检验收”三段式泛化包
首轮生成任务的完整工期建议来自专门工期 seed、公司库、项目库、历史项目回流和 duration suggestion 服务
模板同步展开的工期出口已由 v1.4.22 收口：公开 preview / commit / phase-chain 主链路不再暴露工期模式开关，也不允许业务请求切回快速估算通道。模板生成写入计划参考工期时必须产出受治理的 `plan_reference -> planReferenceDays`；内部性能诊断或冷启动审计如需使用快速估算，只能通过后端内部 `diagnosticDurationSuggestionMode`，并且结果只能保留为 `templateFastEstimateDays` / metadata。
`template_fast_estimate` 不得写入 `smart_reference_days`，不得提升为 `plan_reference`，不得作为后续基线、月计划、材料联动或运行期预测的业务工期来源；完整业务工期仍由 `durationSuggestionService`、`DurationOutputContract` 和 `AlgorithmFactContext` 链路治理。
旧 wbs_templates.wbs_nodes / template_data 中的 reference_days / defaultDurationDays 只作为兼容导入字段,不能替代版本化模板 seed 与工期 seed 的分层权威
```

模板读取规则：

```text
优先读取 wbs_template_nodes 的结构化节点
旧模板只有 wbs_nodes / template_data JSON 时,运行时解析为标准节点 DTO,但不隐式回写数据库
用户保存、沉淀或管理员发布模板时,必须写入 wbs_template_nodes 结构化节点
模板节点与 engineering_categories 的映射失败时,标记为待后台校准,不向普通用户暴露技术标签
```

### 4.1 库分级

模板库分四级，按命中优先级覆盖：

```text
国标库：以中国现行建筑与市政工程施工质量控制通用规范为基础,优先采用 GB 55032-2022,覆盖 10 个分部及其子分部、分项
地方库：在国标库基础上按地区或地方定额扩展,允许覆盖国标节点的默认字段
公司库：按公司业务沉淀,覆盖装配式、钢结构、机电、装饰等公司专长场景
项目库：在单一项目内沉淀,允许覆盖上层库的默认字段,不影响其他项目
```

中国房屋建筑工程标准主干全集边界：

```text
本章必须一次性确定中国房屋建筑工程标准主干全集,不采用国际 WBS 分类作为默认模板来源
模板交付层级固定到 分部 / 子分部 / 分项 / 工序
其中 分部 / 子分部 / 分项 是中国标准权威层级
工序不是 GB 55032-2022 的验收划分层级,属于系统为了计划编制和现场执行生成的施工工艺展开层
因此不得把工序伪装成国标原文；工序只能来自企业工法、项目沉淀、施工组织设计或系统默认工序建议
当某个分项暂未形成成熟企业工法模板时,seed 中必须预置不少于 3 个带分项语义的可排期 process 作为最小专业工序包,metadata.source_standard 必须标记为 enterprise_method,不能标记为 GB55032 或 GB50300
```

命中优先级：

```text
项目库 > 公司库 > 地方库 > 国标库
高优先级未覆盖时使用低优先级默认值
模板节点 ID 在同一逻辑节点的多级库中必须可被映射追溯
```

### 4.1.1 中国房屋建筑工程标准主干定版

本章的国标库必须一次性锁定中国房屋建筑工程分部分项标准主干全集，作为 v1.4.7.2 的默认模板底稿。执行时不得只 seed 少数几个高频分部，也不得用国际项目管理 WBS 分类替代中国工程质量验收分类；市政道路、桥梁、管廊、园林、水利、电力、工业安装等专业域只作为后续可扩展模板域，不纳入本章默认内置库的覆盖承诺。

领域模板子体系并入本章统一治理，原独立 v1.4.7.6 文件不再保留。v1.4.7.2 同时负责“房屋建筑主干 seed + 平行专项 seed”的注册、生成、报告和升级口径，但两者在代码和数据边界上仍保持分离：房建主干 seed 只保留中国房屋建筑标准主干；室外配套、市政基础、精装专项、消防深化等领域以平行 templateId 注册，生成后同样进入共享计划树、v1.4.18 工期建议、v1.4.8 开工条件、v1.4.11 验收挂接和 v1.4.19 偏差分析。

主 seed 与专项 seed 的边界固定为：

```text
房建主干 seed：
  保留 GB55032 / GB50300 口径下属于房屋建筑质量验收主干的分部、子分部、分项。
  即使存在室外电气、室外管网、消防喷淋、装饰装修等名称，也只承担“房建主干质量控制骨架”的作用。

专项 seed：
  承接室外配套、市政基础、精装专项、消防深化等更适合专项计划编制的深化工序包。

计划事项语义固定为“六层模型”：

```text
第一层：来源分区。
packType / catalogGroup 只回答“这条计划事项从哪个模板分区来”，用于模板注册、默认筛选、组合生成和来源追溯。
packType 不得直接决定共享计划树里的行样式、进度填报方式、关键路径参与方式或联动读写权限。

第二层：计划行语义。
planItemKind 回答“这条计划行自身是什么性质”，由它决定共享计划树里的主视觉、类型筛选和默认交互。

planItemKind 固定枚举：
  work_task          正常施工 / 前期准备 / 实体实施任务
  management_task    管理动作、协调动作、方案组织动作
  inspection_task    检查、检测、验收、见证取样、实测实量
  document_task      资料报审、组卷、归档、证据链动作
  commercial_task    签证、计量、付款、结算、索赔等商务动作
  safety_control     安全管控、危大方案、专家论证、专项安全闭环
  milestone          计划骨架上的里程碑
  linked_projection  只读联动投影,真值来自验收时间轴、证照、图纸或其他事实页

计划行计算字段：
  scheduleParticipation = normal | reference_only | read_only_projection | excluded
  progressMode = manual | event_triggered | upload_triggered | binary | inherited
  criticalPathEligible = true | false
  scopeExpansionMode = project | building | floor | building_rhythm_series | floor_anchor | explicit_instances | custom | triggered_object | referenced_work_or_project
  planItemTags = 危大 / 专项 / 紧急 / 关键节点 / 联动 等横切标签

第三层：展示投影层。
rowProjectionMode 回答“这条生成事项在共享计划树里占主行、做门禁、做行内控制，还是只读联动投影”。它不替代 planItemKind、executionNature 或 durationContributionMode。

rowProjectionMode 固定枚举：
  schedule_row       主计划 / Gantt 行,参与首屏 / 单批渲染预算和施工执行视图排序
  gate_marker        门禁、验收、审批、条件确认节点,可见但不按普通施工行展开
  inline_control     挂在承载行下的检查清单 / 控制项 / 资料项,可见但不抢主计划行
  linked_projection  来自验收时间轴、证照、图纸、资料页等事实页的只读投影

控制项不等于非任务：只要它有责任单位、有时间窗口、有交付物或会阻塞后续工作，就可以作为计划事项存在；但是否占主计划行、是否承载工期、是否成为依赖锚点必须分别由 rowProjectionMode、durationContributionMode 和 internalFlow 判断。典型例子：高支模实体搭设、混凝土浇筑旁站和架体变形监测，虽然带 safetyControlRole / inspectionAcceptanceRole，仍可为 schedule_row + duration_bearing；拆除条件强度报告和卸载顺序确认则应为 gate_marker / quality_gate，不得因标题含“拆除”误判为实体施工行。

任务列表默认展示“需要排期管理的主事项”，不是只展示物理施工项，也不是按 packType / catalogGroup 硬决定展示形态。运行期主执行列表只保留 `schedule_row` 和关键 `gate_marker`：里程碑、关键节点、危大验收 / 操作许可、专项验收、竣工验收、移交、备案等可作为主列表门禁；普通 `gate_marker`、`inline_control`、`linked_projection` 默认收纳到承载行详情、检查清单或事实页联动,不占任务列表主行。旧数据若仅写 `planItemKind=linked_projection` 或 `relationRole=projected_link`,也必须按联动投影隐藏,不得回退成普通 `schedule_row`。

施工执行视图默认按 `executionPhase / executionLane / executionSortKey / workfaceId` 展示现场执行顺序,不按 GB 分部 / 子分部 / 分项结构作为主视图。`division / sub_division` 只作为来源结构、筛选上下文和模板治理锚点,不进入执行主列表；`item_work` 若只是带子节点的结构摘要且 `is_executable !== true`,也不进入主列表。国标结构可以在详情、筛选、溯源和模板浏览器中查看,但共享计划主表面向现场排期。

第四层：真实执行性质。
executionNature 回答“这条计划行本质上是不是现场实体施工动作”，用于物理工序识别、资源测算、看板归类和后续历史项目回流治理。
executionNature 不得替代 durationContributionMode：有些非物理事项也会消耗周期，有些复合行虽然显示为验收 / 危大,但内部包含安装、浇筑、搭设等物理动作。
executionNature 的判断只看“是否对现场实体对象发生直接施工、安装、处理、调试、试验性作业”，不得把质量、安全、资料、验收、商务、管理语义混入物理工序判断。
推断优先级必须先识别强管理 / 资料 / 监测 / 检查检测语义,再判断物理作业动词：包含“方案、审批、审核、论证、报审、清单、办理、记录、台账、归档、组卷、签认、报告、资料核验、问题整改、整改闭合、问题销项”等强语义时,即使标题里出现“开挖、吊装、安装、连接、调试”等对象词,也不得直接判为 physical_work。
`实测、复测、偏差、合格确认、外观数量检查、试块留置、复查` 统一按 inspection_test 处理；`监测、观测、测温、沉降、位移` 统一按 monitoring_wait 处理,不得被生成器追加的“作业面准备 / 过程施工”后缀污染成 physical_work。只有标题表达“浇筑、绑扎、搭设、敷设、焊接、灌浆、张拉、压浆、试压、冲洗、调试、铺贴、喷涂、打胶、封堵、防腐、保温、除锈”等对现场实体对象的实际作业,才可判为 physical_work。
典型边界：`吊装方案审批` / `边坡开挖方案和支护设计复核` / `问题处理` = management_action；`安装验收` / `安装偏差实测复核` / `系统冲洗合格确认` / `钢筋加工安装外观数量检查` / `同条件试块留置` = inspection_test；`检测报告闭合` / `混凝土浇筑班组自检记录` / `材料报验` = document_record；`大体积混凝土测温和温差控制过程施工` / `支撑连续监测过程施工` / `沉降观测` = monitoring_wait；`沉降缝和伸缩缝施工` / `沉降缝止水带安装` / `测温管安装` / `样板段施工与评审` / `塔吊基础混凝土浇筑养护验收` 这类包含真实实体作业的复合工序仍可判为 physical_work；`灌水通球和通水试验` / `闭水或淋水试验` / `风管漏光漏风量测试` / `试射和联动测试` 这类对实体系统进行试验性作业的工序判为 physical_work,但必须叠加 test_control；`作业面准备` / `作业面确认` / `准备与交底` / `工艺评定和作业交底` / `工艺参数控制` 即使标题或括号里出现施工对象词,也按 technical_preparation，不得被父工序名称污染为 physical_work。
质量、安全、验收、资料、商务、管理语义统一落到横切控制属性；同一条工序可以既是 physical_work,又承担质量控制点 / 安全控制点 / 资料证据点。

executionNature 固定枚举：
  physical_work          真实现场实体施工 / 安装 / 加工 / 处理 / 调试 / 试验性作业
  technical_preparation  技术准备、样板、参数、配合比、测量放线、复核确认
  inspection_test        检查、检测、试验、验收、见证取样、隐蔽验收
  monitoring_wait        监测、连续运行、报告等待、强度等待、间歇等待
  document_record        资料、记录、台账、组卷、归档、报审报验
  management_action      方案、审批、论证、交底、协调、许可、商务管理动作
  handover_milestone     移交、交付、竣工、备案、联动投影节点

第五层：横切控制角色。
横切控制属性只赋给 process / activity_step,不直接赋给分部 / 子分部 / 分项父级节点；父级需要展示时由子工序聚合。
横切控制属性回答“这条工序还承担什么项目控制角色”，不得反向改写 executionNature。

横切控制属性固定字段：
  qualityControlRole = none | precondition_control | process_control | hidden_control | test_control | acceptance_gate | defect_rework
  safetyControlRole = none | hazardous_work | special_plan_control | safety_acceptance | protective_measure | temporary_facility_safety | operation_permit | monitoring_control | daily_safety_check
  inspectionAcceptanceRole = none | self_check | mutual_check | hidden_acceptance | material_retest | third_party_test | special_acceptance | completion_acceptance
  documentEvidenceRole = none | technical_record | inspection_record | test_report | approval_document | handover_document | commercial_document
  commercialControlRole = none | quantity_measurement | variation_claim | price_approval | progress_payment | settlement | cost_evidence
  managementControlRole = none | planning_control | organization_control | technical_control | resource_control | site_readiness_control | interface_coordination | issue_rectification | progress_control | handover_control

典型表达：
  高支模架体搭设 = executionNature: physical_work + safetyControlRole: hazardous_work
  地下防水节点附加层施工 = executionNature: physical_work + qualityControlRole: process_control + inspectionAcceptanceRole: hidden_acceptance
  高支模专项施工方案审批 = executionNature: management_action + safetyControlRole: special_plan_control + documentEvidenceRole: approval_document
  月度计量申报 = executionNature: management_action + commercialControlRole: quantity_measurement + documentEvidenceRole: commercial_document
  基层含水率检查 = executionNature: inspection_test + qualityControlRole: precondition_control + inspectionAcceptanceRole: self_check
  材料进场复验 = executionNature: inspection_test + qualityControlRole: precondition_control + inspectionAcceptanceRole: material_retest + documentEvidenceRole: test_report
  沉降缝止水带安装 = executionNature: physical_work + qualityControlRole: hidden_control + safetyControlRole: none + inspectionAcceptanceRole: hidden_acceptance
  沉降观测 = executionNature: monitoring_wait + safetyControlRole: monitoring_control
  方案交底执行(危大分区) = executionNature: management_action + qualityControlRole: none + safetyControlRole: special_plan_control + documentEvidenceRole: approval_document
  安全技术交底 = executionNature: management_action + safetyControlRole: special_plan_control + managementControlRole: technical_control

第六层：算法参与语义。
durationContributionMode / internalFlow 回答“这条计划行是否承载施工工期、是否能作为同父级依赖锚点、是否会写入 task_dependencies”。

durationContributionMode 固定枚举：
  duration_bearing  实体施工或真实作业承载工期
  embedded_check    内嵌检查、复核、测量等动作,不单独承载工期
  quality_gate      质量门禁、验收、检测、试验等节点,可作为门禁锚点但不按普通施工工期计
  external_wait     外部等待、送检、第三方报告等等待项,不推进施工游标
  record_only       资料、记录、报审、商务台账等事实项,不贡献施工工期
  handover_marker   移交、交付、联动投影等节点项,作为节点或条件而非普通工期

internalFlow.relationKind 固定枚举：
  hard_sequence     物理或工艺强顺序,可写入 task_dependencies
  acceptance_gate   验收 / 检测 / 复核门禁,可写入 task_dependencies
  soft_sequence     推荐顺序,只写入 standard_task_metadata.internalFlow
  parallel_allowed  可并行或只作参考,只写入 standard_task_metadata.internalFlow

relationRole 只表达依赖 / 引用关系语义,继续服务 v1.4.7.5 dependencyIntentTemplates 和前置依赖解释。
relationRole 不得替代 planItemKind；同一行可以是 inspection_task,但它与被引用工序的 relationRole 可以是 evidence / inspection / prerequisite。

字段默认原则：
  packType 决定来源和默认筛选。
  planItemKind 决定共享计划树展示、类型筛选和默认交互。
  rowProjectionMode 决定是否占主计划 / Gantt 行、是否纳入首屏 / 单批渲染预算、是否作为门禁 / 行内控制 / 只读投影展示。500 行只作为默认渲染预算,不得作为模板生成硬失败阈值；生成器应返回全量 rows 与 generationBatches.rowLimitExceeded,由前端渐进渲染。
  progressMode 决定进度填报组件。
  scheduleParticipation / criticalPathEligible 决定计划行在当前视图和关键路径中的参与方式。
  scopeExpansionMode / rhythmExpansionEligible 决定空间展开策略；必须在 rowProjectionMode 之后判断。只有 rowProjectionMode= schedule_row 或关键 gate_marker 才考虑进入主计划预算,普通控制项即使命中多个楼层也不得放大成楼层任务行。
  executionNature 决定是否是真正物理工序及后续资源 / 历史样本归类。
  qualityControlRole / safetyControlRole / inspectionAcceptanceRole / documentEvidenceRole / commercialControlRole / managementControlRole 决定同一工序叠加的质量、安全、验收、资料、商务、管理控制角色。
  durationContributionMode 决定 reference_duration、父级工期汇总和 activity_step 工期拆分。

动态展开原则：
  overview / generationDepth=item_work 只是默认概览口径,不是禁止下钻。标准层主体等重复流水必须节拍化为 item_work 聚合行；地库穿插、机电综合管综、消防检测整改、幕墙深化测量、电梯调试监督检验等现场排期价值高、内部 process 具备真实工序依赖和作业面移交的 itemPack,可以通过 metadata.overviewExpansionDepth=process 或生成器治理白名单自动展开到 process。activity_step 仍默认只进详情 / checklist,不进入主计划首屏。
  模板生成服务必须先读取模板节点的 durationContributionMode：embedded_check / quality_gate / external_wait / record_only / handover_marker 直接生成 NON_DURATION_BEARING_STANDARD_WORK 的本地 durationSuggestion，不进入工期服务历史样本、环境缓冲或 Supabase 查询链，避免管理、资料、检测、移交类计划行污染工期 seed。
  internalFlow.relationKind 决定同父级兄弟节点是否写入 task_dependencies。
  linked_projection 只做只读投影和跳转,不得反向编辑事实页真值。
```

所有非 core_quality 模板包都必须满足：

```text
不计入 GB55032 主干分部 / 子分部 / 分项统计。
可以与 core_quality 同批生成,但必须保留 templateId / templateGroup / packType / source_template_node_id / generation_batch_id lineage。
同名任务不得物理覆盖或改写原模板节点,只能在生成预览中提示“来源不同、可合并或保留”。
例外：generationMode = replace_core_when_selected 且 replacesCoreQualityCodes 命中时,属于生成期抑制 core_quality 粗颗粒 process / activity_step,不属于模板节点覆盖。
default_selected 节点总量必须控制在 40 行以内,防止普通项目首次生成计划被管理节点淹没。
triggered 节点必须配置 triggerRules 或 dangerTriggers,不能靠前端字符串临时判断。
explicit 节点默认不展开,只在用户选择对应专业专项模板时进入生成预览。
```

建议 3 的跨分区边界规则：

```text
七大 Catalog Group 之间不得复刻同一施工工序。
core_quality 只保留质量主干施工工序；quality_responsibility 只保留五方责任、见证取样、第三方检测、隐蔽验收、实测实量等过程责任动作。
project_milestone 只保留项目级节点；验收时间轴的大节点通过 acceptanceLinkRule 绑定 acceptance_plans，不另起 acceptance_anchor 分区。

  每个分部声明 expectedSubDivisionCount
  生成后立即运行校验：子分部数量 vs 声明数量
  联网搜索 GB 55032-2022 分部分项划分表,校对子分部名称和数量

第二轮：逐分部生成分项全集（10 次独立生成,避免单次上下文过长遗漏）
  每个子分部声明 expectedItemCount
  每次生成一个分部的全部分项后,联网搜索该分部对应的专业验收标准目录校对
  校对维度：分项名称准确性、分项数量完整性、是否有现行标准已废止的分项

第三轮：逐子分部生成工序
  高频分项（混凝土、钢筋、模板、砌体、防水、保温、安装等）展开细化工序
  其余分项生成不少于 3 个可排期工序的最小专业工序包
  工序层不联网校对（非国标内容,按行业通用工艺生成）
```

联网校对规则：

```text
校对时机：每轮生成完成后、写入 seed 文件前
校对来源：
  GB 55032-2022 原文或权威解读（住建部/标准全文网/工程质量验收教材）
  GB50300-2013、GB50411-2019 只作为历史差异核对来源,不得覆盖 GB55032-2022 当前主干,不得作为内置模板 ID 兼容来源
  中国知网/百度学术中的分部分项划分研究文献
校对动作：
  名称不一致 → 以国标原文为准修正
  数量不一致 → 联网确认后补齐或移除
  无法确认 → 不进入正式 seed,进入候选治理池并记录待校对来源 URL
  已废止分项 → 标记 deprecated: true,不计入 expectedCount
联网失败时：
  不写入正式 seed
  只能写入候选治理池,等待人工或专家确认后再进入 verified seed
```

自校验兜底：

```text
每个分部的分项数不低于行业公认最小值：
  地基与基础 ≥ 15 分项
  主体结构 ≥ 20 分项
  建筑装饰装修 ≥ 25 分项
  屋面 ≥ 10 分项
  给水排水及供暖 ≥ 20 分项
  通风与空调 ≥ 15 分项
  建筑电气 ≥ 15 分项
  智能建筑 ≥ 20 分项
  建筑节能 ≥ 15 分项
  电梯 ≥ 5 分项
无重复 stableCode
无空 name / 空 sourceClauseRef
reviewNeeded 节点数量必须为 0
webVerified: false 节点数量必须为 0
全部 error / warn 清零后,seed 进入 verified 状态
```

版本锁定与更新：

```text
seed 文件头部声明：
  catalogVersion: '1.0.0'
  sourceStandards: ['GB55032-2022']
  generatedAt: ISO 日期
  generatedBy: 'LLM + web verification'
  verifiedAt: ISO 日期（严格校验 error / warn 清零后填入）
后续标准修订时（如 GB55032 或其替代规范出新版）：
  新建 catalogVersion 2.0.0
  重新执行三轮生成 + 联网校对
  旧版 seed 归档不删除
  前端模板选择器按 catalogVersion 展示
```

因此交付边界必须这样理解：

```text
分部 / 子分部 / 分项：必须按中国标准全集一次性到位
工序：必须随分项全覆盖；高频分项用细化企业通用工序,其余分项用不少于 3 个带分项语义的最小专业工序包覆盖
默认依赖 / 默认责任角色 / 默认开工条件 / 默认验收链接：随工序一并交付,但不得反过来影响分项全集完整性
```

字段语义：

```text
defaultName 是模板自带的工序名,用户可在生成后改名,模板来源只保留为后端记录
v1.4.7.2 主 seed 不维护 defaultDurationDays；工期建议统一来自专门工期 seed / 公司库 / 项目库 / 历史项目回流和 duration suggestion 服务
defaultResponsibleUnitRole 不是 participant_unit_id,而是角色枚举
同一父级下的 process / activity_step 可由生成器产生 sibling_sequence 本地顺序；同分部 / 同工程对象下跨分项、跨施工包主线依赖由 v1.4.7.5 cross_item_workflow 处理；跨业务域约束引用依赖由 v1.4.7.5 dependencyIntentTemplates 处理
同一分项 / 同一标准工序包内部派生出的 process 顺序、同一 process 下 activity_step 作业步骤顺序,属于标准工序结构的内部工序流,由本章模板结构和生成器 sibling_sequence / internal_flow 元数据承接,不得塞入 workflow_dictionary。
内部工序流只表达同一父级内的本地先后、可并行、验收前必须完成等规则,例如钢筋翻样 -> 加工 -> 绑扎 -> 隐蔽验收,模板安装 -> 成型验收 -> 拆除清理,混凝土浇筑 -> 养护 -> 拆模条件确认。
内部工序流必须来自独立的标准工序内部流规则 seed（当前代码落点为 `standardInternalFlowSeed.ts`），由生成器按同父级相邻节点的 stableCode / level / catalogSource 动态解析；主标准工序 seed 与专项 / 分区模板 seed 不再把 internalFlowFromPrevious 写入模板节点。
生成器不得根据工序名称自行猜测硬前置。未命中人工规则表时只能生成 soft_sequence + review_required 兜底，保留 metadata 供后续治理，不得写入 task_dependencies。
内部流规则必须区分 hard_sequence / soft_sequence / parallel_allowed / acceptance_gate：只有 hard_sequence 和 acceptance_gate 可写入 task_dependencies；soft_sequence 与 parallel_allowed 只写入 standard_task_metadata.internalFlow 作为生成依据和审计依据,不得阻止后续进度填报或把任务强制串行。
内部工序流规则必须记录 seedRuleId、ruleVersion、curationStatus、curationMethod、curationBasis、reviewNeeded、scheduleMode、requiresAllPreviousSiblings、evidenceCodes、governancePriority；curationStatus = curated 才代表已人工确认，review_required 只代表后台待治理，不得在普通业务页暴露技术字段。
同父级内部流不再只能表达“上一个兄弟 -> 当前兄弟”：acceptance_gate 可要求当前节点依赖同父级全部已生成前序节点；parallel_allowed 可让计划日期与前序并行展开；lagDays / dependencyType 必须由规则 seed 明确给出。
同父级内部流在落地依赖前必须先消费 durationContributionMode：只有 duration_bearing / quality_gate / handover_marker 可作为同父级依赖锚点；embedded_check / external_wait / record_only 只生成 reference_only internalFlow metadata，createsDependency=false，reference_duration=null，不推进计划游标，也不得作为后续兄弟节点的普通前置。质量门禁如果 requiresAllPreviousSiblings=true，只聚合前序锚点兄弟，并在 metadata.skippedSiblingClientRowIds 中记录被跳过的检查、等待、资料类节点。
跨业务域约束 dependencyIntentTemplates 消费 referenced*Codes 时也必须套用同一锚点过滤器：被引用目标只有 duration_bearing / quality_gate / handover_marker 时才允许生成真实 predecessorDependencies；embedded_check / external_wait / record_only 只能保留 referenced*Codes 与 relationRole 作为解释性链接或候选事实,不得因为被质量责任、里程碑、资料商务、管理协调引用而反向污染工期 / 依赖网络。典型口径：见证取样应绑定混凝土进场验收、坍落度与试块留置等质量门,不得绑定“浇筑准备与交底”；主体结构验收应绑定实体质量检查等验收锚点,不得绑定模板钢筋预留预埋复核这类前置复核。
activity_step 作业步骤可以按模板顺序默认展示和生成 sibling_sequence，但默认顺序不等于 task_dependencies 硬依赖；只有 `standardInternalFlowSeed.ts` 动态解析结果明确为 hard_sequence / acceptance_gate，且当前节点与前序节点均满足 durationContributionMode 锚点规则时，才允许写入前后置依赖。未命中明确规则的 activity_step 只能保留 soft_sequence / parallel_allowed / reference_only metadata，不能把作业步骤默认串行成硬约束。
后台必须提供同父级内部流治理报告：覆盖主标准工序模板 seed 与专项 / 分区模板 seed，按 catalogGroup、curated / review_required、relationKind、scheduleMode、governancePriority、evidenceCodes 聚合，并输出 top review_required 规则对。当前代码落点为 `/api/wbs-template-governance/internal-flow-rules/report`，仅公司管理员或后台治理流程可读；普通业务页面不得展示 seed 名称、规则 ID、技术状态或规范引用明细。
当前同父级内部流先固化为 v1.4.7.2 可执行基线：高优先级 review_required 必须为 0，curatedCoverageRatio 达到 0.88 以上时进入 execution_baseline_ready；进入该状态后停止无限补 P2 长尾，不再追求把所有低频 review_required 清零。后续只治理三类规则：明确硬前置、明确验收 / 试验 / 隐蔽 / 安全功能关口、需要条件化表达的工法差异；其余不确定或低频 P2 保留为 review_required metadata，交给真实执行数据反校验。
治理报告必须输出 executionBaselineGate：minimumCuratedCoverageRatio、currentCuratedCoverageRatio、highPriorityReviewRequiredRuleCount、operatingMode、p2TailPolicy、runtimePolicy、backValidationEntryPoint。该门槛只用于后台治理和发布判断，不进入普通业务页。
治理报告必须区分原始 seed 依赖口径和最终生成器有效依赖口径：createsDependency / rawCreatesDependency 表示规则 seed 声明会创建依赖；effectiveCreatesDependency 表示经过 durationContributionMode 锚点过滤后实际会落入生成依赖的数量；dependencySkippedByDurationContributionMode 表示因 embedded_check / external_wait / record_only 或无前序锚点而被过滤的规则数量。发布影响预览、统一依赖规则报告和后台审计必须优先看 effectiveCreatesDependency，避免把内嵌检查、资料记录、外部等待误判成真实计划硬前置。
人工治理优先级：P0 = 验收、安全、试验、隐蔽、送电、监督检验等关键关口；P1 = 高频物理顺序或质量资料闭合；P2 = 可穿插、推荐顺序或低频规则。未联网或未人工确认的规则不得从 review_required 自动升级为 hard_sequence / acceptance_gate。
真实项目执行数据可以反校验同父级内部流：`durationExperienceService` 必须把生成任务中的 `standard_task_metadata.internalFlow` 采样到 `duration_experience_samples.metadata.standard_internal_flow`，`algorithmSeedCandidateDiscoveryService` 只可生成 `standard_internal_flow` candidate，用于提示哪些 review_required 规则值得人工补入 `standardInternalFlowSeed.ts`；候选不得直接写入 `task_dependencies`，也不得直接覆盖 `standardInternalFlowSeed.ts`。
`standard_internal_flow` 候选即使通过自动治理，也只能保持 candidate_only / 后台治理事实；只有被人工补成 `standardInternalFlowSeed.ts` 中的 curated 规则后，生成器才允许按 hard_sequence / acceptance_gate 写入同父级依赖。
同父级内部流规则必须区分 curationMethod：manual_registry 表示人工治理规则；stable_code_backfill 表示按 stable_code 精确回填的规则；soft_fallback 表示未命中的后台待反校验兜底。stable_code_backfill 不等同于语义泛化,必须在治理报告中单独统计 stableCodeBackfillCount,后续只能通过高频样本和规则证据升级为更通用的语义规则。
内部流证据链必须从 evidenceCodes 扩展到 evidenceRefs：evidenceCodes 仅保留 GB502xx / GB50300 等标准级摘要；evidenceRefs 记录 standard / clause / process / enterprise_method / execution_history 级别证据、说明硬前置或可并行的依据。当前证据粒度不足时不影响普通生成,但必须进入后台规则治理差距。

## 6. 工程对象展开规则

模板节点不绑工程对象，由用户在生成时选择范围；生成器必须先按 `rowProjectionMode` 判断该事项是否进入主计划行,再按 `scopeExpansionMode / rhythmExpansionEligible` 判断空间展开方式。不能把 `building × floor × zone` 一律笛卡尔积为任务行。

工程特征不参与笛卡尔积。项目类型、结构体系和主要工法只影响模板过滤、工法变体、默认工期和业务理由,不得把一条工序直接按“工法 × 项目类型”展开成多行。

构件对象不作为新的工程对象主数据维度,也不要求用户维护“梁 / 板 / 柱 / 墙 / 楼梯 / 基础”等独立对象。构件只作为模板生成时的派生事实 elementVariant / componentType,用于让钢筋、模板、混凝土、砌体、幕墙、机电支吊架等高频工序在现有工程对象支持的范围内更贴近现场。

`deriveProcessElementVariants(processName, engineeringObjectContext)` 负责按工序名称、WBS 分类和已选工程对象生成构件派生建议。

### 6.1 展开维度

可选维度：

```text
楼栋 buildings
楼层 floors
区域 regions
分期 phases
```

展开规则：

```text
未选任何维度：默认生成 1 行 / 工序,挂在当前层
仅选楼栋：工序数 × 楼栋数
楼栋 + 楼层：默认不直接做笛卡尔积；标准层主体流水等 rhythmExpansionEligible 包生成楼栋级节拍行
楼栋 + 楼层 + 区域：仅当模板声明 explicit_instances / floor_full_expand 或用户选择自定义全展开时,才按实际存在的楼层区域展开
分期独立维度,与楼栋楼层区域同级笛卡尔积
generationDepth=process：只展开到 process,工序日期由工期 seed / duration suggestion 服务给出；非工期承载行不得使用 1 天兜底
generationDepth=activity_step：继续展开 activity_step,作业步骤按同一工序下展示顺序与内部流规则生成；默认不展开,只在用户显式选择时生成
```

标准层和重复空间展开采用三档：

```text
A 档：节拍行。用于标准层主体流水等 rhythmExpansionEligible itemPack。多楼栋 × 多楼层时每栋生成 1 条 schedule_row,metadata.floorRhythm 记录 floorDurationCurve、floorCount、floorDurationDays、floors 和 workfaceInstanceMode=floor_cycle_matrix；CPM 只消费总工期,楼层周期在楼层进度面板或详情中管理。
B 档：锚点行。用于转换层、避难层、设备层、机电屋面层、地下室等非标准楼层。锚点行可独立挂依赖,但不得把普通标准层全部铺开。
C 档：局部全展开。用于地下室防水链、人防链、屋面链、特殊楼层验收链或用户显式 scopeExpansionMode=explicit_instances / floor_full_expand 的场景；它是例外路径,不是默认路径。
```

默认输入 `buildings + floors` 时,若命中 `rhythmExpansionEligible=true` 且未显式声明 `explicit_instances`,生成器必须把楼层序列压缩为 `scope_expansion_mode=building_rhythm_series`。例如 3 栋 × 26 层的 `BDT-04-01-01 标准层主体结构流水施工` 应生成 3 条节拍主行,每条主行内部含 26 个楼层周期；不得生成 78 组相同工序行。若确需逐楼层 process 级行,必须由前端/用户显式传入 `scopeExpansionMode=explicit_instances`。

节拍聚合行对工期 / 依赖 seed 的消费口径（2026-05-26 补充）：
```text
模板 seed 只声明任务、稳定编码、rhythmExpansionEligible、floorDurationCurve / floorDurationCurveByMethod 和 scopeExpansionMode。
默认 building_rhythm_series 行必须作为 itemPack 级 schedule_row 消费 standard_work_duration seed，例如 BDT-04-01-01 命中 rhythm_itempack:BDT-04-01-01。
floorDurationCurve 只负责把已排序楼层序列折算为 totalRhythmDurationDays；工期来源、置信度、method bucket 和治理边界仍归 standard_work_duration seed。
process 级工期 seed 继续保留给 explicit_instances / floor_full_expand；不得因为默认节拍行存在而删除 BDT-04-01-01-Pxx 或 02-01-Pxx 的明细规则。
依赖 seed 默认只对 building_rhythm_series 生成楼栋级聚合依赖锚点；same_floor / next_floor 依赖只在显式楼层展开或锚点楼层行中生成真实 task_dependency。
生成行 metadata.floorRhythm 必须带 durationSeedStableCode、durationSeedScope、floorCount、floorDurationDays 和 workfaceInstanceMode=floor_cycle_matrix，便于前端楼层进度面板解释。
```

任务名称按规则拼接：

```text
默认任务名 = [工序名] · [楼栋] · [楼层] · [区域] · [分期]
所有非空维度按顺序加入,空维度跳过
用户可在生成后改任务名称,模板来源只保留为后端记录
```

### 6.2 展开上限

```text
单次生成首屏 / 单批渲染预算：默认 500 条 schedule_row 主计划行
超过预算时,前端在预览阶段提示“首屏先渲染 500 行,剩余行按阶段 / 楼栋 / 专业继续加载”,不得阻断生成。
允许生成超过 500 行；生成器返回全量 rows 与 generationBatches.rowLimitExceeded,由前端渐进渲染和草稿表格分批加载。
```

500 行不是业务硬上限。大体量项目允许一次生成完整计划,但默认只渲染预算内主计划行；需要用视图折叠、阶段 / 楼栋懒加载和 rowProjectionMode 控制首屏性能。

### 6.2.1 多 phase 生成与排期网络

```text
多 phase 模板生成不得再按 N 次完全独立生成、全部使用同一个 plannedStartDate 起跑。
生成器必须支持两种 preview 排期模式：
1. phase release policy 起点联动：默认模式。按 operations / phaseOperations 顺序逐 phase 生成，但不得简单头尾相接；必须依据 release policy 计算起跳时机。
2. 同一网络排期：多 phase rows 合并后，必须重新执行 cross_item_workflow、dependencyIntentTemplates、冲突剪枝、环剪枝和 dependency schedule，把跨模板 / 跨 phase 的业务依赖边纳入预览日期。
如需保持多个 phase 完全独立预览，前端可显式传 phaseChainMode='none'。
```

生成器输出要求：

```text
phase release policy 支持 strict_finish_start、overlap_after_days、overlap_before_finish_days、overlap_after_percent、parallel_group。
phase-chain 产生的起点联动必须写成显式 predecessorDependencies，source='phase_chain'，而不是只移动 planned_start_date / planned_end_date。
cross_item_workflow / dependency_intent_template 仍优先于普通 sibling_sequence；phase_chain 是弱兜底顺序线,不得高于真实工艺依赖,也不得替代真实工艺依赖。
前端可在整体请求传 phaseReleasePolicies，也可在单个 operation 上传 phaseReleasePolicy；整体 phaseReleasePolicies 优先于 operation 内配置。
单次 operation 的 scope.phases 与多 operation 的 operations / phaseOperations 都必须遵守该口径。
基线 / 月度计划算法仍可在保存后做正式 CPM 精排；模板生成 preview 阶段至少要避免“桩基、主体、装饰、机电全部同日开工”和“所有 phase 完全头尾相接”的两个极端。
```

默认 release policy 口径：

```text
site / danger / quality / doc / milestone：parallel_group,与项目主线并行显示为控制线或支撑线。
foundation-pit / pit-pile：parallel_group,与桩基/基坑主线并行。
basement：overlap_before_finish_days(30),允许在前置基坑/桩基末段插入。
waterproof：overlap_before_finish_days(14),允许跟随地下结构末段插入。
superstructure / structure-core：strict_finish_start,作为主体主线锚点。
mep：overlap_after_days(60),主体/砌体形成作业面后插入。
finishing / fitout：overlap_before_finish_days(30),主体/机电收尾阶段插入。
commission / outdoor：overlap_before_finish_days(30),装饰末段插入。
其它未知 phase：overlap_after_percent(70),作为保守穿插兜底。
```

### 6.3 父子结构归属

```text
生成行始终挂在用户当前选中的父行下
若用户在阅读态走"生成任务"且未选父行,默认挂在根
父行不存在或被删除时拒绝生成,提示用户重新选择

```

## 8. 编辑缓冲与撤销

### 8.1 模板生成作为原子操作

```text
一次模板生成,无论生成多少行,作为一条 template_generate 操作进入编辑缓冲
撤销一次 = 整批 N 行一起回滚出编辑缓冲
重做一次 = 整批 N 行一起恢复
不允许撤销其中部分行
部分行调整请在生成后逐行删除或修改
```

这条规则同时作为 v1.4.7.1 §7.2 撤销与重做规则的补丁。

### 8.2 与 v1.4.7.1 §11.2 commit 模型的衔接

v1.4.7.1 §11.2 PlanningTableOperation 联合类型扩展为：

```ts
type PlanningTableOperation =
  | { type: 'create_row'; clientRowId: string; parentId?: string | null; values: Record<string, unknown> }

  | { type: 'indent_row'; rowId: string }
  | { type: 'outdent_row'; rowId: string }
  | {
      type: 'template_generate';
      generationBatchId: string;
      templateId: string;
      selectedNodeIds: string[];
      scope: {
        buildings?: string[];
        floors?: string[];

```

```ts
interface TemplateGenerationPreviewRow {
  clientRowId: string;                    // 与 create_row 同一空间
  templateNodeId: string;                 // 来源模板节点

  floorId?: string;

提交路径唯一规则：

```text
模板生成预览只返回 previewRows,不得直接写 tasks / task_baseline_items / task_baselines
template_generate 只能作为共享计划树 commit operation 提交
项目基线页通过基线页保存 / 发布流程消费 template_generate
任务列表页通过任务列表保存流程消费 template_generate
月度计划页不产生 template_generate
任何独立的"生成并写库"接口都不得实现
后端必须在同一个事务中展开 template_generate、应用后续单元格编辑、写入 lineage 与业务事实
```

后端接收 template_generate 操作时执行：

```text
按 v1.4.4 给每条 previewRow 生成任务编码
按 v1.4.10 把模板节点的责任单位角色解析为具体 participant_unit_id,解析失败留空并记录字段缺失
按 v1.4.7.5 / v1.4.8 把同父级内部流、同分部 / 同工程对象跨分项跨施工包主线依赖、跨业务域约束依赖意图的有效结果展开为 task_dependencies 行；模板节点自身不携带依赖建议
按 v1.4.11 把模板节点的开工条件类型写入任务条件台账
按 v1.4.11 把模板节点的验收链接类型绑定到对应专项验收节点
按 v1.4.2 写 wbs_classification 字段
按 v1.4.6 写 lineage：source = template,source_template_id,source_template_node_id,generation_batch_id
按 v1.4.5 写初始状态
按 v1.4.7 写来源映射,把当前 surface 与生成批次绑定
```

后端在 template_generate 操作之后、本次 commit 内其他 update_cell / update_row 操作之前先执行展开。这样用户在 diff 预览之后手工微调的字段不会被默认值覆盖。

## 9. 后端生成器规则

```text

```text

```text
WBS 模板候选命中率不得再用 generatedRowCount 直接当 acceptedCandidates。
generatedRowCount = 本次模板生成候选行总数。
retainedRowCount = 用户确认保存后真实落库 / 保留的生成行数。
rejectedRowCount = 预览中被过滤、保存前被取消、或后续同批次明确删除的生成行数。
pendingRowCount = 已生成但尚未形成保留 / 拒绝结果的观察行数。
acceptance_rate = retainedRowCount / generatedRowCount。
后台 wbs_template_candidate_aggregations 只能按 retained / rejected / pending 三态累计；不得把“生成了”解释为“命中了”。
普通前端不展示 generated / retained / rejected / pending 等技术指标；它们只进入后台治理、Golden Case、候选升级和标准库质量报表。
```

候选升级边界：

```text
template_selection_retained、scenario_feature_confirmed_retained 等回流事件必须携带 generatedRowCount 与 retainedRowCount。
命中率达到阈值只说明“进入后台候选升级池”，不自动改 TS seed、不自动改现有任务、不自动回写历史基线 / 月计划。
候选状态至少区分 insufficient_samples / monitor / upgrade_candidate_ready / quarantine_review。
upgrade_candidate_ready 仅供企业标准库后台或治理报告消费；普通项目计划页面不显示“命中率”“候选升级”等词。
```

共享计划树中的用户体验必须保持安静：

不在通知中心强提醒
不进入待办
