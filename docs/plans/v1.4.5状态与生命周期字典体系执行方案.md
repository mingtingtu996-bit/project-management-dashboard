## 0. 2026-06-01 final range-tree boundary (authoritative)

This v1.4-series plan follows the final range-tree model. There is no production history or existing user data that needs a compatibility layer.

Authoritative engineering object types are exactly: `phase / section / building / basement / floor / physical_zone / functional_area`.

The following compatibility surfaces are deleted and must not be reintroduced in runtime code, migrations, or frontend contracts:

- `zone / professional / subproject / custom` as engineering object types.
- `zone_object_id / professional_object_id` task fields.
- `project_materials.professional_object_id` and `engineering_categories.professional_object_id`.
- `legacy_object_type`, deprecated object-type arrays, legacy bridge/backfill helpers, and old scope adapter functions.
- `/api/scope-dimensions`, `scope_dimensions`, and `project_scope_dimensions` as active application surfaces.

Professional/system/domain/method semantics remain business facts through `specialty_type`, `engineering_category_id`, `standard_work_code`, template metadata, and project profile facts. They are not range-tree objects.

Any older section in this document that mentions deleted object types, deleted fields, old scope tables, or compatibility adapters is superseded by this boundary.
# v1.4.5 状态与生命周期字典体系执行方案

## 1. 目标

v1.4.5 的目标是把当前应用中分散在 `任务 / 项目基线 / 月度计划 / 里程碑 / 证照 / 图纸 / 验收 / 风险 / 问题 / 预警 / 材料 / 条件 / 阻碍 / 主数据 / 数据质量 / 计划治理` 等模块里的状态口径统一收口，建立一套系统能理解、后端能校验、前端能稳定展示、BI 和 AI 能复用的状态与生命周期字典体系。

本方案不是把所有状态塞成一个通用枚举，而是按业务域分层治理：

```text
同一业务域内统一
不同业务域之间分层
主状态和派生状态分开
阶段和状态分开
前端业务语言和后端内部状态分开
旧状态只做兼容映射，不继续扩散
```

版本依赖顺序固定为：

```text
v1.4 工程对象主数据体系
-> v1.4.1 项目范围维度体系
-> v1.4.2 WBS 拆解标准体系
-> v1.4.3 施工任务标准数据模型
-> v1.4.4 建筑工程任务编码规则
-> v1.4.5 状态与生命周期字典体系
```

v1.4.5 必须尊重 `v1.3.5.3` 对计划编制三页的调整：项目基线、月度计划、任务列表共用 `PlanningTreeTable`，前端像编辑一张计划表，系统在后端处理草稿、锁、版本、重编、快照、映射和治理状态。不得把 `draft / lock / revision / pending_realign` 等内部治理概念重新推回前台主流程。

## 2. 核心结论

状态体系分为 5 层：

```text
1. 主生命周期状态
2. 派生分析状态
3. 流程阶段
4. 启停与有效性状态
5. 状态相邻字典
```

前端只展示用户需要理解的业务状态和动作。后端可以保留更细的内部状态，但必须通过统一字典、统一映射和统一 DTO 输出。

状态体系不新增一个大的前端“状态管理”页面。v1.4.5 的重点是：

```text
数据库建立状态字典底座
后端统一状态规范化、流转校验和派生计算
前端统一 StatusBadge / statusTheme / PlanningTreeTable 状态展示
旧中文、旧英文、历史状态统一映射
技术运行状态与施工业务状态隔离
```

### 3.5 状态相邻字典

这些不是生命周期状态，但必须统一，否则报表、驾驶舱和 AI 会继续出现口径漂移。

```text
severity: info / warning / critical 或 low / medium / high / critical
priority: low / medium / high / urgent / critical
warning_level: info / warning / critical
risk level: low / medium / high / critical
health_status: 健康 / 亚健康 / 预警 / 危险
confidence_flag: high / medium / low
dependency_kind: hard / soft
review_mode: mandatory / optional / none / manual_confirm
```

### 3.6 技术运行状态边界

`status_kind = technical` 只用于把历史技术状态和运行监控状态从施工业务状态里隔离出来，不作为任务、计划、验收、图纸、证照等业务对象的生命周期口径。

规则：

```text
HTTP 状态、网络在线离线、前端 loading/error、后台 job success/error/timeout 不进入施工业务生命周期
如确需记录技术状态，只能使用 domain_group = technical_runtime
technical_runtime 不参与 BI 施工统计、不进入 PlanningTreeTable、不参与任务完成率和项目健康度主口径
普通业务 DTO 不混入 technical 状态
```

## 4. 计划编制状态特殊规则

### 4.1 v1.3.5.3 的前端表达必须保留

项目基线、月度计划、任务列表共用 `PlanningTreeTable` 后，用户不应该理解三套版本治理流程。前端只表达业务动作：

```text
编辑
暂存
保存发布
确认当月
重新生成
取消
删除施工任务
```

以下状态和动作不作为前台主流程出现：

```text
进入草稿态页面
确认冻结
强制解锁草稿
发起修订
继续草稿
处理观察池
处理修订池
待重整
独立修正流程
延期申请审批
```

后端可以继续保留：

```text
draft
confirmed
closed
revising
pending_realign
archived
is_locked
release_reason
mapping_status
commitment_status
revision_pool_candidates.status
```

但必须通过 DTO 转译为前端业务语言。

### 4.2 项目基线前端状态

后端真实状态：

```text
draft
confirmed
closed
revising
pending_realign
archived
```

前端业务表达：

```text
当前生效
编辑中
待发布
已发布
历史版本
系统建议更新
```

映射规则：

```text
confirmed / pending_realign -> 当前生效
draft / revising -> 编辑中或待发布，取决于是否有未保存改动
closed / archived -> 历史版本
pending_realign -> 当前生效 + 系统建议更新
```

### 4.3 月度计划前端状态

后端真实状态：

```text
draft
confirmed
closed
revising
pending_realign
```

前端业务表达：

```text
未生成
待确认
已确认
已归档
可重新生成
```

映射规则：

```text
无记录 -> 未生成
draft / revising -> 待确认
confirmed -> 已确认
closed -> 已归档
pending_realign -> 已确认 + 可重新生成提示
```

### 4.4 任务列表前端状态

任务列表是现场当前执行表，状态由系统自动计算。前端可以展示：

```text
未开始
可开工
待开工
进行中
受阻
已延期
已完成
```

来源规则：

```text
status / progress / planned dates / actual dates / task_conditions / task_obstacles 共同派生
用户不直接选择“已延期”
进度首次大于 0 自动记录实际开始
进度达到 100% 且确认后自动记录实际完成
超过计划完成且未完成自动判定延期
条件未满足时显示待开工或待条件
存在未解决阻碍时显示受阻
```

后端仍可保存 `tasks.status`，但 `PlanningTreeTable` 展示状态必须优先使用后端 DTO 的 `businessStatus` / `displayStatus`，避免前端各页面重复推导。

### 5.6.1 状态字典 bootstrap 健壮性

v1.4.5 不得只依赖 migration 一次性预填充。运行时必须提供项目级自检和补齐能力，避免不同环境漏跑 migration、测试库清空或预置数据被误删后导致状态派生退化。

执行要求：

```text
statusDictionaryService 启动时检查 status_dictionary_versions 是否存在当前内置版本。
缺失当前版本、核心 domain、核心 status_value、alias、transition 或 derivation rule 时，自动从内置 seed 执行幂等补齐。
bootstrap 必须使用 upsert，不使用纯 insert，允许重复执行且不重复生成记录。
补齐完成后写入或更新 status_dictionary_versions，并记录 content_hash / change_reason / metadata。
启动补齐失败必须记录后端错误日志；普通业务接口不得因为字典缺失静默暴露 draft / lock / revision 等内部状态词。
statusDerivationService 可以保留最后兜底标签，但兜底只能作为临时降级，不替代 bootstrap 自愈。
```

服务入口要求：

```text
server/src/services/statusDictionaryService.ts
  ensureStatusDictionaryBootstrapped()

server/src/index.ts
  启动完成数据库连接校验后调用 ensureStatusDictionaryBootstrapped()

server/src/routes/status-dictionary.ts
  提供受控 POST /api/status-dictionary/bootstrap，用于测试、运维或管理员手动触发补齐
```

验收要求：

```text
空库迁移后启动服务，状态字典自动补齐。
删除某个核心 status_value 后重启或调用 bootstrap，记录被补回。
重复执行 bootstrap 不产生重复 domain/value/transition/alias/rule。
状态派生接口返回 dictionaryVersion，且普通前端仍只看到业务状态文案。
```

### 8.1 不删除旧字段

### 8.2 旧中文/英文状态统一映射

旧状态不直接报错，先进入 `status_aliases`：

```text
未开始 / not_started -> todo
空值 -> pending
进行中 -> in_progress
已完成 -> completed
已暂停 -> paused
待处理 -> pending
处理中 -> resolving / in_progress
已解决 -> resolved
无法解决 -> unresolved / closed_by_exception
待验收 -> draft 或 ready_to_submit，按验收域处理
验收中 -> inspecting
已通过 -> passed / approved，按业务域处理
未通过 / 需修改 -> rectifying / rejected，按业务域处理
待申请 -> pending
办理中 -> external_submission 或 in_progress，按证照域处理
已取得 -> issued
需延期 -> supplement_required 或 overdue，按证照域处理
```

同一个中文词在不同业务域含义可能不同，必须按 `domain_key` 映射，不能做全局字符串替换。

### 8.3 历史兼容字段与新字典关系

规则：

```text
业务表 status 继续保存当前真实状态
status_aliases 负责兼容历史值
status_values 负责标准值和显示值
status_transitions 负责合法流转
status_derivation_rules 负责派生说明
前端不直接解析旧状态字符串
BI 不直接按旧中文状态聚合
```

### 8.4 不确定旧状态的处理

如果旧状态无法明确映射：

```text
读取时归一化为该业务域 initial 状态或 unknown
写入时必须写标准状态
数据质量服务生成 finding
普通前端不显示“状态待校准”标签
读取时由后端 DTO 返回可理解的兜底业务状态或 initial 状态
影响业务动作时复用现有错误提示，不暴露 unknown/rawStatus 等内部字段
主写链不得继续写入未知状态
```

`unknown` 使用规则：

```text
如果某个 domain 允许读取 unknown，则必须在 status_values 中显式 bootstrap status_key = unknown
unknown 只能用于读取兼容和数据质量提示，不得作为普通写入目标
unknown 不参与完成率、关闭率、延期率等业务统计分子
unknown 必须触发 data_quality.finding_status = active
如果 domain 不允许 unknown，则读取无法映射值时回退到该 domain 的 is_initial 状态，并记录 rawStatus
```

### 8.5 旧业务对象如何处理

v1.4.5 只治理“状态与生命周期口径”，不因状态字典改造而重建、删除或迁移已有业务对象记录。

这里的“不迁移业务对象”只约束 v1.4.5 自身，不否定前序版本已经定义的对象治理动作：

```text
v1.4 / v1.4.1 仍可执行范围维度到 engineering_objects 的兼容映射
v1.4.2 仍可执行 WBS 行到 engineering_categories 的语义推断和显式校准
v1.4.3 仍可执行任务标准字段回填和依赖关系回填
v1.4.4 仍可为 active 任务补齐范围对象、工程分类和 task_code
```

v1.4.5 不新增一套独立对象迁移逻辑，只读取这些前序版本已经形成或回填后的对象关系，并接管状态解释、状态显示、状态流转和派生状态口径。

已移除旧流程处理规则：

```text
delay_requests / task_delay_history 已在当前最终态中移除，不作为 v1.4.5 新状态域恢复
历史延期含义通过 change_logs、task_completion_reports、task_summary、progress_deviation、due/lag 派生状态解释

```

这里的旧业务对象包括但不限于：

```text
已有任务
已有项目基线
已有月度计划
已有里程碑
已有证照事项
已有图纸记录
已有验收计划和验收时间轴

```

处理规则：

```text
对象记录本身原地保留
对象主键、关联关系、创建时间、业务内容不因状态字典改造而改变
只对对象上的状态字段做标准化解释、兼容映射、流转校验和派生计算
```

## 9. 流转规则

### 9.1 任务状态流转

标准状态：

```text
todo
pending
in_progress
blocked
completed
cancelled
```

兼容状态：

```text
not_started / 未开始 -> todo
空值 -> pending
unknown 历史值 -> pending；普通写入 unknown 必须拒绝
进行中 -> in_progress
已完成 -> completed
done -> completed
on_hold / delayed -> blocked
```

规则：

```text
pending 表示已创建但尚未进入明确待办或开工判断的任务
todo 表示明确待办/未开始任务
progress > 0 时可自动进入 in_progress
progress = 100 且确认完成时进入 completed
completed 回退必须走 reopenTask，不允许普通 updateTask 隐式回退
blocked 可以由未解决阻碍派生，也可以作为主状态兜底
cancelled 表示任务取消，不等同于删除；取消任务不进入完成率分子
cancelled / archived / voided / deleted 不属于 v1.4.4 activeTaskPredicate 的 active 任务；如需重新激活，必须走主写链并重新校验范围对象、工程分类和 task_code
延期不作为 tasks.status 主状态，作为 due/lag 派生状态
```

### 9.2 条件状态流转

标准状态：

```text
open
met
confirmed
blocked
closed
```

兼容映射：

```text
待处理 / 未满足 -> open
已满足 -> met
已确认 -> confirmed
```

规则：

```text
is_satisfied=true 优先推导 met/confirmed
confirmed 需要 confirmed_by / confirmed_at
条件未满足可以阻断进度推进
```

### 9.3 阻碍状态流转

标准状态：

```text
open
resolving
resolved
closed
unresolvable
```

兼容映射：

```text
待处理 / active -> open
处理中 / resolving -> resolving
已解决 / resolved -> resolved
无法解决 -> unresolvable
closed -> closed
```

规则：

```text
is_resolved=true 优先推导 resolved
resolved/closed 不计入 activeObstacleCount
unresolvable 需要进入问题或风险链路，不得静默消失
```

### 9.4 风险状态流转

标准状态保持：

```text
identified
mitigating
closed
```

规则：

```text
identified -> mitigating
mitigating -> closed
closed -> identified 仅允许 reopen
系统升级链路可以自动将 warning 转 risk
pending_manual_close 作为关闭确认辅助字段，不是状态
```

### 9.5 问题状态流转

标准状态保持：

```text
open
investigating
resolved
closed
```

规则：

```text
open -> investigating
investigating -> resolved
resolved -> closed
resolved -> investigating 允许继续处理
pending_manual_close 作为人工确认关闭辅助字段，不是状态
```

### 9.6 验收状态流转

标准状态保持：

```text
draft
preparing
ready_to_submit
submitted
inspecting
rectifying
passed
archived
```

规则：

```text
passed / archived 视为完成
rectifying 视为未通过后的整改中
blocked 不进入主 status，由 is_blocked / requirement 状态派生
```

### 9.7 证照状态流转

标准状态：

```text
pending
preparing_documents
internal_review
external_submission
supplement_required
approved
issued
expired
voided
```

规则：

```text
current_stage / item_stage 表示阶段，不替代 status
issued 视为已取得
expired 是生命周期状态
voided 是终止状态
supplement_required 是外部报批后的补正状态
```

### 9.8 图纸状态与审查状态

图纸主状态：

```text
preparing
reviewing
revising
issued
completed
voided
```

审查状态：

```text
not_submitted
reviewing
approved
rejected
revision_required
```
