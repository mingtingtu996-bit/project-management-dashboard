## 0. 2026-06-01 final range-tree boundary (authoritative)

This v1.4-series plan follows the final range-tree model. There is no production history or existing user data that needs a compatibility layer.

Authoritative engineering object types are exactly: `phase / section / building / basement / floor / physical_zone / functional_area`.

The following compatibility surfaces are deleted and must not be reintroduced in runtime code, migrations, or frontend contracts:

- `zone / professional / subproject / custom` as engineering object types.
- `zone_object_id / professional_object_id` task fields.
- `project_materials.professional_object_id` and `engineering_categories.professional_object_id`.
- `legacy_object_type`, deprecated object-type arrays, legacy bridge/backfill helpers, and old scope adapter functions.
- `/api/scope-dimensions`, `scope_dimensions`, and `project_scope_dimensions` as active application surfaces.

Professional/system/domain/method semantics remain business facts through `specialty_type`, `engineering_category_id`, `standard_work_code`, template metadata, and project profile facts. They are not range-tree objects.

Any older section in this document that mentions deleted object types, deleted fields, old scope tables, or compatibility adapters is superseded by this boundary.
# v1.4.2 WBS 拆解标准体系执行方案

## 1. 目标

v1.4.2 的目标是把当前项目基线、月度计划、任务列表已经共用的 WBS 表格结构，升级为有明确工程语义的 WBS 拆解标准体系。

本方案不新建一套脱离现有表格的项目 WBS 树。现有 `PlanningTreeTable` 继续作为项目 WBS 的前端承载体，现有 `tasks.parent_id / wbs_code / wbs_level` 继续作为 WBS 树形关系的兼容基础。

v1.4.2 只解决“WBS 节点代表什么工作、哪些节点可执行、简单任务如何压缩层级”。范围维度、工程对象、责任主体、验收检验批不混入 WBS 工作分类。

版本依赖顺序必须固定为：

```text
v1.4 工程对象主数据体系
-> v1.4.1 项目范围维度体系
-> v1.4.2 WBS 拆解标准体系
```

v1.4.2 依赖 v1.4.1 提供的范围对象 ID 口径。若 v1.4.1 未完成，新建或编辑 WBS 行时“至少一个范围对象 ID”的校验无法稳定落地。

## 2. 核心结论

WBS 只回答“做什么工作”。

```text
WBS 拆解：做什么
范围维度：在哪做
责任主体：谁来做
计划字段：什么时候做
执行字段：做到哪了
验收体系：做完怎么验
```

业务默认主干展示为：

```text
分部工程 division
  子分部工程 sub_division
    分项工程 item_work
      工序 process
```

数据库不硬编码 4 层，底层使用通用工程分类树 `engineering_categories`：

```text
category_type 可为 division / sub_division / item_work / process / activity_step / custom
category_level 只表示树深度，不等同于固定业务类型
parent_id / category_path 表示真实父子关系
```

复杂工程可扩展为：

```text
分部工程 -> 子分部工程 -> 分项工程 -> 工序 -> 作业步骤
```

不作为 WBS 工作分类：

```text
单位工程
检验批
施工段
工作包
施工任务
```

处理原则：

```text
单位工程由项目范围维度组合表达，例如 分期 + 标段 + 楼栋
施工段由范围维度表达，例如 楼层 + 区域
检验批进入验收体系，不进入默认 WBS 表格
工作包可后续由系统按范围 + 分项 + 工序聚合生成，不作为标准节点类型
施工任务在当前产品统一收口为 process 工序
作业步骤 activity_step 仅用于复杂工程或精细作业清单，默认不主动生成、不强制使用
```

## 3. 当前共享表格就是 WBS 承载体

当前应用已经形成统一表格底座：

```text
项目基线：冻结版 WBS 总进度计划
月度计划：本月承诺版 WBS 计划
任务列表：现场执行版 WBS 任务表
```

三者不是三套 WBS，而是同一套 WBS 结构在不同计划治理阶段的视图：

```text
项目基线负责确认总进度计划结构
月度计划负责截取和承诺当月执行范围
任务列表负责现场滚动执行和进度事实
```

执行要求：

```text
继续复用 PlanningTreeTable
继续复用行号 / WBS 操作区、缩进、反缩进、展开收起、单元格编辑
不新增独立 project_wbs_nodes 表来替代当前共享表格
不把 WBS 模板页作为项目真实 WBS 的唯一入口
```

## 4. 工程分类类型标准

`division` 分部工程：

```text
含义：工程中较大的工作组成部分
示例：地基与基础、主体结构、建筑装饰装修、屋面、建筑电气
行为：结构汇总节点，默认不直接填现场进度
```

`sub_division` 子分部工程：

```text
含义：分部工程下进一步按工程构造、专业或施工内容拆分的组成部分
示例：混凝土结构、砌体结构、楼地面工程、门窗工程
行为：结构汇总节点，默认不直接填现场进度
```

`item_work` 分项工程：

```text
含义：可形成明确质量、验收和施工内容边界的工作项
示例：钢筋工程、模板工程、混凝土工程、水泥砂浆地面
行为：可作为质量/验收/统计关联对象，通常不直接作为最细执行行
```

`process` 工序：

```text
含义：现场可计划、可分派、可填进度、可确认完成的最小默认执行颗粒
示例：钢筋加工、钢筋绑扎、模板安装、混凝土浇筑、基层清理
行为：叶子执行行，进入计划、进度、责任、条件、阻碍、完成事实
```

`activity_step` 作业步骤：

```text
含义：工序下进一步拆出的细化步骤
示例：材料倒运、放线、自检、整改、报验准备
行为：系统直接支持，但默认不主动生成、不作为必填层级；只有用户明确新增、模板明确携带或导入数据已有时才出现
```

`custom` 自定义分类：

```text
含义：无法归入标准分类的临时工作分类
行为：必须在 metadata 中记录原因，后续沉淀时应归并到标准类型
```

里程碑：

```text
里程碑不是独立 WBS 节点类型
继续使用 is_milestone 或 milestone 标记
任一 WBS 节点都可以被标记为关键节点/里程碑
里程碑标记不改变节点自身的 category_type
```

## 5. 简单任务的合理分解

WBS 标准层级是能力，不是强制四级模板。简单任务不需要为了凑层级而制造空的子分部或分项。

允许三种结构：

```text
标准四级：分部工程 -> 子分部工程 -> 分项工程 -> 工序
压缩三级：分部工程 -> 分项工程 -> 工序
压缩二级：分部工程 -> 工序
```

特殊临时或零星任务允许单行工序：

```text
工序
```

单行工序也必须满足 v1.4.1 的范围归属规则：新建或编辑保存时至少存在一个范围对象 ID。责任人、责任单位不能替代范围归属。

分解规则：

```text
不要创建没有业务含义的中间层
能用一个工序说清楚的，不强制拆成多个作业步骤
同一父级下有 3 个以上同类工序时，建议补一个分项工程承接
跨专业、跨楼栋、跨区域的工作，不靠 WBS 拆分范围，必须用范围维度拆开
需要独立责任、独立计划完成、独立进度确认的内容，应拆成独立工序
只用于备注说明、检查步骤、班组内部动作的内容，不进入默认 WBS 行
```

示例一，标准四级：

```text
2 主体结构                    division
  2.1 混凝土结构              sub_division
    2.1.1 钢筋工程            item_work
      2.1.1.1 钢筋加工        process
      2.1.1.2 钢筋绑扎        process
      2.1.1.3 隐蔽验收配合    process
```

示例二，压缩三级：

```text
3 建筑装饰装修                division
  3.1 墙面工程                item_work
    3.1.1 基层处理            process
    3.1.2 腻子施工            process
    3.1.3 乳胶漆施工          process
```

示例三，压缩二级：

```text
4 临时设施                    division
  4.1 围挡安装                process
  4.2 临水接驳                process
  4.3 临电接驳                process
```

示例四，单行工序：

```text
1 临时排水沟清理              process
```

单行工序适合临时、零星、非模板化任务。后续如沉淀为标准做法，再归入正式分部/分项结构。

示例五，只有两行的极简结构：

```text
1 临时设施                    division
  1.1 围挡安装                process
```

系统不得因为 `围挡安装` 是第 2 层就强行判为 `sub_division`。它是叶子行且可执行，应推断为 `process`。

复杂任务允许增加作业步骤：

```text
2 主体结构                    division
  2.1 混凝土结构              sub_division
    2.1.1 钢筋工程            item_work
      2.1.1.2 钢筋绑扎        process
        2.1.1.2.1 放线复核    activity_step
        2.1.1.2.2 钢筋绑扎    activity_step
        2.1.1.2.3 自检整改    activity_step
```

作业步骤只在确实需要独立计划、独立责任、独立完成确认或班组日计划时创建。普通项目不应把所有工序机械拆成作业步骤。

## 6. 数据模型修订

新增通用工程分类树 `engineering_categories`，用于维护 WBS 工作分类标准。现有任务/WBS 行继续承载项目基线、月度计划、任务列表的实际计划与执行数据。

> 命名约定：数据库表名统一使用 `engineering_categories`，API 使用 `/api/engineering-categories`，前端类型可使用单数 `EngineeringCategory`。文档后续提到 `engineering_category_id` 时，表示引用 `engineering_categories.id` 的外键字段。

`engineering_categories` 必须新增字段：

```text
id: 分类 ID
project_id: 项目 ID，可为空；为空表示系统级或模板级分类
parent_id: 上级分类 ID
category_name: 分类名称
category_type: division | sub_division | item_work | process | activity_step | custom
category_level: 树深度，由后端计算
category_path: 分类路径，例如 /rootId/childId/leafId
specialty_type: 业务专业属性，可为空；不引用 engineering_objects
standard_work_code: 稳定工作分类编码，用于模板沉淀、标准工序识别和后续任务编码
standard_work_name: 稳定工作分类名称快照；默认等于 category_name，可按企业标准别名调整
sort_order: 同级排序
enabled: 是否启用
metadata: 扩展信息
created_at / updated_at
```

执行要求：

```text
默认内置 4 层业务主干，但数据库不限制只能 4 层
category_level 只表示深度，不表示固定类型
category_type 表示业务语义
系统不得仅按 category_level 判断节点语义
parent_id / category_path 表示真实层级
专业归属不使用 professional 工程对象；需要表达专业时使用 specialty_type、standard_work_code、engineering_category_id 或模板 metadata
standard_work_code 由后端生成或从系统标准库导入，不允许前端自由手写重复编码
standard_work_code 不得由 wbs_code、任务标题、前端行号推导
```

唯一约束与覆盖规则：

```text
同一 project_id、同一 parent_id 下，enabled=true 的 category_name 不允许重复。
系统级分类 project_id=null，用作默认标准库；项目级分类 project_id=具体项目，用作项目覆盖或补充。
项目级分类可以与系统级分类同名，但必须通过 metadata.sourceSystemCategoryId 或 standard_work_code 记录来源关系。
同一项目内如果项目级分类与系统级分类同名，读取时优先返回项目级分类，并保留系统级分类作为来源参考。
bootstrap 不得重复创建同名 enabled 分类；重复调用必须幂等。
删除默认软删除 enabled=false，软删除后同级可重新创建同名分类。
```

在现有任务/WBS 行模型上补分类引用和标准语义字段，不新建脱离当前任务树的项目 WBS 主表。

必须新增或标准化字段：

```text
engineering_category_id: 引用 engineering_categories.id
wbs_node_type: division | sub_division | item_work | process | activity_step | custom
wbs_path: WBS 节点路径，例如 /rootId/childId/leafId
is_wbs_summary: 是否结构汇总节点
is_leaf: 是否叶子节点
is_executable: 是否可进入现场执行
standard_work_code: 可选，标准工作编码
standard_work_name: 可选，标准工作名称
```

继续保留并兼容：

```text
parent_id
wbs_code
wbs_level
sort_order
template_id
template_node_id
is_milestone
```

字段含义：

```text
wbs_level 表示当前树深度，不等于固定业务类型
engineering_category_id 存在时，category_type 是工作分类主语义
wbs_node_type 是任务行上的兼容/缓存语义，缺失时由关联分类的 category_type 推导
process 默认 is_executable = true
activity_step 可执行，系统直接支持，但默认新增和默认模板不主动生成
division / sub_division / item_work 默认 is_wbs_summary = true
item_work 如果没有子节点且确实要直接执行，保存前应提示转为 process
```

前端消费规则（与 v1.4.7.1 对齐）：

```text
共享计划树、任务列表、基线页、月度计划页展示 WBS 语义时，必须按以下优先级解析：
1. tasks.wbs_node_type
2. engineering_category_id 关联 engineering_categories.category_type（API 可返回为 engineering_category_type / category_type）
3. 前端 depth / 是否有子级 / is_executable 的展示 fallback

第 3 级 fallback 只能用于兼容缺失数据时的临时展示，不得反向写成业务分类。
行卡片字号、字重、语义标签、汇总/执行行视觉权重，必须使用上述解析结果，不得只靠前端树深度推断。
```

编码边界：

```text
wbs_code 是项目内位置编码，随缩进、反缩进、拖拽排序和同级重排变化
standard_work_code 是标准工作分类编码，不随项目内排序变化
wbs_code 用于项目树展示和位置识别
standard_work_code 用于模板沉淀、标准工序识别、后续任务编码规则衔接
后续建筑工程任务编码规则不得直接复用 wbs_code 作为标准工作编码
```

## 7. 节点行为规则

结构汇总节点：

```text
division / sub_division / item_work 默认是结构行
结构行可展示计划日期、总工期、汇总进度
结构行进度由子级 process 汇总
结构行可编辑名称、分类、层级、排序和里程碑标记
结构行默认不直接填写现场进度、责任人、阻碍和完成事实
结构行的计划开始、计划完成、工期默认由子级汇总；确需手工约束时应作为计划约束字段处理，不覆盖子级执行事实
```

结构行汇总口径：

```text
结构行进度优先按可执行子孙行的计划工期或目标工期加权汇总
缺少工期时，按可执行子孙行等权汇总
已完成执行行按 100% 计入
取消、停用、删除或不纳入计划的执行行不参与汇总
结构行的计划开始取参与汇总子孙行最早开始日期
结构行的计划完成取参与汇总子孙行最晚完成日期
汇总口径由后端统一服务计算，前端不得自行扫描 rows 得出主口径
```

执行节点：

```text
process 是默认执行行
process 可维护计划开始、计划完成、进度、责任人、责任单位、条件、阻碍、完成确认
process 完成后进入任务总结、报表、驾驶舱和里程碑兑现计算
activity_step 作为 process 下的更细执行行，系统直接支持，但默认不主动生成
只有用户明确选择“新增作业步骤”、模板节点明确为 activity_step，或导入数据已有 activity_step 时，才创建 activity_step
如果 process 下存在 activity_step，则 process 自动转为汇总行，由 activity_step 汇总完成
```

`activity_step` 创建规则：

```text
不新增项目级 activity_step 开关。
不在 engineering_categories.metadata 中维护 enableActivityStep。
数据库、后端、模板、导入导出均允许 activity_step。
默认新增子级、默认模板和普通自动推断最多生成到 process，不主动生成 activity_step。
process 下允许新增 activity_step，但必须来自明确用户操作、模板明确字段或导入数据明确字段。
process 下出现 activity_step 后，process 自动转为汇总行，进度、完成事实由 activity_step 汇总。
如果用户在 process 下使用普通“新增子级”而非“新增作业步骤”，后端不得猜测为 activity_step，应返回可理解提示，要求用户选择“新增作业步骤”或先转换父级类型。
```

里程碑标记：

```text
is_milestone = true 时，该节点进入里程碑页、关键节点统计和偏差分析
如果 process 被标记为里程碑，完成事实来自该工序自身
如果结构节点被标记为里程碑，完成事实由其下所有可执行 process 汇总确认
```

删除和缩进：

```text
删除结构节点时必须明确是否包含子节点一起删除
缩进/反缩进后必须重新计算 wbs_code、wbs_level、wbs_path、is_leaf、is_wbs_summary
拖拽或排序后必须保持同级 wbs_code 连续
```

## 8. 与范围维度的关系

WBS 节点不表达施工范围。

范围维度与工程分类是两套不同底座：

```text
范围维度 engineering_objects：回答“在哪做”，例如分期、标段、楼栋、楼层、区域、专业
工程分类 engineering_categories：回答“做什么”，例如分部、子分部、分项、工序、作业步骤
```

现有“范围维度”入口不能直接替代工程分类规则。工程分类优先由 WBS 表格行操作自动推断，不默认新增独立维护入口。后续如合并到同一个“项目设置 / 基础数据”页面壳里，也必须使用不同的数据源、不同 API、不同语义。

正确组合方式：

```text
WBS：主体结构 / 混凝土结构 / 钢筋工程 / 钢筋绑扎
范围：一期 / 一标段 / 1#楼 / 10层 / 东区
专业：土建
责任：钢筋班组 / 张三
```

强制对齐 v1.4.1：

```text
新建或编辑 WBS 行保存为任务/计划行时，必须至少有一个范围对象 ID
责任人、责任单位只能回答“谁做”，不能替代范围对象
旧数据缺少范围对象 ID 时，可展示为历史/异常数据质量问题，但不能作为新建或编辑后的合法状态
```

禁止做法：

```text
把 1#楼、10层、东区写成 WBS 节点类型
把施工段作为 WBS 节点类型
用 WBS 标题文本解析楼栋、楼层、区域
```

## 9. WBS 模板定位

现有 WBS 模板能力保留，但定位调整为“生成和沉淀共享表格行的来源”。

```text
WBS 模板：提供分部 / 子分部 / 分项 / 工序 / 作业步骤的标准拆解建议
项目基线：确认本项目采用后的 WBS 总进度计划
月度计划：从项目基线和任务列表中截取当月承诺范围
任务列表：承接现场执行、进度事实和滚动调整
```

模板节点必须能映射到本方案的工程分类：

```text
division
sub_division
item_work
process
activity_step
custom
```

无法识别的旧模板节点：

```text
优先按是否有子节点推断 summary/process
不能可靠推断时标记为待校准
不自动把单位工程、检验批、施工段、工作包作为新节点类型
```

## 10. 既有 WBS 对象与旧字段处理策略

v1.4.2 不迁移出一张新的项目 WBS 主表。改造后，既有 `tasks` 行仍然是项目真实 WBS 行，项目基线、月度计划、任务列表仍围绕同一套 WBS 表格行工作。

既有对象处理：

```text
现有 tasks 行继续保留，不搬迁到 project_wbs_nodes
现有 parent_id / wbs_code / wbs_level / sort_order 继续作为树形结构兼容基础
现有 template_id / template_node_id 继续作为模板来源追踪
现有 is_milestone 继续作为里程碑标记
现有 WBS 模板继续作为生成和沉淀来源，不替代项目真实 WBS
```

新增语义字段后的处理：

```text
新增 engineering_category_id 后，不强制批量改写全部旧行
旧行首次读取时，后端按模板来源、父子结构、是否叶子、是否可执行推断 wbs_node_type
读取时只返回 inferred=true / calibration_status，不允许因读取动作隐式写库
推断可靠时可在用户保存、显式校准、模板套用或专门 backfill 任务中回填 engineering_category_id / wbs_node_type
专门 backfill 任务必须可重复执行、可审计，并只处理推断置信度足够的旧行
推断不可靠时标记待校准，但不阻断查看、展开、排序、筛选
用户编辑保存旧行时，系统必须自动补齐或确认 engineering_category_id / wbs_node_type
旧行如果缺少 v1.4.1 要求的范围对象 ID，编辑保存时必须补齐至少一个范围对象 ID
```

既有表格行为：

```text
旧行继续在 PlanningTreeTable 中显示
旧行的缩进、反缩进、拖拽排序继续可用
旧行保存后必须重新计算 wbs_code / wbs_level / wbs_path / is_leaf / is_wbs_summary
旧结构行的进度、日期、工期逐步切换为子级汇总
旧执行行的进度、责任、条件、阻碍继续保留
```

旧字段继续保留：

```text
parent_id
wbs_code
wbs_level
sort_order
task_type
template_id
template_node_id
is_milestone
```

旧数据推断规则：

```text
有子节点的行默认 is_wbs_summary = true
无子节点的行默认 is_leaf = true
无子节点且无明确 wbs_node_type 的行默认推断为 process
depth 1 且有子节点的行默认推断为 division
depth 2 且有子节点的行默认推断为 sub_division 或 item_work，无法判断时标记待校准
is_milestone = true 只迁移为里程碑标记，不覆盖 wbs_node_type
旧数据没有 engineering_category_id 时，不阻断展示；后端返回 inferred 标识
```

旧前端展示：

```text
PlanningTreeTable 继续显示 WBS / 任务名称 / 计划开始 / 计划完成等列
新增类型展示时使用中文标签：分部工程 / 子分部工程 / 分项工程 / 工序
如存在作业步骤，展示中文标签：作业步骤
旧 rowType 继续用于视觉样式，但业务判断以 wbs_node_type 为准
```

## 11. API 与兼容

任务创建、编辑、缩进、反缩进、拖拽排序接口必须支持 WBS 语义字段。

旧 `/api/wbs` 兼容策略：

```text
现有 /api/wbs 路由继续保留为兼容入口，不新增第二套 WBS 写入规则。
/api/wbs 的 POST / PUT / DELETE 必须委托同一套任务树写入服务，执行 WBS 语义推断、范围对象 ID 校验、wbs_code / wbs_level / wbs_path 重算。
/api/wbs 不得继续只按 wbs_level / parent_id 直接创建或更新 tasks。
新前端优先调用 tasks / planning 对应写入链；旧前端或旧测试仍命中 /api/wbs 时，返回结构保持兼容，但数据来源和写入规则必须统一。
完成前端迁移后，可把 /api/wbs 标记为 deprecated，但不能在 v1.4.2 直接删除。
```

写入规则：

```text
前端可提交 wbs_node_type，但默认应由后端根据行操作自动推断
前端可提交 engineering_category_id，但仅用于模板套用、低频校准或高级编辑
前端不得直接提交 wbs_path
后端负责计算 wbs_path、is_leaf、is_wbs_summary、wbs_code、wbs_level
如果传入 engineering_category_id，后端必须校验分类 enabled=true 且 project_id 匹配或为系统级分类
如果 engineering_category_id 与 wbs_node_type 同时传入且语义冲突，后端返回 400
如果 process 下新增子节点，只有明确“新增作业步骤”、模板明确 activity_step 或导入数据明确 activity_step 时允许创建 activity_step
如果 process 下使用普通“新增子级”且没有明确 activity_step 意图，后端返回 400，并提示选择“新增作业步骤”或先转换父级类型
```

读取规则：

```text
优先返回 engineering_category_id 和工程分类信息
同时返回 wbs_node_type，优先由关联分类的 category_type 推导
wbs_node_type 缺失且无 engineering_category_id 时，按旧字段推断并返回 inferred 标识
待校准只作为后端 calibration_status 和 data_quality_findings 记录
普通前端不常驻展示“待校准”标签，不新增校准弹窗
新建和编辑保存时如无法自动推断工程分类，后端直接返回明确错误，要求补齐可判定信息
旧任务读取不因待校准阻断查看、展开、排序、筛选
```

BI 化口径约束：

```text
WBS 分类、结构行汇总进度、执行行计数、里程碑汇总、任务总结、报表和驾驶舱统计必须由后端统一服务计算
PlanningTreeTable 只消费后端返回的行语义、汇总字段和展示字段，不得在前端扫描 rows 生成主口径指标
前端可以做视觉映射、展开收起、排序展示和局部交互状态，但不得把这些临时状态写成统计真值
所有对外汇总指标必须接入 projectExecutionSummaryService、project_daily_snapshot 或后续统一 WBS summary service，并登记到 metricRegistry
路由层不得随手 reduce/filter 生成新的对外统计口径；确需新增指标时必须先定义业务口径、服务出口和 metric key
```

新增工程分类 API：

```http
GET /api/engineering-categories?projectId=&professionalObjectId=&enabled=
POST /api/engineering-categories
PATCH /api/engineering-categories/:id
DELETE /api/engineering-categories/:id
POST /api/engineering-categories/bootstrap
```

删除规则：

```text
默认软删除，设置 enabled=false
已被任务、基线、月度计划引用的分类不得物理删除
停用分类不再用于自动推断和模板套用，历史行仍可展示分类名称
```

自动推断规则：

```text
推断优先级：engineering_category_id > 模板节点类型 > 用户操作意图 > 父级类型 > 是否有子级/是否可执行 > 待校准
无父级新增行：默认推断为 division；如果用户使用“新增工序/快速任务”，可直接推断为 process
division 下新增子级：默认 sub_division；如果用户使用“新增工序”，允许直接 process
sub_division 下新增子级：默认 item_work
item_work 下新增子级：默认 process
process 下新增子级：仅在明确“新增作业步骤”、模板明确 activity_step 或导入数据明确 activity_step 时推断为 activity_step
process 下普通新增子级：返回 400，提示选择“新增作业步骤”或先转换父级类型
缩进/反缩进后：后端按新父级和子级关系重新推断 category_type
已人工校准 engineering_category_id 的行：除非发生父子语义冲突，否则不得被自动推断覆盖
模板套用时：优先沿用模板节点的 engineering_category_id / category_type
不能只按第几层判断语义；压缩结构和扩展结构都必须支持
叶子行且可执行时，优先推断为 process 或 activity_step
有子级的行优先推断为结构/汇总行；process 下存在 activity_step 时，process 自动转为汇总行
```

## 14. 执行前评审结论与补充要求

按当前代码状态看，v1.4.2 的体系方向成立，但不能只改 `tasks` 一张表。当前项目基线、月度计划和任务列表已经共享一套树表体验，却分别有自己的持久化表和 DTO，执行时必须把 WBS 语义字段同步到这些承载层。

当前代码差距：

```text
tasks 已有 parent_id / wbs_code / wbs_level / sort_order / template_id / template_node_id / is_milestone 等兼容字段
tasks 已通过 121 增加 engineering_category_id / wbs_node_type / wbs_path / is_wbs_summary / is_leaf / is_executable / standard_work_code / standard_work_name
tasks 已通过 172 增加并回填 duration_contribution_mode；后续新写入必须显式携带或由 task 写链推断持久化，缺失不再按 warning 放行
task_baseline_items 已通过 121 增加 WBS 语义快照字段，但写入链路仍需确认会从 tasks 复制这些字段
monthly_plan_items 已通过 121 增加 WBS 语义快照字段，但写入链路仍需确认会从 baseline_item 或 source_task 复制这些字段
engineering_categories 主表在 121 本体中未包含 standard_work_code / standard_work_name，但当前仓库已通过 121a_add_engineering_categories_standard_fields.sql 补齐；执行时必须识别 121a 或等价修订迁移
wbs_templates 当前主要通过 wbs_nodes / template_data JSON 保存模板节点，模板节点没有稳定 category_type / engineering_category_id / calibration_status 字段
PlanningTreeTable / PlanTreeEditor / GanttViewRows 已能承载树形表格，但尚未具备工程分类语义、后端校准状态消费、结构行/执行行编辑限制
现有 wbs_structure / wbs_template_nodes / standard_processes 属于历史或局部能力，不能被误认为 v1.4.2 的项目真实 WBS 主表
现有 /api/wbs 路由仍可按 wbs_level / parent_id 直接创建或更新 task，尚未委托统一 WBS 语义写入服务
Dashboard 中仍存在按 wbs_nodes.node_type=building 或从 tasks.wbs_code 解析楼栋进度的逻辑，与“WBS 不表达施工范围”冲突
当前报表、驾驶舱和任务总结还不能按 is_executable / is_wbs_summary 可靠区分结构行与执行行
```

数据模型补充要求：

```text
当前仓库 v1.4.2 已使用 `121_add_wbs_engineering_categories.sql`；不得再把 v1.4.2 写成 122，122 已用于 v1.4.3 施工任务标准数据模型
新增 engineering_categories 时必须包含 category_type check、enabled、category_path、category_level、specialty_type、metadata、created_at / updated_at
engineering_categories 必须具备 standard_work_code / standard_work_name；当前 121 本体未补这两个字段，但当前仓库已通过 121a 修订迁移补齐。
如果目标分支已有 121a 或等价修订迁移，不得重复新增同语义迁移；如果目标分支缺少 121a，才按当前最大编号 + 1 新增幂等修订迁移，并让后续版本迁移号顺延。
如果按 v1.4.2 -> v1.4.3 -> v1.4.4 串联执行，v1.4.4 的 123_create_task_code_rules.sql 仍需用 add column if not exists 幂等确认字段存在，但不再承担 v1.4.2 主体字段创建责任。
engineering_categories 必须补索引：project_id / parent_id / category_type / specialty_type / enabled / category_path / standard_work_code
engineering_categories 必须补同级 enabled 分类名称唯一约束，并明确系统级分类与项目级分类覆盖关系
engineering_categories 必须补 RLS：项目成员/company_admin 可读，service_role 或后端 API 可写
tasks 增加 engineering_category_id / wbs_node_type / wbs_path / is_wbs_summary / is_leaf / is_executable / standard_work_code / standard_work_name
tasks 必须具备 duration_contribution_mode，历史数据由 172 迁移从现有字段和 standard_task_metadata 回填，结构汇总行默认 record_only，其余历史执行行默认 duration_bearing，并同步写回 metadata
task_baseline_items 增加同一组 WBS 语义快照字段，保证已确认基线不因源任务后续变化而漂移
monthly_plan_items 增加同一组 WBS 语义快照字段，保证月度承诺、关账和偏差分析有稳定口径
wbs_templates 的 wbs_nodes / template_data 节点结构增加 category_type / engineering_category_id / standard_work_code / standard_work_name / calibration_status / inferred
全量迁移快照 CLEAN_MIGRATION* 与 FULL_MIGRATION* 必须同步加入 engineering_categories 和新增字段
WBS / planning table / task write chain 的新增或更新请求缺失 durationContributionMode 时必须进入 error / block_save；只允许历史读取保留兼容 fallback warning，不允许新数据继续写入缺失 mode
```

与 v1.2 BI 化的兼容约束：

```text
v1.4.2 只补 WBS 工作分类和结构/执行语义，不新增平行报表体系
结构行汇总进度、执行行计数、完成率、延期率、里程碑兑现等对外指标必须来自后端统一服务
新增指标必须进入 metricRegistry
需要趋势的指标必须进入 project_daily_snapshot 或后续统一快照层
前端只做展示和交互状态，不把 rows 扫描结果作为业务统计真值
```

快照语义：

```text
tasks 表示当前执行事实和当前 WBS 树
task_baseline_items 表示已确认基线快照，确认后不随源 tasks 自动漂移
monthly_plan_items 表示月度承诺快照，确认和关账后不随源 tasks 或 baseline 自动漂移
如果源 tasks 分类后续调整，必须通过基线修订、月计划修订或显式同步动作进入快照表
```
