## 0. 2026-06-01 final range-tree boundary (authoritative)

This v1.4-series plan follows the final range-tree model. There is no production history or existing user data that needs a compatibility layer.

Authoritative engineering object types are exactly: `phase / section / building / basement / floor / physical_zone / functional_area`.

The following compatibility surfaces are deleted and must not be reintroduced in runtime code, migrations, or frontend contracts:

- `zone / professional / subproject / custom` as engineering object types.
- `zone_object_id / professional_object_id` task fields.
- `project_materials.professional_object_id` and `engineering_categories.professional_object_id`.
- `legacy_object_type`, deprecated object-type arrays, legacy bridge/backfill helpers, and old scope adapter functions.
- `/api/scope-dimensions`, `scope_dimensions`, and `project_scope_dimensions` as active application surfaces.

Professional/system/domain/method semantics remain business facts through `specialty_type`, `engineering_category_id`, `standard_work_code`, template metadata, and project profile facts. They are not range-tree objects.

Any older section in this document that mentions deleted object types, deleted fields, old scope tables, or compatibility adapters is superseded by this boundary.
# v1.4.11 图纸证照验收与任务联动体系执行方案

## Summary

v1.4.11 的目标是把当前应用中相对独立运行的 `施工图纸 / 前期证照 / 验收流程` 与 `任务列表 / 开工条件 / 计划治理 / 预警` 建立稳定联动口径。

本章不重做三套专项页面，也不把图纸、证照、验收合并成一个页面。三者仍然是专项事实台账：

```text
施工图纸：回答“施工或验收所需图纸是否齐备、是否通过审查、当前有效版本是什么”
前期证照：回答“开工前手续、四证、共享办理事项是否完成或卡住”
验收流程：回答“专项验收、单位工程验收、竣工备案等验收事项是否具备条件、是否通过”
任务列表：回答“现场执行任务当前是否能开工、是否推进、是否完成”
```

本章只治理它们之间的联动关系：

```text
图纸 / 证照 / 验收事实可以满足任务开工条件
图纸 / 证照 / 验收事实可以触发或解除预警
图纸 / 证照 / 验收事实可以作为新一轮基线 / 月计划生成时的参考约束
验收页面创建的是验收任务，任务列表中的任务是普通施工任务
验收任务与普通施工任务之间是“验收覆盖关系”，不是互相改进度关系
任务详情不新增验收摘要，避免任务弹窗继续变重
```

继续沿用 v1.4.8 之后的统一原则：

```text
用户维护业务事实，系统判断治理语义
能由系统自动识别、匹配、归集和提示的，不新增弹窗或必填项打断现场录入
普通前端不展示 source、lineage、confidence、mapping_reason 等治理字段
```

## Business Definitions

### 1. 专项事实

专项事实是图纸、证照、验收各自页面维护的真实业务状态。

```text
图纸事实：图纸包、图纸版本、审查状态、有效版、是否可施工、是否可验收
证照事实：证照实例、办理事项、办理状态、实际完成日期、阻塞原因
验收事实：验收计划、验收要求、验收记录、实际验收日期、通过 / 整改 / 归档状态
```

专项事实不等于任务进度。

```text
图纸通过不代表施工任务完成
证照办结不代表现场任务完成
验收通过不代表被验收的施工任务刚刚完成
这些事实主要用于满足条件、触发预警、支撑计划判断和沉淀历史
```

### 2. 联动关系

联动关系回答：

```text
某个图纸、证照或验收事实，到底影响哪条任务、哪条开工条件、哪条验收要求？
这个影响是强约束、参考信息，还是完成证据？
系统能否在事实变化时自动更新条件、预警和计划提示？
```

联动关系分三类：

```text
强联动：事实达成后可自动满足条件或验收要求
弱联动：事实变化只形成提示、预警或计划生成建议
兼容联动：来自旧字段的历史关系，仅用于展示和迁移，不作为新规则权威来源
```

### 3. 任务边界

任务列表仍是实时执行事实。

```text
任务能否开工：由任务依赖、开工条件、图纸、证照、材料、现场准备等共同判断
任务是否完成：由任务自身状态 / 进度自动派生实际完成，不由图纸或证照直接决定
验收任务：在验收页面创建、维护和完成，不进入普通任务列表进度体系
普通施工任务：在任务列表维护进度和实际完成，不由验收通过反向改写
验收覆盖关系：说明某个验收任务覆盖了哪些普通施工任务，供追溯、预警、计划生成和条件判断使用
```

## Core Design

### 1. 保持三页独立

```text
前期证照、施工图纸、验收流程继续作为专项管理下的三个独立页面
不新增“联动管理中心”
不把三页合并成一个大台账
任务详情不新增验收摘要
任务弹窗不承载图纸、证照、验收完整信息
```

前端变化以现有入口内部增强为主：

```text
开工条件中可关联图纸包、证照办理事项或验收要求
图纸详情可显示被哪些任务条件 / 验收要求引用
证照详情可显示影响哪些开工条件或预警
验收详情可显示关联任务和要求，但不反向塞进任务详情
```

### 2. 建立统一联动关系表

新增一张轻量关系表作为后端联动底座，不要求普通用户直接维护。

```sql
create table if not exists project_entity_links (
  id uuid primary key default gen_random_uuid(),
  project_id uuid not null references projects(id) on delete cascade,
  source_entity_type text not null,

  updated_at timestamptz not null default now()
);

alter table project_entity_links
  add constraint project_entity_links_source_type_check

  add constraint project_entity_links_target_type_check

    'task',

    'certificate_work_item'

  add constraint project_entity_links_relation_type_check
  check (relation_type in (
    'satisfies_condition',
    'satisfies_acceptance_requirement',
    'covers_task',
    'references_certificate',
    'blocks_task_start'
  ));

  add constraint project_entity_links_relation_strength_check

create unique index if not exists idx_project_entity_links_unique_active

  where status = 'active';

create index if not exists idx_project_entity_links_source
  on project_entity_links(project_id, source_entity_type, source_entity_id, status);

create index if not exists idx_project_entity_links_target

```

迁移实现要求：

```text
上方 SQL 是结构口径，实际迁移必须幂等。
ADD CONSTRAINT 必须使用 DO $$ 检查 pg_constraint 后再添加，或先 DROP CONSTRAINT IF EXISTS 再添加。
RLS policy、trigger、index、projection column 和全量迁移快照必须与增量迁移同步，避免新环境初始化和增量升级不一致。
```

字段枚举：

```text
source_entity_type:
  drawing_package
  construction_drawing
  pre_milestone
  certificate_work_item
  acceptance_plan

target_entity_type:
  task
  task_condition
  acceptance_requirement
  pre_milestone
  certificate_work_item

relation_type:
  satisfies_condition
  satisfies_acceptance_requirement
  covers_task
  references_certificate
  blocks_task_start

relation_strength:
  explicit
  system_inferred
  legacy_mapped

status:
  active
  inactive
```

联动强弱与字段含义：

```text
relation_type 表示业务影响类型：
  satisfies_condition / satisfies_acceptance_requirement 属于强联动，满足事实达成后可触发自动满足
  covers_task / references_certificate / blocks_task_start 属于弱联动或引用关系，只形成提示、追溯、预警和计划判断

relation_strength 表示关系来源，不表示业务强弱：
  explicit：用户明确选择或系统依据明确外键写入
  legacy_mapped：旧字段一次性精确回填
  system_inferred：系统按名称、专业、楼栋、阶段等推断，仅作建议

自动满足条件 / 验收要求只允许 relation_strength = explicit 或 legacy_mapped 且 source_ref_field 来自明确字段时触发。
system_inferred 永远不能自动满足条件、不能自动通过验收要求、不能自动修改任务；只能进入数据质量、健康横幅或计划生成建议。
```

关系类型兼容矩阵：

```text
drawing_package -> task_condition / satisfies_condition：允许自动满足图纸类开工条件
drawing_package -> acceptance_requirement / satisfies_acceptance_requirement：允许自动满足图纸类验收要求
pre_milestone -> task_condition / satisfies_condition：允许自动满足证照类 / 手续类开工条件
certificate_work_item -> task_condition / satisfies_condition：允许自动满足证照类 / 手续类开工条件
acceptance_plan -> task_condition / satisfies_condition：允许自动满足后续任务的验收类开工条件
acceptance_plan -> task / covers_task：只表达验收覆盖关系，不改普通施工任务
construction_drawing -> pre_milestone / references_certificate：只表达图纸与证照引用关系，不改任务
construction_drawing -> certificate_work_item / references_certificate：只表达图纸与证照办理事项引用关系，不改任务
pre_milestone -> task / blocks_task_start：只作为计划治理和健康硬阻断来源，不直接改任务状态
certificate_work_item -> task / blocks_task_start：只作为计划治理和健康硬阻断来源，不直接改任务状态
```

不在兼容矩阵内的 source / target / relation_type 组合，后端必须拒绝写入；数据库兜底必须用 trigger 校验组合，不只依赖单字段 CHECK。

说明：

```text
project_entity_links 是业务联动关系，不替代 v1.4.6 的数据来源与映射关系
v1.4.6 解决“数据从哪里生成、如何沿链路传递”
v1.4.11 解决“图纸 / 证照 / 验收事实影响哪条任务、条件或验收要求”
source_entity_id / target_entity_id 使用 text，是为了兼容现有 source_entity_id、drawing_package_code、related_license_id、milestone_id 等旧链路；能确定为 UUID 的关系仍按 UUID 字符串写入
新写入关系能确定实体 UUID 时必须写 UUID 字符串；旧文本编码只允许 relation_strength = legacy_mapped / system_inferred，并不得作为新联动权威来源
预警不通过 project_entity_links 建立 warning_source 关系，预警继续使用 warnings / notifications 自身的 source_entity_type、source_entity_id 和 task_id 表达来源与影响任务
project_entity_links 必须启用 RLS，读写权限按 project_members 判断；写入时后端必须校验 source / target 均属于同一 project_id
project_entity_links 必须有 updated_at 触发器，并同步写入全量迁移快照
手工新增、修改、停用联动关系，以及系统自动满足条件 / 验收要求，必须写审计日志；审计日志不展示给普通前端，只供后台追溯和异常排查
```

## Execution Steps

v1.4.11 必须按以下阶段执行，避免先改前端却仍由旧字段触发业务动作，或先停旧逻辑导致专项页面不可用。

```text
阶段 0：前置检查
确认 v1.4.1-v1.4.10 已落库，确认 task_conditions.drawing_package_id、acceptance_requirements.drawing_package_id、acceptance_plans.task_id、pre_milestones、certificate_work_items、acceptance_dependencies 等旧关系来源存在。
扫描 acceptance_plans.task_id / milestone_id、task_conditions.drawing_package_id / drawing_package_code、acceptance_requirements.drawing_package_id / source_entity_id、construction_drawings.related_license_id 的历史使用情况。
定位当前会反写普通任务的代码路径，尤其是 acceptance-plans.ts 中验收通过调用 updateTaskInMainChain 的逻辑。

阶段 1：数据库迁移
创建 project_entity_links、CHECK 约束、唯一索引、source / target 索引、RLS、updated_at 触发器和全量迁移快照。
用幂等方式添加所有约束，补关系类型兼容 trigger 或等价后端硬校验。
补 task_conditions.source_entity_type / source_entity_id 等投影字段。
补 task_conditions.requires_review / review_reason / review_source_entity_type / review_source_entity_id / review_requested_at。
补 acceptance_requirements.requires_review / review_reason / review_source_entity_type / review_source_entity_id / review_requested_at。
不新增 task_conditions.status = need_review，也不新增 acceptance_requirements.status = need_review，避免打破现有状态枚举。

阶段 2：旧关系回填
按明确字段一次性回填 project_entity_links，relation_strength = legacy_mapped，并写 source_ref_field。

名称相似、专业相似、阶段相似只生成 system_inferred 建议，不自动满足条件。

阶段 3：后端联动服务

图纸、证照、验收、开工条件、计划治理和健康服务都通过该服务读取联动关系。

阶段 4：停止验收反写普通任务
移除或禁用 acceptance-plans.ts 中验收 passed / archived 后调用 updateTaskInMainChain 完成普通施工任务的路径。
验收通过只更新验收域状态和验收实际日期；covers_task 只作为覆盖关系。

阶段 5：自动满足规则接入
图纸通过、证照办结、验收通过只在 active 强联动关系且 relation_strength 符合自动执行门槛时满足对应 task_condition 或 acceptance_requirement。
事实撤回、作废、归档时不直接回滚人工确认结果，进入复核 / 健康提示。

阶段 6：API / DTO 接入
GET / API 返回 relation bundle：linkedTasks、linkedTaskConditions、linkedAcceptanceRequirements、linkedWarnings 等只读聚合。
旧字段继续返回兼容值，但前端新增联动必须写 project_entity_links。

阶段 7：前端接入
开工条件弹窗按条件类型选择图纸包、证照 / 办理事项、验收计划。
图纸、证照、验收详情页显示关联影响；任务列表 / 甘特行只展示轻量“影响验收”标记；任务详情不新增验收摘要。

阶段 8：预警 / 计划治理接入
warningService、projectHealthService、planningIntegrityService、月计划 / 基线生成服务读取联动结果，输出硬阻断、健康横幅或计划生成建议。

阶段 9：测试验收
覆盖迁移、旧字段回填、自动满足、撤回复核、验收不反写任务、删除保护、前端轻量展示、计划生成和无历史数据场景。
```

## Linkage Rules

### 0. 自动执行统一门槛

图纸、证照、验收事实只能在满足以下全部条件时自动改写目标条件或验收要求：

```text
project_entity_links.status = active
relation_type = satisfies_condition 或 satisfies_acceptance_requirement
relation_strength = explicit，或 relation_strength = legacy_mapped 且 source_ref_field 来自明确外键 / 明确旧字段
source / target 均属于同一 project_id
source 专项事实达到对应通过 / 办结 / 可施工状态
target 当前未被人工锁定、未删除、未归档
```

以下情况不得自动满足，只能生成数据质量、健康横幅或计划生成建议：

```text
relation_strength = system_inferred
仅名称相似、专业相似、楼栋相似、阶段相似
source_entity_id / target_entity_id 只能靠旧文本编码模糊识别
source / target 项目不一致
目标条件已被人工确认或人工驳回
```

事实撤回 / 作废 / 归档后的统一规则：

```text
如果目标条件 / 验收要求是系统自动满足，且没有人工确认覆盖，则设置 requires_review = true，并写 review_reason、review_source_entity_type、review_source_entity_id、review_requested_at，同时写健康问题，提示重新复核。
不得写 status = need_review；task_conditions 和 acceptance_requirements 的原 status 枚举保持不变。
不直接把已满足条件改回未满足，避免破坏现场已确认事实。
如果目标条件 / 验收要求已人工确认，则只记录专项事实撤回提示，不改人工确认结果。
如果专项对象只是撤回、驳回、过期或作废但仍需影响当前判断，project_entity_links 保持 active，并由 source 状态进入复核 / 健康问题。
如果专项对象归档、删除或明确退出使用，project_entity_links 必须置 inactive，并保留 display_snapshot；已发布基线、月计划和历史预警不回写。
```

### 1. 图纸 -> 开工条件

图纸包满足下列条件时，可自动满足关联的图纸类开工条件：

```text
图纸包存在 active 关系：
  drawing_package -> task_condition
  relation_type = satisfies_condition

且图纸包达到可施工事实：
  review_status = approved / passed
  或 is_ready_for_construction = true
  或当前有效版 actual_pass_date 已存在
```

状态优先级：

```text
优先 review_status = approved / passed
其次 is_ready_for_construction = true
最后 current_version.actual_pass_date / actual_pass_date 已存在
如果上述字段冲突，以明确驳回 / 作废 / 已撤回状态优先，不自动满足条件
```

系统动作：

```text
自动把 task_conditions.is_satisfied 置为 true
satisfied_reason = linked_drawing_approved
confirmed_at 取图纸实际通过日期或系统处理时间
不改任务 progress
不改任务 status
不改任务 actual_start_date / actual_end_date
```

低置信度情况：

```text
如果只是专业、楼栋、名称相似，系统只能写后台低置信度建议，并在健康提示或计划生成提示中以业务语言提醒
低置信度不自动满足条件
普通前端不展示 confidence 字段
```

### 2. 图纸 -> 验收要求

图纸包通过后，可自动满足关联验收要求：

```text
drawing_package -> acceptance_requirement
relation_type = satisfies_acceptance_requirement
```

系统动作：

```text
acceptance_requirements.is_satisfied = true
acceptance_requirements.status = met
不直接变更 acceptance_plan.status
当全部必需 requirements 满足时，系统只生成 ready_to_submit 建议，不直接写 acceptance_plan.status
正式提交、流转和通过仍由验收状态机控制
```

### 3. 证照 -> 开工条件

前期证照或证照办理事项完成后，可自动满足关联开工条件：

```text
pre_milestone / certificate_work_item -> task_condition
relation_type = satisfies_condition

且状态达到：
  approved
  issued
  completed
  或 actual_finish_date / completed_date 已存在
```

状态优先级：

```text
优先 approved / issued / completed
其次 actual_finish_date / completed_date 已存在
如果证照状态为 revoked / voided / rejected / expired，不自动满足条件，即使存在历史完成日期
```

系统动作：

```text
自动满足对应手续类 / 证照类开工条件
satisfied_reason = linked_certificate_ready
不改任务进度
不改普通施工任务状态
```

### 4. 验收任务 -> 普通施工任务

```text
acceptance_plan -> task
relation_type = covers_task
```

验收页面创建和维护的 `acceptance_plan` 就是验收任务。

任务列表中的 `task` 是普通施工任务。

`covers_task` 表示“该验收任务覆盖哪些普通施工任务”，也可以反向理解为“该普通施工任务被哪些验收任务覆盖”。

系统动作：

```text
验收通过不自动完成普通施工任务
普通施工任务完成也不自动通过验收任务
不改普通施工任务 progress
不改普通施工任务 status
不改普通施工任务 actual_end_date
只作为验收台账、预警、计划生成、复盘分析和任务列表轻量提示的关联事实
```

### 5. 验收 -> 开工条件

某些后续任务可以依赖前置验收通过。

```text
acceptance_plan -> task_condition
relation_type = satisfies_condition
```

系统动作：

```text
验收通过后，自动满足对应开工条件
归档只有在存在已通过验收记录或上一状态为 passed 时，才可视为满足对应开工条件
不直接修改后续任务状态
```

验收状态优先级：

```text
passed 可满足验收类开工条件
archived 只有在保留 passed 证据时可满足验收类开工条件；单纯归档不满足条件
rectifying / inspecting / submitted / ready_to_submit 只生成提示，不满足条件
revoked / voided / rejected 或重新进入整改时，不自动回滚已满足条件，进入复核提示
```

### 6. 计划生成时的联动消费

按 v1.4.7 口径：

```text
任务列表是实时执行事实
项目基线和月度计划是发布时点快照
已发布基线 / 月计划不因图纸、证照、验收变化自动改写
```

生成新一轮基线 / 月计划时，系统读取当前专项事实并提示：

```text
目标任务所需图纸未通过
目标任务所需证照未办结
目标任务前置验收未通过
普通施工任务已完成但覆盖它的验收任务仍未通过
验收任务已通过但其覆盖的普通施工任务仍存在未完成项
图纸 / 证照 / 验收事实与上轮计划假设不一致
```

用户不需要逐条处理这些提示。

```text
非法或硬阻断项进入健康横幅 / 计划生成校验
普通差异作为生成建议，由用户决定是否纳入新一轮计划
```

## Assumptions

当前没有历史生产数据，因此旧关系迁移只做精确字段映射，不做复杂人工清洗。

图纸、证照、验收是专项事实台账，不是任务进度本身。

任务列表仍是实时执行事实，基线和月计划仍是发布时点快照。

任务详情不展示验收摘要，任务列表 / 甘特行只显示只读影响验收名称，验收详情展示覆盖的普通施工任务。

前端以现有页面内部增强为主，不新增一个孤立的联动管理入口。

低置信度推断只做后台建议或计划生成提示，不自动满足条件、不自动完成任务。
