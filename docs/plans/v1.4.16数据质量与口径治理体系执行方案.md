## 0. 2026-06-01 final range-tree boundary (authoritative)

This v1.4-series plan follows the final range-tree model. There is no production history or existing user data that needs a compatibility layer.

Authoritative engineering object types are exactly: `phase / section / building / basement / floor / physical_zone / functional_area`.

The following compatibility surfaces are deleted and must not be reintroduced in runtime code, migrations, or frontend contracts:

- `zone / professional / subproject / custom` as engineering object types.
- `zone_object_id / professional_object_id` task fields.
- `project_materials.professional_object_id` and `engineering_categories.professional_object_id`.
- `legacy_object_type`, deprecated object-type arrays, legacy bridge/backfill helpers, and old scope adapter functions.
- `/api/scope-dimensions`, `scope_dimensions`, and `project_scope_dimensions` as active application surfaces.

Professional/system/domain/method semantics remain business facts through `specialty_type`, `engineering_category_id`, `standard_work_code`, template metadata, and project profile facts. They are not range-tree objects.

Any older section in this document that mentions deleted object types, deleted fields, old scope tables, or compatibility adapters is superseded by this boundary.
# v1.4.16 数据质量与口径治理体系执行方案

## 1. 目标

v1.4.16 的目标是把当前应用中分散在 `任务进度 / 项目基线 / 月度计划 / 任务列表 / 风险问题 / 预警通知 / 图纸证照验收 / 材料 / 责任主体 / 工程对象 / WBS / 来源映射 / 删除保留 / Dashboard / Reports / 健康度` 里的数据质量、数据可靠性和统计口径治理统一收口。

本章解决的是系统能否稳定回答这些问题：

```text
当前数据能不能作为 Dashboard、Reports、健康度、AI 分析和新一轮计划生成的依据
哪些问题属于数据质量问题，哪些问题属于业务风险、业务问题或业务预警
同一个质量问题在任务列表、报表、风险页、关账页和提醒中心如何保持一致
数据质量低时是阻断业务动作、弱提示、降低可信度，还是只做后台记录
旧字段、旧异常、旧任务、旧快照、旧质量发现如何保留和自动消解
前端是否需要新增复杂质量维护入口，还是沿用现有健康横幅、数据可靠性、即时校验和提醒中心
```

本章延续 v1.4.8 之后形成的统一原则：

```text
用户维护业务事实，系统判断治理语义
所有页面以业务数据展示和业务动作处理为主，数据质量只做护栏和轻提示，不成为第二套用户工作流
能自动识别、自动降级、自动消解的数据质量问题，不要求用户手动关闭
数据质量问题不等于业务风险问题，不直接进入“严重阻断”口径
低可信度是分析可信度状态，不是任务执行状态
前端只展示用户需要关注的少量提示，不暴露 rule_code、finding_key、dimension_key、confidence formula 等技术字段
统计指标必须从后端统一口径输出，前端不得重新发明主口径
```

## 4. 当前差异与必须收口项

### 4.1 质量范围仍偏任务进度

当前扫描规则主要围绕任务进度、父子关系、依赖关系、开工条件和责任人负荷。v1.4 系列执行后，质量治理必须扩展到主数据、WBS、状态、来源、验收、风险预警、删除保留等对象。

必须补齐：

```text
工程对象归属质量：任务缺 engineering_object_id，或对象已停用但仍被新任务使用
范围树质量：phase / section / building / basement / floor / physical_zone / functional_area 归属缺失或不匹配；professional 只作为业务专业事实，不作为范围树对象类型
WBS 分类质量：任务行无法归到工程分类、分类层级异常、工序行和结构行语义冲突
任务标准模型质量：标准字段缺失、兼容字段与 object_id 不一致、进度规则与状态不一致
任务编码质量：缺对象/分类导致无法生成编码、编码历史与当前对象快照冲突
状态字典质量：旧状态无法归一、非法状态流转、状态与进度矛盾
来源映射质量：模板到基线、基线到月计划、月计划到任务、导入到任务、完成项目沉淀之间缺映射或重复映射
计划治理质量：基线/月计划/任务列表三者的历史快照和当前事实差异，只做提示和算法输入，不要求用户日常逐条修复
责任主体质量：责任单位缺主数据、责任人自由文本无法匹配项目成员、历史责任单位已归档但新任务仍引用
图纸证照验收质量：任务影响验收但缺关联、验收任务引用普通任务不完整、图纸/证照依赖失效
材料质量：材料到场计划缺失、实际到场与任务开工条件不一致、材料责任单位缺主数据、材料专业对象缺失、AI 工期估算置信度低
风险问题预警质量：来源对象失效、建议关闭未消解、预警链缺来源、同一业务事实重复生成多个预警
删除保留质量：对象被删除后下游链路未写入来源失效解释，或物理删除导致历史解释断裂
```

### 4.2 数据质量与业务异常需要分离

统一口径：

```text
数据质量问题回答“这条数据能不能支撑业务运转或分析”
业务风险回答“未来可能影响项目目标”
业务问题回答“已经发生且需要处理的业务事项”
业务预警回答“需要关注的业务信号”
阻碍回答“任务执行受到什么影响”
健康度回答“项目整体状态”
```

数据质量问题必须拆成两类，不得混用展示和处置方式：

```text
业务运转型数据问题：数据缺失、冲突、引用错误或状态非法，导致当前业务动作不能正常保存、生效、发布、确认、关账或生成
分析可信度问题：业务还能正常开展，但数据可靠性偏低，导致 Dashboard、Reports、健康度、AI 分析、新一轮计划算法的结论置信度降低
```

因此：

```text
异常跳变、批量 100%、连续未更新、字段缺失、映射缺失、旧状态无法归一，不进入风险/问题类型
关键路径任务因数据异常导致分析不可靠，可以触发提醒，但提醒类别仍是 data_quality
低可信度不等于严重阻断，不直接算作业务严重风险
数据质量可以影响健康度封顶、报表提示、AI 输出置信度和计划生成建议
业务运转型数据问题只在录入、保存、发布、确认、关账、生成等业务现场提示；分析可信度问题不进入录入现场阻断，只影响分析页和算法的可信度
```

### 4.3 旧对象处理不足

当前 `data_quality_findings.task_id` 仍是 `ON DELETE CASCADE`。v1.4.15 执行后，任务和关键对象原则上不会被简单物理删除，但仍要补齐历史兼容规则：

```text
质量发现已经进入快照、通知、报表或关账记录后，不应因源任务删除而丢失解释
旧 task_id 为空或任务已关闭/取消/归档时，质量发现应自动转为 status = resolved，并按原因写 resolved_type，而不是持续 active
旧 rule_code、旧 rule_type、旧 severity 不删除，统一通过别名和归一层解释
旧 data_confidence_snapshots 不重算历史分数，除非走 v1.4.14 的高权限历史事实纠错
旧 monthly_plans.data_confidence_* 继续作为当时关账可信度快照，不随当前任务列表变化反写
```

## 5. 标准数据质量对象

### 5.1 质量发现

```sql
resolved_at timestamptz null

```

`rule_type` 不再只固定为 `trend / anomaly / cross_check`，需要扩展为：


`quality_dimension` 固定为：

```text

schedule
wbs
engineering_object
scope
responsibility
status
lineage
dependency
condition
obstacle
milestone
acceptance
drawing

risk_issue_warning
```

字段边界：

```text
dimension_key 继续保留为当前代码里的定位 / 去重辅助键，例如 task:xxx、assignee:xxx，不作为治理分类字段。
quality_dimension 是治理和统计分类字段，只能取上面固定枚举，Dashboard、Reports、健康度和提醒触达按它归类。
旧字段无法映射时不得新增 quality_dimension = legacy_unmapped；应写 rule_code = LEGACY_UNMAPPED，rule_type = mapping，quality_dimension = lineage 或 metric_caliber，并把旧字段名、旧值、无法映射原因放入 details_json。
status 仍只使用 active / resolved / ignored；source_deleted、resolved_source、auto_resolved 等写入 resolved_type，不新增 status = source_deleted。
```

### 5.2 数据可信度快照

可信度快照回答“当前周期的数据能不能支撑分析”。

标准口径：

```text
快照按 project_id + period_month 生成
月计划关账时写入当月可信度，不随当前任务列表反写
Dashboard 和 Reports 默认使用当前月实时 summary
历史对比、月计划关账、周报、复盘使用当时 data_confidence_snapshots
```

可信度分项建议从当前 5 项扩展为 9 项，但前端仍可只展示重点降分项：

```text
timeliness：填报及时性
anomaly：异常检测命中率
coverage：更新覆盖率
consistency：交叉一致性
jumpiness：进度跳变率
masterData：主数据完整性
lineage：来源映射完整性
lifecycle：状态生命周期一致性
caliber：指标口径可用性
```

说明：

```text
当前代码已有 5 项继续兼容
新增 4 项先进入 details_json 和 dimensions，不强制一次性改所有前端
前端 DataQualityWeightKey 暂时保持现有 timeliness / anomaly / consistency / jumpiness / coverage 五项兼容；后端可在 dimensions 中返回 masterData / lineage / lifecycle / caliber 等扩展维度，旧组件忽略未知维度，新组件按 label 展示
权重仍由 project_data_quality_settings 管理，但普通用户不需要频繁配置
```

### 5.3 指标口径问题

指标口径问题不是本章的完整指标体系，完整指标定义放在下一章 `统计指标口径体系`。本章只负责发现和标记“指标不可用或低可信”的原因。

例如：

```text
任务无计划开始/完成，导致应达进度不可计算
缺少历史快照，导致周环比不可计算
责任单位缺主数据，导致责任贡献分析不可计算
任务缺工程对象，导致分楼栋/分区域统计不可计算
月计划未确认，导致兑现率不可计算
基线不存在，导致基线偏差不可计算
```

前端展示口径：

```text
指标不可用显示“暂无”或“数据待完善”
不允许前端用 0、100%、空数组兜底伪造成健康数据
不可用原因由后端返回，不由前端猜
```

## 6. 统一规则

### 6.1 阻断、提示、后台记录

数据质量问题先按业务影响分两层，再决定处置方式：

```text
业务运转型：影响保存、生效、发布、确认、关账、生成等业务动作，必须在业务现场提示、定位或阻断
分析可信度型：不影响业务动作，只影响分析结论、统计指标、健康度、AI 和计划算法可信度，默认后台记录和自动消解
```

具体处置分三类：

```text
阻断：会导致保存后产生非法业务事实，例如任务无任何归属、责任单位自由输入、非法状态流转、对象引用不存在
轻确认：用户正在保存的动作可能合理但需要确认，例如进度首次从 0% -> >0% 且存在人员/设备/现场准备/一般协调类软条件未满足
后台记录：不会阻断业务动作，但会影响分析可信度，例如连续未更新、跳变、映射缺失、历史快照差异
```

默认原则：

```text
能自动判断并后台记录的，不打断用户
能自动满足或自动消解的，不要求用户手动关闭
需要业务事实成立的，才阻断或轻确认
数据质量问题不直接把任务状态改为阻碍、延期、严重风险
业务运转型问题必须提供定位到字段、行、chip 或抽屉分段的能力；分析可信度型问题不得要求用户逐条关闭
```

### 6.1.1 共享计划树校核展示规则

项目基线、月度计划、任务列表按照 v1.4.7.1 的共享计划树口径统一处理数据校核，不再各自实现一套提示方式。

编辑态轻量校核：

```text
发生在用户编辑过程中
只处理会影响保存的轻量规则，例如必填缺失、非法日期、对象不存在、责任单位自由输入、状态非法、依赖成环
共享计划树必须具备定位高亮能力
顶部或底部校核条只做汇总和定位入口
字段、行、chip 或抽屉分段负责现场高亮和解释
不写业务事实，不生成持久质量发现
```

保存前校核：

```text
发生在用户点击保存时，仍属于编辑态
由后端校核编辑缓冲能否提交为正式业务事实
无问题：保存成功，回到阅读态
阻断问题：停留编辑态，显示保存前校核条，并高亮相关行和字段
轻确认问题：弹出最小确认框，继续保存或取消本次保存
```

阻断问题展示方式：

```text
同类问题合并展示，例如“责任单位缺失 5 处”
用户点击同一个问题项时，系统依次定位到第 1 处、第 2 处、第 3 处
定位时对应行和字段高亮
可提供上一处 / 下一处，但不新增复杂问题处理列表
阻断项修正前不允许保存
```

发布/确认前校核：

```text
发生在项目基线发布、月度计划确认前，属于阅读态业务动作
不重复普通录入问题；普通必填、日期、对象引用等问题必须在编辑态轻校核或保存前校核中解决
只校核是否还有未保存编辑、当前数据是否可以形成历史快照、本次发布/确认会形成什么承诺变化
以轻确认弹窗展示，不进入复杂数据质量处理流程
```

发布/确认前轻确认内容：

```text
项目基线发布：新增项、日期调整、删除项、关键路径变化、最后保存时间、与上一版基线的主要差异
月度计划确认：计划任务数、目标进度调整、滚入任务、新增现场任务、与当前任务列表的日期差异、最后保存时间
```

发布/确认前阻断仅限快照动作专属问题：

```text
存在未保存编辑：不能发布/确认
草稿已被协作更新：请先同步后再发布/确认
当前月计划已确认：不能重复确认
没有任何可确认任务：不能确认
基线版本已失效：请重新生成草稿
生成快照失败：不能发布/确认
```

统一分工：

```text
编辑态轻量校核解决“这格/这行现在填得对不对”
保存前校核解决“这次保存能不能成为业务事实”
发布/确认前校核解决“这份已保存数据能不能成为历史承诺”
```

### 6.2 自动消解规则

质量发现不要求用户逐条关闭。系统每次扫描时自动判断：

```text
规则再次命中：保持 active，更新 summary / severity / details_json
规则不再命中：自动变为 resolved，写 resolved_at 和 resolved_type = auto_resolved
源对象被关闭/取消/归档/停用：如果问题随之失效，status = resolved，并按原因写 resolved_type = source_closed / source_cancelled / source_archived / source_inactive
源对象已按 v1.4.15 被判定为来源删除：status = resolved，resolved_type = source_deleted 或 resolved_source，不新增 status = source_deleted
源对象物理删除仅限误录：质量发现可物理删除或写 operation_logs 摘要；已进入链路的质量发现必须保留
用户忽略：仅限非关键、非阻断质量提示，status = ignored，不影响历史快照
```

### 6.3 每天填报进度的消费

每天填报进度是当前应用最大的数据源之一，v1.4.16 必须把它作为核心事实消费。

消费范围：

```text
实际开始 / 实际完成：0 -> >0 自动实际开始，100 且保存确认后自动实际完成
进度快照：形成每日趋势事实
计划偏差：对比计划开始/完成、应达进度
关键路径：关键任务停滞、延期、恢复
填报缺失：连续未更新生成质量发现和必要提醒
收尾停滞：长期卡在 90%-99% 形成质量提示或业务预警输入
异常跳变：大幅跳变、批量 100%，作为数据质量提示
开工条件：首次进度变化触发条件满足判断，软条件轻确认
阻碍：进度恢复后自动降级或建议关闭阻碍相关问题
验收联动：100% 后提示影响哪些验收，但不阻断任务完成
风险/问题建议关闭：来源任务完成或恢复后，进入建议关闭
周报/驾驶舱/健康度：作为趋势、偏差、执行活跃度核心事实
新一轮基线/月计划生成：作为算法参考，不反写历史快照
```

其中已实现和待补强要明确区分：

```text
已实现：实际开始/完成自动补齐、进度快照、数据质量扫描、连续未更新、跳变、批量相同进度、趋势滞后、健康度数据可信度消费、月计划关账可信度写入
部分实现：开工条件交叉校验、阻碍建议关闭、关键路径数据异常提醒、验收联动后的任务完成写入
待补强：软条件轻确认、收尾停滞专项规则、验收影响名称展示、风险/问题建议关闭与数据质量消解联动、新一轮计划算法对进度快照的权重化消费
```

### 6.4 新增数据接入准入规则

后续任何新增数据对象、业务页面、导入字段或系统生成记录，都必须先进入数据质量与口径治理体系，再进入 Dashboard、Reports、健康度、AI 分析、提醒触达和新一轮计划算法。

该准入规则由后端自动判定，前端不新增复杂选择、弹窗或人工维护入口。

统一判定项：

```text
项目归属：数据必须能归属到 project_id；无法归属时不得进入项目级统计
业务对象：数据必须有稳定 entity_type / entity_id，不能只靠页面文本解释
工程归属：能关联工程对象、范围维度、WBS、任务的，后端自动关联；无法自动关联时进入数据待完善，不要求用户手工选择治理语义
责任归属：涉及责任的，优先绑定责任单位主数据和项目成员；责任单位不得自由输入
状态归属：所有状态必须进入 v1.4.5 状态字典；未知状态由后端归一或标记为状态待校准
来源归属：必须记录来源是手工、模板、导入、基线生成、月计划滚入、任务联动、系统扫描还是外部接口
生命周期：删除、关闭、作废、归档、停用等动作统一交由 v1.4.15 判断历史保留方式
变更留痕：保存、批量、删除、归档、系统联动等关键动作统一交由 v1.4.14 写业务摘要
质量规则：后端判断该数据是否需要阻断、轻确认、弱提示、后台记录或自动消解
指标边界：后端判断该数据是否能进入统计指标；不满足口径时指标显示数据待完善，不用 0 或 100% 兜底
触达边界：只有需要用户关注的数据质量摘要进入提醒触达，其余只后台记录
```

接入原则：

```text
用户只新增或维护业务事实
系统自行判断这条数据是否完整、可信、可统计、可追溯、可消解
前端不暴露 rule_code、finding_key、quality_dimension、source_type 等治理字段
新增模块不得绕过 dataQualityService、change_logs、status_dictionary、lineage_mapping、retention governance
新增数据没有完成准入判定前，不得直接参与驾驶舱核心指标、AI 结论和计划生成算法
```

典型新增模块接入方式：

```text
设备管理：设备到场、可用、故障、退场等事实由后端判断是否影响开工条件、阻碍和资源风险
劳动力管理：人员投入、缺勤、班组变更等事实由后端判断是否影响责任主体、进度可信度和风险预警
质量整改：整改项由后端判断是否关联验收、问题、任务完成和关闭建议
安全检查：安全隐患由后端判断是否进入业务风险/问题，还是仅作为质量或合规记录
合同成本：合同、签证、变更、付款等事实由后端判断是否进入成本指标，暂不反向影响进度事实
外部导入：导入批次先形成来源映射和质量发现，低可信数据不得直接覆盖权威字段
```

前端表现：

```text
用户看到的是原业务页面的保存、删除、关闭、作废、归档、导入、批量编辑等常规动作
系统只在必要时提示“数据待完善”“可能影响分析准确性”“保存后将影响若干统计”
不要求用户选择该数据属于哪个治理体系
不要求用户手动关闭每条质量发现
```

## 2026-05-21 progress_quality 与进度数据质量同步口径

`progress_quality` 是数据可信度因子，不是业务延期原因。它只能降低预测置信度、剔除速度学习样本或提示数据可靠性，不得直接加天、不得生成风险 / 问题 / 严重阻断。

### 规则口径

```text
1. 进度跳变、月末集中补录、收尾进度卡停继续由 progressAnomalyService 统一识别。
2. 进度长期未更新纳入 progress_quality；已有快照超过阈值未更新时，降低预测可信度。
3. 置信度扣分按 severity 分级：info 轻扣、warning 中扣、critical 重扣；不再所有异常固定扣分。
4. data_quality_findings 已 resolved / ignored 的异常，不再反复惩罚 progress_quality。
5. 已确认 / 已复核的异常保留可追溯性，但降低置信度惩罚。
6. 90%-99% 收尾停滞如果有验收、整改、资料移交等业务事实支撑，应主要进入业务收尾 / external_readiness / progress_velocity 解释，只对 progress_quality 做轻度降置信度。
```

### 展示口径

```text
前端不新增数据质量中心。
任务列表 / 共享计划树只在录入和保存场景做轻提示。
Dashboard 只保留数据可靠性入口，不把 progress_quality 展示成业务风险。
风险 / 问题 / 预警页面不展示 progress_quality 为业务异常。
```

### 2026-05-21 progress_quality 规则扩展与自动消解口径

新增 3 类进度质量规则，全部属于“数据可靠性低”，不属于业务风险：

`PROGRESS_SOURCE_LOW_CONFIDENCE`：进度主要来自批量导入、迁移、系统同步或未知来源。
`PROGRESS_ROLLBACK`：进度从较高值回退到较低值，说明可能发生修正。
`PROGRESS_DUPLICATE_FILL`：多个快照连续填同一个进度值，趋势学习可信度降低。

这些规则和既有 `SNAPSHOT_GAP / PROGRESS_JUMP / PROGRESS_MONTH_END_BURST / PROGRESS_STUCK_FINISHING` 一起进入 progress_quality。前端仍只在既有数据可靠性入口、共享计划树轻校核和保存 / 发布 / 确认校核中用业务化语言提示，不新增“进度质量维护页”。

自动治理规则：

```text
1. 后续出现已确认进度快照时，低来源可信度和重复填报可自动消解。
2. 已确认的进度回退作为修正事实保留，但不反复惩罚。
3. resolved / ignored 的质量发现不再进入 progress_quality 罚分。
4. 未消解的问题只降低置信度和样本权重，不生成风险、问题、阻碍或严重阻断。
```

### 2026-05-21 progress_quality 自动学习边界

`progress_quality` 具备自动识别、自动消解和自动校准能力，但它属于数据质量治理，不属于业务风险治理。

```text
1. 系统可从低可信来源、进度回退、重复填报、进度跳变、月底集中补录、快照缺口中自动识别进度质量模式。
2. 系统可根据 resolved / ignored / confirmed / system_inferred 状态自动消解或降级质量影响。
3. 系统可把 progress_quality 写入经验样本权重和 learningObservation，影响后续工期经验沉淀。
4. progress_quality 不得直接加天、不得改变任务日期、不得生成风险 / 问题 / 阻碍。
5. progress_quality 的自动升级结果只允许进入数据质量规则、样本权重和后台算法治理候选，不进入普通业务页面作为“现场问题”展示。
```

### 业务化文案

```text
progress_jump：进度填报跳变，预测可信度降低。
month_end_burst：月末集中补录，趋势判断仅作参考。
stuck_finishing：收尾进度长期未变化，需结合验收 / 整改 / 资料事实判断。
snapshot_gap：进度长时间未更新，剩余工期预测可信度降低。
```
