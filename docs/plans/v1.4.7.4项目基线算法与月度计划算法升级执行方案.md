## 0. 2026-06-01 final range-tree boundary (authoritative)

This v1.4-series plan follows the final range-tree model. There is no production history or existing user data that needs a compatibility layer.

Authoritative engineering object types are exactly: `phase / section / building / basement / floor / physical_zone / functional_area`.

The following compatibility surfaces are deleted and must not be reintroduced in runtime code, migrations, or frontend contracts:

- `zone / professional / subproject / custom` as engineering object types.
- `zone_object_id / professional_object_id` task fields.
- `project_materials.professional_object_id` and `engineering_categories.professional_object_id`.
- `legacy_object_type`, deprecated object-type arrays, legacy bridge/backfill helpers, and old scope adapter functions.
- `/api/scope-dimensions`, `scope_dimensions`, and `project_scope_dimensions` as active application surfaces.

Professional/system/domain/method semantics remain business facts through `specialty_type`, `engineering_category_id`, `standard_work_code`, template metadata, and project profile facts. They are not range-tree objects.

Any older section in this document that mentions deleted object types, deleted fields, old scope tables, or compatibility adapters is superseded by this boundary.
# v1.4.7.4 项目基线算法与月度计划算法升级执行方案

## 1. 目标

v1.4.7.4 的目标是把当前已经存在的项目基线生成算法、月度计划生成算法，升级为能充分消费 v1.4 系列底座数据的“规则化智能计划生成算法”。

本章不新建独立页面，不引入 AI 聊天入口，不要求用户理解算法模型。用户仍然只看到：

```text
项目基线：生成新版、编辑、保存发布
月度计划：生成草案、确认启用、月末确认
任务列表：保存实时排期和进度事实
```

系统在后端自动完成：

```text
判断是否需要生成新版基线
生成更合理的基线草案
生成更贴近现场的月度计划草案
给出候选差异和推荐理由
保留用户手工调整，不强行覆盖
把旧基线、旧月计划作为历史快照参与对比，不反写历史
```

本章是 v1.4.7 的算法补充章，必须遵守 `v1.4.7 / v1.4.7.1 / v1.4.7.2 / v1.4.7.3` 已确认的口径：

```text
项目基线 = 总控承诺快照
月度计划 = 阶段承诺快照
任务列表 = 实时执行事实和当前滚动排期权威
项目基线和月度计划确认后不被任务列表静默反写
新一轮项目基线 / 月度计划生成时，以任务列表为主输入，以历史快照和专项事实为算法参考
生成结果先成为草案：基线草案由用户发布，月计划草案由用户确认启用，月末由系统归类后用户做月末确认
```

## 3. 核心结论

项目基线算法和月度计划算法统一采用“多源规则评分 + 草案生成 + 用户确认”的模式。

```text
算法只生成草案和建议
算法不直接发布项目基线
算法不直接确认月度计划
算法不反写已确认历史快照
算法不把数据质量问题当业务风险问题
算法不要求用户逐项理解来源链
```

项目基线在用户侧只保留两个主操作语义：

```text
系统后台判断差距：
  当前任务列表与已发布基线出现明显差异时，系统只生成“是否建议生成新版基线”的候选判断。
  该判断不进入 Dashboard，不形成强待办，也不要求用户日常处理。

用户主动生成新版基线：
  当项目管理者准备更新总控计划时，点击“生成新版基线”。
  系统基于当前任务列表、历史基线、关键路径、里程碑、阻碍、经验工期等自动生成新版基线草案。
  用户检查、微调、发布后，新基线才成为新的历史承诺快照。
```

因此，项目基线不是实时跟着任务列表变化，而是：

```text
系统发现差距 -> 在项目基线页生成入口处轻提示 -> 用户点击生成新版基线 -> 系统生成草案 -> 用户发布后生效
```

项目基线底层仍可存在 draft / confirmed / archived 等状态，但用户侧不要设计成多个治理动作：

```text
生成草案：用户点击生成新版基线后产生，可编辑、可取消
发布基线：用户确认总控计划后发布为 confirmed
旧版归档：新版发布后由系统自动归档旧 confirmed / pending_realign 基线
```

项目基线没有月末确认或关账动作。旧版归档是系统动作，不是用户主流程。

算法输入统一来自现有应用或 v1.4 系列已经要求新增的数据：

```text
任务列表实时事实
项目基线历史快照
月度计划历史快照
工程对象
WBS / 工程分类
任务编码
状态字典
来源映射
进度快照
任务依赖
开工条件
阻碍影响
里程碑和关键节点
责任主体
图纸 / 证照 / 验收联动
材料管控联动
风险 / 问题 / 预警链
提醒通知和待办触达
变更留痕
删除关闭归档历史保留
数据质量和置信度
统计指标口径
经验工期和剩余工期预测
项目健康度和偏差分析
```

不得引入本章之外的新必填数据，例如：

```text
工程量权重
资源产能
劳动力班组排班
资金计划
详细施工日历
天气实况
复杂 CPM lag / lead 人工配置
```

这些可以作为后续增强输入，但不能作为 v1.4.7.4 的必选条件。

## 4. 项目基线算法升级

### 4.1 基线生成类型

基线生成分为三类：

```text
首次基线生成
  项目还没有 confirmed 基线
  来源固定为当前任务列表已保存事实
  标准模板生成、计划文件导入、手工新增都必须先进入任务列表编辑缓冲，保存后再作为首次基线输入
  不再从旧 WBS 模板页、空白基线页或旧默认节点直接生成第一版项目基线

新一轮基线生成
  项目已有 confirmed / pending_realign 基线
  来源以任务列表实时事实为主，历史基线作为对比对象

在建项目补建基线
  项目已经有任务和进度事实，但缺少正式基线
  来源以任务列表当前排期 + 已发生事实为主，不伪造历史基线承诺
```

### 4.2 基线输入优先级

生成基线草案时，算法输入优先级固定为：

```text
1. 当前任务列表 active 任务和结构行
2. v1.4.7.2 模板生成带来的标准分部 / 子分部 / 分项 / 工序语义
3. 当前任务列表计划开始 / 计划完成
4. 任务依赖与关键路径
5. 里程碑和系统派生关键节点
6. 经验工期建议和剩余工期预测
7. 当前进度事实、实际开始、实际完成
8. 开工条件、阻碍、风险问题预警、材料、图纸、证照、验收联动影响
9. 上一版 confirmed 基线
10. 最近 confirmed / closed 月度计划兑现情况
11. 项目健康度与偏差分析摘要
12. 数据质量与置信度
```

输入使用原则：

```text
任务列表日期是当前滚动排期权威
经验工期只辅助新建或明显缺失日期的任务，不覆盖用户已经明确维护的日期
依赖关系用于排序和校验，不要求用户选择 FS / SS / FF / SF
关键路径用于提高权重和提示影响，不单独变成用户维护项
阻碍、风险、材料、验收只影响候选理由和关注优先级，不自动推迟所有日期
数据质量低只降低推荐置信度，不生成业务风险问题
```

### 4.3 基线草案生成规则

后端新增或升级 `baselineGenerationService`，从 `task-baselines.ts` 中抽出算法逻辑，避免路由继续承担算法职责。

核心步骤：

```text
读取当前任务列表
过滤 deleted / cancelled / closed 任务
保留 WBS 结构行，但结构行不参与执行工期计算
识别可执行工序行：is_executable=true 或 wbs_node_type=process / activity_step
按 parent_id + sort_order + wbs_code 重建树
按 task_dependencies 推断前置关系；没有依赖时按同父级 sort_order 推断顺序
用 planned_start_date / planned_end_date 作为已有排期
日期缺失时调用 durationSuggestionService 取得参考工期
日期冲突时以用户已有日期为主，生成候选提示，不强行改
根据关键路径服务标记 is_baseline_critical
根据里程碑标记和关键节点派生结果标记承诺重点
为每一行写入快照字段和来源映射
生成候选差异、推荐等级和原因摘要
```

生成草案不得做：

```text
不得发布基线
不得修改上一版 confirmed 基线
不得把任务列表计划日期改成算法日期
不得删除用户已有任务
不得用经验工期覆盖用户已维护日期
不得因为阻碍存在就机械顺延所有后续任务
```

### 4.4 基线推荐评分

当前 `buildBaselineGenerationCandidate` 已有推荐依据：

```text
关键里程碑偏移超过 3 天
总完工日期偏移超过 7 天
受影响行比例超过 15%
结构变化比例超过 10%
```

v1.4.7.4 在此基础上升级为多维评分，不直接替换旧字段，先在响应中新增 `recommendationScore / recommendationLevel / businessReasons`：

```text
结构变化分：新增 / 删除 / 合并 / 拆分 / WBS 分类变化
时间偏移分：总工期偏移、关键路径偏移、里程碑偏移、关键节点偏移
执行事实分：实际进度长期偏离、连续多日未更新、90%-99% 收尾停滞
月度兑现分：最近月计划未完成滚入比例、关键任务未兑现数量
现场影响分：阻碍影响等级、风险问题预警、材料到货影响、验收影响
责任影响分：责任单位缺失、责任主体变化、关键责任单位任务集中延期
数据可靠性分：工程对象缺失、WBS 语义待校准、进度快照缺失、来源映射缺失
```

推荐等级：

```text
none：不建议生成新版
watch：建议关注，但不打扰用户主流程
suggest：建议生成新版基线草案
strong_suggest：建议尽快生成新版基线草案
blocked：数据无法支撑生成，需要先补齐阻断类数据
```

推荐规则：

```text
业务偏差高且数据可靠性高 -> suggest / strong_suggest
业务偏差高但数据可靠性低 -> watch，并提示“数据不完整，建议先补齐关键字段”
只有数据质量问题 -> 不生成新版基线推荐，只进入 v1.4.16 数据质量治理
只有普通任务新增但不影响关键路径 / 里程碑 -> watch 或 none
结构变化影响超过阈值且涉及关键路径 / 关键节点 -> suggest
关键路径或关键里程碑偏移明显 -> strong_suggest
```

### 4.5 基线候选说明

候选说明必须业务化，不展示内部公式。

示例：

```text
建议生成新版基线：当前任务列表已有 12 项计划变化，其中 3 项影响关键路径，预计总完成时间后移 9 天。
建议关注：新增 5 项任务尚未纳入基线，但未影响关键路径和关键节点。
暂不建议生成：当前任务列表与已发布基线整体一致，仅存在少量非关键任务日期调整。
暂不能生成：当前计划缺少关键工程对象或计划日期，先补齐后再生成基线草案。
```

前端只在项目基线页“生成新版基线”入口处表达，不进入 Dashboard，不要求用户日常处理历史差异。

项目基线页的计划治理轻提示和生成新版基线确认态必须复用同一个入口组件：

```text
默认态 = 计划治理轻提示
  当前任务列表与已发布基线已有明显差异，可生成新版基线草案。
  [生成新版基线]

展开态 / 确认态 = 生成前确认
  本次将基于当前任务列表生成新版基线草案。
  主要变化：12 项计划变化，3 项影响关键路径，预计总完成时间后移 9 天。
  [生成草案] [取消]
```

不得再新增一个独立的 Dashboard 健康度标签、全局弹窗或单独计划治理中心来承载这件事。

## 5. 月度计划算法升级

### 5.0 月度计划动作边界

月度计划与项目基线不同，它有月度经营闭环。因此底层保留三个状态节点，用户侧也允许看到三个自然动作，但不做复杂治理中心：

```text
生成草案：
  系统从基线或当前任务列表生成本月计划草案。
  用户可编辑、保存、撤销、重做。

确认启用：
  用户确认本月计划可作为当月执行承诺。
  confirmed 后成为本月承诺快照，不被任务列表日常变化静默反写。

月末确认：
  月末由系统自动归类本月兑现结果，用户只确认归类是否合理。
  确认后形成月度兑现快照，并为下月滚入提供来源。
```

月末确认不是审批，也不是让用户逐项重新填报。它确认的是：

```text
已完成事项
未完成且需要滚入下月的事项
已取消 / 不再执行的事项
异常待处理事项
```

如果用户发现系统自动归类有问题，应在月末确认前调整归类，而不是确认后回改历史：

```text
把“滚入下月”改为“不再执行”
把“异常待处理”改为“滚入下月”
把“已完成”改为“仍需收尾”
```

确认后，月度计划成为历史快照。后续如确有事实修正，只能按 v1.4.14 / v1.4.15 的高权限历史事实修正和留痕规则处理，不在本章生成算法中直接修改历史。

### 5.1 月计划来源选择

当前 `resolveMonthlyPlanGenerationSource` 已实现：

```text
有 confirmed 基线 -> 从基线生成
没有 confirmed 基线或基线 pending_realign -> 从任务列表生成 schedule 临时月计划
```

v1.4.7.4 保留这个方向，但升级为可解释来源选择：

```text
baseline：
  当前存在 confirmed 基线，且基线未 pending_realign，作为月计划主来源

schedule：
  没有 confirmed 基线，或基线 pending_realign，或用户明确选择从当前任务列表生成
  生成结果标记 temporary_without_baseline=true
  只作为当前排期来源，不作为长期基线替代

mixed：
  基线提供总控结构，任务列表提供当前执行事实和新增任务候选
  默认不强制使用 mixed；作为后端候选模式保留，前端可只展示“系统建议”
```

用户不需要选择复杂模式。默认策略：

```text
有稳定 confirmed 基线 -> 默认从基线生成
无基线 / 基线待重整 -> 默认从当前任务列表生成
生成弹窗可展示一句来源说明，不要求用户理解 source_mode
```

### 5.2 月计划纳入规则

月度计划候选项纳入优先级：

```text
1. 计划日期与目标月份重叠的可执行工序任务
2. 上月未完成且仍 active 的任务
3. 当月到期的里程碑
4. 当月影响关键路径的任务
5. 已实际开始但未完成的跨月任务
6. 预计在 3 天内需要启动的前置准备任务
7. 因材料、验收、图纸、证照影响需要提前关注的任务
```

不纳入：

```text
已删除任务
已取消任务
已关闭且不再参与执行的任务
纯结构行，除非用于保持 WBS 展示上下文
只有数据质量问题但无当月执行意义的任务
已完成且不影响当月验收 / 收尾的任务
```

结构行处理：

```text
月计划可以带结构行用于展示层级
结构行 target_progress 为空
结构行 commitment_status 不参与兑现率
工序行 / 可执行行才参与目标进度、兑现率、滚入和偏差分析
```

### 5.3 目标进度算法

当前 `estimateMonthTargetProgress` 主要按日期线性估算目标进度。v1.4.7.4 保留线性估算作为基础口径，但增加修正输入。

基础公式：

```text
计划在本月结束前完成 -> target_progress = 100
计划跨月执行 -> target_progress = 按本月结束日在总计划工期中的比例
里程碑计划在本月完成 -> target_progress = 100
当前进度高于线性目标 -> target_progress 至少等于当前进度
```

修正规则：

```text
若任务已完成 -> target_progress = 100，commitment_status=completed
若任务已实际开始但计划日期不在本月，且未完成 -> 纳入候选并按当前进度 + 剩余工期预测计算目标
若任务为关键路径任务 -> 不降低目标，只提高候选优先级
若存在 blocked 级阻碍 -> 不直接改目标进度，但在候选说明中提示执行影响
若剩余工期预测显示无法按期完成 -> 不自动下调目标，提示“计划目标偏紧”
若进度快照连续缺失 -> 保持目标，但降低置信度
若当前进度异常跳变 -> 保持目标，进入数据质量轻提示
```

目标进度不得做：

```text
不得为了看起来合理而自动降低已承诺目标
不得因为阻碍存在就自动把目标调低
不得把低置信预测写成确定延期
不得把数据质量问题当成业务风险问题
```

### 5.4 月计划滚入规则

滚入只处理上期承诺未完成事项，不回改上期月计划。

```text
上月计划项未完成且任务仍 active -> 生成 carryover 候选
上月计划项完成 -> 不滚入
上月计划项取消 / 关闭 / 删除 -> 按 v1.4.15 判断是否保留历史，不滚入执行计划
任务已完成但验收仍受影响 -> 不作为施工任务滚入，可作为验收影响提示
任务已实际恢复推进 -> 若仍未达上月目标，可滚入但标记为继续推进
```

滚入说明示例：

```text
滚入本月：上月计划未完成，当前进度 65%，仍需继续推进。
不再滚入：任务已完成，后续仅影响消防专项验收。
建议关注：任务已恢复推进，阻碍已降级为待观察。
```

### 7.5 工期统一底座前置要求

v1.4.7.4 不允许再出现第二套工期算法。所有涉及“推荐工期、剩余工期、延期风险、材料到货影响工期、基线缺失日期补齐、月计划目标进度修正”的逻辑，统一遵循：

```text
新建任务工期：durationSuggestionService 输出 recommendedDurationDays / conservativeDurationDays
执行中任务剩余工期：taskDurationForecastService 输出 remainingDurationDays / forecastFinishDate / forecastDelayDays
现场上下文因子：durationContextService 输出 factorSummary / calculationContext / businessReasons
旧 AI 工期接口：已退役，不再作为兼容路由
旧 reference_duration / ai_duration / planned_duration / standard_duration：当前无历史数据环境由 178/208 迁移物理删除，不作为前端业务展示、用户手填入口或当前业务兜底输入
```

2026-06-13 收口后，基线和月计划生成只能消费 v1.4.22 定义的工期三层体系：

```text
事实型 SSOT：
inclusiveDurationDays = 计划工期。
constructionCalendar / delayDayDelta = 施工生产日。

推断型五引擎：
durationSuggestionService / taskDurationForecastService / projectCriticalPathService / projectRemainingDurationForecastService / scheduleAccelerationService。

派生输出：
父节点 rollup / 偏差 / 延期 / 完成总结 / 学习样本 / 滞后与业务状态派生。
```

基线 / 月计划生成不得把上述结果再次展开成私有天数公式。缺失计划日期时可消费 `durationSuggestionService` 形成草案日期；已执行任务只能消费 `taskDurationForecastService` 的剩余预测；关键链压力只能消费 `projectCriticalPathService`；父级节点只消费 `wbsPlanRollupService` 的包络 / 包窗口。生成算法可以解释这些结果为什么影响草案，但不能新建第二套计划工期、施工生产日或剩余工期真值。

前端约束：

```text
任务新增 / 编辑弹窗不展示“参考工期 / AI 工期”手填项，也不新增“标准任务选择”或低置信确认；手工任务标准映射由后端写入链路自动完成
工期建议只在模板生成预览、计划生成预览、任务编辑态日期 / 工期字段旁或材料联动等明确业务场景中展示一句业务化参考
任务保存 payload 不写 reference_duration / ai_duration
执行中剩余工期预测展示范围以 v1.4.18 / v1.4.22 为准：任务列表阅读态展示行内结论，任务详情展示完整业务解释，月度计划阅读态展示来源任务剩余工期预测；项目基线页不展示执行预测
v1.4.7.3 GanttView 薄壳迁移时，taskFormUtils / GanttViewDialogs / GanttViewPanels 或其后续替代组件必须继承上述约束
```

```text
    模式识别评分口径：
      building_construction_pattern 不再只靠 applicableKeywords 命中。
      resolver 必须同时消费 standardWorkCode / templateNodeId / scopeDimensions / rhythmDrivers / primaryWorkfaceType / phaseWindow / expansionStrategy。
      scopeDimensions 来源于任务或模板生成范围中的 building / floor / zone / section / system / workface 事实。
      rhythmDrivers 来源于楼层数、楼栋数、分区数、施工段数、系统数、工法变体、验收门禁、材料 / 开工条件和责任单位承载信息。

      当多个模式同时命中时，优先选择工程特征、结构 / 系统形态、工法方法和构件对象同时命中的模式；再结合 patternRole、conflictGroup、patternPriority、controlChains 和 durationCurveProfile 做同分仲裁；full_project 这类宽阶段窗口只能作为低分背景信号，不得压过 superstructure / mep / commissioning / renovation / handover / opening 等更具体阶段。
      resolver 同分时必须显式按 patternPriority、confidenceScore、resolverSource、原始顺序依次排序，不得只靠数组顺序决定 single_building / multi_building 等冲突模式。
      25 类模式均不命中时返回 no-op fallback：record=null、patternCode=null、actionPolicy=candidate_only；下游必须保持当前显式任务 / 模板事实，不得伪造 general pattern 或新增施工组织上下文。
```

```text
  3. 计算下道工序最早开始日期 = 前道工序计划完成日期 + mandatory_lag_days
  4. 当用户日期紧于硬约束时，候选理由提示"混凝土养护需 7 天，建议下道工序 X 月 X 日开始"
  5. 不强行改用户日期，只显示在候选

作用边界：
  mandatory_lag_days 来源为已确认模板节点或系统 seed 时，可作为生成草案日期的 auto_apply 输入
  用户已维护日期早于硬约束时，不直接覆盖，只 candidate_only 提示建议日期

  软识别无法识别：跳过硬约束计算，候选理由不提示

不允许：

  自动改用户已维护的日期
```

### 13.4 进度趋势学习与速度修正


### 13.6 现场承载压力识别

```text
目标：帮助系统识别"现场可能排不开"的执行压力，作为工期预测、计划生成和偏差解释的候选信号，不引入完整资源调度。

  tasks.building_object_id

    本章新增 seed：resource_class_mapping / site_capacity_pressure

    必须通过 standardWorkCode / engineeringCategoryStableCode 指向 v1.4.7.2 标准库节点

    seed 文件：server/src/seeds/v1474SiteCapacityPressureSeed.ts
    管理 pressureScore 权重、阈值、加天上限、置信度扣减上限、冷启动策略、进度趋势窗口、同类资源每日承载上限、单任务推进异常降权策略
    规则可由项目执行样本自动生成候选，但候选只进入算法治理，不直接覆盖企业规则

算法消费：
  1. 按天聚合并行任务：所有 planned_start_date <= D <= planned_end_date 的任务
  2. 现场承载压力识别规则：
     同一排期窗口 + 同 responsible_unit_id 任务重叠 -> 责任单位承载压力信号
     同一排期窗口 + 同 building_object_id / 同工作面任务重叠 -> 工作面承载压力信号
     同一排期窗口 + 同 resource_class 任务重叠 -> 同类工序承载压力信号

     重叠任务近期应达进度明显高于实际进度 -> 推进偏慢压力信号；应达进度必须复用执行中剩余工期算法的工序曲线口径，不得简单按日期线性推算

     人员 / 设备 / 材料开工条件长期未满足 -> 资源准备承载压力信号
     资源类阻碍未解除或已持续超过 7 / 14 天 -> 现场承载压力增强信号
     关联材料到货逾期 -> 材料侧承载压力信号
  3. 判断优先级：
     推进情况 = 主证据。责任单位名下任务的应达进度明显高于实际进度、连续多天推进不足、多个任务临近完成但进度低时，才说明责任单位真实承压。应达进度判断必须区分 linear / front_heavy / back_heavy / s_curve / hold 类工序：验收、养护、检测、移交、等待类任务天然后重或等待，不按线性进度误判；钢筋、砌筑、抹灰、防水等前重任务更早暴露推进压力；机电安装、装饰装修按 S 曲线判断。
     当前任务自身推进偏慢但没有重叠、没有趋势样本、没有同责任单位历史偏慢时，只能按 singleTaskProgressOnly 降权处理，避免把单个填报滞后误判为整体资源排不开。
     工序语义解析优先级：显式 standard_work_code / standard_task_metadata > standard_work_duration_seed 的 durationContributionMode / executionNature / keywords > v1472TitleWeakRecognitionSeed 低置信兜底 > 普通文本关键词。标题弱识别只能提供候选 standardWorkCode 和低置信上下文，不能绕过标准工序 seed 直接形成强资源压力。
     resource_class_mapping 必须优先按 exact standardWorkCode / longest standardCatalogCodePrefix 仲裁，再退到 keywords；不得用数组顺序首个关键词命中决定资源类别。幕墙、钢结构吊装、塔吊、施工升降机、电梯安装 / 调试、室外道路 / 园路铺装、装饰湿作业、脚手架等容易重名的现场标题必须由标准工序语义分流，避免 facade 抢 curtain_wall、tower_crane 抢 steel_hoisting、室内 flooring 抢室外 utility / landscape、elevator 抢 commissioning。
     resourceOperationType 只做行为上下文，不替代 standardWorkCode，不单独生成前端字段。现场承载压力消费时必须区分加节 / 安装 / 拆除 / 吊装这类短期强占用、使用 / 支撑这类长期背景资源、检测验收 / 调试这类门禁或收尾动作、清理这类收尾清场动作，避免把同一 resourceClass 下的不同施工行为按同一种压力放大。统一解释映射只影响资源窗口压力权重、置信度和偏差原因，不直接输出 add_days；只有叠加推进偏慢、计划窗口紧、承载上限超限、资源类开工条件 / 阻碍 / 材料事实长期未解除等证据时，才从 `resource_window_impact_only` 升级为 `conditional_duration_candidate`。不新增前端展示。
     空间重叠必须分层计分：同区域 > 同楼层 > 同楼栋；同一排期窗口按实际重叠天数 / 当前任务计划天数形成 overlapRatio，不能只按重叠任务条数粗判。
     同类资源必须考虑并行承载能力：塔吊、施工电梯、混凝土浇筑、钢结构吊装、外架、幕墙、电梯调试等低并行资源可放大压力；电气、给排水、暖通、智能化、室外管网、景观等高并行资源只能轻量修正。parallelCapacity 与 sameBuilding / sameUnit / sameFloor / sameZone / sameSystem 日限由 resource_class_mapping / site_capacity_pressure seed 治理；E3 关键路径只消费这些已治理上限，不在服务内另建资源规则。
     非施工承载工序处理：durationContributionMode 非 duration_bearing，或 executionNature 为 inspection_test / monitoring_wait / document_record / management_action / handover_milestone 时，只能作为等待、门禁、资料或管理动作解释，现场承载压力贡献必须降权；不得把验收、养护、检测、移交等待类任务按普通施工任务放大。
     责任单位 / 工作面 / 同类工序重叠 = 背景证据。只有重叠但推进正常时，只能输出低压力和轻置信度影响。
     材料 / 条件 / 阻碍 = 原因解释和增强证据。长期未解决时可放大压力，但不得替代推进表现成为主证据。
     历史履约和趋势快照 = 稳定性证据。它们用于提高 / 降低压力置信度，不要求用户新增资源录入，也不直接生成风险问题。
  4. 按 site_capacity_pressure seed 形成 pressureScore / pressureLevel（low / medium / high），并进入候选理由："1#楼本周同责任单位多项任务推进偏慢，且存在资源类阻碍未解除，建议生成计划时关注错峰"
  5. 不阻断保存，不强行改日期

作用边界：
  只 candidate_only 参与工期预测、计划生成候选理由和偏差解释
  天气、工序多为客观约束；资源压力来自现场执行事实，是三类上下文中最动态、最能反映真实现场压力的一类。只要推进滞后证据充分，工期修正不应过度保守。
  不自动生成风险、问题、阻碍
  不自动调整任务日期，不写 task_dependencies
  不做资源排班、班组产能、机械台账或塔吊覆盖面精算；CPM 资源约束只做同资源 / 同空间日限下的计划网络保护，不输出独立资源排班结果
  不把低置信现场承载压力写成业务风险
  权重、阈值、加天上限、置信度扣减上限必须来自 site_capacity_pressure seed，不能散落在服务代码里

降级策略：
  responsible_unit_id 缺失：跳过班组负载检测
  resource_class_mapping 未配置或未解冻：仅做责任单位、楼栋 / 工作面和进度表现侧面检测
  progress 快照不足：不做推进偏慢信号，仅保留排期重叠信号
  历史完成样本不足：不做责任单位历史承载压力信号，不用少量样本制造强结论

  只有重叠、没有推进异常且没有资源准备事实时：pressureLevel 必须保持 low，multiplier / confidenceDelta 只做轻微影响
  只有当前任务自身推进偏慢，没有同责任单位 / 同工作面 / 同资源重叠和历史证据时：必须按 singleTaskProgressOnly 降权，不能形成高压力

前端展示：
  不新增展示位置、不新增模块、不新增按钮。
  已有位置继续消费：任务详情抽屉工期预测卡、共享计划树工期提示、月度计划非编辑态预测摘要、模板生成预览工期提示、Reports 偏差原因。
  未接入的位置不因本规则新增展示；Dashboard 不新增现场承载压力模块。

自我升级：

  当同类现场承载压力反复导致实际历时偏长或预测误差偏大时，生成 raise_pressure_impact / lower_pressure_impact / stabilize_pressure_impact 候选

不允许：
```

### 13.7 验收时间轴补链候选与观测学习

```text
目标：只识别“看起来应接入验收时间轴但当前未绑定”的高价值验收候选，避免算法用静态默认值替代 v1.4.11 验收时间轴。

数据来源（既有事实）：
  v1.4.11 acceptance_plans / acceptance_records 当前可用字段：
    acceptance_plans.planned_date / actual_date / status
    acceptance_records.record_date / acceptance_result / created_at
    project_entity_links / acceptance_requirements 任务关联

算法消费：
  1. 重大验收只从 v1.4.11 task -> acceptance_plan 关联读取；存在验收时间轴记录时，直接由 acceptance_plans 提供 planned_date / actual_date / status 事实。
  2. 模板生成只把重大验收节点自动写入 acceptance_plans：包括 linked_projection、isAcceptanceMilestone 或显式 acceptanceLinkRule；普通质量检查、分项 / 分部验收、自检复核和资料动作不得因 acceptance_checkpoints 数量自动生成验收时间轴记录。
  3. 同一重大验收在任务列表和验收时间轴同时存在时，计划日期、实际日期、状态以 acceptance_plans 为单一事实；任务列表编辑同一事项时同步写 acceptance_plans，验收时间轴编辑时同步受控反写同一任务，不建立两套计划口径。
  4. 执行中预测只把未通过且 planned_date 晚于当前可完成窗口的验收计划作为 finish gate；pending acceptance 不再按固定默认天数加到 remainingDurationDays。

验收时间归属：
  standard_work_duration：只管标准工序本身参考工期；验收 / 检测 / 复核 / 资料类非承载动作不得贡献普通 baseDays。
  process_constraint：只管已存在依赖边上的搭接能力、门禁约束、时间来源路由、释放工程量门槛和置信度影响；不保存具体等待天数，不直接增加 reference_duration / remaining_duration。养护、技术间歇、检测等待、法定间隔等具体天数统一回到 standard_work_duration_seed、显式承载工序、验收时间轴或项目事实。搭接放行优先看任务真实 planned/completed quantity，缺失时才用 standard_work_duration 默认工程量低置信代理，最后退回楼层 / 分区 / 流水段工作面候选。
  process_constraint 当前规则宽度已按主标准模板和专项 / 分区模板补齐高频模板域，覆盖土方基坑、桩基、地下防水、屋面、防水保温、钢结构、装配式、暖通、给排水、电气、智能化、消防、室外市政、洁净医疗等。模板新增或专项模板增减高频工序时，只同步检查是否需要新增“边存在后的搭接 / 门禁 / 来源路由 / 工程量释放规则”，不得因此自动生成泛化等待天数或替代依赖生成规则。
  生成链路覆盖核查必须落到 `/api/wbs-template-governance/dependency-rule-system/report.processConstraintCoverage`：统计模板已确认关系边总量、生成依赖边总量、process_constraint 命中边量、专项模板命中量和高频未命中边。该指标用于判断是否需要继续扩展规则宽度，不作为普通前端展示，不作为运行期阻断条件。高频规则精度收紧后，覆盖率允许短期下降，但误命中率必须同步下降；不得为了提高覆盖率重新放开两位大类编码或单关键词泛化命中。
  process_constraint 深度治理要求同步进入该报告：必须统计 `byMatchQuality`、`byQuantityEvidenceRequirement`、`byQuantityProxyRiskLevel`、`conditionalEffectMatchedEdgeCount` 和 `backValidationCandidateEligibleRuleCount`。结构化命中必须来自足够具体的 stable_code / template prefix / 专项前缀，且仍需满足 `requiredKeywordGroups` 与 `excludedKeywordTerms`，两位大类编码只能作为背景，不得单独放行搭接；关键词兜底命中的边只能作为低置信治理依据。月度计划和基线算法消费这些结果时，只能把它们转成搭接可行性、门禁原因、置信度或治理候选，不得把 process_constraint 变成新的工期天数来源。`conditionalEffects` 只能根据项目气候画像、天气事实、洁净等级、危大等级或工法变体收紧释放比例、降低穿插置信度或要求项目事实门禁，不得生成新的等待天数。
  acceptance_plans / acceptance_records：管重大验收计划日期、实际日期和通过状态；执行中剩余工期算法只把它作为 finish gate 或闭合事实消费。
  task_conditions / task_obstacles / external_readiness：管资料、条件、阻碍等执行事实；可影响剩余工期 buffer、风险指数和业务原因。

不允许：
  凭任务标题或关键词生成未绑定验收候选
  自动延后用户已维护的下道工序日期
  跨项目共享 acceptance_records 学习
  把检验批、分项 / 分部、普通电气测试、暖通调试、智能化验收、室外管网验收等宽泛质量验收泛化为算法 seed
```

### 13.9.1 有效算法辅助 seed 的自主升级机制

本章有效算法辅助 seed 必须具备类似 v1.4.7.2 标准库 seed 与 v1.4.18 经验工期体系的长期升级能力，但“自主升级”不得理解为运行时直接改写 `server/src/seeds/v1474*Seed.ts` 文件。

核心原则：

```text

自主升级 = 数据库版本治理 + 项目 / 公司校准 overlay + 升级候选 + 自动校核门禁 + 自动发布 / 异常隔离
```

```text

禁止运行时代码直接修改 seed TS 文件
禁止把低置信项目样本直接覆盖系统内置 seed
禁止把单项目偶发偏差提升为公司级或系统级规则
禁止无 sourceStandard / sourceVersion / sourceClauseRef / evidenceSources 的规则进入 active 版本
禁止建设算法 seed 人工审核发布前端入口
禁止通过人工逐条审批替代系统自动校核
```

### 13.10.4 building_pattern 自我升级与自我校准

```text
building_pattern 不做前端置信度展示，只向后端算法输出 confidence_score / confidence_level / matchedSignals / missingSignals / actionPolicy。
经验样本来源必须来自 duration_experience_samples.building_pattern_observation，经由 algorithm_seed_candidates 进入候选治理，不直接改写 TS seed 文件。

当观测样本持续显示缺失信号、冲突信号或低置信命中时，只允许降级为 confidence_only 或 candidate_only，不得自动提升为强约束。
```


## 2026-05-20 progress_velocity / external_readiness 落地补充

本补充用于统一执行中剩余工期、资源压力、外部准备和材料联动的判断口径。

### progress_velocity 因子

`progress_velocity` 不再用 `elapsed / progress` 的线性外推作为兜底判断。

执行口径：

```text
优先消费 project progress velocity learning。
没有项目历史学习结果时，复用 durationContextService 的工序进度曲线：
  linear：普通均衡推进任务。
  front_heavy：钢筋、砌筑、抹灰、防水等前重任务，早期应更快暴露推进压力。
  s_curve：机电、精装、调试、安装类任务，按 S 曲线判断。
  hold / back_heavy：验收、养护、检测、等待、移交类任务，不因前期低进度误判为推进慢。

90%-99% 且已过计划完成日的任务，单独识别为收尾停滞，不混入普通线性速度判断。
进度明显超出工序曲线时，只作为 candidate_only 的轻微工期收紧信号。
进度明显落后工序曲线时，作为 candidate_only 的剩余工期拉长信号。
该因子只影响工期预测、计划生成候选和偏差归因，不阻断用户保存进度，不自动生成风险 / 问题。
```

### external_readiness 因子

`external_readiness` 不再按开工条件、阻碍、材料条数简单叠加。

执行口径：

```text
hard 开工条件未满足：强影响，只有在任务已经正常推进时才降级为置信度信号。
soft / info 开工条件未满足：只轻微影响置信度，不直接加天。
材料有预计到场日：按预计到场日影响最早可开工时间；实际到场后不再影响。
材料没有预计到场日：不凭空制造等待天数，只降低置信度。
阻碍处于 blocked / severe / critical 时：若任务尚未正常推进，可作为候选工期影响。
阻碍存在但任务进度已经恢复或正常推进：自动降级为观察信号，不继续强拉长工期。
已开工且按工序曲线推进正常时，未关闭条件、未关闭阻碍、材料台账滞后不继续作为强影响，只保留为低置信或后台治理提示。
```

验收口径：

```text
验收 / 养护 / 等待类任务在早期低进度下不生成 progress_velocity 慢速因子。
钢筋 / 砌筑 / 抹灰 / 防水等前重任务实际进度明显低于曲线时生成 progress_velocity 因子。
任务正常推进时，未关闭 hard 条件和阻碍不会拉长工期，只进入 external_readiness 的 confidence_only。
材料预计到场晚于计划开工时，external_readiness 输出 materialStartDelayDays；无预计到场日材料只降低置信度。
```
## 2026-05-21 progress_velocity / external_readiness 深化补充

本补充用于把进度速度和外部准备两类因子进一步分清：`progress_velocity` 只回答“任务自身推进速度是否异常”，`external_readiness` 回答“外部事实是否解释了推进异常或开工等待”。两者可以同时存在，但不能重复把同一个原因加天。

### progress_velocity 深化规则

```text
1. 优先读取 task_progress_snapshots 最近趋势，不只看当前 progress 一个点。
2. actual_start_date 为空时，使用第一次 progress > 0 的进度快照作为实际开工事实；没有快照时才回退 planned_start_date。
3. 标准工序 / 专项工序 seed 如果显式给出 progressCurve，优先使用 seed 曲线；关键词只作为兜底。
4. 进度落后但同时存在材料、图纸、hard 条件或强阻碍事实时，progress_velocity 降级为次要证据，主要原因交给 external_readiness。
5. 90%-99% 收尾停滞必须细分原因：整改、验收时间轴未闭合、资料移交、材料收尾、实体收口；不得只写“进度慢”。
6. 最近连续快照显示恢复时，仍落后曲线的任务只做轻量修正，不按持续慢速强拉长工期。
```

### external_readiness 深化规则

```text
1. 材料影响优先读取 task_conditions.source_type/source_ref_id 或 source_entity_type/source_entity_id 的显式材料挂接；project_materials.linked_task_id 仅作为低置信兜底。
2. 开工条件分为 start / process / finish 三类：start 硬条件影响最早开工，process / finish 条件只在任务执行中或收尾阶段影响剩余工期或置信度。
3. 阻碍打开但最近至少两次进度快照持续恢复时，系统自动降级阻碍影响，不立即自动关闭。
4. 材料、条件、阻碍没有日期时，只降低置信度，不凭空增加等待天数。
5. 对外输出业务原因优先级固定为：材料 > 图纸 > hard 条件 > 阻碍 > soft 条件。
```

### 验收补充

```text
显式 progressCurve = hold 的工序，即使标题包含钢筋、混凝土等关键词，也按 hold 曲线判断。
缺 actual_start_date 但存在进度快照的任务，不再按 planned_start_date 误算执行速度。
材料条件明确挂接 source_ref_id 时，只消费该材料；linked_task_id 同时存在的材料不抢占原因。
连续恢复的阻碍只进入观察，不作为严重阻断或强制加天。
收尾停滞的偏差原因必须能区分整改、验收、资料和实体收口。
```

## 2026-05-21 progress_quality 深化补充

`progress_quality` 只作为数据可信度因子参与算法，不作为业务延期、资源压力或外部准备原因。项目基线和月度计划算法消费该因子时，只能用于降低推荐置信度、剔除速度学习样本、提示数据可靠性。

### 执行规则

```text
进度跳变、月末集中补录、收尾卡停：来自 progressAnomalyService。
进度长期未更新：来自 task_progress_snapshots 与 data_quality_findings 的 SNAPSHOT_GAP。
已 resolved / ignored 的 data_quality_findings 不再继续惩罚 progress_quality。
已 acknowledged / confirmed 的异常仍保留记录，但置信度惩罚降级。
stuck_finishing 如果能被验收时间轴未闭合、整改、资料移交等业务事实解释，则主要进入 progress_velocity / external_readiness 的业务归因，progress_quality 只轻度降置信度。
```

### 算法边界

```text
生成新版基线 / 月计划：progress_quality 只影响草案置信度和提示，不直接改任务日期。
执行中剩余工期预测：progress_quality 只降低 confidence，不增加 remainingDurationDays。
速度学习：被 progress_quality 标记 excludedFromVelocityLearning 的样本不得进入速度学习。
健康度 / 偏差分析：progress_quality 进入数据可靠性，不进入业务风险 / 问题。

### 2026-05-21 progress_quality 自我学习升级补充

本次进一步补齐 6 个进度质量治理点，仍坚持“数据质量不等于业务问题”的边界。

1. 进度来源可信度：手工确认、现场日报、移动端填报视为较高可信；批量导入、迁移、系统同步、未知来源只降低置信度，不直接生成业务风险。
2. 快照缺口按工序曲线判断：普通施工任务、短周期任务、收尾任务、养护 / 验收时间轴等待类任务采用不同缺口阈值，避免把 hold 曲线任务的正常等待误判为填报异常。
3. 进度回退识别：从高进度回退到低进度时，系统视为修正事实；未确认的大幅回退会剔除速度学习样本，已确认的小幅修正只降置信度。
4. 重复填报识别：连续多天重复相同进度值时，只降低趋势学习可信度，不改变计划日期。
5. 学习观测输出：progress_quality 输出 `learningObservation`，标记 `retain_with_lower_confidence / downgrade_duration_learning / exclude_duration_learning`，供 v1.4.18 经验样本沉淀消费。
6. 质量发现联动：`PROGRESS_SOURCE_LOW_CONFIDENCE / PROGRESS_ROLLBACK / PROGRESS_DUPLICATE_FILL` 纳入数据质量规则字典；resolved / ignored 后不重复惩罚。

算法作用边界：

progress_quality 永远 `confidence_only`，不加天、不调整 multiplier、不进入风险问题链、不阻断用户保存。
progress_quality 可以让完成任务样本降级为 weak / unusable，防止经验工期自我升级被低质量填报污染。
progress_quality 的候选学习只进入算法治理候选或经验样本元数据，不直接改 seed 文件。
```

## 2026-05-21 四因子自动校准与收口口径

本节用于明确 `progress_velocity / external_readiness / progress_quality / resource_conflict` 四类现场上下文因子的自动化边界。四类因子均可由系统自动判定，不要求用户额外维护算法字段；但它们的自动升级层级不同，后续实现不得混同。

| 因子 | 自动判定 | 自动校准 | 自动升级 | 收口说明 |
|---|---:|---:|---:|---|
| `progress_velocity` | 是 | 是 | 是 | 通过进度快照、同类已完成任务、预测误差回流校准速度权重和曲线判断 |
| `external_readiness` | 是 | 是 | 弱 | 以材料、图纸、证照、条件、阻碍的事实自动消解和自动降级为主，不做强学习型规则 |
| `progress_quality` | 是 | 是 | 是 | 自动识别低可信进度数据，影响置信度、样本资格和经验学习权重 |
| `resource_conflict` / 现场承载压力 | 是 | 是 | 是 | 通过现场承载压力样本生成 `site_capacity_pressure` 候选，再走自动治理门禁 |

执行边界：

```text
1. 四类因子不得自动改写用户任务、基线、月计划或历史快照。
2. 四类因子不得直接生成风险、问题、阻碍或审批事项。
3. 自动升级只允许进入候选、项目级 overlay、经验样本权重或 seed 治理候选。
4. 生效前必须经过样本量、方差、置信度、误差复盘和 v1.4.7.5 / v1.4.22 的治理门禁。
5. 外部准备因子是事实型规则：材料是否到场、图纸是否通过、条件是否满足、阻碍是否解除，本身应由实时事实驱动；不得把一次性阻碍学习成长期规律。
6. 进度速度、进度质量、现场承载压力可以形成明确自学习闭环；外部准备只做自动判定、自动降级、自动消解和预测误差间接校准。
```

## 2026-05-21 最早开工规则与外部准备事实补充

项目基线和月度计划生成继续以任务列表实时事实为核心，不直接改写历史快照。执行中剩余工期预测里的 `earliest_start_rule` 只负责“未开工但已逾期”的最早可开工日判断，供生成新版基线 / 月计划时作为候选解释，不作为独立计划动作。

最早可开工日只允许消费明确日期事实：
```text
前置任务预计完成 / 可开工日
材料预计到场日
critical 阻碍预计解除日
hard 开工条件 target_date
图纸条件 target_date
证照条件 target_date
验收 / 移交类开工条件 target_date
```

过期但未解除的日期事实不继续推迟最早开工日。系统应把它识别为“已失效的开工日期事实”，只进入置信度、风险指数和业务原因，不额外制造等待天数。

计划生成算法消费该结果时，只能读取业务化输出：最早可开工等待、未知日期阻断数量、过期未解除日期数量和原因摘要；不得把 `forecastSources` 内部技术字段直接展示给普通用户。
