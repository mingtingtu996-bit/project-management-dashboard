# v1.2.3 性能收口方案

编制日期：2026-04-28

## 1. 背景

v1.2.1 已完成首包拆分，v1.2.2 已完成项目初始化 bootstrap 聚合。当前用户仍反馈“页面打开后切换、展开、重复进入部分页面仍有慢感”，说明主要瓶颈已经从首包和项目壳层初始化，继续下沉到页面运行时请求与重复渲染链路。

v1.2.3 不新增业务功能，只做运行时性能收口。

## 2. 收口目标

- 减少短时间内重复 API GET 请求。
- 合并并发相同 GET，避免页面多个组件同时订阅同一数据时重复打后端。
- 写操作后立即清空运行时读缓存，避免业务数据被长期旧值污染。
- 保持浏览器层 `no-store` 策略不变，短缓存只存在于前端内存中。
- 用单元测试和性能契约测试固定行为，避免后续退化。

## 3. 本轮实施范围

### 3.1 API GET 并发去重

在 `apiClient` 内增加 `apiReadInflight`：

- 相同 URL、相同认证头、相同 GET 请求并发发起时，只发送一次网络请求。
- 后续并发调用复用同一个 Promise。
- 请求完成后移除 inflight 记录。

### 3.2 API GET 运行时短缓存

在 `apiClient` 内增加 `apiReadCache`：

- 默认 TTL：`2500ms`。
- 最大缓存条目：`80`。
- 仅作用于 `/api` GET。
- 带 `AbortSignal` 的请求不进入缓存，避免破坏页面卸载和取消请求语义。
- 缓存写入和读取均做 payload clone，避免页面本地突变污染缓存。

### 3.3 写操作缓存失效

`POST / PUT / PATCH / DELETE` 进入 `authFetch` 时清空运行时缓存：

- 保证新增、编辑、删除之后的下一次查询重新请求后端。
- 不改变现有业务页面的显式刷新逻辑。

## 4. 本轮不纳入

以下内容收益明确，但改动面更大，放入后续性能专项：

- Dashboard / Risk / Reports 独立摘要接口二次聚合。
- 甘特、风险、材料、验收、月计划虚拟列表。
- Supabase 慢查询日志、Explain 与索引专项。
- Brotli 预压缩、HTTP/2/CDN 策略调整。
- 生产端真实用户性能埋点与慢接口 TopN 面板。

## 6. 放行标准

- 并发相同 API GET 只触发一次 `fetch`。
- 短时间重复 API GET 走运行时缓存。
- 写操作后短缓存失效。
- 前端入口脚本 gzip 继续小于 `350 KB`。
- 本地测试、构建、体积门禁和部署流水线全部通过。
