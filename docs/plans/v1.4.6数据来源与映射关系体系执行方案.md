## 0. 2026-06-01 final range-tree boundary (authoritative)

This v1.4-series plan follows the final range-tree model. There is no production history or existing user data that needs a compatibility layer.

Authoritative engineering object types are exactly: `phase / section / building / basement / floor / physical_zone / functional_area`.

The following compatibility surfaces are deleted and must not be reintroduced in runtime code, migrations, or frontend contracts:

- `zone / professional / subproject / custom` as engineering object types.
- `zone_object_id / professional_object_id` task fields.
- `project_materials.professional_object_id` and `engineering_categories.professional_object_id`.
- `legacy_object_type`, deprecated object-type arrays, legacy bridge/backfill helpers, and old scope adapter functions.
- `/api/scope-dimensions`, `scope_dimensions`, and `project_scope_dimensions` as active application surfaces.

Professional/system/domain/method semantics remain business facts through `specialty_type`, `engineering_category_id`, `standard_work_code`, template metadata, and project profile facts. They are not range-tree objects.

Any older section in this document that mentions deleted object types, deleted fields, old scope tables, or compatibility adapters is superseded by this boundary.
# v1.4.6 数据来源与映射关系体系执行方案

## 1. 目标

v1.4.6 的目标是建立一套后端统一维护的“数据来源与映射关系体系”，把当前应用中分散在 `模板生成 / 项目基线生成 / 月度计划滚入 / 执行任务 / 导入数据 / 完成项目沉淀模板 / 计划调整 / 任务拆分合并` 等链路里的来源关系收口为稳定 ID 映射。

本章解决的是系统内部能否回答这些问题：

```text
这条任务最早来自哪个模板节点
这条基线行由哪个模板节点或任务生成
这条月计划行来自哪条基线行
这条执行任务来自哪条月计划行或基线行
这条导入数据最终落到了哪条任务或计划行
这条任务被拆分、合并、替换或沉淀成模板后，前后关系如何追踪
计划开始时间、计划完成时间、实际开始时间、实际完成时间分别由哪个链路写入
```

本章不做前端来源链路展示，不新增来源详情弹窗，不新增拆分合并历史面板，不在任务表格、任务弹窗、计划编制页面展示导入批次、映射明细、来源明细和 lineage 链路。

版本依赖顺序固定为：

```text
v1.4 工程对象主数据体系
-> v1.4.1 项目范围维度体系
-> v1.4.2 WBS 拆解标准体系
-> v1.4.3 施工任务标准数据模型
-> v1.4.4 建筑工程任务编码规则
-> v1.4.5 状态与生命周期字典体系
-> v1.4.6 数据来源与映射关系体系
```

### 1.1 当前代码执行前置门禁

基于当前代码核查，现有迁移最高只到：

```text

121_add_wbs_engineering_categories.sql
121a_add_engineering_categories_standard_fields.sql

```

当前代码中尚未看到 v1.4.5 状态与生命周期字典体系的数据库底座迁移。因此 v1.4.6 不允许直接跳过 v1.4.5 执行。

执行 v1.4.6 前必须先满足：

```text
1. v1.4.5 状态字典相关迁移已落库。
2. 后端已存在统一状态规范化、状态别名、状态流转校验能力。

```

如果实施时发现 v1.4.5 尚未落库，必须先暂停 v1.4.6，补齐 v1.4.5 后再继续。不得在 v1.4.6 中临时自建一套状态字典，也不得绕过状态字典直接写自由字符串。

## 2. 核心结论

来源、映射、拆分、合并、导入批次全部后端记录：

```text
前端不展示来源链
前端不展示映射关系
前端不展示拆分合并记录
前端不展示导入批次号
前端不展示 lineage/debug 字段
前端不需要理解模板 -> 基线 -> 月计划 -> 任务的内部映射过程
```

前端继续保持 v1.3.5.3 已确定的体验：

```text
项目基线、月度计划、任务列表共用 PlanningTreeTable
用户像编辑一张计划表一样工作
系统在后端处理来源、映射、版本、重编、滚入、拆分、合并、导入和沉淀
```

v1.4.6 的关键是后端主写链路必须稳定留痕，而不是把治理概念推给用户。

```text
验收目录：acceptance_catalog 作为验收节点或验收条件的参考来源
```

数据库硬约束原则：


### 5.0 data_lineage_entity_types 与 data_lineage_relation_rules

实体类型表用于把 `source_entity_type / target_entity_type / entity_type` 从自由字符串收敛为系统字典。

```sql
create table if not exists data_lineage_entity_types (
  entity_type text primary key,
  entity_name text not null,
  entity_group text not null,
  table_name text null,
  id_column text not null default 'id',
  project_id_column text null default 'project_id',
  is_project_scoped boolean not null default true,
  is_global_reference boolean not null default false,
  is_business_lineage_allowed boolean not null default true,
  metadata jsonb not null default '{}',
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),
  check (not (is_project_scoped and is_global_reference))
);
```

必须 bootstrap 的规则：

```text
第 6 章列出的实体类型必须全部写入 data_lineage_entity_types

standard_process / acceptance_catalog / external_record 等可作为全局参考来源的对象可设置 is_global_reference = true
```

bootstrap 校验要求：

```text
1. table_name 不为 null 的实体，validateEntityExists 必须按 table_name + id_column 校验存在。
2. project_id_column 为直接字段时，必须读取该字段校验 project_id。
3. project_id_column 需要反查时，必须在 data_lineage_entity_types.metadata.projectResolver 中写清反查路径，例如 task_id -> tasks.project_id。
4. scope = legacy_compat 的实体只允许 system_backfill 或显式兼容链路写入，不允许新业务主流程写入。
5. scope = non_business 的实体不得写入 data_lineage_links，只能写 data_lineage_events.metadata 或后端日志。
```


project_id 规则：

```text
source 和 target 都是项目内对象时，project_id 必填且必须等于两个对象所属项目
source 或 target 是全局参考库对象时，project_id 仍优先写目标项目 ID，用于项目内追踪
只有纯全局参考关系允许 project_id = null，并且必须在 metadata.scope = 'global' 中说明
跨项目业务对象默认禁止；如未来确需跨项目复用模板，必须走全局模板或 external_record，不允许直接跨项目链任务
```

关系校验规则：

```text
recordLineageLink 写入前必须检查 data_lineage_relation_rules 是否存在 active 规则
如果规则 cardinality = one_to_one，同一 source 和同一 target 都不得存在其他 active 同类映射
如果规则 requires_mapping_weight = true，mapping_weight 必填
同一拆分批次的 mapping_weight 建议合计为 1；无法合计时必须写 metadata.weightBasis
confidence = low / inferred 不得用于覆盖正式业务字段，只能用于数据质量提示或待确认建议
```

```sql
    'merged',
    'replaced',
    'imported',
    'rolled_in',
    'materialized',
    'precipitated',
    'backfilled'
  ))
);
```

索引：

```sql
create index if not exists idx_data_lineage_events_entity
  on data_lineage_events(entity_type, entity_id, occurred_at desc);

create index if not exists idx_data_lineage_events_batch
  on data_lineage_events(batch_id, occurred_at desc);
```

事件不可变要求：

```sql
create or replace function prevent_data_lineage_event_mutation()
returns trigger as $$
begin
  raise exception 'data_lineage_events is append-only';
end;
$$ language plpgsql;

drop trigger if exists trg_prevent_data_lineage_event_update on data_lineage_events;
create trigger trg_prevent_data_lineage_event_update
  before update or delete on data_lineage_events
  for each row execute function prevent_data_lineage_event_mutation();
```

snapshot 安全要求：

```text
before_snapshot / after_snapshot 只允许写白名单字段，不写 password、token、cookie、身份证、手机号等敏感信息
单个 snapshot 序列化后建议不超过 256KB；超限只写摘要和变更字段名
事件用于后端审计和数据质量追溯，不作为普通前端 DTO 字段返回
```

### 5.4 data_import_batches

导入批次只做后端记录，用于幂等、错误定位和数据质量检查，不做前端批次管理页面。

```sql
create table if not exists data_import_batches (
  id uuid primary key default gen_random_uuid(),
  project_id uuid null references projects(id) on delete cascade,
  import_type text not null,
  source_file_name text null,
  source_file_hash text null,
  idempotency_key text null,
  row_count integer not null default 0,
  success_count integer not null default 0,
  failed_count integer not null default 0,
  status text not null default 'completed',
  triggered_by uuid null,
  occurred_at timestamptz not null default now(),
  metadata jsonb not null default '{}',
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),
  check (status in ('pending','completed','failed','cancelled'))
);
```

索引与幂等：

```sql
create unique index if not exists uq_data_import_batches_idempotency
  on data_import_batches(project_id, import_type, idempotency_key)
  where idempotency_key is not null;

create unique index if not exists uq_data_import_batches_completed_file_hash
  on data_import_batches(project_id, import_type, source_file_hash)
  where source_file_hash is not null and status = 'completed';
```

导入重复策略：

```text
同一 project_id + import_type + source_file_hash 的 completed 导入默认不重复执行
用户明确重新导入时必须生成新的 idempotency_key，并在 metadata.reason 中说明
重复导入不得静默覆盖正式任务；覆盖必须写 imported_from 链接和 data_lineage_events
```

### 5.5 data_import_rows

记录导入行与业务对象之间的落库结果。

```sql
create table if not exists data_import_rows (
  id uuid primary key default gen_random_uuid(),
  import_batch_id uuid not null references data_import_batches(id) on delete cascade,
  row_number integer not null,
  source_row_hash text null,
  raw_payload jsonb not null default '{}',
  raw_payload_redacted boolean not null default true,
  normalized_payload jsonb not null default '{}',
  payload_retention_until timestamptz null,
  target_entity_type text null,
  target_entity_id text null,
  row_status text not null default 'mapped',
  error_message text null,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),
  unique(import_batch_id, row_number),
  check (row_status in ('mapped','created','updated','skipped','failed','duplicate')),
  check (octet_length(raw_payload::text) <= 1048576),
  check (octet_length(normalized_payload::text) <= 1048576)
);
```

导入行规则：

```text
target_entity_type / target_entity_id 只记录主落库对象
一行导入生成多个业务对象时，全部对象关系以 data_lineage_links 为准
raw_payload 必须默认脱敏；如保留原始值，必须设置 payload_retention_until 并说明用途
raw_payload / normalized_payload 不得保存密码、token、cookie、身份证、银行卡等敏感字段
```

### 5.6 RLS 与权限

```text
data_lineage_entity_types：普通用户只读或仅通过后端 API 读取；service_role 可写

data_import_rows：普通用户不可直接写；导入接口或后端内部服务可写
```

RLS 实施要求：

```text
所有 data_lineage_* / data_import_* 表 enable row level security
drop policy if exists 后重建 policy
普通业务 API 默认不返回 lineage/import/debug 字段
内部审计接口如未来需要，必须单独规划并要求项目管理员或系统管理员权限
```

## 7. 写入规则

### 7.0 写入事务与失败策略

v1.4.6 的底线是业务事实和 lineage 留痕不能长期不一致。

必须同事务写入的链路：

```text
模板生成基线
基线生成月计划
月计划物化任务
任务拆分
任务合并
任务替换或重新生成
导入行落库到任务、基线、月计划或图纸
验收回写任务完成
任务依赖、证照依赖、验收依赖的创建和删除
图纸版本切换当前版本
```

同事务要求：

```text
业务对象写入成功但 lineage 写入失败时，必须回滚业务写入
lineage batch 创建成功但业务写入失败时，batch 标记 failed，并写失败 metadata
同一个业务动作只能生成一个主 batch；批量动作可通过 metadata.itemCount 记录规模
```

允许异步补偿的链路：

```text
数据质量 finding
BI 快照
周报摘要
风险统计
责任预警
AI 分析上下文
```

异步补偿要求：

```text
必须有 idempotency_key
失败后写 failed batch 或 data_quality finding
后台重试不得重复生成 active lineage
超过重试次数后只提示数据质量问题，不阻塞普通查看
```

### 7.1 模板生成基线

模板套用或生成基线时：

```text
创建 data_lineage_batches(batch_type = template_apply 或 baseline_generate)
每个 template_node -> task_baseline_item 写 data_lineage_links
relation_type = generated_from
confidence = confirmed
task_baseline_items.source_task_id / source_milestone_id 等局部字段继续保留
```

禁止规则：

```text
不得仅通过标题、层级、日期推断生成后的长期映射
标题、层级、日期只允许用于第一次匹配建议或低置信度数据质量检查
```

### 7.2 基线生成月计划

月计划从基线生成或滚入时：

```text
创建 data_lineage_batches(batch_type = monthly_generate 或 monthly_roll_in)
每个 task_baseline_item -> monthly_plan_item 写 data_lineage_links
relation_type = rolled_into
monthly_plan_items.baseline_item_id 继续作为局部快捷字段
carryover_from_item_id 继续表示月度计划行之间的滚动来源
```

### 7.3 月计划物化执行任务

月计划行生成或更新执行任务时：

```text
创建 data_lineage_batches(batch_type = task_materialize)
每个 monthly_plan_item -> task 写 data_lineage_links
relation_type = materialized_from
tasks.monthly_plan_item_id 继续作为局部快捷字段
tasks.baseline_item_id 可继续作为跨层锚点，但不能替代 lineage_links
```

如果一条月计划行拆成多条执行任务：

```text
写多条 monthly_plan_item -> task 映射
relation_type = split_from
mapping_weight 可记录拆分比例
原月计划行不删除
```

如果多条月计划行合并为一条执行任务：

```text
写多条 monthly_plan_item -> task 映射
relation_type = merged_from
target task 为当前执行对象
来源月计划行保留原始记录和状态
```

### 7.4 执行任务调整

任务在任务列表或甘特图中自由编辑时：

```text
不要求用户选择来源
不要求用户理解映射
后端根据当前任务 ID 写 data_lineage_events(event_type = updated)
如果编辑导致范围对象、WBS 分类、计划时间或责任主体变化，记录 before_snapshot / after_snapshot
```

普通编辑不重建 lineage 链。只有明确发生拆分、合并、替换、重生成、导入覆盖、模板沉淀时，才新增或变更 lineage_links。

### 7.5 导入数据

导入只在后端记录批次和行级结果：

```text
创建 data_import_batches
逐行创建 data_import_rows
每个成功落库的 import_row -> target_entity 写 data_lineage_links
relation_type = imported_from
同时创建 data_lineage_batches(batch_type = import)
```

导入匹配优先级：

```text
稳定 ID
task_code 等系统编码
既有 lineage link
对象 ID + 工程分类 ID + 日期范围 + 名称的组合匹配
低置信度匹配只允许进入待确认或数据质量 finding，不得静默覆盖正式任务
```

### 7.6 完成项目沉淀模板

项目完成后沉淀模板时：

```text
completed task / baseline item -> template_candidate 写 data_lineage_links
relation_type = precipitated_to
沉淀结果先进入 template_candidate 或待发布模板版本
不得反向改写历史任务、历史基线、历史月计划
```

### 7.7 验收、证照、图纸链路

验收依赖和条件不是计划主链，但属于工程执行联动来源，必须记录：

```text
acceptance_plan -> acceptance_plan 写 depends_on，对应 acceptance_dependencies.source_plan_id / target_plan_id
task_condition / drawing_package / certificate / warning / issue -> acceptance_requirement 写 requires
acceptance_plan / acceptance_node -> task 写 triggers 或 linked_to，仅在验收回写任务完成时记录
pre_milestone -> pre_milestone 写 depends_on，对应 pre_milestone_dependencies
pre_milestone -> certificate_work_item 写 materialized_from 或 linked_to，对应 certificate_work_items
certificate_work_item -> certificate_work_item 写 depends_on，对应 certificate_dependencies
certificate_approval -> certificate_work_item 写 approval_of，仅限历史 certificate_approvals 兼容回填
drawing_version.previous_version_id -> drawing_version 写 versioned_from
drawing_package -> acceptance_requirement 写 requires 或 linked_to
```

规则：

```text
验收时间轴仍是独立业务模块，不把验收摘要塞回任务详情
验收回写任务完成时必须记录来源，不得只改 tasks.progress / status
图纸版本替换必须保留 previous_version_id，并写 versioned_from / supersedes
证照依赖只记录证照事项之间的关系，不合并进任务 WBS
certificate_approvals 不作为新证照审批入口；如旧库仍有记录，只通过 system_backfill 写 approval_of 兼容链
```

### 7.8 材料、条件、阻碍和任务依赖链路

```text
project_material -> task 写 linked_to 或 requires
material arrival reminder -> notification 写 triggers
task_condition -> task 写 requires
task_obstacle -> task 写 blocks
task_obstacle -> issue 写 escalated_to，对应 obstacle_escalated
task_condition -> issue 写 escalated_to，对应 condition_expired
task -> task 写 depends_on，对应 task_dependencies
task_preceding_relation -> task 写 depends_on 或 linked_to，对应旧前置关系兼容
```

规则：

```text
材料、条件、阻碍仍由各自模块维护，不进入任务来源链主视图
条件满足、阻碍解决、材料到场如果改变任务业务状态，必须写 data_lineage_events
任务依赖的 source_type 继续保留，但跨模块追溯读 data_lineage_links
```

### 7.9 风险、问题、预警、通知升级链

风险问题预警链路当前已有 `source_type / source_id / source_entity_type / source_entity_id / chain_id / escalated_to_risk_id / resolved_source`，v1.4.6 需要统一解释：

```text
warning -> notification 写 reported_by 或 linked_to
notification -> risk 写 escalated_to
risk -> issue 写 converted_to 或 escalated_to
task_condition -> issue 写 escalated_to
task_obstacle -> issue 写 escalated_to
acceptance_plan -> issue 写 escalated_to
source_deleted / manual_closed / condition_satisfied 等关闭来源写 resolved_by
同一升级链共享 chain_id，并可通过 data_lineage_links 追踪
```

规则：

```text
chain_id 继续保留为风险问题预警链的快捷字段
source_type 继续用于业务分类统计
data_lineage_links 用于跨对象追溯和审计
普通前端不新增升级链详情面板
```

### 7.10 变更日志、治理信号、快照和报表来源

```text
change_log -> target entity 写 changed_by，对应 resource_type / resource_id / change_source
project_daily_snapshot -> project 写 snapshot_of
task_progress_snapshot -> task 写 snapshot_of，并保留 planning_source_* 快捷字段
task_progress_history -> task 写 linked_to 或 snapshot_of，用于解释实际进度事实
task_timeline_event -> task 写 linked_to，用于解释任务时间轴事件
planning_governance_signal -> task / monthly_plan / baseline / change_log 写 reported_by 或 linked_to
data_quality_finding -> source entity 写 reported_by
data_confidence_snapshot -> project / task / monthly_plan / baseline 写 snapshot_of
responsibility_watchlist -> notification / warning 写 triggers
responsibility_alert_state -> notification 写 linked_to
risk_statistics -> risk / project 写 snapshot_of
weekly_digest -> project / task / warning 写 snapshot_of 或 generated_from
warning_acknowledgment -> warning 写 resolved_by 或 linked_to
report / task_summary / completion_report -> source entity 写 snapshot_of 或 generated_from
```

规则：

```text
快照和报表是派生事实，不反向改写来源对象
BI 可以用 lineage 做口径解释，但不把 lineage 主键展示成业务维度
change_logs 继续作为用户可理解的变更记录，data_lineage_events 作为更底层的审计事件
```

### 7.11 里程碑、关键路径与旧 WBS 兼容链路

```text
task -> milestone 写 linked_to，对应 task_milestones 或 tasks.milestone_id
task_critical_override -> task 写 overrides
task_critical_override -> anchor task 写 anchors，对应 anchor_task_id / anchor_ref_type
wbs_structure -> task / task_baseline_item / monthly_plan_item 写 mapped_from，仅用于旧结构兼容回填
wbs_task_link -> task 写 linked_to，仅用于旧结构兼容回填
```

规则：

```text
任务里程碑关联只解释节点归属，不改变任务来源主链
关键路径人工干预只解释调度分析口径，不改变任务、基线、月计划的来源
旧 wbs_structure / wbs_task_links 不是 v1.4.2 后的新 WBS 分类权威，只能作为 low 或 inferred 兼容来源
技术日志、锁表、定时任务执行日志不写 data_lineage_links
delay_requests / task_delay_history 不恢复，不作为新的延期来源链
```

### 7.12 参考库、配置和派生摘要边界

```text
standard_process -> wbs_template_node / engineering_category 写 generated_from 或 linked_to
acceptance_catalog -> acceptance_node / acceptance_requirement 写 generated_from 或 linked_to
project_data_quality_setting / system_setting / dialog_frequency_setting 不写 lineage
users / project_members / project_invitations 不写 lineage，责任主体关系按 v1.4.3/责任主体体系读取
```

规则：

```text
参考库只能解释业务对象的生成来源，不能反向覆盖项目执行数据
配置、偏好、权限对象只影响系统行为，不属于工程业务来源链
责任预警、周报、风险统计属于派生事实，能追踪来源，但不反向改写来源任务或风险
```

## 8. 计划时间字段治理

计划开始时间、计划完成时间、实际开始时间、实际完成时间的来源、映射和留痕放在 v1.4.6；谁能写、谁不能写、写入后如何传播的治理规则放在 v1.4.7。

### 8.1 字段权威边界

```text
模板节点：只提供建议工期、建议偏移和默认逻辑，不是项目真实计划时间
项目基线：项目级承诺计划，保存 baseline planned_start / planned_end
月度计划：当月承诺计划，保存 monthly planned_start / planned_end
执行任务：现场当前执行计划，保存 tasks.planned_start_date / tasks.planned_end_date，并兼容 tasks.start_date / tasks.end_date
实际开始：来自执行事实，通常由后端根据 progress 首次大于 0、状态进入进行中或系统事件生成；手工更正只作为 correction 来源留痕
实际完成：来自执行事实，通常由后端根据 progress 达到 100、完成确认、验收通过事件或兼容迁移事件生成；手工更正只作为 correction 来源留痕
```

### 8.2 写入优先级

```text
实际时间不得被模板、基线、月计划重新生成覆盖
执行任务计划时间可由月计划物化生成，也可由用户在执行表中调整
执行任务计划时间调整必须写 data_lineage_events，而不是改写来源基线或月计划
基线计划时间调整必须走基线修订链路，不得由任务编辑反向覆盖
月计划计划时间调整只影响当月计划，不得自动回写基线，除非进入明确修订流程
导入数据写入计划时间时必须记录 import_row 和 batch
```

### 8.3 推荐新增时间来源字段

```sql

alter table tasks add column if not exists actual_end_source text null;
alter table tasks add column if not exists actual_end_source_ref_type text null;

```

允许值：

```text

```

规则：


## 9. 拆分、合并、替换规则

### 9.1 拆分

任务或计划行拆分时：

```text
原对象保留
新对象获得自己的主键、任务编码和状态
原对象到新对象写 split_from 链接
拆分比例可写 mapping_weight
原对象是否关闭、停用、取消由业务状态决定，不由 lineage 自动决定
```

### 9.2 合并

任务或计划行合并时：

```text
多个来源对象保留
目标对象获得自己的主键、任务编码和状态
每个来源对象到目标对象写 merged_from 链接
来源对象是否关闭、停用、取消由业务状态决定
```

### 9.3 替换和重新生成

重新生成基线、月计划或任务时：

```text
旧对象不物理删除
旧映射 mapping_status = superseded
新对象写新的 active 映射
必要时写 replaced_by 链接
```

禁止用覆盖更新的方式让旧对象“看起来从未存在”。

## 10. 后端服务

### 10.0 当前代码的事务落地方式

当前后端很多主写链路使用多次 `supabase.from(...).insert/update/delete` 或 `executeSQL` 顺序调用，例如：

```text
wbs-templates.ts：创建 task_baselines 后再插入 task_baseline_items
task-baselines.ts：创建/替换基线行
monthly-plans.ts：创建 monthly_plans 后再插入 monthly_plan_items
tasks.ts / taskWriteChainService.ts：任务创建、编辑、范围回填、快照写入
drawing-packages.ts / construction-drawings.ts：图纸版本切换多个表
acceptanceFlowService.ts：验收依赖、验收条件、验收记录写入
certificate-work-items.ts：部分链路已有 RPC 原子写入，部分仍是多次 SQL
```

因此 v1.4.6 不能只在 service 中“写完业务再补 lineage”。必须先补一个统一事务能力，推荐落点：

```ts
// server/src/database.ts
export async function withTransaction<T>(
  handler: (client: PoolClient) => Promise<T>,
): Promise<T>
```

实现要求：

```text
1. withTransaction 内部使用 getClient()，显式 BEGIN / COMMIT / ROLLBACK / release。
2. 新增 dataLineageService 方法必须支持可选 txClient；传入 txClient 时不得再使用独立 supabase 请求写库。
3. 主写链路需要同事务时，业务写入和 lineage 写入都必须走同一个 txClient，或改造成一个数据库 RPC。
4. 如果某条链路短期无法改造成 txClient，必须先迁移为数据库 RPC，再在 RPC 内完成业务写入和 lineage 写入。
5. 禁止使用“业务写成功后 Promise.all 补 lineage”的方式满足同事务要求。
6. 异步补偿链路只能用于数据质量、BI 快照、周报、风险统计、责任预警等第 7.0 允许异步的派生事实。
```

执行落点要求：

```text
第一步先补 database.withTransaction 和 tx 版 query helper。
第二步改造 dataLineageService，使 createLineageBatch / recordLineageLink / recordLineageEvent 都可接收 txClient。
第三步优先改造模板生成基线、基线生成月计划、月计划物化任务、任务拆分合并、导入落库五条主链。

第五步测试必须模拟 lineage 写入失败，断言业务写入被回滚。
```

新增服务：

```text

```

`dataLineageService` 必须提供：


## 13. 与 v1.4 到 v1.4.5 前端口径核查

核查结论：v1.4 到 v1.4.5 没有要求普通前端展示来源链、映射链、拆分合并记录或导入批次。

逐章口径如下：


新增数据质量检查：

```text
基线行缺少模板或任务来源
月计划行缺少基线来源
执行任务缺少月计划或基线来源
同一来源对象 active 映射到多个目标但未声明 split

mapping_status 与业务状态冲突
导入行成功但未形成 target_entity
导入行覆盖已有任务但没有 lineage event
实际时间被模板、基线或月计划覆盖
低置信度 inferred 映射被用于正式覆盖写入
验收依赖指向不存在的 source_plan_id / target_plan_id
验收条件 source_entity_type / source_entity_id 指向不存在对象
证照依赖出现循环
证照工作项脱离前置里程碑或项目
历史 certificate_approvals 兼容回填指向不存在的 certificate_work_item

任务依赖跨项目、循环或 source_type 非法

change_logs.resource_type / resource_id 指向不存在对象
快照 planning_source_* 与 task 的 baseline/monthly 锚点冲突
```

BI 使用规则：

```text
BI 可以使用 lineage 计算模板命中率、月计划兑现率、任务来源完整率和导入质量
BI 不把 lineage ID 当作业务维度展示
BI 对外展示业务指标，不展示批次号、映射主键、行级导入 ID
AI 可以读取 lineage 上下文做分析，但回答用户时应转成业务语言
```

AI 与后台诊断边界：

```text
数据来源异常默认进入后端数据质量 finding、审计日志或管理后台，不新增普通前端诊断区
AI 可以解释异常原因、汇总影响范围、生成修复建议或修复草案
AI 不得绕过权限、状态机、来源规则和数据质量校验直接改写业务数据
自动修复只能调用后端确定性修复接口，并保留操作人、原因、变更日志和 lineage event
影响已确认基线、已确认月计划、实际完成事实的修复必须经过人工确认或既有审批/更正流程
```

BI 指标落点：

```text
模板命中率、月计划兑现率、任务来源完整率、导入成功率、断链率必须通过 metricRegistry 或统一指标服务暴露
页面不得直接扫描 data_lineage_links 计算业务指标
BI 快照必须记录 lineageVersion 或 lineageBatchId 摘要，用于口径审计
lineage ID 不作为普通维度下钻；只允许内部审计使用
```

数据质量规则必须落成 rule_code：

```text
LINEAGE_MISSING_SOURCE：缺少来源，默认 warning，影响重新生成时可阻断
LINEAGE_ORPHAN_LINK：来源或目标不存在，默认 error，阻断使用该链路覆盖业务数据
LINEAGE_DUPLICATE_ACTIVE：重复 active 映射，默认 error，阻断生成/导入
LINEAGE_CROSS_PROJECT：跨项目错链，默认 error，阻断写入
LINEAGE_LOW_CONFIDENCE_WRITE：低置信关系用于正式覆盖，默认 error，阻断写入
LINEAGE_TIME_SOURCE_CONFLICT：时间来源冲突，默认 warning；实际时间被覆盖时升级 error
LINEAGE_TECH_OBJECT_LEAK：技术日志、锁表、权限配置等进入业务 lineage，默认 error
LINEAGE_FRONTEND_LEAK：普通 DTO 或页面展示内部 lineage 字段，默认 error
```

## 17. Assumptions

当前没有历史生产数据，所以 v1.4.6 不做复杂历史清洗；只对当前开发数据、样例数据和明确可识别关系做轻量 backfill。

现有 `tasks / task_baseline_items / monthly_plan_items` 的局部来源字段继续保留，作为查询加速和兼容字段；统一跨模块追溯以 `data_lineage_links` 为准。

v1.4.6 不改变普通用户的主流程。来源与映射体系服务于后端治理、审计、数据质量、BI 和 AI，不服务于普通前端展示。

如果后续要做内部审计页面或导入批次管理页面，必须作为单独版本规划，且不得回头污染普通任务表格、任务弹窗和计划编制三页。

## 18. 与计划快照 / 当前执行事实的关系

来源与映射体系必须遵循 v1.4.7 的计划真相模型。普通任务编辑是当前执行事实变化，不等于重新生成历史计划快照。

执行项：

```text
普通任务编辑只写任务变更日志、进度快照或轻量 lineage event，不重建完整来源链。
生成新版项目基线时，创建当前任务 -> 基线行的快照映射链。
生成或重新生成月度计划时，创建当前任务 / 当前基线 / 上月关账结果 -> 月计划行的快照映射链。
已发布基线、已确认月计划的旧映射保留，不因任务后续变化被覆盖。
```
