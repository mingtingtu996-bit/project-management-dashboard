## 0. 2026-06-01 final range-tree boundary (authoritative)

This v1.4-series plan follows the final range-tree model. There is no production history or existing user data that needs a compatibility layer.

Authoritative engineering object types are exactly: `phase / section / building / basement / floor / physical_zone / functional_area`.

The following compatibility surfaces are deleted and must not be reintroduced in runtime code, migrations, or frontend contracts:

- `zone / professional / subproject / custom` as engineering object types.
- `zone_object_id / professional_object_id` task fields.
- `project_materials.professional_object_id` and `engineering_categories.professional_object_id`.
- `legacy_object_type`, deprecated object-type arrays, legacy bridge/backfill helpers, and old scope adapter functions.
- `/api/scope-dimensions`, `scope_dimensions`, and `project_scope_dimensions` as active application surfaces.

Professional/system/domain/method semantics remain business facts through `specialty_type`, `engineering_category_id`, `standard_work_code`, template metadata, and project profile facts. They are not range-tree objects.

Any older section in this document that mentions deleted object types, deleted fields, old scope tables, or compatibility adapters is superseded by this boundary.
# v1.4.14 变更留痕、审批、审计体系执行方案

## 1. 目标

v1.4.14 的目标是把当前应用中已经存在但口径分散的 `变更记录 / 版本记录 / 快照 / 历史兼容强制来源 / 后端治理修复记录 / 审批确认 / 操作审计` 收口为一套统一的后台治理体系。

本章解决的是系统内部能否稳定回答这些问题：

```text
谁在什么时候改了什么业务事实
这次变更是用户手动、系统自动、发布确认、后端治理修复，还是高权限纠错
哪些变更只需要留痕，哪些变更需要确认，哪些变更属于高权限治理或审批记录
历史基线、月度计划、任务事实、风险问题、图纸证照验收等对象发生变化后如何追踪
安全审计、请求日志和业务变更记录如何分工，避免混成一张表
旧字段、旧日志、旧版本记录如何继续兼容
```

本章继续沿用 v1.4.8 之后形成的统一原则：

```text
用户维护业务事实，系统判断治理语义
能由系统后台留痕和审计的，不新增弹窗、不新增必填理由、不把技术字段推给用户
普通前端不展示 source、lineage、chain_id、request_id、audit_id、change_source 等治理字段
审批不做成完整 OA 流程；当前应用只保留“统一审批边界 + 统一审批记录底座”，高权限动作由项目管理员直接授权并留痕
```

说明：本章提到的高权限动作是后端治理能力或未来管理员后台能力，不代表当前新增普通前端入口，也不代表恢复“强制关账 / 强制解锁 / 强制解除开工条件”等前台主动作。

### 1.1 与 v1.4.7.1 共享计划树的上游边界

`v1.4.7.1` 是项目基线、月度计划、任务列表三页的共享计划树交互与提交契约。本章只处理共享计划树保存后、发布确认后、关闭归档后形成的业务留痕、确认边界和审计归档，不重新定义阅读态、编辑态、保存、撤销、重做、删除行和业务动作按钮。

必须固定以下原则：

```text
阅读态 / 编辑态 / 业务动作三层模型以 v1.4.7.1 为准，本章不得另起一套“留痕编辑态”“审计草稿态”或“日志确认态”。
保存前只属于编辑缓冲：单元格编辑、复制粘贴、批量填充、删除行、移动、缩进、template_generate、撤销/重做，在保存前不写 change_logs，不写业务 operation_logs 摘要。
保存是留痕分界点：共享计划树 commit 成功后，本章按一次提交写业务摘要；失败、取消、预览、撤销到未保存状态都不写业务成功留痕。
阅读态业务动作独立于保存：生成基线、发布基线、确认月计划、月度关账、关闭阻碍、归档资料等必须按阅读态业务动作单独留痕，不能和编辑态保存合并成一个按钮或一条含混记录。
v1.4.7.2 的阅读态“生成任务”只打开模板选择、预览并把结果加入编辑缓冲，不在点击生成时写业务留痕；只有最终共享计划树 commit 保存成功后，才按“一批 N 行模板生成”聚合写摘要。
删除行不是删除事实：共享表格里的 delete_row 只是编辑意图，保存后才由 v1.4.15 判断真实处置；本章只记录最终处置摘要，不记录保存前删除动作流水。
变更摘要按字段注册表 mergeGroup 聚合：字段展示组、协作合并组、变更摘要组必须来自 v1.4.7.1 后端字段注册表，不得由本章在前端或日志服务里硬编码第二套字段分组。
协作更新不是业务变更：presence、merge base 更新、自动合并提示、同字段冲突提示只属于共享计划树协作信号；只有用户保存成功或执行业务动作成功后才写 change_logs。
校核条、健康横幅、数据质量提示不等于系统建议或业务变更：项目基线和月度计划基础问题由校核条与发布/确认前校核承接，任务列表健康横幅只承载实时执行事实问题；本章不得把这些提示本身写成业务变更。
template_generate 服从共享计划树：保存前是原子编辑操作，保存后按“一批 N 行模板生成”聚合留痕；模板来源明细归来源映射和模板候选事实承载。
月度计划页不产生 template_generate，也不提供生成任务 / 智能展开入口；月度计划只消费已落地任务、基线和滚入生成结果。
普通三页主流程必须走 v1.4.7.1 的 commit / publish / confirm / close 语义，旧 PUT / POST / DELETE 只能兼容，不能绕过共享计划树提交治理直接写留痕。
```

与前面章节的关系：

```text

v1.4.1 记录项目范围维度的对象化、适配、停用与旧范围兼容
```

## 2. 核心结论

本章把四类概念明确拆开：

```text
业务变更留痕：业务对象发生变化后的事实记录
业务确认：用户明确保存、发布、确认、关闭、归档某个业务状态
高权限治理 / 审批记录：少量高权限动作在生效前需要项目管理员授权，或至少写入统一治理记录
技术审计：系统请求、登录、安全、权限、异常、后台任务的运行记录
```

它们不是一件事。

```text
任务进度从 40% 保存到 60%：业务变更留痕，不需要审批
任务进度保存到 100%：显式保存即确认完成，系统自动写实际完成，不需要审批
项目基线发布：业务确认，必须写版本记录、快照、change_logs
已确认月度计划、已发布基线、已关账月份原则上不做常规修正；确因数据错误、导入回填、系统迁移需要修正时，作为项目管理员高权限动作留痕
历史事实纠错、冻结后纠错、后端治理修复：高权限治理动作，必须留痕和审计，不做复杂审批流
用户登录、修改密码、接口访问：技术审计，不进入业务变更时间线
```

前端原则：

```text
不新增“审批中心”
不新增“审计中心”
不在任务表格中展示变更日志列
不要求用户为普通保存填写原因
不要求用户理解 change_source、audit_type、request_id
已有版本记录、差异详情、健康横幅、提醒中心继续作为用户可见入口
项目基线、月度计划、任务列表沿用 v1.3.5.3 的共享 PlanningTreeTable / PlanTreeEditor，不另起一套留痕编辑界面
专项管理页面即使不是共享大表，也沿用“用户做业务动作，系统解释治理影响”的同一原则
用户看到的是编辑、删除、撤销、重做、保存、发布、确认等表格动作；系统后台理解留痕、审计和业务影响
撤销/重做作为共享表格底座稳定能力存在，支持工具栏、底部编辑栏和快捷键，不依赖短时 toast
编辑态删除行就是普通表格删除；保存前可撤销，保存时由后端按 v1.4.15 判断是真删除、取消、停用、归档还是拒绝删除
复制粘贴、批量填充、批量改字段不能绕过后端校验；保存时仍要执行 v1.4.7.1 的共享表格提交规则、v1.4.7 的计划治理规则，以及 v1.4.15 的历史保留规则
```

### 2.1 共享表格底座的操作口径

项目基线、月度计划、任务列表统一采用“用户像编辑 Excel 一样维护业务事实，系统后台理解业务影响”的原则。专项管理页面不强行改成共享大表，但沿用同一原则：用户做业务动作，系统解释治理影响。这里的“草稿”只作为系统内部状态和保存前编辑缓冲，不作为新的前台流程。

用户可感知状态只能是：

```text
未保存更改
保存中
已保存
保存失败
可撤销 / 可重做
离开前提醒
```

前端不得展示：

```text
进入草稿态
草稿页面
作废草稿
修订草稿
强制解锁草稿
处理草稿流程
```

共享表格操作分两层：

```text
编辑态表格操作：单元格编辑、复制、粘贴、批量填充、批量改字段、删除行、缩进、升降级、上移、下移、撤销、重做、行选择、拖拽预览。
阅读态业务动作：生成基线、生成任务、采纳或忽略生成建议、发布基线、确认月计划、月度关账、关闭风险/问题/阻碍、归档资料、作废图纸/证照/验收记录、后端治理修复、高权限纠错。
```

编辑态表格操作只进入表格编辑缓冲区和本地历史栈，不逐条写 `change_logs`，不逐条写 `operation_logs` 业务摘要，也不得绕过后端校验。点击保存时才统一提交到后端，由后端按 v1.4.7.1、v1.4.7、v1.4.8、v1.4.15 等规则校验后写业务事实、快照和一组变更摘要。发布、确认、关账、关闭、归档等阅读态业务动作必须独立提交，不能和保存合并成一个按钮。

四个当前代码偏差必须按以下口径收口：

```text
任务列表 / Gantt：当前单元格失焦保存、粘贴后逐条 POST、批量填充逐条 PATCH、删除行逐条 DELETE 的即时落库行为，必须改为编辑态缓冲。单元格编辑、粘贴、填充、删除、移动、缩进只更新本地编辑缓冲和 pending operations；用户点击保存后统一提交。普通任务表格保存必须使用当前统一入口 POST /api/tasks/commit，或完全等价的统一提交服务，不新增第二套 table-commit 路由，承接 create / update / delete / move / indent / outdent 等操作。
撤销 / 重做：当前月度计划已有局部历史栈，项目基线仍是 canUndo=false，任务列表也没有统一 undo/redo。必须抽成共享表格历史能力，作用于保存前编辑缓冲；保存后的撤回不是本地 undo，而是新的业务动作，必须重新校验、重新提交、重新留痕。
月度计划批量操作：当前 batch-scope / batch-shift-dates / batch-target-progress / batch-notes 等接口会立即落库并写 change_logs。执行本章时，表格内批量填充、批量改字段、批量移入/移出必须先作为编辑态操作进入缓冲区；只有用户点击保存时才写 change_logs 摘要。确认月计划是阅读态业务动作，只基于已保存内容生成承诺快照，不再承接未保存编辑。
章节结构：本节是 v1.4.14 的执行口径，不只是视觉原则。项目基线、月度计划、任务列表和专项管理页面都必须按本节区分“编辑态表格操作”和“阅读态业务动作”，避免执行时继续把每次单元格编辑或批量按钮误当成业务留痕动作。
```

v1.4.7.2 的模板生成必须按以下口径纳入本章：

```text
template_generate 是共享计划树的一条原子 operation，不是多条任务创建审计。
阅读态“生成任务”打开模板选择与预览，但生成结果仍进入编辑缓冲；保存前不写 change_logs，不写业务 operation_logs 摘要。
编辑态“智能展开”直接作为 template_generate 进入编辑缓冲；保存前可撤销/重做，不写 change_logs。
点击保存后，后端按“一批 N 行模板生成”写一组聚合摘要；不逐行、不逐字段、不逐模板节点写 change_logs。
同一次保存中如果包含 template_generate、update_cell、delete_row、move、indent/outdent，仍按一次共享表格提交写摘要，并在摘要里区分新增、覆盖、删除处置和字段调整数量。
模板来源、模板节点 ID、批次 ID、duplicatePolicy、previewRows 明细归 v1.4.6 data_lineage_links / data_lineage_events 或 v1.4.7.2 模板候选事实承载，change_logs 只写业务动作摘要。
月度计划页不得提交 template_generate，也不得把模板生成伪装成月度计划行新增；月度计划缺工序时只能提示跳转项目基线页或任务列表补齐。
```

确认回答：

```text
用户是否明确提交了这个业务状态？
```

确认不是审批。确认只表示用户完成当前动作。

典型确认：

```text
保存任务进度
任务达到 100% 时显式保存
发布项目基线
确认月度计划
关闭风险 / 问题
确认验收记录
确认图纸版本通过
确认材料封样或到货事实
```

确认动作系统自动记录：

```text
confirmed_by / changed_by / updated_by
confirmed_at / changed_at / updated_at
action_type
before / after 摘要
```

普通确认不要求用户填写原因。

### 5.2.1 确认动作清单

确认的核心是“用户明确提交当前业务状态”，不是“上级批准”。v1.4.14 统一补充以下确认动作，后续可以按业务需要删减，但实施口径必须先完整覆盖。

```text
任务确认：保存任务、保存进度、100% 完成保存、重新打开任务、删除未进入快照/治理链路的误录任务、批量删除/批量归档前确认
计划确认：发布基线、确认月计划、月计划关账、采纳或不采纳新一轮基线/月计划生成建议
条件确认：人员/设备/现场准备/一般协调类条件在首次 0 -> >0 进度时轻确认、手动确认开工条件满足、条件不适用/归档
阻碍确认：新增阻碍、关闭阻碍、重新打开阻碍、接受系统建议关闭
风险确认：风险关闭、风险重新打开、风险转问题
问题确认：问题关闭、问题重新打开
预警确认：知悉预警、解除/静音用户层面的预警提醒
里程碑确认：标记里程碑、取消里程碑；关键节点不提供手工标记/取消，由系统基于里程碑、关键路径、延期影响和计划治理自动识别
责任确认：责任人保存、责任单位选择、责任单位在维护入口归档/停用；不设置“责任恢复确认”
图纸确认：图纸版本通过、图纸版本作废、图纸替换确认
证照确认：证照办理事项状态更新、证照完成/作废确认
验收确认：创建验收任务、提交验收记录、验收通过、整改完成、验收归档、验收与普通任务关联调整
材料确认：材料计划保存、到货确认、封样确认、材料状态更新
导入确认：导入批次提交、导入结果确认、导入失败行忽略或重试
模板确认：当前只包含共享计划树 commit 保存模板生成结果；从项目沉淀模板、采纳模板更新建议属于未来模板管理后台，不进入普通前端确认主线
批量确认：批量删除、批量归档、批量合并主数据、批量清理已进入链路的数据均需要用户确认和后台留痕，但不走审批
```

确认的前端表现：

```text
已有保存按钮、确认按钮、关闭按钮、发布按钮继续承担确认语义
不因为确认而新增审批流
不要求普通确认填写原因
系统后台自动记录确认人、确认时间、来源和变更摘要
```

### 5.3 高权限治理与审批记录

高权限治理回答：

```text
这个动作是否超出普通编辑者权限，需要项目管理员执行或授权，并在后台留下统一治理记录？
```

v1.4.14 不建设完整 OA 审批流程。当前应用权限只有项目管理员和编辑者两级，因此执行口径是：

```text
编辑者提交或保存普通业务事实，不走审批
项目管理员通过后端治理能力执行高权限动作，直接生效并留痕；当前不代表新增前端管理员入口
确实需要保留“申请-批准-执行”历史的动作，才写 governance_approval_records
高权限动作不是日常入口，不新增审批中心、不让用户选择审批人
```

高权限动作边界：

```text
历史事实修正：实际开始/实际完成历史事实修正、进度快照补偿或回滚、编码历史纠偏；仅限数据错误、导入回填、系统迁移、管理员纠错
冻结后纠错：已确认月度计划、已关账月份、已发布基线快照、历史快照的纠错；常规计划调整不得修改历史快照，应通过任务列表实时变化和新一轮基线/月计划生成消化
后端治理修复：服务端回填、草稿锁异常释放、历史事实补偿、冻结后纠错；不作为普通前端入口
批量治理动作：批量删除、批量归档、批量合并主数据、批量清理已进入链路的数据；这些动作常见但影响大，需要确认和留痕，不走审批
权限动作：owner 转让、成员权限批量调整由项目管理员直接操作并写 operation_logs，不走审批
责任单位主数据合并或归档：用于治理责任单位重复和污染；无历史数据时可先只做归档/停用，合并能力后置
后续扩展动作：合同变更、设计变更、工程签证、索赔变更、成本变更、外部合规审批
```

执行口径：

```text
当前 v1.4.14 只把高权限边界和审批记录底座列清楚，先落地历史事实纠错、冻结后纠错、后端治理修复和批量治理动作的记录规则
合同/签证/设计/索赔/成本类变更当前应用未完整承载，先作为后续审批域预留，不在本章强行实现
能由 owner/admin 权限直接执行的后端治理修复，写 high_privilege_correction；仅为兼容旧来源时映射为 force_action，不制造完整审批流
确实需要“申请-批准-执行”的动作，才写 governance_approval_records；当前默认是 editor 提交、项目管理员审批，项目管理员自己执行不需要审批
```

审批不覆盖：

```text
任务日常新增 / 编辑 / 删除
任务进度保存
任务 100% 完成确认
任务计划开始 / 完成时间调整
批量删除 / 批量归档 / 批量合并主数据 / 批量清理链路数据
风险关闭
问题关闭
阻碍关闭
开工条件自动满足或轻确认
图纸 / 验收 / 材料普通状态更新
owner 转让 / 成员权限批量调整
```

统一审批体系说明：

```text
执行 v1.4.14 后，系统形成的是统一高权限边界和统一审批记录底座
它统一回答“哪些动作需要项目管理员授权、哪些动作需要确认、哪些动作只需要留痕”
它不是完整 OA 审批中心，不提供通用流程设计器、会签、抄送、组织级审批模板
前端不新增独立审批中心；历史事实纠错、冻结后纠错当前只落后端治理能力，已有确认/归档动作继续在原业务页面触发
```

### 6.2 change_logs 标准化

保留 `change_logs` 为业务变更留痕主表，不重建。

补强字段建议：

```sql
alter table change_logs
  add column if not exists action_type text null,
  add column if not exists action_group text null,
  add column if not exists request_id text null,
  add column if not exists before_snapshot jsonb not null default '{}',
  add column if not exists after_snapshot jsonb not null default '{}',
  add column if not exists metadata jsonb not null default '{}',
  add column if not exists visibility text not null default 'internal',
  add column if not exists retention_policy text not null default 'project_lifecycle';
```

兼容规则：

```text
老字段 field_name / old_value / new_value 继续保留
新写入同时写 action_type / action_group / before_snapshot / after_snapshot
旧记录读取时由 adapter 根据 field_name 生成 action_type
change_source 继续保留，但必须归一到标准枚举
不删除历史 change_logs
```

约束与幂等迁移规则：

```text
执行前必须检测 live schema 中 change_logs 的 entity_type / change_source check 约束
如果仍存在 057 原始窄枚举约束，必须先通过 pg_constraint 定位并安全 DROP，再补新字段和字典数据
不得直接追加只包含新标准值的 check 约束，否则历史 manual_adjusted / admin_force / approval 等旧值会导致迁移失败
新写入由服务层和 change_action_types 字典校验，数据库层如保留 check，必须同时兼容旧来源值和新标准来源值
全量迁移快照也必须同步更新，避免新环境初始化和增量迁移不一致
```

标准 `change_source`：

```text
system_auto：系统自动生成或自动修复
user_save：用户显式保存
user_confirm：用户确认、发布、关闭、归档
force_action：兼容既有强制类来源，后续仅用于后端治理修复或少量确需 owner/admin 直接兜底的动作；不得恢复为普通前台主动作
high_privilege_correction：项目管理员授权后的历史事实纠错或冻结后纠错
```

### 6.4 operation_logs 标准化

保留 `operation_logs` 为技术审计表，不并入 `change_logs`。

命名兼容规则：

```text

v1.4.14 不新增 audit_logs 表，不维护 operation_logs / audit_logs 两套并行审计模型
```

补强规则：

```text

operation_logs 可记录失败请求，change_logs 只记录业务事实成功变化
operation_logs 不作为 Dashboard / BI / 风险问题链统计来源
operation_logs 可用于管理员排查、安全审计、越权追踪和异常分析
```


### 6.5 审批 / 高权限记录

不新增大而全审批中心。

本章只为“历史事实纠错 / 冻结后纠错 / 后端治理修复 / 必要的申请-批准-执行动作”预留统一治理记录表。批量删除、批量归档、批量合并主数据、批量清理链路数据默认只做确认和留痕，不写审批记录：

```sql
create table if not exists governance_approval_records (
  id uuid primary key default gen_random_uuid(),
  project_id uuid not null references projects(id) on delete cascade,
  approval_type text not null,
  target_entity_type text not null,
  target_entity_id uuid not null,
  status text not null default 'pending',
  reason text null,
  requested_by uuid null references users(id) on delete set null,
  requested_at timestamptz not null default now(),
  decided_by uuid null references users(id) on delete set null,
  decided_at timestamptz null,
  decision text null,
  executed_by uuid null references users(id) on delete set null,
  executed_at timestamptz null,
  payload jsonb not null default '{}',
  result_change_log_id uuid null references change_logs(id) on delete set null,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),
  check (status in ('pending', 'approved', 'rejected', 'cancelled', 'executed'))
);
```

使用边界：

```text
月度计划 correction-request 可逐步迁入或适配到 governance_approval_records，但只承载极少数纠错治理，不作为常规调整入口
项目管理员直接执行的后端治理修复写 high_privilege_correction 或 force_action 兼容来源 + operation_logs，不写 governance_approval_records
只有确实存在 editor 申请、项目管理员批准、系统或管理员执行的过程时，才写 governance_approval_records
历史事实纠错和冻结后纠错必须写 high_privilege_correction；如果存在申请-批准-执行过程，再额外写 governance_approval_records 并绑定 result_change_log_id
批量删除、批量归档、批量合并主数据、批量清理链路数据只写 user_confirm + change_logs，必要时追加 operation_logs，不写 approval record
普通任务保存不写 approval record
普通风险问题关闭不写 approval record
已经被 119 移除的 delay_requests 不恢复
```

补充约束：

```text
governance_approval_records 必须补 project_id/status/target_entity/created_at 索引和 updated_at 触发器
状态流转只允许 pending -> approved/rejected/cancelled，approved -> executed/cancelled，不允许 executed 回退
reason 只用于历史事实纠错、冻结后纠错、后端治理修复或真正审批记录；普通保存、普通确认、普通关闭不得要求用户填写原因
治理记录写入失败时，对应高权限业务动作必须失败回滚，不能出现业务已改但无治理记录的状态
```

## 7. 写入规则

### 7.1 总规则

所有业务写入服务统一遵守：

```text
主业务写入成功后，写 change_logs
主业务写入失败，不写 change_logs
请求经过但无业务变化，只写 operation_logs
系统自动动作写 system_auto / algorithm_generated
用户显式保存写 user_save
用户发布、确认、关闭、归档写 user_confirm
后端治理修复写 high_privilege_correction；确需兼容旧来源时可映射为 force_action
历史事实纠错 / 冻结后纠错写 high_privilege_correction 或 approved_correction，具体取决于是否存在申请-批准-执行记录
导入写 imported
历史回填写 backfill
共享表格提交写入前必须统一跑后端校验和治理判断，不能因为来自复制粘贴、批量填充、批量改字段、批量删除而跳过领域规则
```

原子性规则：

```text
普通低风险字段编辑、普通确认、普通关闭的 change_logs 写入失败时，可以 warn 并降级，不阻断主业务，但必须进入 operation_logs 或后台异常记录
包含 template_generate、delete_row 转译、实际开始/实际完成自动写入、里程碑标记/取消、依赖重写、发布/确认/关账、高权限纠错、后端治理修复、历史事实纠错、冻结后纠错、真正审批执行、已进入链路数据的批量治理动作，留痕/治理记录写入失败时必须阻断主业务并回滚，或进入可靠 outbox 且保证最终写入；不得静默成功
涉及删除、取消、关闭、归档、停用、作废的动作，除 change_logs 外还必须绑定 v1.4.15 的 deletion_retention_events；删除保留决策写入失败时不得先改变业务事实
批量删除、批量归档、批量合并主数据、批量清理链路数据必须记录 affected_count、affected_entity_ids、引用关系摘要和 before_snapshot
已被任务、验收、图纸、证照、风险问题、来源映射引用的关键数据，优先归档/停用/合并，不允许普通硬删除绕过 v1.4.11 和 132 删除保护
operation_logs 仍可记录请求级技术审计，但不替代 change_logs 的业务摘要；业务页面不展示 operation_logs
```

### 7.2 action-level 留痕，不做 cell-level 审计

与 v1.3.5.3 保持一致：

```text
不记录每一次光标移动
不记录每一次单元格编辑草稿
不记录每一次复制、粘贴、拖拽预览、批量选择
不记录保存前撤销/重做；撤销/重做属于表格本地编辑历史
只在保存、发布、确认、关闭、归档、后端治理修复、高权限纠错等业务动作落地时留痕
一次保存包含多个单元格、多行、复制粘贴、批量填充、层级调整或批量删除时，写一组变更摘要
业务摘要必须包含影响条数、关键对象、关键字段变化、before/after 摘要；批量删除、批量归档、批量清理链路数据必须额外记录引用关系摘要和 before_snapshot
保存后撤销不是简单回滚数据库，而是新的业务动作，必须重新校验权限、状态和 v1.4.15 retention decision
任务列表 / Gantt 不再允许“单元格失焦即业务落库、粘贴即逐条创建、批量填充即逐条 PATCH、删除行即逐条 DELETE”作为共享表格主线；这些动作必须先进入保存前编辑缓冲，用户点击保存后统一提交和留痕
项目基线、月度计划、任务列表的撤销/重做必须作用于保存前编辑缓冲，不作用于已保存数据库事实
```

示例：

```text
用户在 PlanningTreeTable 里连续改 20 个单元格，点击保存后写 1 组变更摘要
用户在 PlanningTreeTable 里复制粘贴 20 行、批量删除 5 行，保存后按一次提交写 affected_count、affected_entity_ids 和 before/after 摘要
用户在任务列表里把 3 个任务进度改到 100%，保存前不写实际完成和 change_logs；点击保存后后端统一确认完成、写 actual_end_date、进度快照和摘要
用户在月度计划里批量顺延或批量目标进度，表格内先表现为未保存更改；点击保存时统一提交，不在每次批量按钮点击时单独写治理日志
用户发布项目基线，写 baseline.published，并由 task_baselines / task_baseline_items 保存版本详情
用户确认月度计划，写 monthly_plan.confirmed，并由 monthly_plans / monthly_plan_items 保存承诺快照
用户保存任务进度，写 task.progress_saved，并由 task_progress_snapshots 保存每日进度事实
```

### 7.3 快照和变更记录的分工

```text

task_baseline_items：记录项目基线发布时的计划快照
```


### 8.3 需要高权限授权或治理记录的动作

这些动作必须由项目管理员执行或授权，并写纠错/治理留痕；只有确实存在“申请-批准-执行”过程时才写 `governance_approval_records`：

```text
已确认月度计划、已发布基线、已关账月份的历史纠错
实际开始 / 实际完成 / 进度快照等历史事实纠错
后端治理修复，包括服务端回填、草稿锁异常释放、冻结后纠错补偿
```

用户操作口径：

```text
能自动判断权限的，不让用户选择审批人
能后台记录原因的，不要求用户填写原因
确实需要原因的，只限历史事实纠错、冻结后纠错或后端治理修复类动作
普通 editor 看不到治理修复入口
owner / admin 执行治理修复后，系统按 v1.4.13 触达规则通知受影响人
owner / admin 自己直接执行治理修复时，不制造审批流，只写 high_privilege_correction / force_action 兼容来源 + operation_logs
editor 申请且 owner / admin 批准后执行时，才写 governance_approval_records，并在执行成功后绑定 result_change_log_id
高权限留痕、治理记录或通知触达写入失败时，后端必须返回业务错误，不得静默成功
批量删除、批量归档、批量合并主数据、批量清理链路数据不走审批，但必须有确认和留痕
```

高权限动作入口清单：

```text
已关账月份的历史纠错：当前不新增普通前端入口；只落后端治理服务和只读复盘能力。确需处理时由 owner/admin 通过后端治理能力执行，未来可接管理员后台。
实际开始 / 实际完成 / 进度快照等历史事实纠错：当前不进入任务编辑弹窗，不允许普通用户直接改；由后端治理能力执行并写 high_privilege_correction。
月末关账：不是高权限兜底动作，而是确认/归档动作。数据不完整时表达为“按当前数据确认关账”或“确认归档，数据待完善”，写 user_confirm + 月度关账摘要，不作为 force_action 主线。
计划草稿锁：不提供“强制解锁计划草稿”前台入口。草稿锁、超时释放、冲突合并属于后端协作能力；异常释放只作为 operation_logs / 后端治理修复记录。
开工条件：不提供“强制解除关键开工条件”入口。普通页面只保留“确认已满足 / 标记不适用 / 删除误录”，后台治理可修复状态或归档误录。
删除已被引用的关键主数据：不在 v1.4.14 定义入口和处置方式，交由 v1.4.15 删除、关闭、归档与历史保留体系统一判断；v1.4.14 只负责记录最终动作摘要。
```

权限边界必须明确：

```text
不进入 approval record 不等于低权限动作。批量删除、批量归档、批量合并主数据、批量清理链路数据、历史事实纠错、冻结后纠错、后端治理修复等动作，必须由 owner/admin 或明确授权角色执行，并在服务端校验权限。
这些动作默认写 change_logs 和 operation_logs；确实存在“申请-批准-执行”过程时，才额外写 governance_approval_records。
高风险动作的 change_logs / governance_approval_records 写入失败时，主业务动作必须失败回滚，不能先改事实再丢失治理留痕。
批量动作必须记录 affected_count、affected_entity_ids、引用关系摘要、before_snapshot / after_snapshot 或等价摘要，避免只留下“批量处理完成”的空日志。
```

## 多公司空间与数据隔离统一口径

本文件执行时必须承接 `v1.4.20 权限角色与协作体系执行方案` 的多公司空间要求。除非本文件明确声明为 `system_seed`、全局字典或演示样例数据，否则所有项目级数据都必须先归属于项目，再通过项目解析到所属公司。

```text
所有新增表：优先包含 project_id；确属公司级数据时包含 company_id；确属系统公共数据时标记 scope = system_seed / global_dictionary。
所有查询：先按 currentCompanyId / company_id 隔离，再按项目权限过滤，不允许前端二次过滤替代后端隔离。
所有汇总：公司级汇总只统计当前公司项目；项目级汇总只统计当前项目；演示项目不进入真实公司汇总和真实项目统计。
所有引用：禁止跨公司引用任务、工程对象、范围维度、责任单位、图纸、证照、验收、风险、问题、预警、计划、模板沉淀和经验数据。
所有模板 / 经验数据：系统公共种子可跨公司复用；公司沉淀模板、公司经验工期、公司历史数据只能在当前公司内使用。
所有旧数据：没有 company_id 的历史数据在迁移时归入默认公司，并保留兼容读取；不得因为补公司空间而删除旧对象。
```
