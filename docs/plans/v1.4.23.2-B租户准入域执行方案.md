> 架构归属：本文件建的是 v1.4.23.1 §4.7.1 的**「底座·组织权限」单元的商业化延伸**（母文件 3.4.2 只是 `commercial_foundation` 的 registry 分组标签）。v1.4.23.1 §4.7.3 已写明"商业化补强进入 v1.4.23.2"。

> 一句话职责：**把底座·商业化从空壳建成可执行——能区分 free/paid、能 enforce active project 上限、能放行免费钩子、能审计停用、订单/支付事件/人工开通闭环建好默认关，且不污染业务主链**。功能全建、计量全程记、拦截开关默认关（先免费后一键启用）。

## 0. 范围口径（先划死，避免膨胀也避免缺斤短两）

**本文件做（全建，拦截默认关）：** 租户商业状态机 + active project quota guard + 免费钩子白名单 + 升级提示 + 商业状态审计 + 高危操作弹窗二次确认 + 收款闭环最小后端（订单表、支付事件表、人工开通、默认关事件适配层、开关开启后 verified paid 事件联动开通，母文件 4.9）。
**本文件不把真实外部支付网关当完成项：** 微信/支付宝 provider 签名校验、官方 webhook、自动对账差异告警、发票/收据归档属于本阶段后的自动收款增强；冷启动收费验证先走人工收款 + 后台改 tier + 审计。
**本文件不做：** 运维/灾备/告警/分层健康（移交 v1.6，母文件第 9 节）、业务缺陷（v1.4.23.1 C-17/18）、前端呈现（v1.5）。

**核心口径——总开关 + 全程计量（承接母文件 4.1）：**
- **功能全建**：状态机、quota、付费档、订单/支付事件/人工开通闭环一次建齐；真实外部网关对接不阻塞本阶段。
- **拦截默认关**：全局开关 `billing_enabled` 默认 `false`；关闭时所有公司视同最高档、不撞墙、不暂停。启用只改开关，无需再开发。
- **计量全程记**：开通时间、active 项目数、用量从注册第一天就记，无论开关开关——这是"先免费、后收费"不留历史债的前提。

理由：本产品上线先免费，用户量起来再启用收费。"先免费"≠"先不做"，而是"建好、关着、一直在记"。收款闭环同理：订单和支付事件先建好默认关，冷启动期个别付费走人工开通（转账后改 tier）；真实微信/支付宝自动收款等确认有付费需求后再接。

## 1. 当前真实基线（核查于本轮代码）

| 事实 | 核查结果 | 含义 |
|---|---|---|
| `companies` 类型 / plan / tier / subscription / quota / seat 字段 | `server/src/types/db.ts` **完全不存在**（grep 无任何命中） | 租户商业模型是 greenfield，从零建表，无历史兼容负担 |
| 项目创建入口 | `routes/projects.ts:769` `router.post('/')`，以及 `:793` `router.post('/with-id')`（seed/test 用） | quota guard 的唯一插桩点；两处都要拦 |
| 创建时公司解析 | `resolveProjectCreationCompanyId(req.user!.id, getRequestCompanyId(req))` 然后 `supabase.createProject({ company_id })` | guard 应在 `createProject` **之前**、拿到 companyId **之后**插入 |
| 现有权限中间件 | `middleware/auth.js` 的 `authenticate / requireProjectMember / requireProjectOwner` | quota guard 是**独立一层**，挂在业务权限**之后**（6.2 执行项 3：业务权限 → 商业 guard） |
| 角色模型 | `auth/types.ts`：GlobalRole = company_admin / regular；ProjectPermissionLevel = owner / editor | tier 升级动作限 company_admin；guard 不改既有角色 |

> **关键观察**：项目创建走的是 `routes/projects.ts` 的 POST `/` 和 `/with-id`，公司已由 `resolveProjectCreationCompanyId` 解析出来。这是 active-project quota 唯一需要设卡的地方——不必扫全部 ~72 个挂载点，**创建项目本身就是计价主轴的 enforcement 点**。

## 2. 能力面契约（落地 v1.4.23.2 3.4.4「底座·商业化」契约）

本能力面对外保证三条，每条挂 CI 校验：

1. **计价主轴 = active project**：项目创建受 active project 上限约束；seat/storage/export 不作计价轴（4.1 已立硬口径，禁止 per-seat）。
2. **免费钩子不可被 gate**：免费档必须放行"1 个 active 项目的完整建模 → 生成计划 → 录进展"闭环。guard 只拦"创建第 2 个及以上 active 项目"，不拦第 1 个项目内的任何业务动作。
3. **停用/到期/超限可审计、可恢复、可解释，不靠前端隐藏**：商业状态变更写审计；被拦截返回可解释的升级提示（错误码 + 文案 + 升级路径），不是静默 403。

**依赖方向合规（v1.4.23.1 C-16.1 / §4.7.2）**：本单元可只读消费主执行环的"项目数/成员数"计量事实；**主执行环及其它业务单元不得反向依赖本单元**——业务代码里不得出现"没付费就少算指标"。gating 只在创建入口的 guard 层，不渗进业务算法。这是 C-16.1 "禁止底座反向被业务依赖以改变结论"方向的实例。

## 3. 数据模型（greenfield，从零建）

**3.1 商业字段（新增迁移，建议独立 `company_commercial` 表）**

```text
company_commercial（1:1 关联 companies，独立表避免污染业务列）：
  plan_tier            free / pro            -- 计价档，默认 free
  commercial_state     trial / active / suspended / expired / archived  -- 状态机，默认 trial
  active_project_limit int                   -- 该档 active 项目上限；free 默认 1（数字留白，结构先定）
  billing_enabled      bool                  -- 总开关，默认 false；关闭时本公司视同最高档、不撞墙
  onboarded_at         timestamp             -- 开通时间，注册即写（计量起点，先免费也要记）
  plan_started_at / plan_expires_at          -- 续费/到期
  updated_by / updated_at                    -- 谁改的，审计用
```

- **总开关 billing_enabled**：可设全局默认（环境级）+ 公司级覆盖。冷启动先免费 = 全局默认 `false`；guard 见 `false` 直接放行（仍记计量）。启用收费 = 改默认为 `true`，老用户可逐个/批量豁免。
- **计量字段 onboarded_at + active 项目数**：从注册第一天写，与 billing_enabled 无关——这是"先免费后收费"不留历史债的物理保证。

建议用独立 `company_commercial` 表而非给 `companies` 加列：契约「主执行环不依赖商业层」在物理层也成立，业务查 companies 不会顺手读到商业字段。

**3.2 商业状态审计（新增）**

```text
company_commercial_audit：
  company_id / from_state / to_state / from_tier / to_tier
  reason / actor_user_id / created_at
  -- 复用 operation_logs / change_logs 亦可（6.2 执行项 5）；新表更清晰
```

**3.3 active project 计数口径**
`active_project_limit` 约束的是 **active** 项目数，需先定义"active"：建议 = 未 archived/deleted 的项目。计数来自主执行环的项目事实（只读，不反向依赖商业层），guard 调用一个 `countActiveProjects(companyId)`。

## 4. quota guard（核心 enforcement）

**4.1 插桩点（唯一）**
`routes/projects.ts` 的 `POST /`（:769）与 `POST /with-id`（:793）。位置：`resolveProjectCreationCompanyId` 之后、`supabase.createProject` 之前。

```text
1. authenticate（已有）
2. requireXxx 业务权限（创建无 project 级权限，但有 company 归属）
3. 【新增】commercialGuard.canCreateProject(companyId)：
     - 先记计量（active 项目数等），无论下面是否放行
     - 若 billing_enabled=false → 直接放行（冷启动先免费态；计量已记）
     - commercial_state ∈ {suspended, expired, archived} → 拒绝（状态拦截）
     - countActiveProjects(companyId) >= active_project_limit → 拒绝（quota 拦截）
     - 否则放行
4. createProject（原逻辑）
```

> **总开关位置（承重）**：`billing_enabled` 判断在最前、计量在更前。这保证两件事——① 先免费期所有创建畅通（开关关）；② 但计量始终在记（不留历史债）。启用收费只需把开关翻 true，guard 代码一行不改。

**4.2 免费钩子白名单（契约 2 的落地）**
guard **只在创建入口**生效。第 1 个项目创建成功后，该项目内的建模/生成计划/录进展/Gantt 等所有业务写动作**一律不经过 commercial guard**——它们属主执行环，受 quota 影响即违反 C-16.1 依赖方向。这从架构上保证"免费钩子不可被误 gate"。

**4.3 被拦截的响应（契约 3 的落地）**
返回统一错误契约（对齐 v1.4.23.2 4.7 错误码统一）：稳定错误码（如 `COMMERCIAL_PROJECT_LIMIT_REACHED` / `COMMERCIAL_STATE_SUSPENDED`）+ 可读文案 + 升级路径，前端据此弹升级提示。不得只靠前端隐藏"新建项目"按钮（6.2 执行项 4）。

**4.4 升级动作**
改 tier / 调 limit / 续费的接口限 `company_admin`，每次变更写 `company_commercial_audit`。冷启动期收款人工：管理员转账后由后台改 tier，状态机和审计照走。

## 5. 执行步骤

1. 新增迁移：`company_commercial`（3.1，含 `billing_enabled` 默认 false、`onboarded_at` 注册即写）+ `company_commercial_audit`（3.2）。默认值保证存量公司 = free + 上限 1（或给存量一次性宽限，见第 7 节）。

3. 在 `routes/projects.ts` POST `/` 与 `/with-id` 插入 guard（4.1，开关关时直接放行但仍记计量）。
4. 实现统一错误码 + 升级提示响应（4.3）。
5. 升级/续费接口（company_admin，4.4）。
6. **收款闭环（母文件 4.9，建好默认关）**：订单表 + 支付事件表 + 默认关闭的 provider 事件适配层；`billing_enabled=false` 时只留痕不触发开通；`billing_enabled=true` 且事件为 verified paid 时联动 `changeTier`。冷启动期人工开通即可；微信/支付宝官方签名 webhook、自动对账差异告警、发票/收据归档不作为本阶段完成判定。

8. 前端：捕获 `COMMERCIAL_*` 错误码 → 升级提示 UI（与 v1.5 冷启动激活态/付费墙呼应；本步可延后到前端批次，后端先可用）。
9. CI 校验四条契约：① project 创建入口确有 guard（扫描 POST `/` 链路含 commercialGuard）；② 依赖方向门禁确认主执行环不 import 商业层（复用 A 的 C-16.1 依赖方向扫描）；③ 商业状态变更必写审计（契约测试）；④ `billing_enabled=false` 时所有创建畅通且计量仍写（开关契约测试）。

## 6. 验收标准

1. `billing_enabled=false`（先免费态）：所有公司建任意数量项目畅通、不撞墙，但 active 项目数/onboarded_at 已全程记录（总开关 + 计量契约）。
2. `billing_enabled=true` 后，free 档公司仍能完整完成"建第 1 个项目 → 生成计划 → 录进展"，全程不被拦（免费钩子成立）。
3. 开关开启后，free 档公司创建第 2 个 active 项目被拦，返回 `COMMERCIAL_PROJECT_LIMIT_REACHED` + 升级路径，非静默失败。
4. suspended/expired 公司创建项目被拦并可解释；恢复后可继续（可恢复），数据不删。
5. tier/limit 变更只 company_admin 可做，且每次写 `company_commercial_audit`。
6. 计价主轴是 active project；代码中无 per-seat 计费路径。
7. 主执行环代码无 import 商业层（C-16.1 依赖方向门禁通过）。
8. guard 只在 project 创建入口，未渗入任何业务写动作（白名单契约成立）。
9. 收款闭环最小后端建好且默认关：人工开通可跑通（管理员改 tier → 状态机+审计正确）；订单/支付事件可留痕；`billing_enabled=false` 时 verified paid 事件不自动开通；`billing_enabled=true` 且 verified paid 事件可联动开通。
10. 高危操作有弹窗二次确认 + 审计。

## 7. 边界与诚实声明

- **存量公司迁移**：上线 guard 前需决定存量公司默认档。建议存量一次性置为宽限档（如 active_project_limit = 当前已有项目数，避免老用户一升级就超限被锁）；新注册才默认 free=1。此决策需在迁移方案中写死，不可静默把老用户锁死。
- **"active 项目"定义**未在现有代码中存在统一口径，本文件给出建议（非 archived/deleted），落地时需与主执行环的项目状态字段对齐，避免又造一套口径。
- **收款闭环建好但默认关**：本文件含订单、支付事件和默认关事件适配层，但 `billing_enabled=false` 期间不自动开通；冷启动期走人工开通。"能收费"指人工收款 + 状态机 + 审计 + 事件留痕可跑通，不等于真实微信/支付宝自动收款已接入。
- 具体上限数字（free 给 1 还是 2、pro 给几个、留存期）需用真实试用数据压测，本文件只定**结构**（按项目 gate、钩子=建计划、墙=第 2 项目/导出），不拍数字。付费分档待文件全部改定后单独商讨。
- 插桩点、字段缺失、角色模型均为本轮核查事实；随代码演进以实际为准。
