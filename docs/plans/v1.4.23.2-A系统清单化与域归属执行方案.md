# v1.4.23.2-A 系统清单化与单元归位执行方案

> 2026-06-01 final range-tree boundary (authoritative): phase / section / building / basement / floor / physical_zone / functional_area.
> No production history or existing users need migration. `/api/scope-dimensions and scope_dimensions / project_scope_dimensions adapters` are removed compatibility surfaces and must not return as live write paths.

> 派生自 `v1.4.23.2后端商业化补强与AI可维护体系执行方案.md` 第 6.1 阶段（系统清单化）与第 3.4 节（单元归位模型，已对齐 v1.4.23.1 §4.7）。
> **直接落地 v1.4.23.1 的 C-16 / C-16.1 / C-16.2 三条门禁**：本文件不另立架构口径，归位目标是 v1.4.23.1 §4.7.1 的 **7 个架构单元**（主执行环 / 学习治理环 / 预测桥 / 横切履约 / 验收事实子通道 / 底座·组织权限 / 底座·平台运行观测）。
> 一句话职责：**把现存后端全部入口扫出来、各归一个 §4.7.1 单元、清掉反向依赖违规（C-17.45）、并让归属是代码生成而非人手维护**——没有这张地图且单向依赖未修，商业化补强不知道该往哪设卡，AI 维护读到的是过期且已被违反的边界。

## 0. 为什么这份必须先做

`v1.4.23.2` 3.4 已把 `domain_registry` 的 `runtime_scope` 对齐为 v1.4.23.1 §4.7 的 7 单元分组；其依赖方向以 **C-16.1** 为权威门禁、归位以 **C-16.2** 为权威扫描。但这些门禁与契约校验**都需要一份"成员已归位 + 反向依赖已清零"的真实清单才能断言**：

- 商业化（底座）契约要求"所有项目级写入口过 quota guard"——不先列出哪些 route 是项目级写入口，无从校验。
- 描述分析单元契约要求"被 v1.5 消费的能力有 production-ready 标注"——不先把 service 归位，C-13 清单挂不上 registry。
- C-16.1 的依赖方向门禁——不先有归位，静态扫描没有判定依据；且 **C-17.45 已记账"service 反向 import 10+ routes、依赖门禁不存在且已被违反"**，必须由本文件的扫描器清零，否则"底座单向被依赖"不是已兑现保证。

因此执行序锁定：**A（本文件：清单化 + 单元归位 + 依赖方向门禁 + 清 C-17.45）→ B（租户准入，底座·商业化）→ 平台契约校验 → 其余 P0**。先有地图、先修单向，再设卡。

## 1. 当前真实清单基线（核查于本轮代码，非估算）

| 入口类型 | 真实位置 | 数量（核查值） | 初始输入源（registry 抽取起点） |
|---|---|---|---|
| route 挂载 | `server/src/index.ts` 的 `app.use('/api/...')` | ~72 个挂载点（行 272–372，之后无 `/api` 挂载） | `index.ts` |
| route 文件 | `server/src/routes/*.ts` | ~80 个文件 | 同上，挂载点 → 文件映射 |
| service | `server/src/services/*.ts` | ~250 个文件 | 目录扫描 |
| job | `server/src/jobs/*.ts`，经 `server/src/scheduler.ts` 装配 | 24 个 job | `scheduler.ts` import + `jobs/` 目录 |

> **量级即论据**：~250 个 service 无法靠人脑记住归属，这正是"AI 可维护"必须先清单化的原因。也意味着**单元归位不能纯人工逐个填**（250 行手填第二天就漂移），必须用"扫描 + 启发式预归类 + 人工只裁决歧义项"的混合法（见第 3 节）。

## 2. 产出物（全部为代码生成 + CI 校验，禁止人工副本）

落地 `v1.4.23.2` 3.4.4 的硬规则。产出四件：

1. **registry 生成器**（`scripts/` 下新增）：从第 1 节的输入源抽取，产出机读 registry（JSON 或 TS），字段对齐 `v1.4.23.2` 5.4。
2. **单元归位声明文件**：每个 route/service/job 标注所属的 §4.7.1 单元，并附带 `runtimeScope` 分组标签（`business_core / governance / platform_foundation / commercial_foundation`）。声明可人写，但**"成员存在与否"必须来自扫描**——声明里有、代码里没有 → 标 deprecated；代码里有、声明里没有 → CI 阻断。
3. **unknown-entry 扫描门禁**（接入 CI）：新增 route/service/job 未归位即阻断（落地 6.1 执行项 6 + C-16.2）。
4. **依赖方向门禁**（接入 CI = C-16.1 的实现载体）：静态检查 import 是否违反 v1.4.23.1 §4.7.2 的允许方向；**必须先清掉 C-17.45 记账的存量反向 import（service 反向 import 10+ routes），再把门禁设为阻断**。先实现对商业化补强最关键的两条：底座 ↛ 业务主链、业务主链 ↛ 商业层（见母文件 3.4.3）。

## 3. 单元归位方法（混合法，不纯手工；归位目标 = v1.4.23.1 §4.7.1 的 7 单元）

> 归位目标是 v1.4.23.1 §4.7.1 的 **7 个架构单元**，不是早期草稿那套"四标签分组"。母文件 3.4.2 的 `runtime_scope` 分组标签只供 registry 字段用；此处归位到细粒度单元，因为 C-16.1 守护的正是单元间边界（如预测桥 ↛ 写 actual、横切 ↛ 抢写执行事实）。

**3.1 route 归位（~72 个，最可处理）**
按挂载路径前缀 + 资源语义启发式预归类到 7 单元，人工只裁决歧义：

| 启发式规则 | 预归单元（§4.7.1） | 示例（来自真实挂载） |
|---|---|---|
| `/api/auth/*`、`/api/members`、`/api/invitations`、`/api/workspace`、`/api/transfer-owner` | 底座·组织权限 | 登录鉴权、成员、邀请、工作台（v1.4.23.1 §4.7.1 已明确归此） |
| `/api/jobs`、`/api/health`、`/api/status-dictionary`、`/api/client-errors`、`/api/performance-reports` | 底座·平台运行观测 | jobsRouter、健康检查、状态字典、错误/性能上报（§4.7.1 已明确） |
| `/api/planning/algorithm-seeds`、`/api/admin/*-governance`、`/api/admin/duration-*` | 学习治理环 | algorithmSeedsRouter、各 governance router |
| `/api/duration-suggestions`、`/api/critical-paths`、`/api/schedule-acceleration` | 预测桥 | 只读预测，**不得写 actual/baseline**（C-16.1 方向） |
| `/api/project-materials`、`/api/construction-drawings`、`/api/drawing-*`、`/api/certificate-*`、`/api/pre-milestones` | 横切履约 | 只写条件/阻碍/关联投影，不抢写执行事实 |
| `/api/acceptance-*` | 验收事实子通道 | 经 AcceptancePass 合法写 actual 的受治理第二入口 |
| `/api/projects`、`/api/tasks`、`/api/risks`、`/api/progress-deviation`、`/api/dashboard`、`/api/reports`、`/api/health-score` 等 | 主执行环（建模/计划/执行事实/描述分析/行动闭环 5 段） | 占多数；按 §4.7.1 五段细分 |

> 注：`/api/health-score` 按 §4.7.1 存量归位补充明确属"描述分析消费面"，与运维 `/api/health` 区分；`/api/jobs` 标运维边界。这些 v1.4.23.1 已裁决，本文件直接采用，不重判。

**3.2 service 归位（~250 个，量最大）**
用命名前缀聚类预归类到 7 单元，大幅压缩人工量：

| 命名前缀/特征 | 预归单元 | 真实样本 |
|---|---|---|
| `algorithm*`、`*PolicyReplay*`、`*Governance*`、`*Calibration*`、`*ShadowReplay*`、`durationContextPolicy*` | 学习治理环 | algorithmAsset*（20+）、constructionDependencyReplayCalibration* |
| `durationSuggestion*`、`taskDurationForecast*`、`projectCriticalPath*`、`projectRemainingDurationForecast*`、`scheduleAcceleration*` | 预测桥 | 只读读模型，C-16.1 禁其写 actual/baseline |
| `material*`、`drawing*`、`certificate*`、`preMilestone*` | 横切履约 | 只写条件/阻碍/投影 |
| `acceptance*`（`acceptanceTaskSync`、`acceptanceFlow`） | 验收事实子通道 | 合法写 actual 的受治理通道 |
| `jobRuntime`、`migrationRunner`、`realtimeServer`、`readModelWarmup`、`requestBudget`、`supabaseService`、`dbService` | 底座·平台运行观测 | 纯技术底座 |
| 业务事实/结论：`progressDeviation`、`projectHealth`、`responsibilityInsight`、`projectExecutionSummary`、`metricRegistry` 等 | 主执行环（执行事实 / 描述分析段） | 占多数 |
| 商业运营（**当前几乎为空，B 阶段才建**） | 底座·组织权限（商业化延伸） | 现状无 |

**3.3 共享基础设施的归属裁决（唯一归属硬规则会撞上的现实）**
`dbService`、`projectExecutionSummaryService`、`metricRegistryService` 等被多单元调用。裁决规则：**按"它是什么"归属，不按"谁调用它"**——
- 纯技术底座（dbService、jobRuntime、migrationRunner）→ 底座·平台运行观测，按 §4.7.2 允许被各单元依赖。
- 产出业务真值的（projectExecutionSummaryService、metricRegistryService）→ 主执行环·描述分析，其它单元**读它的输出**合法（C-16.1 允许的方向）。
- 这样"唯一归属"成立，"被多单元使用"通过依赖方向（C-16.1）而非多重归属解决。

**3.4 job 归位（24 个）**
按其写入的事实类型归到 §4.7.1 单元：`riskStatisticsJob/criticalPathRefreshJob/responsibilityAlertJob` → 主执行环；`algorithmSeedCandidateDiscoveryJob/durationContextPolicyLearningJob/forecastResidualOverlayProductionJob/*PolicyAutoPublishJob` → 学习治理环；`projectWeatherForecastJob/projectClimateProfileJob` → 预测桥支撑或学习环（按其写入物裁决）；`dataRetentionJob/deletionRetentionCleanupJob/officialHolidayCalendarJob` → 底座·平台运行观测。

## 4. 执行步骤

### 4.A 迭代一：清单化 + 单元归位（本文件主体）

1. 写 registry 生成器，从 `index.ts` / `scheduler.ts` / `jobs/` / `services/` / `metricRegistryService` / `migrations/` 抽取，产出机读 registry。
2. 跑生成器得到全量清单：~72 route 挂载、~80 route 文件、~250 service、24 job。
3. 按第 3 节启发式预归类，产出单元归位声明初稿；人工只裁决预归类置信低的歧义项（重点是 auth/members/workspace 这类跨 platform/commercial 的边界）。
4. 实现 unknown-entry 扫描：代码有、registry 无 → 阻断。接入 CI（`.github/workflows/deploy.yml`）。
5. 实现 forbidden 依赖扫描的前两条（business_core ↛ commercial_foundation、platform_foundation ↛ business_core），接入 CI。
6. 把 business_core 成员的 `production_readiness_source` 字段接到 `v1.4.23.1-A` 的 C-13 活表 / 当前状态索引；未在 A 文件中明确标注 `production-ready` 的能力，一律不得默认 production-ready。
7. registry diff 接入新增能力流程：每次新增 route/service/job 先生成 registry diff，再跑 unknown-entry + 依赖扫描。

### 4.B 迭代二：deprecation 回流扫描（now_safety，承接母文件 9.3）

> 为什么并进 A 而非单起文件：deprecation_registry 已由母文件 5.4 定义字段、6.4 步骤 3 定义扫描要求、7.3 定义具体门禁目标；它的扫描器与 A 的 unknown-entry / 依赖扫描**共用同一套 registry 抽取与 CI 接入基础设施**，单起文件会重复地基。本节只把母文件已有的 deprecation 要求**算子化**成 A 扫描器的一个新增模式，不重新定义概念。
>
> 为什么是 now_safety：AI 一旦开始改代码，缺这个扫描会把废止对象接回主链路（母文件 5.3 禁止项、9.3）。它不依赖付费或规模，与 4.A 同属地基。

8. 生成 `deprecation_registry`（字段对齐母文件 5.4：`deprecated_surface / replacement_surface / forbidden_import_or_route_pattern / deletion_migration_ref / scan_test_ref`）。初始废止面**直接取自母文件 7.3 已点名的目标**，不另立清单：
   - 旧 scope 对象与字段：`zone / professional / subproject / custom`、`zone_object_id / professional_object_id`、`scope_dimensions / project_scope_dimensions`、`/api/scope-dimensions`（与 v1.4.23.1 / v1.4.22.3 的 range-tree 边界一致）。
   - 旧 AI 命名链路：`ai-duration / ai-schedule` 及任何 AI 助手/LLM 包装 route（母文件 3.3 去 AI 化、7.3）。
   - 旧兼容 route / 旧 service facade / 旧 seed 兼容壳（母文件 6.4 步骤 3）。
9. 实现 deprecation 扫描器（作为 A 扫描器的新增模式）：对每个废止面断言 **0 live consumer**——无 runtime import、无 active route 挂载、无新写入链路引用。命中即阻断。
10. 接入 CI，对齐母文件 7.3 门禁原文："deprecation scan 对旧 scope、旧 ai-duration / ai-schedule、旧兼容 route 返回 0 live consumer"。
11. 与依赖方向门禁（4.A 步骤 5 = C-16.1）协同：依赖方向门禁管"单元间不该调的方向"，deprecation 扫描管"废止物不该被任何单元调"——两者同一基础设施、不同规则集。

## 5. 验收标准

### 5.A 迭代一验收（落地 C-16 / C-16.1 / C-16.2）

1. 每个现存 route/service/job 都在 registry 中且归位到 v1.4.23.1 §4.7.1 的唯一单元；无"隐式存在"（= C-16 归属门禁 + C-16.2 存量归位扫描）。
2. registry 是生成产物，跑生成器可重现；不存在人工维护的副本（人工只维护"单元归位声明"，且声明与扫描结果对账）。
3. unknown-entry 扫描在 CI 中可阻断新增未归位入口（C-16.2）。
4. 依赖方向门禁（C-16.1）在 CI 中可阻断违反 §4.7.2 方向的 import；**且 C-17.45 记账的存量反向 import（service 反向 import 10+ routes）已清零**——清零前门禁可先报告、不设阻断，清零后转阻断。
5. 主执行环·描述分析成员的 production_readiness_source 已接 `v1.4.23.1-A` 的 C-13 活表 / 当前状态索引；未明确 production-ready 的成员不伪装 production-ready。
6. 共享基础设施按 3.3 规则归属，唯一归属与被多单元使用不冲突。
7. 本文件产出的 registry 成为 B 阶段（底座·商业化 quota guard 选址）和平台契约校验的输入。

### 5.B 迭代二验收

8. `deprecation_registry` 已生成，字段对齐母文件 5.4，初始废止面覆盖 7.3 三类目标（旧 scope / 旧 AI 命名 / 旧兼容 route）。
9. deprecation 扫描在 CI 中对三类废止面返回 **0 live consumer**，命中即阻断（落地母文件 7.3 门禁原文）。
10. 新增能力的 registry diff 流程（4.A 步骤 7）同时跑 deprecation 扫描，防止 AI 误接废止对象。

## 6. 边界与诚实声明

- 本文件**只做清单化、单元归位与依赖方向门禁**，不实现 quota/状态机（B 阶段）、不实现备份/告警/registry SSOT 的运维闭环（按 v1.4.23.2 触发条件矩阵推进）。
- 单元归位以 **v1.4.23.1 §4.7.1 的 7 单元**为唯一目标，不自造架构口径；母文件 3.4.2 的 `runtime_scope` 四标签只是 7 单元的粗粒度分组，供 registry 字段用。
- 启发式预归类**不保证一次到位**；歧义项（尤其 auth/members/workspace、跨业务与治理的 service、预测桥 vs 描述分析的边界）需人工裁决并在 registry 留裁决理由。v1.4.23.1 §4.7.1 已裁决的存量归位（如 health-score 属描述分析、jobs 属运维）直接采用。
- `production_readiness_source` 依赖 `v1.4.23.1-A` 的 C-13 活表 / 当前状态索引；本文件不替它生成 production-ready 判定，只挂载来源字段。
- **C-17.45 是本文件的前置债务**：首版 `guard-architecture-boundaries` 已关闭“完全无机器门禁 / service 反向 import routes”缺口，但更细颗粒的七单元允许依赖矩阵仍需持续扩展；后续完成记录统一回填 `v1.4.23.1-A`，不得把"单向依赖"当成已全量兑现保证来引用。
- 数量（~72/~80/~250/24）为本轮核查的执行证据，随代码演进，以生成器实际扫描结果为准，不作为硬编码验收值。
