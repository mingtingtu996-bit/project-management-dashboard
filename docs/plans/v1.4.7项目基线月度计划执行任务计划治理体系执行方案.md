## 0. 2026-06-01 final range-tree boundary (authoritative)

This v1.4-series plan follows the final range-tree model. There is no production history or existing user data that needs a compatibility layer.

Authoritative engineering object types are exactly: `phase / section / building / basement / floor / physical_zone / functional_area`.

The following compatibility surfaces are deleted and must not be reintroduced in runtime code, migrations, or frontend contracts:

- `zone / professional / subproject / custom` as engineering object types.
- `zone_object_id / professional_object_id` task fields.
- `project_materials.professional_object_id` and `engineering_categories.professional_object_id`.
- `legacy_object_type`, deprecated object-type arrays, legacy bridge/backfill helpers, and old scope adapter functions.
- `/api/scope-dimensions`, `scope_dimensions`, and `project_scope_dimensions` as active application surfaces.

Professional/system/domain/method semantics remain business facts through `specialty_type`, `engineering_category_id`, `standard_work_code`, template metadata, and project profile facts. They are not range-tree objects.

Any older section in this document that mentions deleted object types, deleted fields, old scope tables, or compatibility adapters is superseded by this boundary.
# v1.4.7 项目基线 / 月度计划 / 执行任务的计划治理体系执行方案

## 1. 目标

v1.4.7 的目标是把当前应用里已经存在的 `项目基线 / 月度计划 / 执行任务` 三类计划数据，收口为一套后端统一治理、前端轻量表达的计划治理体系。

本章重点解决这些问题：

```text
项目总进度计划以哪一版项目基线为准
月度计划从哪套数据生成，确认后是否还能被任务变化自动改写
执行任务的计划开始、计划完成、实际开始、实际完成分别由谁写入
任务列表变化什么时候影响月度计划，什么时候触发新版项目基线建议
基线、月计划、任务之间的版本、快照、映射、锁和治理状态如何留痕
前端如何继续保持 v1.3.5.3 的简单计划表体验
```

v1.4.7 不重做 WBS、不重做任务编码、不重做来源映射模型。状态字典原则上由 v1.4.5 提供，但必须以“计划状态域和值都已落库”为前提：如果目标分支只创建了 `baseline.lifecycle` / `monthly_plan.lifecycle` 两个 domain，却没有写入对应 `status_values` 和 `status_transitions`，则 v1.4.7 迁移必须补齐计划状态字典，不得继续依赖静态 fallback 或前端硬编码状态词。

版本依赖顺序固定为：

```text
v1.4 工程对象主数据体系
-> v1.4.1 项目范围维度体系
-> v1.4.2 WBS 拆解标准体系
-> v1.4.3 施工任务标准数据模型
-> v1.4.4 建筑工程任务编码规则
-> v1.4.5 状态与生命周期字典体系
-> v1.4.6 数据来源与映射关系体系
-> v1.4.7 项目基线 / 月度计划 / 执行任务的计划治理体系
```

本章必须尊重 `v1.3.5.3` 已确认的前端口径：项目基线、月度计划、任务列表共用 `PlanningTreeTable`，用户像编辑一张计划表一样工作，系统在后端处理版本、草稿、锁、快照、映射、重编和治理状态。

## 2. 核心结论

计划治理体系分为 `三层计划对象 + 一层实际执行事实`：

```text
项目基线：项目总进度计划的版本化承诺
月度计划：某个月的执行承诺快照
执行任务：现场当前滚动排期
实际执行事实：现场真实发生的开始、推进、完成
```

前三层是计划对象，第四层是执行事实。四者不是互相覆盖的同一张表，而是不同业务层级的数据事实：

```text
项目基线确认后不能被任务日常编辑直接改写
月度计划确认后不能被任务日常编辑直接改写
任务列表的 planned_start_date / planned_end_date 代表当前现场滚动排期
任务列表的 actual_start_date / actual_end_date 代表实际执行事实
任务列表长期偏离基线时，系统生成新版基线建议，而不是偷偷修改已发布基线
任务列表变化影响下月或重新生成的月度计划，而不是自动改写已确认月度承诺
```

### 2.1 计划真相模型

v1.4.7 是后续所有计划相关体系的总口径。项目基线、月度计划和任务列表必须按以下真相模型理解：

```text
项目基线 = 总控承诺快照
月度计划 = 阶段承诺快照
任务列表 = 当前执行事实和现场滚动排期权威
```

已发布项目基线、已确认月度计划在发布 / 确认那一刻就成为历史快照。它们后续主要参与考核、对比、偏差分析、回溯当时承诺和下一轮生成参考，不再参与当前任务事实的直接写入。

```text
日常变化只更新任务列表
任务列表变化不静默回写已发布基线和已确认月计划
新一轮项目基线 / 月度计划生成时，系统以当前任务列表为主输入
旧基线、旧月计划、历史人工调整、里程碑、关键路径、对象、WBS、依赖、阻碍、实际进度只作为算法参考输入
生成结果先成为草案，由用户决定直接接受还是继续手动调整
```

因此，“当前任务事实与历史基线 / 历史月计划不一致”不是普通用户日常必须处理的问题，也不应作为 Dashboard 或月度计划页问题反馈。系统只在生成新版基线、重新生成月计划、偏差分析、AI 分析、BI 指标或数据来源审计时消费这些差异。

前端不新增独立“计划治理中心”，不新增来源链路弹窗，不展示草稿锁、版本冲突、pending_realign、lineage、mapping 等技术细节。前端只保留用户需要理解的业务动作：

```text
项目基线：生成新版、编辑、暂存、保存发布、取消
月度计划：生成、编辑、暂存、重新生成、确认当月、取消
任务列表：新增、编辑、删除、调整计划、更新进度、维护责任、维护条件和阻碍
```

### 2.2 新项目首入口和基线维护口径

从本章起，新项目计划编制入口收口到任务列表：

```text
新项目第一步：进入任务列表
任务来源：导入常见计划编制文件 / 手工编辑 / 通过 v1.4.7.2 标准 seed 生成任务
任务列表保存后：可从当前任务列表生成第一版项目基线，开启计划治理
```

项目基线页和月度计划页仍然保留各自的编辑能力，但不再承担新项目第一步：

```text
项目基线页：已有任务事实后的总控计划版本维护页，支持生成新版、编辑、保存发布和确认
月度计划页：已有基线或当前任务排期后的月度承诺维护页，支持生成、重新生成、编辑、确认和关账
没有可用基线时：项目基线页和月度计划页以空态 / 冻结态引导用户回到任务列表补齐任务事实
```

任务列表业务动作按钮按项目是否已有可用基线区分文案：

```text
没有可用基线：按钮显示“计划治理”，高亮，说明“基于当前任务列表生成第一版项目基线，开启计划治理”
已有可用基线：按钮显示“更新基线”，普通样式，作为日常计划维护动作
任务列表是否存在未保存编辑，不改变按钮文案和样式；保存规则由共享计划树编辑缓冲负责
```

基线更新提示继续遵循本章原口径：任务列表变化不反写已发布基线，只在生成新版基线、重新生成月计划、偏差分析、AI 分析、BI 指标或数据来源审计时消费差异。普通用户侧不得展示 `pending_realign / realign / revision_pool / lock / mapping` 等内部治理词。

### 3.1 当前代码差异与必须收口项

以下内容是基于当前代码扫描得到的现实差异。v1.4.7 实施时必须把这些差异作为改造清单处理，不能只按目标口径写新服务。

```text
任务新增 createTask 目前仍可直接写入 actual_start_date / actual_end_date，需要改为普通创建链路忽略或拒绝这两个字段
任务更新 updateTask 目前会接收 actual_start_date / actual_end_date，并在同一次更新中叠加 autoActualStart / autoActualEnd，需要收口到统一执行事实服务
甘特任务弹窗当前仍展示“实际开始日期”，需要从普通新增 / 编辑弹窗移除
甘特任务弹窗保存当前仍会把 actual_start_date 带入任务接口，需要移除普通保存链路中的实际时间字段
任务列表行内进度当前仍存在失焦即保存，需要改为显式保存机制，避免误操作直接形成执行事实
当前 100% 完成确认弹窗属于早期兜底，应收口为统一进度保存口径，不再把 100 单独做一套用户流程
批量完成当前前端会做 actual_start_date / actual_end_date 乐观补齐，只能作为临时 UI 展示，不能作为权威写入值
验收通过联动任务完成当前会显式传 actual_end_date，需要改为提交完成事件，由后端统一采用验收事件日期或系统日期
旧里程碑兼容映射当前可能把 milestone.actual_date / completed_at 写入 task.actual_end_date，需要改为 backfill/correction 通道
月度计划创建当前只有 baseline_version_id / source_version_id / source_version_label，没有 source_mode / temporary_without_baseline / governance_metadata，需要新增迁移和写入逻辑
项目基线页、月度计划页、共享计划表当前仍有映射、锁、pending_realign 等技术词或列，需要改为业务文案或隐藏到后台治理
全应用仍有大量 start_date / end_date 优先读取点，需要逐步统一为 planned_start_date / planned_end_date 优先，旧字段只兜底
```

这些差异不表示方案方向错误，而是说明 v1.4.7 的实施重点必须包含“当前代码收口”，不能只新增字段。

## 5. 三层计划对象定义

### 5.1 项目基线

项目基线回答：

```text
项目总进度计划是什么
项目最终承诺版本是什么
当前现场是否已经明显偏离总计划
是否需要发布新版总进度计划
```

项目基线的权威表：

```text
task_baselines
task_baseline_items
```

规则：

```text
confirmed / pending_realign 中业务版本号最大的记录为当前可参考基线
draft / revising 是工作副本，不占用业务 vN
保存发布时才生成或确认业务版本号
发布新版后，旧 confirmed 版本归档或关闭
已发布基线项不可被任务列表日常编辑直接改写
已发布 confirmed 基线发起修订时，只能生成 revising 工作副本，不得直接把原 confirmed 记录改成可编辑记录
取消基线修订只丢弃 revising 工作副本，不影响原 confirmed / closed / archived 历史承诺
修订副本发布后生成新的 confirmed 基线，并通过 superseded_by_id / lineage / change_logs 关联旧版本
任务长期偏离基线时，只生成新版基线建议或 pending_realign 治理状态
```

### 5.2 月度计划

月度计划回答：

```text
本月承诺干什么
本月计划完成到什么程度
月末兑现率按哪张表判断
上月未完成事项如何滚入本月
```

月度计划的权威表：

```text
monthly_plans
monthly_plan_items
```

规则：

```text
同一项目同一月份只能有一个当前确认口径
confirmed 月度计划是月度承诺快照
confirmed 后不再被任务列表变化静默改写
closed 表示该月已经关账
上月未完成事项通过 carryover 进入后续月份，而不是回改上月承诺
重新生成只作用于未确认月度计划
人工修改未确认月度计划后，同月重新生成必须保留 manual_override 字段
已确认月度计划发起修订时，只能生成 revising 工作副本，不得直接改写原 confirmed 记录
取消月度计划修订只丢弃 revising 工作副本，不影响原 confirmed / closed 历史承诺
修订副本确认时必须在同一事务内把旧 confirmed 记录归档为 archived，并写 superseded_by_id / superseded_at / lineage / change_logs，然后再把修订副本确认为新的 confirmed，避免同月 confirmed 唯一索引冲突
```

同月确认口径落地规则：

```text
同一 project_id + month 只允许一条 status = confirmed 的月度计划
确认 draft / revising 月度计划前，后端必须检查同项目同月是否已有其他 confirmed 计划
如果已存在其他 confirmed 计划，默认拒绝确认并返回业务提示“本月已有已确认月度计划，请先进入修订流程”
不得通过创建第二条 confirmed 月度计划来替代既有月度承诺
已 closed 的月度计划表示月度关账结果，不因新草稿确认被自动改写
```

月度计划版本号口径：

```text
沿用当前代码的项目级递增版本号：createMonthlyPlanVersion 继续按 project_id 查询 monthly_plans 最大 version 后 +1
monthly_plans.version 是项目内计划版本序列和并发校验辅助，不是同一月份内从 1 开始的局部版本号
同一月份当前确认唯一性由 project_id + month + status = confirmed 的服务校验和 partial unique index 保证
不得在 v1.4.7 中把 getLatestVersion(projectId) 静默改成 getLatestVersion(projectId, month)
如果未来产品明确要“每月独立版本号”，必须同步修改唯一约束、接口校验、测试和前端版本文案，本章不做该改口
```

月计划行删除 / 移出口径：

```text
未确认月度计划允许移出、删除或合并计划行，但必须写 manual_override_fields / change_logs / data_lineage
已确认月度计划不允许直接删除或移出计划行，也不允许通过重新生成覆盖原行集合
已确认月计划中的不再执行、延期、取消、拆分、合并，只能在月末关账、下月滚入、修订工作副本或任务执行事实中处理
从月计划移出的行不得物理删除来源任务、基线项或 lineage，只改变当前未确认月计划的纳入状态
```

### 5.3 执行任务

执行任务回答：

```text
现场现在怎么排
现在干到哪里了
谁负责
条件和阻碍是否满足
实际开始和实际完成是否已经发生
```

执行任务的权威表：

```text
tasks
task_conditions
task_obstacles
task_progress_snapshots
task_timeline_events
change_logs
```

规则：

```text
tasks.planned_start_date / planned_end_date 是当前滚动排期
tasks.actual_start_date / actual_end_date 是执行事实
任务列表可以长期编辑，因为它代表现场当前事实
任务变化写快照、写变更日志、写来源映射，但不直接改写已确认基线或已确认月计划
任务计划变化进入后续月度计划生成和项目基线重编算法
```

## 6. 计划时间字段治理

计划时间字段治理在本章落地。v1.4.6 负责记录来源和映射，本章负责定义谁能写、谁不能写、谁只能消费。

| 字段 | 权威位置 | 写入来源 | 消费场景 | 禁止行为 |
|---|---|---|---|---|
| 项目基线计划开始 | `task_baseline_items.planned_start_date` | 基线新建、导入、从任务生成、发布前编辑 | 总进度计划、基线偏差、驾驶舱计划口径 | 任务日常编辑直接覆盖已发布基线 |
| 项目基线计划完成 | `task_baseline_items.planned_end_date` | 基线新建、导入、从任务生成、发布前编辑 | 总进度计划、关键节点偏差 | 任务日常编辑直接覆盖已发布基线 |
| 月度计划开始 | `monthly_plan_items.planned_start_date` | 月计划生成、确认前编辑、上月滚入 | 月度承诺、月度兑现、月报 | 确认后被任务变化静默覆盖 |
| 月度计划完成 | `monthly_plan_items.planned_end_date` | 月计划生成、确认前编辑、上月滚入 | 月度承诺、月度兑现、月报 | 确认后被任务变化静默覆盖 |
| 月度目标进度 | `monthly_plan_items.target_progress` | 月计划算法、确认前编辑 | 月度兑现率、偏差分析 | 确认后随任务进度自动变化 |
| 任务计划开始 | `tasks.planned_start_date` | 任务列表、任务弹窗、导入、系统物化 | 甘特图、任务列表、月计划生成、基线重编 | 用已发布基线反向覆盖现场排期 |
| 任务计划完成 | `tasks.planned_end_date` | 任务列表、任务弹窗、导入、系统物化 | 甘特图、任务列表、月计划生成、基线重编 | 用已确认月计划反向覆盖现场排期 |
| 任务实际开始 | `tasks.actual_start_date` | 后端根据执行事件自动生成 | 执行分析、月末归档、任务总结 | 普通任务编辑手动填写、基线或月计划生成时写入 |
| 任务实际完成 | `tasks.actual_end_date` | 后端根据完成事件自动生成 | 任务总结、完成率、延期判断 | 普通任务编辑手动填写、仅因计划完成日期到达而自动写入 |

兼容规则：

```text
tasks.start_date / tasks.end_date 继续作为旧字段兼容
新写入优先写 planned_start_date / planned_end_date
短期内同步回填 start_date / end_date，避免旧页面、旧接口、旧报表断裂
读取时优先读 planned_start_date / planned_end_date，缺失时才读 start_date / end_date
```

全应用消费口径：

```text
甘特图、任务列表、任务详情、任务总结、Dashboard、报表、风险预警、关键路径、材料到场提醒、周报和项目健康度服务，统一优先消费 tasks.planned_start_date / tasks.planned_end_date
仅当 planned_start_date / planned_end_date 为空时，才使用 start_date / end_date 作为旧字段兜底
新增或编辑任务时，前端仍可在界面上叫“计划开始 / 计划完成”，但提交给后端必须写 planned_start_date / planned_end_date，并短期兼容回填 start_date / end_date
任务排序、逾期判断、依赖提示和进度偏差分析不得再优先读取 start_date / end_date
旧导入、旧本地缓存、旧初始化数据可以继续带 start_date / end_date，但进入服务端后必须标准化为 planned_start_date / planned_end_date
```

第一批必须收口的当前代码读写点：

```text
client/src/pages/GanttView.tsx：表单初始化、逾期判断、保存 payload、依赖校验优先 planned_*，actual_start_date 从普通保存中移除
client/src/pages/GanttViewRows.tsx：行内日期展示和编辑优先 planned_*，不得 start_date 优先
client/src/pages/GanttViewPanels.tsx：详情日期区优先 planned_*，缺失才读旧字段
client/src/pages/GanttView/TaskTimelineView.tsx：时间轴当前排期优先 planned_*，避免 start_date / end_date 覆盖标准字段
client/src/pages/Reports.tsx 与 Reports/components/SCurveChart.tsx：计划曲线、目标日期、报表口径统一 planned_* 优先
server/src/services/projectCriticalPathService.ts：关键路径算法优先 planned_start_date / planned_end_date
server/src/services/taskDurationForecastService.ts：预测模型优先 planned_*，start_date / end_date 只做历史兜底
server/src/routes/task-summaries.ts：任务总结、按时判断、完成月归集统一计划字段优先
server/src/services/taskDueService.ts 与 dueDateService.ts：到期判断优先 planned_end_date
```

实际时间规则：

```text
实际开始 / 实际完成的唯一业务来源是后端自动生成
普通任务新增 / 编辑弹窗不提供实际开始 / 实际完成输入
普通任务 API 不接受前端把 actual_start_date / actual_end_date 当作日常字段写入
进度 0-100 统一采用“修改进度 -> 点保存 -> 后端提交”的显式保存机制
进度输入失焦、拖动、键盘输入、粘贴、填充均不得直接提交，必须经保存动作确认
取消进度修改表示放弃本次修改，不自动改为 99，也不提交任何进度写入
进度首次大于 0 且 actual_start_date 为空时，后端写入 actual_start_date
状态从未开始进入进行中且 actual_start_date 为空时，后端写入 actual_start_date
进度保存为 100 时，后端写入 actual_end_date 并派生完成状态
状态改为 completed 时，也必须经同一保存入口提交；若 progress 未到 100，后端同步 progress = 100 并补 actual_end_date
验收通过、旧里程碑兼容、导入回填等业务链路不得绕过自动生成规则，必须通过后端统一执行事实服务写入
完成后回退进度不自动清空 actual_end_date，只记录更正日志或要求明确更正动作
actual_start_date / actual_end_date 属于执行事实，不属于计划生成字段
```

实际时间更正规则：

```text
手动/API 显式写 actual_start_date / actual_end_date 不作为普通业务来源
只有管理员更正、导入历史数据回填、系统兼容迁移可以显式修正实际时间
更正必须写 change_logs，记录原值、新值、更正人、更正原因和来源类型
更正不回改已关账月份的月度兑现终值，只在详情中保留更正说明
```

## 7. 计划生成与传播规则

### 7.0 现有算法继承与补强口径

v1.4.7 不新建第二套项目基线算法或月度计划算法，而是在 v1.3.5.3 已落地的两个算法之上补规则、补边界、补字段和补可追溯性。

当前代码已经具备的算法骨架：

```text
server/src/routes/task-baselines.ts
  buildGeneratedBaselineItemsFromTasks：已支持从当前任务列表生成待发布新版基线条目
  POST /api/task-baselines/:id/generate-version：已支持生成新版基线草案

server/src/services/baselineGovernanceService.ts
  resolveMonthlyPlanGenerationSource：已支持月计划来源自动判断
  mapBaselineItemsToMonthlySeedItems：已支持从基线条目生成月计划种子项
  mapTasksToMonthlySeedItems：已支持从当前任务列表生成月计划种子项
  estimateMonthTargetProgress：已支持按月份窗口估算目标进度
  scanProjectBaselineValidity：已支持扫描基线是否需要重整

server/src/routes/monthly-plans.ts
  POST /api/monthly-plans：已使用 resolveMonthlyPlanGenerationSource 的结果生成月度计划
```

v1.4.7 的补强原则：

```text
保留现有算法入口，不另建一套独立生成入口
保留现有共享 PlanningTreeTable 前端主线，不增加来源选择器
把当前算法中隐含的优先级、字段口径、边界条件和异常处理写成明确规则
把算法需要但当前缺失的治理字段补齐到 monthly_plans / monthly_plan_items / task_baselines / tasks
把复杂来源、映射、拆分、合并、批次留痕放在后端，不前台化为普通用户流程
```

算法建设节奏：

```text
v1.4.7 现在先做算法底座和低风险补强，不把最终智能权重一次写死
当前阶段必须确定输入口径、输出字段、快照边界、人工覆盖规则、确认后不回写规则和后端留痕字段
inclusion_score / feasibility_score / confidence / generation_metadata 可以先按默认规则落地，允许后续章节继续补充输入因子
第 8 到第 21 章完成后，再统一回看图纸、证照、验收、风险、问题、预警、责任主体、模板经验、指标口径等新输入，对算法权重和阈值做最终校准
后续章节新增的业务体系只能作为算法输入或反馈，不得反向要求普通前端新增来源选择、算法配置或复杂差异处理流程
```

必须补强的算法规则：

```text
项目基线生成仍以当前任务列表生成新版草案为主，但必须补充 WBS 分类、工程对象、里程碑、关键路径、实际进度快照、历史人工覆盖规则、上一版基线差异和上一轮月计划兑现情况
新版基线生成不得覆盖已发布基线，只生成 draft / revising 工作副本，发布后才成为 confirmed 版本

月度计划生成仍由后端自动判断来源，用户不选择来源
有 confirmed 基线时，不能只机械复制基线项，还要合并当前任务排期、上月滚入、已开工未完成、实际进度快照、当前依赖、当前对象归属、当前里程碑 / 关键节点和任务执行约束状态
基线 pending_realign 或无基线时，允许自动切到当前任务排期生成，但必须写 source_mode / temporary_without_baseline / governance_metadata

同月重新生成时，必须保留未确认月计划中的 manual_override 字段
确认后的月度计划不因任务变化自动回写，任务变化进入执行事实、月末关账和下月算法输入
当前任务事实与已发布基线 / 已确认月计划存在正常差异时，不要求用户日常处理；差异只作为新版基线生成、月计划重算、偏差分析、AI 分析和 BI 指标的后端输入
生成结果必须是草案，用户可以直接接受，也可以在表格中继续手动调整；系统不得把算法建议自动发布成新基线或自动确认成月计划
异常项只在必要行显示“需确认”或业务提示，且必须同时给出业务原因和下一步动作；算法细节写后端算法日志和 lineage。月度计划页普通可见原因只表达月度承诺表自身是否可确认，不展示前置任务、开工条件、阻碍等任务执行治理原因。
```

### 7.1 项目基线生成

项目基线生成输入：

```text
当前任务列表
WBS 工程分类
工程对象归属
里程碑和关键节点
任务依赖
实际进度快照
累计偏差
历史人工修正偏好
```

生成规则：

```text
无基线时，第一版项目基线只能基于当前任务列表生成。空白录入、文件导入、v1.4.7.2 seed 模板生成都必须先落入任务列表编辑缓冲，保存形成当前任务事实后，再由任务列表入口开启计划治理并生成第一版基线草案
已有基线时，继续复用现有 generate-version 能力，从当前任务列表和实际执行事实生成新版基线草案
生成结果先成为 draft / revising 工作副本
用户保存发布后才成为 confirmed 版本
发布时写 data_lineage_batches / data_lineage_links
发布时写 change_logs
发布时归档或关闭旧当前基线
```

现有基线生成算法补强规则：

```text
从任务生成基线时，稳定映射优先使用 source_task_id / baseline_item_id，不允许只按任务名称匹配
任务缺少 WBS 分类或工程对象归属时，按 v1.4.2 / v1.4.3 的规则自动补齐或标为待校准，不阻断普通查看
父子层级调整时，优先保持原 source_task_id 映射，父级变化只影响结构路径，不生成新的业务任务身份
删除、取消、关闭任务不进入新版基线计划集合，但保留历史 lineage
新增任务进入新版基线草案，mapping_status 可为 pending，但前端不把 pending 作为普通流程
关键路径、里程碑和实际进度快照参与重排建议，但不直接改写已发布基线
```

进入新版基线生成算法的信号：

```text
总完工日期偏移超过阈值
关键里程碑偏移超过阈值
关键线路影响后续工期
任务累计新增或删除达到阈值
主要分部或分项发生明显变化
连续多个月月度计划大量滚入或纠偏
计划完整性检查发现大量孤立映射或断链
```

以上信号不要求用户在任务列表日常处理。系统只在用户进入“生成新版基线 / 发起基线修订”时用于生成草案、解释变化来源和辅助用户判断是否接受。

### 7.2 月度计划生成

月度计划生成输入：

```text
当前生效项目基线
当前任务列表滚动排期
上月月度计划关闭结果
未完成滚入项
任务实际进度快照
人工覆盖规则
```

生成优先级：

```text
1. 上月未完成且需要滚入的事项
2. 已开工但未完成的现场任务
3. 当前任务列表中计划与本月重叠的任务
4. 当前生效项目基线中本月应执行的基线项
5. 本月关键节点、里程碑相关任务
```

这个优先级是对现有 `resolveMonthlyPlanGenerationSource` 的补强，不是新增用户可选来源。实现时可以继续让后端自动选择来源，但生成明细时必须按上述优先级合并、去重和保留人工覆盖。

数据源选择：

```text
如果当前基线为 confirmed，月度计划优先从基线和当前任务排期共同生成
如果当前基线为 pending_realign，月度计划可自动切换为从当前任务排期生成
如果没有基线，月度计划页不作为新项目首入口；只允许在当前任务列表已有保存事实时从任务列表生成临时月度计划，不阻断项目使用
如果任务列表为空，允许生成空月计划并提示无本月任务
```

`source_mode` 判定必须固定，避免执行时每个接口各自理解：

```text
baseline：只从 confirmed 基线条目生成，未合并当前任务排期、滚入项或人工覆盖
mixed：存在 confirmed 基线，且本次生成同时合并当前任务排期、上月滚入、已开工未完成或实际进度快照
schedule：没有 confirmed 基线，或当前基线处于 pending_realign 且后端自动切到当前任务排期生成
manual：由用户手工创建或手工维护，未经过自动生成算法
imported：由外部文件导入形成月度计划草稿
```

v1.4.7 默认推荐：

```text
有 confirmed 基线且合并当前排期时，source_mode 写 mixed，baseline_version_id 写 confirmed 基线 ID
有 confirmed 基线但严格只复制基线项时，source_mode 写 baseline，baseline_version_id 写 confirmed 基线 ID
基线 pending_realign 自动切到当前排期时，source_mode 写 schedule，baseline_version_id 写 null，governance_metadata.referenced_realign_baseline_id 记录该 pending_realign 基线 ID
无基线时，source_mode 写 schedule，baseline_version_id 写 null，temporary_without_baseline = true
```

无基线临时月度计划规则：

```text
source_mode = 'schedule'
baseline_version_id = null
source_version_label = '当前排期'
governance_metadata.is_temporary_without_baseline = true
governance_metadata.baseline_required_for_long_term = true
```

业务边界：

```text
临时月度计划只解决本月执行承诺，不作为长期项目基线替代
临时月度计划可以确认，但确认时后端必须保留当前排期来源标记
临时月度计划可以进入月度兑现、月末关账和任务执行闭环
临时月度计划不得反向生成“已发布项目基线”
后续建立项目基线时，系统可以把这些临时月度计划作为参考输入，但必须生成新的基线草稿并由用户保存发布
```

前端表达：

```text
不增加来源选择器
不展示 source_mode / baseline_version_id / lineage 字段
无基线生成月计划时，只在月度计划页弱提示“当前按任务排期生成，建议后续建立项目基线”
Dashboard / 驾驶舱不展示此类计划对齐问题；如消费计划治理指标，只展示汇总结果，不作为问题处理入口
```

确认规则：

```text
未确认月度计划可以编辑、暂存、重新生成
确认后成为月度承诺快照
确认后任务变化不回写本月承诺
本月执行变化进入任务列表、进度快照、月末关账和下月生成输入
临时月度计划确认后仍保持 source_mode = 'schedule'，不得在确认时自动改成 baseline / mixed
```

目标进度估算补强规则：

```text
已完成任务：target_progress = 100
已开工任务：target_progress 不得低于当前 progress
本月内计划完成的普通任务：默认 target_progress = 100
跨月任务：优先按工程量权重估算；没有工程量时按计划工期在本月占比估算
里程碑 / 控制节点：节点日期落在本月时 target_progress = 100，否则保持当前进度或 0
缺少计划日期的任务：不参与自动月计划主集合，进入后端算法异常记录；如必须显示为月度计划“需确认”行，必须展示业务原因“月度计划条目缺少计划开始或计划完成，需要补齐日期”
```

同月重新生成补强规则：

```text
未确认月度计划允许重新生成
重新生成先读取原 monthly_plan_items.manual_override_fields
用户改过的计划开始、计划完成、目标进度、备注等字段优先保留
系统只更新未被人工覆盖的字段
新增算法项追加到计划表，已消失且未人工保留的项标记为待移除或不再纳入
确认后的月度计划不执行重新生成，只能作为历史承诺查看和月末关账输入
未确认月度计划允许把待移除项移出本月计划；已确认月度计划不得删除或移出原承诺行，只能在关账、下月滚入或修订副本中处理
```

`manual_override_fields` 写入规则：

```text
用户在未确认月计划中编辑 planned_start_date 时，manual_override_fields.planned_start_date = true
用户在未确认月计划中编辑 planned_end_date 时，manual_override_fields.planned_end_date = true
用户在未确认月计划中编辑 target_progress 时，manual_override_fields.target_progress = true
用户在未确认月计划中编辑 commitment_status 时，manual_override_fields.commitment_status = true
用户在未确认月计划中编辑 notes 时，manual_override_fields.notes = true
批量移入 / 移出、批量目标进度、批量备注、单行日期编辑和修正执行都必须同步维护 manual_override_fields
系统重新生成不得清空人工覆盖标记；只有用户明确“恢复系统生成值”时才移除对应字段标记
```

算法智能化补强规则：

```text
生成月度计划时，后端为每个候选任务计算 inclusion_score，不需要前端展示
inclusion_score 由月份重叠、上月滚入、已开工未完成、关键路径、里程碑、条件阻碍、责任主体和历史滚入次数共同决定
分数高的任务优先进入本月计划，分数低但存在关键节点约束的任务可以进入后端候选异常；如果普通前端显示“需确认”，只能转成月度承诺表自身原因，不展示 inclusion_score

任务去重优先级：source_task_id / baseline_item_id > engineering_object_id + engineering_category_id > WBS 路径 + 任务名称
同一任务同时命中基线、当前排期、上月滚入时，只生成一行月度计划项，并把来源原因写入 monthly_plan_items.generation_metadata.generation_reasons

依赖关系参与生成：前置任务未完成时，后置任务不得简单按计划日期纳入 100% 目标，应自动下调目标进度或写入后端 generation_metadata，不在月度计划页展示“前置任务未完成”
条件和阻碍参与生成：未满足开工条件、存在未关闭阻碍时，任务仍可进入月计划，但 target_progress 应保守估算，并写入 generation_reasons
关键路径和里程碑参与生成：关键路径任务和本月控制节点拥有更高 inclusion_score，但不得绕过依赖、条件和阻碍规则

目标进度估算优先级：工程量权重 > WBS / 工程分类经验权重 > 计划工期占比 > 线性兜底
历史纠偏参与估算：同类任务连续滚入或历史完成偏慢时，下月 target_progress 自动保守；历史完成稳定时可按正常比例估算
算法原因进入后端 generation_metadata / governance_metadata / lineage / 算法日志；普通前端如出现“需确认”，必须展示月度承诺表自身的业务原因和下一步动作，不展示评分、字段名和算法参数
```

智能评分建议公式：

```text
基础分：计划日期与本月重叠 +30
上月滚入未完成：+35
已开工未完成：+30
本月计划完成：+25
本月计划开工：+20
关键路径任务：+15
本月里程碑 / 控制节点相关：+20
责任人或责任单位已明确：+5
开工条件未满足：-15
存在未关闭阻碍：-20
前置任务未完成：-25
已完成且无需本月复核：-100
已取消 / 已关闭 / 已删除：-100
连续滚入次数每增加 1 次：-5，但最低不低于需确认阈值
```

候选任务进入规则：

```text
inclusion_score >= 50：自动进入本月计划
30 <= inclusion_score < 50：如果关联关键路径、里程碑或已开工，进入本月计划并标记需确认
0 <= inclusion_score < 30：默认不进入主计划，只记录算法原因
inclusion_score < 0：排除
```

“需确认”行展示规则：

```text
可以显示“需确认”，但必须同时展示业务原因，不能让用户理解算法字段或评分逻辑
月度计划页允许原因：本月条目缺失、月度日期缺失、目标进度缺失、重复计划条目、确认口径冲突
月度计划页允许动作：生成或补齐本月条目、补齐月度日期、补齐目标进度、合并或移出重复条目、进入修订流程
任务执行原因如前置任务未完成、开工条件未满足、存在未关闭阻碍，只进入任务列表/甘特页健康横幅或后端算法日志
禁止展示：inclusion_score、confidence、generation_metadata、blocking_factors、source_mode、lineage ID
```

来源合并去重规则：

```text
先收集候选项：上月滚入、当前任务排期、当前生效基线、本月关键节点
再按稳定键去重：source_task_id / baseline_item_id > engineering_object_id + engineering_category_id > wbs_code > 标准化任务名称
同一稳定键命中多个来源时，只保留一条 monthly_plan_item
保留项的计划日期优先级：人工覆盖 > 当前任务排期 > 上月滚入承诺 > 基线计划
保留项的 target_progress 优先级：人工覆盖 > 已开工实际进度推算 > 工程量权重 > 分类经验权重 > 工期比例
被合并来源写入 generation_metadata.merged_sources，不在前端拆成多行
```

`generation_metadata` 建议结构：

```ts
{
  inclusion_score: number;
  confidence: 'high' | 'medium' | 'low';
  generation_reasons: string[];
  merged_sources: Array<'carryover' | 'task_schedule' | 'baseline' | 'milestone' | 'manual_override'>;
  source_priority: string[];
  target_progress_method: 'manual_override' | 'quantity_weight' | 'category_experience' | 'duration_ratio' | 'linear_fallback';
  blocking_factors: Array<'predecessor_unfinished' | 'condition_unmet' | 'active_obstacle' | 'missing_date' | 'mapping_attention'>;
}
```

后端执行顺序建议：

```text
1. 读取当前月份窗口、当前生效基线、当前任务列表、上月关闭结果、任务依赖、条件、阻碍、关键路径、里程碑
2. 分别生成 carryover / task_schedule / baseline / milestone 候选集合
3. 为候选集合计算 inclusion_score 和 generation_reasons
4. 按稳定键合并去重，保留 merged_sources
5. 应用 manual_override_fields，保护用户未确认月计划中的人工判断
6. 计算 planned_start_date / planned_end_date / target_progress
7. 写 monthly_plan_items.generation_metadata / last_generated_at
8. 普通前端只展示生成后的计划行和必要业务提示，不展示评分、来源树和算法字段
```

算法延后校准边界：

```text
现在可以确定：候选来源、快照截止时间、去重规则、人工覆盖保护、确认后不回写、generation_metadata 结构、基础评分框架
现在只做默认建议：inclusion_score 权重、target_progress 估算权重、confidence 判断阈值、需确认阈值
暂不最终锁死：材料准备度权重、图纸准备度权重、证照影响权重、验收反馈权重、风险问题预警权重、责任单位产能权重、经验工期权重
第 8 到第 21 章完成后，统一建立算法复核清单，对所有新增业务输入做一次权重校准和回归测试
```

## 8. 状态与版本规则

计划状态继续使用 v1.4.5 字典和当前状态机。

项目基线状态规则：

```text
draft：工作副本
revising：修订工作副本
confirmed：已发布版本
pending_realign：仍可作为当前参考，但系统建议重编
closed / archived：历史版本
```

月度计划状态规则：

```text
draft：未确认，可编辑
confirmed：已确认月度承诺
closed：已关账
archived：被修订版本替代后的历史承诺，不再参与当前确认口径
revising / pending_realign：后端兼容状态，不作为前端主流程
```

版本规则：

```text
项目基线 draft / revising 不占用业务版本号
项目基线 confirmed 时才分配 v1 / v2 / v3
月度计划 version 沿用当前项目级递增口径，用于项目内月度计划版本序列、接口并发校验和审计追踪
月度计划不得按月份重新从 1 编号；同月确认唯一性由 confirmed 口径约束控制
已确认或已关闭版本只读，不在原记录上静默重算
confirmed / closed / archived 记录不得被普通编辑、重新生成、任务删除、任务关闭直接改写
从 confirmed 发起修订时必须新建 revising 工作副本，取消修订只丢弃工作副本，不改变原承诺记录
所有发布、确认、关闭、重新生成动作都必须写 change_logs 和 data_lineage
```

协作规则：

```text
planning_draft_locks 继续存在
普通用户不看到 LOCK_HELD / VERSION_CONFLICT 等技术码
非重叠字段冲突由后端自动合并
同一字段冲突才提示用户确认
强制解锁是管理员或 owner 的异常处理能力，不作为普通前端主动作
```

```text
task-baselines 路由继续负责基线版本生成、发布和归档，不直接承担月计划智能算法
```

实际时间自动生成实现方式：

```text
updateTask 是实际开始 / 实际完成的主写入口
普通 createTask / updateTask 请求体中的 actual_start_date / actual_end_date 默认忽略或返回校验错误
updateTask 根据 progress / status / completion intent 自动生成 actual_start_date / actual_end_date
批量完成只提交完成意图，不把前端乐观日期作为权威日期
验收通过联动任务完成时，只提交 completion event，由后端统一生成或采用验收事件日期作为系统事件日期
旧里程碑兼容映射和历史导入走 backfill/correction 通道，不走普通任务编辑通道
```

`planningScheduleGovernanceService` 的实际时间上下文参数必须明确：

```ts
type ExecutionFactContext = {
  actorUserId?: string | null;
  intent:
    | 'progress_advance'
    | 'status_change'
    | 'completion_confirm'
    | 'acceptance_passed'
    | 'milestone_backfill'
    | 'import_backfill'
    | 'admin_correction'
    | 'reopen';
  eventDate?: string | null;
  eventSource?: 'task' | 'acceptance' | 'milestone' | 'import' | 'admin_correction' | 'system';
  correctionReason?: string | null;
  allowActualTimeWrite?: boolean;
};
```

```text
普通任务新增 / 编辑：allowActualTimeWrite = false，丢弃或拒绝 actual_start_date / actual_end_date
进度推进 / 状态变更：eventDate 默认使用服务端当前日期
验收通过：eventDate 使用 acceptance_plans.actual_date，缺失时才使用服务端当前日期
旧里程碑回填：eventDate 使用 milestone.actual_date 或 completed_at，并标记 eventSource = 'milestone'
导入回填 / 管理员更正：必须提供 correctionReason，并写 change_logs
reopen：只通过明确 reopen intent 清空或保留 actual_end_date，不允许普通进度回退隐式清空实际完成
```

后端必须修正当前隐患：

```text

```

## 15. Assumptions

当前没有历史生产数据，所以 v1.4.7 迁移只做轻量兼容回填，不做复杂历史清洗。

项目基线、月度计划、任务列表的前端形态以 v1.3.5.3 为准，不重新引入草稿态页面、确认冻结、修订池、观察池、来源选择器等重流程。

`三层计划对象 + 一层实际执行事实` 是对业务流程优化清单“四层时间线”的落地表达，不改变原始业务含义。

v1.4.7 只治理计划承诺和执行排期，不实现完整审批流、完整经验工期库、完整外部导入平台和完整进度索赔管理。
