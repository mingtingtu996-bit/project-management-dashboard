## 0. 2026-06-01 final range-tree boundary (authoritative)

This v1.4-series plan follows the final range-tree model. There is no production history or existing user data that needs a compatibility layer.

Authoritative engineering object types are exactly: `phase / section / building / basement / floor / physical_zone / functional_area`.

The following compatibility surfaces are deleted and must not be reintroduced in runtime code, migrations, or frontend contracts:

- `zone / professional / subproject / custom` as engineering object types.
- `zone_object_id / professional_object_id` task fields.
- `project_materials.professional_object_id` and `engineering_categories.professional_object_id`.
- `legacy_object_type`, deprecated object-type arrays, legacy bridge/backfill helpers, and old scope adapter functions.
- `/api/scope-dimensions`, `scope_dimensions`, and `project_scope_dimensions` as active application surfaces.

Professional/system/domain/method semantics remain business facts through `specialty_type`, `engineering_category_id`, `standard_work_code`, template metadata, and project profile facts. They are not range-tree objects.

Any older section in this document that mentions deleted object types, deleted fields, old scope tables, or compatibility adapters is superseded by this boundary.
# v1.4.15 删除、关闭、归档与历史保留体系执行方案

## 1. 目标

v1.4.15 的目标是把当前应用中分散在 `任务 / 项目基线 / 月度计划 / 风险问题 / 预警通知 / 验收 / 图纸证照 / 责任单位 / 工程对象 / WBS / 来源映射 / 快照 / 日志` 里的删除、关闭、归档、停用、作废和历史保留规则统一收口。

本章解决的是系统能否稳定回答这些问题：

```text
用户点击删除时，到底是物理删除、软删除、关闭、归档、停用、作废，还是拒绝删除
哪些对象一旦进入快照、计划承诺、来源映射、升级链、验收链、预警链后不能物理删除
任务、基线条目、月计划条目、风险、问题、验收项这类历史对象如何保留
删除或关闭当前对象后，旧基线、旧月计划、BI、AI、报表、审计是否还能解释历史
前端是否需要新增复杂按钮，还是沿用现有删除 / 关闭 / 归档入口
旧对象、旧字段、旧物理删除接口如何兼容
```

本章延续 v1.4.8 之后形成的统一原则：

```text
用户维护业务事实，系统判断治理语义
能自动判断的，不要求用户理解物理删除、软删除、归档、source_deleted 等技术概念
前端可以继续出现“删除”动作，但后端必须根据引用和历史消费情况决定真实处置方式
进入历史快照、来源映射、升级链、验收链、计划承诺、报表口径的对象不做简单物理删除
删除、关闭、归档、停用、作废都必须写 v1.4.14 的 change_logs / operation_logs / lineage 摘要
```

### 1.1 与 v1.4.7.1 共享计划树的上游边界

`v1.4.7.1` 是项目基线、月度计划、任务列表三页的共享计划树交互与提交契约。本章只负责在共享计划树保存时、阅读态业务动作发生时，判断删除、关闭、归档、停用、作废和历史保留的真实处置方式，不重新定义表格删除、撤销、重做、保存或业务动作入口。

必须固定以下原则：

```text
阅读态 / 编辑态 / 业务动作三层模型以 v1.4.7.1 为准，本章不得把表格删除行直接解释为物理删除。
保存前删除只属于编辑缓冲：删除未保存行、删除已保存行的本地意图、撤销/重做、template_generate 后删除生成行，都不触发 retention decision，不写 deletion_retention_events。
保存是删除保留分界点：共享计划树 commit 成功前不执行真实删除；commit 时才对 delete_row、overwrite 命中旧行、批量删除等操作生成 per-row decision。
阅读态业务动作单独判断：发布、确认、关账、关闭、归档、作废等不承接未保存删除；存在未保存编辑时必须先保存或取消。
delete_row / overwrite 的真实处置由本章判断：physical_delete、soft_delete、cancel、close、archive、deactivate、void、hide、merge_into_existing、replace_draft_row、supersede、reject 都只能在保存或业务动作边界产生。
协作更新只更新 merge base：他人新增、修改、删除导致的协作变化不能在本地直接触发 retention decision；保存时以后端最新引用关系重新判断。
字段注册表和 mergeGroup 不决定能否删除：mergeGroup 只用于协作冲突、变更摘要和数据质量归因；删除保护必须以引用、快照、来源映射、升级链、验收链、计划承诺和权限为准。
校核条、健康横幅、数据质量提示不是删除动作：它们只能提示和定位问题，不能替代删除保留决策，也不能自动关闭、归档或取消对象。
template_generate 生成行保存前与普通新增行一致；保存后与手工新增行同权；overwrite 旧行必须在保存时由本章重新判断真实处置。
旧 DELETE 接口可以保留兼容，但普通三页表格删除必须进入 v1.4.7.1 commit，不能直接调用旧 DELETE 绕过 retention decision。
```

## 4. 用户动作与系统处置语义

本章的核心原则是：用户端不暴露复杂治理词，系统端保留完整处置语义。

用户只需要理解少量业务动作：

```text
删除：默认主操作。用于误录、草稿、普通记录、当前页面不再需要的对象。系统自动判断是真删除、软删除、取消、停用还是历史保留。
关闭：只用于风险、问题、阻碍等处理事项，表达“这件事不再继续跟踪或已经处理完”。
作废：只用于工程业务中强语义对象，例如图纸版本作废、证照作废、验收记录作废、材料封样作废。
归档：只用于资料或强归档场景。历史基线、历史月计划、旧通知、旧版本等应由系统自动归档，不要求用户手动理解。
移除/隐藏：用于个人提醒、通知列表、个人视图，不改变业务事实。
```

用户点击“删除”时，系统必须自动判断：

```text
未被消费的误录 / 草稿：物理删除
已进入计划、快照、来源映射、升级链、验收链、预警链、审计链：不物理删除
已经形成计划承诺但不再执行：后台表达为取消或关闭
主数据仍被历史引用：后台表达为停用或归档
通知类个人视图：后台表达为隐藏
项目基线、月度计划、任务列表中的删除行，在保存前就是普通表格删除，可撤销/重做，不立即触发物理删除
点击保存时，系统统一计算本次提交中哪些行是真删除，哪些行要转为取消、停用、归档或历史保留
发布、确认、关账不承接未保存删除；必须先保存或取消当前编辑
专项管理页面如果不是共享大表，也沿用相同原则：用户执行业务动作，系统解释实际处置和影响
```

删除和取消的区别不要求用户主动判断：

```text
删除是用户的通用入口，表达“我不想让它继续出现在当前业务中”。
取消是系统内部对已进入计划或承诺链路对象的解释，表达“它曾经成立，但现在不再执行”。
如果对象尚未被历史消费，删除可以是真删除。
如果对象已经进入历史消费，删除请求由系统转译为取消、停用、关闭、归档或隐藏。
保存前撤销/重做：完全按表格本地历史栈处理，不写 change_logs，不触发 retention decision
保存后撤销：不是简单回滚数据库，而是一次新的业务操作，必须重新校验权限、当前状态、引用关系和下游消费
如果保存后的操作尚未被下游消费，允许按反向操作恢复
如果已经进入基线、月计划、验收、预警、风险问题、快照或来源映射，撤销必须给出影响提示，必要时拒绝或转为新的取消/停用/恢复动作
删除未保存行：直接从表格移除，可撤销
删除已保存但未被消费的误录行：保存后物理删除
删除已进入计划或历史链路的行：保存时转译为不再执行、停用或历史保留
删除影响验收、风险、问题、预警、关键节点或责任主体时：在保存前给出业务影响摘要，不展示技术字段
```

v1.4.7.2 模板生成行按同一套规则处理，不新增“模板行删除”特例：

```text
template_generate 生成的新行在保存前只是编辑缓冲中的新增行，删除后直接从缓冲移除，可撤销/重做，不触发 retention decision。
template_generate 保存成功后，生成行与手工新增行完全同权；后续删除时按任务、基线条目或计划条目的真实引用进入 retention decision。
模板生成行不因为 source = template 就允许硬删除；只要进入基线、月计划、进度、验收、风险问题、预警、来源映射或快照链路，就必须转译为取消、关闭、归档、停用或拒绝。
用户在前端不看到“模板行”“来源行”等技术身份，删除反馈仍按任务、基线条目、月计划条目等业务对象表达。
月度计划行不是 template_generate 直接生成物；即使其来源任务来自模板，删除或移出时也只按月计划条目、任务引用关系和承诺快照判断，不展示“模板行删除”。
```

前端反馈示例：

```text
该任务已进入计划或产生历史记录，不能直接删除，已改为不再执行。
该对象已被历史任务引用，已停用，新建时不再可选，历史记录仍保留。
该提醒已从你的列表移除，业务预警状态不受影响。
```

以下 9 种标准语义只属于系统内部处置层，不要求普通用户理解，也不作为前端通用按钮直接展示。

### 4.1 物理删除 physical_delete

```text
含义：数据库记录被删除
适用：草稿、误录、未被任何历史事实消费的对象
要求：删除前必须通过引用检查、快照检查、来源映射检查、升级链检查、业务统计消费检查
用户端对应动作：删除
系统记录：change_logs 或 operation_logs 记录删除动作；如记录本身被删除，至少要有删除摘要
```

### 4.2 软删除 soft_delete / deleted_at

```text
含义：记录保留，设置 deleted_at 或 deleted_by
适用：已有 deleted_at 机制的对象，例如 wbs_templates 或后续统一补齐的业务对象
要求：默认不出现在新建选择器和普通列表；历史视图可查询
用户端对应动作：删除
系统记录：change_logs 写 deleted_at 设置
```

### 4.3 关闭 close

```text
含义：业务事项已经处理完毕或不再需要继续推进，但保留为历史事实
适用：风险、问题、阻碍、任务受保护关闭、通知/预警解除、月度计划关账
要求：不再进入 active 统计，但可进入历史统计、复盘、趋势和责任分析
用户端对应动作：关闭，仅在风险、问题、阻碍等处理事项中出现
系统记录：closed_at / closed_by / closed_reason 可由系统后台写入，不要求用户必填
```

### 4.4 归档 archive

```text
含义：对象不再作为当前可维护对象参与日常选择，但历史引用有效
适用：责任单位、旧基线版本、已完成历史计划、通知历史、验收历史、WBS 模板、完成项目沉淀模板
要求：不进入新建下拉和默认列表；历史任务、快照、报表继续显示当时名称
用户端对应动作：归档，仅在资料或明确归档场景中出现；历史版本自动归档不要求用户操作
系统记录：archived_at / archived_by / status = archived
```

### 4.5 取消 cancel

```text
含义：计划中的业务对象不再成立，但它曾经被创建过，需要解释为什么不再执行
适用：任务取消、月计划条目取消、未执行验收计划取消、证照办理事项取消
要求：不进入完成率分子；可进入取消率、偏差解释和后续计划重编建议
用户端对应动作：通常仍从“删除”进入，由系统转译为取消；必要时在计划类场景显示“不再执行”
系统记录：status = cancelled 或 commitment_status = cancelled
```

### 4.6 作废 void

```text
含义：文件、图纸、证照、记录版本已经失效，不再作为有效依据
适用：图纸版本作废、证照作废、验收记录作废、材料封样作废
要求：保留版本链和替代关系，不删除历史版本
用户端对应动作：作废，仅在图纸版本、证照、验收记录、材料封样等工程凭证类对象中出现
系统记录：status = voided / replaced_by_id / voided_at
```

### 4.7 停用 deactivate / inactive / disabled

```text
含义：主数据、关系或链接不再可用于新业务，但历史引用有效
适用：工程对象、责任单位 disabled、task_dependencies、project_entity_links、工程分类、范围维度适配对象
要求：不进入新选择器；历史展示保留名称和 ID
用户端对应动作：通常仍从“删除”进入，由系统转译为停用；普通用户不需要理解 inactive / disabled
系统记录：status = inactive / disabled
```

### 4.8 来源已删除 source_deleted

```text
含义：下游风险、问题、预警、通知仍存在，但其来源对象已经被删除、关闭、取消或归档
适用：风险问题预警升级链、通知链、来源映射链
要求：不删除下游链路对象，只把来源状态标记为 source_deleted 或 resolved_source
用户端对应提示：来源已失效，仅在需要解释历史链路时弱提示；不作为用户操作按钮
系统记录：resolved_source / source_type = source_deleted / metadata.sourceDeletedAt
```

### 4.9 个人隐藏 hidden

```text
含义：用户不再在个人通知列表看到该提醒，但业务通知主记录仍保留
适用：通知中心删除已处理提醒、个人静音、个人已知悉
要求：不改变 warning_lifecycle_status，不删除业务来源
用户端对应动作：移除提醒 / 隐藏此提醒
系统记录：notification_recipients.hidden_at 或 equivalent user state
```

## 5. 统一删除决策服务

新增后端服务：

```text
server/src/services/deletionRetentionGovernanceService.ts
```

核心接口：

```ts
export type RetentionDecisionAction =
  | 'physical_delete'
  | 'soft_delete'
  | 'close'
  | 'archive'
  | 'cancel'
  | 'void'
  | 'deactivate'
  | 'hide'
  | 'reject';

export interface RetentionDecision {
  decisionId?: string;
  decisionToken?: string;
  entityType: string;
  entityId: string;
  requestedAction: 'delete' | 'close' | 'archive' | 'cancel' | 'void' | 'deactivate' | 'hide' | 'restore';
  requestedAllowed: boolean;
  resolvedAction: RetentionDecisionAction;
  resolvedAllowed: boolean;
  executionMode: 'auto_execute' | 'require_user_confirm' | 'reject';
  requiresUserConfirmation: boolean;
  reasonCode: string;
  userMessage: string;
  referenceSummary: Record<string, number | boolean | string | null>;
  affectedEntityIds?: string[];
  suggestedAction?: {
    method: 'POST' | 'PATCH' | 'DELETE';
    endpoint: string;
    label: string;
  };
  expiresAt?: string;
  writesChangeLog: boolean;
  writesOperationLog: boolean;
  writesLineageEvent: boolean;
}
```

所有删除类接口先调用：

```ts
evaluateRetentionDecision({
  projectId,
  entityType,
  entityId,
  requestedAction: 'delete',
  actorId,
});
```

统一规则：

```text
requestedAllowed 只表示用户原始请求能否按原语义执行，例如 DELETE 是否真的可以物理删除
resolvedAllowed 表示系统是否允许把原请求转译为 close / archive / cancel / void / deactivate / hide 等处置
executionMode = auto_execute：低风险动作可由原接口直接执行并返回 resolved_action，例如未消费误录物理删除、通知个人隐藏
executionMode = require_user_confirm：高影响转译必须返回 409 / ENTITY_RETENTION_REQUIRES_CONFIRMATION 和 suggestedAction，前端展示业务影响摘要，用户确认后再提交
executionMode = reject：既不能原动作执行，也不能转译执行，返回业务化错误和 suggestedAction，不返回技术栈错误
只有 resolvedAction = physical_delete 且 requestedAllowed = true 时，才允许执行数据库 DELETE
DELETE 路由不得自由选择“内部转为更新”还是“返回建议动作”；必须按 executionMode 执行
所有 action 必须写 v1.4.14 的变更留痕
服务必须检查普通外键、project_entity_links、data_lineage_links、task_baseline_items、monthly_plan_items、task_progress_snapshots、change_logs、risk/issue/warning/notification 链路
```

执行模式默认规则：

```text
未被消费误录 / 草稿 physical_delete：auto_execute
通知个人隐藏 hide：auto_execute
已被引用关键主数据 delete -> deactivate / archive：require_user_confirm，除非用户点击的原按钮本身就是“归档/停用”
风险 / 问题 / 阻碍 delete -> close：require_user_confirm，不自动替用户关闭处理事项
任务 delete：未开始但已承诺时转 cancel；已有进度或链路时转 close；已完成时 reject；均不得自动替用户关闭或取消任务
验收 / 图纸 / 证照 / 材料凭证 delete -> void / archive / cancel：require_user_confirm
项目、成员、责任主体、配置类对象已进入历史链路时：require_user_confirm 或 reject，不允许静默物理删除
快照、来源事件、change_logs、operation_logs、deletion_retention_events：reject，普通业务接口不得删除
```

二次确认协议：

```text
executionMode = require_user_confirm 时，后端必须先写一条 deletion_retention_events，execution_status = pending_confirmation，并返回 decisionId / decisionToken / expiresAt
前端展示业务影响摘要，用户确认后再次提交 suggestedAction，并携带 decisionToken
后端收到 decisionToken 后必须重新计算 referenceSummary 和权限；如果引用关系、状态、权限、目标对象版本发生变化，原 decisionToken 失效，返回 ENTITY_RETENTION_DECISION_EXPIRED
decisionToken 默认 10 分钟有效，只能由同一 actor 在同一 project_id 下使用一次
共享计划树 commit 中只要任一行返回 require_user_confirm 或 reject，默认整批不落库；前端保留编辑缓冲并展示 per-row decision。用户确认后必须携带 decisionToken、原始 commit operations、merge base/content_hash 重新提交，由后端重新校验协作版本、引用关系和权限。
确认重提时如 merge base 已过期或同字段冲突，返回协作冲突或 ENTITY_RETENTION_DECISION_EXPIRED，不得把旧确认套到新数据上。
确认执行成功后更新 deletion_retention_events.execution_status = executed，写 confirmed_by / confirmed_at / executed_at，并绑定 change_log_id / operation_log_id
用户取消确认时可把 execution_status 标记为 cancelled_by_user；不写业务 change_logs
```

### 5.1 已被引用关键主数据删除规则

关键主数据是会被任务、计划、验收、报表、AI 分析、来源映射或历史快照反复引用的对象。用户可以继续点击“删除”，但系统必须接管真实处置方式。

适用对象：

```text
工程对象 engineering_objects
范围树工程对象 engineering_objects（phase / section / building / basement / floor / physical_zone / functional_area）
WBS 工程分类 engineering_categories
责任单位 participant_units
状态字典 status_dictionary / status_values / status_aliases
验收目录 acceptance_catalog
图纸审查规则 drawing_review_rules
证照办理配置和证照依赖 certificate work item / certificate_dependencies
材料分类、材料计划、材料封样相关配置
WBS 模板 wbs_templates
项目成员、责任人、责任主体关系
```

统一判断：

```text
完全未被引用、未进入快照、未进入来源映射、未进入审计链：允许物理删除
已被当前任务、历史任务、基线、月计划、验收、材料、图纸、证照、风险问题、预警、通知、报表、快照或 AI 分析引用：不允许物理删除
已被引用但不再用于新业务：系统转译为停用、归档或隐藏，不要求用户理解后台状态
删除动作影响历史解释时：拒绝物理删除，并返回业务化提示和 resolved_action
```

前端原则：

```text
用户侧主按钮仍然是“删除”
如果系统转为停用/归档/隐藏，响应中返回 resolved_action 和用户可读文案
不让用户选择“物理删除 / 软删除 / 停用 / source_deleted”
不把已引用关键主数据删除做成审批流程
v1.4.14 只记录最终动作摘要，不在 v1.4.14 重复定义处置规则
```

文案示例：

```text
该对象已被历史任务引用，已停用，新建时不再可选，历史记录仍保留。
该责任单位已被计划和验收引用，不能直接删除，已从新建选择中移除，历史记录仍保留。
该规则已被历史图纸审查使用，不能删除，已停用。
```

### 5.3 批量删除决策规则

共享表格和批量操作必须返回逐项决策，不允许只返回一个笼统错误。

```ts
export interface BatchRetentionDecision {
  requestedAction: 'delete' | 'archive' | 'cancel';
  totalCount: number;
  autoExecutableCount: number;
  requiresConfirmationCount: number;
  rejectedCount: number;
  decisions: RetentionDecision[];
  summaryMessage: string;
}
```

批量执行规则：

```text
保存前批量删除：只记录本地编辑缓冲，不写 change_logs，不触发 retention decision
点击保存时批量删除：后端对每一行生成 per-row decision
发布 / 确认 / 关账不处理未保存批量删除；必须先保存或取消当前编辑
全部 physical_delete 且低风险：可一次提交
存在 cancel / archive / deactivate / hide：必须给用户展示业务影响摘要，确认后提交
存在 reject：默认整批不提交，并提示哪些行不能处理；v1.4.15 不做“跳过失败项继续”
批量提交成功后写一组 change_logs 摘要和多条 deletion_retention_events；摘要包含 affected_count、resolved_action 分布和关键对象名称
```

template_generate 的 duplicatePolicy 与删除保留关系：

```text
skip：本批次跳过命中对象，不产生删除、取消、关闭或停用决策。
duplicate：本批次只新增新行，不处理旧行；旧行保持原状态。
overwrite：覆盖只是一种保存意图，不等于立即删除旧行。保存时后端必须对命中的旧行逐条生成 retention decision，判断是 replace_draft_row、merge_into_existing、supersede、取消、关闭、停用、归档还是拒绝覆盖。
replace_draft_row：只允许用于未被消费的草稿行，等价于保存前替换草稿内容。
merge_into_existing：只允许用于不破坏历史解释的字段合并，例如补齐名称、日期、责任、工程对象等当前草稿字段；不得覆盖实际事实、已发布基线、已确认月计划和来源事件。
supersede：用于保留旧行历史、生成新行替代当前可用行的场景，旧行进入取消/归档/停用等状态并保留 lineage。
overwrite 命中的旧行如果在保存前已被他人删除、关闭、归档、进入保护链或权限发生变化，覆盖意图失效；后端应降级为新增并提示，或返回 per-row decision 阻断本次保存。
同一次提交里 template_generate 后续又 delete_row 的行，按最终 pending operations 计算；保存前删除新增行不写 deletion_retention_events，保存后删除已存在行才写。
存在 reject 时，默认整批不提交，不静默跳过失败项；除非后续版本明确提供“跳过失败项继续”的业务设计。
```

### 5.4 权限边界

本章不新增审批流，但必须保留权限边界。

```text
editor：可删除自己有权限维护范围内的未消费误录、草稿行、个人通知隐藏；可关闭自己负责或被授权处理的风险、问题、阻碍
project admin / owner：可确认受保护对象的取消、归档、停用、项目归档、责任单位归档、成员停用、配置停用
system：可执行生命周期归档、保留期清理、source_deleted 标记、自动 inactive、后台快照保留
普通用户不得删除或停用关键主数据、项目、已消费配置、历史快照、来源事件、change_logs、operation_logs
权限不足时返回 FORBIDDEN + 业务化文案，不把 retention decision 包装成技术错误
```

当前代码角色映射：

```text
旧 viewer：按 v1.4.20 迁移为非有效项目成员；历史 viewer 只保留日志和历史展示，不得执行 delete / close / archive / cancel / void / deactivate / restore / retention confirm。
editor：可执行普通业务编辑范围内的误录删除、个人通知隐藏、风险/问题/阻碍关闭；删除只能删除自己创建的条目；不能停用关键主数据、归档项目、停用成员、停用已消费配置。
owner：可确认受保护对象的取消、归档、停用、项目归档、责任单位归档、成员停用、配置停用和恢复类动作。
company_admin：按 v1.4.20 跨项目 owner 等效权限处理，可执行 owner 级删除、归档、停用、恢复和 retention confirm，但不强行写入 project_members。
system：只能通过后台任务、迁移、生命周期服务执行自动归档、source_deleted、保留期清理和兼容回填。
```

### 5.5 保存后恢复 / 重新启用规则

删除体系必须同时约束恢复边界，避免“删不了但能随便恢复”的反向漏洞。

```text
physical_delete：不提供恢复，重新创建
cancelled task / monthly_plan_item：恢复必须作为 reactivate / reopen 新动作，重新校验当前计划、WBS、工程对象、责任主体和状态字典
closed risk / issue / obstacle：恢复走 reopen，不删除原关闭记录
archived participant_unit / project / template：恢复只影响后续新业务可选性，不回写历史快照
inactive relation：恢复必须重算依赖、开工条件、关键路径或来源映射
voided evidence：图纸、证照、验收记录、材料封样作废后原则上不恢复；应新建替代版本并保留 replaced_by_id
hidden notification：只恢复当前用户个人可见性，不改变业务预警生命周期
任何恢复动作都必须写 v1.4.14 change_logs，并写 deletion_retention_events 的 restore 类决策
```

## 6. 各对象处置规则

### 6.1 任务 tasks

当前任务是实时执行事实，不能把“删除任务”简单等同于物理删除。

```text
允许物理删除：
  未开始 / 草稿 / 误录
  progress = 0
  无子任务
  无开工条件
  无阻碍
  无验收计划
  无风险、问题、预警、通知链路
  无 task_progress_snapshots
  无 task_baseline_items / monthly_plan_items / baseline_item_id / monthly_plan_item_id
  无 project_entity_links active 关系
  无 data_lineage_links 历史映射

不允许物理删除：
  已产生进度
  已完成或曾经完成
  已进入项目基线或月度计划
  已关联验收、开工条件、阻碍、风险问题预警
  已被下游任务依赖
```

处置方式：

```text
误录任务：物理删除
未开始、progress = 0、无实际开始/完成、但已进入基线/月计划承诺的任务：不物理删除，改为 cancelled
已有进度、实际开始、快照、验收、风险问题预警或来源链的任务：不物理删除，改为 closed
已完成任务：delete 请求直接 reject，保持 completed；如确需修正完成事实，走 v1.4.14 历史事实纠错或 reopen
取消任务：status = cancelled，不进入完成率分子；不回改已发布基线和已确认月计划
关闭任务：当前代码 POST /api/tasks/:id/close 可继续承担受保护任务的关闭动作
删除受保护任务时继续返回 TASK_DELETE_PROTECTED，并提供 close_action 或 cancel_action
```

v1.4.15 需要补强：

```text
loadTaskDeleteProtectionSummary 增加 monthly_plan_item_id、task_progress_snapshots、data_lineage_links、project_entity_links、risks、issues、notifications、change_logs 消费检查
deleteTaskInMainChain 只能在 retention decision = physical_delete 时被调用
dbService.deleteTask fallback 直接 DELETE 必须被保护服务包住，禁止绕过保护
任务删除、取消、关闭、重开都写 change_logs
```

### 7.2 前端不新增复杂入口


## 8. 数据库与迁移

迁移落点：

```text
当前代码已由 server/migrations/133_v1414_change_audit_governance.sql 承载 v1.4.14 / v1.4.15 的 change_logs、operation_logs 和 deletion_retention_events 基础表。
后续如需补字段、补约束或补策略索引，新增迁移编号必须从当前最新编号之后继续，例如 server/migrations/134_xxx.sql，不再新增 133_create_deletion_retention_governance.sql，避免与已存在迁移冲突。
```

迁移内容：

```sql
create table if not exists deletion_retention_events (
  id uuid primary key default gen_random_uuid(),
  project_id uuid null references projects(id) on delete set null,
  project_name_snapshot text null,
  entity_type text not null,
  entity_id text not null,
  entity_name_snapshot text null,
  requested_action text not null,
  resolved_action text not null,
  requested_allowed boolean not null default false,
  resolved_allowed boolean not null default false,
  execution_mode text not null default 'reject',
  execution_status text not null default 'decided',
  requires_user_confirmation boolean not null default false,
  reason_code text not null,
  reference_summary jsonb not null default '{}',
  affected_entity_ids jsonb not null default '[]',
  suggested_action jsonb not null default '{}',
  actor_id uuid null references users(id) on delete set null,
  change_log_id uuid null references change_logs(id) on delete set null,
  operation_log_id bigint null references operation_logs(id) on delete set null,
  request_id text null,
  confirmed_by uuid null references users(id) on delete set null,
  confirmed_at timestamptz null,
  executed_at timestamptz null,
  created_at timestamptz not null default now()
);

create index if not exists idx_deletion_retention_events_entity
  on deletion_retention_events(entity_type, entity_id, created_at desc);

create index if not exists idx_deletion_retention_events_project
  on deletion_retention_events(project_id, created_at desc);

create index if not exists idx_deletion_retention_events_request
  on deletion_retention_events(request_id);
```

策略口径：

```text
v1.4.15 不创建 deletion_retention_policies 作为运行时依赖，避免策略同时存在于数据库和服务代码造成分叉。
本阶段权威策略写在 server/src/services/deletionRetentionGovernanceService.ts 的 typed policy registry 中，并由单元测试覆盖。
如后续要把策略管理化，另开后续章节迁移 deletion_retention_policies，并提供 seed、版本、发布和回滚规则。
```

说明：

```text
deletion_retention_events 是决策日志，不替代 change_logs
deletion_retention_events 不跟随 projects 级联删除；项目被归档、关闭或后台清理后，决策日志仍保留 project_name_snapshot 和 entity_name_snapshot
change_logs 记录业务事实变化
operation_logs 记录请求审计
data_lineage_events 记录来源链变化
迁移必须幂等：create table / create index 使用 if not exists；后续补字段使用 add column if not exists；约束变更先查 pg_constraint 再处理
全量迁移快照必须同步更新，避免新环境初始化后缺 deletion_retention_events
```

## 10. 旧对象处理

v1.4.15 不删除旧对象、旧表、旧字段、旧接口。

```text
旧物理删除接口继续保留 URL，但内部必须先走 retention decision
旧 deleted_at 字段继续有效，不强制迁移为 status
旧 status = deleted / archived / cancelled / voided 通过 v1.4.5 状态字典归一
旧 source_deleted 风险/问题/预警继续作为历史兼容来源，不重新触发升级
旧 notifications 已物理删除的记录不补回；未删除记录按 v1.4.13 lifecycle 口径接管
旧 task_baselines / monthly_plans / snapshots 不回写
旧 task_code_history、change_logs、operation_logs 不物理删除
旧 projects DELETE、members DELETE、invitations DELETE、critical_paths DELETE、pre_milestones DELETE、acceptance_catalog DELETE、drawing_review_rules DELETE 保留路由兼容，但内部统一接入 retention decision
旧 ON DELETE CASCADE 不作为业务删除语义；只在 retention decision 明确允许 physical_delete 后才允许触发
```

兼容原则：

```text
没有历史生产数据时也按新规则建设，避免后续真实数据进入后再返工
如果 live schema 缺少 deleted_at 或 lifecycle 字段，先用 status / reference check 兜底
如果旧路由仍返回 200 删除成功，但实际执行的是归档/停用/隐藏，响应 data 中应返回 resolved_action，便于前端文案解释
旧 status = deleted / archived / cancelled / voided / inactive / disabled 在普通列表默认隐藏，历史视图和只读复盘可查询
新建下拉、任务选择器、责任单位选择器、工程对象选择器默认排除 archived / inactive / disabled / voided
历史任务、历史基线、历史月计划、验收记录和报表必须优先显示当时名称快照；缺快照时显示“已停用对象”或“历史对象已不可选”，不得显示技术 ID
旧记录已被物理删除且无法补回时，不伪造历史对象；只在历史视图中显示“历史来源已删除，保留当时业务摘要”
旧 API 如果无法立即返回 RetentionDecision 新结构，至少返回 code、message、resolved_action、reference_summary 四个字段，前端按新文案处理
旧前端测试中断言“删除后列表消失”的用例必须区分 personal hide / physical_delete / archive；不能再统一按物理删除验证
```

```text
删除被任务引用的责任单位后，任务历史仍显示原责任单位，新任务下拉不再出现该单位
删除已产生业务事实的项目时，系统提示归档/完成项目，不触发级联删除任务和历史快照
删除已被图纸审查使用的审查规则时，系统提示停用规则，新图纸不再可选，历史审查仍显示原规则
批量删除 10 行任务，其中 3 行可物理删除、5 行需取消、2 行拒绝；系统展示汇总确认且默认整批不提交
恢复已归档责任单位后，新任务可重新选择该单位，历史任务不被回写
作废图纸版本后新建替代版本，历史验收仍能看到原图纸版本和作废状态
后台 dataRetentionService 清理 operation_logs 时不影响 change_logs、deletion_retention_events、快照和来源链
```

## 12. 不做内容

```text
不做完整回收站
不做普通用户可见的删除审计中心
不做所有对象的人工恢复入口
不把删除保护做成审批流程
不要求用户填写删除原因
不恢复 delay_requests / task_delay_history
不把历史快照改写成当前事实
```

## 13. 交付结果

v1.4.15 完成后，系统应具备：

```text
删除、关闭、归档、取消、作废、停用、隐藏的统一业务语义
所有关键对象删除前都有统一 retention decision
进入历史事实链路的对象不再被简单物理删除
用户仍按原业务按钮操作，不需要理解后台治理字段
旧基线、旧月计划、风险问题链、验收链、通知链、BI 快照和 AI 分析可持续解释历史
v1.4.14 的留痕、审计和高权限边界有稳定的业务动作来源
```
## 多公司空间与数据隔离统一口径

本文件执行时必须承接 `v1.4.20 权限角色与协作体系执行方案` 的多公司空间要求。除非本文件明确声明为 `system_seed`、全局字典或演示样例数据，否则所有项目级数据都必须先归属于项目，再通过项目解析到所属公司。

```text
所有新增表：优先包含 project_id；确属公司级数据时包含 company_id；确属系统公共数据时标记 scope = system_seed / global_dictionary。
所有查询：先按 currentCompanyId / company_id 隔离，再按项目权限过滤，不允许前端二次过滤替代后端隔离。
所有汇总：公司级汇总只统计当前公司项目；项目级汇总只统计当前项目；演示项目不进入真实公司汇总和真实项目统计。
所有引用：禁止跨公司引用任务、工程对象、范围维度、责任单位、图纸、证照、验收、风险、问题、预警、计划、模板沉淀和经验数据。
所有模板 / 经验数据：系统公共种子可跨公司复用；公司沉淀模板、公司经验工期、公司历史数据只能在当前公司内使用。
所有旧数据：没有 company_id 的历史数据在迁移时归入默认公司，并保留兼容读取；不得因为补公司空间而删除旧对象。
```

本文件如出现“全部项目”“公司汇总”“项目列表”“可见项目”等表述，执行层一律理解为：先限定当前公司，再按 v1.4.20 的 `owner / editor / 当前公司 company_admin / regular` 权限模型过滤。
