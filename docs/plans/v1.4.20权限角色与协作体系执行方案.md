## 0. 2026-06-01 final range-tree boundary (authoritative)

This v1.4-series plan follows the final range-tree model. There is no production history or existing user data that needs a compatibility layer.

Authoritative engineering object types are exactly: `phase / section / building / basement / floor / physical_zone / functional_area`.

The following compatibility surfaces are deleted and must not be reintroduced in runtime code, migrations, or frontend contracts:

- `zone / professional / subproject / custom` as engineering object types.
- `zone_object_id / professional_object_id` task fields.
- `project_materials.professional_object_id` and `engineering_categories.professional_object_id`.
- `legacy_object_type`, deprecated object-type arrays, legacy bridge/backfill helpers, and old scope adapter functions.
- `/api/scope-dimensions`, `scope_dimensions`, and `project_scope_dimensions` as active application surfaces.

Professional/system/domain/method semantics remain business facts through `specialty_type`, `engineering_category_id`, `standard_work_code`, template metadata, and project profile facts. They are not range-tree objects.

Any older section in this document that mentions deleted object types, deleted fields, old scope tables, or compatibility adapters is superseded by this boundary.

## 21. 多公司隔离增量落地规则

本节用于约束 v1.4.20 落地后的代码实现，不新增前端复杂操作，只把多公司空间边界沉到后端公共能力中。

```text
请求中的 companyId / X-Company-Id 只能作为候选上下文，不能作为可信事实。
所有公司级接口必须先通过 getCurrentCompanyMembership(userId, requestedCompanyId) 解析真实公司，再使用 membership.companyId 查询或写入。
所有项目级接口必须先通过 project_id 解析 projects.company_id，再要求访问用户是该项目所属公司的 active 成员；随后再判断 project owner / project editor / 当前公司 company_admin。
项目 owner 或 project_members 关系不能单独绕过公司成员关系；如果用户已不属于项目所属公司，即使 project_members 仍有旧记录，也必须拒绝业务访问。
company_admin 只在当前所属公司内等效 owner，不得跨公司访问其他公司项目。
```

工作台、邀请、加入申请的后端约束：

```text
公司搜索只返回可发现公司，不返回 hidden / invite_only 公司。
主动加入公司必须检查 companies.is_active / status / discoverability / join_policy；invite_only 公司只能通过邀请链路加入。
项目加入申请必须要求申请人已经是项目所属公司的 active 成员。
项目加入申请被审批通过前，后端再次校验申请人仍属于项目所属公司；否则不写 project_members。
项目定向邀请只能发给项目所属公司的 active 成员。
项目邀请码接受链路必须先补齐或激活 company_members，再补齐 project_members，避免“有项目成员但没有公司空间”的半隔离状态。
```

WBS 模板、工期建议、提醒通知的后端约束：

```text
wbs_templates 必须区分系统公共模板、公司模板、项目模板。
项目模板写入时必须同步写入项目所属 company_id；项目模板不可只依赖 project_id 悬空。
公司模板只能使用当前 membership.companyId 读写；系统公共模板保持 company_id = null 且只读复用。
AI 工期建议、批量工期预测、剩余工期刷新必须按任务或项目反查项目权限，不能通过 taskIds 旁路读取其他公司项目数据。
提醒偏好 project_id 为空时必须带 company_id，作为公司级偏好隔离边界。
通知列表、待办触达、关注摘要必须先按当前公司或可访问项目过滤，再校验接收人和项目权限。
```

实时协作与 WebSocket 约束：

```text
WebSocket URL 不得携带 token；生产环境必须通过 auth message 完成认证。
客户端订阅 projectIds 只是请求意图，服务端必须按认证用户逐个过滤项目权限。
subscribe 消息里的 userId 不得覆盖认证用户身份。
presence update 只能写入当前连接已授权订阅的项目；未授权项目直接忽略。
用户被移出公司或项目后，后续 HTTP 权限校验和新订阅必须立即失效；长期连接由心跳、重连和下一次订阅刷新兜底。
```

迁移与旧对象处理：

```text
已有 projects 按 137 迁移归入默认公司，不删除旧项目。
已有 project_members 只作为项目成员关系保留；读取时必须叠加项目所属公司 active membership 校验。
已有 project_invitations / project_direct_invitations / project_join_requests 必须按 projects.company_id 回填 company_id。
已有项目 WBS 模板必须按 projects.company_id 回填 wbs_templates.company_id。
companies 需要补齐 is_active / discoverability / join_policy；旧公司默认 active + invite_only + approval_required，避免突然暴露给搜索。
```

本章明确采用待修正清单的权限结论：

```text
项目角色收敛为 owner / editor
viewer 不再作为 project_members 的有效项目角色
company_admin 是公司内角色，访问当前公司内任意项目时按 owner 等效权限校验，但不强行写入 project_members
editor 可日常编辑，但删除只能删除自己创建的条目
owner / company_admin 可删除全部允许删除的项目内条目
公司成员未加入项目时，只可在工作台 / 项目目录看到允许发现的项目基础卡片，不可进入项目详情和业务接口
无公司用户可创建公司、加入已有公司或查看产品预览，不强制邀请码
开始使用页只保留创建公司、加入已有公司、查看产品预览三个入口
加入项目必须通过有效邀请链接、邀请码或项目加入申请，项目邀请默认只授予 editor
权限以后端为准，前端隐藏或置灰只是体验，不替代后端校验
```

本章不沿用旧文件中 `owner / editor / viewer` 三项目角色模型，也不沿用 `company_admin 未加入项目时只读` 的旧口径。产品入口遵循国内主流 SaaS 逻辑：先有公司空间，再有项目权限；项目真实业务数据只对项目成员或当前公司管理员开放。

## 4. 多公司空间、工作台入口与产品预览

本节用于补齐国内主流产品常见的 `公司 / 项目 / 个人入口` 三层关系，避免新用户注册后直接面对空白或无权限墙，也避免把公司成员误当成项目成员。

### 4.1 设计原则

```text
账号可以属于多个公司
公司是租户边界，项目必须归属于公司
项目真实业务数据只对项目成员和当前公司 company_admin 开放
项目可发现性不等于项目业务权限
新用户不能因为没有项目权限而进入空白页
只读产品预览使用样例数据，不接触真实客户项目
```

### 4.2 数据底座

已由当前仓库 `137_company_workspace_isolation.sql` 落地的底座：

```text
companies：公司 / 租户主表
company_members：账号与公司的成员关系
projects.company_id：项目所属公司
users.last_active_company_id：用户上次进入的公司
project_visibility：private / company_visible / invite_only
默认公司迁移：旧 projects 归入默认公司，旧 users 写入 company_members
```

v1.4.20 本章仍需补齐的增量：

```text
company_join_requests：公司加入申请
project_join_requests：项目加入申请
company_invitations：公司邀请码 / 邀请链接
project_direct_invitations：定向项目邀请，用于工作台待处理邀请、接受、拒绝
demo_projects：只读产品预览配置或样例项目标记，不进入真实公司统计
companies.discoverability：searchable / invite_only，公司是否可被搜索发现
companies.join_policy：approval_required / invite_only，公司加入方式
/api/workspace 聚合接口与 payload 契约
viewer / admin 旧项目角色迁移日志
currentCompanyId / X-Company-Id 上下文安全收口
```

新增工作台、加入申请、演示项目相关表的访问策略必须在 v1.4.20 增量迁移中一并定稿：

```text
默认由 Express 后端作为唯一写入与读取事实源，前端不得直连 Supabase 操作 company_join_requests / project_join_requests / company_invitations / project_direct_invitations / demo_projects
如开启 RLS，策略只允许 service_role 或后端受控角色访问；普通 authenticated 用户不得绕过后端查询申请表或演示项目配置
所有接口返回前仍必须按 currentCompanyId、company_members、project_members.permission_level 和 project_visibility 过滤
```

角色归属：

```text
company_admin：公司内管理员，只在所属公司内具备跨项目 owner 等效能力
regular：公司内普通成员
owner / editor：项目内角色
```

`users.global_role` 作为旧兼容字段保留读取，但 v1.4.20 落地后公司级权限以 `company_members.role` 为准。执行期可以短期把旧 `users.global_role = company_admin` 迁移为默认公司下的 `company_members.role = company_admin`。

### 4.3 登录后的统一入口

新增统一入口：

```text
/workspace
```

登录后不直接进入某个项目，也不默认进入公司驾驶舱，而是进入工作台。工作台按用户状态展示不同内容：

```text
无公司：显示开始使用
有一个公司：进入该公司工作台
有多个公司：默认进入上次公司，并提供公司切换弹层
有项目权限：展示我的项目和最近访问
有邀请：展示待处理邀请
有可发现项目：展示可申请项目
```

普通项目成员的 `/workspace` 内容固定为：

```text
最近访问项目：最多 3 个快捷卡片
我的项目列表：所有已加入项目，按最近活跃排序
待处理：邀请 / 加入申请状态
可申请项目：company_visible 且未加入的项目
```

项目卡片点击规则：

```text
点击已加入项目卡片 -> /projects/:id/dashboard
点击可申请项目卡片 -> 申请加入或查看基础卡片，不进入项目详情
```

`/company` 保留为公司驾驶舱，但只给当前公司 `company_admin` 或具备公司级汇总权限的用户访问。普通公司成员访问 `/company` 时，应回到 `/workspace`，并用业务化提示说明“公司驾驶舱仅管理视角可见”。

### 4.4 开始使用与公司切换

无公司用户看到“开始使用”，不强制邀请码：

```text
主 CTA：创建公司
次 CTA：加入已有公司，支持输入邀请码 / 搜索可发现公司
底部链接：查看产品预览
```

用户如果有邀请链接，应从邀请链接直接进入邀请预览和确认流程，不作为开始使用页的显式选项。

登录 / 注册入口（LoginDialog）必须暴露使用邀请码登录的快速入口，避免持有邀请码的新用户绕到工作台再进入加入流程：

```text
LoginDialog 注册 tab 底部追加"我有邀请码"链接
点击后切换为邀请码登录模式，输入项目邀请码 / 公司邀请码
登录或注册成功后，根据邀请码所属类型直接 Navigate 到 /join/:code 或公司加入确认页
该入口不替代 /workspace 内的"加入已有公司"，两条路径并存
```

加入已有公司 Sheet 的内部结构必须优先安抚低信息用户，避免新用户在"搜不到任何东西"的搜索框里卡住：

```text
Sheet 第一区块：等待邀请
  文案：如果有人邀请你，请让对方发送邀请链接给你，或告诉你邀请码。
  入口：输入邀请码 + 提交按钮
Sheet 第二区块：主动搜索
  文案：知道公司名也可以搜索并提交加入申请。
  入口：搜索框 + 仅展示可被发现公司的结果
两区块顺序固定为等待邀请在前、主动搜索在后；不允许直接展示空搜索框作为唯一入口
```

公司可发现规则必须由后端字段决定：

```text
companies.discoverability = searchable：可通过 GET /api/companies/search?q= 搜到公司名称，提交加入申请后进入 pending
companies.discoverability = invite_only：不可通过搜索返回公司名、项目名、管理员信息，只能通过有效邀请码 / 邀请链接加入
companies.join_policy = approval_required：加入申请需当前公司 company_admin 审批
companies.join_policy = invite_only：不接受主动申请，只接受邀请码 / 邀请链接
```

创建公司成功后不回到空工作台，而是直接弹出“创建第一个项目”引导。引导必须接入 v1.4 系列的底座能力，不恢复旧 WBS 模板页面：

```text
创建公司成功
-> 创建第一个项目
-> 填项目基础信息
-> 选择工程类型 / 建筑类型 / 结构类型
-> 初始化工程对象和项目范围维度
-> 基于分部分项标准库生成初始计划树草案
-> 用户确认后进入共享计划树 / 基线草案
```

该流程使用：

```text
v1.4 工程对象主数据
v1.4.1 项目范围维度
v1.4.7.1 共享计划树
v1.4.7.2 分部分项标准库与模板生成体系
```

前端文案使用”生成初始计划树草案”或”按工程类型生成计划树草案”，不得使用”模板填充 WBS”或引导用户回到已移除的 WBS 模板页面。

创建公司与创建第一个项目分两次提交，避免一次失败回退整段引导：

```text
公司创建成功立即写入 companies / company_members，用户当下就成为该公司 company_admin，可在工作台 ContextStrip 看到当前公司
创建项目引导是公司创建之后的可选续作步骤，不与公司创建绑定为同一事务
任意创建项目步骤失败（工程类型未填、计划树草案生成失败、网络异常等）：
  公司已创建状态保留，不回滚
  引导 Sheet 可关闭，关闭后落回 /workspace 的 EMPTY_PROJECTS 状态
  EMPTY_PROJECTS 状态必须暴露”创建项目”显式按钮，让用户再次进入引导
  toast 报告失败原因，按 v1.3 错误反馈规范展示
不允许：失败时把用户卡死在引导 Sheet 内不可退出
不允许：失败时回滚公司，迫使用户重新创建公司
```

等待审批期间，工作台应展示产品预览入口卡片：

```text
等待审批期间，先了解 WorkBuddy 能为你的项目做什么
```

已加入公司但没有可见项目时，工作台空状态固定为：

```text
暂无可查看的项目。请联系公司管理员将你加入项目，或等待项目邀请。
```

若公司信息中存在管理员联系方式，空状态展示管理员姓名 / 手机 / 邮箱；若没有联系方式，展示输入项目邀请码和查看产品预览入口。该状态不得展示项目概要、健康度、进度、风险或公司驾驶舱数据。

公司切换不单独做冷启动页面。用户已有当前公司时，通过工作台顶部公司名或头像菜单打开切换弹层。弹层背后可以是当前公司工作台或公司驾驶舱的模糊背景；如果用户还没有公司，则直接展示开始使用，不显示公司切换弹层。

### 4.5 项目可发现性

项目可见性固定为：

```text
private：只有项目成员和当前公司 company_admin 可发现
company_visible：当前公司成员可在工作台 / 项目目录看到基础卡片，并可申请加入
invite_only：只能通过邀请链接或邀请码发现
```

公司成员未加入项目时，只能看到基础卡片：

```text
项目名称
项目类型
项目阶段
项目负责人
项目位置或简称
申请加入入口
```

不得展示：

```text
项目健康分
进度偏差
任务明细
风险问题
验收情况
图纸证照材料详情
报表数据
关键路径和预警链路
```

### 4.5.1 邀请类型固定口径

v1.4.20 同时保留“通用邀请码”和“定向邀请”，两者不能混用：

```text
project_invitations：既有项目通用邀请码 / 链接，用户持码后主动验证和加入；不进入工作台 pendingInvitations
company_invitations：新增公司通用邀请码 / 链接，用户持码后主动验证和加入公司
project_direct_invitations：新增定向项目邀请，必须包含 invitee_user_id / status，用于 /api/workspace.pendingInvitations
```

工作台“待处理邀请”只来自 `project_direct_invitations`，不能从既有 `project_invitations` 通用码临时拼装。通用码没有目标用户和拒绝状态，不能表达“待我处理”。

```text
project_direct_invitations 状态：pending -> accepted / declined / revoked / expired
accepted / declined / revoked / expired 为终态
invitee 只能接受或拒绝自己的 pending 定向邀请
created_by / owner / 当前公司 company_admin 可撤销 pending 定向邀请
接受跨公司项目定向邀请时，先补齐目标公司 company_members regular，再补 project_members editor，并切换 users.last_active_company_id 到目标公司
```

公司邀请码本期必须建设 `company_invitations`，不再保留“若不建设”的执行分支：

```text
company_invitations 状态：active / revoked / expired
invite_only 公司只能通过有效 company_invitations 或公司管理员直接添加加入
searchable + approval_required 公司可通过搜索提交 company_join_requests
POST /api/companies/join 必须同时支持 company invitation code 和 searchable 公司申请
```

### 4.6 只读产品预览

只读产品预览用于解决新产品冷启动和价值解释，不作为真实项目权限绕行。

推荐样例：

```text
海棠里住宅二期总承包项目
```

产品预览必须展示 WorkBuddy 区别于普通 `BI + 表格` 和通用项目管理产品的核心能力：

```text
工程对象主数据：分期、标段、楼栋、楼层、区域、专业被任务、图纸、验收、风险复用
共享计划树：项目基线、月度计划、任务列表共用表格体验，但语义不同
三层计划 + 实时执行：基线是承诺快照，月计划是周期计划，任务列表是实时执行事实
进度驱动治理：进度填报自动驱动实际开始 / 完成、偏差、健康度和预警
开工条件 / 阻碍：系统根据事实判断，不要求用户维护大量表单
图纸 / 证照 / 验收联动：任务能看到受哪些资料约束、影响哪些验收
风险问题预警链：风险、问题、预警基于来源事实升级和建议关闭
偏差原因分析：展示关键路径、阻碍、验收、责任单位、连续未更新等现场原因
```

产品预览约束：

```text
产品预览为只读交互式预览，用户可以点击、展开、筛选、切换视图，但不可编辑，不进入真实公司统计
```

产品预览实现机制：

```text
后端：独立 demo_projects 表与预置 seed 数据，不与真实 projects 表混用统计
URL：统一使用专属 /demo 路由；/demo 内部可复用项目页组件，但不得伪装成真实 /projects/:id
权限：所有写入接口对 demo 项目命名空间直接返回 403 或软拦截，前端组件读取只读标记后禁用编辑按钮、隐藏保存动作、阻断快捷键写入
隔离：演示项目的筛选 / 展开 / 视图切换等 UI 状态使用前端临时存储（sessionStorage 或内存），多用户互不影响，刷新后回归默认
退出：演示项目内置返回工作台入口，避免用户被困在只读项目里
不允许：演示项目数据进入 companyHealth、companyCockpit、reports、dashboardSummary 等任何真实公司汇总
```

演示项目页面必须明确传达"产品功能预览，不可复制带走"的边界，避免用户预期偏差：

```text
演示项目顶部固定渲染产品预览说明条：
  文案：这是产品功能预览，仅供了解 WorkBuddy 能力，不可编辑也不可复制为真实项目。如需开始使用类似工程类型的项目，请创建公司后选择对应工程类型。
  视觉：信息 tone，不抢主内容权重，常驻不可关闭
说明条之外不再使用 toast / dialog 重复提醒，避免打扰浏览
点击说明条中的"创建公司"链接 -> Navigate 到 /workspace 的开始使用页或公司创建引导
```

### 4.7 新用户真实路径

企业负责人：

```text
注册 -> /workspace -> 查看产品预览 -> 创建公司 -> 创建真实项目 -> 成为该公司 company_admin 和项目 owner
```

被邀请的项目成员：

```text
打开邀请链接 -> 登录 / 注册 -> 查看公司名、项目名、邀请人、拟加入角色 -> 接受邀请 -> 进入 /workspace 的我的项目
```

普通自然注册用户，准备加入公司或项目：

```text
注册 / 登录 -> /workspace -> 无公司开始使用 -> 输入公司邀请码 / 项目邀请码，或打开别人发来的邀请链接
无邀请码时，可搜索允许被发现的公司并提交加入申请
公司不可被发现时，只能等待管理员邀请或查看产品预览
申请通过前不进入公司驾驶舱，不展示项目目录，不读取真实项目数据
加入公司后成为 company regular，再根据项目可见性看到可申请项目或接受项目邀请
```

公司普通成员但未加入项目：

```text
登录 -> /workspace -> 查看最近访问项目 / 我的项目 / 待处理 / 可申请项目 / 产品预览
不能进入公司驾驶舱，不能读取项目真实业务数据
```

多公司用户：

```text
登录 -> 进入上次公司工作台 -> 通过公司切换弹层切换公司 -> 项目列表、通知、成员、驾驶舱、报表全部按当前公司刷新
```

### 4.8 边界用户路径与异常状态

未登录用户打开邀请链接：

```text
打开邀请链接 -> 看到极简邀请预览 -> 登录 / 注册 -> 回到邀请确认
登录过程不得丢失邀请 code、companyId、projectId 和拟加入角色
```

已有公司 A 的用户收到公司 B 或项目 B 邀请：

```text
接受邀请前必须弹 ConfirmDialog 二次确认：
  标题：接受邀请将切换到 海棠地产
  说明：你当前活跃公司为 万科地产。接受后会切换到 海棠地产，当前工作上下文（页面、筛选）将刷新。
  操作：[暂不接受]（取消）/ [接受并切换]（默认按钮）
确认后再调用接受邀请接口：加入公司 B
若是项目邀请，同时加入公司 B 和项目 B
接受成功后切换 currentCompanyId 到公司 B，进入 /workspace 的公司 B 上下文，并 toast 提示"已切换到 海棠地产"
不得把公司 B 的项目混入公司 A 工作台
不得在用户未确认前直接切换公司
```

项目邀请自动补齐公司成员关系：

```text
用户不是目标公司成员时，接受项目邀请后先创建 company_members regular
再创建 project_members editor
项目成员关系不得脱离公司成员关系单独存在
```

加入申请状态：

```text
申请加入公司或项目后，工作台展示待处理 / 已拒绝 / 可重新申请
待处理和已拒绝状态不展示真实项目数据
```

公司不可发现：

```text
不可发现公司在搜索和申请入口不返回公司名、项目名、管理员信息
只提示未找到可申请的公司或邀请已失效
```

用户被移出公司或项目：

```text
被移出当前公司时，前端清理 currentCompanyId 和相关缓存，回到 /workspace
被移出当前项目时，前端退出项目详情，回到当前公司工作台
后端立即拒绝后续业务接口和实时订阅
```

公司管理员保护：

```text
每个公司至少保留一个 company_admin
不能移除、降级或转让导致公司没有 company_admin
company_admin 保护不能由项目 owner 替代
```

外部参建方用户：

```text
参建单位是业务责任主体，不是权限主体
外部人员需要被邀请为某公司成员并加入项目后，才可获得项目权限
不能因为责任单位名称、联系人名称或任务责任人文本自动获得账号权限
```

### 4.9 跨公司 URL 直接访问的业务化拦截

用户可能通过书签、历史记录、外部分享链接，直接访问不属于当前公司的项目详情 URL。前端不能仅依赖后端 403 toast，必须给出业务化阻断与回路：

```text
后端：所有项目级 GET 必须先校验 project.company_id == currentCompanyId，否则返回 403 PROJECT_NOT_IN_CURRENT_COMPANY
前端：项目路由加载阶段命中该错误码后，不展示通用 toast，而是渲染业务化阻断页：
  - 标题：该项目不在当前公司
  - 说明：项目所在公司与你当前活跃公司不同。可切换公司或返回工作台。
  - 操作：[切换到该项目所在公司]（若用户为该项目所在公司成员）/ [返回工作台]
  - 不展示项目名、健康分、进度、负责人等真实业务字段
前端：被移出公司或项目时，复用同一业务化阻断页 + 自动清理 currentCompanyId / 缓存
不允许：直接 Navigate 回 /workspace 或 /company 而不告知用户原因
```

切换公司命中跨公司项目的情况（用户切换公司后，原 URL 不再有效）：

```text
公司切换成功后，若当前 URL 仍为 /projects/:id/*，立即重新校验当前公司可见性
不可见时静默 Navigate 回 /workspace，并 toast 提示"已切换到 {新公司}"
可见时保持当前页面，仅刷新数据
```

登录回跳避免误命中业务化阻断页：

```text
LoginDialog 关闭与会话恢复路径必须先调用 resolveLoginRedirect（v1.4.20.1 §3.3 定义）
若 redirect 目标项目属于用户其他已加入公司，自动切换 currentCompanyId 后再跳转
若目标项目不属于用户任何已加入公司，业务化提示后 fallback 到 /workspace 或 /company
不允许：登录后直接 Navigate 到目标 URL，让用户撞业务化阻断页
```

### 4.10 现存数据迁移与默认公司

当前仓库已经通过 `137_company_workspace_isolation.sql` 建立默认公司、公司成员和项目 company_id 底座。v1.4.20 上线前必须先复核 137 是否已成功执行，再补本章增量迁移，确保老用户登录后能找到自己的项目。迁移失败的方案不允许发布。

默认公司定义：

```text
公司名：默认公司（部署时可由运维改名为客户公司名，避免品牌错乱）
ID：固定常量或环境变量注入，迁移脚本与运行时一致
角色归属：
  现存 globalRole = company_admin 用户 -> 默认公司 company_admin
  现存 globalRole = regular 用户 -> 默认公司 regular
项目归属：
  若仍存在 projects.company_id 为空的数据，填默认公司 ID
  projects.owner_id 同步落到 project_members.permission_level = owner
  project_members.permission_level 是项目角色数据库权威字段；前端 DTO 中的 role / myRole 只能作为展示派生字段，不得反向作为权限事实源
  现存 project_members.permission_level = viewer 视为已废弃，不得自动升级为 editor；迁移时先保留历史日志，再从 project_members 删除或迁入专用历史表，不得继续保留 viewer 权限事实
项目可见性：
  以当前 137 底座为准，新项目默认 project_visibility = private
  若仍存在 project_visibility 为空的数据，默认填 private，不批量放大为 company_visible
  company_visible 必须由 owner / 当前公司 company_admin 明确开启；invite_only 只能通过有效邀请链接或邀请码发现
```

迁移流程：

```text
1. 部署前导出现存 users / projects / project_members 备份
2. 执行迁移脚本：
   - 若 137 未执行，先执行公司空间底座迁移；若 137 已执行，只做校验和缺口补齐
   - 校验默认公司 companies 记录、company_members、projects.company_id、users.last_active_company_id、project_visibility 是否完整
   - 批量补齐 project_members owner 关系，确保 projects.owner_id 与项目 owner 成员一致
   - viewer 成员先写迁移日志，再从 project_members 删除或迁入专用历史表，不自动转 editor
   - viewer 邀请置为失效
3. 校验脚本：对比迁移前后项目数、可见用户数、角色分布，差异写入日志
4. 切换 RootRedirect 默认导向（权限系统启用后所有已登录用户 -> /workspace；company_admin 通过工作台进入公司驾驶舱）
5. 灰度放量观察 24 小时，确认无大规模"找不到我的项目"反馈再全量
```

幂等与回滚：

```text
迁移脚本必须可重复执行：检查目标记录已存在则 skip，不重复写入
迁移失败回滚：保留备份与版本号，可一键回到迁移前状态
迁移期间应用降级运行：前端继续按旧 globalRole 渲染 /company；新工作台路由仅在迁移完成后启用
不允许：迁移半成品状态对全部用户开放
```

迁移完成判定：

```text
所有现存 users 都已写入至少一条 company_members 记录
所有现存 projects 都已填 company_id
所有 project_members.permission_level 已映射到 owner / editor，无 viewer 残留；不存在新增 project_members.role 权限事实字段
所有 projects.owner_id 都存在对应 active owner 项目成员；company_admin owner 等效不能替代项目自身必须存在 owner 的完整性要求
RootRedirect 切换为统一进入 /workspace，老用户登录后能在工作台看到全部历史项目；company_admin 可从工作台进入 /company 公司驾驶舱
```

## 5. 权限角色模型

### 5.1 公司角色

公司角色固定为：

```text
company_admin：当前公司管理员
regular：当前公司普通成员
```

`company_admin` 权限：

```text
可查看当前公司驾驶舱全部项目
可查看当前公司跨项目汇总
可重置用户密码
访问当前公司内任意项目时后端按 owner 权限校验
不强行写入 project_members
前端展示“公司管理员”，并解释其拥有项目 owner 等效能力但不是实际项目成员
```

`regular` 权限：

```text
只可进入已加入项目的详情和业务接口
未加入项目时只能在 /workspace 或项目目录看到可发现项目的基础卡片
加入公司或项目可通过邀请链接、邀请码、项目加入申请或管理员添加
```

### 5.2 项目角色

项目角色收敛为：

```text
owner：项目负责人 / 项目管理员
editor：编辑成员
```

不再保留：

```text
viewer：不再作为 project_members 的有效项目角色
admin：旧命名兼容读取为 owner，前端不再展示
```

角色语义：

```text
owner：成员管理、高权限治理、审批、全部允许删除动作、项目级关键操作
editor：日常业务录入、编辑、保存、提交；删除仅限自己创建的条目
company_admin：当前公司内跨项目 owner 等效，但不写入项目成员关系
regular 非成员：工作台 / 项目目录基础卡片预览，不可进入项目详情和业务接口
```

字段事实源：

```text
数据库项目角色权威字段固定为 project_members.permission_level
project_members.permission_level 只允许 owner / editor；旧 admin 在迁移期读取为 owner，迁移后写回 owner
不得新增或依赖 project_members.role 作为权限事实源；若历史代码、DTO 或前端类型里存在 role，只能由 permission_level 派生展示
ProjectPermissionLevel 执行期收敛为 owner / editor；无项目权限返回 null / no_access，而不是 viewer
前端只读态用 accessState / readonlyReason / canEdit=false 表达，不再用 viewer 伪装成只读角色
viewer 仅作为历史迁移标签或旧记录展示文案存在，不进入新权限判断
```

### 5.3 责任主体与权限主体

```text
责任人：任务或事项由谁推进，可自由输入，也可关联项目成员
责任单位：任务或事项属于哪家参建单位，必须来自 participant_units
项目成员：拥有登录账号和项目权限的人
项目角色：owner / editor
公司角色：company_admin / regular
```

责任人自由文本不能自动获得项目权限，责任单位也不能成为登录权限主体。

## 6. 权限矩阵

### 6.1 可见性

```text
company_admin：当前公司级汇总和当前公司项目业务接口可见全部项目
regular + owner/editor：可进入已加入项目
regular 非成员：只能在工作台 / 项目目录看到可发现项目的基础卡片，不可进入项目详情
匿名用户：只能访问登录、注册、邀请码校验、健康检查等白名单接口
```

后端要求：

```text
业务详情、汇总、导出接口必须先按 company_id 隔离，再按 getVisibleProjectIds 或 requireProject* 过滤
项目目录可以返回 regular 非成员的基础预览字段，但不得返回业务数据
前端项目目录隐藏详情入口只是体验，后端必须 403 拦截
/api/projects 这类项目列表接口不得先读取全量项目再 JS 过滤；必须按 visibleProjectIds 查询可见项目集合，权限旁路仅限测试/迁移兼容
```

### 6.2 读取

```text
owner/editor/current-company company_admin：可读项目业务数据
regular 非成员：只读项目基础预览，不可读业务数据
旧 viewer 成员：迁移后不再作为成员读取权限，历史展示按旧对象处理
```

### 6.3 写入

```text
owner/editor/current-company company_admin：可执行日常业务写入
regular 非成员：不可写入
旧 viewer：不可写入，迁移后不再作为项目成员
```

日常写入包括：

```text
任务列表编辑保存
项目基线草案编辑保存
月度计划草案编辑保存
工程对象、工程分类、范围对象维护
开工条件、阻碍、依赖维护
风险、问题、预警业务处理
图纸、证照、验收、材料专项维护
责任人自由输入和责任单位选择
导入数据、模板生成、智能展开、工期建议采纳
```

### 6.4 删除

删除权限必须按待修正清单 ROLE-4 收口：

```text
owner：可删除全部允许删除的项目内条目
company_admin：当前公司内跨项目 owner 等效，可删除全部允许删除的项目内条目
editor：只能删除自己创建的条目
regular 非成员 / 旧 viewer：不可删除
```

删除仍必须交给 v1.4.15 判断真实处置：

```text
可物理删除
软删除
取消
停用
归档
拒绝删除
```

权限允许不等于一定删除成功。已被引用、已进入链路或受历史保留约束的数据，仍按 v1.4.15 处理。

### 6.5 管理与审批

管理动作：

```text
添加、移除项目成员：owner / company_admin
调整成员权限：owner / company_admin
转让 owner：owner / company_admin
撤回邀请码：owner / company_admin
停用或恢复关键主数据：owner / company_admin
历史事实修正、冻结后修正：owner / company_admin
```

审批动作：

```text
editor：可发起审批申请
owner / company_admin：可 approve / reject
```

本章不建设完整 OA 审批中心，只固定统一审批边界和审批记录底座。

### 6.6 导出与统计

```text
项目内导出：owner/editor/current-company company_admin 可导出
regular 非成员不可导出业务数据
公司汇总：company_admin 可看当前公司全部项目，regular 只看自己参与项目或项目基础预览
Dashboard / Reports / CompanyCockpit：统一使用后端过滤后的项目集合
```

## 14. 后续模块接入规则

后续任何新增业务模块必须按以下规则接入：

```text
1. 判断是否项目级数据；如果是，表必须有 project_id 或可解析 project_id
2. 判断是否公司级数据；如果是，表必须有 company_id 或可由 project_id 解析 company_id
3. GET / summary / export 使用 requireProjectMember 或 visibleProjectIds，并先按 company_id 隔离
4. POST / PUT / PATCH 使用 requireProjectEditor
5. DELETE 使用 requireProjectEditor + created_by + v1.4.15 retention decision
6. 成员、审批、归档、恢复、高权限治理使用 requireProjectOwner
7. 前端用 usePermissions(projectId)，不写第二套角色判断
8. 前端不得再新增 viewer 角色入口
9. 邀请默认只能授予 editor
10. 统计、健康、报表、公司驾驶舱必须使用后端按当前公司和项目权限过滤后的项目集合
11. 工作台 / 项目目录只能展示当前公司范围内的可发现项目
12. 共享计划树相关模块必须走 v1.4.7.1 commit / mergeGroup / presence / conflict 语义
```

新增模块不得发明“负责人 / 审批人 / 管理员 / 超级用户”等未映射角色。确实需要更细权限时，先归入 `read / write / manage / approve / delete_own / delete_any / export` 动作，再由本章统一扩展。

## 多公司空间与数据隔离统一口径

本文件是 v1.4 系列多公司空间与数据隔离的主控文件。执行时以 `companies / company_members / projects.company_id / users.last_active_company_id / project_visibility` 为底座，所有项目级数据必须先归属项目，再通过项目解析到所属公司。

```text
所有项目级接口：先校验 currentCompanyId / X-Company-Id，再校验项目成员、项目 owner 或当前公司 company_admin。
所有公司级汇总：只统计当前公司可见项目；不得把其他公司项目混入公司驾驶舱、工作台、报表、风险问题、通知和健康度。
所有项目目录：非项目成员只能看到 company_visible 项目的基础卡片，不能读取任务、计划、图纸、证照、验收、风险、问题、预警、材料等业务数据。
所有后台任务：系统定时任务可跨公司批处理，但人工触发必须具备系统运维权限或当前公司管理权限，并写入审计。
所有旧数据：迁移时归入默认公司，不删除旧对象；users.global_role 仅作为兼容字段，最终公司角色以 company_members.role 为准。
所有公司级用户偏好：当 project_id 为空时必须使用 company_id 作为隔离边界；同一用户在不同公司的提醒偏好、工作台偏好、视图偏好不得串写。
```

WBS 模板与模板治理接口必须额外区分三类作用域：

```text
系统公共模板：project_id 为空，且 catalog_scope 属于 national / global / system / system_seed / global_dictionary，或 is_builtin = true，或 standard_catalog_code 不为空；可跨公司只读复用结构。
公司模板：project_id 为空，但 company_id = currentCompanyId；只能在当前公司读取、治理和生成，不得被其他公司看见。
项目模板：project_id 不为空；必须先通过项目解析 company_id，再按 currentCompanyId 和项目权限过滤。
```

`wbs_templates` 必须补 `company_id` 字段和数据库触发器：当模板带 `project_id` 写入时自动回填所属公司；已有项目模板由 `projects.company_id` 回填；真正系统公共模板保持 `company_id = null`。`/api/planning/wbs-templates` 与 `/api/wbs-template-governance` 不得再把所有 `project_id IS NULL` 模板视为全局可见。

经验工期与模板结构分开隔离：

```text
模板结构可以存在系统公共模板、公司模板、项目模板三类作用域。
duration_benchmarks 必须带 company_id；当前公司 benchmark 优先，company_id 为空的 benchmark 只能作为系统公共兜底。
duration_suggestion_overrides 必须按 project -> company -> system global 三层隔离；project_id 不为空时只服务对应项目，project_id 为空且 company_id 不为空时只服务当前公司，project_id/company_id 都为空时才是系统公共兜底。
task_duration_forecasts 必须带 project_id；读取和刷新都必须先通过任务解析项目，再校验当前公司和项目权限。
durationSuggestionService 读取 template reference_days 时，必须确认模板属于当前项目、当前公司或系统公共模板，不得凭模板 ID 跨公司读取参考工期。
```

## 2026-05-16 代码收口记录
